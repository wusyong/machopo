# dom_js

DOM（`dom`、`dom_api`）的 JS 前端（V8），頁面的 document 都是它的（對應 Blink 的 `bindings/core/v8`）。`machopoDom`（`install_machopo_dom`）在測試的 realm 裡建 DOM 的 document，`bench.py calls` 也經過它量（`tests/it/bench.rs`）；測試在自己的 realm 裡裝上 interface 物件。

不寫 `unsafe`（`#![forbid(unsafe_code)]`）：要 `unsafe` 的在 `bindings`（isolate 的狀態和它的借法 `StateScope`、`NoGc`，`set_isolate_state_with_embedder_heap`、`wrap`），論證在 `crates/bindings/soundness.md`。

## 一次呼叫

先看誰拿著什麼：

```text
V8 的 callback（templates.rs 的 Member<M>）
└─ V8Front<'a, 's, 'i, 'r>：scope（isolate 的狀態是 DOM 的）、參數、Call（結果的格子、操作前建好的 wrapper）
   ├─ 1. 操作外：轉參數（可能跑 script、丟例外）
   ├─ 2. read / mutate：從 scope 借出狀態（DOM、快取、layout），scope 被佔住
   │     └─ V8Op<'o, 's, 'i, 'r>：NoGc、參數、&mut Call、快取
   │           └─ Dom::read / Dom::mutate 的 Cx<'_, 'gc>：成員的函式在這裡跑
   └─ 3. 操作後（finish）：結果變成 V8 的值，沒有 wrapper 的節點建一個
```

- `'s`、`'i`：V8 的 handle scope 和它的 isolate（rusty_v8 的 `PinScope<'s, 'i>`），`Local<'s, _>` 活到 callback 結束；
- `'a`：front 借 scope 和參數多久（一次 callback）；
- `'r`：回傳值的（property callback 的 `ReturnValue` 有自己的 lifetime）；
- `'o`：一次操作借 front 多久，`V8Op` 只活在操作裡；
- `'gc`：DOM 的操作裡的物件（`for<'gc>` 的 closure），帶不出操作，所以操作外拿著的節點都是 wrapper 或 root。

拿著狀態的只有第 2 步，那時 scope 被佔住，所以 V8 不會在裡面配置、GC（下面的「V8 不在 DOM 的操作裡配置」）。

**參數和結果單純的成員走另一個 front**（`info_front.rs` 的 `InfoFront`、`templates.rs` 的 `InfoMember<M>`，`bindings::StateInfoMethod`）：`dom_api` 標成 `TypedMember::PLAIN` 的（物件的 getter、setter、method，參數是字串、數字、布林、節點和 DOM 的其他物件，callback、`any` 的值、rest、個數不定的節點或字串，以及操作前整個讀成 DOM 的值的（sequence、形狀特別的 dictionary、structured clone、keyframes：每個在當場建的 scope 裡由 `V8Front` 的那段程式讀），結果是這些、null 或沒有；表上除了會讓 script 跑的、要找別的 realm 的 window 的和 legacy factory 之外的所有 getter、setter、method、constructor、static），callback 只拿 V8 的 `FunctionCallbackInfo`（`bindings::StateInfo`），像 Blink 產生的 callback：

```text
V8 的 callback（templates.rs 的 InfoMember<M>）
└─ InfoFront<'s>：只有 info
   ├─ 1. 操作外：字串參數原地借得到的（ASCII 的字面值）直接拿，數字和布林本身直接讀，節點和物件的參數確認是 wrapper：都只用 isolate
   ├─ 2. read / mutate：從 info 借出狀態
   │     └─ InfoOp<'o, 's>：InfoNoGc（只要 isolate 的 unwrap、回傳，和 OpReturn）、receiver、快取
   └─ 3. 操作後：操作裡給不出去的結果（成員自己的區域變數）做完；沒有就結束
```

一定會建新節點的成員（`createElement`、`createTextNode`、`cloneNode`…）在操作前先建好 wrapper（`InfoFront::prepare_new_node`：這時才建 scope；`createElement` 的 interface 照名稱猜，`foresee_element` 只看名稱；`cloneNode` 的先開一個讀的操作看 `this` 是哪個 interface），它是成員的區域變數（`RetType::Prepared`），操作裡 `InfoOp::ret_new_node` 收下它、直接接上節點：沒有 root、沒有操作後的事。interface 猜錯的（大寫的名稱、XML 文件的元素）那個 wrapper 浪費掉，照沒有 wrapper 的節點處理。

callback 參數（listener、event handler 屬性的值、`requestAnimationFrame` 的）就是那個參數的 handle（`FrontTypes::Callback` 是 `Local<Value>`）：操作前只確認它是物件或函式，DOM 的函式在操作裡把它原樣交回 `InfoOp::store_callback`（寫進 listener 的邊）或 `same_callback`（和邊指的物件比位址，不建 `Local`），front 不留它。只有布林、數字、字串成員的 dictionary（`removeEventListener` 的 options）沒給時是預設值；給了的話成員交給 `V8Front` 讀（getter 可能執行 script），讀出來的是值，或成員的值本身的 handle（`addEventListener` 的 `signal`、`CustomEventInit` 的 `detail`：`V8Front` 的 scope 不開 handle scope，handle 活到 callback 返回）。

`any` 的參數就是參數的 handle（`FrontTypes::Any`；undefined 要換成 null 時才建 scope），`InfoOp::store_any` 寫進邊；rest（`setTimeout` 多的參數，`FrontTypes::Rest`）沒有多的參數時是 none，有才建 scope 做陣列。個數不定的節點或字串（`append`）一個一個從 info 讀：節點是 wrapper 本身，字串照字串參數借。回傳存在邊裡的值（event handler 的 getter、`event.detail`、`signal.reason`）直接從邊的 traced handle 寫進回傳值（`InfoNoGc::return_value`），不建 `Local`；event handler 的原始碼還沒編譯時，操作後交給 `V8Front` 編譯。

操作裡給不出去的結果（V8 要配置的：還沒有的字串、沒有 wrapper 的節點、不是 Smi 的數字）不放在 front 裡：`InfoOp` 的 `ret_string`、`ret_node`、`ret_u32`… 回傳它（`PendingString`、節點的 root 和 interface、`f64`），`dom_api` 的回傳型別把它帶出操作（`RetType::Pending`），操作後交給 `finish_string`、`finish_node`、`finish_number`。回傳布林的成員沒有這個變數；其他 front（`V8Front`、named property 的、wasm 的）在操作裡自己留著結果，這幾個型別填 `Infallible`，那一段編掉。

isolate、receiver、參數、回傳值都在用的地方從 info 讀，不建 rusty_v8 的 scope、不建 `Call`；跑的是同一份 `TypedMember::call`。要 V8 配置、丟例外、執行 script 的（參數要 `ToString` 或複製、結果是 V8 還沒有的字串、沒有 wrapper 的節點、不是 Smi 的數字、錯誤、custom element 的 reaction、要告訴 V8 heap 長大了）當場建一個 scope 和上面的 `V8Front`（`InfoFront::with_front`），交給它做，用完就丟；這些路都在 inline 之外。哪個成員走哪個 front 在編譯時決定（`Members::function` 的 `const { M::PLAIN }`）；跨 origin 的物件的成員照舊（它的 callback 先檢查呼叫者）。

static 的 operation 和 attribute（`CSS.escape`、`URL.canParse`、`AbortSignal.abort`）也走這個 front，callback 是 `InfoStatic<M>`（`bindings::StateInfoFunction`）：函式沒有 signature，`this` 是任何值，所以 info 是 `StateInfo<State, Unsigned>`、沒有 `receiver()`，`InfoFront<'s, K>` 的 `K`（`InfoKind`：`Signed` 或 `Unsigned`）決定有沒有 receiver 和冷的路交給 `V8Front` 時怎麼讀參數。要目前的 realm 的 window 的成員（`#[front]` 的 static：`Front::prepare_window`）只是記下「要」，操作裡 `InfoOp::current_window` 才從 isolate 讀目前的 context 的 global（`InfoNoGc::current_global`，不建 scope）；沒要的成員拿到 none。

overload 的一組一個函式（`Overloaded`），也只拿 info：組的編號從函式的 data 原地讀（小整數），照參數的個數和第一個分得出的參數是哪個 interface 選形式（`dom_api::resolve_overload`，候選放在 stack 上；`implements` 只用 isolate），再呼叫那個形式的 `info_call::<M>`：`PLAIN` 的形式是它的 `InfoMember<M>`（或 `InfoStatic<M>`），不是的當場建 scope、照舊呼叫它的 `Member<M>`。個數不對的 `TypeError` 才建 scope。interface 有好幾個 constructor 的那一組照舊（拿 scope 的 `Overloaded`）。

constructor 也是（`InfoConstructor<M>`，`InfoKind` 的 `Construct`）：`InfoFront::construct` 原地檢查是不是用 `new` 呼叫、參數夠不夠（不是才交給 `V8Front` 丟 `TypeError`；`HTMLElement` 的一律交給它比 `new.target` 是不是 interface 物件本身），操作裡 `InfoOp::construct_object` 把 V8 替這次呼叫做的新物件（`this`，prototype 是 `new.target` 的）接上建好的物件。`HTMLElement` 的 constructor 的 `new.target` 從 info 讀（編號是 identity hash，和定義的 constructor 的邊比位址）。interface 有好幾個 constructor 的那一組也是只拿 info 的 `Overloaded`。

indexed getter 的 interceptor（`list[i]`，`Indexed<M>` 的 `StateInfoIndexedGetter`，`InfoKind` 的 `IndexedGet`）也走這個 front：info 是 interceptor 的（`bindings::StateIndexInfo`：V8 的 `PropertyCallbackInfo` 和索引），索引照數字讀（`InfoKind::number_arg`，不做成 V8 的值），`this` 是 interceptor 的 holder。結果是 null 或空字串（包括名稱表的空字串）時記下「沒有這一項」（`InfoKind::note_no_item`），回 `kNo`，V8 接著查 prototype；查詢和列舉的 callback 照舊。

named property 的 getter 和 setter（`dataset.a`、`children.px`、`style.color = 'red'`）是 plain 的時候各有自己的 callback（`named.rs` 的 `NamedGetter<M>`、`NamedSetter<M>`，`bindings::StateInfoNamedGetter`、`StateInfoNamedSetter`，`InfoKind` 的 `NamedGet`、`NamedSet`），template 建立時就知道是哪個成員：info 是 `bindings::StateNameInfo`（interceptor 的 info、名稱、setter 的值），參數就是名稱和值的 handle。getter 的結果是 null 時回 `kNo`（沒有這個屬性，V8 接著查物件自己和 prototype；空字串是值）；setter 給 `false` 時記下「不收這個名字」、回 `kNo`（一般的屬性），不寫回傳值。照數字當名字的（`dataset[9]`）、查詢、定義、刪除、列舉仍然是共用的 `NamedProperties` 加 `PropertyFront`。

回傳空字串不做字串：`InfoOp::ret_string` 和名稱表的空字串都直接設成 V8 自己的空字串（`OpReturn::set_empty_string`，root 表的常數）。

成員的函式在操作裡問 front 的事，`InfoOp` 都有（`OpFront` 的這類方法沒有預設實作）：讀 `ImageData` 的陣列的 bytes（`with_array_bytes`：從邊取出 handle、原地讀，handle 在 callback 自己的 handle scope 裡，`InfoNoGc::strong_value`）。要留到操作後的（要丟的 abort reason、`ImageData` 的像素、upgrade 中的元素）由錯誤或結果帶出操作，不留在 front 裡。

其餘的成員，每個一個 V8 callback（`templates.rs` 的 `Member<M>`，`bindings::StateCallback`：template 只在 isolate 的狀態是 DOM 時建得出來，callback 讀狀態不檢查），是 `dom_api` 替它展開的專用路徑（`TypedMember::call`）加上 V8 這一側的 front（`front.rs` 的 `V8Front`，Blink 產生的 callback 拿 `FunctionCallbackInfo` 做的事）：

1. 操作外轉參數：WebIDL 的 `ToString` 可能跑 script；節點的參數先確認是 wrapper（`bindings::is_wrapper`）；dictionary 照成員名稱的順序 `Get`（getter 可能跑 script、丟例外：例外留著，呼叫停在那裡）。建構子先確認是 `new` 呼叫的、參數夠不夠（照 Chrome 的訊息）。字串參數（`ArgString`）是 V8 的字串：平的 one-byte ASCII 字串在操作裡才讀，讀 V8 自己的字元（`bindings::LentString`，不複製、不經過 `ValueView`），借出期間 V8 的 GC 會 abort，所以呼叫在操作一結束就放掉參數；其他的（cons、two-byte、Latin-1）在這裡複製（攤平 cons string 會配置）。
2. 一個 DOM 的操作，由 front 開（getter 是 `V8Front::read`：共享地借 isolate 的狀態、`Dom::read`，不經過安全點；setter 和 method 是 `V8Front::mutate`：借整個狀態、`Dom::mutate`）。狀態從呼叫的 scope 借出，借著時 scope 被佔住；操作裡的那一側（`V8Op`）只拿 `bindings::NoGc`（不配置、不呼叫回來的那幾個）和 `bindings::OpReturn`（不配置的 setter），碰不到會配置的 V8 API。`this` 和節點的參數 unwrap 一次（receiver 由 V8 的 `Signature` 檢查過；回傳 promise 的成員裝在物件上的是外面一層沒有 `Signature` 的函式，在 `TryCatch` 裡呼叫它，receiver 不對、參數轉換和 DOM 的錯誤都變成 rejected promise（`templates::rejecting`，Blink 的 `ExceptionToRejectPromiseScope`），wrapper 的 tag 分辨它是哪一種 GC 型別：`EventTarget` 的 `this` 可能是節點或單純的 target），呼叫成員的函式，結果先記下：已經是 V8 的（節點的 wrapper、快取裡的 V8 字串、名稱的 V8 字串）從它的 handle 直接寫進回傳值（不建 `Local`，V8 的 `ReturnValue::Set` 對 `Global`、`TracedReference` 的讀法），否則記下 DOM 的字串或節點（root）。
3. 操作後（`Front::finish`）把結果變成 V8 的：建字串、不是 Smi 的數字（`double` 的結果多半是）；節點沒有 wrapper 時建一個，再開一次操作 wrap 它。建構子的新物件在操作裡就包進呼叫自己的 receiver（V8 照 interface 的 instance template 和 `new.target` 的 prototype 建好的，所以可以繼承），不用 root。表上標了 `[NewObject]` 的成員（`createElement`、`createTextNode`、`createElementNS`）在操作前先建好 wrapper，在操作裡 wrap，不用 root；receiver 是別的 realm 的（別的 frame 的方法用在這個 realm 的物件上）時不先建，之後在新節點的 relevant realm 建（`dom_api::realm_document`）。
4. setter 和 method 之後，DOM 的 heap 長大或縮小超過 64 KiB 就告訴 V8 它現在用了多少（`bindings::report_embedder_used_size`），V8 照它決定什麼時候開始 GC。V8 的 major GC 結束時，DOM 的 heap 直接告訴 V8 它的存活量（`EmbedderHeap::end`：marker 標到的加上 marking 期間新配置的），V8 照它定下一次的門檻，如 Chrome 用 cppgc 標到的 bytes；不是 sweep 做完之前、含死物件的大小。

**V8 不在 DOM 的操作裡配置，由借用檢查保證**：V8 配置時可能 GC，V8 的 major GC 經過 isolate 的狀態標 DOM 的 heap（`State` 是 isolate 的 embedder heap），而操作裡的節點不是 root。狀態只經過 isolate 借（`state::Scope`，`bindings::StateScope`），借著時沒有完整的 scope，所以拿著狀態時（操作裡，或讀寫快取時）呼叫不了會配置的 V8 API：V8 的物件（wrapper、字串、例外）都在操作外建，要放進快取的先放掉狀態、建好再借回來（`cached_string`、`templates::template`、`new_wrapper`）。`tests/marking.rs` 在 V8 幾乎一直標記的情況下跑。Blink 在型別上沒有這個保證：只有 `DCHECK`（`NoAllocationScope`），靠 Oilpan 保守地掃 stack。

## API

| 型別、函式 | 對應 Blink | 用途 |
| --- | --- | --- |
| `install` | `V8Window` 的 interface 物件、`V8PerIsolateData` 的 template | 把表上的 interface 物件和 `DOMException` 裝到一個 global 上：lazy data property（第一次讀時才做出來），不可列舉。isolate 的 DOM 在第一次裝時建 |
| `install_machopo_dom` | runtime enabled features | global 上不可列舉的 `machopoDom`，`createDocument()` 建 isolate 的 DOM 的一份 HTML document（它的 wrapper 在操作前建好）；DOM 的 interface 物件也在它上面（`machopoDom.Event`，lazy）。測試的 realm（`tests/it/env.rs`，`bench.py calls` 的也是）裝它 |
| `uncaught_exceptions` | （無） | 測試用：listener 和 timer 丟的例外裡，沒被 `error` 的 listener 取消、印出來的有幾次 |
| `create_window_realm` | `LocalWindowProxy::CreateContext` | 一個 global 是新的 window 的 realm：context 的 global template 是 `Window` 的 template，global proxy 包住一個新的 document（給定的 URL）的新 `Window`（global proxy 是 API wrapper，`Object::Wrap` 得了；裡面的 global object 不是），表上的 interface 物件裝在它上面。要在 isolate 的某個 context 裡呼叫（template 是 isolate 的） |
| `V8Engine` | `ScriptController`、`LocalWindowProxy` | `dom_api::ScriptEngine` 的 V8 實作，renderer 每份文件用它：自己的 isolate（建的時候建好 isolate 的 DOM），每個 browsing context 一個 global 是 window 的 realm（`create_window_realm`，time origin 照給的，document 從 loading 開始，告訴 inspector：V8 的 `console` 經過它到 console 的 sink，沒被取消的例外和沒處理的 rejection 也印到那裡（`bindings::devtools::report_uncaught`，`uncaught` 的訊息：例外的去掉 `Uncaught `，rejection 的是 `(in promise) 原因`；renderer 印成 `[uncaught] …`）；最上層的換文件時子 frame 都不在了；frame 換文件時沿用它的 global proxy（HTML 的 `WindowProxy`，Blink 的 `LocalWindowProxy`：之前的 context `detach_global`，新的用同一個 proxy 建），子 frame 的初始 `about:blank` 換成同 origin 的文件（`about:` 的或同一個 tuple origin）時沿用同一個 realm 和 window（`dom` 的 `reuse_window`）），classic script 在 frame 的 realm 裡跑（`ScriptOrigin` 的行號從給的那行起，例外和語法錯誤都經過 `report_caught` 在 window 回報）；microtask checkpoint 之後通知沒處理的 rejection（`bindings` 記下的，`unhandledrejection` 沒被取消、或 realm 不是 DOM 的 window 時印到 console 的 sink，也告訴 DevTools 的 console）；DevTools（`devtools.rs`）：session 接上、拿掉，命令是執行 script 的入口（`dispatch_devtools_message`，之後一次 microtask checkpoint），host 的 DevTools 佇列包成 `bindings` 的 `Queue` 交給 inspector（停在斷點時、要打斷 script 時拿），`set_idle` 交給 inspector；`document_ready`、timer（每個 frame 的 window 的一起照到期時間跑，各在自己的 realm）、平台的 task（`pump_platform_tasks`）；web tests 時 window 上有 `testRunner`（`reportHarnessResults` 把文字留給 host 拿）。window 的 realm 另外有 `queueMicrotask`（包一層、例外在 window 回報；不經過宣告表：只碰 engine 的 microtask 佇列） |
| `run_timers`、`next_timer` | `DOMTimerCoordinator`、renderer 排的 task | host 照時鐘跑 global 是新的 window 的 context 的 timer：給的時間（沒給是 window 的現在）前到期的都跑，每個之後做一次 microtask checkpoint（每個是 HTML 的一個 task；scope 要在那個 context 裡、沒有 script 在跑）；`next_timer` 是下一個到期的時間。測試用；renderer 用 engine 的 `run_due_tasks`：一輪裡每次重讀時鐘，從所有 frame 的 window 挑 `Cx::next_task` 最早的一個，在它的 context 裡跑（`window::run_task`），只跑這一輪開始前排的 |
| `set_load_sink` | `FetchManager` | renderer 給的 `dom_api::LoadSink`：blob URL 的登記和撤銷（`frames.rs`）、frame 不在了（`discard_child`）當下交給它；`fetch()` 在操作留下的 `Microtasks::FETCHES`（`state::report`）裡、呼叫回來之前送（`frames::send_fetches`），送了什麼排成 `FrameRequest::FetchSent` |
| `wrappers_made`、`heap_stats` | （無） | 測試用：做過的 wrapper 數，DOM 的 heap 的統計 |
| `new_string` | `V8StringResource` | 一個 `DomString` 的 V8 字串，現在做：照 UTF-8 複製成 V8 自己的字串。不像 Blink 做成借它的 buffer 的 external string：`DomString` 是 thread 自己的（非 atomic 的計數），V8 在它的 GC 的 worker 上放掉 external string 的 buffer；而且量起來複製比較快（external string 要一個物件、它的表裡的一項和 GC 時的回呼）。太長、V8 放不下時是 `None` |
| `StringCache` | `StringCache` | `DomString` 的 V8 字串的快取，照字串的位址（`DomString::addr`）找：intern 過的屬性值在每個元素上是同一個字串，它的 V8 字串只做一次。`find` 給那一項的 weak handle（操作裡經過 `NoGc` 打開或寫進回傳值），`make` 建 V8 字串和它的 weak handle、`insert` 放進去（isolate 的狀態裡的快取：建的時候放掉狀態），`get` 是不在狀態裡的快取的找不到就建、`peek` 只找。每一項留著那個字串（它活著時位址不會給別的字串）和 V8 字串的 weak handle；V8 收掉那個字串時 finalizer 只記下那一項死了，快取下一次用時才拿掉（finalizer 裡不 drop 自己的 handle）。一個 isolate 一份，在 isolate 的狀態裡 只被這次呼叫持有的字串（`DomString::is_unique`：現算的結果）不登記，位址隨呼叫消失、之後找不到；Blink 的也照 `StringImpl` 找不到，但它給的是 external 的字串、不用複製。 |
| `ArgString`、`arg_string` | `V8StringResource<>`、`NativeValueTraits<IDLString>` | 成員的字串參數：操作前照 WebIDL 的 `ToString` 轉，操作裡讀它的文字（`text`）：ASCII 的平的 one-byte 字串借 V8 的字元，其他的在操作前複製成 UTF-8（落單的 surrogate 變成 U+FFFD） |
| `string_arg` | `NativeValueTraits<IDLString>` | 參數照 WebIDL 的 `ToString` 轉成字串（可能跑 script：丟了例外是 `None`）；V8 的 one-byte 字串是 ASCII 時直接拿 bytes（rusty_v8 的 `ValueView`）。落單的 surrogate 變成 U+FFFD，DOM 的字串改成 WTF-8 時保留 |
| `throw_type_error` | `ExceptionState::ThrowTypeError` | 丟 `TypeError` |

內部的模組：

- `state.rs`：isolate 的 DOM（Blink 的 `V8PerIsolateData`），在 isolate 的狀態裡，只經過 isolate 借（`Scope`：成員的 callback 不檢查，其他的 callback 和 engine 檢查一次）：`Dom`（沒有 `Rc`、`RefCell`），driven 的 heap（`bindings::gc_platform` 上做平行的工作），engine 建好時（或 `machopoDom` 第一次裝時）就是 isolate 的 embedder heap（`bindings::set_isolate_state_with_embedder_heap`：V8 的 GC 經過 slot 拿 `&mut State`，跟著 isolate 一起放掉；heap snapshot 也經過它拿，`EmbedderHeapState::snapshot` 用 `Dom::walk` 把 DOM 的每個物件交給 `bindings::HeapGraph::add_heap`，不在任何文件的樹裡的節點是 detached、在的是 attached、其他物件不標，Blink 的 `V8EmbedderGraphBuilder`），字串快取、名稱的 V8 字串（照名稱的編號，第一次回傳時做，強參照：名稱表不會縮小；從 `Global` 直接寫進回傳值，不建 `Local`，V8 的 `ReturnValue::Set(const Global&)`）、每個 interface 的 template 和 wrapper 的 boilerplate。
- `templates.rs`：表上的 interface 的 template，每個 isolate 第一次用到時建，繼承 parent 的；常數在 interface 物件和 prototype 上（唯讀、不可刪），attribute 是 prototype 上的 accessor（沒有 setter 的唯讀），method 是 prototype 上的函式（`length` 是必要參數的數量），interface 物件的 `prototype` 唯讀（Blink 的 `InstallInterfaceTemplate`），prototype 的 `Symbol.toStringTag` 是 interface 的名稱；同名的 method（和一個 interface 的幾個建構子）是 overload：一個函式（`Overloaded`，data 是 overload 的編號，`length` 是各形式最少的必填參數），呼叫時用 `dom_api::resolve_overload` 選形式、再呼叫那個形式的 callback（`Member<M>`，存成函式指標）；overload 的清單照宣告表在第一次用到時建一次，process 裡共用（`OVERLOADS`：和 Blink 產生的 overload 分派一樣，是程式不是狀態；只有 overload 的形式的 callback 被取位址，在編譯時照 `declare::is_overload` 決定，其他成員的 callback 照樣 inline 進 V8 的 trampoline），分形式要問的 interface 的物件照 wrapper 的 tag 認（`implements`，現在是 `ImageData`、`Uint8ClampedArray` 和 `Path2D`）；常數、method 和 attribute 照宣告表的順序裝（物件的 key 的順序：WebIDL 的、Blink 的），iterable 的 method 在成員之後；unforgeable 的成員裝在 instance template 上（不能設定；method 也不能寫），祖先的 unforgeable 成員也裝在子類別的 instance template 上（V8 的 instance template 不繼承 parent 的；每個 interface 各自做一份函式），`#[global]`（`Window`）的成員也在 instance template 上（global 自己的屬性，WebIDL 的 `[Global]`），其他的在 prototype 上；`#[replaceable]` 的 attribute 有一個 setter，把值定義成物件自己的資料屬性（WebIDL 的 `[Replaceable]`）；`#[is_html_dda]`（`HTMLAllCollection`）的 instance template 是 undetectable 的，呼叫它就是呼叫它的 `item`（`bindings::set_state_call_as_function_handler`，`this` 是被呼叫的物件）；global 上還有 `[LegacyWindowAlias]` 的名稱（`LEGACY_WINDOW_ALIASES`：`WebKitMutationObserver`）；`#[indexed]` 的 method 另外是 instance template 的 indexed property handler（`object[i]` 走它的專用路徑，給 null 或空字串是沒有這個屬性：CSSOM 的 `item` 不是 nullable，過了最後一個給空字串，字串的清單沒有空的項目），宣告它的 interface 的 prototype 的 `@@iterator` 是 `Array.prototype.values`（query 和 enumerator 經過 `named.rs` 的 `PropertyFront` 問 getter：從 0 往上問到沒有為止，只在列舉時走到）；instance template 不繼承 parent 的 interceptor，所以自己沒有 indexed getter、祖先有的 interface 也裝上最近的祖先的（`HTMLFormControlsCollection`、`RadioNodeList`；Blink 產生的 bindings 也是每個 interface 各自裝）；沒有名字的（`#[indexed(getter)]`，`HTMLFormElement`）只是 handler，不在 prototype 上；`#[iterable]` 的 prototype 另有 `entries`、`forEach`、`keys`、`values`（`Array.prototype` 的）；`#[named(..)]` 的 method 不放在 prototype 上，它們是 instance template 的 named 和 indexed 的 interceptor（`named.rs`）；有 `#[indexed(setter)]` 的 interface 的 indexed handler 也有 setter（`bindings::set_state_indexed_properties`，data 是 interface 的編號，`named.rs` 的 `IndexedSetter` 經過 `PropertyFront` 呼叫它；祖先的 getter 和自己的 setter 一起裝：`HTMLOptionsCollection`）；window 的 instance template 就是 global template。`#[legacy_factory]` 的 method 是 global 上不可列舉的 lazy 的屬性（`install`，data 是 interface 和成員的編號），第一次讀時做函式（它的專用路徑：先檢查是 `new` 呼叫的，回傳的物件取代 `new` 做的），`name` 是成員的名稱，`prototype` 是 interface 的 prototype 物件、唯讀（WebIDL 的；Blink 的 legacy factory 用和 interface 同樣的 instance template，這裡用回傳的 wrapper，不另外做 instance template）。表上有建構子的 interface 物件的 callback 是建構子的專用路徑（`length` 是它必要參數的數量），沒有的不是建構子（`new Node()` 丟 `TypeError`），它的 `[[Prototype]]` 是 parent 的 interface 物件（Blink 在做出它時設）。新的 wrapper 是每個 context 一個的 boilerplate 的複製（`v8::machopo::clone_object`，Blink 的 `CreateWrapperFromCache`），照節點的種類最衍生的 interface。節點和它擁有的物件（collection、`NamedNodeMap`、`DOMTokenList`、`DOMStringMap`、元素的 style：`dom_api::realm_document`）的新 wrapper 做在它的 document 的 realm（`front.rs` 的 `new_wrapper_in_realm`；HTML 的 relevant realm，Chrome 的結果）：先和 current context 的 window 的 document 比一次，一樣（大多數）就不換 context，不一樣時進那個 frame 的 context 做；沒有 frame 顯示的 document（`createHTMLDocument`、`DOMParser` 的）照 current。成員自己建的新節點（`createElement` 這些）的 wrapper 在操作前做好，照 current。
- `front.rs`：V8 這一側的一次呼叫（上面的「一次呼叫」）。front 對呼叫的參數是泛型的（`CallArgs`）：函式的 callback 用 V8 的 `FunctionCallbackArguments`，indexed getter 用 `IndexArgs`（只有索引和 holder），一般的成員各自單態化，讀參數沒有多的分支。`current_window` unwrap 目前的 context 的 global proxy（只有標 `#[front]` 的建構子問：`Text`、`Comment`、`DocumentFragment`、`Document`、`DOMParser` 的照它找目前的 realm 的 document）。engine 一定要配置的結果（陣列、dictionary、record、promise、第一次讀才做的值）不留在 front 裡：`dom_api` 的回傳型別把資料帶出操作，操作後呼叫 `Front` 的專屬方法（`finish_strings`、`finish_objects`、`finish_dictionary`、`finish_resolved_string`…），當場做 V8 的值、設成回傳值；`InfoFront` 的這些方法建 scope、交給 `V8Front` 的同一個方法。`timer_handler_arg` 收函式，其他的在操作前照 `ToString` 成字串（front 的 callback 那一格是任何值：listener 的物件存成 object 的 strong 參照，timer 的字串存成任何值的）；`rest_arg` 在操作前把後面的參數做成陣列，`store_rest` 存成 strong 的 `TracedReference<Value>`（`bindings::set_strong_value`）；`ret_any` 照原樣交回 DOM 存的值（沒有時 undefined，`ret_any_or_null` 是 null）；`any_arg` 和 `dict_any` 把值放進 callback 的那一格（沒有成員兩個都拿；參數的 undefined 先換成 null，op 裡沒有 scope 做不出 null），`store_any` 存成 strong 的參照；`target_arg` 收節點、window 和單純的 target 的 wrapper，`target` 在操作裡照順序 unwrap；`i32_arg` 是 `ToInt32`。`blob_parts_arg` 照 WebIDL 一邊走 iterable 一邊轉（`observable_array::for_each_item`）：blob 的 wrapper 留著，`ArrayBuffer` 從 backing store、view 用 `copy_contents` 複製當時的 bytes（detach 了是空的），其他的照 `ToString`；`number_if` 只在值是數字時讀它；`round_rect_radii_arg` 照 WebIDL 的 union：undefined 是 0，有 `@@iterator` 的物件是 sequence（一邊走一邊轉），其他的物件和 null 是 `DOMPointInit`（成員照名稱的順序讀 `w`、`x`、`y`、`z`），其他的 `ToNumber`；promise 的字串和 bytes 的結果在操作後才做（`finish_resolved_string`、`finish_resolved_bytes`：bytes 直接當新的 `ArrayBuffer` 的 backing store）。`V8Front` 在操作裡留著的結果只剩它自己給的（`Kept`：不是 Smi 的數字、V8 還沒有的字串、沒有 wrapper 的節點和物件、custom element 的建構、`ImageData` 的像素）；`finish` 只 inline「有沒有留」的判斷，其他的在 `finish_kept`。callback 的參數是任何物件（函式，或呼叫時才取 `handleEvent` 的物件），front 留著它，比的時候比 listener 的參照指的是不是同一個物件，存的時候用不 droppable 的 `TracedReference`（`bindings::set_strong`：V8 的 scavenge 把它當 root，Blink 的 `TraceWrapperV8Reference`）；物件的結果沒有 wrapper 時操作後才建（節點的在 cold 的 `keep_node`：找 interface 要讀元素的名稱，不放進有 wrapper 的快路）。
- `observable_array.rs`：WebIDL 的 observable array（`adoptedStyleSheets`，Blink 的 `ObservableArrayExoticObject`）：attribute 的值是一個 `Proxy`，target 是空的陣列（`Array.isArray`、`Array.prototype`），handler 的 trap 讀、改 backing list：`length` 和它以下的索引是 list 的，其他的是 target 的。list 的三個操作是表上的專用路徑（attribute 的 getter 給 list，`#[observable(..)]` 的 method 設定一格、拿掉最後一個），各自的函式由它的 template 做（`State::observable`，interface 的 template 建好時記下），trap 照一般的函式呼叫，丟的例外往上。handler 每個 realm 一個，掛在 global 的 private key；target 用 private key 記著 platform 物件和 attribute 的編號；wrapper 也用 private key 留著它的陣列，每次給同一個。attribute 的 setter 先把值照 WebIDL 轉成 sequence（每一個都要是 item interface 的物件，否則 `TypeError`、什麼都不改），再全刪、一個一個加。
- `custom_elements.rs`：`define` 讀建構子（Blink 的 `ScriptCustomElementDefinitionBuilder`）：照 HTML 的步驟的順序 `Get`（getter、proxy 的 trap 可能跑 script，丟的例外就是 `define` 的，front 記下 `RareCall::threw`、不再丟別的）：`prototype`（不是物件是 `TypeError`）、四個生命週期 callback（undefined 或函式，否則 `TypeError`）、`observedAttributes`（有 `attributeChangedCallback` 時）和 `disabledFeatures`（`sequence<DOMString>`，經過 `observable_array::sequence`）、`formAssociated` 和它的四個 callback（讀、檢查，不留）。front 把讀到的 callback 放在 `Call` 的 `RareCall` 裡（少數成員才用的一格：每多一個欄位，每次呼叫都要清、要 drop），給之後的操作存進定義的 JS edge（strong）。`whenDefined` 的 promise 在操作後才建：名稱已經定義的，新的 promise resolve 成定義的建構子（`finish_resolved_constructor`：再開一個讀的操作從定義的邊讀）；還沒定義的 pending，新的 resolver 照 registry 給的編號放進 `State::when_defined`，或是那個編號已經有的 resolver 的 promise（`finish_pending_promise`）；`define` 從表拿出那些編號的 resolver，resolve 成建構子。registry 不在了、名稱沒定義的 resolver 留在表裡（window 走了也一樣，現在一個 isolate 一個 window）。建構子的編號是 V8 的 identity hash（`GetIdentityHash()`，不配置，可以在操作裡算；Blink 的 `V8CustomElementConstructorHashTraits`），`define` 存它，`new X()` 照 `new.target` 的、`getName` 照參數的找定義、再比 handle。`HTMLElement` 的建構子給 upgrade 中的元素時，有 wrapper 的在操作後換成 `new.target` 的 prototype（`construct_html` 回傳它的 root，`Front::finish_upgrading`，`[[SetPrototypeOf]]`），V8 用 API 建構子設的物件當 `new` 的結果；沒有的用呼叫的新 wrapper（V8 照 `new.target` 做的，prototype 已經是它的）。`createElement` 的 custom element（`Kept::Construct`，`finish_construct`）：在 `TryCatch` 裡 `new` 建構子，再開一個操作檢查，丟的或檢查的錯在建構子的 realm 回報（`listeners::report_caught`），給 failed 的元素。upgrade（`upgrade_element`，front 和 `listeners::Host` 共用）一樣在 `TryCatch` 裡 `new`，給的不是元素的 wrapper 時丟 `TypeError` 再回報。生命週期 callback（`call_lifecycle_callback`，front 和 `Host` 共用）：定義的函式，`this` 是元素（沒有 wrapper 時建），`adoptedCallback` 拿舊的和新的 document，`attributeChangedCallback` 拿名稱、舊值、新值、命名空間（沒有的是 null），在 `TryCatch` 裡呼叫，丟的在它的 realm 回報；存 callback 時告訴 DOM 定義有哪幾個。`state::report` 每次呼叫之後讀一次 DOM 要排的 microtask（一個 byte，通常是 0）：backup element queue 的是 `ProcessReactions`（`process_backup_element_queue`，`Host` 當 script host），engine 的 checkpoint 前也 report。文件的 parser 的 host（`ParserHost`，`engine.rs`）：已定義名稱的元素（HTML 的 create an element for a token 會跑 script 的那一支）先跑 microtask checkpoint、推 element queue，`front::construct_custom_element`（和 `createElement` 共用）建構和檢查，加上屬性，invoke 那個 queue；parser 插入時留下的 queue 也由它跑。
- `templates.rs` 的 legacy callback interface object（`dom_api::CALLBACK_INTERFACES`，`NodeFilter`）：global 上 lazy 的屬性（不可列舉），一個沒有 `prototype`、呼叫就丟 `TypeError` 的函式，帶著常數（唯讀、可列舉、不可刪）。`listeners.rs` 的 `call_node_filter`（`ScriptHost::call_node_filter`）：在 `TryCatch` 裡呼叫 filter（函式的 `this` 是 undefined，物件的 `acceptNode` 的 `this` 是它，不能呼叫是 `TypeError`；filter 的 realm 的文件已經 discarded 時不呼叫、丟 `TypeError`，Blink 的 `IsCallbackFunctionRunnable`），結果 `ToUint16`；丟的例外留在 `RareCall`，traversal 清掉旗標之後成員丟出時重新丟出。`unsigned long` 的參數（`front::to_uint32`）：數字照 V8 的 `Uint32Value`，其他的先 `ToNumber` 再自己取模（V8 的不讓字串的負數 wrap：`"-1"` 是 0）。`StaticRangeInit` 的 container 在操作前留在 `RareCall`。
- `templates.rs` 的靜態的 operation（`Member::is_static`）裝在 interface 物件上、沒有 signature（overload 的也是）；namespace（`InterfaceDesc::namespace`，`CSS`）是 global 上的普通物件（`Object.prototype` 的、不能呼叫），operation 從 template 的函式拿過來，`Symbol.toStringTag` 是它的名稱（Blink 的 IDL namespace）；`getHTML` 的選項（`get_html_options`）在操作前讀，`shadowRoots` 轉成序列、每個都要是節點的 wrapper：handle 交回去，操作裡換成節點、檢查是 shadow root。
- `named.rs`：WebIDL 的 named property（`dataset.fooBar`，Blink 產生的 `NamedPropertyGetterCallback` 那些）：interface 的 template 建好時記下它的 getter、setter、deleter、名稱的專用路徑（`NamedCalls`，在 isolate 的狀態裡，interceptor 的 data 是 interface 的編號），`bindings::set_state_named_properties` 裝上 named 和 indexed 的 interceptor（數字的索引也當名稱，interface 自己有 indexed getter 時（`CSSStyleDeclaration`）不當；只攔字串，不攔 symbol；`[LegacyOverrideBuiltIns]` 是 masking 的，不然 non-masking）。interceptor 的回傳值是 `Boolean`、`Integer` 或 `Array`，不是函式的 `Value`，所以不用 `V8Front`，走自己的小 front（`PropertyFront`：參數是名稱和值（indexed setter 的是索引和節點，`u32_arg`、`node_arg`），結果先記成 DOM 的字串、名稱、物件（root 住，和它的 interface）或 none，回到 interceptor 才變成 V8 的：物件的 wrapper 在操作之後做）。get：getter（字串，或 `form[name]` 這種物件），none 是沒有這個 property；query：也是 getter，可設定、有 setter 時可寫、有名稱時可列舉；set：setter，給 `false` 的是沒收這個名稱（物件的一般屬性：`style.notAProperty`）；define：值經過 setter，getter 或 setter 的描述拒絕；delete：getter 有的才經過 deleter；enumerate：名稱。
- `templates.rs` 的靜態的 attribute（`Member::is_static` 的 getter）裝在 interface 物件上，是唯讀的 accessor（`PerformanceObserver.supportedEntryTypes`）。
- `templates.rs` 的 accessor 的函式照 WebIDL 命名（`get x`、`set x`：`set_class_name`）；overload 的一組只包括同是 static 或同不是的同名 operation（`Response.json()` 和 `response.json()` 各自一個函式）。
- `pairs.rs`：WebIDL 的 pair iterator（`iterable<K, V>`，Blink 的 `PairSyncIterable`）：有 `#[pairs]` 成員的 interface 的 prototype 上的 `entries`、`keys`、`values`、`forEach`（可列舉）和 `@@iterator`（同一個 `entries`，不可列舉），檢查 receiver；default iterator object 是普通的物件，private 的 target、kind、index，prototype 是每個 realm 第一次時做、存在 global 的 private key 上的 `%XIteratorPrototype%`（它的 prototype 是 `%IteratorPrototype%`，`@@toStringTag` 是 `X Iterator`）。`next()` 和 `forEach` 的每一步呼叫 `#[pairs]` 成員的專用路徑（`IndexArgs`，結果是 `[key, value]` 的新陣列，空的是結束），所以看到的是當時的清單。
- `window_properties.rs`：window 的 named properties object（WebIDL 的，`[Global]` 的 `Window`；Blink 的 `WindowProperties`）：每個 realm 建 window 時做一個，放在 `Window.prototype` 和 `EventTarget.prototype` 之間；V8 的 non-masking named interceptor，只攔字串：global 自己的、`Window.prototype` 和更上面的 prototype 有的名稱都不問它，所以找得到的 global 不多花成本。getter 照 `dom_api::named_property` 在 interceptor 所在的 realm 的 window 找（child window、元素，好幾個時才在 mutate 裡做 collection），wrapper 在操作之後做；define 一律拒絕（WebIDL 的 [[DefineOwnProperty]]，`[[Set]]` 收到物件自己是 receiver 時也走到這裡），有的名稱 delete 拒絕；`@@toStringTag` 是 `WindowProperties`。
- `state.rs` 的 `report` 在每個會改 DOM 的呼叫後也看 DOM 的「要排 mutation observer 的 microtask」：有就排一個 V8 的 microtask（`Deliver`：函式的 template 第一次時做，跑 `dom_api::deliver_mutations`）；engine 在跑 script 和 microtask checkpoint 之前也看（parser 改的）。
- DevTools 要 stack 時（`ScriptEngine::set_stacks_wanted`，交給 DOM：`Dom::set_stacks_wanted`），`report` 看到 DOM 記下了 script 在呼叫裡要載入的（`Microtasks::stacks`）就抓一次 stack（`state::capture_stack`：`bindings::devtools::capture_stack`，帶所有 async 的 parent，`Runtime.StackTrace` 的 JSON）交給 DOM（`Dom::note_request_stacks`）：呼叫結束之後抓，因為呼叫裡不能配置 V8 的物件。`import()` 在 V8 的 callback 裡當場抓，放進它的 graph 的根的抓取（`modules.rs` 的 `Host` 的 `root`）。
- `listeners.rs`：`Host`（操作外的 script host：跑 timer、回報例外時分派 `error` 的 listener；它的操作從 scope 借狀態，存例外和 rejection 的值時經過 `NoGc`）。engine 每次從 native 呼叫 JS 都算一次進入 script（`bindings::trace::enter_script`；HTML 的 prepare to run script）：callback 和 script 經過 `run_callback`，回來時已經不在 script 裡就做 microtask checkpoint（HTML 的 clean up after running script：UA 分派的事件的 listener 之間有一次，script 的 `dispatchEvent()` 裡沒有；Blink 的 `V8RunMicrotasksScope`），settle promise（可能跑 `then` 的 getter）和 checkpoint 本身只計數；engine 自己跑的 classic script 計到回報完例外為止（`error` 的 listener 之間沒有 checkpoint），parser 建構 custom element 也是 callback。debug build 裡 JS 呼叫 DOM 的成員時檢查計數大於 0（`V8Front::new`），漏算的入口在測試裡就失敗。`call_listener`：在操作裡讀 callback、看 current target 和 event 有沒有 wrapper，操作後才建缺的，再呼叫（函式的 `this` 是 current target，物件的是它自己）。`call_timer`：timer 的函式，`this` 是它的 window 的 global proxy，參數是存的陣列；字串的 handler 照 classic script 在 window 的 realm 跑（名字是 document 的 URL，參數不用）；之後做 microtask checkpoint。`call_mutation_callback`：observer 的函式，`this` 和第二個參數是 observer，第一個是 record 的新陣列。`call_blob_callback`：`toBlob` 的函式，`this` 是 undefined，參數是它的 blob（沒有 wrapper 的在操作後建）或 null。丟的例外由 `TryCatch` 接住，不丟回給呼叫者，在 callback 的 realm 的 global 回報（timer 的是它的 window；`report_caught` 是 cold 的、不 inline，呼叫的路上只多一個分支）：global 是 DOM 的 window 時經過 `dom_api::report_exception` 觸發 `ErrorEvent`（`message` 是例外的字串，`filename`、`lineno`、`colno` 是 V8 的 message 的位置，`error` 是丟的值），沒被取消、正在回報另一個、或 global 不是 window 時印出來（`tracing`）並記一筆給測試的計數。
- `exception.rs`：`DOMException`，純 V8 的物件（不在 DOM 的 heap 上：它只有名稱和訊息，放在 internal field，`code` 照名稱查 WebIDL 的表）；interface 物件是建構子（`new DOMException(message, name)`），prototype 的 prototype 是那個 realm 的 `Error.prototype`，丟出時附上 `stack`，在目前的 realm 裡建。`QuotaExceededError` 是它的子類別（template 的 slot 在它之後，WebIDL 的；多 `quota`、`requested` 兩個 internal field，`double?`），建構子照 Chrome 152 不做 `RangeError` 的檢查；DOM 丟的 `QuotaExceededError` 做成它（兩個值是 null）。兩種都有 private symbol 的品牌（`brand`），structured clone 照它認，script 看不到也改不了。
- `devtools.rs`：frame 的 realm 怎麼告訴 V8 的 inspector（Blink 的 `MainThreadDebugger::ContextCreated`、`ContextWillBeDestroyed`、`DidClearContextsForFrame`）：建的時候（`create_window` 和 `frames.rs` 的 `create_child`）帶著 host 給的 frame 的 DevTools id（`ScriptEngine::set_devtools_frame_ids`，存在 isolate 的狀態裡：插入 iframe 的呼叫裡也拿得到）和文件的 origin（初始的 `about:blank` 是 parent 的；opaque 的是 `"://"`，Chrome 的寫法），最上層的 frame 的是沒指定 context 的命令跑的地方；子 frame 換成別的 realm、iframe 不在了（和它裡面的 frame）時告訴它不在了；最上層的換文件時一次清掉（`Runtime.executionContextsCleared`，console 的訊息和回報過的例外跟著清掉）。沒被取消的例外（`listeners.rs` 的 `report`）和沒處理的 rejection 交給 DevTools 的 console（`Uncaught`、`Uncaught (in promise)`），位置是 stack 最上面那一格（在丟出的 script 裡時），否則是 V8 的 message 的；rejection 之後加了 handler 時 `bindings` 劃掉它。
- `devtools_page.rs`：DevTools 的命令借的 page（`dom_api::DevToolsPage`，Blink 的 agent 直接拿 `Document`）：從 isolate 的狀態借 `Dom` 和 layout（`dom_and_layout`，layout 照 operation 的方式拿出來、page 走時放回去），停住時和不停住時都一樣；`DevToolsObjects`（`resolveNode`、`requestNode`、`$0`、Event Listeners：listener 的位置、還沒編譯的屬性 handler 先編譯）經過 inspector 的 `wrapObject`、`unwrapObject`、`addInspectedObject`；節點在 Console 裡的 subtype 和名字（`div#a.x.y`，Blink 的 `ThreadDebugger`）。
- `frames.rs`：engine 的 browsing context（Blink 的 `LocalFrame` 和它的 `LocalWindowProxy` 的 context），在 isolate 的狀態裡：最上層的一個，和每個連著的 iframe 的子 frame（`dom_api` 的 iframe 的步驟在每次呼叫之後建：`create_child`），各自的 realm、現在的文件、parent 和 iframe，照 `FrameId` 找；host 要做的事照順序記下（`FrameRequest`）。V8 的 security token 照文件的 origin（Blink 照 document 的 `SecurityOrigin` 設）：同源的 realm 互相碰得到，其他的經過 `cross_origin.rs`；opaque origin 每次一個新的，子 frame 的 `about:` 文件（初始的 `about:blank`、`about:srcdoc`）跟著 parent 的。子 frame 的初始 window 的 page 的 system focus 照 parent 的 window（engine 建的 window 照 engine 的）：它換成同 origin 的文件時留著，也收得到 window 的 `focus`、`blur`；一次 rendering update 只走一次 frame tree、照樹的順序，之後的 update 再走，update 期間拿掉的 frame 不給、新加的等下一次；host 的 loop 問動畫要不要 frame 時不走（`frame_tree_walks_for_testing`）；全域的 `window`、`document` 是 cached accessor：迴圈裡讀不呼叫 getter，getter 沒有 `prototype`、不能 `new`，沿用的 window 換了 document 之後是新的（`window_document_gets_for_testing`）。
- `cross_origin.rs`：HTML 的跨 origin 的物件（Blink 的 `V8Window`、`V8Location` 的 cross-origin interceptor）：`Window` 和 `Location` 的 instance template 有 V8 的 access check（fork 的 `set_access_check_callback_and_handler`，經過 `bindings::set_state_access_check`；window 是 global proxy，V8 只在 security token 不同時問，location 每次存取都問：比它的 creation context 和存取的 context 的 token），拒絕時屬性走這裡的 interceptor：HTML 的 CrossOriginProperties（window 的 `window`、`self`、`location`、`close`、`closed`、`focus`、`blur`、`frames`、`length`、`top`、`opener`、`parent`、`postMessage`，location 的 `href`（只能設）和 `replace`），method 的值和 attribute 的 accessor 是存取的 realm 的函式（每個成員一個 template，`State::cross_origin`，V8 每個 context 留一個函式：同一個 realm 每次拿到同一個，不是物件自己 realm 的（它的 `Function` 會在那個 realm 跑 script）；`name` 是 `get location` 這樣的）；getter 在物件的 realm 裡跑（它做的 wrapper，例如 window 的 `Location` 的，是那個 realm 的，別的 origin 碰不到）；子 window 照索引（可列舉）和 iframe 的 `name`（不在 own keys 裡，HTML 的 [[HideFromKeys]]）；`then` 和三個 well-known symbol 是 undefined；其他的、delete、define、設 prototype 是 `SecurityError`（isolate 的拒絕回報，fork 的 `set_failed_access_check_callback_function`；HTML 的 [[SetPrototypeOf]]、[[PreventExtensions]] 給 false 再 `TypeError`，V8 只告訴 embedder 拒絕了，Chrome 也是 `SecurityError`）。這些成員自己的函式也是同一個 callback（`CrossOriginMember`，WebIDL 的 `[CrossOrigin]`：宣告表的 `#[cross_origin]`，展開時就分給 visitor 的 `cross_origin`），不檢查 receiver 的 access：自己 realm 的 `postMessage` 也能用在別的 origin 的 window 上；其他成員的函式都檢查（`templates::checks_receiver`，`set_accept_any_receiver(false)`，Blink 的 `IDLMemberInstaller`；`queueMicrotask` 也是），所以拿自己 realm 的 getter `call` 別的 origin 的 window 也是 `SecurityError`。
- `serialize.rs`：訊息的 structured clone（HTML 的 `StructuredSerializeWithTransfer`，V8 的 `ValueSerializer`，Blink 的 `SerializedScriptValue`）：JS 的值 V8 自己 clone，傳的 `MessagePort` 寫成它在訊息的 port 裡的位置、讀回那個位置的 port，傳的 `ArrayBuffer` 是 V8 自己的 transfer（backing store 跟著訊息，原本的 detach），`DOMException` 寫成名稱和訊息、`QuotaExceededError` 寫成訊息、quota 和 requested（照品牌認；讀回時在讀的 realm 做新的），其他平台物件是 `DataCloneError`；transfer list 的檢查照規範的順序（不能傳的、重複的、自己的 port，序列化之後 detach 過的 buffer、送過或關了的 port）。
- `machopo_dom.rs`：`machopoDom`。
- `modules.rs`：realm 的 module script（Blink 的 `ModulatorImpl`）：frame 的狀態在它的第一個 module script 時建 `bindings::ModuleRecords` 和 `dom_api::module::Modulator`，跟著 realm（初始的 `about:blank` 的 window 被沿用時留著）；`ModuleHost` 在 frame 的 context 裡 compile、建 parse error（`SyntaxError`、`TypeError`）、link，要抓的經過 DOM 給 host（`Cx::queue_module_fetch`，CORS），抓到的經過 `ScriptEngine::module_fetched` 回來；graph 好了告訴它的 pending script（`Cx::module_graph_fetched`）。evaluate 的 promise reject 時（丟的、或 error to rethrow）在 window 回報（`listeners::report_value`）。`import()`（`import_dynamically`，V8 的 host import callback）：照呼叫它的 script 的 host-defined options 的 base URL 解析（沒有時是文件的 URL：event handler 的）、用它的 credentials mode 抓（classic script 的照 `crossorigin`：`frames::credentials_of`；沒有時 same-origin），promise 在 realm 的表裡（`bindings::PromiseResolvers`，和 module 的狀態一起建）；graph 已經在 map 裡的在 microtask 裡 link、evaluate（不在 `import()` 裡跑 module），其他的抓到時在那個 task 裡；抓失敗的 reject `TypeError`。`import.meta.resolve` 照 module 的 base URL 解析（`ModuleRecords::with_resolve`）。`preload`：`<link rel=modulepreload>` 的 `href`、`as`（不是 script 類的觸發 `error`）、`crossorigin`，只抓那一個 module，之後在 link 上排 `load` 或 `error` 的 element task。
- `handlers.rs`：event handler 的編譯（`ScriptHost::compile_event_handler`）：在元素（或 window）的文件的 frame 的 realm 裡（HTML 的：scope 的最後是元素的 relevant global）用 V8 的 `CompileFunction`，元素的以 document 和元素當 context extension（還沒有 form owner），window 的沒有；參數是 `event`，window 的 `onerror` 是五個；原始碼的行號當 `ScriptOrigin` 的行。編譯不過在 window 回報、handler 拿掉（HTML 留著、值是 null：再設時這裡排最後）。`listeners.rs` 的 `call_listener` 對 handler：只呼叫函式（不是函式的物件什麼都不做），window 的 `onerror` 拿 `ErrorEvent` 的五個部分、回傳 `true` 取消，其他的回傳 `false` 取消（DOM 的 set the canceled flag，`dom_api::cancel_event`）。
- `webdriver.rs`：WebDriver 的 script（`V8Engine` 的 `execute_webdriver_script`、`webdriver_element_property`）：body 是 async function 的（`await` 用得了），在 window 的 realm 裡建、`this` 是 window；Execute Script 照它的 promise 結束，Execute Async Script 照最後一個參數的函式第一次被呼叫時（給的是 promise 時等它），在那之前 body 的 promise 被 reject 才是錯；結果在 V8 裡照 JSON clone（不像 chromedriver 在頁面裡注入 JS，頁面改了 `JSON` 或 `Array.prototype` 也不受影響）：元素和 window 是 id、`HTMLCollection`、`NodeList`、`DOMTokenList` 和 arguments 是陣列、自己的 `toJSON`、只算自己可列舉、名稱是字串的屬性，循環、symbol 和 BigInt 是錯。結果在 promise 結束的 handler（microtask）裡寫進 isolate 的狀態，engine 交給 host（`take_webdriver_results`）。

- `strings.rs`：字串複製進 V8（ASCII 的也不是 external、V8 不拿 DOM 的字串的參照），長度是 UTF-16 的；同一個字串（clone）只做一個 V8 字串、內容相等但不是同一個字串的各做一個，非 ASCII 的也快取；只被這次呼叫持有的字串（每次現算的，例如 `style.color`）不進快取、DOM 持有的進；V8 沒有的字串由 V8 的字串建構子直接建、不建 scope（`bindings::InfoHandles::new_string`），現算的文字（`DomStr::Fresh`）連 `DomString` 都不做；V8 收掉字串之後，快取下一次用時拿掉那一項和它留著的字串，之後再要時重做；名稱（local name、大寫的 tag name、找不到屬性時的空字串）的 V8 字串一個 DOM 只做一次，屬性值不算；dictionary 的成員照名稱的編號從同一份快取拿 key（第一次讀到那個名稱時做一次，internalized），不再每次讀都建字串；快取的屬性值之後從快取回傳（同一個值每次、每個元素）；成員的每一種字串參數都讀得完整（字面值、執行期做的 ASCII 字串借 V8 的字元，cons、two-byte、Latin-1、落單的 surrogate 複製），呼叫回來時沒有留下借出；參數照 `ToString`（數字、null、undefined、物件的 `toString`），`toString` 丟例外時是 `None`、例外留著；`TypeError` 的訊息。

`tests/marking.rs`（自己的 binary，`--stress-incremental-marking`）：V8 幾乎一直標記時，script 建樹、讀新的字串、走 scavenge 丟掉 wrapper 的節點、放掉樹；V8 標過 DOM 的 heap，留著的部分完整。

單元測試：`src/strings.rs`（一個 key 被記成死了、它的那一項卻已經重做，那一項留著）、`src/state.rs`（V8 在操作裡呼叫 heap 時 panic）。
