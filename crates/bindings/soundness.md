# `bindings` 的 soundness

這份文件說明 `bindings` 為什麼不會讓 safe code 造成 undefined behavior：要保證什麼、依賴哪些假設、用什麼方式守住、哪裡還沒辦法保證，以及修改時要審查什麼。範圍包括 rusty_v8 fork（`../third_party/rusty_v8`）裡我們改的部分：GC 物件指向 JS 值的 slot（`v8::cppgc::TracedSlot`）、新物件的初始化，和 elise 的 heap 和 V8 一起標的 `v8::machopo`（連同它的 V8 fork 裡的 patch，`v8/include/v8-machopo.h`）。elise 的 heap 本身的論證在 `../third_party/elise/docs/soundness.md`。

假設和不變式的編號不連續：留下的沿用原本的編號，程式碼的註解照這些編號引用。

## 結論

**目標**：不寫 `unsafe` 的程式碼只透過 `bindings` 的 API，不可能造成 UB，包括 use-after-free、data race、違反 Rust 的 aliasing 規則。其他 crate 本來就不能寫 `unsafe`（workspace 的 `unsafe_code = "deny"`），所以這等於整個專案除了 `bindings`、fork 和 `ipc`（和 elise）以外都是 safe code。elise 的論證在 `../third_party/elise/docs/soundness.md`；`ipc`（共用記憶體 IPC）的 `unsafe` 和 GC 無關，論證不在這份，和那個 crate 一起寫。

| 模式 | 結論 |
| --- | --- |
| **Incremental marking**（預設） | 在假設 A1–A5、A7–A10 下成立。`trace()` 只在 heap 自己的 thread 上執行，V8 自己升級成 concurrent 的路徑也關掉了 |
| **cppgc 的 concurrent marking** | 不打開：machopo 在 `CppHeap` 上沒有物件（它只是 elise heap 接上 V8 的 GC 的地方，V8 讓 embedder 跟著它的 GC 追蹤只有這個 API），標記方式固定 incremental（`V8PerIsolateData::new`）。elise heap 自己的 marker 在背景讀物件的 `TracedReference`（`unified_heap.rs` 的 `TracedSink`），靠的是 C4 |

**這是論證，不是證明。** Miri 不能執行 V8 的 C++ 程式碼；機械化的證明則需要把 cppgc 的行為也形式化，不切實際。所以做法是：把假設和不變式明確寫出來，再分別用編譯器、執行期檢查、測試和人工審查守住它們。

## 假設

這些是 V8、cppgc 和 `v8` crate 的行為，我們證明不了，每一條都對照過 fork 裡的 V8 原始碼，升級 V8 時要重新確認。cppgc 的內部實作在 `v8/src/heap/cppgc-internal/`，接上 isolate 的部分在 `v8/src/heap/cppgc-js/`，下面沒有寫前綴的路徑都相對於 `v8/src/heap/`。

| | 假設 | 依據 |
| --- | --- | --- |
| A1 | 有 finalizer 的物件不會被背景 thread 釋放；finalizer 在 heap 自己的 thread 上執行。每個 Rust 物件都有 finalizer | Concurrent sweeper 碰到這類物件只記下來，由 main thread finalize（`cppgc-internal/sweeper.cc` 的 `DeferredFinalizationBuilder`）。例外有兩個：heap 被銷毀時，finalizer 在銷毀它的 thread 上執行，而接上 isolate 的 heap 跟著 `V8PerIsolateData` 銷毀，它不是 `Send`，所以一定是 heap 自己的 thread；`FreeUnreferencedObject` 在呼叫它的 thread 上執行，我們沒有用它。**單獨的 heap 被銷毀時 cppgc 自己不執行 finalizer**：`cppgc::Heap` 的解構子只收尾進行中的 GC、不 finalize 還活著的物件（`cppgc-internal/heap.cc` 的 `~Heap`），會 finalize 的 `HeapBase::Terminate` 只有 `CppHeap` 呼叫。所以 fork 的 `cppgc__StandaloneHeap__DELETE` 先做一次 `kNoHeapPointers` 的 atomic GC 再 `delete`（`build.rs` 比對這一段；單獨的 heap 見「Fork 的 `src/cppgc/slot.rs` 和新物件的初始化」） |

| A3 | 不是從 platform task 發起的 GC，會保守地掃描 stack 和 register；platform task 發起的 GC 不掃描 | 預設會掃描（`heap.h` 的 `embedder_stack_state_`），incremental marking job 的 task 改成不掃描（`incremental-marking-job.cc`）。掃描前會把 callee-saved 的暫存器推上 stack（`base/stack.cc` 的 `PushAllRegistersAndIterateStack`）。沒有由 signal 觸發的 GC：GC 一定發生在 main thread 呼叫 V8 的時候，包括 cppgc 的配置本身：接上 isolate 的 heap 回報配置量時可能同步做一次 full GC（`cppgc-js/cpp-heap.cc` 的 `ReportBufferedAllocationSizeIfPossible`），這時 stack state 是預設的 `kMayContainHeapPointers`。**單獨的 heap**（fork 的 `cppgc__StandaloneHeap__*`）用 `kNoConservativeStackScan` 建立，從不掃描 stack：要做 atomic GC 時（配置量到了、配置失敗）不當場做，改排一個 non-nestable task（`gc-invoker.cc` 的 `GCInvokerImpl::CollectGarbage`）；cppgc 每一輪 GC 只排第一步的 marking task，fork 的 `cppgc__StandaloneHeap__MarkingStep` 做 cppgc 那個 task 做的事，標完時用 heap 開始這輪 GC 的設定、`kNoHeapPointers` 收尾，`build.rs` 比對 cppgc 的這幾段和它。單獨的 heap 被銷毀時 fork 先做一次 `kNoHeapPointers` 的 GC（A1）；cppgc 自己的 `~Heap` 接著用 `kMayContainHeapPointers` 收尾進行中的 GC，但前一次 GC 之後沒有配置，所以沒有 GC 在進行 |

## 不變式

| | 不變式 | 怎麼守住 |
| --- | --- | --- |
| I10 | **`unsafe` 只出現在 `bindings`、fork 和 `ipc`（elise 照它自己的規則）** | 編譯器：`unsafe_code = "deny"`；`python3 scripts/sanity.py unsafe` 檢查 `allow(unsafe_code)` 只出現在允許的檔案。Fork 在 workspace 之外，靠審查。elise 的論證在 `../third_party/elise/docs/soundness.md`；`ipc` 不碰 GC 的物件，它的論證另外寫 |
| I14 | **用一種型別的 tag wrap 的物件都是那個型別**（`src/unified_heap.rs` 用 0x4000 到 0x4fff wrap elise 的物件的位址，一種型別一個 tag，見「`bindings` 的 unified heap（`src/unified_heap.rs`，fork 的 `src/machopo.rs` 和 V8 的 patch）」；`check_wrap_tags` 用 0x5ffe wrap 一個 cppgc 的探針，不交給 JS），所以用那個 tag `unwrap` 拿到的一定是活著的那個型別的物件 | `v8::Object::wrap` 是 `unsafe`，其他 crate 不能呼叫；`bindings` 裡只有 `src/unified_heap.rs` 的 `wrap`（經過 fork 的 `v8::machopo::wrap`）和 `check_wrap_tags` wrap 物件，不同型別不會共用 tag（A9 讓 tag 能分辨它們）。wrap 之前確認物件是 API wrapper、不管 tag 都還沒有 wrap 任何東西（fork 的 `Object::is_wrapping`）；wrapper 活著時 V8 會 trace 它 wrap 的物件，所以物件也活著。Marking 進行中、wrapper 已經被標記之後才 wrap cppgc 的物件也一樣：`v8::Object::Wrap` 寫入 `CppHeapPointer` 時有 marking barrier（`v8/src/objects/cpp-heap-object-wrapper-inl.h` 的 `SetCppHeapWrappable` 呼叫 `WriteBarrier::ForCppHeapPointer`，`build.rs` 比對），當場標記被 wrap 的物件 |

## Concurrent marking

Concurrent marking 時，marker thread 會在 main thread 修改物件的同時執行我們的 `trace()`。除了上面的不變式，還需要：

- **Slot 的讀寫不衝突**：Rust 的物件裡的 `TracedReference` 用的是 fork 的 `TracedSlot`，不是上游的型別。上游的寫入要 `&mut self`、trace 要 `&self`，concurrent 時兩個 thread 會同時持有 `&mut` 和 `&`；儲存又是 `[u8; N]`，對齊只有 1，而 C++ 把它當成 `std::atomic` 存取。Fork 的 slot：
  - bytes 放在 `UnsafeCell` 裡，每次寫入和 trace 都只把 raw 指標交給 C 函式，從不建立指向這些 bytes 的 Rust reference，和 `AtomicPtr` 一樣；
  - 對齊等於大小（一個指標）；
  - 是 `Sync`，前提是接 `&self` 的方法**全都是 `unsafe`**、契約裡寫明能在哪個 thread 上執行。
- **新物件的內容在發布前就寫好**：fork 的 `make_garbage_collected` 在 `RustObj` 的建構子裡寫入 Rust 的資料（`support.h` 的 `RustObjInit`），也就是在 cppgc 用 release store 標記「已建構完成」之前（A4）。Marker 一定先用 acquire 讀這個位元才 trace 物件（C2），所以讀得到完整的資料，包括 `trace()` 要用的 `dynamic` 指標。上游是標記之後才寫入，形式上是 data race；之前曾用兩個 fence 補，fork 改了之後就拿掉了。`build.rs` 比對這三處，rebase 弄丟時編譯失敗。

cppgc 的 concurrent marking 依賴這些 cppgc 的行為（incremental 不需要，因為 marker 只在 main thread 上執行）。它現在不打開，C1–C3 只在重新打開時要；C4 是 elise heap 的 marker 在 mutator 寫入的同時讀 `TracedReference` 的依據：

| | 假設 | 依據 |
| --- | --- | --- |
| C1 | **對同一個 `Member` 混用一般讀取和 atomic 存取是安全的**：main thread 的讀取（fork 在 Rust 裡 inline 的 relaxed atomic load，debug build 和 C++ 的 `Get()` 比對）和 marker 同時的 atomic 讀取 | 兩者都是讀，跨 thread 的寫入又全是 atomic，所以沒有 data race。但 cppgc 的 atomic 存取是把一般的記憶體 `reinterpret_cast` 成 `std::atomic`（`v8/include/cppgc/internal/member-storage.h`），C++ 標準不保證這樣做有效，V8 依賴的是編譯器實際的行為。**所以 concurrent 形式上最多只能做到和 V8 本身一樣** |
| C2 | **Marker 讀物件內容之前，一定和寫入它的 thread 同步過**；insertion barrier 加上最後 pause 重新掃描 root 和 stack，就不會漏標 | 每條讓 marker 開始 trace 一個物件的路徑，都先用 acquire 讀「已建構完成」位元（`cppgc-internal/marking-state.h`、`heap-object-header.h`），或經過 mutex 保護的 worklist 交接（`base/worklist.h`）。Marker 用 relaxed 讀到 slot 裡的新指標之後，acquire 讀目標的 header 仍可能讀到舊的「建構中」位元（slot 的讀取不帶同步）：cppgc 這時把物件放進 not-fully-constructed worklist，最後的 pause 再處理（`marker.cc` 的 `MarkNotFullyConstructedObjects`），讀到「已建構完成」時才 trace，而那次 acquire 就和建構子的寫入同步了。cppgc 沒有 black allocation（`object-allocator.cc` 在 marking 中不設 mark bit），新物件靠 insertion barrier 或 pause 的 root、stack 掃描被找到。Barrier 只有 insertion（Dijkstra），沒有 deletion barrier（`write-barrier.cc`）；最後的 pause 重新掃描 persistent，並依 stack state 決定是否掃描 stack（`marker.cc`） |
| C3 | **GC 自己寫入 slot，只在 mutator 停下時** | 清除死掉的 weak slot 可能在 worker thread 上做，但都在最後的 pause 裡，而且 `Join` 之後 pause 才結束（`marker.cc`）；compaction 只在 pause 裡 |
| C4 | **`TracedReference` 可以在 main thread 寫入的同時被 marker trace** | Slot 只存一個指向 V8 traced handle 節點的指標，讀寫都是 relaxed atomic（`v8/include/v8-traced-handle.h` 的 `SetSlotThreadSafe` / `GetSlotThreadSafe`）。節點的內容另外發布：`TracedNode::Publish` 用 release store 寫入物件（`v8/src/handles/traced-handles-inl.h`），`TracedHandles::Mark` 用 acquire load 讀（`v8/src/handles/traced-handles.cc`）。Marking 中 destroy 只用 atomic store 清掉物件，節點到最後的 pause 才釋放，所以 marker 讀到舊的 slot 也是活的節點。Blink 依賴的是同一套，所以 `TracedSlot` 不需要自己同步 |

**cppgc 的 concurrent 不會打開。** 標記方式固定 incremental；V8 有一條不檢查我們設定、把 incremental 升級成 concurrent 的路徑：一輪 GC 在 efficiency mode 下開始時，會呼叫 `CppHeap::ReEnableConcurrentMarking`。`bindings::initialize` 一律在所有 flag 之後加上 `--no-single-threaded-gc-in-background` 關掉它。`CppHeap::SelectMarkingType` 只會降級、不會升級，所以這是唯一的升級路徑。換成 elise heap 之後 `CppHeap` 上沒有 machopo 的物件，升級了 cppgc 的 marker 也只會看到空的 worklist（V8 交給 embedder 的物件經過 fork 的 `Hand` 進 elise heap 的 marker，不進 cppgc 的）；仍然關著，是因為這條路沒有在有 DCHECK 的 V8 上跑過，打開它也沒有好處（它只在 isolate 降低 priority 時有作用，machopo 沒有背景分頁）。

**重新打開 cppgc 的 concurrent 之前還要處理的**：
- TSan：自己編 V8 之後做得到了，但還沒做。cppgc 的 marking verifier 已經在 debug 的 V8 裡（見「怎麼驗證的」），但它只在最後的 pause 檢查標記的結果，抓不到碰巧沒出事的 race；
- 記憶體順序的錯誤測不出來：x86-64 不會重排寫入，ARM64 會，但 stress 也很難碰上（曾在 ARM64 上拿掉 release fence，測試照樣通過），所以只能靠審查。

## 找到並修正過的問題

| 問題 | 後果 | 修正 | 怎麼確認 |
| --- | --- | --- | --- |
| 上游的 `Member::set` / `TracedReference::reset` 要 `&mut self`、trace 要 `&self` | Concurrent 模式下違反 aliasing 規則 | 自己的 slot 型別，只用 raw 指標（最早在 `bindings`，2026-10-02 搬進 fork） | `bindings` 的 `cppgc_member`、`cppgc_traced` 測試；直接用上游的型別會被 clippy 的 `disallowed-types` 擋下 |
| 上游的 slot 是 `[u8; N]`，對齊只有 1，`NodeKindData::Element` 的 `template_content` 被放在 offset 1 | 沒對齊的 `std::atomic` 存取；ARM64 上不保證 atomic | Slot 對齊到它的大小 | 對齊測試（`bindings` 的 `cppgc_member`，跟著只有已刪的舊的 DOM 用的 `MemberSlot` 拿掉了）；`TracedSlot` 的對齊由 fork 的 const assert 檢查（A5） |
| 新物件的 Rust 資料在 C++ 的 release 之後才寫入 | Concurrent 時形式上有 data race；ARM64 上 marker 可能讀到舊的 `dynamic` 指標而 crash | 最早用 `assign` 的 release fence 加上 `trace` 的 acquire fence 補；fork 改成在建構子裡寫入之後拿掉 | 對照 cppgc 原始碼，`build.rs` 比對。測試測不出來 |
| 測試用的 safe 函式接受任何 `&Heap` | Safe code 可以把接了 isolate 的 heap 傳進去，違反 V8 的前提（release build 不檢查） | `DetachedHeap` | 型別檢查 |
| 單獨的 heap 被銷毀時沒有任何 finalizer 執行（2026-10-06 審查時發現） | 不是 UB，是洩漏：wasm 文件的 DOM 拆掉時，還活著的每個節點、listener、holder 的 Rust `Drop` 都不跑，`NodeState` 的字串和 `Arc<ComputedStyle>` 全部漏掉 | Fork 的 `cppgc__StandaloneHeap__DELETE` 先做一次 `kNoHeapPointers` 的 GC 再 `delete`（A1）；之後單獨的 heap 沒有 crate 用，fork 拿掉了它 | — |
| `dom_js` 把 `DOMException` 的 constructor 用 `v8::Global` 放在 context 的 slot（2026-10-07，實驗時發現） | 不是 UB，是洩漏：slot 是 V8 看不見的 Rust 的表，`Global` 在那裡是 root，撐住 constructor，constructor 撐住 context，context 撐住 slot；每個丟掉的 realm 連同它的 window、document 和整棵樹都不會被回收 | 改放 context 的 embedder data（V8 把它當成 context 的一部分 trace）；規則寫在當時的 `dom_js` 的 README`：context 的 slot 不放 `v8::Global` | 當時 `dom_js` 的 `realms` 的 `a_dropped_realm_is_collected_with_its_document`，改回 slot 時失敗（跟著 `dom_js` 拿掉了）；`bindings` 的 `modules_go_with_their_realm` 測模組的表不撐住 context |
| 上游 rusty_v8 的 `Weak` 在 isolate 拆掉的期間被 drop 時，不 reset V8 的 handle 就釋放 `WeakData`（2026-10-08，`test.py fuzz` 在 `--stress-compaction` 底下找到） | Use-after-free：`OwnedIsolate::drop` 先 dispose isolate 的 handle，再跑 guaranteed finalizer（context 的 annex 在這裡釋放，連同看著 context 的 `Weak<Context>` 和 slot 裡的 `Weak`），最後才是 V8 自己的拆除；`Weak` 看到 handle 已 dispose，就當成 callback 不會再來，但 V8 拆除時的 GC 還是用釋放掉的 `WeakData` 呼叫 first pass callback（access violation，或 V8 的 `Check failed: node->IsInUse()`）。之前 `bindings` 的測試沒有 context 放 slot，所以沒碰到 | Fork 的 `Weak` 的 `Drop`：指標還在時 leak `WeakData`（和 second pass 還沒跑時一樣），標成已 drop，有 second pass 時由它釋放；代價是 isolate 拆掉時還登記著、V8 又不回呼的每個 weak handle 留下一個 `WeakData` | `bindings` 的 `isolate_teardown`（自己的 binary，帶 `--stress-compaction`）：拿掉修正時每次都 crash，一般的 `cargo test` 就會跑 |

## 怎麼驗證的

- **編譯期**：clippy 的 `disallowed-types` / `disallowed-methods` / `undocumented_unsafe_blocks`、`unsafe_code = "deny"`、`bindings` 的 `build.rs`。
- **V8 的 DCHECK**：`python3 scripts/test.py matrix`、`fuzz` 連結 debug 的 V8（`V8_FORCE_DEBUG=1`；fork 的 release 兩種都有，Windows 例外），所以 `bindings`、`dom_js` 的測試在 V8 自己的 DCHECK 底下跑。一般的 build 和 `cargo test` 連結 release 的，沒有 DCHECK；`matrix` 和 `fuzz` 由每週的 CI 跑（開發機上不跑；動到 GC 時手動開始一次），所以 GC 的修改、這兩個 crate 其他部分的修改（例如 binding 或 script 的入口）在下一次 CI 之前不一定在 DCHECK 底下測過；`browser`、`shell` 這些也會執行 script 的端到端測試不在 DCHECK 底下跑（在 debug 的 V8 底下跑全部的測試太花時間，而 `unsafe` 依賴 V8 前提的那幾個 crate 已經由 `matrix` 涵蓋）。DCHECK 抓到過一個測試在建立 heap 之前就建立 slot。
- **Heap verifier**：debug 的 V8 打開了 V8 的 verification features，所以 cppgc 的 marking verifier（`CPPGC_VERIFY_HEAP`）在每一輪 cppgc 的 GC（接上 isolate 的和單獨的 heap 都是）標記完、sweep 之前，重新走一遍標記過的物件，碰到指向沒標記物件的 edge 就 `FATAL`，印出父子兩個物件的型別。漏掉 write barrier 時，它在釋放之前就報錯；release 的 V8 要等讀到被釋放的記憶體才 crash（2026-10-05 用當時的 `dom` 確認：讓 `Edge::set_from` 直接複製 bytes、跳過 barrier，`incremental_stress` 在 debug 的 V8 是 `MarkingVerifier: Encountered unmarked object`，在 release 的是 SIGBUS）。JS heap 的 `--verify-heap` 沒有用（原因見 `docs/test-gaps.md` 的「缺少的工具和檢查」）。
- **測試**：`bindings` 的 `cppgc_traced`、`cppgc_traced_marking`、`v8_smoke`、`isolate_teardown`，unified heap 的 `unified_heap`、`unified_heap_marking`、`unified_heap_linear`（見那一節），`dom_js` 的測試，以及 `python3 scripts/test.py matrix` 和 `fuzz`。
- **Mutation test**：暫時弄壞實作，確認有測試失敗。結果和次數記在每份 RFC 的 `progress.md`；做過的範圍：
  - Fork 的 slot：`TracedSlot` 的 trace / `is_empty` / `set` / 清除；
  - `build.rs` 比對的原始碼。
- **抓不到、也不用抓的 mutation**（等價，或只靠審查）：
  - `TracedSlot` 的 `Drop` 不 destroy V8 的節點：finalizer 在 sweeping 中執行，V8 這時本來就不釋放節點，下一輪 GC 才回收（A7）；heap 銷毀時整張表一起釋放。所以這個 destroy 只在 sweeping 以外的 drop 有作用，而 `TracedSlot` 只放在 GC 物件裡。
- **沒有的**：TSan（做得到，還沒做）、Miri（不能執行 FFI）、能抓到記憶體順序錯誤的測試、ARM64 的 CI。

## 需要人工審查的地方

以下的正確性編譯器檢查不了，修改時要特別仔細。

### 通用做法

- **找出所有要審的地方**：`grep -rn "unsafe" crates/bindings`，加上 fork 裡標了 `machopo:` 的修改（`src/cppgc/`、`src/cppgc.rs` 的 `init_rust_obj`、`src/support.h` 的 `RustObj`、`src/binding.cc`、`src/machopo.rs`，和 V8 fork 裡的 `include/v8-machopo.h` 和它改的 `src/heap/`；完整清單在 fork 的 `README.machopo.md`）。
- **確認 SAFETY 註解還成立**：clippy 強制每個 `unsafe` 區塊都要有 `// SAFETY:` 註解，但不檢查內容。程式碼改了，註解常常沒跟著改。
- **對照上面的不變式**：改動會不會讓哪一條不再成立？
- **`#[allow(unsafe_code)]` 的位置**：只應該出現在 `bindings` 的 crate root，以及直接使用 `unsafe` API 的測試檔（`ipc` 也在允許清單裡，但不屬於這份的範圍）。
- **改了下面這些地方，就做一次 mutation test。**

### Fork 的 `src/cppgc/slot.rs` 和新物件的初始化

`TracedSlot` 的 `unsafe impl Sync` 是 concurrent marking 安全的依據。
- **`Sync` 的前提**：接 `&self` 的方法是不是**全部**都還是 `unsafe`？加一個 safe 的 `&self` 寫入方法，`unsafe impl Sync` 就不再成立，而編譯器完全不會察覺。這是最重要的一條。
- **沒有 reference**：有沒有地方建立了指向 storage 的 `&` / `&mut`？應該只有 raw 指標。
- **Layout**：大小和對齊的 const assert 還在不在。
- **`extern` 宣告和 C 簽章一一對應**：`TracedSlot` 自己宣告了 `v8__TracedReference__*`，要和 `src/binding.cc` 一致（參數個數、順序、指標或值）。Rust 不檢查跨語言的簽章。
- **`TracedSlot`**：`trace` 碰到空的 slot 不呼叫 C++（所以沒接 isolate 的 heap 上，空的 `TracedSlot` 不會讓 cppgc 用一般的 visitor trace `TracedReference`，A7），`is_empty` 用 relaxed atomic 讀，和 `GetSlotThreadSafe` 一樣；非空的 slot 不能搬動，`set` 的契約要求 slot 已經在 heap 上的 GC 物件裡；順序由 V8 保證（C4），改成自己讀寫 traced handle 的節點就不再成立。
- **新物件的初始化**：`init_rust_obj` 要在建構子裡寫入 value 和 `dynamic` 兩者；`make_garbage_collected` 不能改回「配置之後才寫入」。這是 slot 不需要 fence 的唯一理由。

升級 V8 或 rebase fork 時：
- **`build.rs` 失敗**：照錯誤訊息重讀對應的 C++ 函式，確認語意沒變，再更新比對的字串。不要只是把字串換成新的內容就結束。
- **`build.rs` 沒有檢查的 cppgc 語意**，要自己確認 A4：`cppgc/member.h` 的 `operator=` 還是用 `SetRawAtomic`，`cppgc/visitor.h` 的 `Trace(const Member&)` 還是用 `GetAtomic`。
- **fork 在 Rust 裡讀 `Member`**（照 `cppgc__POINTER_COMPRESSION_SHIFT` 和只讀一次的 cage base 解壓縮）**和 `Persistent`**（`PersistentBase` 的第一個欄位）：升級時確認 `Member::Get`、`Persistent::Get` 的實作和壓縮方式沒變（A5）。debug build 每次讀都和 C++ 比對，但只在測試踩到時有用。
- **重新確認 A1–A3、A9 和 C2、C3**：它們是讀 V8 原始碼得到的。A9 要看 `ReadCppHeapPointerField` 的範圍檢查和 tag 的分區還一樣（`build.rs` 比對分區），啟動時的自我檢查只驗證一組 tag。
- **cppgc 的 build 設定**：A4、C1–C4 是照壓縮的 `Member`（4 bytes 的 `CompressedPointer`）論證的。V8 在 x64、arm64 上預設開 cppgc 的 caged heap（`v8/BUILD.gn` 的 `cppgc_enable_caged_heap`），它會一起編進 cppgc 的 pointer compression 和 young generation。這和 V8 本身的 pointer compression 無關。改變這些 GN 參數時，要重讀 A4、C1–C4 和 A10。

### `bindings` 的 V8 callback 和 context 的 slot

`promise_reject_callback`、module 的 `resolve_module` 和 `initialize_import_meta` 都用 `v8::callback_scope!` 開 scope，是 `unsafe`；跨 origin 的物件的 access check（`isolate_state.rs` 的 `access_check`，V8 的 `AccessCheckCallback`）和拒絕的回報（`refused_access`，`FailedAccessCheckCallback`）也是：V8 只在 script 存取那個物件、或呼叫成員檢查 receiver 時（isolate 的 thread 上、在存取的那個 context 裡）呼叫它們。`Error.isError` 問 API wrapper 是不是 native error 的 `is_native_error_wrapper`（fork 的 `IsJSApiWrapperNativeErrorCallback`）也一樣：V8 只在 script 執行 `Error.isError` 時呼叫，從物件開 callback scope，交給 DOM 的 `NativeErrorCheck`（安全的函式，只讀物件的 private、不執行 JS）。拒絕的回報只拿到物件、沒有 context，scope 從 isolate 開：fork 讓 `Local<Object>` 的 `GetIsolate` 用 thread 現在的 isolate（和 `Local<Context>` 的一樣，V8 呼叫時那個 isolate 是 entered 的）。兩者都不借狀態以外的東西：access check 只讀 security token（不執行 JS，V8 那時是 `EXTERNAL`），回報只丟例外：
- **只在 V8 執行 script 或 link 的當下被呼叫**：SAFETY 的依據是「V8 在 isolate 的 thread 上、在那個 context 裡呼叫」。不能從別的地方直接呼叫它們，也不能把它們設成會在 GC 中被呼叫的 callback。
- **不碰 DOM**：promise 和 module 的 callback 不借 isolate 的狀態，也不需要；access check 和拒絕的回報經過 `StateScope` 借，照「`bindings` 的 isolate 的狀態（`src/isolate_state.rs`）」的規則。要碰 DOM 的工作（例如回報 module 的例外）放在 JS 的 handler 裡，由入口執行。
- **context 的 slot 不放強的 `v8::Global`**：slot 是 V8 看不見的 Rust 的表，`Global` 在那裡是 root，值撐住 context 時 context 永遠收不掉（「找到並修正過的問題」）。module 的表在 slot 裡只放 `v8::Weak` 和不含 V8 值的資料，強參照在 `ModuleRecords`，由 realm 的擁有者拿著。唯一的例外是等待中的 `import()` 的 promise（callback 和 handler 只拿得到 context）：`ModuleRecords` 的 `Drop` 清掉它們，所以 realm 丟掉之後 slot 裡不剩強參照；新增這種例外時要有同樣的清除，並測 realm 丟掉之後被回收（`bindings` 的 `modules_go_with_their_realm` 測模組的表；等待中的 `import()` 現在沒有這樣的測試）。slot 在 context 被回收時、GC 的第二階段才釋放，那時 drop `v8::Weak` 是安全的（rusty_v8 的 `Weak` 的 `Drop` 處理了 finalizer 已經跑過的情況）；isolate 拆掉時 slot 在 V8 的拆除之前釋放，靠的是 fork 對 `Weak` 的 `Drop` 的修正（「找到並修正過的問題」、「可以回報上游的修改」第 4 項）。

### `bindings` 的 isolate 的狀態（`src/isolate_state.rs`）

DOM 的 binding 用的，和 DOM 無關：

- **isolate 的狀態**（`set_isolate_state`、`isolate_state_mut`、`StateScope`、`drop_isolate_state`）：狀態和它的型別的 `TypeId`、drop 函式、embedder heap 的 registration（有的話）放在同一個 box 裡（`#[repr(C)] Slot<T>`，前三個在前面，所以對任何 `T` 都在同一個 offset），放在 V8 的 embedder 的 isolate data slot 0（rusty_v8 自己的 slot 之後）。論證：
  - **只設一次，只有 isolate 的擁有者放掉**：第二次 `set_isolate_state` panic；`drop_isolate_state` 是 `unsafe`，契約是之後 isolate 不再跑任何 callback（`V8PerIsolateData` 的 drop 第一件事呼叫它，isolate 拆掉時沒有 callback 在跑）；沒呼叫就是漏掉，不是 use-after-free。它先拿出 registration 放掉（slot 還設著、沒有人借著狀態：V8 進行中的 GC 在這時收尾，經過 slot 拿到完整的狀態），再清空 slot、照建的時候的 `T` 放掉整個 box。
  - **只經過 isolate 借，借用不重疊**：`isolate_state_mut` 拿 `&mut Isolate`、給的 `&mut T` 活得和那個借用一樣久；`StateScope` 拿 `&mut PinScope`，`state`、`state_mut` 借 `&mut self` 給 `&T`、`&mut T` 和 `NoGc`（`NoGc` 拿著 scope）。所以 Rust 這一側同時只有一份借用（狀態不在 isolate 的記憶體裡，`&mut Isolate` 和 `&mut T` 不重疊）。巢狀的 callback 只會在外層把 scope 交給 V8 時進來（V8 的呼叫都要完整的 scope），那時外層手上不可能有狀態的借用（它佔著 scope）；V8 的 GC 經過 slot 拿狀態（下面的 `StateHeap`）也一樣。新增拿狀態的路要照樣綁在 isolate 的借用上，不能給不綁借用的參照（以前的 `StateRef`）。
  - **讀 slot 不檢查的那條路**：`StateScope::new` 檢查一次 slot 的型別；state callback（`state_function_template` 的 trampoline）不檢查，release 只讀 slot、加上 `value` 的 offset（`isolate_state::unchecked`，debug build 照樣檢查）。成立的理由：這兩個函式在 isolate 的狀態不是 `T` 時 panic、不建 template；template 是它的 isolate 的（`FunctionTemplate` 在給的 scope 上 build，callback 掛不到別的 isolate 的 template 上：rusty_v8 不讓一個 isolate 的 handle 在另一個 isolate 打開，`Global`、`Weak` 會檢查）；狀態只設一次、和 isolate 一起放掉，放掉之後不跑 callback（`drop_isolate_state` 的契約）。`set_state_indexed_getter` 收的 `ObjectTemplate` 要是那個 scope 的 isolate 的（`dom_js` 用同一個 scope 建的）。跨 origin 的物件的 access check 和它拒絕時的 interceptor（`set_state_access_check`）、拒絕的回報（`set_state_refused_access`，isolate 的：V8 存在 isolate 自己的 `ThreadLocalTop`）照同樣的理由不檢查：裝的時候檢查，template 和 isolate 是那個狀態的。

  - **只拿 callback 的 info 的 callback**（`StateInfo`、`StateInfoMethod`、`state_info_method_template`、`InfoNoGc`；fork 的 `FunctionCallbackInfo::isolate`）：trampoline 是 V8 自己的 callback（`FunctionTemplate::builder_raw`，`extern "C"`，panic 穿過它 abort），不建 rusty_v8 的 `CallbackScope`：那是 rusty_v8 自己記 isolate 的結構，V8 不需要它（callback 的 handle scope 是 V8 在呼叫前後自己開關的）。論證：
    - **isolate**：`StateInfo::isolate` 從 frame 上放 isolate 指標的那一格做 `&mut Isolate`（`Isolate` 是那個指標，`repr(transparent)`；rusty_v8 的 `CallbackScope::new` 讀同一格，debug build 和 V8 的 `GetIsolate` 比對）。那一格在 callback 期間有效（`'s`，info 的 lifetime），借用跟著 `&mut self`；`StateInfo` 每個 callback 只有 trampoline 建的那一個、不能複製，所以同一格同時只有一份參照。`with_scope` 建的 scope 自己存一份指標（不是那一格的記憶體），外層的 Rust 拿的 `&mut Isolate`、`&mut V8PerIsolateData` 也在別的位置：和 scope 一樣照 A8。
    - **狀態的借用照「只經過 isolate 借」**：`state`、`state_mut` 借 `&mut self`，給 `&T`、`&mut T` 和 `InfoNoGc`（拿著 isolate 和回傳值）。借著的期間 `StateInfo` 的其他方法（`isolate`、`with_scope`）都呼叫不了，能碰 V8 的只有 `InfoNoGc`：`unwrap`、`unwrap_receiver`、`wrap`、`set_wrapper`、`set_strong`、`set_strong_value`、`refers_to`、`return_wrapper`、`return_value`、`return_global`、`return_weak`、`ascii` 和 `ret`（`OpReturn`），就是 `NoGc` 裡只需要 isolate 的那幾個（`set_wrapper`、`set_strong`、`set_strong_value` 建的是 traced handle，不是 `Local`：fork 的 `TracedSlot::set`、`set_droppable` 收 isolate；`refers_to` 只讀邊的 traced handle 指的物件的位址，和 handle 的比，fork 的 `TracedSlot::refers_to`），理由一樣（下面「拿著狀態時只能用 `NoGc` 和 `OpReturn`」）。回傳值在借著狀態時只以 `OpReturn` 給出去；完整的 `ReturnValue`（有會配置的 setter）只在 `with_scope` 裡給，那時狀態沒有被借。`args` 給的參數只能讀（`This`、`Length`、每個參數、`NewTarget`、`Data`），不配置。讀 slot 不檢查：照上一條，template 在狀態是 `T` 的地方建（`state_info_method_template` 檢查）。
    - **沒有 signature 的函式的 info 沒有 `Receiver`**：`StateInfo<'s, T, K>` 的 `K` 是 `Signed`（`state_info_method_template`：signature 設在 builder 的最後）或 `Unsigned`（`state_info_function_template`：static 的 operation，`this` 是任何值）。`receiver()` 只在 `Signed` 上有，trampoline 各建各的，所以 `Receiver`（不讀 map 就 unwrap）只會從 V8 檢查過的 `this` 做出來。
    - **indexed getter 的 info**（`StateIndexInfo`、`StateInfoIndexedGetter`、`set_state_info_indexed_getter`；fork 的 `PropertyCallbackInfo::isolate`、`arguments`）：trampoline 是 V8 自己的 interceptor callback（`getter_raw`），和函式的一樣不建 `CallbackScope`。isolate 的指標從 info 讀一次（V8 的 `GetIsolate`）、放在 `StateIndexInfo` 裡，`&mut Isolate` 借的是那個欄位，每個 callback 只有 trampoline 建的那一個；狀態的借用、`with_scope` 的論證和 `StateInfo` 的相同（`InfoState` 是兩者共同的介面）。`holder()` 給 `Receiver`：interceptor 裝在這個模組給的 object template 上，V8 用裝著 interceptor 的那個物件呼叫它。**named interceptor 的 callback**（`info_named_query_trampoline`、`…delete…`、`…define…`、`…enumerate…`，和數字當名稱的 `info_index_*_trampoline`；`StateInfoNamed`）全部是 V8 自己的 callback。回傳值不是 `Value` 的（`Integer`、`Boolean`、`Array`）info 經過 `value_info` 轉成 `<Value>` 的 info 再做成 `StateNameInfo`、`StateIndexInfo`，論證同下面的索引 query：型別只是 phantom；被呼叫的一方寫進回傳值的東西（query 的 getter 不寫：`NamedHas`；enumerate 寫的就是結果的陣列）不是 callback 的結果時，由 trampoline 用原本型別的 info 蓋過，或落在 V8 不讀回傳值的情況（沒有這個屬性、有例外）。數字的名稱（`index_name`）和 define 的值（`defined`）在 trampoline 當場用 info 開的 `CallbackScope` 裡建：scope 在 info 交給被呼叫的一方之前就結束，建的 handle 是 V8 替 callback 開的 handle scope 的（和 `with_scope` 的論證相同）。define 的 descriptor 的值在 descriptor 活著時複製進那個 handle scope。**query 和 enumerator**（`info_indexed_query_trampoline`、`info_indexed_enumerate_trampoline`，V8 自己的 `query_raw`、`enumerator_raw`）拿到的是 `PropertyCallbackInfo<Integer>`、`<Array>`：交給 `StateInfoIndexedGetter::query`、`length` 之前轉成 `<Value>` 的 info，和 named setter 的 trampoline 同一個論證（回傳值的型別只是 rusty_v8 的 phantom，info 是 `repr(C)` 包著原始的 info）；兩個 callback 都不經過 `StateIndexInfo` 寫回傳值（它們回的是 `Option<bool>` 和 `u32`），attribute 和陣列由 trampoline 用原本型別的 info 寫。enumerator 的陣列在 trampoline 當場用 info 開的 `CallbackScope` 裡建，論證和 `with_scope` 的相同。
    - **named property 的 info**（`StateNameInfo`、`StateInfoNamedGetter`、`StateInfoNamedSetter`、`info_named_getter`、`info_named_setter`；fork 的 `SealedLocal::unseal_in_callback`）：和 `StateIndexInfo` 同一個論證。名稱和值是 V8 傳給 callback 的 handle（rusty_v8 包成 `SealedLocal`，它自己的 trampoline 在建好的 scope 上解開），lifetime 給 info 的。setter 的 info 是 `PropertyCallbackInfo<Boolean>`，轉成 `<Value>` 的參照：rusty_v8 的那個型別參數只是 `PhantomData`（struct 是 `repr(C)`），而 setter 的回傳值那一格從不寫（`dom_js` 的 setter 把布林的結果記下來、不經過 `OpReturn`）。
    - **`InfoNoGc::current_global`**（fork 的 `Context::current_global`）：`GetCurrentContext()->Global()`，兩個都只在 V8 替 callback 開的 handle scope 裡加一個 handle，不配置 heap、不呼叫回來。callback 裡一定有進入的 context（V8 呼叫 API 函式前進入它的 context），handle 的 lifetime 是 info 的。
    - **`InfoNoGc::strong_value`**（fork 的 `TracedSlot::get_in_callback`）：`TracedReference::Get`，只在 V8 替 callback 開的 handle scope 裡加一個 handle（和有 scope 的 `strong_value` 同一個呼叫，差在 handle 的 lifetime 是 info 的，不是 rusty_v8 的 scope 的）。
    - **`with_scope` 的 handle 活得比 scope 久**：`CallbackScope::new` 從 info 建的 scope 不開 handle scope（`needs_scope` 是 false），在它上面建的 handle 在 V8 替 callback 開的那個 handle scope 裡，到 callback 返回為止；rusty_v8 給它們的 lifetime 也是 info 的（`PinnedRef<CallbackScope<'i>>` 的 `Deref` 的註解），不是 scope 那個區域變數的。所以 `with_scope` 回傳之後 handle 還能用（`dom_js` 把轉換好的字串參數帶出來）。
    - **`Receiver`**：`StateInfo::receiver` 用 `This()` 建，只在 `Signed` 的 info 上有：那是 `state_info_method_template`（signature 放在 builder 的最後）和 `state_cached_getter_template`（signature 是必填的參數）的 trampoline 建的，所以照下面「檢查過的 receiver 不再讀 map」。call handler（`set_state_call_as_function_handler`）的 info 是 `Unsigned` 的：`this` 是被呼叫的物件，這裡不替它做保證。
    - **`ReturnValue::set_traced` 收 isolate**（fork）：release 直接從 traced handle 的 node 讀物件寫進回傳值；debug build（和沒有指標壓縮的 build）另外呼叫 V8 自己的 setter 對照，那個 `Local` 建在 V8 目前的 handle scope 裡（`TracedSlot::get_in_current_scope`：callback 的那個；不在 V8 的 heap 上配置，同 `NoGc` 的 `wrapper`）。

### `bindings` 的 unified heap（`src/unified_heap.rs`，fork 的 `src/machopo.rs` 和 V8 的 patch）

elise 的 heap 經過 V8 fork 的 patch（`include/v8-machopo.h`）在 V8 的 major GC 裡標記，照 cppgc 的物件在 Chrome 的 unified heap 裡的方式；elise 那一側的論證在 `../third_party/elise/docs/soundness.md` 的 I11。fork 的 `v8::machopo` 是 glue 的 C 函式的薄包裝（帶型別的指標、`unsafe` 的契約），`bindings` 在它上面接 elise。
- **wrapper 存物件的位址，tag 是 0x4000 加上型別在 elise 的表裡的編號**（`wrap::<T>`、`unwrap::<T>`；編號在 `elise::MAX_TYPES`（4096）以下，0x4000 到 0x4fff 剛好放得下，編譯期的 assert，所以 `tag` 用遮罩取、不每次檢查範圍）：只有 patch（`machopo::kTagRange`，0x4000 到 0x4fff）和這個檔案用這段 tag（`check_wrap_tags` 的探針用 0x5ffe、0x5fff）。所以用 `T` 的 tag 讀出的位址一定是 `wrap::<T>` 寫的，也就是 `elise::Mutation::engine_address` 給的一個 `T` 的位址（I14 的做法：一種 tag 一種型別）。那一格存的不是 cppgc 的物件：patch 讓 V8 的標記（主要的和 young 的 visitor）、wrap 的 write barrier、heap snapshot、heap profiler 碰到這段 tag 時不把它當 cppgc 的物件，標記時把位址交給 elise 的 heap。patch 靠 `CppHeapPointerTable` 的 tag 分辨，只在開了 pointer compression 時成立（machopo 每個平台都開）。`wrap` 之前確認是還沒 wrap 任何東西的 API wrapper，patch 再 `CHECK` 一次 API wrapper 和 tag 的範圍；`unwrap` 和 `is_wrapper` 只讀那一個 tag 的，別的 tag 的、不是 API wrapper 的讀出來是 null。fork 的 `unwrap` 對 API wrapper（map 的 instance type 是 V8 的 API 物件的）在 Rust 裡讀，照 V8 標頭檔 inline 的 `ReadCppHeapPointerField`：物件的 header 之後的 handle、isolate 的 `CppHeapPointerTable` 的那一格（relaxed atomic，和 V8 一樣）、那一格的 tag；別的物件經過 glue 的 C 函式。讀法依賴的 offset 和常數記在 fork 的 `README.machopo.md`，升級 V8 時照 `include/v8-internal.h` 核對；debug build 每次也呼叫 C 函式、assert 兩者相同。
- **檢查過的 receiver 不再讀 map**（`unwrap_receiver`、`Receiver`、`StateInfo::receiver`）：`Receiver` 的欄位是 private，只在 `src/isolate_state.rs` 建：有 signature 的 function 的 info（`state_info_method_template` 把 signature 放在 builder 的最後，`configure` 改不掉；`state_cached_getter_template` 的 signature 是必填的）用 `This()` 建，indexed interceptor 的 trampoline 用 `Holder()` 建（A11）。所以拿到 `Receiver` 的就是 header 之後有 `CppHeapPointerHandle` 的物件（API wrapper，或 window 的 global proxy：machopo wrap 的就是 proxy），fork 的 `unwrap_receiver` 跳過 instance type 的檢查，直接讀 header 之後的 handle、那一格和它的 tag，和 `unwrap` 一樣比 tag（I14），還沒 wrap 的、別的型別的讀出來是 null；位址照樣交給 `from_engine` 檢查 cage、經過讀取的 barrier。新增建 `Receiver` 的地方，要是 V8 保證那個物件是 template 建的。沒有 signature 的路（constructor、static 的成員、legacy caller、iterator 的 target、參數裡的物件）用 `Unsigned` 的 info 或 `StateCallback`，照舊用 `unwrap`。
- **位址指著活的物件**：wrapper 活著時一直撐著它的物件（V8 標到 wrapper 就交出物件，elise 的 I11），物件在 driven 的 heap 的 old、不搬。標記中才 wrap 的不交出：V8 的 write barrier 碰到這段 tag 就返回，因為物件已經是標過的（標記中配置的是黑的；之前的在 SATB 的快照裡，或經過會標記的讀取拿到）；這條假設由 elise 的 fuzz 的假 engine 守著（下面）。`unwrap` 交給 `elise::Mutation::from_engine`，它再檢查位址在那個操作的 heap 的 cage 裡（不同 heap 的 cage 不重疊），所以拿錯 heap 的操作只會 panic。
- **借出 V8 字串的字元**（`src/v8_text.rs` 的 `LentString`，fork 的 `v8::machopo::one_byte_chars`）：fork 照 V8 標頭檔的佈局讀字串（map 的 instance type、header 之後的長度和字元，thin string 跟著它指的那一個走一次），只回答平的 one-byte 字串，debug build 每次和 `ValueView` 比對；依賴的常數記在 fork 的 `README.machopo.md`。`LentString::ascii` 借出那段字元當 `&str`（只借 ASCII：Latin-1 不是 UTF-8；只檢查一次：第一次找到 ASCII 之後記下，之後只重讀位置不再掃。V8 字串的字元不會變，GC 只會搬動它，或把它變成 thin string、指向同樣的字元；變成別的排列（像 externalize）時 fork 不回答，照樣不借），論證：字串由它的 `Local` 撐著活到 `'s`；字元在 GC 之前不會搬，而**借出期間 GC 一定 abort**：第一次借出時 thread 的計數加一、`LentString` drop 時減一，回傳的 `&str` 借著 `LentString`，所以它活著時計數不是 0；`V8PerIsolateData::new` 給 isolate 一個 GC prologue（`kGCTypeAll`：scavenge 也搬字串），在 isolate 的 thread 上、任何東西搬動之前看計數，不是 0 就 abort；沒有這個 prologue 的 isolate 用 data slot 1 認出來，一律不借。前提（和 rusty_v8 的 `ValueView::new` 一樣，不檢查）：字串是傳進來的 isolate 的，計數是 thread 的，prologue 裝在 machopo 建的每個 isolate 上（正式程式只有 `V8PerIsolateData::new` 建 isolate）；binding 讀的是 callback 在它的 isolate 上拿到的參數。從 `Local` 拿回 `'s` 的那個轉換照 rusty_v8 的 `ValueView::new`。`LentString::lending`（`new` 加 `lends` 合成一步，給字串參數用）先用同一個 `chars` 檢查（裝了 prologue 的 isolate、平的 one-byte、ASCII），通過了才建出 `LentString`、直接記成「已知 ASCII」，所以它和先 `new` 再 `lends` 得到的是同一個狀態；兩個旗標（借出了沒有、已知 ASCII）放在同一個字裡，只是為了讓編譯器搬這個結構時讀寫的寬度一致（分開的兩個 byte 被當成一個字搬走時 CPU 不能 forward），不影響論證。`LentString::peek_ascii` 只在一次 closure 的呼叫裡借出：呼叫前計數加一、回來後減一，`&str` 只是 closure 的參數、活不過那次呼叫，所以借出期間的 GC 一樣 abort（closure panic 時計數留著，之後的 GC 也 abort，不會讀到搬走的字元）。改的時候：不能讓 `&str` 活得比 `LentString`（`peek_ascii` 的是那次呼叫）久，不能在 prologue 以外的地方放寬計數，新增建 isolate 的地方要裝 prologue。 **`LentString::latin1_to_utf8`**（給不是 ASCII、借不出去的字串的複本）：同樣只在裝了 prologue 的 isolate 上，用 `one_byte_chars` 拿到扁平 one-byte 字串的字元之後，在同一個函式裡當場用 simdutf 轉成 UTF-8、複製完才回傳，中間不呼叫 V8、不配置 V8 的東西，所以字元不會被搬；輸出的 buffer 是輸入的兩倍長（Latin-1 的一個字元最多兩個 byte 的 UTF-8，simdutf 的 `convert_latin1_to_utf8` 的契約），任何 Latin-1 都轉得成合法的 UTF-8，所以 `from_utf8_unchecked` 成立。
- **註冊**（`register_embedder_heap`，`unsafe`：registration 要在 isolate 的 thread 上、isolate 之前 drop）：fork 的 `set_embedder_marking` 把 `Box<Marking>` 的指標交給 glue 的 marking，`set_roots_handler` 把 `Box<Roots>` 交給 roots handler。V8 的 marking thread 只經過 `Marking` 碰 `marker`（在 mutex 裡，`WrapperMarker` 是 `Send + Sync`）和 local；`heap` 只在 isolate 的 thread 上碰（`Marking::heap` 比對 `ThreadId`，不是就 panic；目前的 thread 的 `ThreadId` 存在 thread-local，不每次經過 `thread::current()`），所以 `Marking` 標成 `Sync`（fork 的 `EmbedderMarking` 要求 `Sync`）。fork 的每個 callback 包在 `catch_unwind` 裡，panic 時 abort（不能 unwind 過 C++）。registration drop 時照 Chrome 拆掉 `CppHeap` 的方式，先呼叫 patch 的 `machopo::FinishMarking`，讓 V8 進行中的 GC 收尾（`FinalizeIncrementalMarkingAtomicallyIfRunning`：原子地收尾，concurrent marker 都 join 了），elise 的 marking 照一般的 GC 結束，那時 heap 還是完整的（`EmbedderHeap` 自己拿著它）。之後沒有 V8 的 thread 在標記，也不會呼叫 glue 的物件，直到下一次 GC 開始；所以接著從 `CppHeap` 拿掉、刪掉 glue 的 marking、放掉 `Marking`，再從 isolate 拿掉、刪掉 roots handler（只在這個 thread 的 scavenge 裡被呼叫），什麼都不漏。拆掉時不能只 detach、不刪：worker 可能在檢查之後、使用之前碰上釋放，patch 在 worker 上讀 embedder marking 的指標也不是 atomic 的。
- **local**：V8 的每個 marking state 一個（`new_local`），是 `Box<Local>`（`elise::WrapperLocal` 和它那一輪 marking 的旗標）的指標，只有那個 state 的 thread 一次一個用，`delete_local` 放掉一次；glue 不拿 null 的 local 呼叫它們。`hand` 把 V8 交來的位址交給 `WrapperLocal::hand`（`unsafe`）：那是 V8 標到的、用 machopo 的 tag 的 wrapper 的位址，照第一條是這個 isolate 的 heap 的活的物件；不在 cage 裡的 elise 不理。local 和它的 `WrapperMarker` 可能比 heap 活得久（heap 在 V8 標記途中丟掉：註冊先取消，V8 的 marking state 還拿著 local）：heap 收尾和丟掉時 elise 先 retire 那個 marker，之後交來的什麼都不碰（elise 的 I11）。
- **物件的參照就是 V8 的 `TracedReference`**（`set_wrapper`、`wrapper`；listener 和 timer 的 callback 的 `set_strong`、`strong` 也是；任何值的 `set_strong_value`、`strong_value`：`ErrorEvent` 的 `error`、timer 的參數的陣列，同一格當成 `TracedSlot<Value>`，型別參數只是 phantom，佈局和 `TracedSlot<Object>` 一樣，C++ 那一側本來就是 `TracedReference<Data>`；一格只用其中一種，寫的和讀的是同一組函式；`strong_resolver` 讀 `set_strong` 寫的 promise 的 resolver（動畫的 `ready`、`finished`）：V8 的 `Promise::Resolver` 就是那個 promise 本身（它的 `Cast` 只檢查 `IsPromise`，`GetPromise` 給回同一個物件），所以確認是 promise 之後把那個 handle 當成 resolver（`Local::cast_unchecked`），不是 promise 的（空的、寫成 `undefined` 的）是沒有）：`elise::JsEdge` 的 8 bytes、對齊 8，和 fork 的 `TracedSlot<Object>` 一樣大（編譯期的 assert），elise 建成 0（空的 `TracedReference`）之後不讀不寫；它在 old 的物件裡，不搬。只在 isolate 的 thread 上寫（wrapper 用 fork 的 `TracedSlot::set_droppable`，callback 用 `TracedSlot::set`、不 droppable：V8 的 scavenge 把它當 root、不交給 roots handler 重設；兩者都經過 V8 的 `SetSlotThreadSafe`，是 atomic 的），elise 的 marker thread 經過 fork 的 `TracedMarker::mark`、V8 的 `GetSlotThreadSafe` atomic 地讀。`return_wrapper` 在 isolate 的 thread 上經過 fork 的 `ReturnValue::set_traced` 讀那一格（relaxed atomic，同 `is_empty`）和它指的 node 的物件（`BasicTracedReference::ptr` 的讀法：那一格指著 node 的 `object_`，只有這個 thread 寫），直接寫進回傳值；debug build 每次也走 `TracedSlot::get` 和 V8 的 setter 比對。物件死了（elise 的 sweep）不碰那一格：V8 在這之前（`ClearNonLiveReferences` 的 `ResetDeadNodes`）已經放掉沒被標到的 `TracedReference`，而物件死了就表示它沒被標到（它活著時 marker 會交出那一格）；這次 marking 期間建的（V8 一建好就標上），它的物件也是這次活下來的。
- **droppable、`TryResetRoot` 和 `ResetRoot`**：V8 的 scavenge 丟掉沒改過、只被這個參照撐著的 wrapper 時，先在它平行的 thread 上呼叫 glue 的 roots handler 的 `TryResetRoot`（回 false 的才在 main thread 上再呼叫 `ResetRoot`），它從 wrapper 讀出物件（任何 machopo 的 tag），`Roots::reset` 用 `elise::js_edges_of` 找出物件的 JS 的邊，把指著同一個 wrapper 的那一格 `Reset`（fork 的 `RootHandle::reset_if_same`；Blink 的 `BlinkRootsHandler::TryResetRoot` 同樣在那裡 `Reset`，`DOMDataStore::ClearInlineStorageWrapperIfEqualTo`）。在平行的 thread 上安全，因為：那一格指的就是 V8 交來的那個 traced node（`reset_if_same` 只在相等時 `Reset`），V8 把每個 node block 交給一個 thread 處理，處理期間 `disable_block_handling_on_free_` 讓 `TracedHandles::FreeNode` 只改那個 block 自己的 free list（`v8/src/handles/traced-handles.cc`）；一個物件的參照只指一個 wrapper，所以兩個 thread 不會寫同一格；main thread 在 scavenge 裡等著（mutator 不跑），那一格在 scavenge 開始之前由它寫好（V8 開始平行工作時把之前的寫入排在前面）；型別表（`types::entry`）是 atomic 讀的；elise 的 sweep 這時可能在 V8 的 worker 上跑，但它只碰死的物件，而這個物件活著（下面）。升級 V8 時確認 `ProcessWeakYoungObjects` 還在平行處理時設 `disable_block_handling_on_free_`，`TryResetRoot` 的契約沒變。物件活著：它在 old，只在 elise 的 major GC 死，那時它的 wrapper 也一起死、V8 已經放掉那個 handle。這版的 V8 不在它的 major marking 期間做 scavenge（開了 pointer compression 時 scavenger 收尾的 `DCHECK(!IsMajorMarking())`），所以 `Reset` 不會和 elise 的 marker 同時讀寫那一格。
- **`TracedMarker`**（patch 的：一份 V8 的 worklist、`UnifiedHeapMarkingState`、設好 isolate 的 scope，和 cppgc 的 `ConcurrentUnifiedHeapMarkingVisitor` 一樣；fork 的 `TracedMarker::new` 是 `unsafe`，契約是 V8 的 major marking 進行中、在它結束前 drop）：只有這個檔案的 `TracedSink` 建它，sink 在 V8 的 `start` 時才給 elise，而 elise 只在那次 marking 的 run 和 heap 的 thread 的步驟（V8 的 `AdvanceMarking` 裡）建 local、結束時 drop，`advance_marking` 回報做完和 `finish_marking` 之前都 drop 了（elise 的 `JsEdgeSink` 的契約）；V8 等兩邊都做完才收尾，所以收尾時沒有 `TracedMarker` 活著。`mark` 交給 V8 的是 elise 交來的 JS 的邊：elise 保證那是它標過的物件的邊，物件活到 marking 結束。
- **local 不比它的 marking 活得久**（debug build 檢查，`Running`）：V8 的 `start` 給那一輪一個旗標，`end` 在 heap 收尾之後放下；V8 的 local 交出物件、發布非空的 local、帶著物件被刪，elise 的 marker 建 local、標記參照、drop local（發布到 V8 的 worklist），都在旗標放下之後就 panic（在 fork 的 callback 裡就是 abort）。這幾件事違反上面兩條的前提，但當下沒有症狀：交出、發布到結束的 marking 的物件沒被標，wrapper 還活著物件就被收掉；晚發布的參照進了 V8 的下一輪，撐住垃圾。旗標只是檢查，不是同步（`Relaxed`）：論證不靠它，release build 不讀。
- **`set_isolate_state_with_embedder_heap`**（安全的，給不寫 `unsafe` 的 binding，`dom_js`）：狀態本身是 isolate 的 embedder heap（`EmbedderHeapState`，方法拿 `&mut self`）。先確認 isolate 還沒有任何型別的狀態（有的話先 panic，不註冊：註冊之後才失敗的話，drop 那個 registration 會拆掉 isolate 的 embedder marking，不管原本是誰的），`set_isolate_state`，再 `register_embedder_heap` 一個 `StateHeap<T>`（只記 isolate 的指標），registration 放進 slot 的 box（`keep_registration`）。`register_embedder_heap` 的契約（在 isolate 的 thread 上、isolate 之前 drop）由 box 的生命守住：只有 `drop_isolate_state` 放掉它，在 isolate 的 thread 上、isolate 拆掉之前；永遠沒人放掉時，registration 跟著狀態漏掉，V8 指著的 box 也一直有效。`StateHeap::state` 從 slot 拿 `&mut T`（`unchecked`）：在 isolate 的 thread 上（`Marking::heap` 比對 thread）；狀態在註冊之前就設好、在 registration 放掉之後才放掉，所以 V8 呼叫它時一定是 `T`；V8 只在一個拿了完整 isolate 的呼叫裡呼叫 embedder heap（配置、step、`report_embedder_used_size`、registration 的 drop），也不在它自己對 heap 的呼叫裡再呼叫，所以那時沒有別的借用（上面的「只經過 isolate 借」），它的借用在那次呼叫結束時結束。
- **拿著狀態時只能用 `NoGc` 和 `OpReturn`**（`dom_js` 的操作裡、讀寫快取時；從 `StateInfo` 借狀態時是 `InfoNoGc`，`NoGc` 裡只需要 isolate 的那幾個）：狀態的借用佔著 scope（`StateInfo` 的佔著它自己：scope 只能從它建），所以 rusty_v8 要 scope 的 API（配置、跑 script）都呼叫不了，由借用檢查保證；`NoGc` 開放的是不在 V8 的 heap 上配置、不觸發 GC、不呼叫回來的那幾個，各自的理由（升級 V8 時照樣核對）：
  - `unwrap`：讀 wrapper 的 embedder 欄位和 `CppHeapPointerTable` 的那一格（上面「wrapper 存物件的位址」），只讀。
  - `wrap`：寫 wrapper 的 embedder 欄位，`CppHeapPointerTable` 配一格（`ExternalEntityTable::AllocateEntry`：在 `DisallowGarbageCollection` 底下，表用完是 `FatalProcessOutOfMemory`，不 GC）。
  - `set_wrapper`、`set_strong`、`set_strong_value`：建 traced handle（`TracedHandles::Create`，node 的 block 用 `base::AllocateAtLeast`，不是 V8 的 heap；標記中只把新的 node 標上）。
  - `wrapper`、`strong_value`、`strong_resolver`、`local`、`weak_local`：在 handle scope 裡建 `Local`（`HandleScope::Extend` 的 block 用 `NewArray`，不是 V8 的 heap）。
  - `return_wrapper`、`return_value`、`return_global`、`return_weak`：從 handle 寫進回傳值，不建 `Local`（`return_value` 是 `return_wrapper` 把同一格當成任何值的 `TracedSlot<Value>` 讀：listener 的 callback、`detail`）。
  - `ascii`：`LentString` 借出的字元（上面「借出 V8 字串的字元」），只讀。
  `ReturnValue` 有幾個 setter 不要 scope 卻會配置（`set_double`、超過 Smi 的整數：heap number），所以操作裡的回傳值只經過 `OpReturn`（handle、bool、null、undefined、Smi 範圍內的整數、V8 的空字串：`SetEmptyString` 寫的是 root 表的常數，不建字串）。會配置的那一個（非 Smi 的數字）不拿著狀態時才給：`InfoState::return_number` 借整個 info（`&mut self`），借著時拿不到狀態，heap number 建在 callback 自己的 handle scope 裡，不建 rusty_v8 的 scope。**不建 scope 而會配置的都經過 `InfoHandles`**（`InfoState::handles`，同樣借整個 info）：`new_string`、`new_internalized_string`（fork 的 `String::new_from_utf8_in_callback`：`unsafe`，契約是在 V8 的 callback 裡、handle 不活過 callback）回的 handle 帶 info 的生命（`'s`），和 `with_scope` 的 `SAFETY` 同一個理由：V8 呼叫 callback 時自己開著 handle scope，callback 回去前不關。rusty_v8 的 scope 在這裡只是「可以建 handle」的憑證，憑證換成「借著 info」；V8 配置時可能 GC，那時沒有人借著狀態（借用檢查保證），和 scope 佔住 `StateInfo` 是同一條規則。`InfoHandles` 的欄位是 private，只在 `src/isolate_state.rs` 建，三種 info 各一處；新增它的方法時，那個 V8 的呼叫只能要 isolate（和它從 isolate 拿得到的 context），而且回的 handle 是 callback 的 handle scope 的。`current_context`（fork 的 `Context::current_in_callback`）和 `clone_object`（fork 的 `machopo::clone_object_in_callback`：`Object::Clone` 會配置）也是這樣。拿著狀態的那一側多一個 `InfoNoGc::local`（fork 的 `Local::new_in_callback`：從 `Global` 建 local handle，先比對那個 `Global` 是這個 isolate 的，和 `Local::new` 一樣；只在 handle scope 裡加一格，不配置 V8 的 heap，和 `NoGc::local` 同一個理由）。新增 `NoGc` 或 `OpReturn` 的方法要照這樣寫出不配置的理由；不要 scope 而會配置、或會呼叫回來的 rusty_v8 API（`ReturnValue` 那幾個以外）不能經過它們給出去。違反時是 V8 的 GC 在借著狀態時拿到 `&mut` 的狀態（UB），所以這幾條只靠審查。
- **heap snapshot**（`HeapGraph`、`Graph`，fork 的 `v8::machopo::add_build_embedder_graph_callback` 和 `EmbedderGraph`）：`register_embedder_heap` 也把 `Graph` 交給 V8 的 heap profiler（`AddBuildEmbedderGraphCallback`，registration 的第一個欄位：最先拿掉，`RemoveBuildEmbedderGraphCallback`，然後才 drop builder；契約和其他兩個一樣，在 isolate 的 thread 上、isolate 之前）。`Marking` 和 `Graph` 共用 heap（`Rc<dyn EmbedderHeap>`：V8 的兩個 registration 都呼叫它，誰都不比誰活得久）；`Rc` 只在 isolate 的 thread 上 clone（註冊時）和 drop（registration drop 時），V8 的 marking thread 不碰 `heap`，所以 `Marking` 的 `Sync` 照舊成立。V8 只在 isolate 的 thread 上、拍 snapshot 時呼叫 builder（`Graph::build` 比對 thread），在它的 GC 之後、`DisallowGarbageCollection` 底下；拍 snapshot 是拿了完整 isolate 的呼叫（`Isolate::take_heap_snapshot(&mut self)`，或 inspector 的 `HeapProfiler.takeHeapSnapshot`，經過執行 script 的入口 `dispatch_devtools_message`、停在斷點時的巢狀迴圈、打斷的 callback，三者都不拿著狀態的借用，見「`bindings` 的 inspector（`src/devtools.rs`）」），所以 `StateHeap::state` 照上一條拿 `&mut` 的狀態。builder 開一個自己的 handle scope，只呼叫不在 V8 的 heap 上配置、不呼叫回來的：讀 JS 的邊（`strong_value`，同 `NoGc`）、`v8::machopo::unwrap`（讀）、圖的 `add_node`、`v8_node`、`add_edge`（V8 的 `EmbedderGraphImpl` 的 vector，`V8Node` 記下物件本身：snapshot 做完之前沒有 GC，不會搬），所以 V8 不會在它裡面再呼叫 embedder heap。fork 那一側：圖和 node 只在 callback 裡有效，`EmbedderGraph<'g>` 和 `GraphNode<'g>` 帶著每次 build 自己的 invariant lifetime，node 帶不出 callback、也混不進別的圖；V8 在 callback 之後才問 node（名字、大小、位址、detachedness、wrapper）和讀邊的名字，所以 glue 的 `RustEmbedderGraphNode` 在加入時把資料複製進去（不回呼 Rust），邊的名字要 `&'static CStr`；callback 包在 `catch_unwind` 裡，panic 時 abort。物件的 wrapper 是它的 JS 的邊裡、用它的型別的 tag `unwrap` 回到它自己的位址的那個（I14），和它的 node 併成一個（`WrapperNode`）。
- **`clone_object`**（fork 的）：V8 的 `Object::Clone` 回的是 `scope` 的 handle scope 裡的 handle，照 rusty_v8 做 `Local` 的方式（`cast_local`）。
- **測試**：`bindings` 的 `heap_snapshot`（V8 的 heap snapshot 裡 heap 的物件：照型別命名、和 wrapper 併成一個、照欄位名字的邊和 JS 的值的邊、detachedness、root）、`unified_heap`（V8 的 full GC：script 拿著 wrapper 時物件活著、放掉就收；heap 的 root 拿著的物件的 wrapper 和它的屬性活著；scavenge 丟掉沒改過的 wrapper、清掉參照；兩個 heap 各經過兩次的循環收得掉；`unwrap` 分得出型別）和 `unified_heap_marking`（自己的 binary，`--single-threaded-gc --stress-incremental-marking`：在標記中建、設參照的一串 wrapper 活過增量的 marking、之後收掉；標記中 drop registration 會先收尾）。斷言收掉的都經過不掃 stack（`NoHeapPointers`）的完整 GC：V8 在可能有 heap 的指標在 stack 上的停頓裡保守地掃 stack，舊的 word 指著某個 `TracedReference` 的節點時那個 wrapper 會多活一輪（Blink 放在 stack 上的 `TracedReference` 靠這個）。`src/unified_heap.rs` 的單元測試讓上一條的每個檢查在 marking 結束後觸發一次。elise 的 fuzz 的 driven 的 run 用一個假 engine 對著參考模型比（`../third_party/elise/crates/elise/tests/it/ops.rs`）：死掉的 wrapper 的物件一定已經到不了，活的物件的 wrapper 一定活著。

### `bindings` 的 `src/gc_platform.rs`：elise 的 heap 的工作在 V8 的 worker 上

V8 推進的 elise 的 heap 的平行工作（marking、scavenge、sweep）經過 `elise::Platform` 交給 V8 的 platform 的 `PostJob`（fork 的 `v8::machopo::post_job`、glue 的 `RustJobTask`），和 V8、cppgc 的 GC 共用一組 worker。
- **`run` 借用 job**：`elise::Platform::run` 的 job 是借來的（`&dyn Job`），交給 V8 的 worker 前延長成 `'static`（`transmute`）。依據是 `run` 返回之前所有的 run 都返回了：呼叫的 thread 自己跑完 joining run（elise 的 job 的 joining run 等整個工作做完才返回）之後 `Cancel`，V8 的 `Cancel` 讓 worker 的 run 收手、等它們都返回、之後不再開新的 run。V8 可能之後才刪掉 task（task 拿著 `Arc<Task>`，裡面有那個參照），刪的時候只 drop 參照、不讀它。不用 V8 的 `Join`：它只在 job 還要 worker 時才讓呼叫的 thread 跑，但 elise 的 job 一開始的項目（seed）只有 joining run 拿得到，那時 job 一個 worker 都不要，`Join` 會直接返回、seed 沒人做。
- **task**：fork 的 `post_job` 把 `Box<Box<dyn JobTask>>` 交給 glue 的 task，V8 刪 task 時（任何 thread）放掉一次；`post_job` 是 `unsafe`，契約是 platform 比 job 活得久（V8 的 platform 一直活到 process 結束）。`JobTask` 要求 `Send + Sync`：`Task` 的 job 是 `Sync`（posted 的也是 `Send`），panic 在 `Mutex` 裡。`run`、`max_concurrency` 只在 task 活著時被呼叫，`JobDelegate` 只在那次 run 裡借用。
- **panic 不跨過 C++**：`bindings` 的 `Run` 把每次呼叫包在 `catch_unwind` 裡，第一個 panic 記在 `Task`，之後的 run 直接返回、`max_concurrency` 回 0（job 結束）；`run` 在 `Cancel` 之後、posted 的在 handle 的 `cancel` 之後重新拋出，和 `elise::ThreadPool` 一樣。漏到 fork 的 trampoline 的 panic 會 abort。
- **handle**：fork 的 `JobHandle` 擁有 V8 的 `JobHandle`，`cancel`（等）或 `cancel_and_detach`（不等）各 delete 一次，drop 時 cancel（等）。`bindings` 的 handle 放在 `Mutex<Option<_>>`，取出之後才 cancel，所以只 cancel 一次；它被 drop（包括 unwinding 中）時是 fork 的 handle 自己 cancel、等 run 返回，run 的 panic 跟著丟掉（cancel 讓 run 看到 `should_yield`，等待不會卡住）。

### `bindings` 的 inspector（`src/devtools.rs`）

V8 的 inspector 和 isolate 一起建，放在 isolate 的 slot（和 `V8PerIsolateData` 的欄位）裡：
- **client 拿著 isolate 的 raw 指標**（`as_raw_isolate_ptr`，`unsafe`）：只在 client 活著時用，client 屬於 inspector，inspector 比 isolate 先走：`V8PerIsolateData` 的 `Drop` 先清掉 slot，欄位照順序 drop（session 在 inspector 之前，inspector 在 isolate 之前）。不能把 `DevTools` 的 `Rc` 交到 `V8PerIsolateData` 以外活得比 isolate 久的地方。
- **`ensure_default_context_in_group`**（V8 找命令的 context 時呼叫）用 `Isolate::from_raw_isolate_ptr` 和 `callback_scope!`（`unsafe`），把 main frame 的 realm 的 `Weak` 變成 `Local` 交回，延長它的 lifetime（`extend_lifetime_unchecked`）：V8 在 isolate 的 thread 上、在自己的 handle scope 裡呼叫，`Local` 在那個 handle scope 裡，V8 讀它時還在。這裡不能開自己的 handle scope（交回的 `Local` 會跟著它消失），也不能從別的地方呼叫它。
- **session 的命令是執行 script 的入口**：`Runtime.evaluate`、`callFunctionOn` 這些會執行頁面的 JS，所以命令只能從執行 script 的入口經過 `V8PerIsolateData::dispatch_devtools_message` 交給 inspector：`dom_js` 的 `V8Engine::dispatch_devtools_message`，拿 `&mut self`，和 engine 的其他入口一樣手上沒有 isolate 的狀態的借用，命令跑的 JS 呼叫的 binding 照「`bindings` 的 isolate 的狀態（`src/isolate_state.rs`）」的規則借；不能在入口之外呼叫 `V8InspectorSession::dispatch_protocol_message`。inspector 自己在 script 執行中呼叫的（`console` 交給 `console_api_message`、`exception_thrown`、`exception_revoked`、context 的通知）不執行 JS、不碰 DOM：`console` 的 sink 只拿到格式好的文字。`dom_js` 在 DOM 的呼叫裡（插入、拿掉 iframe 時）告訴 inspector context 的建立和消失、在回報例外時呼叫 `exception_thrown`：都在放掉狀態的借用之後，只交給 scope。
- **停在斷點和打斷時的 DevTools 命令**：V8 停在斷點時在頁面的 script 裡呼叫 `run_message_loop_on_pause`，巢狀迴圈把 renderer 的 DevTools 佇列的命令交給 session（`Debugger.evaluateOnCallFrame`、`Runtime.evaluate` 執行頁面的 JS）；`RequestInterrupt` 的 callback（`interrupted`，`unsafe`：`from_raw_isolate_ptr`，V8 在 isolate 的 thread、它執行的 script 的安全點上呼叫）把要打斷 script 的命令交給 session。兩者都在外層執行 script 的時候，停住的地方是 JS 的敘述，外層的 Rust 正在一個把 scope 交給 V8 的呼叫裡，手上沒有 isolate 的狀態的借用（「`bindings` 的 isolate 的狀態（`src/isolate_state.rs`）」的「只經過 isolate 借」）：巢狀執行的 JS 呼叫的 binding 照那裡的規則重新借，和 JS 呼叫的 callback 再呼叫 JS 一樣。所以它們不碰 renderer 和 DOM，只交命令給 session；session 在 `Shared` 的 `RefCell` 裡，交命令前先 clone 出 `Rc`、放掉借用（命令可能再停住，巢狀迴圈要再借）；佇列只設一次（`OnceCell`），迴圈拿共用的參照，巢狀的迴圈也一樣。佇列是 renderer 的（`dom_api::DevToolsQueue`）：等下一則、拿走要打斷的訊息、放回去，和讓 renderer 自己的 agent 回答（`answer_here`：agent 只寫自己的狀態和送給 browser 的訊息，不回頭呼叫 engine）。停住時 renderer 的 agent 要讀 DOM、重算 style 和 layout（Blink 的 agent 在 pause 的巢狀迴圈裡也這樣），所以 `run_message_loop_on_pause` 從 client 記的 isolate 指標開 isolate（`unsafe`：`from_raw_isolate_ptr`，V8 在 isolate 的 thread 上、script 停在敘述時呼叫，isolate 活著：inspector 比它先走），交給 `answer_here`（和 `paused`、`waiting`、`render`：`render` 用借來的 `Frame` 跑 style、layout、paint 和 commit，不跑 script），`dom_js` 用它做一個 page（`devtools_page` 的 `Page`，`dom_api::DevToolsPage`）借給 renderer；不停住時 renderer 的命令也用同樣的 page（`ScriptEngine::devtools_page`，從 engine 的 isolate）。這時外層的 Rust 手上沒有狀態的借用（上面的理由；不停住時 renderer 不在任何 engine 的呼叫裡），page 只在 `dom_and_layout` 回答的借用裡借狀態（經過 `isolate_state_mut`），借用跟著 page 的 `&mut self`，所以 agent 拿著 DOM 時不能同時呼叫 page 的其他方法；page 在這幾個方法回來時就沒了，在迴圈把下一則交給 session（可能執行 JS、重新借狀態）之前。agent 在 DOM 的借用裡只跑 Rust（讀樹、style、layout）。layout 照 operation 借它的方式拿出來、page 走時放回去；呼叫停住的 script 的 operation 拿著它時是空的（現在沒有 operation 拿著 layout 呼叫 JS）。page 的 `objects`（`DevToolsObjects`：`resolveNode`、`requestNode`、`$0`、Event Listeners）先放回 layout、不拿著狀態的借用，再開自己的 scope、進 context，經過 `StateScope` 借狀態做 wrapper，呼叫 inspector 的 `wrapObject`、`unwrapObject`、`addInspectedObject`（安全的 binding）；listener 的 `handleEvent` 的 getter 和屬性 handler 的編譯會執行頁面的 JS，那時也沒有狀態的借用（`StateScope` 的借用在讀完 listener 時就結束）。`$0` 的值（`Inspected`，`InspectableImpl::get`）是 V8 在 script 讀 `$0` 時呼叫的 callback，從它給的 scope 經過 `StateScope` 借，和其他 callback 一樣；DevTools 叫值的名字（`set_subtypes` 的 `Subtypes`，`value_subtype`、`description_for_value_subtype`）在 inspector 描述一個值時呼叫：在命令裡、`console` 的呼叫裡、page 的 `wrapObject` 裡，那時都沒有人借著狀態，它也經過 `StateScope` 借，只讀節點的名字和屬性，不執行 JS。巢狀迴圈跑著時斷線的 session 不刪：先讓它停止除錯，迴圈回來之後才 drop（V8 不讓 embedder 在迴圈裡刪 session），拿掉的訊息也放回佇列，給 renderer 自己的 agent。要打斷的方法（browser 的清單）都不執行頁面的 script。
- **context 和 promise 的參照是 `v8::Weak`**：預設的 context、回報過的 rejection 都是弱的，inspector 不讓 realm 收不掉（和 context 的 slot 同一條規則）。

### `bindings` 的 `initialize_v8_before_main!`

合併成一個 binary 的整合測試（`bindings`、`dom_js`、`gc_bench` 的 `tests/it/`）用它在 `main` 之前初始化 V8，讓整個 process 的 flag 不取決於哪個測試先跑。它展開成 `ctor` 的 constructor，`ctor` 要求標 `unsafe`：
- **只在測試的 binary 裡展開**：不能放進 library。library 的 constructor 在動態載入時、在 loader 的 lock 底下執行，那時開 thread 會 deadlock。
- **只做初始化**：讀環境變數（C runtime 在任何 constructor 之前就準備好了）、開 V8 的 platform（它的 worker thread 是 V8 自己開的，不經過 std）。不在裡面用 std 的 thread、stdout 或其他要 `main` 之後才保證可用的東西；要加別的工作，先確認它在 `main` 之前可以做。
- **panic 會讓 process abort**：測試跑不起來，不會靜悄悄地用錯的 flag 跑。

## 可以回報上游的修改

Fork 相對上游 `v8` crate 修了五個問題，之後可以整理成 issue 或 PR 回報（都還沒回報，2026-10-08）：
1. `Member` / `WeakMember` / `TracedReference` 的儲存是 `[u8; N]`，對齊只有 1，而 C++ 把它們當成 `std::atomic` 存取。
2. `Member::set(&mut self)` 和 trace（`&self`）在 concurrent marking 下會讓兩個 thread 同時持有 `&mut` 和 `&`；`TracedReference::reset(&mut self)` 也一樣。
3. `make_garbage_collected` 在 C++ 把物件標記為「已建構完成」之後，才寫入 Rust 的資料，concurrent marker 讀它時沒有同步。Fork 讓 `RustObj` 的建構子接一個初始化 callback。
4. `Weak` 在 isolate 拆掉的期間（`OwnedIsolate::drop` dispose isolate 的 handle 之後、V8 的拆除之前，例如 context 的 annex 被 guaranteed finalizer 釋放時）被 drop，不 reset V8 的 handle 就釋放 `WeakData`，V8 拆除時的 GC 再用它呼叫 first pass callback（use-after-free）。上游 `v152.2.0` 的程式一樣；重現：一個 context 呼叫過 `set_slot` 的 isolate，在 `--stress-compaction` 底下 drop（machopo 的 `bindings` 的 `isolate_teardown`）。Fork 在這種情況 leak `WeakData`；上游也可以改成在 dispose handle 之前跑 finalizer，但那改變上游刻意安排的拆除順序。細節在 fork 的 `README.machopo.md`。
5. `ValueSerializer` 的 delegate 丟了例外之後回傳 `None` 時，shim 還是轉呼叫 V8 自己的 delegate，在呼叫者的例外上面再丟一個（`Isolate::Throw` 只容許已經有 termination exception；release 的 V8 留著第一個，debug 的 V8 檢查失敗）。丟了例外再回傳 nothing 是 Blink 的 `V8ScriptValueSerializer` 的寫法，當時 machopo 的 `dom_js` 在 `history.pushState` 收到 `SharedArrayBuffer` 時也這樣。Fork 改成只在沒有 pending exception 時才轉呼叫（wasm 模組那一個 delegate 本來就直接回 `Nothing`）；動到 C++，prebuilt 跟著發了新的 release（fork 的 `kun-v152.2.0-7`，`main` 已經換過去）。上游 `v152.2.0` 的程式一樣；重現：delegate 丟例外之後拒絕序列化 `SharedArrayBuffer`，連結 debug 的 V8（當時 machopo 的 `dom_js` 的 `bindings` 的 `history_and_its_state`，`test.py matrix` 找到的）。細節在 fork 的 `README.machopo.md`。
