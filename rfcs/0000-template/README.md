## 摘要

一段話：要做什麼，選了哪個做法。

## 動機

為什麼要做：現況、問題或風險，起因是什麼。列出目標，以及明確**不在範圍內**的事。要解決的 `docs/limitations.md` 裡的限制列在這裡：`rfcs/` 以外的文件不寫 RFC 的編號，由 RFC 指過去，做完時照這份清單刪掉那幾條。

## 設計概要

從使用的人的角度（網頁的作者、machopo 的使用者，或之後改這部分程式的人），用例子說明做完之後怎麼用、行為怎麼變。不需要讀過實作就看得懂。

## 詳細設計

給實作的人：架構、資料和介面、和現有部分怎麼接、邊界情況。最後寫：

### 測試

怎麼證明它是對的：哪些自動測試、哪些只能手動確認或靠審查。

### 分階段

這份 RFC 分幾步做；有哪些可以先做的原型。

## 缺點

選了這個做法要付出什麼：複雜度、效能、相容性、要長期維護的東西。

## 理由和其他做法

為什麼選這個；考慮過哪些做法、為什麼不選；不做會怎樣。完整的比較放在 `details.md`。

## 先例

其他實作（Chromium、Firefox、V8、wasmtime…）怎麼做，哪些照做、哪些不照做。

## 已決定的事項

確認的日期，然後編號列出，讓其他 RFC 可以引用某一條。草稿時寫「無」。

## 待決定

還沒決定的問題，以及要怎麼回答（原型、實測、等某件事發生）。

## 之後的可能

這份 RFC 之後自然會接著做的事；寫在這裡不代表已經決定要做。
