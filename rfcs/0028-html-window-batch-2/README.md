# RFC 0028：HTML 元素和 Window 的雜項（H2）

- 開始日期：2026-10-10
- 狀態：✅ 已完成：2026-10-10（RFC 0012 路線圖的 H2；第 1、2 條開始前接受，第 3 到 22 條在各段開始前確認，都在 2026-10-10；五段都做完，驗收在 `progress.md`，限制在 `docs/limitations.md`）
- 進度：`progress.md`
- 細節：`details.md`

這份是 RFC 0012 的路線圖（`rfcs/0012-speedometer/roadmap.md`）的代號 H2，DOM 線接在 G（RFC 0023）之後的下一份：H1（RFC 0017）做了 M1 要的最小部分，這份做其他的。範圍以 2026-10-10 第一次在 kun 上跑 20 個 default suite 的盤點為準（`rfcs/0012-speedometer/progress.md`、`details.md` 的「盤點」）。

**和 RFC 0027（`fetch`）的關係**（2026-10-10，兩份同時做）：RFC 0027 的第 1 段先 merge 回 `main`，宣告表有了 `Promise<T>`（JS 和 WIT，它的第 2 條）和 DOM 自己的 task runner（每份文件一份，它的第 13 條），這份照用：`img.decode()`、`Blob` 的讀取回傳 `Promise<T>`，`<img>` 的 `load` / `error` 排進 DOM 的 task。RFC 0027 把「bytes 的形式」交給這份（它的第 1 條）：宣告表的 `BufferSource`、`ArrayBuffer`、`Blob`、`Response` 和 `Request` 的 `arrayBuffer()`、`bytes()`、`blob()`，和 `BufferSource`、`Blob` 當 body，都在第 5 段；`FormData`（表單的 entry list）另開（第 22 條）。

## 摘要

補上 Speedometer 的 suite 用到、kun 還沒有、而且照著規範就能做的 HTML 和 Window 的成員，分五段，照擋住的 suite 多寡排序：

1. **`console`**：補齊 Console 規範的方法（`error`、`warn`、`info`、`debug`、`assert`、`trace`、`dir`、`table`、`count`、`group`、`time`……）和格式化。現在只有 `log`，`console.error` 一呼叫就丟 `TypeError`，擋住 NewsSite-Next、NewsSite-Nuxt 和 Charts-chartjs，runner 量完之後的 `console.assert` 也是。
2. **節點和 HTML 元素的小成員**：`Node.isConnected`、HTML 元素的 global attribute（`title`、`lang`、`dir`、`hidden`、`contentEditable` 的 reflection……）、`HTMLTemplateElement.content`、`Document.getElementsByName`、`Document.dir`、`document.visibilityState` / `hidden`、`WebKitMutationObserver`。
3. **`<a>` 的網址成員**（`HTMLHyperlinkElementUtils`）：`href` 和 `protocol`、`host`、`pathname` 等，`rel`、`relList`、`target`。
4. **`<img>` 和 `Image`**：`src`、`alt`、`width`、`height`、`naturalWidth`、`complete`、`currentSrc`、`decode()`，`new Image()`。
5. **Window 的雜項和 bytes**：`crypto`（`getRandomValues`、`randomUUID`）、`requestIdleCallback`，以及 bytes 的形式：宣告表的 `ArrayBuffer` / `BufferSource`、`Blob` 和 `URL.createObjectURL`（runner 量完之後的最後一步）、`Response` 的 `arrayBuffer()`、`bytes()`、`blob()`（RFC 0027 交給這份的）。

每一段可以分開決定和驗收；各段開始前把那一段的設計定下來（「分階段」）。

## 動機

**現況**（2026-10-10，`python3 scripts/ci.py speedometer --inventory`）：20 個 default suite 裡 11 個跑完、不丟例外；其他的卡在 kun 沒有的 API 上。卡住的原因裡，這份能補的：
- **`console`**：kun 的 `console` 是 `bindings` 手寫的、只有 `log`（`crates/bindings/src/bindings.rs`）。NewsSite-Next、NewsSite-Nuxt 一開始就停在 `console.error is not a function`，Charts-chartjs 跑完但有例外。Chrome 跑的時候這三個都沒有呼叫 `console.error`（它不在 Chrome 的盤點裡）：是 kun 先有別的錯誤，框架才去印。所以補了 `console` 之後，這三個會停在**真正的**第一個錯誤上，那才是下一步要補的。
- **kun 缺、最多 suite 用到的成員**（default 的 20 個裡，用到的 suite 數；完整的表在 `details.md`）：`HTMLElement.contentEditable`（7）、`Node.isConnected`（6）、`HTMLAnchorElement.href=`（6）、`HTMLTemplateElement.content`（5）、`HTMLImageElement.src=` / `Image`（3）、`HTMLElement.title=`（3）、`WebKitMutationObserver`（3）、`Document.getElementsByName`（2）、`Document.dir`（2）、`crypto.randomUUID`（2）、`requestIdleCallback`（2）、`HTMLImageElement.complete` / `width` / `height` / `alt`（2）。
- **`docs/limitations.md` 的限制**（這份做完時刪掉）：「Bindings 和 DOM API」的 `console` 只有 `log`；沒有 `HTMLTemplateElement`；HTML 元素的 interface 很少（`HTMLElement` 沒有 `title`、`lang`、`dir`、`hidden`、`inert`、`accessKey`，WPT 的 `reflection-forms.html` 的 baseline 都是它們）；`<a>` 沒有 `href` 等 IDL attribute（script 要用 `setAttribute`）；`document.links` 等。

目標：
- NewsSite-Next、NewsSite-Nuxt、Charts-chartjs 不再停在 `console`；這份的成員用到的 suite 不再因為它們丟例外。
- 成員照規範和 Chrome 運作，由 `dom_api` 的單元測試和 WPT 驗證（`html/dom/reflection-*.html`、`html/semantics/` 的對應目錄、`console/`、`html/webappapis/` 的 `crypto` 和 idle callback）。
- 照 RFC 0008 的規則，成員同時在 JS（`dom_js`）和 wasm（`kun:dom`），`any` 的只給 JS；型別和分層照 Chromium，宣告照 Blink 的目錄放（RFC 0014）。

不在範圍內（路線圖的其他代號，或之後）：
- `contentEditable` 的編輯本身（路線圖的 P）：這份只做 attribute 的 reflection 和 `isContentEditable`。
- shadow DOM、custom element、constructable stylesheet（K）；`MessageChannel`（J）；`IntersectionObserver`、`ResizeObserver`（M）；Canvas（N）；SVG 的 interface（O：TodoMVC-Vue 卡在 `SVGElement`）；`fetch`、`XMLHttpRequest`（L）；`Selection`、`Range`（I、P）。
- `PerformanceObserver`、Navigation Timing、`navigator.scheduling`、`navigator.connection`（框架用來偵測功能，沒有比較安全）。
- `console.createTask`（Chrome 的非標準 API，React 和 Next 只在有的時候用）；`console` 的 DevTools 那一側（kun 沒有 DevTools）。
- Trusted Types（`TrustedTypePolicy`）、`document.all`、`window.opener` 的導覽關係。

## 設計概要

**給寫網頁的人**：
- `console.error("x", 1)`、`console.warn`、`console.assert(cond, "msg")`、`console.group("g")`、`console.time("t")` / `timeEnd`、`console.count()`、`console.log("%s is %d", "a", 1)` 照 Console 規範的 formatter；輸出和 `console.log` 一樣在 stderr，帶等級。
- `node.isConnected`；`el.title = "x"`、`el.hidden = true`、`el.lang`、`el.dir`、`el.contentEditable = "true"`、`el.isContentEditable`；`template.content`；`document.getElementsByName("q")`；`document.visibilityState`。
- `a.href = "/next"`、`a.pathname`、`a.host`、`a.relList`。
- `new Image()`、`img.src = "x.png"`、`img.complete`、`img.naturalWidth`、`await img.decode()`。
- `crypto.randomUUID()`、`crypto.getRandomValues(new Uint8Array(16))`、`requestIdleCallback(cb, { timeout })`、`URL.createObjectURL(new Blob(["…"]))`。

**給 wasm 的 guest**：照 RFC 0008 的規則，非 `any` 的成員也在 `kun:dom`；`console` 的引數是 `any`，只給 JS（第 2 條；guest 用 WASI 的 stdout）。

**給改 kun 的人**：加 API 的流程不變（`crates/dom_api/README.md` 的「怎麼新增一個 API」）。宣告表的 `Promise<T>` 是 RFC 0027 的，`img.decode()`、`Blob.text()` 照用；這份加的形式：namespace（`console`，第 2 條；之後的 `CSS` 也用）、別名（`WebKitMutationObserver`，第 4 條）、成員層級的 `[JsOnly]`（`requestIdleCallback`）、`ArrayBufferView`（第 19 條）、`BufferSource` 和回傳的 `ArrayBuffer`、`Uint8Array`、`[Clamp] long long`（`Blob`）。

## 詳細設計

- **第 1 段 `console`**（第 2 條）：
  - **宣告表的 namespace**：`namespaces!` macro（`declare.rs`），`[JsOnly] namespace console { method ...; }`，每個 method 是 `declare!` 的 `static method`（函式接 realm 的 window），產生 `NamespaceDesc`（名字、`exposure`、members），`interfaces/mod.rs` 的 `NAMESPACES` 收集。`console` 放在 `interfaces/core_inspector.rs`（Blink 沒有 `console.idl`：Chrome 的是 V8 的 builtin，訊息經過 inspector）。`kun:dom` 還沒有 namespace 的形式，每個 namespace 都要是 `[JsOnly]`，WIT 的產生器不看 `NAMESPACES`（`crates/dom_api/tests/wit.rs` 檢查）。`spec` 測試的 WebIDL reader 讀 `namespace`，和 `console.idl` 比對 19 個 operation。
  - **JS**：`dom_js` 用 `ObjectTemplate` 建 namespace 物件，operation 是 writable、enumerable、configurable 的 data property，`@@toStringTag` 是名字；物件的 prototype 是一個空物件，空物件的 prototype 是 `%Object.prototype%`（WebIDL 的 namespace 物件，V8 自己的 `console` 也是；WPT 的 `console-is-a-namespace.any.js` 找到的：原本直接是 `%Object.prototype%`）。`install` 把它放在 global 上，蓋過 `bindings` 給每個 context 的 `console`（只有 `log`，留給沒有 DOM 的 context）。namespace 的 member 和 static operation 共用 member 的編號：`INTERFACES` 之後的編號是 namespace 的。
  - **訊息**：照 Chrome 印到終端機的樣子（實測在 `details.md` 的「Chrome 怎麼把 `console` 印到終端機」），不照規範的 Formatter：Chrome 的終端機輸出不套用 `%s` 等（DevTools 才套用），group 不縮排。每個引數經過 `ScriptHost::console_string`（V8 那一側在 `dom_js` 的 `console.rs`，照 V8 inspector 的 `V8ValueStringBuilder`：primitive 照 `ToString`、symbol 是描述、BigInt 加 `n`、陣列逐個元素攤平、函式、`Date`、`RegExp`、`Error` 照 `ToString`、其他物件是 `[object` 加 constructor 的名字 `]`，不執行頁面的 `toString`；一個引數裡的陣列元素加起來超過 10000 個、或巢狀超過 32 層時，那個引數是空字串，也照 inspector），空格分開，整個訊息是空的時不印；沒有引數時 `log` 等不印，`assert`、`group`、`groupCollapsed`、`trace` 印它們的名字（`console.assert`……），`groupEnd` 印 `console.groupEnd`；`count` 是 `label: n`，`timeLog` / `timeEnd` 是 `label: n ms` 再接引數，`countReset`、`time`、`timeLog`、`timeEnd` 的警告用 Chrome 的字。訊息經過 `FrameClient::console_message`（帶等級）交給 renderer，renderer 寫到 stderr（`[console] …`）。
  - **狀態**：count map 和 timer table 每個 realm 一份，放在 `dom` 的 `Window` 的 `#[no_trace]` 欄位（`RefCell<HashMap<String, …>>`，沒有新的 `unsafe`）；時間是 `performance.now()` 的時鐘。group 不縮排，不必記深度。
- **第 2 段 節點和 HTML 元素**（第 3 到 5 條）：
  - **`Node.isConnected`**：根是 document（kun 沒有 shadow tree，shadow-including root 就是根）。
  - **`HTMLElement` 的 global attribute**（`html_element.rs`，Blink 的 `html_element.cc`）：照實測的 Chrome 152（`details.md` 的「Chrome 的 global attribute」）。`title`、`lang`、`accessKey` 是字串的 reflection，`inert` 是 boolean，`dir`、`enterKeyHint`、`inputMode` 是「limited to only known values」的列舉（forms 的 `reflected!` macro 移到 `reflection.rs` 共用，第 3、4 段也用）。`translate`、`spellcheck` 從最近的有那個 attribute（狀態不是 inherit）的 HTML 祖先算，沒有時是 true；SVG 元素的 attribute 不算，照樣往上找。`hidden` 是 `(boolean or unrestricted double or DOMString)?` 的 union：讀回 `"until-found"` 或 boolean，設 `false`、`null`、空字串、0、NaN 拿掉 attribute。`draggable` 沒有 attribute 時 `<img>` 和有 `href` 的 `<a>` 是 true。`autocapitalize` 照 Chrome 和 WPT：不認得的值是 `sentences`（HTML 現在寫的是 default，回傳空字串），沒有或空的時 HTML 的「autocapitalize-and-autocorrect inheriting element」用 form owner 的。`contentEditable` 是 attribute 的狀態，設成四個關鍵字以外的是 `SyntaxError`（訊息照 Chrome）；`isContentEditable` 照最近的 `contenteditable` 不是 inherit 的 HTML 祖先，從 DOM 算：Chrome 從 style 算，但不在文件裡、`display: none` 的也算，結果一樣。只有 IDL attribute，不做編輯、拖放、翻譯、`inert` 的效果。
  - **`HTMLTemplateElement`**：只有 `content`（`dom` 跟著 template 建的 fragment）。不做 declarative shadow DOM 的 `shadowRootMode` 等 attribute：kun 的 parser 不做 shadow root，Lit 等函式庫看 prototype 有沒有 `shadowRootMode` 決定要不要自己處理。
  - **`Document.getElementsByName`**：`dom` 的 `CollectionFilter::Name`，`name` 是那個值的 HTML 元素，live 的 `NodeList`（和 `getElementsByClassName` 一樣每次新的一個，Blink 會快取）。**`Document.dir`**：html element 的 `dir`，沒有時是空字串、設定什麼都不做。
  - **`WebKitMutationObserver`**：宣告表的別名（第 4 條）。`interface ... legacy_window_alias(Name) as Handle`，`InterfaceDesc::legacy_window_alias`；`dom_js` 把同一個 interface object 放在 global 的第二個名字上；`kun:dom` 不變。DOM 規範的 IDL 沒有這個別名，`spec-differences.txt` 寫明是 Blink 的；`spec` 測試的 WebIDL reader 讀 interface 的 `[LegacyWindowAlias]`，IDL 有、表沒有的（`webkitURL`、`SVGRect`）列進 `spec-missing.txt`。
  - **`visibilityState`、`hidden`、`visibilitychange`**（第 5 條）：狀態是整頁的，照 Chromium 的分層（`Page::visibility_state_`）：renderer 的 `FrameSettings`（每個 frame 共用）記下 `WasHidden` / `WasShown`，document 經過 `FrameClient::is_page_visible` 讀（Blink 的 `Document::IsPageVisible` 問 page）；沒有 frame 的 document 是 `hidden`（HTML 的初始值，`createHTMLDocument` 的）。改變時 renderer 照 frame tree 的順序（主 frame 先）對每份 document 發 trusted、bubble、不能取消的 `visibilitychange`（`dom_api::document::visibility_state_changed`）：全部改好之後才發，和 Blink 一樣；告訴它已經是的狀態時不發。初始的狀態沒有放進啟動 renderer 的參數：browser 背景開分頁時改成先 `was_hidden`、再導覽（Chromium 的 `WebContents::CreateParams::initially_hidden`），IPC 有順序，renderer 在 commit 任何文件之前就知道；`open_from`（連結）和 `open_tab`（DevTools 的 `Target.createTarget`）都是。視窗縮到最小、被擋住不算隱藏（限制）。
  - **順便修的**：`cloneNode` 複製 attribute 時沒有跑 attribute change steps，複本沒有 event handler content attribute 的 handler（WPT 的 `Event-dispatch-single-activation-behavior.html` 拿得到 `template.content` 之後找到的）；照 DOM 的「clone a node」，在 cloning steps（`<input>` 的狀態）之前跑。
  - **`kun:dom`**：只有新增（`is-connected`、global attribute、`get-elements-by-name`、`dir`、`visibility-state`……），不升版。`hidden` 的 union 是第一個同時當參數和回傳值的 union：只有值的 union 可以（有 resource 的，參數 borrow、回傳 own，不行），`dom_wasm` 的回傳多了 boolean 的 case，Lua 的產生器多了「只有值的 union」（boolean、數字、字串照 Lua 的型別）。
- **第 3 段 `<a>` 和 `<area>`**（第 6 條）：
  - **`HTMLHyperlinkElementUtils`**（`hyperlink.rs`，Blink 的 `HTMLAnchorElement` 和 `DOMURLUtils`）：元素的 URL 是 `href` 照 node document 的 base URL（有 `<base>`，`document::document_base_url`）解析，每次重算（HTML 的「set the url」；Blink 也是每次讀時補成完整網址），所以「reinitialize url」不必另外做。getter 和 setter 用 `url::quirks`，和 `URL` 共用：沒有 URL 時 `href` 是原樣的 attribute、`protocol` 是 `:`、其他是空字串；setter 改一份複本，用「update href」寫回；照規範不能改時（不能有帳號密碼和 port 的網址的 `username`、`password`、`port`，opaque path 的 `host`、`hostname`、`port`、`pathname`）什麼都不寫。`href` 是 stringifier。
  - **和 Chrome 不同、照規範的三處**（實測在 `details.md` 的「Chrome 的 `<a>`」）：`protocol` 不在 special 和其他 scheme 之間切換（Chrome 會把 `mailto:` 換成 `ftp://`、`https://`）；`file:` 網址的 `origin` 是 `null`（Chrome 是 `file://`）；不能改網址的 `username`、`password`、`port` 不改 `href`（Chrome 寫回序列化之後的網址）。前兩處 WPT 的 URL 測試和 kun 的 `URL` 都是規範的寫法；第三處只有 `href` 本身不是標準寫法時看得出來。
  - **`HTMLAnchorElement`**：`target`、`download`、`ping`、`rel`、`relList`、`hreflang`、`type`、`text`、`referrerPolicy`（Referrer Policy 的值，limited to only known values），過時的 `coords`、`charset`、`name`、`rev`、`shape`。**`HTMLAreaElement`**：`alt`、`coords`、`shape`、`target`、`download`、`ping`、`rel`、`relList`、`referrerPolicy`、過時的 `noHref`；不做 HTML 新加、Chrome 也還沒有的 `hreflang`、`type`。兩者都沒有 Chrome 的實驗 `hrefTranslate`、`interestForElement`。`relList` 支援 `noopener`、`noreferrer`、`opener`（Blink 的）。只有 IDL，不做 image map。
  - **`document.links`、`document.anchors`**：`dom` 的 rare data 裡的集合（每次同一個，`[SameObject]`），`CollectionFilter::DocumentLinks`（有 `href` 的 HTML `<a>` 和 `<area>`）、`DocumentAnchors`（有 `name` 的 `<a>`）。
  - **測試**：WPT 的 `url/a-element.html`、`url-setters-a-area.window.js` 要 `fetch` 讀資料，`dom_api` 的 `url_data` 測試改讀同一批資料，也跑 `<a>` 和 `<area>`：失敗都是 `url` crate 的（和 `URL` 一樣，`non-spec:/.//p` 的序列化錯了，寫回 `href` 再解析時路徑變成 host）。
- **第 4 段 `<img>`**（第 7 到 10 條，三小段）：
  - **4a 載入和成員**（第 7 條）：`dom_api` 的 `image.rs`（Blink 的 `HTMLImageElement` 和 `ImageLoader`）。元素的 current request 存在 `dom`（`ImageRequest`：狀態、網址、natural size、延後哪份 document 的 load event、等著的 `decode()`、第幾次更新），只有一個 request（沒有 pending request，限制）。「update the image data」在 `src`、`srcset`、`sizes`、`crossorigin`、`referrerpolicy` 改變（parser 建立的元素也經過同一個 attribute change steps）和 adopt 時，由 `update_elements` 執行：document 已經有那張圖（`FrameClient::cached_image`，HTML 的「list of available images」，每份 document 一份）時當場可用，`load` 仍在 task 裡發；否則等一個 microtask（`Microtask::UpdateImageData`），照那時的 base URL 解析，請 frame 抓（`FrameClient::request_image`）。所以設了 `src` 之後插入的 `<base>` 也算（Chromium 2021 年起；WPT 的 `image-base-url.html`），網址解析不了時當下的 `complete` 是 false。`load` / `error` 是 DOM manipulation 的 task（`Task::ImageEvent`），request 已經換掉的不發。request 從開始到事件發出延後 node document 的 load event：Blink 的 load event delay count，`dom` 的 document 上一個計數，renderer 判斷 `load` 時也看它（不在文件裡的 `new Image()` 也延後，Chrome 152 實測一樣）。renderer 這一側：`FrameRequests` 當場記下元素顯示哪個網址（layout 照它拿圖，所以換成已經有的圖時 `width` 當場就是新的），`start_loads` 抓還沒有的，回應交回 `image_fetched`；取代原本 renderer 在 `start_loads` 掃文件裡的 `<img src>`（每個元素只載第一次、不在文件裡的不載）。回應的狀態碼不是 2xx 但內容是圖時照樣顯示（Blink 的 `ImageResource`；WPT 的 `404-response-with-actual-image-data.html`）。
  - **4a 的成員**：照實測的 Chrome 152（`details.md` 的「Chrome 的 `<img>`」）。`complete`（沒有或空的 `src`、可用、壞圖時是 true）、`naturalWidth` / `naturalHeight`、`currentSrc`（圖來了之前是空字串，照 Chrome；HTML 是 microtask 之後就是新網址）、`width` / `height`（有 box 時是 content box，否則是 attribute 的非負整數，再否則是 natural size）、`decode()`（宣告表的 `Promise<()>`；圖已經可用時在 task 裡確認、那時 request 換了就 reject；在等的隨 `load` resolve、`error` 或換 request 時 reject，`EncodingError`）、`new Image(width, height)`（`[LegacyFactoryFunction]`），其他的是 reflection（`decoding`、`loading`、`fetchPriority` 是 limited to only known values）。`ExceptionName` 多了 `EncodingError`（`kun:dom` 的代碼 19）。沒有 Chrome 的 `x`、`y`、`browsingTopics`。
  - **4b `srcset`、`sizes`、`<picture>`**（第 8、11 到 13 條）：
    - **media query**（`style` 的 `media.rs`，Blink 的 `MediaQueryEvaluator` 和 `SizesAttributeParser`）：`MediaQueryList`、`MediaCondition`（`and`、`or`、`not`，Level 4 的三值邏輯：`<general-enclosed>` 和不認得的 feature 是 unknown，`<any-value>` 裡有沒配對的右括號就無效）、feature 有 `width`、`height`、`aspect-ratio`、`orientation`、`resolution`（和 `-webkit-device-pixel-ratio`）、`prefers-color-scheme`（`light`）、`prefers-reduced-motion`、`hover` / `any-hover`、`pointer` / `any-pointer`、`color`、`monochrome`、`grid`、`display-mode`，`min-` / `max-` 和範圍寫法；長度有 px、em / rem（16px）、in、cm、mm、q、pt、pc、vw、vh、vmin、vmax。`source_size`：`sizes` 的第一個 condition 符合（或沒有）、長度有效的那一項，都沒有時是 `100vw`（`default_source_size`）。和 Chrome 的 `matchMedia` 比對過，只有 `(hover)` 不同（headless 的 Chrome 說 `none`，kun 給桌面的答案）。
    - **`srcset`**（`dom_api` 的 `srcset.rs`）：HTML 的「parse a srcset attribute」逐步照做（descriptor 的 tokenizer、`w`、`x`、`h` 的錯誤）；選候選照 Blink 的 `PickBestImageCandidate`：`w` 是寬度除以 source size，依密度排序、同密度留第一個（有 `w` 時 `src` 不算），取第一個不小於 device pixel ratio 的（過了和前一個的幾何平均才取它，1x 以下另算），已經載入的、比較密的優先（`AvoidDownloadIfHigherDensityResourceIsInCache`）。
    - **選來源**（`select_source`，HTML 的「select an image source」）：`<picture>` 裡在 `<img>` 前面、有候選、`media` 符合、`type` 是 PNG、JPEG、GIF 的第一個 `<source>`，否則 `<img>` 自己的 `srcset` 和 `src`。request 帶著密度（`ImageRequest.density`），`naturalWidth` 和 layout 的大小（renderer 的 `DocumentImages`）都除以它。選不到來源時，只有有 `src` 屬性才發 `error`（照 Chrome 和 WPT 的 `null-image-source.html`；HTML 說用 `srcset` 或 `<picture>` 時也要）。
    - **relevant mutation**：`<source>` 的 `srcset`、`sizes`、`media`、`type` 改變時更新它後面的 `<img>`（`attribute_changed`）；`<img>` 插進或移出 `<picture>`、`<source>` 插進或移出 `<picture>`（它後面的 `<img>`）由 `dom` 記下（`record_picture_change`，`ElementChange::Image`）。
    - **留著同一張圖**：「update the image data」選到和 current request 同一個網址、密度，而那張圖已經可用或正在抓時，不換 request：舊的 `decode()` 不 reject，可用的再發一次 `load`（Blink 的同一個 `ImageResourceContent`；WPT 的 `image-decode-path-changes.html` 和 `image-decode-with-quick-attach.html`）。
    - **環境改變**（第 13 條）：renderer 在 `UpdateVisualProperties` 換了大小或 device pixel ratio 時對每個 frame，layout 換了子 frame 的大小時對那個 frame（記在 `FrameView`，下一個 `BeginMainFrame` 在 animation frame callback 之前，HTML 的「evaluate media queries and report changes」的位置；那次 layout 會再要一個 frame），呼叫 `dom_api::image::environment_changed`：document 裡用 `srcset` 或 `<picture>` 的 `<img>` 重新選，換了網址才更新 image data；同一個網址只換了密度時只改密度，不重新載入、不發 `load`（Blink 的 `HTMLImageElement::SelectSourceURL`，whatwg/html#4646；HTML 說要重新載入）。script 在第一次 layout 之前看到的主 frame 的大小和每個 frame 的 device pixel ratio 是視窗的（`LayoutClient::viewport`），parser 建的 `<img srcset>` 才選得對；還沒 layout 過的子 frame 沒有 viewport（`None`），選來源時先 layout 它一次（`geometry::with_layout`，和 `innerWidth` 一樣），拿到 iframe 的大小：Blink 的子 frame 在 iframe 插入時就有大小，kun 的要 layout 才有，所以只對還沒 layout 過的子 frame 這樣做，主 frame 的 parser 不必每個 `<img>` 都 layout（WPT 的 `srcset-natural-size-in-dynamic-iframe.html`，`browser` 的 `a_child_frames_images_select_for_its_iframes_size`：窄的那張不會先被抓）。
    - **和 Chrome 比對**（`browser` 的 `srcset_and_picture`、`srcset_and_picture_at_2x`，頁面在 Chrome 152 跑過）：Chrome 的 `w` 描述子的結果看時序：它的 preload scanner 先抓好的圖會因為「已經載入的比較密的優先」被選上，同一頁跑幾次答案不同（resize 之後大約一半留著比較密的、一半重新抓）。測試對照照 Blink 的規則、沒有 preload scanner 介入的那幾次；`<picture>` 的 AVIF `<source>`，Chrome 會用、kun 跳過。
    - **順便修的**：script 建的 iframe 的初始 `about:blank`，在 renderer 收下子 frame 之前（插入時同步發的 `onload` 裡）沒有 fallback base URL，相對網址解析不了；`FrameClient::create_child_frame` 帶著父 document 那時的 base URL（HTML 的「about base URL」，Chrome 也是建立時的值）。
  - **4c lazy loading 和 `sizes="auto"`**（第 9、14 到 16 條）：
    - **延後**（HTML 的「will lazy load element steps」，Blink 的 `LazyImageHelper`）：「update the image data」在 microtask 之後選好來源、解析好網址，`loading=lazy`、文件會跑 script、frame 願意看著它（`FrameClient::defer_lazy_image`）時不抓：request 記下網址，`deferred`（`complete` 是 false、`currentSrc` 是空的、沒有事件），frame 忘掉元素原本的圖。document 已經有的圖照舊當場可用（HTML 的這一步在 lazy 的檢查之前）。lazy 的 request 不延後 load event，繼續載入之後也不（Chrome 實測：viewport 裡的 lazy 圖在 window 的 `load` 之後才 `load`；HTML 沒有這樣寫）。
    - **繼續**（第 14 條）：renderer 的 `FrameRequests` 記著等著的元素和它的 request 的 generation；每次 rendering update 的 layout 之後，`FrameView::lazy_images_due` 看每個元素的 box（`client_rects`，沒有 box 的不算：`display: none` 的永遠不載）有沒有碰到最上層的 viewport 放大上下 1250px、左右 625px（第 15 條實測的值，邊碰到也算，`IntersectionObserver` 的 edge-adjacent）；子 frame 的元素只算 iframe 的 content box 露出來、和放大的 viewport 重疊的部分。碰到的，frame 不再看著它，render thread 在 commit 之後請 `dom_api::image::lazy_load_intersected` 排一個 task（DOM manipulation 的 task source；Chromium 的 `IntersectionObserver` 在 lifecycle 之後 post task），task 裡 generation 還對、還在等時用當時解析好的網址抓（HTML 的「lazy load resumption steps」：之後插入的 `<base>` 不算，WPT 的 `image-loading-lazy-base-url*.html`）。捲動時 compositor 的捲動帶著 scroll 事件，那個 main frame 有 rendering update，所以捲到附近就會檢查。`loading` 改成不是 lazy 時，`attribute_changed` 記下更新，「update the image data」看到同一個網址、還在等的 request 就立刻繼續。不在文件裡的（`new Image()`）沒有 box，永遠不載（Chrome 一樣）。
    - **`sizes="auto"`**（第 16 條，HTML 的「allows auto-sizes」）：lazy、`sizes` 的第一項是 `auto`（不分大小寫）時，`auto` 是上一次 layout 的 content box 的寬度（`LayoutClient::element_box`）；沒有 box（沒在 render）時是 `100vw`；沒有 `width` 屬性、還沒有圖、layout 的寬度是 0 時是 HTML 的 default object size 的 300px（kun 的 layout 對沒有圖的 `<img>` 不用 default object size）。`<picture>` 裡沒有自己的 `sizes` 的 `<source>` 也用 `<img>` 的 `auto`（WPT 的 `sizes-auto.html`）。不是 lazy 的 `sizes="auto, 10px"` 照 Chrome 是 `100vw`（HTML 說跳過 `auto`、用 `10px`；Chrome 的 `SizesAttributeParser` 看到開頭的 `auto` 就整個當 `auto`）。lazy 的圖繼續載入時重新選（那時寬度才知道）。frame 看著寬度（`FrameClient::watch_auto_sizes`，選的時候給 layout 的寬度），layout 之後寬度變了（或沒有 box 了）就請 `dom_api::image::auto_sizes_changed` 重新選，和環境改變一樣：換了網址才重新載入，只換密度就只改密度（Blink 用 `ResizeObserver` 做同樣的事）。
    - **`complete`**：照 HTML，`src` 和 `srcset` 都沒有、或只有空的 `src` 才直接是 true；原本只看 `src`，只有 `srcset` 的圖（包括還在等的 lazy 圖）載入中也是 true（`img.complete.html`、`lazy-out-of-band-load.html` 找到的）。
    - **和 Chrome 比對**（`browser` 的 `lazy_images`，`crates/browser/tests/resources/lazy.html` 在 Chrome 152 跑過）：viewport 裡的圖不延後 `load`、遠的不載、捲過去才載、iframe 在畫面外時裡面的不載、側邊 625px 內的載、改成 eager 立刻載（之後捲到也不再載一次）、`sizes="auto"` 用 content box（不含 padding）、寬度變了重新選、不是 lazy 的 `auto` 是 `100vw`，加上抓了哪些網址（`display: none` 的、不在文件裡的都沒抓）。
- **第 5 段 Window 的雜項**（第 17 條，三小段）：
  - **5a `crypto` 和 bytes 的形式**（第 18、19 條）：
    - **宣告表的 `ArrayBufferView`**（`dom_api` 的 `buffer.rs`）：`Base::ArrayBufferView`、`Value::BufferView`。JS 的是頁面自己的 typed array 或 `DataView` 的 handle（`BufferView::Script`，`ScriptValue`），經過 `ScriptHost` 的 `view_kind`、`view_byte_length`、`view_bytes`、`write_view` 讀寫（`dom_js` 的 `buffer.rs`：元素型別用 V8 的 `is_*_array`，讀用 `copy_contents`，寫進 buffer 的 backing store 的 `Cell<u8>`、從 view 的 `byte_offset` 開始，不需要 `unsafe`；每次都看當下的長度，detach 之後是 0），回傳時是同一個物件。WIT 是 `record typed-array { kind: typed-array-kind, bytes: list<u8> }`（`kind` 的說明寫著每個 case 的 JS 建構子名字，Lua 的 runtime 用它）：guest 的一份（`BufferView::Bytes`），成員寫進去、當結果交回。要留住內容的成員在呼叫的當下 `bytes()` 複製（第 19 條）。Lua 的產生器多了回傳 record（一個 table）和 bytes 的欄位（Lua 字串）。
    - **`Crypto`**（`dom` 的 `crypto.rs`，照 `Navigator`：只有 wrapper 和 window 的 edge，`window_crypto` 每次同一個；`dom_api` 的 `crypto.rs`，Blink 的 `modules/crypto`）：`getRandomValues` 先看元素型別（float 和 `DataView` 是 `TypeMismatchError`），再看長度（超過 65536 byte 是 `QuotaExceededError`），訊息照 Chrome；亂數用 `getrandom` 的 `fill`（第 18 條），寫回同一個 view 再回傳它。`randomUUID` 是第 4 版（16 個亂數 byte 設好版本和 variant 的 bit，小寫的十六進位）。沒有 `subtle`；`randomUUID` 在任何頁面都有（kun 沒有 secure context）。`window.crypto` 是 `Window` 的屬性（WebCrypto 的 `WindowOrWorkerGlobalScope` mixin）。
    - **例外**：`ExceptionName` 多了 `TypeMismatchError`（`kun:dom` 的代碼 20）、`QuotaExceededError`（21）。Chrome 152 的 `QuotaExceededError` 已經是 WebIDL 的 `DOMException` 子類別（WPT 的 `assert_throws_quotaexceedederror` 也要它）：`dom_js` 的 `glue.js` 定義它（`quota`、`requested` 預設 null；`QuotaExceededErrorOptions` 照 WebIDL 的 `double` 轉換，非有限是 `TypeError`；照 Chrome 不檢查負數和 `requested` 小於 `quota`，WebIDL 說是 `RangeError`），`glue.js` 回傳兩個建構子，`new_dom_exception` 對這個名字用子類別建。
    - **和 Chrome 比對**（`dom_js` 的 `crypto` 測試，`details.md` 的「Chrome 的 `crypto`」）：每一種 typed array、範圍在 buffer 中間的 view、detach 的、長度的邊界、不是 view 的參數、`QuotaExceededError` 本身。wasm 的 guest（`crypto.c`）和 Lua（W9 的第 32 項）也測同樣的事。
  - **5b `requestIdleCallback`**（第 20 條）：
    - **DOM 和宣告表**：`dom` 的 `Timers` 多了 idle callback 的表（handle 和 timer、animation frame 共用一個序號），每個記著 window、callback、是否「這段 idle period 可以跑」、`timeout` 的到期時間。`start_idle_period` 把已經排著的都標成可以跑，callback 自己再排的等下一段（HTML 的「start an idle period」）。`dom_api` 的 `requestIdleCallback`、`cancelIdleCallback` 是 `[JsOnly]` 的成員（宣告表多了成員層級的 `[JsOnly]`）：callback 型別 `IdleRequestCallback` 收 deadline（文件的時間）和 `didTimeout` 兩個值，`IdleDeadline` 由 `dom_js` 的 `glue.js` 包：私有欄位存兩個值，`timeRemaining()` 用頁面拿不到的 `performance.now()` 算剩多少（`didTimeout` 時是 0），頁面的 `new IdleDeadline()` 是 `TypeError`。不進 `kun:dom`：wasm 的 guest 有自己的排程，沒有要等 frame 的理由。
    - **idle period**（`renderer` 的 render thread，Blink 的 `IdleHelper` 和 `ScriptedIdleTaskController`）：loop 的 channel 空了（沒有輸入、Viz 的訊息）時跑一個 idle callback，一個一個跑、中間讓其他 task 先。正在畫的時候（等 BeginMainFrame、有 mouse move 要送、有 animation frame callback）期限是上一個 main frame 加 1000/60 ms，過了就等下一個 frame；沒有東西要畫時是最長 50 ms 的 long idle period，下一個 timer 或 DOM 的 task 更早到期就提早結束。期限在 period 開始時就固定（Chrome 也是，`deadline-max-*-dynamic.html` 兩邊都失敗），傳給頁面前和 `performance.now()` 一樣 coarsen。
    - **timeout**：到期的照一般的 timer 排，和 timer 照到期時間交錯（Blink 是同一條 queue 上的 delayed task），連續的 `setTimeout(0)` 擋不住它；這時沒有 idle period，`didTimeout` 是 true。文件換掉時和 timer 一起丟掉。
    - **和 Chrome 比對**（`browser` 的 `idle_callbacks`，`crates/browser/tests/resources/idle.html` 在 Chrome 152 跑過；`details.md` 的「Chrome 的 `requestIdleCallback`」）：沒有東西要畫時剩不超過 50 ms、callback 裡排的到下一段才跑、`requestAnimationFrame` 一直在跑時剩不超過一個 frame、忙碌時 timeout 照樣在忙完前執行、取消的不跑、順序、`IdleDeadline` 本身。
  - **5c `Blob`、`blob:` 網址和 bytes 的 body**（第 21、22 條）：
    - **宣告表的 bytes**（`dom_api` 的 `buffer.rs`）：`Base::BufferSource`（參數，`Value::BufferSource`：JS 是頁面的 `ArrayBuffer` 或 view 的 handle，成員在呼叫的當下 `bytes()` 複製；WIT 是 `list<u8>`）、`Base::ArrayBuffer` 和 `Base::Uint8Array`（回傳值，`Value::ArrayBuffer` / `Value::Uint8Array`，`Arc<[u8]>`：JS 建新的 buffer，WIT 是 `list<u8>`），以及 `Base::ClampedI64`（`[Clamp] long long`，`slice` 的參數，WIT 是 `s64`）。JS 的 union 照 WebIDL 先認 `ArrayBuffer` 和 view、再認 iterable（typed array 是 iterable）。照 WebIDL 和 Chrome，沒有 `[AllowResizable]` 的成員不收 resizable 的 buffer（`TypeError`），5a 的 `ArrayBufferView` 也一樣。
    - **`Blob`**（`dom` 的 `blob.rs`，Blink 的 `Blob` 和 `BlobDataHandle`：沒有 edge 的 GC 型別，`BlobData` 是 `Arc<[u8]>` 的一段和 type，建立之後不變，`slice` 共用同一份 bytes；`dom_api` 的 `blob.rs`）：建構子照 File API 的「process blob parts」（字串 UTF-8，`endings: "native"` 時換行轉成平台的；buffer 當場複製；blob 照它的 bytes），type 有 U+0020 到 U+007E 以外的字元就是空的、否則轉小寫；`size`、`type`、`slice`（負的從尾端算、clamp，`[Clamp]` 四捨六入）；`text()`、`arrayBuffer()`、`bytes()` 和 body 的讀取共用一條路：在 networking task source 的一個 task 裡 settle（在之前排好的 microtask 之後）。沒有 `stream()`、`textStream()`（沒有 streams）和 `File`。
    - **bytes 的 body**：`BodyInit` 多了 `Blob` 和 `BufferSource`。`extract` 時 blob 的 type 不是空的才當 `Content-Type`，buffer 沒有；`Request` / `Response` 多了 `arrayBuffer()`、`bytes()`、`blob()`。`blob()` 的 type 照 Chrome 是 `Content-Type` 的值轉小寫（`text/html; charset="utf-8"`），不是 Fetch 解析、序列化過的 MIME type。
    - **`blob:` 網址**（第 21 條）：`URL.createObjectURL` 給 `blob:`、目前 realm 的 origin（opaque 的是 `null`）、`/` 和新的 UUID，經過 frame 登記（`FrameClient::register_blob_url`）；`revokeObjectURL` 只撤銷同 origin 的。renderer 的 `BlobUrls`（`loader.rs`，Blink 的 `PublicURLManager`）記著每個網址是哪份文件的 realm 登記的：登記當場送 `RendererHostMsg::RegisterBlobUrl`（網址、type、bytes）；撤銷在 renderer 當場生效（之後的 `fetch()`、`<img>` 在 stable state 之後解析到它就是 network error，不再問 Browser），送給 Browser 的 `RevokeBlobUrl` 延到 loop 這一輪的最後（`flush_revoked`），同一個 task 裡先要的載入（`fetch()`、`<script>`、iframe、主 frame 的導覽）都已經送出、拿得到 blob。文件丟棄時撤銷它登記的網址：iframe 移除時由 `dom_api` 當場通知（`FrameClient::documents_discarded`），其他時候在丟棄的地方。Browser 的 blob URL 表在 `net`（`blob.rs`，Chromium 的 `BlobUrlRegistry` 和 `BlobURLLoader`，在 Browser process）：每個網址記著登記的 renderer；IO thread 收到登記就加進去，子資源的 `blob:` 在 IO thread 上當場回應（只給登記它的 renderer、`GET`、沒被撤銷的；`Range` 給 206 和 `Content-Range`；`Content-Type` 是 blob 的 type，空的照樣送，MIME type 空的時候 sniff），不經過 network thread。撤銷分兩步：IO thread 把網址標成子資源不能用，再轉給 UI thread，UI thread 處理到時才拿掉；主 frame 的導覽在 UI thread 上照順序處理，所以同一個 task 裡先要的導覽拿得到 blob（Chromium 用解析網址時拿的 `BlobURLToken` 做到同樣的事）。renderer 結束時 Browser 拿掉它所有的網址。導覽到 `blob:` 的文件的 origin 是網址裡的 origin。
    - **和 Chrome 比對**（`dom_js` 的 `blob` 測試和 `browser` 的 `blobs`，`crates/browser/tests/resources/blob.html` 在 Chrome 152 跑過；`details.md` 的「Chrome 的 `Blob` 和 `blob:` 網址」）：建構子的各種 part、type、`slice`、resizable 的 buffer、body 的 `Content-Type`；讀取的時機、`fetch()` 一個 blob URL 的 status、headers、range、`POST`、撤銷前後、`<img>`（撤銷之後才解析，載不到）、`<script>`、iframe、子 frame 的網址跟著文件走、主 frame 導覽到剛撤銷的 blob URL。wasm 的 guest（`blob.c`）和 Lua（W9 的第 33 項）也測同樣的事；Lua 的字串本身就是 bytes，union 裡的 bytes 的 case 不給 Lua 用，字串走字串的 case。

### 分階段

五段，照上面的順序做：先做擋住最多 suite、最小的 `console`，跑一次盤點看三個 suite 真正的第一個錯誤，再決定後面的順序（第 3 條：照原來的）。每段開始前只決定那一段的事（C 到 F 各屬一段）；第 4、5 段各分三小段（第 10、17 條）。第 1 到 4 段做完時各自 merge 回 `main`，第 5 段的三小段一起。

## 缺點

- 範圍是一堆小東西，每一個都要對規範和 Chrome；reflection 的成員很多，主要的風險是漏掉邊界。
- 宣告表多了好幾種形式（namespace、別名、成員層級的 `[JsOnly]`、bytes 的四種型別），每一種都碰到 `dom_js`、`kun:dom` 和 Lua 的產生器。
- 和 RFC 0027 同時做：宣告表、`ScriptHost`、`dom_js` 的 `templates.rs` 兩邊都改，各段 merge 前 rebase 到最新的 `main`（`progress.md` 記了那次 rebase）。
- `<img>` 的「update the image data」改動了既有的載入路徑，和背景圖共用的 `images` 表要小心。

## 理由和其他做法

A、B 在開始前定（「已決定的事項」第 1、2 條），C 到 F 在各自那一段開始前定。完整的比較見 `details.md`。

- **A. 範圍和順序**：A1 五段，`console` 第一；A2 照路線圖原本的清單、不加 `console` 和 global attribute；A3 把 `console` 單獨拉出去先做、H2 其他的另開。決定：A1（第 1 條）。
- **B. `console` 在哪裡實作**：B1 照 Chromium 用 V8 自己的 `console` 加 `v8::debug::ConsoleDelegate`（rusty_v8 的 fork 加 binding、重編 V8）；B2 擴充 `bindings` 手寫的 `console`；B3 宣告表新增 namespace 的形式，`console` 是一個 namespace。決定：B3（第 2 條）。
- **C. `srcset` 和 `sizes`**：照 HTML 的「select an image source」挑，或只看 `src`。決定：C1（第 8 條）。
- **D. `getRandomValues` 的亂數**：`dom_api` 用作業系統的 CSPRNG，或由 renderer 經過 `FrameClient` 給。決定：D1（第 18 條）。
- **E. `requestIdleCallback` 什麼時候算閒**：照 Chromium 的 idle period，或 event loop 沒有 task 時。決定：E1（第 20 條）。
- **F. `Blob`、`blob:` 網址和 `FormData`**：`Blob` 在這份（RFC 0027 交給這份）；存在 renderer 或 Browser；`FormData` 做不做。決定：F1c（第 21 條）、F2b（第 22 條）。

## 先例

- **Chromium**：`console` 是 V8 的 builtin（`src/builtins/builtins-console.cc`），Blink 透過 inspector 的 `V8Console` 和 `ConsoleMessage` 輸出；`Blob` 的 bytes 和 blob URL 在 Browser 的 `BlobRegistry` / `BlobUrlRegistry`（這份只把 blob URL 放在 Browser，第 21 條）；`HTMLElement` 的 global attribute 在 `html_element.idl`（大多是 `[Reflect]`）；`HTMLHyperlinkElementUtils` 是 Blink 的 `HTMLAnchorElement` 加 `DOMURLUtils`；`HTMLImageElement` 和 `ImageLoader`（「update the image data」）；`Crypto`（`core/` 外的 `modules/crypto`）；`ScriptedIdleTaskController`（`requestIdleCallback`，閒置時間由 scheduler 的 idle period 給）；`Blob` 和 `BlobRegistry`（Browser process 存 blob，renderer 經過 mojo）。
- **RFC 0017（H1）**：同一類的工作，照它的做法（每組一個階段、新的 GC 型別照 `crates/dom/README.md`、WIT 的版本）。

## 已決定的事項

1. **五段，`console` 第一（A1）**（2026-10-10）：`console`、節點和 HTML 元素的小成員、`<a>` 的網址成員、`<img>` 和 `Image`、Window 的雜項（`crypto`、`requestIdleCallback`、`Blob`），照擋住的 suite 多寡排；`console` 最小、擋住最多 suite（NewsSite-Next、NewsSite-Nuxt、Charts-chartjs），而且做完才看得到那三個 suite 真正的第一個錯誤，第 2 段起可以照那時的盤點調整順序。比路線圖原本的 H2 多了 `console` 和 `HTMLElement` 的 global attribute（盤點裡用到的 suite 數排在前面）。不選只做路線圖原本的清單（A2）：三個 suite 還是停在 `console`；不選把 `console` 另開一份（A3）：內容一樣，多一份 RFC 要維護。
2. **`console` 是宣告表的 namespace（B3）**（2026-10-10，第 1 段開始前）：宣告表新增 `namespace` 的形式（WebIDL 的 namespace：沒有建構子、沒有 prototype 鏈，成員是 namespace 物件上的函式），`dom_js` 和 `kun:dom` 的產生器都支援；`console` 的方法、Console 規範的 Logger 和 Formatter、count / timer / group 的狀態都在和 engine 無關的 `dom_api`，輸出交給 frame 的 client（renderer 寫到 stderr）。引數是 `any`，照 RFC 0008 的規則 `console` 只給 JS；wasm 的 guest 照舊用 WASI 的 stdout。namespace 的形式之後 `CSS`（`CSS.supports`、`CSS.escape`）等也用得到。和 Chromium 的分層不同（Chrome 的 `console` 是 V8 的 builtin，Blink 經過 inspector 的 `V8Console` 拿到訊息），之後接 DevTools 時要改成 V8 的 `console` 加 delegate（B1）。不選 B1：要在 rusty_v8 的 fork 加 C++ 的 binding、重編 V8，而從原始碼編 V8 只在 macOS 上做過；不選擴充手寫的 `console`（B2）：工作量最小，但什麼都沒留下，邏輯也綁在 V8 上。

3. **第 2 段起照原來的順序（G1）**（2026-10-10，第 2 段開始前）：第 1 段之後的盤點裡，NewsSite-Next 停在 `crypto.getRandomValues`（第 5 段），NewsSite-Nuxt 停在 `SVGElement`（O），Charts-chartjs 停在 Canvas（N）；第 2 段的成員是最多 suite 用到的（5 到 7 個）。不選把 `crypto` 提到第 2 段（G2）：NewsSite-Next 會早一點往前，但 `getRandomValues` 要宣告表的 `ArrayBufferView`，bytes 的形式會拆成兩次設計，D 也要先定。
4. **宣告表有別名（H1）**（2026-10-10，第 2 段開始前）：interface 可以帶 `[LegacyWindowAlias=名字]`（WebIDL 的 extended attribute，Blink 在 IDL 上寫、bindings 的產生器處理），`dom_js` 把同一個 interface object 放在 global 的第二個名字上（和第一個一樣 DONT_ENUM），`kun:dom` 不管它（guest 用不到）；`spec` 測試和 IDL 的 `[LegacyWindowAlias]` 比對。`WebKitMutationObserver` 是第一個，之後 `webkitURL` 等也用。不選在 `dom_js` 的 install 寫死（H2）：宣告表看不到，`spec` 測試比對不到。
5. **`visibilityState` 接 `WasHidden` / `WasShown`（I1）**（2026-10-10，第 2 段開始前）：renderer 收到時對分頁裡的每份文件跑 HTML 的「update the visibility state」：改 `Document` 的狀態，同步發一個 bubble 的 `visibilitychange`（Chromium 的 `Page::SetVisibilityState` → `Document::DidChangeVisibilityState`）；背景分頁一開始就是 `hidden`。不選永遠是 `visible`（I2）：最小，但分頁切走時頁面不知道。實作時（2026-10-10）兩處照 Chromium 的分層調整：狀態放在整頁（renderer 的 `FrameSettings`，Blink 的 `Page`），document 經過 frame 讀，不是每份 `Document` 各存一份；初始的狀態不放進啟動 renderer 的參數，改成 browser 背景開分頁時先 `was_hidden` 再導覽（Chromium 的 `initially_hidden`），IPC 有順序，renderer 在 commit 任何文件之前就收到：效果一樣，不必多一個參數，relaunch 的 renderer 也照原本的方式補送 `WasHidden`。
6. **`<area>` 和 `<a>` 一起做（J1）**（2026-10-10，第 3 段開始前）：`HTMLAreaElement` 和 `HTMLAnchorElement` 共用 `HTMLHyperlinkElementUtils` 的函式和 `target`、`download`、`ping`、`rel`、`relList`、`referrerPolicy`，加上它自己的 `alt`、`coords`、`shape`（Blink 的 `HTMLAreaElement` 繼承 `HTMLAnchorElement`；規範是同一個 mixin），只做 IDL，不做 image map 的點擊區域；`document.links` 照規範包含有 `href` 的 `<area>`。不選只做 `<a>`（J2）：`<area>` 還是 `HTMLElement`、`document.links` 要寫成限制，省下的工作很少。
7. **`<img>` 的載入照 Chromium 的 `ImageLoader`（K1）**（2026-10-10，第 4 段開始前）：`dom_api` 照 HTML 的「update the image data」（`src`、`srcset`、`sizes`、`crossorigin`、`referrerpolicy` 改變、parser 建立帶 `src` 的元素、adopt）在元素上記下 current request（`dom` 的每個元素一份：網址、狀態、natural size），經過元素的 node document 的 frame 請 renderer 抓；回應來時 renderer 更新元素的狀態，`load` / `error` 排進 DOM 的 task。不在文件裡的元素也載（`new Image()` 預載）；layout 和 paint 照元素的 current request 拿圖。不選保留 renderer 在 `start_loads` 掃文件裡的 `<img>`（K2）：改動小，但 `new Image()` 不在文件裡就不載，狀態也在 renderer、`dom_api` 要另外問。
8. **`srcset` 和 `sizes` 照 HTML 的「select an image source」（C1）**（2026-10-10，第 4 段開始前）：解析 `srcset`（`x` 和 `w` descriptor）和 `sizes`（media condition 和長度，要 viewport 的寬和 device pixel ratio），照 Chromium 挑一張，viewport 或 DPR 變了時重新挑（HTML 的「relevant mutations」和「environment changes」）。不選只看 `src`（C2）：工作量小，但 `currentSrc` 和挑出來的解析度和 Chrome 不同。
9. **`loading="lazy"` 做 lazy loading（L2）**（2026-10-10，第 4 段開始前）：照 Chromium 的 `LazyLoadImageObserver`，元素接近 viewport 才開始載入，在 `IntersectionObserver`（路線圖的 M）之前先在 renderer 的 rendering update 裡、layout 之後檢查位置。不選只做 reflection、照樣立刻載（L1）。
10. **第 4 段分三小段**（2026-10-10，第 7 到 9 條之後）：4a 是 K1 的載入和 `HTMLImageElement` 的成員、`Image()`、`load` / `error`、`decode()`；4b 是 C1；4c 是 L2。每小段開始前只決定那一小段的事。
11. **`style` 做 media condition（M1）**（2026-10-10，4b 開始前）：照 Blink 的 `MediaQueryEvaluator`，`style` 有 media query 的解析和評估：`width`、`height`（含 `min-`、`max-` 和 Level 4 的範圍寫法）、`resolution`、`orientation`、`prefers-color-scheme`，`and`、`or`、`not`，media type；長度有 px、em / rem（初始字型大小）、vw / vh 等。`sizes` 和 `<source media>` 用它，之後 `matchMedia`、`@media` 共用。不選 `sizes` 只認沒有 condition 的長度（M2）：最小，但常見的 `(max-width: …) …, …` 都落到預設值，挑出的解析度和 Chrome 不同。
12. **`<picture>` 和 `<source>` 一起做（P1）**（2026-10-10，4b 開始前）：`HTMLPictureElement`、`HTMLSourceElement`（`src`、`srcset`、`sizes`、`media`、`type`、`width`、`height`），「select an image source」照 HTML 先看 `<picture>` 裡在 `<img>` 前面的 `<source>`（`media` 用第 11 條的評估，`type` 只認 kun 會解碼的 PNG、JPEG、GIF）。不選只做 `<img>` 自己的 `srcset`（P2）：`<picture>` 裡的 `<img>` 只看自己的，記成限制。
13. **viewport 或 device pixel ratio 改變時重新挑（R1）**（2026-10-10，4b 開始前）：renderer 在 viewport 的大小或 device pixel ratio 改變時，對用了 `srcset` 或在 `<picture>` 裡的 `<img>` 重新跑「select an image source」，挑到別張才重新載入（HTML 的「react to environment changes」，Chromium 在 media query 的結果改變時）。不選只在 relevant mutation 時挑（R2）。
14. **lazy 的圖在 layout 之後檢查、在 task 裡恢復（S1）**（2026-10-10，4c 開始前）：每次 `BeginMainFrame` 的 layout 之後，renderer 走過每個 frame 裡延後中的 `<img>`，算它的 box 和（加上距離的）viewport 有沒有相交，相交的在之後的一個 task 裡跑 HTML 的「lazy load resumption steps」。Chromium 的 `IntersectionObserver` 也是在 lifecycle 結束時算交集、post task 通知 `LazyLoadImageObserver`，時間點和分層一樣，之後有 `IntersectionObserver` 時換成它。不選在 layout 的當下同步恢復（S2）：簡單，但在 layout 中途跑 script 那一側的步驟，Chromium 不這樣做。
15. **距離照 Chromium（T1）**（2026-10-10，4c 開始前）：先量 Chrome 152 用的值（Chromium 的 `lazyImageLoadingDistanceThresholdPx*`，照網路的速度）。實測（2026-10-10）是上下 1250px、左右 625px，從不含捲軸的 viewport 邊緣算；子 frame 裡的圖對最上層的 viewport 算（`IntersectionObserver` 的 implicit root：iframe 在畫面外時，裡面的圖不載），原本寫的「對它自己的 viewport」是猜的，量了之後改。不選距離 0（T2）：規範允許，但和 Chrome 差很多，捲動時圖比較晚出現。
16. **`sizes="auto"` 一起做（U1）**（2026-10-10，4c 開始前）：lazy 的 `<img>` 的 `sizes=auto` 用它 layout 出來的寬度當 source size（恢復時寬度已知），之後寬度改變時在同一個 layout 後的檢查裡重新選（照 Chrome；WPT 的 `sizes-auto-dynamic-attributes.html`）。不選照舊當無效（U2）：WPT 的 `sizes/sizes-auto*.html` 的失敗留著。
17. **第 5 段分三小段（V1）**（2026-10-10，第 5 段開始前）：5a 是 `crypto` 連同宣告表的 bytes 形式（`getRandomValues` 收 typed array），5b 是 `requestIdleCallback`，5c 是 `Blob`、`blob:` 網址和 `Response` / `Request` 的 bytes（`arrayBuffer()`、`bytes()`、`blob()`、bytes 的 body），`FormData` 在 5c 開始前決定。`crypto` 先做：它擋住 NewsSite-Next（uuid 用 `getRandomValues`），bytes 的形式是它和 `Blob` 共用的基礎。不選一段做完（V2）：太大，中間沒有審核的點。
18. **亂數來自作業系統的 CSPRNG（D1）**（2026-10-10，5a 開始前）：`dom_api` 用 `getrandom` crate（依賴樹裡已經有）。Chromium 也在 renderer 裡產生（Blink 的 `Crypto::getRandomValues` → `crypto::RandBytes` → BoringSSL 的 `RAND_bytes`，底下是 Linux sandbox 允許的 `getrandom` 系統呼叫），拆 process 之後一樣能用。不選經過 `FrameClient` 由 renderer 或 Browser 給（D2）：多一層介面，Chromium 不這樣做。
19. **bytes：JS 是 view 的 handle，wasm 複製（X3）**（2026-10-10，5a 開始前）：宣告表多一種 typed array 和 `ArrayBuffer` 的參數，JS 那邊是 engine 的物件的 handle，`ScriptHost` 讀它的元素型別、長度、內容和寫回（Blink 的 `DOMArrayBufferView` 指著 V8 的記憶體；每次讀寫重新檢查 detach 和長度）；WIT 是 `list<u8>`（component 之間只能複製），原地寫入的參數在 wasm 是「傳進去、傳回來」。規範要求在呼叫的當下「get a copy of the bytes」的 API 在 `dom_api` 用共用的函式當場複製。不選在邊界上一律複製（X1）：簡單，但之後 `TextEncoder.encodeInto`、Streams 的 BYOB 讀取等原地寫入的 API 要再改；不選 JS 和 wasm 都是 handle（X2）：wasm 的 guest 的記憶體 host 拿不到，要另做一個逐段讀寫的 resource，又慢又難用。
20. **`requestIdleCallback` 照 Chromium 的 idle period（E1）**（2026-10-10，5b 開始前）：render thread 在每次 rendering update（commit）之後、到下一個 frame 的預期時間之前，event loop 沒有別的 task 時開一段 idle period，在裡面執行開始之前排好的 callback，`timeRemaining()` 是到期限還剩多少；沒有東西要畫時是最長 50 ms 的 long idle period。給了 `timeout` 的，到期還沒執行就排成一般的 task，`didTimeout` 是 true（Blink 的 `ScriptedIdleTaskController` 和 scheduler 的 idle task）。不選 event loop 空下來就全部執行、一律 50 ms（E2）：簡單，但有動畫時會插在兩個 frame 之間，時間點和 Chrome 不同。
21. **Blob 的 bytes 在 renderer，`blob:` 網址登記在 Browser（F1c）**（2026-10-10，5c 開始前）：`Blob` 的 bytes 在 renderer（不可變，`slice` 共用同一份），`text()`、`arrayBuffer()`、`bytes()` 在 renderer 當場讀。`URL.createObjectURL` 把網址、origin 和 bytes 登記到 Browser 的 blob URL 表，`revokeObjectURL` 和文件丟棄時撤銷；`blob:` 的載入（導覽、子資源、`fetch()`）都照一般的路經過 Browser 的 `net`，Browser 照網址的 origin 檢查請求的一方。撤銷延到那個 task 的子資源送出（`start_loads`）之後才送：同一個 task 裡設好的 `src` 在撤銷前就到 Browser（規範在解析網址時抓住 blob，WPT 的 `url-in-tags-revoke.window.js`；Chromium 用解析時拿的 `BlobURLToken`）。bytes 現在是 `Arc<[u8]>`，同一個 process 裡不複製，拆 process 之後 `createObjectURL` 時複製一次。實作時（2026-10-10）兩處調整：子資源的請求沒有 initiator，Browser 不知道是哪個 origin 要的，所以照登記的 renderer 檢查（子資源只給它，導覽不限），同一個 renderer 裡的 origin 由 renderer 檢查（`revokeObjectURL` 只撤銷同 origin 的）；撤銷分兩步，IO thread 先標記子資源不能用、UI thread 再拿掉，因為導覽在 UI thread 上照順序處理，IO thread 當場拿掉的話，同一個 task 裡先要的導覽會拿不到。不選全在 renderer（F1a）：主 frame 導覽到 `blob:`、開新分頁時 Browser 拿不到。不選照 Chromium 全在 Browser 的 `BlobRegistry`（F1b）：每個 Blob 被 GC 收掉時要送釋放的訊息（`dom` 要 finalizer），讀取也要經過 Browser。之後 Blob 要跨 process（`postMessage`、IndexedDB）時再把 bytes 送過去；大的 blob 不存到磁碟。
22. **`FormData` 另開，和表單送出一起做（F2b）**（2026-10-10，5c 開始前）：form 的 entry list 和 `multipart/form-data` 的編碼是表單送出（POST）和 `FormData` 共用的（Chromium 的 `FormData` 和 `FormSubmission` 也共用）；Chrome 錄下的 default 20 個 suite 都沒用到 `FormData`。5c 只做 `Blob` 和 bytes。不選在這份加 5d（F2a）：表單送出不在這份，entry list 要做兩次或做一半。不選只做 `FormData` 物件和它當 body（F2c）：沒有從 `<form>` 建的部分，是半套。
