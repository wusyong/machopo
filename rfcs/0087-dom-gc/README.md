- 狀態：✅ 已完成：2026-10-26（GC 本身，第 0 到 6 段；驗收和做過的檢查見 `progress.md`。第 7 到 9 段各自另寫）

## 摘要

用 Rust 寫一個專門給 DOM 用的 GC，取代現在經過 FFI 用的 cppgc。架構照 V8 給 JS heap 用的那一套：bump 配置的 nursery 和平行的 scavenge、old generation 的 concurrent marking 和 concurrent sweeping、32 位元的壓縮指標（old 不搬動：量過碎片，在量的工作上 compaction 放不掉頁）；但照 DOM 的特性設計：一個 heap 只有一個 mutator，GC 只在安全點收尾（那時沒有任何沒 root 的指標，所以能搬動物件、也不必掃 stack），barrier 是 SATB 加上 black allocation，marker 照每個型別的 layout 描述只讀指標欄位，物件預設沒有 finalizer。對外的 API 是 safe 的（`unsafe` 只在 GC 的 crate 裡），soundness 由 soundness 文件、Miri、loom、shuttle、TLA+ 的協定模型、Verus、對著參考模型的 fuzz 和 heap verifier 守住。DOM 照這個 GC 的規則重新設計；wasm 文件先用，JS 文件之後經過每個 wrapper 背後一個小的 cppgc 物件接上 V8。這份只寫 GC 本身、DOM 用它的規則和接 wasm、V8 的介面；GC 做完了（`crates/gc`，還沒有 crate 用它，`gc_bench` 量），新的 DOM、`dom_wasm` 和 `dom_js` 的改寫各自另寫，整條路的順序在「分階段」。

## 動機

**現況**：DOM 的物件放在 V8 附帶的 cppgc 上：JS 文件用接上 isolate 的 `CppHeap`，wasm 文件用不接 isolate 的單獨的 `cppgc::Heap`（rusty_v8 fork 的 `StandaloneHeap`）。每一次配置、寫邊、建 root 都穿過 FFI，不能 inline；cppgc 不知道 Rust 型別的性質，每個 Rust 物件都要一個 finalizer、一律交回 main thread；它的規則（保守掃描、Dijkstra barrier、不搬動）是為 C++ 的 Blink 設計的，kun 為了配合它，root、id 表和 fork 裡的 C++ 改動越來越多，`crates/dom/soundness.md` 的 concurrent 模式形式上最多只能和 V8 本身一樣（C1）。2026-10-24 的取樣（`details.md` 的「動機的量測」）：Speedometer 裡 strong root 約佔 renderer main thread 的 2.2%，GC 那一類 kun 自己的機制每個 iteration 約 21 ms，加上 wasm 的路徑只為了 cppgc 連結 V8。

GC 換成自己的，配置、barrier、回收的時機、物件的佈局都能照 DOM 的需要設計，之後的優化也不再被 cppgc 和 FFI 擋住。

**目標**：

- 一個用 Rust 寫的 GC，marking 和 sweeping 在背景的 thread 上做，main thread 只在很短的 pause 裡收尾。
- 效能媲美 V8 的 GC：在同樣的 DOM 工作上不輸 cppgc，同樣的配置模式下 scavenge 和 marking 的速度和 V8 相當（量法在「測試」）。
- 專門為 DOM 設計：先設計 GC，DOM 照它的規則重新設計；目前 `dom` 的型別和限制不是前提。
- 對外的 API 是 safe 的：不寫 `unsafe` 的 DOM 程式碼不可能造成 UB。
- 支援 wasm 文件和 JS 文件（JS 照舊跑在 V8、JS 的物件照舊由 V8 的 GC 管）；這是第二順位，和 GC 本身的設計衝突時以 GC 為準。

**不在範圍內**：

- JS 的物件、取代 V8、JIT。
- 新的 DOM 和 `dom_api` 的改寫、`dom_wasm` 和 `dom_js` 換過來：各自另寫（「分階段」），這份只定它們要照的規則和介面。
- wasm GC 的物件放進這個 heap：「之後的可能」。

要解決的 `docs/limitations.md` 裡的限制：「GC 和 `dom`」的「Concurrent marking 還不是預設」（換過來的文件）。

## 設計概要

之後寫 DOM 的人看到的樣子（名稱照 Chromium 的 Oilpan；`Element` 是示意，新的 DOM 另寫）：

```rust
#[derive(GcObject)]
struct Element {
    parent: Member<Node>,          // 指向 GC 物件：atomic 的 32 位元，寫入經過 barrier
    first_child: Member<Node>,
    attributes: Member<HeapVector<Attribute>>,
    flags: Cell<u32>,              // 純資料：照一般的 Rust 寫，marker 不讀
    computed: External<RefCell<Option<Arc<ComputedStyle>>>>,  // native 的資料一律包在 External 裡
}

heap.mutate(|cx| {
    // derive 產生的 init struct：Member 的欄位在這裡是 Option<Gc<'gc, T>>，
    // alloc 在 heap 上的位置寫成物件，Member 從頭到尾不在 heap 外
    let div = cx.alloc(ElementInit {
        parent: None,
        first_child: None,
        attributes: Some(HeapVector::new(cx, 0)),
        flags: Cell::new(0),
        computed: External::new(RefCell::new(None)),
    });
    parent.append_child(cx, div);          // Gc<'gc, Element>：這次操作裡的裸指標
    div.parent.set(cx, Some(parent));      // 之後改的邊經過 barrier
    let keep = Persistent::new(cx, div);   // 要留到操作之外的才 root
});
```

- **一次操作**（`mutate` 的 closure）裡不會 GC：`Gc<'gc, T>` 是裸指標，lifetime 綁在這次操作，可以放進 `Vec`、被 closure 捕捉，編譯器保證它活不出操作。不需要掃 stack，也不需要 RFC 0060 的 no-GC scope。
- **安全點**：操作之間（wasm 是每次 host 呼叫的進出和 task 之間，JS 文件是每次進入 V8 之前）。scavenge、marking 的開始和收尾都只在這裡；那時所有參照都在 heap 的欄位、root 表和 id 表裡，所以 GC 可以搬動物件。
- **留到操作之外**用 `Persistent<T>`：root 表的一格，存的是索引，物件搬動時表跟著更新。wasm 的 guest 拿到的 handle 就是它。
- **欄位只有幾種**：`Member` / `WeakMember`（和它們的陣列）、`EphemeronPair`、純資料（`HeapData`：整數、`Cell<u32>` 這類沒有指標的）和 `External<T>` / `LocalExternal<T>`。`Arc`、`Box`、`Vec` 這類 native 的資料要包在 `External<T>`（`T: Send`）或 `LocalExternal<T>` 裡，直接放在欄位上 derive 會報錯；陣列和清單是另一個 GC 物件 `HeapVector`。現在 `External<T>` 的值就放在物件裡；之後可以不改 DOM 的程式碼換成 side table 的索引，讓 heap 成為沙盒（已決定的事項 7）。
- **大部分物件沒有 finalizer**：陣列放在 GC heap 上（`HeapVector`；GC heap 上的字串留給新的 DOM），死掉時什麼都不用做；只有 `External<T>` 或 `LocalExternal<T>` 的 `T` 有 `Drop` 時才需要：`External` 的（`Send`）在 sweep 的 worker 上跑，`LocalExternal` 的在 heap 的 thread 上。
- **和現在不同的地方**：DOM 的型別不再需要「traced region 必須 `Sync`、可變的放 `#[no_trace]`」，一般的 `Cell` 就能用、可變的 native 資料放在 `External` 裡的 `RefCell`；`Member` 不能放在 `RefCell<Vec<_>>` 裡，要多個參照用 `HeapVector`。

## 詳細設計

這裡寫做完時的設計（2026-10-26）；每一部分怎麼運作、API 和規則在 `crates/gc/README.md`，做的時候的取捨在「已決定的事項」，動工前的完整比較在 `details.md`。

### Heap 的佈局

- **cage**：一個 heap 預留 4 GiB、對齊 4 GiB 的虛擬位址，用到時一頁一頁 commit；`Member` 是相對於 cage 的 32 位元 offset（照 V8 的 pointer compression，shift 0）。
- **young generation**：nursery 是一串 young 的頁，物件不分大小一個接一個 bump；cage 裡每頁一個 byte 的表記哪些頁是 young。大小照 V8 的 `ResizeNewSpace`：活下來的多就加倍（最多 16 MiB），full GC 時活下來的少就減半。V8 的整頁升上去沒有做（`docs/limitations.md`）。
- **old generation**：256 KiB 一頁，每頁一種 size class（到 128 bytes 每 16 bytes 一級，之後約大 12.5%，到 32 KiB，52 級）。sweep 只讀 mark bit、找出空區段，配置在空區段裡 bump；區段用完時先拿同一頁的下一段，再拿那一級空格子最少的頁（mimalloc 的挑法），再拿 pool 的空頁、新頁。熱門的型別（Element、Text）要不要有自己的頁留給新的 DOM（已決定的事項 18 的第 3 條）。
- **large object**：大於 32 KiB 的物件獨佔一段連續的頁，只 commit 用到的，不搬動。
- **mark bit**：頁旁邊（heap 外）的 bitmap，和有 drop glue 的物件的 bitmap 一起放在 `Marks`；每輪 marking 開始時清掉。
- **pool**：sweep 找到的空頁和死掉的 large object 的頁進 pool，任何一級都能拿；過一整輪 GC 沒人拿的，由 worker 把記憶體還給作業系統（V8 等 8 到 16 秒，`docs/limitations.md`）。

### 物件模型

- header 8 bytes：型別在 process 的型別表裡的編號（cppgc 的 `GCInfoTable`），和 flags（nursery 裡活過一次、被搬走了、配置的地方 `Site` 的編號）。
- 每個型別在型別表裡登記一份 **layout 描述**：`Member`、`WeakMember`、`EphemeronPair` 的 offset，drop glue 和它在哪個 thread 跑；marker、scavenger、verifier 都照它，不呼叫型別的程式碼。
- 物件在 heap 上**就地初始化**：derive 產生的 init struct 寫進 `cx.alloc` 拿到的格子，`Member` 從頭到尾不會是 heap 外的值。
- **欄位型別的檢查**：`derive(GcObject)` 要求每個欄位實作「可以放在 heap 上」的 trait（`HeapField`），`Arc`、`Box`、`Vec`、參照沒有，物件自己也不能實作 `Drop`；native 的資料只會在 `External` 和 `LocalExternal` 裡。

### 配置和 barrier

- **配置**：nursery 的 bump；nursery 滿了而這次操作還沒完時，放 old（不在操作中途 GC）；大於一格的物件直接放 old。**pretenuring**：照配置的地方（`Site`，V8 的 `AllocationSite`）：一個 `Site` 的物件第一次 scavenge 就大多活下來時，之後直接放 old，full GC 發現它在 old 的物件大多死了時撤回；`cx.pretenured` 讓呼叫的人直接指定。
- **寫 `Member` 的 barrier**（inline）：
  - **generational**：old 的格子指向 young 的物件時，記進那一頁的 slot set（每 4 bytes 一個 bit，第一次記時才配置；strong、weak、ephemeron 各一種，V8 的 `OLD_TO_NEW`）。
  - **marking**（concurrent marking 進行中）：SATB，被覆寫的舊值是 old 的、還沒標過的，當場標上、推進 heap 的 thread 的本地清單；拿掉的 root 也一樣。
- **沒有 read barrier**：物件只在安全點的 scavenge 搬動，mutator 不會看到搬到一半的物件；weak 的讀取在 marking 期間標上讀到的物件。

### Young GC：scavenge

在安全點，交給 heap 的 platform 平行做：從 root 表和 slot set 記著的邊出發，把 from-space 裡活的物件 copy 出去，第一次活下來的留在 nursery，第二次的升到 old（V8 的 semi-space 加 age mark）；兩個 thread 搶同一個物件時用 CAS 在舊的 header 寫上去向，輸的用贏家的。死的物件不讀，只有 nursery 的 finalizer 清單上沒被搬走的跑它的 `Drop`（在這次停頓裡，`docs/limitations.md`）。weak 的邊、ephemeron、id 表指向 nursery 的，照搬動更新或清掉。

### Old GC：concurrent marking

- **開始**：old 的量到了 full GC 門檻的一半（platform 有背景的 worker 時），那個安全點先做一次把活的全部升到 old 的 scavenge（nursery 變空，快照只有 old，old 的 marker 不必走 young），root 當場標上，把 marker 交給 platform 的 posted job。
- **進行中**：mutator 照常跑。SATB barrier 保住快照時到得了的物件；新配置的、升上來的物件一律算標過（配置的區段整段標黑，V8 的 black area）。old 長到門檻時，照 V8 再多給一段 overshoot margin（門檻的一半或 32 MiB 取大的，最多 cage 剩下的一半）讓 worker 做完。
- **收尾的 pause**（安全點）：worker 做完或撞到 margin 時，取消 job、發布 mutator 的本地清單、所有的 thread 一起標完剩下的，處理 ephemeron（反覆到沒有新的標記）、清 weak 的邊和 weak root、id 表裡死的。目標 1 ms，量到的 p99 最多約 0.4 ms（ids 走一百萬格的 id 表，402 µs；其他 44 µs 以內，`progress.md`）。
- 沒有 platform 的 worker、或 `Heap::collect` 時，同樣的 marking 在停頓裡一次做完（stop-the-world）。

### Sweeping 和 finalizer

concurrent sweeping（cppgc 的 concurrent sweeper）：收尾的停頓把 size class 的頁照級別交給一個 posted job（最多一個 worker），它只讀 mark bit 算出每頁的空區段，heap 的 thread 在安全點和配置的慢路徑套用；某一級沒有掃好的頁時自己掃一頁。下一輪 marking 開始和 `Heap::collect` 前在停頓裡掃完。`used` 和下一輪的門檻在 sweep 做完時才定（sweep 找到的活的量；V8 和 cppgc 在 marking 結束時用 marker 數的量，已決定的事項 36 的第 4 條：marker 不數，標記才快得過 cppgc）。

finalizer 由型別決定（編譯時，物件本身的欄位只有 `External` 和 `LocalExternal` 可能有 `Drop`）：

1. **沒有**（預設、最多的一種）：sweep 不碰死掉的物件。
2. **`External<T>`（`T: Send`）**：old 的在 sweep 的 worker 上跑（V8 在 worker 上放 ArrayBuffer 的 backing store）；nursery 裡死的在 scavenge 的停頓裡，和 `LocalExternal` 同一頁的跟著在 heap 的 thread 上。
3. **`LocalExternal<T>`**：在 heap 的 thread 上、收尾之後的安全點跑；這種物件所在的頁整頁由 heap 的 thread 掃（`docs/limitations.md`）。

`Drop` 拿不到 `Mutation`，碰不到其他 GC 物件，所以 finalizer 不可能讀到死掉的物件或讓它復活；worker 上的 `Drop` panic 時，panic 在 heap 的 thread 下一次等 job 時往上拋，不會 finalize 兩次。

### Compaction

沒有：old 的物件不搬動。第 6 段量了碎片（已決定的事項 38、39）：sweep 剛做完時頁上的空格子不少，但之後的配置先填最滿的頁的空格子，到下一次 marking 開始時（V8 挑要搬空的頁的時候），照 V8 的挑法能放掉的頁在每個量過的工作上中位數都不到事先定的 10%（多數是 0，ids 1%，old 只有 11 頁的 gc-mini-tree 的錄製 6.2%）。量測（`HeapOptions::measure_fragmentation`）留著，wasm 文件換過來、跑真的頁面時再看（`docs/limitations.md`）。

### Root、weak、ephemeron 和 id 表

- `Persistent<T>`：root 表的一格（索引加上 free list），建一個 root 就是寫一格；`WeakPersistent<T>` 是 weak 的一格。
- `WeakMember<T>`：full GC 的收尾清掉指向死掉的 old 物件的，scavenge 清掉指向死掉的年輕物件的。
- `EphemeronPair<K, V>`：value 只在 key 活著時活著（cppgc 的同名型別）；會長大的 ephemeron 的 map 和 weak 的容器留到要用時（「之後的可能」）。
- **id 表是 GC 的一部分**：照 id 直接索引的分塊表，id 不重複，GC 搬動時更新、回收時清掉，不用每個節點一個 weak root。style、layout、paint 照舊用 id 指節點。

### Thread 和排程

- GC 經過 heap 的 `Platform`：預設是 process 共用的一組 worker（核心數減 1 個，照 V8 的 `PostJob`：有可以分的工作才叫醒 worker）；沒有 worker 的 platform 一切在停頓裡做。renderer 拆成 process 之後，每個 process 一組。
- 排程：nursery 的大小照存活率；full GC 的門檻是上次留下的 2 倍（最少 2 MiB），concurrent marking 在一半時開始；marking 做完就在下一個安全點收尾。門檻固定、不照速度動態調（`docs/limitations.md`）。
- 一次操作做很久時不 GC：記憶體會先長上去，marking 照樣在背景進行。

### 接 wasm 和 V8

（第 8、9 段，另寫；這裡是這份定下的介面。）

- **wasm 文件**：guest 的 handle 是 root 表的索引；Store 和 guest 的 callback 之間的循環照現在 holder 的做法，holder 是 heap 上的物件。
- **JS 文件**：每個 wrapper 背後一個很小的 cppgc 物件（stub），存著 root 表的索引和快取的位址；V8 做 major GC 時經過 stub 進到我們的 heap，DOM 指向 JS 的參照交回 V8 的 visitor，兩邊的循環在同一輪收掉。我們的 scavenge 把 stub 指的物件當成 root。規則：DOM 的操作裡不呼叫 V8，所以 V8 的 GC 只發生在我們的安全點。兩邊的 marking 怎麼對齊，第 1 段的原型兩種都做了（「之後的可能」；細節在 `details.md` 的「接 V8」）。

### Soundness

- `unsafe` 只在 `gc` 裡（`sanity.py unsafe` 的名單有它）；論證寫在 `crates/gc/soundness.md`（假設、不變式、找到的漏洞、人工審查清單）。
- 對外的保證：`Gc<'gc, T>` 活不出操作（invariant lifetime 和 brand）；`Member` 只存在 heap 上（就地初始化）；finalizer 碰不到 GC 物件；marker 只用 atomic 讀指標欄位，其餘的欄位它不讀；物件裡的 native 資料只在 `External` / `LocalExternal` 裡（derive 檢查）；`External` 的值是 `Send`，因為它的 `Drop` 在 worker 上跑。
- concurrent 的論證比 cppgc 的簡單：SATB 加 black allocation 加「只在安全點收尾」，沒有建構中的物件、不重掃 stack（`details.md` 的「記憶體模型」，`tla/` 的模型檢查它）。

### 測試

- **正確性**：每個安全點都 GC 的 stress；heap verifier（`HeapOptions::verify`：每次 GC 之後從 root 自己重走一遍，檢查標記、頁的帳、slot set、weak 和 ephemeron、id 表、SATB 的 floating garbage）；debug build 把釋放的記憶體填上毒值；對著參考模型的 fuzz（cargo-fuzz 加 ASan，錄製縮小當種子，找到的 regression 進 `cargo test`）。
- **協定的模型**：`tla/` 的 TLA+ 模型（1a 的 SATB 和 Dijkstra 兩份，加上照實作的 `SatbYoung`：涵蓋 marking 期間的 scavenge、weak、ephemeron、sweep 時的 slot set），用 TLC 檢查「收尾時活的物件都標過」；模型本身也做 mutation（拿掉一個 barrier 要找到反例）。
- **機械化的檢查**：Miri（Stacked Borrows、strict provenance，`cargo miri nextest run` 平行跑、全部一起，使用者每週定時跑一次，已決定的事項 40 的第 1 條）；loom 窮舉 worklist、scavenge 的 forwarding、marking 的發布順序；shuttle 隨機排程整個 GC（marking、sweep 和 mutator 同時跑）；Verus 證明頁的 bitmap 搜尋（Kani 試過、只證得到有界的範圍，不用）。
- **mutation test**：照 `docs/testing.md`，每一步都做，結果在 `progress.md`。
- **效能**：`bench.py gc` 在同一組 DOM 的工作、錄下的 DOM 工作的重播和配置模式上，和 cppgc、V8 比 GC 的時間、停頓、記憶體的峰值和 marking 的速度；目標是已決定的事項 16 的數字，每段在 Apple M4 上驗收（`progress.md`）。

## 缺點

- **工作量大**：粗估 GC 本身（第 0 到 6 段）6 到 9 個月，不確定性高；新的 DOM 和 `dom_api` 的改寫比 GC 本身還大（`dom` 約 3 萬行、`dom_api` 約 5.7 萬行）。
- **concurrent 和搬動的 bug 最難找**：漏標、漏更新就是 use-after-free，而且只在特定的 interleaving 出現；驗證的工具要自己做，cppgc 的 marking verifier 和 DCHECK 不能再用。
- **要長期維護一個 GC**：效能要自己調到和 cppgc、V8 相當，cppgc 被 V8 團隊調了很多年。
- **SATB 的 floating garbage**：一輪 marking 裡被拿掉的子樹多活一輪，記憶體的峰值高一些。
- **「只在安全點收尾」**：一次操作做很久時（一次 parse 很大的 HTML）收尾要等它做完，記憶體先長上去。
- **過渡期有兩套 GC**：新 DOM 和兩個 engine 換完之前，cppgc 照舊在；JS 文件接上 V8 要靠 stub，每個 wrapper 多一個 cppgc 物件。
- **wasm 每次 host 呼叫的固定成本不變**：那是 wasmtime 的（RFC 0067 量的 `nodeType` 約 2000 個指令），GC 碰不到。

## 理由和其他做法

完整的比較在 `details.md` 的「每個決定的完整比較」。

- **維持 cppgc、只減少呼叫的次數或試跨語言 LTO**（RFC 0085 的來源 1 的丙、甲）：成本最低，但 GC 的規則還是 cppgc 的，不能搬動、不能分代、finalizer 照舊，wasm 的路徑照舊依賴 V8。
- **照 Oilpan 做一個不搬動的 Rust GC**：比較簡單，但放棄了 DOM 最多的短命物件的好處；Oilpan 不搬動是因為保守掃描，我們沒有這個限制。
- **refcount（WebKit）、refcount 加 cycle collector（Gecko）**：樹的 parent 和 child 互指，refcount 收不掉樹，每次寫邊還要加減計數。
- **LXR（refcount 加 concurrent tracing）**：throughput 和延遲都好，但 DOM 的寫邊多、樹是循環，refcount 那一半的好處小，複雜度高。
- **保守掃描 stack**：2026-10-24 量過，只有它能省的 root 最多約 0.95%（`details.md` 的「動機的量測」），而且要放棄 safe 的保證。
- **gc-arena 原樣拿來用**：API 的模型（brand、只在 `mutate` 之間 GC）照它，但它的 heap 是每個物件一次 `Box`、單 thread、不搬動，不符合效能的目標。
- **不做**：DOM 的 GC 一直是 cppgc 的規則和 FFI 的成本，wasm 的路徑一直要連結 V8。

## 先例

- **V8 的 JS heap**：照它的架構（平行的 Scavenger、concurrent marking 和它的 overshoot margin、black allocation、pointer compression、allocation site 的 pretenuring）；它的 compaction 量過碎片之後不做，heap growing 用固定的倍數。不照它的 barrier：V8 是 Dijkstra 式的 insertion barrier 加 black allocation，這份是 SATB 加 black allocation（理由在 `details.md`）。
- **Oilpan（cppgc）**：名稱（`Member`、`Persistent`、`HeapVector`）和「DOM 的 GC 物件」的規則照它；不照它的保守掃描、不搬動、每個物件的 finalizer。
- **SpiderMonkey**：精確的 root 加上會搬動的 nursery、SATB 式的 pre-barrier；它用 `Rooted<T>` 和靜態的 hazard analysis，這份用 lifetime 和安全點。
- **JavaScriptCore 的 Riptide**：concurrent、不搬動、sticky mark bit 的分代。
- **Go**：concurrent、不搬動、hybrid barrier、不重掃 stack。
- **Java 的 G1**：SATB。
- **gc-arena**：brand 和 `mutate` 的 API 模型。
- **wasmtime**：49 版有自己的 copying collector（semi-space、更新 stack 上的 root），collector 的介面（`GcRuntime`、`GcHeap`、`GcCompiler`）是 crate 內部的，要接進來得 fork（`details.md` 的「接 wasmtime」）。
- **V8 的 sandbox**：heap 裡的 native 指標經過 external pointer table，是乙的做法；Blink 的 DOM（Oilpan）不在 sandbox 裡、直接放 native 指標，是丙的做法。`External<T>` 的名字照 V8 的 external pointer。

## 已決定的事項

2026-10-24（使用者確認的目標和範圍，和第 8 條的設計）：

1. **做 kun 自己的 GC，用 Rust 寫，要 concurrent**，效能要媲美 V8 的 GC。
2. **專門為 DOM 設計**：先設計 GC，DOM 照它的規則重新設計；目前專案裡的型別和限制不是前提。
3. **支援 JS 和 wasm 是第二順位**：JS 文件照舊用 V8 跑 JS、V8 的 GC 管 JS 的物件，只有 DOM 的物件放在這個 GC 上；和 GC 本身的設計衝突時以 GC 為準。不自己做 JS engine 和 JIT。
4. **對外必須是 safe 的**：GC 的實作可以用 `unsafe`，用它的程式碼不寫 `unsafe` 就不可能造成 UB；可以用任何工具（Miri、loom、Kani、形式化驗證）和 soundness 文件保證。
5. **效能照「測試」的三種比法量**：和 cppgc 在同樣的 DOM 工作上比、和 V8 的 GC 在同樣的配置模式上比、目標寫成具體的數字。
6. **這份只寫 GC 本身**，加上 DOM 用它的規則和接 wasm、V8 的介面；新的 DOM、`dom_wasm` 和 `dom_js` 換過來各自另寫，整條路的順序寫在這份的「分階段」。
7. **heap 裡的 native 資料：現在照丙，API 照乙**（`details.md` 的「照 wasmtime 的介面實作 collector」的甲、乙、丙）。DOM 和 wasm GC 的物件之後在同一個 heap；物件裡的 native 資料（`Arc`、`Box`、`Vec` 這類）一律包在 `External<T>` 裡、經過它的方法存取，`derive(GcObject)` 從第一天就檢查欄位的型別，直接放 native 的欄位編譯失敗。現在 `External<T>` 的值直接放在物件裡（丙，沒有額外的成本）；wasm GC 的物件要放進這個 heap 時，量過間接存取的成本再決定要不要換成 side table 的索引（乙），換的時候 DOM 的程式碼不用改。不選全照乙：乙要防的是 wasm 碼寫壞 host 的記憶體，wasm GC 的物件進來之前這個風險不存在，現在做只多一個要跟著 marking、分代、sweep 的表；不選丙而不包裝：之後要換成乙就得改每個 DOM 型別。**不綁定 wasmtime 現在的 GC 介面**：它還在變動，只要確保最終能以某種形式支援 wasm GC 就好。
8. **接受「設計概要」和「詳細設計」的設計**（2026-10-24，使用者確認）：分代（bump 配置的 nursery、平行 scavenge）、old generation 的 concurrent marking 和 concurrent sweeping、只在安全點收尾、root 表和 id 表存索引、layout 描述、32 位元的壓縮指標、預設沒有 finalizer、JS 文件經過 wrapper 背後的 cppgc stub 接 V8、整條路照「分階段」。「待決定」的各項在各自的段落開始前定，不影響這些。
9. **第 0 段（量測的基礎）**（2026-10-24，使用者照建議確認）。新的 GC 到第 8 段才跑得了真的 DOM，所以比較分兩層：GC 這一層從第 2 段起比，整個 DOM 在第 8 段之後比。
   1. **工作的形式：手寫的 microbenchmark 加上錄製重播**。microbenchmark 用 Rust 寫在像 DOM 的測試物件模型上（建樹、反覆建拆子樹、`innerHTML` 式的替換、長清單）；重播是在 `dom` 加記錄的掛點，錄下真的 DOM 工作（wasm 的 guest、`bench.py blink-perf` 的 DOM 頁）的配置、寫邊、root 的增刪和安全點，在兩個 heap 上重播，錄到的也回答第 1 段要量的存活率和 card 的數量（待決定 2）。真的 DOM 的工作（C 的 guest、blink-perf 的 DOM 頁）現在記一次基準，第 8 段再對照。不只用 microbenchmark：太人造；不只用真的 DOM：新的 GC 到第 8 段才跑得了。重播不是 Chromium 的做法（V8 和 Oilpan 主要看真實的 benchmark 和 Blink 的 perf_tests），是因為這份「GC 先做、DOM 後換」才需要。
   2. **基準是 kun 現在整套的 GC**：測試物件模型的 cppgc 版直接用 `dom` 現有的 safe API（`derive(GcObject)`、`Member`、`Handle`），包含要取代的 FFI 和 root 的成本，也不用寫新的 `unsafe`。不用 C++ 寫裸的 cppgc 的 benchmark：比較公平地比演算法，但要另外 build C++，也量不到要省的 FFI 成本。
   3. **cppgc 那一側的數字**：wasm 文件的 pause 是 kun 自己在 task 裡呼叫 `marking_step` / `collect_garbage` 的時間，在 kun 的 trace 加 span；JS 文件的 pause 從 V8 的 trace event（`disabled-by-default-v8.gc`）取；記憶體的峰值在 rusty_v8 的 fork 接出 cppgc 的 `CollectStatistics`（只改 Rust 和 `binding.cc`、要重編 V8，記在 `README.machopo.md`、同一次改動更新 `third_party.toml`），不只看 process 的 working set（量到的不只是 GC）；配置的成本用 samply 取樣。
   4. **和 V8 的 GC 比，用 kun 自己連結的 V8**：一個小的測試 binary 經過 `bindings` 跑 JS，用 `MACHOPO_V8_FLAGS=--trace-gc` 和 trace event 取 scavenge、marking 的時間；配置模式是樹、鏈結串列、隨機的圖，存活率高和低各一組；比 GC 的階段（每秒處理的物件數和 byte 數、pause 的長度），不比 mutator 的速度。不編 d8：要在 `rusty_v8_build` 另外編，版本也要跟著 kun 的 V8。
   5. **在哪台機器量**：平常在 Windows 的開發機上（samply 經過 ETW）；段落驗收時在 Apple Silicon 上再量一次（marking 期間的 release 寫入在 ARM 上比較貴，x86 上看不出來）；Linux 只在要 `perf stat` 的指令數時用。
   6. 照慣例的部分：工具是新的 `bench.py gc`（script 放在 `scripts/bench/` 底下的 `gc` 目錄，結果在 `target/bench/gc/`，記錄照 `docs/benchmarks.md`），做法和數字寫進 `progress.md`；目標的具體數字是第 0 段量完基準後的產出，再拿來確認。
10. **第 0 段的實作**（2026-10-24，使用者照建議確認）：
   1. **cppgc 版的測試物件模型在 `dom` 裡**：一個給量測用的公開模組，定義幾種測試用的 GC 型別（樹的節點、有 N 個邊的一般物件），經過現有的 `derive(GcObject)` 和 `Edge`，付的 FFI、barrier、root 的成本和 DOM 的物件一樣。`dom` 以外不能定義會改邊的 GC 型別（`Edge::set` 只在 `dom` 裡）。不直接用真的節點：混了 DOM 本身的成本，不能和新 GC 的測試物件模型一對一比；不另開 crate：碰不到 `Edge`，直接用 cppgc 又要 `unsafe`。
   2. **錄製的掛點是執行期的開關**：thread-local 的記錄器，環境變數打開；沒打開時每個掛點是一次 thread-local 的讀取和一個分支，錄的就是平常的 binary（照 `dom::testing` 一直開著的計數器）。不用 cargo feature：錄製時要另一個 target 目錄重編 `dom` 和下游。
   3. **錄製的格式**：binary 檔，每筆一個操作（配置：物件的編號、型別、大小、邊的數量；寫邊：來源、第幾格、目標或空；root 的建和放；安全點；GC）。物件用遞增的編號，不用位址（會搬動、會重用）。重播成「大小級距加上 N 個邊」的一般物件；cppgc 版在第 0 段，新 GC 版在第 2 段用同一份錄製。mutator 本身的計算不錄（第 9 條）。
11. **0c 的 microbenchmark**（2026-10-24，使用者照建議確認）：
   1. **在新的 crate `gc_bench`**：一個執行檔，依賴 `dom`，用 `perf` 的 profile 編；第 2 段起新的 GC 也接進同一個執行檔，同一份工作在兩個 heap 上跑。Chromium 的對應是 V8 的 `test/benchmarks/cpp/cppgc/`（`allocation_perf`、`trace_perf`、`binary-trees_perf`，單獨的 benchmark 執行檔）。不用 `dom` 的 example：`cargo test -p dom` 會一起編、多 link 一個帶 V8 的執行檔；不用 `shell` 的子指令：混進 shell 的啟動和其他 thread。0d 放不放在同一個 crate，0d 開始時再定。（2026-10-25 補，使用者確認）它也依賴 `bindings`：V8 的初始化、JS 文件的 heap、trace 都要；`sanity.py deps` 把它列進可以用 V8 的 crate（它不在 `kun` 裡）。不選把 V8 的部分搬進 `dom_js`、`gc_bench` 只依賴 `dom_js`：`dom_js` 多了量測用的 API，規則照樣要改一條；也不選整個放進 `dom_js`（像 `bench_calls`）：wasm 文件的 heap 的量測放在 JS 的前端，也推翻了自己一個 crate 的決定。
   2. **兩種 heap 都跑，報告並排**：wasm 文件的單獨 heap（cppgc 自己排 GC）和 JS 文件的 CppHeap（V8 推進 marking），兩者的排程和 pause 的形狀不同，第 8、9 段各要對照一次。
   3. **GC 照 cppgc 自己的規則觸發**：程式模擬 event loop，每輪做一批改動再執行 heap 排的 task；每個工作結束時在活著的物件上加一次強制的 full GC，量 marking 的吞吐量（對應 V8 的 `trace_perf`）。不只用強制的 GC：只有 atomic 的收集，量不到 incremental marking 和 barrier（0a 的 trace 裡 278 次 marking 步驟有 276 次在配置時）。
   4. **量什麼**：pause 和 GC 的時間從 trace 取（cppgc 的事件包含配置途中的 marking 步驟，程式自己計時量不到），`bench.py gc` 用 speedometer 的 trace reader 算 pause 的分布（中位數、p95、最大）和 main thread 花在 GC 的總時間；記憶體的峰值是每輪之後讀 `heap_statistics()` 的 committed 和 used 的最大值；加上每個工作的總時間和 GC 佔的比例。配置的成本用 samply 手動取樣，不放進 `bench.py`。結果在 `target/bench/gc/gc.md` 和 `gc.json`，跑 3 次取中位數。
   5. **物件模型和工作**：樹的節點（parent、first/last child、prev/next sibling 五個邊，加上大小接近 `Node` 的資料）和有 N 個邊的一般物件（`[Edge; N]`，幾種 N；0f 再擴充成大小級距）；root 用 `dom` 現有的，測試型別不加進 `ObjectTag`。四個工作，大小可調：build（建一棵 10 萬個節點的樹）、churn（1 萬個節點的樹，反覆拆一棵約 100 個節點的子樹再建新的，1000 輪）、replace（容器底下 1000 個節點整批換掉，500 次）、list（2000 個節點的窗口，每輪底下加 50、上面丟 50，1000 輪）。`gc_bench` 的整合測試用很小的大小每個跑一次。樹、鏈結串列、隨機的圖留給 0d。（2026-10-25 補，使用者確認）有 N 個邊的一般物件延到 0d：0c 的四個工作都只用樹的節點，要哪幾種 N 要看 0d 的工作和錄製的重播（0f）用到什麼，先做了用不到的型別只是多一份要維護的程式。
12. **0d 和 V8 的 GC 比的 microbenchmark**（2026-10-25，使用者照建議確認）：
   1. **在 `gc_bench` 裡加一種 heap `v8`**：同一個執行檔、同一個 `bench.py gc`，和 cppgc 的兩種 heap 並排；JS 經過 `bindings` 的 `ScriptState::evaluate_classic_script` 跑，不加新的 API。不另開 crate：V8 的例外要再開一次、trace 的讀法和報告要再寫一份；不放進 `dom_js` 的 `#[ignore]` 測試（像 `bench_calls`）：報告就分成兩份。Chromium 量 V8 的 GC 主要用 d8 上的 JS benchmark（例如 Octane 的 Splay），cppgc 的是單獨的執行檔；放在一起是為了同一份工作在三種 heap 上並排。
   2. **同樣的模式在三種 heap 上都跑**（V8 的 JS 物件、cppgc 的單獨 heap 和 isolate 的 CppHeap）：鏈結串列（N = 1，marking 是一條深而不能平行的鏈）、二元樹（N = 2，像 V8 的 `binary-trees_perf` 和 Benchmarks Game）、隨機的圖（N = 4，邊隨機指向同一群裡的物件）；每個物件 N 個邊加上 2 個字的資料（cppgc 是 `[Edge; N]` 加上資料，延到這裡的「有 N 個邊的一般物件」，見第 11 條的第 5 條；JS 是欄位固定的物件），header 不同，報告物件數和 byte 數都列。存活率三個模式一樣定：每批建完留下固定的比例，高 90%、低 5%（世代假說）。cppgc 也跑，第 2 段的新 GC 跑同樣的工作時才能三方對照；cppgc 沒有 young generation，低存活率在它上面都是 full GC，這也是要量的差別。不選只跑 V8：0c 的工作裡沒有這三種模式，就沒有 cppgc 在同樣模式上的數字。
   3. **V8 的數字照它自己的 GCTracer 的定義**：時間和停頓從 trace 取（`bench.py gc` 已經認得 `MinorGC`、`MajorGC` 和 `V8.GC_*`），背景 thread 上的 GC（平行的 scavenge、concurrent marking，cppgc 的 concurrent marking 也一樣）另外加總，算得出全部 thread 做了多少；byte 數從 `--trace-gc-nvp` 每次 GC 的一行取（`new_space_survived`、`promoted`），scavenge 的速度是存活的 bytes 除以 scavenge 的時間（GCTracer 的 `ScavengeSpeedInBytesPerMillisecond`），marking 照 0c：強制 GC 之後留下的 bytes 除以 marking 的時間。不從工作的結構推算存活了多少：自然觸發的 scavenge 在哪個時間點不固定，推出來的不準。
   4. **V8 的設定**：主要的數字用 kun 跑 JS 文件時的旗標（平行的 GC），每個工作另外跑一次 `--single-threaded-gc`：前者是 JS 文件實際拿到的，後者是每顆核心的演算法速度，第 2 段的新 GC 若先做單一 thread 就比後者。不固定 young generation 的大小：量到的就不是 V8 平常的行為；報告記下每次的 `new_space_capacity`，看得出它怎麼變。
13. **0e 錄製：`dom` 的記錄掛點和格式**（2026-10-25，使用者照建議確認）。Chromium 沒有錄下來換一個 heap 重播的工具：V8 的 `--trace-gc-object-stats`、DevTools 的 allocation sampling 和 Oilpan 的 `HeapStatistics` 都只統計；最接近的是 Java 的 Elephant Tracks（錄配置、寫指標和物件的死亡）。
   1. **配置經過 `dom` 自己的一個函式**：現在 33 個檔案的 85 處直接呼叫 `make_garbage_collected_on`，改成都呼叫它（`gc_stress` 也在裡面），掛點只有一處，第 8 段換成新的 GC 時換的也只是它。不在 rusty_v8 的 fork 裡掛：fork 要盡量小，這是 `dom` 的事；不讓 `derive(GcObject)` 產生建構函式：要改每個型別的建構方式。
   2. **寫邊的來源和第幾格由記錄器自己找**：記錄器留一張照位址排序的「位址 → 物件」的表，寫邊時找出包著那一格的物件，第幾格記成它在物件裡的 byte offset；新配置的物件清掉它範圍裡的舊項，位址被重用也不會找錯。只在錄製時有成本，`Edge` 的 API 不變。不讓 `Edge::set` 帶擁有它的物件：要改每個寫邊的地方，只為了錄製。
   3. **型別表**：每個型別第一次配置時寫一筆（編號、`type_name`、配置的大小、邊的數量），之後的配置只記編號。邊的數量由 `derive(Trace)` 和 `derive(GcObject)` 靜態算出（`Trace` 加一個常數，陣列是 N 倍），沒寫過的空格也算：marking 的成本和它有關；`dom` 裡手寫的 `Trace` 只有固定大小的容器。不從寫過的格子推：從來沒寫過的會漏掉。
   4. **root、weak 和 JS**：strong 的 root（`Root` 和直接用 `Persistent` 的幾處）記建和放，記在它指的物件上（做的時候改的：`Persistent` 會跟著 struct 搬動，位址當不了 root 的編號；重播只要知道每個物件現在有幾個 root）；weak 的（`WeakEdge`、`WeakPersistent`）照樣記、標成 weak（新的 GC 有 weak 的 id 表）；DOM 指向 JS 的參照（`JsEdge`）記成指向「外部」的寫邊。JS 拿著的 DOM 物件：錄製時記錄器為每個建過 wrapper 的物件留一個 weak handle，每次 GC 之後檢查哪些清掉了，記一筆「JS 放掉了它」，重播時照這個時間點當成 root 放掉；用現有的 API，不改 fork。不為每個物件都留 weak handle 記下所有的死亡：錄製時記憶體多很多，wasm 文件靠重播就算得出來；不把 wrapper 當成永遠不放的 root：JS 文件的存活率會被高估。
   5. **安全點和 GC**：`DomIsolate` 的每個 `DomMutationScope` 和 `DomReadScope` 結束時記一筆安全點：那時沒有沒 root 的指標，和新 GC 的安全點（wasm 的 host 呼叫之間、JS 進 V8 之前）一致。不只在 task 之間記：一個 task 裡有很多操作，新的 GC 要能在操作之間收尾。GC 記開始和結束和種類（incremental 的一步、完整的、強制的）：standalone 的 heap 在 kun 呼叫 GC 的地方記（做的時候發現不夠，改成第 9 條的 GC 計數），isolate 的 heap 用 V8 模組現有的 GC callback 記；這是重播時對照用的，重播時的 GC 照重播的 heap 自己決定。
   6. **檔案和工具**：環境變數 `MACHOPO_GC_RECORD=<目錄>`，一個 `DomIsolate` 一個檔（process id 加 isolate 的序號），寫在 buffer 裡、`DomIsolate` 結束時 flush；整數用 LEB128 varint，檔頭有 magic、格式的版本和 heap 的種類。寫檔和讀檔在 `dom` 的一個模組裡，格式只定義在一處，0f 的重播也用它。0e 做一個小的 `gc_bench inspect <檔>`，印各型別的物件數和 bytes、寫邊、root、安全點和 GC 的數量，測試用它檢查一次真的工作錄下的內容；存活率和 card 的數量（待決定 2）要重播，在 0f。不用 Python 讀：格式會有兩份。
   7. **沒打開時的成本**：每個掛點一次 thread-local 的讀取和一個分支（第 10 條的第 2 條）；測試確認沒打開時記錄器沒有建、沒寫任何東西；0e 做完用 `bench.py gc` 比一次改動前後的執行時間，寫進 `progress.md`。
   8. **記錄器是 `DomIsolate` 的，不是 thread-local**（2026-10-25 補，使用者確認，改了第 10 條的第 2 條）：每個掛點本來就拿得到 isolate 自己的東西（寫邊和配置有 scope，root 有 `RootCounter`），經過它們拿到記錄器；一個 thread 上同時有幾個 `DomIsolate` 時（測試、JS 和 wasm 文件換 DOM 時新舊的短暫並存）分得出是哪一個的，一個 isolate 一個檔；沒打開時是一次欄位的讀取和一個分支，比 thread-local 便宜。不照原樣用 thread-local：同時有兩個 isolate 時掛點分不出寫邊是哪一個的，還是要比對 isolate 的東西。
   9. **standalone 的 heap 的 GC 用 fork 的 GC 計數來記**（2026-10-25 補，使用者確認，改了第 5 條）：做的時候發現 standalone 的 heap 的 GC 大多在 cppgc 自己 post 的 task 裡整個做完（atomic），kun 呼叫 GC 的地方和 marking 的狀態都看不到，照第 5 條的做法會漏掉 wasm 文件大部分的 GC。rusty_v8 的 fork 加 `StandaloneHeap::gc_count`：heap 的 platform 帶一個 cppgc 內部 `StatsCollector` 的 observer，每次 marking 完成時加一（atomic 和 incremental 的都只有一次，不管是誰開始的）；kun 在每個 heap 的 task（cppgc 的和自己的 marking step）前後比對，變了就在那個 task 之後記一筆 `Major`。原本建議接 cppgc 公開的 `HeapState::IsSweeping`、從 sweeping 開始推出 GC，做的時候改成計數：上一次的 sweeping 還沒做完時開始的 GC 從狀態分不出來。不從 used bytes 推測：全部存活的 GC 會漏掉，也依賴 cppgc 怎麼算 used；不記每個 cppgc 的 task：sweeping 的 task 也算進去，數不出 GC。這個分支一直用 `RUSTY_V8_ARCHIVE` 連結本機編的 V8（使用者確認），fork 的改動不等 release。
14. **0f 重播：在 cppgc 上重播錄下的工作**（2026-10-25，使用者照建議確認）。Chromium 沒有對應的工具（第 13 條）。
   1. **`gc_bench replay FILE --heap standalone|isolate`**：時間、記憶體和強制的 GC 照 0c 的工作量，`bench.py gc --replay FILE...` 把它們和其他工作並排；重播用的物件在 `dom` 的 `bench`（`Edge::set` 只在 `dom` 裡）。不另開 crate：V8 的例外和報告要再做一份。（2026-10-25 做的時候補）錄製裡的 GC（包括工作自己的強制 GC）只計數、不重做：重播的 heap 照自己的時機收，強制的 GC 只在重播的最後做一次，和 0c 的工作一樣；照錄製的時間點強制 GC，量到的就是錄製的 heap 的排程，不是重播的。
   2. **重播的物件是一個 const generic 的型別**：N 個邊加上資料，邊數往上取到 {0, 1, 2, 4, 8, 16, 32, 64}，大小往上取到固定的級距（小的每 32 byte 一級，大的照比例），只編固定的組合；超過最大的取最大的、計數。測試比對重播和原本的 heap 的 used，誤差寫明。不照錄下的大小配置：fork 要接出 cppgc 的 `AdditionalBytes`，不固定的邊數的 `Trace` 要寫 `unsafe`，只為了少一點取整的誤差。
   3. **重播自己拿著每個物件，從配置到它在錄製裡最後一次出現**（先掃一遍算出來）：它在原本的工作裡至少活到那時候，這個 root 不會讓它活得比原本久，放掉之後照圖決定；代價是 root 多了「還會被用到的物件」的窗口，報告寫出窗口的最大值和平均。不用不追蹤的指標表：安全要靠錄製和重播的圖一模一樣，檔案壞了就是 use-after-free；不為每個物件留 weak handle：每次 GC 都要處理全部的 weak，扭曲更大。
   4. **格式的第 2 版加一筆「一輪的開始」**（`DomIsolate::run_platform_tasks` 的開頭），重播照它跑 heap 的 task（standalone 的 platform 的 task 和 marking step，isolate 的 V8 的 task），和 0c 的工作一樣；讀到第 1 版的檔停下、說明原因。不每 K 個安全點跑一次：K 是猜的，GC 的排程的形狀和原本不同。
   5. **weak、JS 和不明的**：weak 的寫邊和 root 不重播，只計數（不影響誰活著）；指向 JS 的寫邊不重播；wrapper 照第 13 條的第 4 條當成 root，到「JS 放掉了它」時放掉；指向不明的物件的寫邊照清掉處理；跳過的都在報告裡計數。不重播 weak：物件要分強弱兩種邊，型別的組合加倍，只為了量 weak 的處理。
   6. **存活率和 card 的數量（待決定 2）用 `gc_bench analyze FILE` 在錄製的圖上模擬分代**，不經過 cppgc：nursery 試 1、4、16 MiB，滿了在下一個安全點做一次 minor GC，活過兩次的升到 old（第 8 條）；每次 minor GC 報告存活率（存活加升級的 bytes 除以 nursery 的 bytes，照 V8 的 GCTracer 的 survival rate）、升級的 bytes、old 指向 young 的欄位數（對應 V8 的 OLD_TO_NEW remembered set）和它們所在的 old 物件數。card 的大小第 3 段才定，現在不報告 card 數。（2026-10-25 做的時候補）只做 minor GC 的話，死掉的 old 物件的邊會一直撐住它指著的 young 物件，存活率越跑越高，所以也模擬 full GC：old 的一代長到上次 full GC 留下的兩倍（至少四個 nursery）時，在那個安全點放掉沒人指著的 old 物件；這個門檻是猜的，報告寫出每次 full GC 留下的 bytes。不打開 cppgc 的 young generation：要另一組 gn 參數重編 V8，它是 sticky mark bit 而不是 semi-space，數字對不上這份的設計。
   7. **測試**：錄一次 `gc_bench` 自己的工作，在同一種 heap 上重播，比對配置的物件數、最後的 used 和 root 的平衡；`analyze` 用答案算得出來的小錄製（例如一條鏈每次留一半）；照常跑 mutation test。真的 DOM 的工作（C 的 guest、blink-perf 的 DOM 頁）在 0g 才錄。
15. **0g 基準：真的 DOM 的工作**（2026-10-25，使用者照建議確認）。
   1. **工作**：Blink 的 perf_tests 裡配置很多節點的頁：`bindings/` 的 `gc-tree`、`gc-forest`、`gc-mini-tree`、`create-element`、`insert-before`，`dom/` 的 `deep-tree-clonenode`、`long-sibling-list`，`parser/innerHTML-setter`；每頁另外用 C 寫一個做同樣操作的 guest，當 wasm 文件跑，JS 文件和 wasm 文件在同一份工作上比（「分階段」的第 0 段）。`long-sibling-list` 斷言要有 `GCController`，跑不了就拿掉。不只用現在有效的頁：清單上會配置很多節點的只有兩頁，量不到 GC；不用整個 `dom/`、`bindings/`：要改寫的 guest 太多，很多頁和 GC 無關。（2026-10-25 做的時候補）做的是六頁：`long-sibling-list` 斷言要有 `GCController`，拿掉；`deep-tree-clonenode` 的 JS 頁讓 kun 的 stack 溢位（已知的限制：很深的樹讓 renderer 的 stack 溢位），拿掉，等那個限制修掉再加。
   2. **`PerfTestRunner.gc()` 照現在**：沒有 `GCController` 時它只配置一些 JS 的垃圾，kun 和 Chrome 一樣，GC 照各自的時機，這就是要量的；guest 那一側什麼都不做。不加 `--expose-gc` 的 `gc()` 和 guest 用的 GC 函式：每輪之前強制收一次，量到的就不是 GC 自己的排程，還要多一個非標準的 API。
   3. **在 `bench.py blink-perf` 加 `--gc`**：用 `MACHOPO_TRACE` 跑 kun，照 `bench.py gc` 的讀法從 trace 取量測期間 main thread 上的 GC 時間和停頓，背景 thread 另外加總；wasm 文件的頁也由它開，guest 自己量時間、用 `fetch` 把結果 POST 回去，和 `hook.js` 一樣。Chromium 也這樣做（Telemetry 的 blink_perf 從 trace 讀 `BlinkGC.*` 和 `V8.GC_*`）。不另寫一個 runner：開頁、檢查有效、比對 document 的摘要都要再寫一份。（2026-10-25 做的時候補）runner 的 `console.time("blink_perf")` 由 `hook.js` 寫成 User Timing：第一個算數的那輪的 mark 和結束時的 measure，GC 在 measure 的區間、mark 所在的 thread 上讀（Telemetry 也找這個 timer）；guest 自己寫一樣的 mark 和 measure。guest 每輪之間等 1 ms 回到 event loop：期限已經過了的等待（`usleep(0)`）不讓出，而 wasm 文件的 GC 只在 loop 的頂端收尾，整個量測在一個 task 裡時，create-element 約 8 秒用完 cppgc 的保留區。這是新 GC 要解決的事之一（task 裡也要收得掉），寫進 `docs/limitations.md`。
   4. **記憶體和存活率從錄製來**：每頁用 `MACHOPO_GC_RECORD` 錄一份（`target/bench/gc/recordings/`），`gc_bench replay` 在兩種 heap 上重播（記憶體看重播的 peak），`gc_bench analyze` 回答待決定 2。不讓 kun 自己輸出 heap 的大小：要在 renderer 加 trace 的 counter，重播已經量得到。
   5. **機器**：Windows 上量；Apple Silicon（第 9 條的第 5 條）寫好指令，第 0 段驗收時由使用者在 Mac 上跑。
   6. **產出**：數字寫進 `progress.md`、量法寫進 `docs/benchmarks.md`，照第 9 條的第 6 條提出新 GC 的目標數字（停頓、吞吐量、記憶體）給使用者確認；之後跑 `cargo test --workspace`、fmt 和 clippy，第 0 段才做完。
16. **新 GC 的目標數字**（2026-10-25，使用者照建議確認）。基準是第 0 段的數字（`progress.md` 的 0d、0g）；GC 這一層從第 2 段起在同樣的 microbenchmark 和錄製的重播上比，整個 DOM 在第 8 段之後在 0g 的六頁上比。
   1. **停頓**：minor GC 的 p99 在 1 ms 以內；整批都活著的工作（gc-tree 這一類，存活率 100%）在 5 ms 以內。收尾的 pause 照「Old GC」的 1 ms（2026-10-26 補：不含 sweep 的標記收尾在第 4 段驗收，含 sweep 的整個 pause 在第 5 段，已決定的事項 29 的第 7 條）。現在單獨的 cppgc 在重播上最長 24 到 88 ms，JS 文件的 gc-tree 是 543 ms（V8 的 atomic pause）。
   2. **main thread 的 GC 時間**：存活率低的 wasm 錄製（create-element、gc-forest、gc-mini-tree、innerHTML-setter）重播時，不超過單獨的 cppgc 的 1/3；gc-tree 不超過 cppgc。0g 量到 DOM 的垃圾幾乎都在第一次 minor GC 前死掉（0% 到 3%），分代應該省下大部分的 marking 和 sweeping；gc-tree 沒有可以省的，只要求不變慢。
   3. **記憶體**：同一份重播的 peak used 不超過單獨的 cppgc 的（219 到 336 MiB）。
   4. **和 V8 的 GC 比**：0d 的配置模式裡存活率低的那組，GC 時間在 V8 的 1.5 倍以內（V8 是 2.2 到 3.8 ms，單獨的 cppgc 是 27 到 45 ms）；存活率高的那組不超過 isolate 的 heap 上的 cppgc。
   5. **marking 的速度**：每秒處理的 byte 不低於單獨的 cppgc 在重播上的（463 到 589 MB/s）。
   6. 數字在 Windows 的開發機上比，段落驗收時在 Apple Silicon 上用同一套量法再比一次（第 9 條的第 5 條）。不用和 Chrome 的頁面成績比：差的大部分是 kun 的 binding 和 layout，不是 GC；不把目標定成「和 V8 一樣」：DOM 的物件經過 handle 和 root 表，0d 的 V8 是 JS 物件，沒有這些成本。

   1. **範圍**：拿掉「scavenge 在 DOM 型的工作上的存活率」：0g 的 `gc_bench analyze` 已經回答了待決定 2（Windows 和 Apple Silicon 都量了）。改成**在錄製上算兩種 barrier 的次數**（details.md 的「Barrier」要第 1 段比的）：擴充 `gc_bench analyze`，在 0g 的錄製上模擬一輪 marking，數 SATB 和 Dijkstra 各會觸發幾次 barrier，Dijkstra 收尾要重掃的 root 用錄到的 root 數估計。不在 API 的原型裡兩種都實作再跑 microbenchmark：工作是人造的、成本高很多；不只靠模型和論證：待決定 1 就少了成本的數字。V8 和 cppgc 用 Dijkstra，barrier 的成本靠 benchmark 量、沒有形式化的模型；這份不照 V8 的 barrier，所以模型和錄製上的次數都要拿得出來。
   2. **分段**：1a TLA+ 模型（SATB 和 Dijkstra 各一份，待決定 1 的協定）、1b 錄製上的 barrier 次數（待決定 1 的成本）、1c safe 的 API 原型在 Miri 下（待決定 5、10）、1d 接 V8 的 stub 原型（待決定 6）。1a、1b 互相獨立，先做；1d 用 1c 的原型的 heap 和 root 表，放最後；它可能要改 fork 的 C++（`CppHeap` 收尾前再問 embedder 一次的掛點），怎麼改在 1d 開始前定。每段開始前再列那一段的決定。

   5. **1b 的模擬**（2026-10-25，使用者照建議確認）：
      - **marker 照配置的量前進**：mutator 每配置 1 byte，marker 掃 k byte（k 是 1 和 4），從開始時的 root 表一格一格出發、照錄製的圖寬度優先走；另外報 k = 0（收尾前 marker 什麼都沒做）當上限。V8 的 incremental marking 的排程有一部分也照配置的量（allocation observer 每配置一段做一步）。不只報上限：兩種 barrier 都只對還沒標的走 slow path，只看上限兩邊都高估、看不出差距怎麼隨進度變；不用時間：錄製沒有時間戳記。
      - **區間**：照 analyze 的 full GC 的時機（old 長到上次的兩倍）開始，開始前先做一次 scavenge（活的全部升上 old，nursery 清空，照設計）；marker 照 k 走完之後的下一個安全點收尾，k = 0 用 k = 1 的同一段區間。三種 nursery 照舊各算一次。
      - **Dijkstra 照 V8**：barrier 檢查所有寫入（寫進 young 的物件也是），old 的 marking 也走 young，收尾重掃整個 root 表（JS 文件每個 wrapper 一格）。這樣比的是這份的設計和 V8 的做法；不選「Dijkstra 加上 young 的過濾」：沒有現成的 GC 這樣做，還要另外證明它對。
      - **報什麼**：每輪 marking 期間的寫入（兩邊的 fast path 都要檢查 flag）、slow path 的次數（SATB 記下的舊值，欄位和 root 的刪除分開；Dijkstra 標的新值）、收尾的工作（SATB 是剩下的 buffer 和 worklist；Dijkstra 是重掃的 root 數加上那之後要標的）、floating garbage（收尾時標了、已經到不了的 bytes）。印在 analyze 每個 nursery 的那一段後面。
      - **算不到的**：weak 的讀取沒有錄（id 表的讀取不經過錄製的掛點），SATB 的 weak 讀取 barrier 次數算不到，寫在報告的說明裡；要補得在 `dom` 的錄製加一種 record，不在 1b 做。
   6. **1c 的原型**（2026-10-25，使用者確認；第 2 條照建議，就地初始化改成甲）：
      - **heap**：只在安全點收的 semi-space copying collector：`std::alloc` 配置的一小塊 cage、32 位元的 `Member`、bump 配置、照 layout 描述搬物件、更新 root 表；不做 concurrent 和分代。不只配置不回收：「操作之間 GC 搬動物件、safe 的程式碼留不住舊的指標」只有真的會搬的 heap 在 Miri 下驗證得到；不照第 2 段的設計做：那是第 2 段本身。
      - **就地初始化（待決定 5）是甲**：derive 為每個型別產生一個 init struct（`Member<T>` 的欄位在那裡是 `Option<Gc<'gc, T>>`，其他欄位照舊），`cx.alloc(ElementInit { ... })` 在 heap 上的位置把它寫成物件。每條邊只寫一次，配置在 young 時沒有 barrier；配置在 old 時（pretenure）整個物件判斷一次、對指向 young 的邊記 card。`Member` 從頭到尾不在 heap 外：init struct 裡的是這次操作的 `Gc`。不選乙（`Member` 在 heap 外只能是 null、配置後 `set`）：每條非 null 的邊多一次寫入和一次白做的 barrier 檢查，`HeapVector` 長大、clone 子樹、parser 一次建一串節點時量大；不選 pin-init 式的 macro：要自己的語法，錯誤訊息差，init struct 是一般的 struct literal。V8 的 TurboFan 對剛配置在 young 的物件的初始化寫入拿掉 barrier、cppgc 在 heap 上直接跑建構子，都是同一個方向。之後要改的邊用 `set(cx, …)`，照常經過 barrier。
      - **其餘的 API**：`member.get(cx)` 回 `Option<Gc<'gc, T>>`；`HeapVector` 本身是 GC 物件（長度和一段 `Member` 的陣列，寫入經過 barrier，長大時配置新的、複製過去；原型只做 push、get、set、len、remove）；`External<T>` 只借出 `&T`，lifetime 綁在物件的借用上，可變的放 `T` 裡的 `Cell` / `RefCell`（換成 side table 時，side table 在一次操作裡不能搬動它的格子，否則借出的 `&T` 懸空）；純資料是一個 trait，給整數、`bool`、`char`、它們的陣列和 `Option`、`Cell` / `RefCell` 包著的純資料，參照、raw pointer、`Box`、`Arc`、`Vec` 都不給；`Persistent` 每次存取在執行期檢查 heap 的 id，對不上就 panic（一直開著才 sound；cppgc 只在 debug 檢查）；derive 是 proc macro（原型是 `gc` 和 `gc_derive` 兩個 crate），產生 layout 描述、檢查欄位、用 pin-project 的做法擋住物件型別自己實作 `Drop`；finalizer 只做 main thread 上同步的 `Drop`（在 sweeper 上跑和 `Send` 的分類在第 5 段）。
      - **Miri**：原型的 `rust-toolchain.toml` 釘 `nightly-2026-10-01`（加 `miri`、`rust-src`），`cargo miri test` 在 Stacked Borrows 和 Tree Borrows 下各跑一次；沒有 thread，loom 和 data race 留到第 4 段。
      - **測試**：一個小的、像 DOM 的物件模型（`Node` 的 parent、first child、next sibling，`Element` 的 attributes 和一個 `External<Arc<…>>`）上建樹、拆樹、搬子樹，每個安全點都 GC 的 stress，debug 時把舊的一半填上毒值；compile-fail（照 `dom` 用 trybuild）擋住 `Gc` 帶出操作、heap 外的 `Member`、物件型別自己實作 `Drop`、欄位直接放 `Box` / `Vec` / 參照、`External` 裡放 `Member`、`Drop` 碰到 GC 物件；照常跑 mutation test。
   7. **1d 的原型：兩種對齊的做法都做**（2026-10-25，使用者確認）。待決定 6 的甲（同步：stub 的 `Trace` 延到 main thread、當場走我們的 heap）和乙（交換：我們的 marker 和 V8 的各自推進，V8 收尾前問我們做完了沒）都實作、都量，再決定要不要 fork V8。原本的建議是只做甲、乙只寫分析：乙要的掛點 V8 沒有（以前的 `EmbedderHeapTracer` 有，已經拿掉），要改 V8 本身，而 kun 的 fork 只改 rusty_v8 的 glue、`v8` 是 denoland 的 submodule；使用者要先兩種都做做看，看實際的停頓和 patch 的大小再決定。
      - **改動不進 fork**：V8 本身和 rusty_v8 的 glue 的改動都是原型資料夾裡的 patch，由腳本套用到本機的 checkout、編完還原；fork 不多 commit，`third_party.toml` 的 pin 不動。`ci.py third-party` 只在 commit 和 pin 不同時切換 checkout、檢查改動時不看 submodule，所以不會蓋掉套用中的 patch。

18. **第 2 段：heap 的核心**（2026-10-25，使用者照建議確認）。
   1. **crate**：`crates/gc` 是 GC 本身、`crates/gc_macros` 是 derive 的 proc macro（照 `dom_macros`）；`gc` 不碰 V8、`dom`，只依賴保留和 commit 位址空間的 rustix（macOS、Linux）和 windows-sys（2026-10-25 實作時：原本寫只依賴 `base`，但用不到它）。它是可以寫 `unsafe` 的第四個 crate：`sanity.py unsafe` 的名單加上它，論證在 `crates/gc/soundness.md`。不叫 `heap`：`gc` 直接，和 `gc_bench` 一致（待決定 8）。
   2. **cage**：4 GiB、shift 0（V8 的預設，解壓縮是一個加法），對齊到 4 GiB：從 heap 裡任何位址算得出基底，1c 原型的 `Member` 每次 get、set 的範圍檢查變成一次 AND 和比較。每個 heap 一個 cage。保留虛擬位址用 workspace 已有的 `rustix`（`mm`）和 `windows-sys`（`Win32_System_Memory`）；Windows 上多保留一段再取對齊的部分（V8 也是）。不選 shift 3（32 GiB）：每次解壓縮多一個 shift，重播時 DOM 的 heap 最多 366 MiB（0g、第 0 段驗收；JS 的 gc-tree 的 2.3 GB 是 V8 還沒宣告死的 wrapper 撐著的，活的是 336 MiB）（待決定 3）。
   3. **page 和 size class**：page 256 KiB（V8；cppgc 是 128 KiB）；size class 照 mimalloc 的分法，128 byte 以內每 16 byte 一級、之後每級約 12.5%、到 4 KiB；超過半頁的放 large object page（2b 改成 size class 到 32 KiB、以上是 large object，已決定的事項 19 的第 1 條）；mark bitmap 在 page 旁邊；第 2 段的 sweep 在 stop-the-world 的 pause 裡做完（concurrent 是第 5 段）。不照 V8、cppgc 的「混合大小的 page 加 free list」：設計已經定了照大小分的 page（決定 8）。熱門型別要不要自己的 page 留到第 7 段量：0g 的錄製裡今天的 DOM 幾乎全是一種 `Node`（336 byte、15 條邊，99.99% 的物件），新的 DOM 會拆成很多型別，現在的分布算不出 size class（待決定 4）。
   4. **從 1c 的原型帶過來**：API 和 derive 照搬（`Gc`、`Member`、init struct 和 `ObjectInit`、`External`、`HeapData`、`HeapVector`、`Persistent`、`heap.mutate`），加上原型學到的：`Member` 的檢查用 cage 的對齊、欄位型別的錯誤訊息、`HeapData` 讓 DOM 自己的純資料型別實作。`JsEdge` 和 wrapper 的那一格等第 9 段、weak 等第 4 段。
   5. **平行 marking**（stop-the-world，在安全點）：GC 自己的 thread pool（決定 8），最多「核心數減 1」個 worker（V8 的做法）；worklist 照 V8、cppgc 的分段 worklist（每個 worker 一段本地的，例如 64 項，滿了發布到全域、閒著的拿走整段）；side bitmap 的 mark bit 用 `fetch_or`。不用 rayon：排程對 shuttle、loom 是黑盒子，還和 layout 搶 thread；不用 `crossbeam-deque`：多一個依賴，內部放不了 shuttle 的切換點。
   6. **驗證的工具**（`details.md` 的「驗證的工具」的「怎麼接成流程」）：Miri（`cfg(miri)` 時 page 用 `std::alloc`；2026-10-25 使用者決定平常只跑預設的 Stacked Borrows：2b 時兩種各跑一次要 11.5 和 17 分鐘以上，Stacked Borrows 在大部分情況比較嚴，它報了像是誤報的錯時才用 Tree Borrows 確認；同一天也決定什麼時候跑：子段改了 `unsafe` 區塊、`crates/gc/soundness.md` 的不變式或它們依賴的程式（heap、page、cage、member、vector、platform、worklist）時跑，只改測試、文件、verifier、fuzz、Verus 的部分或純演算法的子段不跑，每個階段做完時和 `cargo test --workspace` 一起跑一次整套；一次 12 到 15 分鐘。2026-10-26 改成只在每個階段做完時跑一次整套，子段不跑：整合測試都開著 heap verifier 之後一次要半小時以上；同一天再改成先不跑，等整份 RFC 收尾時再決定怎麼用（例如 `cargo miri nextest run` 平行跑、哪些測試在 Miri 底下跳過或縮小））、heap verifier、stress、毒值、compile-fail；fuzz 照 bbtree 的做法、用 0g 的錄製縮小當種子，cargo-fuzz 要 nightly，放在自己的資料夾、釘自己的 toolchain；第 2 段就有平行的 worker，shuttle 和 loom 就用上。**shuttle 和 loom 兩個都留**：loom 照 C11 記憶體模型窮舉、抓得到重排但只跑得了很小的測試，shuttle 一次跑一個 thread、抓不到重排但跑得了大的情境；GC 的 atomic 都經過一個小模組、用 `cfg(loom)` 和 `cfg(shuttle)` 切換，切換點插一次兩個都能跑。**Verus 和 Kani 試過選一個**：用途重疊（算術和資料結構的性質），兩個都維護等於寫兩套證明、兩套 CI；2d 拿同一個模組（壓縮指標、bitmap 的索引）各做一次，選一個長期用（預期第 2 段的算術 Kani 就夠，Verus 的優勢在迴圈和協定的不變式，待決定 9）。
   7. **分段**：2a crate、API、derive，單 thread 的 mark-sweep 跑在 cage 上，Miri；2b page、size class、large object、sweep 之後的空區段；2c 平行 marking（worklist、worker），shuttle 和 loom；2d heap verifier、fuzz、Verus 和 Kani 的試用；2e `gc_bench` 加上新 heap 的 backend，在 0c、0d 的 microbenchmark 和 0g 的錄製重播上和 cppgc 比。驗收照決定 16：marking 的速度不低於 cppgc（重播的強制 GC：Windows 463 到 589 MB/s、Apple M4 771 到 918 MB/s），peak used 不超過 cppgc；停頓的目標要等分代和 concurrent（第 3、4 段）。

19. **2b：page、large object、空區段**（2026-10-25，使用者逐條確認）。
   1. **size class 到 32 KiB，以上是 large object**：2a 的 size class 做到半頁（128 KiB），一頁 256 KiB 除不盡大的格子，頁尾最多浪費 25.7%；到 32 KiB 時最多 8.6%（52 級）。大於 32 KiB 的物件獨佔一段連續的頁，只 commit 用到的部分（以作業系統的頁為單位），死掉時整段回到 pool。不選大小混放（V8、cppgc 的做法）：同一頁大小不一時，sweep 要讀每個物件的 header 才找得到下一個，死的也要讀，free list 還要寫進死掉的記憶體；它們混放是因為指標可能指到物件中間（cppgc 要保守地掃 stack），本來就要有找物件開頭的機制，我們的邊一定指到開頭、不掃 stack。JavaScriptCore 的 `MarkedBlock`、SpiderMonkey 的 arena 也是照大小分的。不選中等大小（32 到 128 KiB）另外混放（丁）或用好幾頁的 span（乙，mimalloc 的 medium page、Go 的 span）：中等物件很少（0g 的錄製裡 99.99% 是 336 byte 的 `Node`），為它們多一套配置器、sweeper 和驗證不划算；第 7 段有了新 DOM 的型別分布、32 到 128 KiB 的多時再加，介面不變。代價是剛超過 32 KiB 的物件在 Mac（16 KiB 的頁）上 commit 最多浪費約 33%，每個 large object 至少用掉 256 KiB 的位址空間。
   2. **sweep 之後在空區段裡 bump**：bitmap 本身記著哪些格子有物件（GC 之外，配置寫完物件時設上它的 bit；2026-10-25 實作時改成只有 debug build 設：配置看空區段、不看它，release 的 fast path 省掉一次查頁，`progress.md` 的 2b），另一張 bitmap 只標有 finalizer 的物件；sweep 只讀 bitmap，一次看 64 格，找出連續的空格子記成區段（存在 heap 外），配置時在區段裡 bump（加法和比較，和之後 nursery 的 bump 同一段程式）。沒有 finalizer 的死物件 sweep 不碰（debug build 照舊填毒值）。V8、cppgc 也是 sweeper 找出空的區塊、配置時在一段裡 bump（LAB），但把 free list 寫進死掉的記憶體；同一頁的格子一樣大，區段可以記在外面。不選每格一個 free list（mimalloc）：sweep 要寫每個死格子，碰到全部的垃圾；不選配置時直接找 bitmap 的下一個 0（Go 的 allocBits）：第 4 段 concurrent marking 時要分成兩張 bitmap、每輪交換，fast path 也多幾個指令。很碎的頁每次配置都走 slow path，交給第 6 段的 compaction 和下一條的挑頁。
   3. **空的頁回到 pool，待一整輪 GC 沒人拿才 discard**：sweep 後整頁空的頁（和死掉的 large object 的頁）回到 cage 共用的 pool，任何一級和 large object 都能拿；在 pool 裡待過一整輪 GC 還沒人拿的才 discard（放掉實體記憶體、保留位址：macOS、Linux 用 `MAP_FIXED` 重新映射成沒有權限的匿名記憶體，V8 在 Mac 上 decommit 也是這樣；Windows 用 `MEM_DECOMMIT`）。同一級先用最滿的頁（mimalloc），讓接近空的頁有機會整頁空出來。cppgc 的空頁進 page pool、之後再 discard，V8 的進 pool、由 memory reducer 晚一點縮。不選每次 sweep 就全部 discard：一直配置又回收的工作會一直還、一直要回來（Mac 上重新 fault 一頁約 16 µs，配 1 GiB 多約 65 ms）；不選照 2a 不還。
   4. **mark bit 一格一個，第幾格用乘法算**：每一級預先算 `ceil(2^40 / 格子大小)`，頁內的位移（小於 2^18）乘上它、右移 40 位，和除法的結果一樣（誤差小於 2^-22，比 1/格子大小小；52 級 × 2^18 個位移的有限範圍，2d 的 Kani / Verus 試用拿它當題目）。熱路徑沒有除法（M4 上 64 位元的除法約 7 到 9 個 cycle、Raptor Lake 十幾個），sweep 和找區段照 64 格的 word 做。不選每 16 byte 一個 bit（V8 一個 tagged word 一個 bit；它的頁大小混放、沒有「格」）：格子不是 16 的 2 的冪倍時有物件的 bit 間隔不規則，找區段要一格一格跳。mark bit 每輪換極性不在 2b 做：每輪清一次在 366 MiB 的 heap 上約 3 MB 的 memset，等第 4、5 段 sweep 和 marking 重疊時再做。

20. **2c：平行 marking**（2026-10-25，使用者逐條確認；決定 18 的第 5、6 條已經定的不重談：GC 自己的 worker 最多核心數減 1、V8 式的分段 worklist、`fetch_or` 的 mark bit、不用 rayon 和 `crossbeam-deque`、shuttle 和 loom 都留）。
   1. **worker 由 `Platform` 給**：`gc` 定一個照 V8 的 `PostJob` / `JobTask` 形狀的小 trait：交給它一個平行的工作，工作回報現在最多要幾個 worker（`GetMaxConcurrency`），呼叫的 thread 也一起做，全部做完才返回。`gc` 附一個預設的實作：process 共用的一組 worker（核心數減 1），第一次用到時建立；嵌入的一方沒給時用它。V8 和 cppgc 就是這樣（不自己開 thread，經過 embedder 的 platform；Chromium 接到 process 共用的 `base::ThreadPool`）。理由：JS 文件現在 V8 的 default platform（`bindings` 建的，約每個核心一個 worker）已經有一組，我們再開一組，兩邊同時 GC 時 thread 數接近核心數的兩倍；有了 trait，第 9 段可以讓 `bindings` 把工作轉交給 V8 platform 的 worker（要先查 rusty_v8 能不能從 Rust 丟工作給它，可能要 fork 加 glue）；測試也能傳 shuttle、loom 的 thread 或只在呼叫的 thread 上做的實作。預設的 pool 一直活著、工作借用 heap，所以借用交給別的 thread 要 `unsafe`，靠全部做完才返回保證（rayon 的 `scope` 同一個道理），寫進 `crates/gc/soundness.md`。之後不需要和 V8 共用 thread 時可以退回只有預設的實作，只動 `gc` 內部。不選每個 heap 一組（thread 數跟著 heap 數乘上去）；不選只有 process 共用的一組（第 9 段要改）。
   2. **有可以分的工作才平行**：照 V8 的 `GetMaxConcurrency`：main thread 先標，本地一段（64 項）滿了發布到全域時，工作回報的 worker 數才往上加，platform 照它叫醒 worker；全域空了 worker 就退出，結束的判斷要算進還拿著工作的。小 heap 一個 worker 都不叫醒。mark bit 先普通地讀、沒標過才 `fetch_or`（V8 也是先讀再 CAS），relaxed：stop-the-world 期間物件不變，worker 被叫醒時已經經過 platform 的同步。不選每次 GC 都叫醒全部（小 heap 的 GC 只要幾十 µs，叫醒和等它們停下本身就要幾十 µs）；不選照 heap 大小的門檻（要調，而且大小不等於能分的工作）。
   3. **shuttle 和 loom 經過 `cfg` 接**：`RUSTFLAGS="--cfg loom"` / `--cfg shuttle`，GC 的 atomic、mutex、condvar、thread 經過一個小模組（`gc::sync`）換成 std、loom 或 shuttle 的，平常是 std、沒有成本；換 `RUSTFLAGS` 會重編全部依賴，用另外的 target 目錄。不用 Cargo feature：feature 在 workspace 裡會合併，`--all-features` 會把別的測試的 atomic 換掉。測試在 `crates/gc/tests/it` 裡用 cfg 選模組（一個 crate 一個測試 binary）：loom 只測協定（worklist 的 push、pop、發布、偷和結束的判斷，兩三個 thread、限制搶占次數）；shuttle 測整個平行 marking（小 heap、隨機排程跑幾千次，mark bit 和單 thread 的一樣、結束時全空，並數真的碰到偷和結束判斷的排程，一次都沒有就失敗，照 bbtree）；Miri（Stacked Borrows）照舊跑平常的測試，裡面用真的 thread 的平行 marking 由它查 data race。`test.py` 加 `gc-models` 一次跑 loom 和 shuttle，2c 和之後改到 marking、worklist、barrier 時在本機跑；要不要進每天的 CI 由使用者決定。loom（tokio）和 shuttle（AWS）只是 `gc` 的 dev-dependency，記進 `docs/architecture.md` 的「Crate 選型」。V8、cppgc 是 C++，靠 TSan 和 stress 旗標；Rust 的 TSan 要 nightly 和 `-Zbuild-std`，data race 已經有 Miri，不另外加。
   4. **`Member` 在 2c 不改成 atomic**：stop-the-world 時 worker 讀 `Member` 的期間沒有人寫，普通的讀是對的（Miri 查 data race）。改成 atomic（cppgc 的 `Member` 和 V8 的 tagged 欄位都是 relaxed 的 atomic）和順序（relaxed 還是 release）跟著待決定 1 的 barrier，第 4 段一起改；範圍集中在 `member.rs`、`vector.rs` 和 marking 讀邊的地方。

21. **2d：heap verifier、fuzz、Verus 和 Kani 的試用**（2026-10-25，使用者逐條確認；決定 18 的第 6 條和 `details.md` 的「怎麼接成流程」已經定的不重談）。
   1. **heap verifier 是選項**：`HeapOptions::verify`，預設關，`stress` 時也一起跑，測試和 fuzz 打開；每次 GC 之後跑。它從 root 自己重走一遍（單 thread 的 DFS、自己的「看過」集合，不共用 marker 的程式，只共用頁的位址計算），檢查走到的每個物件的 header 是註冊過的型別、在用中的頁的格子開頭或 large object 的開頭、mark bit 設著（cppgc 的 `MarkingVerifier`）；頁的帳（空格數、空區段不重疊而且都在 0 上、`available` 和 pool 的頁的狀態、commit 和 `used_bytes` 的總數）；有 finalizable bit 的格子 mark bit 也設著；root 表的每一格指到活的物件。失敗時 panic，寫出物件、邊和頁。V8 的 heap verifier 也是編進 debug build、用 `--verify-heap` 打開；cppgc 在打開 `CPPGC_VERIFY_HEAP` 的 build 裡每次 marking 之後跑。不選 debug build 一律跑（之後接 DOM，debug build 的每次 GC 都要重走整個 heap）；不選只在 fuzz 下（平常的測試看不到）。verifier 自己也做 mutation：弄壞 heap 的狀態，它要報。
   2. **fuzz**：`crates/gc/fuzz/`（cargo-fuzz 的結構，不在 kun 的 workspace 裡，`rust-toolchain.toml` 釘 Miri 也在用的 `nightly-2026-10-01`）。輸入用自己寫的解碼器（一個 byte 選操作、接著它的參數，解到 bytes 用完，bbtree 的做法），同一個檔案有對應的編碼器，種子才能從錄製編出來；不用 `arbitrary`（只有解碼）。操作和參考模型在 `crates/gc/tests/it/ops.rs`，fuzz target 用 `#[path]` 引同一個檔案：regression 由一般的 `cargo test -p gc` 重播（不要 nightly、libFuzzer，Miri 也能跑）。操作：配置一般物件（幾條邊、有沒有 finalizer）、large object、`HeapVector`，寫邊，vector 的 push、remove，`Persistent` 的增刪，安全點，強制 GC；開頭的 byte 選 heap 的設定（stress、`InlinePlatform` 或 2 個 worker 的 pool）。參考模型是不回收的圖：每次 GC 之後跑 verifier，到得了的物件內容都還在、到不了的剛好 finalize 一次。種子：`gc_bench fuzz-seeds <錄製…> <資料夾>` 從 0g 的錄製（`target/bench/gc/recordings/`，12 份、共 27 GB，只在本機）取開頭和中間幾段、每段約 2000 個事件，大小和邊數換成測試的型別、指到段外的操作丟掉，每個幾 KB。corpus 在 `target/gc-fuzz/corpus/`（本機、接著用、不進 repo）；進 repo 的只有縮小過的 regression（`crates/gc/fuzz/regressions/`），和修正一起 commit。`cfg(fuzzing)` 下用 ASan 的 `__asan_poison_memory_region` 把死掉的格子和 discard 的頁標成不能碰、配置時解開（我們自己 mmap 的 cage ASan 看不出讀到死物件，`0xdb` 毒值只有讀出的值被用到才出事），一般的 build 沒有這段。`test.py gc-fuzz [--minutes N]`（預設 10 分鐘）先補種子（錄製不在就跳過）再跑 cargo fuzz、crash 縮小後印出路徑；要不要進每天的 CI 由使用者決定。第 2 段只有一個 target，照 GC 模式分的等第 3、4 段。V8、Chromium 的 heap fuzz 主要在 ClusterFuzz 上用大量的 JS 間接打 GC，cppgc 有直接打 API 的；這份是後者加參考模型。
   3. **Verus 和 Kani 試 `free_ranges` / `next_bit`**：一頁最多 16384 格，單元測試窮舉不了所有 bitmap，錯了（區段多給一格，兩個物件同一格）Miri 和 sanitizer 都看不出；規格是「回傳的區段剛好是所有連續的 0、不重疊、由低到高」。倒數乘法單元測試已經窮舉，不拿來試。Kani：`page.rs` 裡 `#[cfg(kani)]` 的 harness，證所有最多 2 個 word（128 格）的 bitmap（有界，不用寫不變式）；Verus：規格和迴圈不變式在 `verus!` 裡、證任何長度（無界），先放 `rfcs/0087-dom-gc/prototype/verus/`，不合併。比證到什麼、花的功夫（行數、時間）、跑多久、接進來的成本（決定 18 要「證過的程式就是跑的程式」：Kani 的 harness 和程式同一個檔案、一般的 build 不受影響；Verus 要確認一般的 build 要不要依賴它的 crate、或證的是拷貝）、toolchain；寫成一張表，使用者選一個長期用。V8、Oilpan 沒有形式化驗證，沒有對照。工具由使用者同意後安裝：Kani 是 `cargo install --locked kani-verifier` 和 `cargo kani setup`；Verus 是 GitHub 上 verus-lang/verus 的 release 加它要的 rustup toolchain。做的順序是 verifier、fuzz、試用。**2026-10-25 試用的結果，使用者選 Verus**（數字在 `progress.md` 的 2d）：Kani 只證得到有界的範圍（`next_bit` 到 8 個 word 2 秒、32 個 42 秒、一頁的 256 個 400 秒內做不完；`free_ranges` 回傳 `Vec`，16 格就 137 秒、13 GB），Verus 對任何長度都證完（約 200 行規格和證明、0.4 秒）；兩個都抓到 2b 那條 mask 的 mutant。**接法用甲（`gc` 裡的 `verus!` 模組，`cargo verus verify -p gc` 驗證整個 crate）**，不用乙（只放證過的程式的小 crate）：甲讓證明以後能用 `gc` 自己的型別（`Page`、worklist），乙的小 crate 碰不到它們；甲的風險（整個 `gc` 要過 Verus 的編譯器、可能要到處標 `#[verifier::external]`）實驗過：derive 巨集、`unsafe`、rustix、`cfg(loom)` 都不用標，第一次 45 秒、之後約 1 秒。`gc` 一般的 build 依賴 `vstd`（和 Verus 執行檔同一個 release 的版本，一起升級；帶進 `verus_builtin`、它的巨集等 7 個 crate，從零編多約 5.5 秒，執行期沒有成本）；只在驗證時存在的 import 用 `cfg(verus_only)`；`verus!` 裡的程式照樣受 clippy 和 numerics 的規則管（`#[expect]` 的理由寫 Verus 證了什麼）。Verus 只認一部分的 Rust（沒有 `while let`、位移量用 `u64`）：證的程式照它的寫法寫。`test.py gc-verus` 跑驗證，要不要進每天的 CI 由使用者決定。Kani 不採用（harness 拿掉，工具留在機器上不影響 kun）。（`prototype/` 收尾時刪掉，在 `de8ea619`。）

22. **2e：和 cppgc 比**（2026-10-25，使用者逐條確認；決定 18 的第 7 條已經定的不重談：`gc_bench` 加上新 heap，在 0c、0d 的 microbenchmark 和 0g 的錄製重播上比，驗收是 marking 的速度和 peak used）。
   1. **workload 用 `gc` 的 API 再寫一份**：`gc_bench` 加新 heap，workload 照 `dom::bench` 的物件模型（和真的 `Node` 一樣 336 byte、5 條邊的節點，N 條邊的一般物件，重播照大小和邊數分的類別），回合數和亂數都一樣，測試確認兩邊做的事一樣（節點數、留下的物件數）。不抽一個 trait 讓兩種 heap 共用：`'gc` 的 closure 和 cppgc 的 scope 形狀差很多，抽象也可能讓某一邊多付成本。V8 的 cppgc benchmark 也直接用 cppgc 的 API；第 0 段 V8 的 pattern 也是另寫成 JS。
   2. **量法照 cppgc**：`gc` 內部記每次 GC 的紀錄（各階段的時間、標到的物件和 bytes、worker 掃的數量），同時經過 `Platform` 的 tracing 掛點（兩個預設什麼都不做的方法：開始、結束一個有名字的階段，cppgc 的 `Platform::GetTracingController`）發出 `Gc.Pause`、`Gc.Mark`、`Gc.Sweep`、`Gc.Finalize`；`gc_bench` 把掛點接到 `bindings::trace`，`bench.py gc` 用量 cppgc 的同一把尺（`Gc.Mark` 加進 marking 的 slice），JSON 另外帶 `gc` 自己的紀錄對帳。之後接到 DOM，renderer 的 `MACHOPO_TRACE` 也看得到 GC 的階段。cppgc 的 `StatsCollector`、V8 的 `GCTracer` 都是兩個都做。不選只記紀錄、`bench.py` 對新 heap 改讀 JSON（兩把尺）；不選只發 trace（沒有對帳）。成本是每次 GC 幾次 `Instant::now()` 和空的呼叫。
   3. **比什麼**：第 0 段的 trace 裡，單獨的 cppgc 在重播的強制 GC 時 `CppGC.*` 事件全在 main thread（6 份 wasm 錄製各 18 個，別的 thread 沒有），所以 marking 速度的驗收用單 thread 的新 heap（`InlinePlatform`），預設的 pool（核心數減 1）另報平行的速度。這一欄是「強制 GC 後留下的 used bytes ÷ 最外層的 marking slice」（決定 16 第 5 條的 463 到 589 MB/s 是 Windows 的、Mac 是 771 到 918 MB/s，同一欄）；兩個 heap 的 used 都含自己的進位（真的 `Node` 在 cppgc 約 344 byte、在新 heap 進到 368 這一級，多約 7%），所以 MB/s 之外另報每秒標的物件數（兩邊標同一批物件，沒有進位的偏差），**兩個都不低於 cppgc 才算達標**。peak used 直接比（進位是真的多用的記憶體）。`bench.py gc --heaps` 同一次執行跑 cppgc 和新 heap，比一起量的數字，第 0 段的當參考；12 份錄製的重播和 microbenchmark 都跑。停頓（16.1）、main thread 的 GC 時間（16.2）、和 V8 比的 pattern（16.4）這一段只報不驗收，要等第 3、4 段。先在 Mac 上比完，Windows 等有 Windows 機器時用同樣的指令跑（決定 16 第 6 條原本先 Windows）。V8 的 `GCTracer` 也把 main thread 的 marking 速度和整體的分開記。
   4. **不達標時在 2e 裡剖析再最佳化**（Instruments 或 samply，不先猜：每個物件查頁的狀態、算格子、讀 header 和型別表、單 thread 也用 atomic 的 mark bit、worklist 的進出、cache miss 和預取），每一項量過、記進 `progress.md`，直到達標；要改設計（header 的格式、頁的資料放哪裡、worklist 的結構）時先停下來列選項。不帶著差距進第 3 段：分代只讓 marking 少做，不讓每個物件標得更快。
   5. **第一次量完之後改的量法**（2026-10-25，使用者照建議；`progress.md` 的 2e 有第一次的數字）：
      1. **peak used 兩邊都在一輪結束、heap 的 task 跑之前量**：cppgc 原本在一輪的 task（sweep、可能做完的 GC）之後才量，新 heap 在下一個操作開始的 GC 之前量，整輪的垃圾都算進去，兩邊不在同一個時間點。改成之前量，量到的是一輪結束時真正的最高點，cppgc 的數字會變高，第 0 段的基準不能直接比，同一次執行的兩邊是公平的。Chromium 的記憶體 benchmark 也是在固定的時間點取 dump，不等 GC。不選兩邊都在之後量（新 heap 把安全點的 GC 挪到一輪結束）：新 heap 的數字幾乎只剩活著的量，對它太有利；不選照舊：對新 heap 不公平。
      2. **marking 速度的驗收看 microbenchmark 裡活著的物件多的強制 GC**（build 和三個 high：30 到 56 MiB、10 萬到 92 萬個物件），重播只驗 peak used：重播最後的強制 GC 只剩 27 個物件（約 7 KB），第 3 條說的「771 到 918 MB/s」量到的是固定的開銷，這幾份錄製在每一輪的邊界上活著的都很少，換個時間點強制 GC 也一樣。
      3. **以每秒標的物件數為準，MB/s 只報、不驗收**：第 3 條預期新 heap 的物件比較大，量到的是反過來（配置模式的物件新 heap 32 byte、cppgc 56 byte，cppgc 的物件多一個 vtable），MB/s 對比較小的那一邊不利；兩邊標同一批物件，每秒的物件數沒有大小的偏差。
      4. **平行 marking 在 2e 裡修**（使用者決定）：第一次量到預設的 pool（核心數減 1 個 worker）在樹和小的圖上比只在 heap 的 thread 上標慢（tree-high 每秒約 4900 萬個物件對 2.4 億、replace 和 list 也慢），只有大而寬的 build 快（2.4 倍）。不改驗收（還是看單 thread 的），但至少不比單 thread 慢、大的圖要快；先量是哪個原因（每 64 項一次的全域鎖和叫醒 worker、mark bit 的 bitmap 在 thread 之間的 false sharing），調參數（段的大小、什麼時候叫醒）在 2e 裡做，要改 worklist 或 bitmap 的結構時先停下來列選項。
      5. **之後每一段的驗收都重跑 2e 的比較**（使用者照建議）：同一套 microbenchmark 和 wasm 錄製的重播、同樣的標準（每秒標的物件數不低於 cppgc、peak used 不超過），退步了在那一段修或停下來列選項，不帶著差距進下一段。不讓它每段多 25 分鐘：cppgc 照釘住的 V8 跑、之後的階段不改它，量一次存成基準，每段只跑新 heap、和存下的基準並排（`bench.py gc --baseline`；時間跨兩次執行比雜訊大一點，peak used 每次一樣）；兩邊同一次執行的完整比較只在第 2 段做完、整份 RFC 驗收、V8 或機器換了時跑。重播在同一個 process 裡用同一份計畫跑每一次（原本每次各讀一次 1.3 到 4.4 GB 的錄製、排一次計畫，比重播本身久）。之後各段自己要量的（停頓等）加成同一份報告的欄位，同一次執行一起量，不另跑一套。V8 和 cppgc 也是 benchmark 在 bot 上一直跑、抓 regression。
      6. **之後一定要付的成本在 2e 先做成實驗量一次**（使用者照建議）：寫邊時檢查「marking 在跑」的 barrier（SATB 和 Dijkstra 都要的那一個讀和分支）、marking 用 atomic 讀邊（concurrent marking 要）、marking 時看邊指到的是不是年輕的物件（分代要），量 microbenchmark 的 marking 和回合的時間，看餘裕（graph-high 每秒的物件數只多 7%）夠不夠；量完拿掉，不留在程式裡。barrier 的 slow path 要等待決定 1 才量得了。
23. **第 3 段：young generation**（2026-10-26，使用者逐條確認；決定 8 已經定的不重談：bump 配置的 nursery、平行 scavenge、一個操作裡 nursery 滿了就直接配置在 old、不在操作中途 GC）。
   1. **分段**：3a nursery 和單 thread 的 scavenge（在安全點複製、header 記已搬走和年齡）、升到 old、寫邊的 generational barrier 和 remembered set、root 表跟著更新，full GC 先做一次把活的全部升上去的 scavenge 再標 old，heap verifier 和 fuzz 一起擴充；3b 平行的 scavenge（worker 各自一塊複製的目的地、CAS 搶 forwarding），shuttle 和 loom 一起擴充；3c nursery 的大小照存活率調、pretenuring、和 cppgc 及 V8 比。barrier 不拆到後面：old 指向 young 的邊不記，scavenge 就會漏。
   2. **young 的頁散在 cage 裡、每頁一個 byte 的表記哪些是 young**（semi-space 的兩半各是一串頁；4 GiB ÷ 256 KiB 是 16384 頁，表 16 KiB）。不選 cage 裡固定的一段（判斷只要一次比較，但大小在開 heap 時固定，而且存活率高時每個活的物件都要複製：16 MiB 的 nursery 單 thread 要 8 到 16 ms，決定 16 要 gc-tree 這類 5 ms 以內）：頁散開時活的多的頁可以整頁改成 old、不複製（V8 的 page promotion），nursery 也不受上限。代價是判斷要讀一次表，2e 量過同類的檢查在 marking 上是 0 到 5%。V8 的 semi-space 也是一串 page，page 的 header 有 young 的 flag。
      （2026-10-26 開始 3a 前補，使用者決定）**young 的頁大小混放、一個 bump 指標，整頁升上去的頁變成 old 的第二種頁「混放頁」**：old 的頁照 size class 分（決定 19），一頁混放的 young 頁不能直接變成 size class 的頁。混放頁的 mark bit 是每 8 byte 一個（每個物件的開頭）；sweep 照 bitmap 找活的物件、讀它的大小，活的之間的空隙是空的（V8 的 sweeper 也這樣，不讀死的物件，有 finalizer 的例外）；空出來的地方不再配置，整頁空了才回 pool。整頁升上去只在活的超過約七成時（V8 的門檻），所以最多浪費那些頁的三成，這種頁多半一整批一起死。不選 young 的頁也照 size class 分（升上去只改旗標、old 只有一種頁，但 nursery 每個用到的大小至少一頁，DOM 約 20 到 30 級、至少 5 到 8 MiB，配置也不像 V8 那樣大小混放）；不選不做整頁升上去（回到固定一段的處境）。代價：old 有兩種頁，第 4 到 6 段的 marking、sweep、compaction 都要處理兩種。V8 的 young 和 old 都是混放的頁，Oilpan 的頁照大小分、不搬動；這份是 young 照 V8、old 照 Oilpan。
   3. **remembered set 是每頁一個 slot set**（old 的頁上一格 4 byte 一個 bit，有這種邊的頁才配置，可以再分小塊；V8 的 `OLD_TO_NEW`）。barrier：寫進去的值是 young、被寫的物件是 old 時設那一格的 bit。不選 card table（cppgc 的 young generation 的 `AgeTable`，RFC 原本寫的）：scavenge 要掃整張 card 上的物件、找物件的起點；不選 store buffer（V8 舊的做法）：反覆寫同一格會一直長，要去重或另設上限。0g 量到每次 minor GC 這種邊最多 1 到 4 條，三種都不慢，slot set 精確、有上限。
   4. **活過兩次才升到 old**：header 記一個年齡的 bit，第一次活下來複製到另一半。不選一次就升：剛好跨過 scavenge 的短命物件（innerHTML 這種一棵樹活一陣子再整批丟）會被升上去，要等 full GC 才收得掉；兩次的代價是真的長命的要多複製一次，整頁升上去讓它大多不用複製。V8 的 semi-space scavenger 也是兩次（age mark）；0g 的 `gc_bench analyze` 也照兩次模擬。
   5. **有 finalizer 的 young 物件記在一份清單上**：配置時記一筆，scavenge 之後清單上沒搬走的跑它的 `Drop`，升到 old 的改由 old 的 `finalizable` bitmap 管；finalizer 照舊在 heap 整理好之後才跑。不選這類型別一律配置在 old：成本只該落在真的有 finalizer 的物件上，新的 DOM 的節點帶不帶 `External` 還不知道，不讓它被 GC 綁住。V8 對 `ArrayBuffer` 的 extension 也在 young 這邊另外追。
   6. **新 heap 的重播照錄製裡的安全點分操作**（DOM 每開一個 mutation 或 read scope 記一個；create-element 有 1.36 億個安全點、1946 萬個物件、46 個回合），連續的空操作合成一個；cppgc 那邊不變（它照自己的 task 和配置時的步驟收）。不選照現在一回合一個操作：一回合配置約 130 MB，nursery 一下就滿、剩下的掉進 old，量不到分代，也不像真的 DOM。多出的 `mutate` 呼叫不算在 GC 的時間裡；2e 的新 heap 的 peak used 是一回合一個操作量的，3c 重跑時註明量法不同。
   7. **驗收照決定 16，在 Mac 上同一次執行比**：minor GC 的停頓 p99 在 1 ms 以內、全部活著的（gc-tree 這類）5 ms 以內，存活率低的 wasm 錄製的 main thread 的 GC 時間不超過 cppgc 的 1/3、gc-tree 不超過 cppgc，peak used 不超過 cppgc，存活率低的配置模式的 GC 時間在 V8 的 1.5 倍以內、高的不超過 isolate 上的 cppgc，marking 的速度照決定 22（單 thread、每秒的物件數）；另外照決定 22 第 5 條的第 5 項和 2e 的基準比、不退步。停頓和 GC 時間看 gc-parallel，marking 看 gc；full GC 的停頓這一段只報（old 的 marking 要到第 4 段才 concurrent）。V8 和 isolate 的 heap 不在 2e 的基準檔裡：3c 在 Mac 上 v8、v8-single、isolate、standalone、gc、gc-parallel 同一次執行量一次，存成第 3 段的基準。
24. **3b：平行的 scavenge**（2026-10-26，使用者逐條確認；決定 23 第 1 條已經定的不重談：worker 各自一塊複製的目的地、CAS 搶 forwarding，shuttle 和 loom）。
   1. **先複製、再用 CAS 寫上去向**：header 的 8 bytes 當成一個 64 位元的 atomic，複製完用一次 CAS 換成「去向 + `FORWARDED`」；輸的 thread 用贏家寫的去向，自己那份在 LAB 的最上面就退回，不然原樣留著（一份完整、沒人指著的物件，從頁的開頭走得過去）。不選先用 CAS 佔住再複製（每個物件多寫一次，看到「搬移中」的要原地等，贏家被暫停時大家都等）。V8 的平行 scavenger 也是先複製再 CAS map word。
   2. **複製的目的地是每個 thread 自己的**：留在 nursery 的進自己的 to-space LAB（一段 32 KiB，從 young 的頁上切，拿的時候才鎖）；升到 old 的用自己的每一級一個 cursor，區段用完時才拿 heap 的鎖取一段空區段，結束時把沒用完的區段還回那一頁。不選每次升級都拿鎖：gc-tree 這種全部活著的，第二次 scavenge 一次升很多，平行時會搶。V8 的每個 scavenge task 也有自己的 old space LAB。
   3. **工作照 marking 的分段 worklist 分**：每個 copy（留下的和升上去的）推進 worklist，誰拿到誰掃；root 表在呼叫的 thread 上，slot set 照頁切成一份一份的工作；經過 `Platform`，有段可以拿才叫醒 worker，小的 nursery 都在 heap 的 thread 上做完。單 thread 的 scavenge 也走 worklist（`InlinePlatform`），不留兩套。不選留著 Cheney 的掃描、各 thread 掃自己的 LAB（新的協定、要另外驗，效果差不多）。V8 的平行 scavenger：每個 task 自己的 copied 和 promotion list，remembered set 切成工作。
   4. **slot set 的 word 改成 atomic**：設 bit 用 `fetch_or`，那一頁第一次要 slot set 時用 CAS 換上配置好的 bitmap（輸的丟掉自己的）。mutator 的 barrier 只在 slow path 碰到它，fast path 不變。不選各 thread 先記在清單上、最後合併（只解決 scavenge，第 4 段的 concurrent marking 時 slot set 也可能要在 thread 之間用）。V8 的 slot set 也是 atomic 的 bucket、CAS 換上。
   5. **驗證和這段的驗收**：shuttle 比平行和單 thread 的結果一樣（活的、值和邊、誰留下誰升上去、哪些 finalizer 跑了），而且數到真的有兩個 thread 搶同一個物件、worker 真的拿到 slot set 的工作，一次都沒有就失敗；loom 只窮舉 forwarding 的協定（兩三個 thread、一兩個物件）；heap verifier 照舊在平行的 scavenge 之後跑；fuzz 的 pool 選項會打到平行的路；Miri 照決定 18 第 6 條先不跑。驗收：`gc_bench` 量 scavenge 本身的時間（gc 對 gc-parallel，5 次的中位數），活得少的（replace、list、三個 low）平行不比單 thread 慢，活得多的（build、三個 high）平行比較快；決定 16 的完整目標照決定 23 在 3c 量。
      （2026-10-26 量了之後改，使用者照建議）**活得多的分兩部分**：1 MiB 的 nursery 時一次 scavenge 的工作太少，worker 拿不到東西，平行和單 thread 持平（V8 也大約每 MB 的 nursery 才開一個 scavenge task）；暫時開到 16 MiB 時，寬的圖（build 0.44 倍、churn 0.71 倍）平行比較快，三個 high 持平（一組一組串起來的窄圖，2e 平行 marking 時也是）。所以寬的圖（build、churn）在 nursery 長大之後平行要比較快，到 3c 做 nursery 的大小時再驗；三個 high 只要求不比單 thread 慢。
25. **3c 和 3d：nursery 的大小、pretenuring、和 cppgc 及 V8 比**（2026-10-26，使用者逐條確認）。
   1. **分成兩段**：3c 是 nursery 的大小和 pretenuring；3d 是重播照安全點分操作（決定 23 第 6 條）和完整的比較、驗收（決定 23 第 7 條、決定 24 第 5 條的補充），量的是 3c 調好的 heap。
   2. **nursery 的大小照 V8**：從 `nursery_bytes`（1 MiB）開始，scavenge 累積活下來的 bytes 超過 nursery 的容量時加倍，最多 16 MiB（V8 的 `survived_since_last_expansion_`、64 位元的 semi-space 上限）；full GC 時，上次 full GC 之後的 scavenge 幾乎都是垃圾（活下來的不到看過的 1/16）就減半，不小於起始的大小。不選固定一個大小（工作不同、要的不同）；不選照配置的速度（錄製沒有時間）。peak used 的餘裕夠（2e 的重播 351 對 cppgc 的 620 到 737 MiB），停頓由第 5 條看著。
   3. **不做整頁升上去**（決定 23 第 2 條的補充裡的混放頁也不做）。更正：V8 的 page promotion 在 full GC（mark-compact）時做，marking 之後才知道每頁活多少，V8 的 scavenger 不做；決定 23 第 2 條當時說 scavenger 會，不精確。在 full GC 做（甲）只省 full GC 的 copy，不改善 scavenge 的停頓，卻讓 old 多一種頁、第 4 到 6 段都要處理；每次 scavenge 前先標一次 young（乙）在存活率低（DOM 大多數）時每次白走一趟、V8 也沒有。存活率高時靠平行 scavenge、nursery 的上限和 pretenuring；3d 量到 gc-tree 的 scavenge 停頓超過 5 ms 時再考慮乙。young 的頁散在 cage 裡照舊（nursery 的大小不受限制）。
   4. **pretenuring 是明確的 API**：`Mutation::pretenured` 裡的配置直接放 old（像 V8 的 `AllocationType::kOld`），呼叫的人知道時用（例如 parser 建初始文件）。不選照型別自動（parser 和 script 的 `Element` 同一個型別，會把短命的也放進 old）；不選照呼叫的地方自動（V8 的 allocation site pretenuring：新的 DOM 的元素可能都經過同一個函式配置、header 要放編號），等新的 DOM 量到需要時再加。3d 的重播量不到 pretenuring（錄製沒有誰在 parse）。
   5. **驗收（3d）**：照決定 23 第 7 條和決定 24 第 5 條的補充（nursery 長大之後寬的圖平行 scavenge 比較快）；V8、isolate、standalone、gc、gc-parallel 在 Mac 上同一次執行量一次，存成第 3 段的基準；重播照安全點分操作之後新 heap 的量法和 2e 不同，報告註明。

26. **3d 的驗收沒過的部分**（2026-10-26，使用者逐條確認）。Mac 上同一次執行量到：存活率低的 minor GC 停頓、低存活率的重播（GC 是 cppgc 的 0.11 倍以下、peak used 1.3 到 6.4 MiB 對 622 到 737 MiB）、marking 的速度、寬的圖平行比較快都過了；沒過的是 gc-tree 的重播（gc-parallel 4318 ms 對 cppgc 1901 ms：824 次 scavenge 共 2237 ms，幾乎全部活著、每個物件複製兩次，加上 85 次 full GC 共 2081 ms）、graph-high（minor GC 的 p99 11.5 ms，GC 70.9 ms 對 V8 54.3 ms）、graph-low（V8 的 1.92 倍：full GC 4.3 ms，V8 沒有）、churn、replace、list 的 peak used，和 2e 的基準比 high 的模式的 GC 多 40% 到 66%。實驗：nursery 設成 0 時 gc-tree 1841 ms、graph-high 41.9 ms，退步的是複製活下來的物件。
   1. **存活率高時照配置的地方 pretenure**（丁）：`alloc` 用 `#[track_caller]` 拿到呼叫的位置當 site（site 怎麼認，決定 27 第 1 條改成明確宣告），每個 site 記配置和活下來的數目，活下來的比例到了門檻（V8 是 85%）的 site 之後的配置直接放 old，full GC 時重新判斷（V8 的 allocation site pretenuring 和它的撤回）。不選整個 heap 一起切換（甲）：存活率高的那陣子配置的短命物件也會放進 old；parser 和 script 的 `Element` 是同一個型別，照 site 才分得開（決定 25 第 4 條不選照型別的理由）。不在這一段做先標 young、活得多的頁整頁升上去（乙，V8 的 MinorMS 和 full GC 的 page promotion）：它省掉複製、不省標記，估計 gc-tree 還是 2.7 到 3 秒；old 要能收混放的頁。乙在第 4 段評估（待決定 12）。細節（site 怎麼記在物件上、門檻、什麼時候重新判斷）開始做之前列出來確認。

29. **4a：concurrent marking 的核心的細節**（2026-10-26，使用者逐條確認）。
   1. **marker 在 GC 的 `ThreadPool` 上，照 V8 的 `PostJob` 和 `JobHandle`**（甲）：`Platform` 多一個交出背景工作、馬上返回的 `post_job`（handle 可以等它做完、要它停下、通知它有更多工作），`JobDelegate` 多一個 `should_yield`；pool 同時可以有一個背景工作和一個前景工作（`run` 的 scavenge 或收尾），前景的優先拿 worker，背景的 worker 在物件的邊界檢查 `should_yield`，要停就把本地的工作發布出去、返回；scavenge 前 heap 讓 marking 停下、等所有 marker 返回（V8 的 `PauseScope`），做完再繼續。V8 的 `ConcurrentMarking` 和 cppgc 的 concurrent marking 都經過 platform 的 `PostJob`，不自己開 thread（V8 的註解：job 進行中物件不能搬動，要先停下）。不選 heap 自己開專用的 marker thread（乙：和 pool 的 worker 搶核心、marking 只能用那一兩個 thread，每份文件一個 heap 時 thread 數跟著分頁數長大）。
   2. **`Member` 和 `HeapVector` 的格子是 `AtomicU32`：marking 沒在進行時 relaxed 寫、進行中 release 寫，mutator relaxed 讀；marker 原本打算 acquire 讀，實作改成 relaxed 讀一批（16 條）再一次 acquire 的 fence**（甲；fence 是 4a 實作時改的：每條邊 acquire 讀時，背景標一條鏈慢三分之一，C++ 的 fence 同步給的保證一樣，loom 的模型窮舉；mark bit 的表的讀取也是 relaxed，同一個 fence 之後才用到它指的頁，acquire 讀時 stop-the-world 的 build 慢約 13%）：marker 和 mutator 同時讀寫邊，`Cell` 是 data race；marker 看到 marking 期間新配置的物件的指標時，要看得到它的 mark bit（black allocation，發布之前設好），否則會去掃格子裡殘留的舊指標。判斷 marking 的 flag 本來就是 SATB barrier 的檢查，平常的寫入沒有額外的成本；ARM 上 marking 期間的 `stlr`、marker 的 `ldar` 在 4a、4e 量。cppgc 的 `Member` 一律 relaxed（`member-storage.h`），它的發布另外處理（建構中的物件，沒有逐行查證）；我們就地初始化、寫完才發布。不選一律 release（乙：平常也付 ARM 的成本），不選一律 relaxed、用事先標黑的配置區域解決發布（丙：改配置和 mark bit 的結構，順序還是要另外證）。
   3. **SATB barrier 先標再推，推進 marking 的 worklist 的 mutator 本地段**（甲）：marking 中寫 `Member`、`HeapVector` 的格子（含長大時換掉的舊陣列）和刪 root 時，讀出舊值；是 old 的就用 atomic 設它的 mark bit，這次才設上的推進本地段；0 和 young 的不管；物件配置時的 init 不經過（格子原本是垃圾，靠 black allocation）。本地段滿了（512 項）發布、通知 marking 的工作，安全點時發布手上的。每個物件最多推一次。V8 的 `MarkingBarrier::MarkValue`、cppgc 的 Dijkstra barrier 都是先標再推（它們標新值）。不選只推不標（乙：buffer 跟著寫入次數長大），不選 SATB 專用的佇列（丙：G1 的 thread-local queue，對一個 mutator 多一套交接）。
   4. **black allocation 整段標黑**（乙，V8 的 black area）：marking 中，配置的 cursor（和 scavenge 的 copier）每拿一段新的空區段，就把整段的 mark bit 一次設上，段裡的配置不再做事，快路徑不變；收尾時清掉每個 cursor 沒用完的那段、copier 還回頁上的區段的 bit。large object 照舊各自設 `marked`。不選每個物件發布時設自己的 bit（甲：每個 old 的配置多查一次頁表和 bitmap，gc-tree 這種 marking 期間幾乎都在配置 old 的工作是常駐的成本；cppgc 是這種）。V8 的 black allocation 是區域層級（新的配置區域整段標黑，較新的版本整頁標黑；印象，沒有逐行查證）。verifier 收尾時改成檢查「到得了的都標過」，標過但到不了的（floating garbage）只能是開始時的快照裡的或 marking 期間配置的（第 8 條）。
   5. **marking 期間的 scavenge 時 marker 停下**（甲，details.md 的「marking 期間的 scavenge」）：heap 經過 `JobHandle` 要 marking 停下，marker 在物件的邊界看到 `should_yield` 就發布本地的工作、返回，heap 等到沒有 marker 在跑，scavenge 照舊用全部的 worker，做完再繼續。worklist 只有 old 的物件（開始時的快照緊接著一次 scavenge、marker 跳過 young、SATB 不記 young 的舊值），不用更新；升上來的落在整段標黑的區段；scavenge 改寫 old 的邊時 marker 停著、舊值是 young；新的 young 頁先設 young 的表再配置，經過第 2 條的 release 和 acquire，marker 看到指標時看得到它是 young。V8 的 `ConcurrentMarking` 也要求先 `Stop()` 或 `PauseScope`。不選 scavenge 時 marker 繼續跑（乙：scavenge 本來就用全部的 worker、時間短，只會搶 thread，還要另外證明 marker 不會讀到正在被改的邊）。
   6. **marking 在進 old 的量到了門檻的一半時開始，做完或撞到門檻時收尾**（甲）：現在的 full GC 門檻（上次留下的量，最少 2 MiB）當硬上限；到了一半，在安全點先 scavenge、拍 root 的快照、交出 marking 的工作；marker 做完（全域的 worklist 空、沒有 marker 在跑）之後下一個安全點收尾（交出 mutator 的 buffer、剩下的平行做完、sweep）；撞到硬上限或 `Heap::collect` 時在那個安全點把剩下的做完（全部的 worker 加上 main thread）。main thread 平常不幫忙標，撞到上限的次數和停頓在 4e 量，常撞到再加「落後時每個安全點幫忙一小段」。50% 是 cppgc 的範圍的下限（照配置速度從硬上限往前推 500 ms 的配置量，限制在上次的大小到硬上限之間的 50% 到 90%，`heap-growing.cc`）。不選現在就照配置速度推（乙：和待決定 13 同一件事，4e 一起評估），不選一做完就開始下一輪（丙：barrier 永遠開著）。
   7. **收尾的 pause**（甲）：讓背景的 marking 停下、等它返回；交出 mutator 的本地段；剩下的用前景的 `run` 平行做完（全部的 worker 加上 main thread、同一個 worklist）；清掉 black area 沒用完的 bit；sweep 到第 5 段之前照舊 stop-the-world；finalizer、site 的撤回（背景和收尾數的標到的合起來）、verifier。trace 裡標記的收尾（`Gc.Mark`）和 `Gc.Sweep` 分開：4e 用標記的收尾對決定 16 的 1 ms，整個 pause 照實報告，含 sweep 的整個 pause 在 1 ms 以內改到第 5 段驗收（3e 的 gc-tree 每次 full GC 的 sweep 約 1.2 ms）。V8 和 cppgc 的收尾也不含 sweep（concurrent 或 lazy）。不選在 4a 就把 sweep 移出 pause（乙：第 5 段的內容，第 5 段還會再改）。
   8. **驗證**（甲）：TLA+ 照實作另寫一份 `SatbYoung.tla`（`Satb.tla` 留著當 1a 的協定）：young 的物件、marking 期間的 scavenge（marker 停下、升上來的算黑）、young 裡的寫入不經過 barrier、marker 跳過 young，不變式照舊是收尾時到得了的都標過，拿掉「開始前先 scavenge」或「升上來的算黑」TLC 要找到反例（「old 的 marking 不必走 young」是 V8 和 cppgc 都沒有的論證）；loom 窮舉發布的順序（換成 relaxed 要找到 marker 看到沒標的物件）、背景工作的停下和繼續、結束的判斷；shuttle 隨機排程整個 concurrent marking 加上 mutator 的寫入、刪 root、配置和 scavenge，要數到 marker 和 mutator 真的同時碰同一個物件；fuzz 用不開 thread 的 platform，背景的 marking 在操作之間照 bytes 做一段（新的操作 `MarkStep`），可以重播；`stress` 多一種每個安全點都開始或收尾 marking；verifier 每次收尾檢查到得了的都標過、標過但到不了的只能是開始時的快照裡的（SATB 的 floating garbage）或 marking 期間配置的（verifier 打開時開始時記下快照、marking 期間記下配置的；確認時原本只寫了後者，實作前更正）、black area 沒用完的 bit 清掉了；mutation test 照慣例；Miri 照決定先不跑。V8 和 cppgc 靠 TSan、cppgc 的 marking verifier 和 stress，沒有形式化的模型。不選不擴充 TLA+（乙）。
   9. **marker 經過每頁一格的固定大小的表找 mark bit**（甲）：mark bit 原本在 `space.states`（`Vec<PageState>`）裡的 `Page`，mutator 拿新頁時 Vec 會搬家、頁的狀態和只有它用的欄位會改，和 marker 同時讀是 data race。heap 上一張 16384 格的表（像 slot set 的表和 `young_pages`），每格是 atomic 的指標，指向那一頁 marking 用的資訊（種類、算第幾格的常數、atomic 的 mark bitmap，large object 的 `marked`）；頁變成某一級或 large object 時先建好、release 寫進表，再在頁上配置；只在 sweep（stop-the-world）時釋放、清掉。空區段、空格子數、finalizable 留在 `space.states`。表 128 KiB 一個 heap。不選照 V8 的 `MemoryChunk` 把 bitmap 放在每頁開頭（乙：每頁要留一段，大小級別的格子數都要改，cage 裡的越界寫入可能改到它；V8 開了 sandbox 之後 metadata 也移到 cage 外的表，印象，沒有逐行查證），不選讀頁表時加鎖（丙）。cppgc 的 mark bit 在物件的 header。
   10. **刪 root 的 barrier 保留**（乙，2026-10-26，4a 的 mutation test 之後）：root 在開始時全部當場標上，刪 root 的 barrier 在 4a 的實作裡是多餘的（`SatbYoung.tla` 拿掉它照樣成立，mutation test 拿掉它沒有測試失敗），記成 `docs/test-gaps.md` 的等價的 mutation。留著的理由：JS 文件的 root 表每份 25 萬到 120 萬格（1b），第 9 段開始時一次標完可能超過停頓的目標，改成 concurrent 地掃 root 時它是必要的；成本只在 marking 期間（drop `Persistent` 時記一筆、安全點時處理）。V8 和 cppgc 的 Dijkstra 在收尾重掃 root，不需要它。不選拿掉（甲：程式少一點，但改成 concurrent 地掃 root 時要記得加回來）。

30. **4b：weak 的細節**（2026-10-26，使用者逐條確認）。
   1. **API 是 `WeakMember<T>` 和 `WeakPersistent<T>`**（甲）：`WeakMember<T>` 可以當欄位、也可以寫成 `[WeakMember<T>; N]`，layout 另外列出 weak 的 offset（marker 和 scavenge 不從它往下走），`get(cx)` 回 `Option<Gc>`（目標死了是 `None`）、`set(cx, Option<Gc>)`，和 `Member` 一樣是 atomic 的 32 位元 offset；`WeakPersistent<T>` 是 weak 的 root，`'static`、`new(cx, gc)`、`get(cx)`。現在 DOM 的 `WeakSet` 是固定格數的塊，在新的 GC 上寫成帶 `[WeakMember<T>; N]` 的物件。沒有用到 weak 的型別不付成本。不選乙（加上 weak 版的 `HeapVector`：陣列的長大、複製、`remove` 要分兩種，收尾清掉之後 `len` 以下有 0，容器要在停頓裡壓緊或由呼叫的人跳過；現在的 DOM 用不到），不選丙（加上 cppgc 的自訂 weak callback：使用者的程式跑在收尾的停頓裡，停頓的長短和 soundness 的論證都不再只由 GC 決定；現在的 DOM 沒有人用）。乙、丙記在「之後的可能」。Blink 的 Oilpan 四種都有（`WeakMember`、`WeakPersistent`、weak 的容器、自訂的 weak callback）。
   2. **收尾時要清的 weak 格子由 marker 掃物件時記下，照 cppgc 過濾**（甲）：型別的 layout 另有一份 weak 的 offset 清單；marker 掃一個物件時讀它的 weak 欄位，目標還沒標的把格子的位址記進自己 thread 的清單（目標已經標過的不記，它會一直標著），run 結束時合起來；收尾時一格一格看，目標沒標就清成 0，weak root 的表整張走一遍。黑的物件不用處理：SATB 下 mutator 拿得到的物件（快照裡的、marking 期間配置或升上來的、weak 讀出的）收尾時都標過，所以 marking 期間寫進任何欄位的值收尾時都標過；開始前 nursery 清空了，黑的物件都在 marking 期間建、weak 欄位都在這段時間寫。會指向死物件的只在開始前就在、這一輪活著的物件裡，它們被標上時一定被 marker 掃一次。這條論證加進 TLA+ 的模型（第 6 條）。查證（kun 釘的 V8）：cppgc 平常的 marking 沒有 black allocation（只有 prefinalizer 期間，`object-allocator.cc`），`Visitor::Trace(WeakMember)` 在走到物件時經過 `RegisterWeakReferenceIfNeeded` 登記、目標已經標過的不登記（理由是 `WeakMember` 的 write barrier 會留住之後寫進去的值），收尾的 `MarkerBase::ProcessWeakness` 處理登記的和 weak root 的表；V8 的 JS heap 有 black allocation，它的 marking barrier 不分 weak 和 strong 都標寫進去的值（`MarkingBarrier::MarkValue`、`MarkRange`），少數特別的 weak 物件在配置時登記（transition array，`factory.cc`）。成本是 marker 每個物件多一個「型別有沒有 weak 欄位」的分支，4e 量。不選丙（每頁一張「有 weak 欄位」的 bitmap，物件寫完時設上：原本為了不漏黑的物件，有了上面的論證就用不上；收尾要走每頁的 bitmap、連死的也要看 mark bit，`publish` 在有 weak 的型別上要查頁），不選乙（收尾時走過所有標過的物件：停頓跟著整個 heap 長大）。
   3. **scavenge 也把 weak 當 weak**（甲）：weak 的邊不當 scavenge 的 root；copy 完之後處理 nursery 裡活下來的物件的 weak 欄位（scavenger 掃 copy 時記下）、old 指向 young 的 weak 邊（寫 `WeakMember` 和配置時的 init 的 barrier 記進另一張 weak 的 slot set，每個 heap 一張 16384 格的表）、weak root 的表：目標搬走的改成新的位置（還是 young 的留在 weak 的 slot set），死掉的清成 0。只被 weak 指著的年輕物件第一次 scavenge 就收掉：現在 DOM 的 document 用 `WeakSet` 存 live range、`MutationObserver` 的登記，都是 old 的容器用 weak 指著用完就丟的年輕物件。`Member` 的寫入路徑不變（`WeakMember::set` 是另一個函式）。查證（kun 釘的 V8）：V8 的 scavenger 把 weak 當 strong（`scavenger.cc` 的「Treat weak references as strong」、weak root 除了 global handle 都當 strong、`OLD_TO_NEW` 的格子不分 weak），例外只有 JS 的 `WeakRef` 和 `FinalizationRegistry` 的 cell（`--handle-weak-ref-weakly-in-minor-gc`，`ScavengerWeakObjectsProcessor`）；V8 的 JS 物件很少只被 weak 指著，DOM 的 weak 容器是常態。不選乙（照 V8 當 strong：scavenge 不用改，但上面的年輕物件會被複製、升上去、等 full GC），不選丙（nursery 裡的當 weak、old 指向 young 的當 strong：不用第二張表，但正好幫不上 old 的容器指著年輕物件的情況）。
   4. **weak 讀取的 barrier**（甲）：marking 期間 `WeakMember::get`、`WeakPersistent::get` 讀出 old、還沒標過的目標時，用 SATB 寫入的同一段（`Inner::satb`）標上、推給 marker；young、0 和 marking 沒在進行時不管（收尾在停頓裡清掉 weak，marking 以外讀到的都是活的）。讀出來的這一輪留下（floating garbage）。不加是錯的：讀出的物件寫進掃過的物件時 SATB 不記新的值（1a 的模型的反例）；「讀出來的在操作裡當 root」也不夠，它可以在操作裡被寫進欄位。成本是每次 weak 讀多一次旗子的檢查，`Member` 的讀取不變。V8 和 cppgc 是 Dijkstra（寫進欄位的值被標、收尾重掃 root 和 stack），不需要讀取的 barrier；V8 的 `WeakRef.prototype.deref` 的 `AddToKeptObjects`（`Heap::KeepDuringJob`）是 JS 規格的語意。用 SATB 的 HotSpot G1 在 `Reference.get` 有同樣的 keep-alive barrier（沒有在本機的原始碼查證）。
   5. **`WeakPersistent` 是自己一張表**（甲）：`Shared` 裡多一個同樣型別的 `RootTable`，`WeakPersistent` 拿著它的一格，drop 時還回去，讀到 0 是 `None`；刪 weak 的 root 不用記（不切斷 strong 的路）。full GC 收尾時整張走一遍、目標沒標的清成 0；scavenge 時 young 的目標搬走的改位置、死的清成 0。strong 的 root 表和走它的地方（開始時標 root、scavenge 的 root、verifier、heap 的 drop）都不用改。weak root 多了之後 scavenge 每次整張走，要另外記指向 young 的格子，現在的用量（DOM 9 處）不需要。查證：cppgc 的 `HeapBase` 有分開的 `strong_persistent_region_` 和 `weak_persistent_region_`（`heap-base.h`），收尾只走 weak 的（`ProcessWeakness`）。不選乙（同一張表、每格一個 weak 的標記：每個走 root 的地方都要跳過它，漏一處 weak 就變成 strong；清 weak 時要走整張表）。
   6. **驗證**（甲）：`SatbYoung.tla` 加上 weak 的邊、marking 期間的 weak 讀取、收尾和 scavenge 的清除（實作時改成整個 heap 一條 weak 的邊、weak root 不建模：每個物件一條 weak 的邊加上 weak root，3 個物件時 TLC 跑了五分鐘還沒完、狀態檔 2 GB，一條就夠每個反例用；weak root 收尾時整張看，不靠記下），不變式多一條「weak 讀不到釋放的物件」；拿掉讀取的 barrier、收尾的清除、scavenge 的清除各要找到反例，收尾只清 marker 掃過的物件（第 2 條的論證）要照樣成立。verifier：full GC 之後活物件的 weak 欄位和 weak root 都是 0 或指向標過的，scavenge 之後沒有 weak 指向 from-space、old 指向 young 的 weak 邊都在 weak 的 slot set 上。fuzz：寫、讀 weak 欄位，加、刪、讀 weak root；參考模型多記 weak 的目標，讀到 `Some` 要和模型一樣、讀到 `None` 時模型裡的目標要已經沒有 strong 的路。shuttle：marking 和 mutator 同時跑時加上 weak 讀取（讀出寫進 strong 的欄位）。loom 不加（沒有新的跨 thread 協定）。整合測試 `crates/gc/tests/it/weak.rs`、mutation test 照慣例，Miri 照決定先不跑。V8 和 cppgc 靠 verifier、stress 和 TSan。不選乙（不擴充 TLA+：第 2 條的論證是 SATB 加整段標黑才成立，沒有可以參考的實作）。

31. **4c：ephemeron**（2026-10-26，使用者逐條確認）。
   1. **只做 GC 這一側的基本單位，不做容器**（丙）：一種新的欄位 `EphemeronPair<K, V>`（weak 的 key 和 strong 的 value），marking、收尾、scavenge、verifier、fuzz 和 TLA+ 的模型都處理它；會長大的容器（`HeapEphemeronMap`）等第 8 段的新 DOM 或 guest 的 `WeakMap` 要用時，照需要建在它上面。現在 kun 的 DOM 在 cppgc 上沒有用到 ephemeron（沒有 `EphemeronPair`、沒有 weak key 的 map），容器的 API（hash、key 死了之後誰拿掉那一格、長大）只能用猜的；marking 的固定點和 SATB、black allocation、scavenge 的交互作用最難事後補，和 4a、4b 一起做、一起驗證，4e 量到的收尾停頓也含它。查證（kun 釘的 V8）：cppgc 的基本單位是 `EphemeronPair`（`Visitor::TraceEphemeron`），key 標過就標 value、不然放進 discovered 的清單（`BasicMarkingState::ProcessEphemeron`），`MarkerBase::ProcessWorklistsWithDeadline` 反覆處理到 worklist 空了、這一輪沒有發現新的 pair；Oilpan 的 `HeapHashMap` 的 weak key 自動是 ephemeron；V8 的 JS heap 有 `EphemeronHashTable`，scavenge 有自己的 ephemeron remembered set（`ephemeron-remembered-set.cc`）。不選甲（照原定做 `HeapEphemeronMap`：沒有使用者，API 用猜的，容器的工作比 GC 這一側大），不選乙（延後、移出第 4 段：之後要回來改 marker、收尾和 scavenge，TLA+ 和驗證重來一部分，4e 的收尾停頓不含它）。
   2. **pair 是一個欄位：一條 weak 的 key、一條 strong 的 value**（甲，使用者照建議）：`EphemeronPair<K, V>`，也可以寫成 `[EphemeronPair<K, V>; N]`；`key(cx)`、`value(cx)`、`set(cx, key, value)`，key 死了兩個都是 `None`；layout 多一種種類。和 cppgc 的 `EphemeronPair`（`WeakMember` 的 key、`Member` 的 value）一樣；之後的 map 可以是固定格數的塊，像現在的 `WeakSet`。不選乙（value 是多條邊或非 GC 的資料：現在沒有人要）。
   3. **marking 的固定點照 cppgc**（甲，使用者照建議）：marker 掃到 pair 時，key 是 old 而標過、或是 young（old 的 marking 不判斷 young），就把 value 當 strong 標上，不然把 pair 記進每個 run 的 discovered 清單（合起來）；背景的 run 在沒有段可拿時再看一次 discovered，key 標過的標 value，反覆到沒有新的；收尾用同樣的迴圈做完（有新標的 value 時再跑一次 `run`）。黑的物件的 pair 不用處理（4b 的論證：marking 期間寫進去的值收尾時都標過）。寫 key 不用 SATB（同 weak），寫 value 要（同 strong 的邊）。cppgc 的 concurrent marker 也處理 discovered（`concurrent-marker.cc`）。不選乙（只在收尾的停頓裡處理 discovered：長的 ephemeron 鏈整條在停頓裡標）。
   4. **收尾清掉 key 死掉的 pair 的 key 和 value**（甲，使用者照建議）：discovered 清單剩下的 pair 的 key 都沒標，sweep 之前兩個一起清成 0，照 cppgc 的 `ClearKeyAndValueIfKeyIsDead`（`EphemeronPair` 的 trace 登記的 weak callback）。只看 discovered 就夠：掃到時 key 標過的一直標著，黑的物件的 key 收尾時都標過。不選乙（只清 key：value 指的物件沒標、被 sweep，留下一條指向釋放的物件的 strong 邊）。
   5. **scavenge 照 V8：value 一律當 strong，key 是 weak**（甲，使用者照建議）：copy 的 pair 的 value 照 strong 的邊處理，old 物件的 pair 的 value 指向 young 時記在 strong 的 slot set（寫 value 走一般的 barrier）；key 照 4b 的 weak 處理，死掉的 key 連同 value 一起清成 0。key 死掉的年輕 value 多活一次 scavenge。old 物件指向 young 的 key 原本打算記在 4b 的 weak 的 slot set，實作時改成第三張 ephemeron 的 slot set：weak 的 slot set 分不出格子是不是 pair 的 key，清 key 時要一起清 value。查證：V8 的 scavenger 的 ephemeron 表的 value「treated as strong independently of whether the key is live」（`scavenger.cc` 的 `VisitEphemeronHashTable`），copy 完之後 key 死了整格拿掉、活的改位置，old 的表靠 ephemeron 的 remembered set（`ScavengerEphemeronProcessor`）。不選乙（scavenge 也做固定點：value 早一次收，但平行的 scavenge 要多一套重複的機制，V8 也沒有做）。
   6. **驗證照 4b**（甲，使用者照建議）：`SatbYoung.tla` 加上 pair（實作時把模型裡 4b 的那一條 weak 的邊加上 value，合成一個 ephemeron：沒有 value 時就是 weak 的邊，記下的條件也一樣；另外加一個 pair 的話狀態又要乘上好幾倍。「拿掉固定點」的反例要 holder、key、value 三個不同的物件，2 個物件時照預期成立，`check.py` 讓一項可以依大小給不同的預期；marking 的固定點、收尾清掉 key 死掉的、scavenge 時 value 當 strong、key 當 weak），不變式多一條「key 活著時 value 也活著」，拿掉固定點、收尾的清除、寫 value 的 SATB 各要找到反例；verifier：full GC 之後活物件的 pair 是兩個 0，或 key 和 value 都標過，scavenge 之後都不指向 from-space；fuzz 加寫 pair、讀 pair；整合測試 `crates/gc/tests/it/ephemeron.rs`；mutation test 照慣例；loom 不加，shuttle 看情況。不選乙（不擴充 TLA+：ephemeron 和 SATB、整段標黑的組合沒有可以參考的實作）。

32. **4d：GC 管的 id 表**（2026-10-26，使用者逐條確認）。
   1. **照 id 直接索引、分塊的表**（甲）：一個目錄，每格指向一塊（或空），每塊 1024 格，存物件在 cage 裡的 offset（0 是沒有或死了）；id `n` 在第 `n / 1024` 塊的第 `n % 1024` 格，新的 id 一直往上數；GC 清掉死的格子，整塊清空的放掉。查詢和發 id 都是陣列操作；成批建立的節點 id 連在一起，成批死掉時整塊收回。記憶體：活的塊每格 4 bytes，目錄每 1024 個 id 8 bytes（400 萬個 id 32 KiB）；最壞的情況（每 1024 個 id 留一個長壽的）表跟著發過的 id 長大，可以觀察、之後再補（稀疏的塊或零散的格子改用 hash）。kun 每個節點建立時就有 id（style、layout、paint 在 heap 外用 id 指節點），id 不重複（WebDriver 的 element reference 依賴它），表的大小接近節點數、查詢在熱路徑上。查證（Chromium `main`）：Blink 的 `DOMNodeIds` 只給需要的節點發 id（`IdForNode` 時，存在節點上，`Node::EnsureNodeID`；layout object 直接拿節點的指標），id → 節點是一個 process 共用的 `GCedHeapHashMap<DOMNodeId, WeakMember<Node>>`（死的 entry 由 hash map 的 weak 處理清掉），`DOMNodeId` 是 `int`（DevTools 協定要求），數到最大值從 0 重來、跳過還在用的（會重用）。不選乙（照 Blink 的 hash map：適合它稀疏、量小的 id，放到 kun 每次找節點都要算 hash，現在的 `NodeIdMap` 為了熱路徑才換成 FxHash），不選丙（格子重用、id 帶世代號碼：u32 的世代繞回來 id 就重複，要不重複得把 `NodeId` 改成 u64、牽動整條 pipeline），丁（照 Blink 只給需要的節點發 id）是 DOM 的設計、不在這份 RFC。
   2. **每個 heap 一張表，格子不分型別，查詢時比對型別**（甲）：`cx.new_id(gc) -> Id` 發下一個 id（DOM 把它存在節點的欄位上），`cx.by_id::<T>(id) -> Option<Gc<'gc, T>>` 查詢，物件死了、id 沒發過或不是 `T` 都是 `None`；比對的是物件 header 的型別編號和 `T` 的 `TypeSlot`（多一次比較，讀的是本來就要碰的物件），所以格子不記型別也是 safe 的；`by_id::<Erased>` 不比對，給節點分成很多 GC 型別的新 DOM 先拿再判斷。表放在 heap 上（實作時放在 `Inner`、不在 `Shared`：id 只經過 `Mutation` 用，不用活得比 heap 久，不像 `Persistent`），GC 直接處理這一張。之後有第二種 id 時和節點共用一串編號。查證（Chromium `main`）：Blink 的 `DOMNodeIds` 是一個 process 共用、型別固定是 `Node` 的表（它的節點是同一個 class 階層）；cppgc 沒有 id 表。不選乙（有型別、可以很多張的 `IdTable<T>`：每張要向 heap 登記、GC 一張一張走，節點分成很多型別時 `T` 就是 `Erased`，現在也沒有第二種 id）。
   3. **full GC 在收尾的停頓裡把整張表走一遍**（甲）：sweep 之前，指向 old、沒標的格子清成 0（young 的是 scavenge 的事），整塊清空的放掉。成本和 id 的數目成正比，估計每格 2 到 3 ns（一萬個節點不到 0.03 ms，一百萬個 2 到 3 ms，超過收尾 1 ms 的目標）；4e 量，太慢就把表分給 `Platform::run` 的 worker 平行走，或改成乙。查證：V8 的 weak global handle 在 full GC 整份走一遍（`IterateWeakRootsForPhantomHandles`），Blink 的 `DOMNodeIds` 的 hash map 在收尾的 weak 處理裡走它的 entry（cppgc 的 `ProcessWeakness` 先處理 weak container callback）。不選乙（每頁一張「有 id」的 bitmap、sweep 從死物件讀 id 反查：GC 要知道 id 在哪個欄位、要讀死物件，第 5 段 sweep 改成 concurrent 時要拉回停頓），不選丙（移出停頓：要等收尾標完才知道誰沒標，清完之前 mutator 不能查）。
   4. **scavenge 只走「指向 young 的 id」的清單**（甲）：`new_id` 時物件是 young 的就把 id 放進清單（建在 old 的不放：old 不會再變 young）；copy 做完之後走清單，搬到 to-space 的改位置、留著，升上去的改位置、拿出清單，死了的清成 0、拿出清單；full GC 開頭的 scavenge 之後清單是空的。成本大約是 nursery 裡的節點數，不跟著整張表長大。查證：V8 的 global handle 在 `Create` 時把指向 young 的放進 `young_nodes_`（`NeedsTrackingInYoungNodes`），scavenge 只走它（`ProcessWeakYoungObjects`），之後 `UpdateListOfYoungNodes`；Blink 不用處理（cppgc 的新生代在 Chrome 不是預設：`gni/v8.gni` 的 `cppgc_enable_young_generation` 預設 false，只有 caged heap 時編進去，執行期的旗子沒查；Oilpan 的物件不搬）。4b 的 weak root 表每次 scavenge 整張走（DOM 9 處，先不改），之後多了可以套用同一個做法。不選乙（每次 scavenge 走整張表：十萬個節點的頁每次多約 0.3 ms，3e 的 minor GC p99 約 0.4 ms）。
   5. **查詢經過 weak 讀取的 barrier；不擴充 TLA+**（甲）：marking 期間 `by_id` 查到 old、還沒標的物件時經過 `Inner::read_weak`（型別不符回 `None` 的不標），verifier 的 floating 照 4b 記下它到得了的。id 表在協定上是 weak root 的表，查詢是模型裡的 weak 讀取（拿掉讀取的 barrier 有反例）；scavenge 走清單、full GC 整張走是「有沒有漏處理哪一格」，由 verifier、fuzz 和 mutation test 守。verifier：full GC 之後每格是 0、標過的 old 物件或（concurrent 時）young 的，沒有整塊都是 0 的塊；scavenge 之後沒有一格指向 from-space、指向 young 的 id 都在清單上、清單上的都指向 young。fuzz 加 `NewId`、`ById`（空 bit 上）；整合測試 `crates/gc/tests/it/ids.rs`（含 `HeapStats` 的表的塊數、id 不重複）；mutation test 照慣例，loom、shuttle 不加。V8 的 global handle 和 Blink 的 `DOMNodeIds` 都沒有形式化的模型。不選乙（為 id 表擴充 TLA+：模型裡「每一格都有人處理」很容易成立，會漏的是實作的細節，狀態又變多）。

33. **4e：量測和第 4 段的驗收**（2026-10-26，使用者照建議確認）。
   1. **驗收條件**：決定 16 的五條，套到 concurrent marking 上時：「GC 時間」只算 main thread 的停頓（marking 的開始和收尾、scavenge），worker 在背景標的時間另外報告；「marking 的速度」照舊在單 thread、stop-the-world 的 `gc` heap 上量（和第 3 段比得起來）；停頓多一條：concurrent marking 收尾的標記（`Gc.Mark`）p99 在 1 ms 以內，含 sweep 的整個停頓照實報告（第 5 段驗收）。第 3 段的每一條照樣要過。
   2. **量測工具**：`bench.py gc` 多報 concurrent marking 開始和收尾的停頓（收尾拆成標記和 sweep）、撞到門檻收尾的次數、worker 在背景標的時間、id 表的塊數；`gc_bench` 多一個工作：一百萬個帶 id 的節點、留下一部分，量收尾走 id 表的時間；weak 和 ephemeron 的成本量「沒用到時」（第 3 段的工作有沒有變慢）；barrier 的成本用同一個工作在 `gc` 和 `gc-parallel` 上的總時間扣掉停頓比（雜訊大，只當參考）。
   3. **分三段**：4e-1 補量測工具和測試；4e-2 完整量一次、對照驗收和第 3 段的基準，跑階段做完時的 `cargo test --workspace`、`fmt --check`、clippy，沒過的照 3d 逐條決定；4e-3 用量到的數字評估待決定 13 和 15（到時再列選項）。
   4. **在 Apple Silicon 上量**（決定 16 第 6 條的段落驗收）：這台 M4、接電源，和第 3 段同樣的量法（`bench.py gc --runs 5`，microbenchmark 跑全部的 heap，6 份 wasm 錄製跑 standalone、gc、gc-parallel），存成 `bench-4-apple-m4.json`；Windows 這一段不量（第 3 段也只量了 Mac）。

34. **4e-3：marking 撞到門檻和標記時數 site**（2026-10-26，使用者照建議確認，並要求第 8 段評估這裡沒選的做法：記在待決定 13、15、16）。4e-2 的量測（`progress.md` 的 4e-2）只有「收尾的標記 p99 ≤ 1 ms」沒過：全部活著的工作，worker 還沒標完 old 就撞到門檻，剩下的在停頓裡標（chain-high 1.34、tree-high 1.66、graph-high 5.30、gc-tree 的重播 4.34 ms）。
   1. **marking 期間 old 可以超過門檻一段 margin，照 V8**（甲）：marking 在跑時，進 old 的量到了門檻加 `max(門檻/2, 32 MiB)`（不超過 cage 剩下的一半）才在停頓裡收尾；沒在 marking 時照舊。32 MiB 是 `HeapOptions` 的一個值，測試用小的。查證（kun 釘的 V8）：`heap.cc` 的 `AllocationLimitOvershotByLargeMargin`，margin 是 `heap-controller.h` 的 `old_generation_overshoot_margin`（`min(max(limit/2, 32 MB), (max - limit)/2)`），撞到之前 V8 讓 concurrent marking 繼續、不在停頓裡做完。V8 的 limit 是 old 整個的大小，我們的門檻是上次 GC 之後可以再進 old 的量（等於上次留下的量），所以 heap 大時我們的 margin 是 V8 的一半；量的是這個。實驗（gc-parallel，各 3 次）：收尾的標記 p99 全部在 31 µs 以內、撞到門檻 0 次，peak used 多不到 1 MiB，main thread 的 GC 時間最少（graph-high 23.5 → 10.3 ms）。代價：配置遠快過標記時，heap 最多可以多長 32 MiB 以上。cppgc 單獨用時撞到上限就在停頓裡做完（和現在一樣），在 Chrome 裡由 V8 帶著用這個 margin。不選 marking 期間把門檻放寬成固定的 2 倍（乙：graph-high 1.6 ms，過不了），不選不改、驗收只算沒撞到門檻的收尾（丙）；更早開始（門檻的 25%）和 main thread 落後時幫忙標量過都沒有幫助（配置模式一個操作就配置超過剩下的門檻）。
   2. **full GC 的門檻維持固定的 2 倍，開始 marking 維持門檻的一半**：不照配置速度動態調，第 8 段用真的頁面評估（待決定 13）。
   3. **標記時照舊數 site**（甲，待決定 15）：不數時小物件的標記快 4% 到 10%（chain-high +8%、tree-high +10%、graph-high +4%），DOM 的 build 一樣；標記已經比 cppgc 快 3% 到 48%，而且大多在背景，對停頓的影響小。不選乙（沒有 site 被 tenure 時不數：幫不上 chain-high、tree-high）、丙（照 V8 整個 old 一起撤回、不數：old 裡長命的多時，一個死光的 site 撤不掉），留到第 8 段。
   4. **marking 開始時把活的全部升上去的 scavenge 先不處理**：gc-tree 的重播最長 17.8 ms（全部活著、nursery 最大時；加了第 1 條的 margin 之後重量是 3.3 ms，原因沒有查），驗收沒有這一條；第 8 段用真的頁面評估（待決定 16）。

35. **第 5 段：concurrent sweeping 和三種 finalizer**（2026-10-26，第 1、2 條使用者照建議確認，第 3 條逐條看了選項之後選甲，要求第 8 段評估乙：待決定 17）。開始前量了 gc-tree 的重播（gc-parallel）收尾的停頓：6.4 ms 幾乎都在 `Gc.Sweep`，其中掃每頁的 bitmap 約 0.4 ms（約 1400 頁、350 MiB），把在 pool 裡待過一輪的空頁還給系統（每頁一次 `mmap`）約 6.1 ms（p90）；連續的頁合併成一次呼叫沒有幫助（1405 頁只有 7 段，還是 6.4 ms：成本跟著還的 bytes）。
   1. **分成四段**：5a 還頁移出停頓；5b concurrent sweeping 的核心（背景掃頁，配置時那一級沒有掃好的頁就自己掃一頁，下一輪 marking 開始前做完）；5c 三種 finalizer（沒有、`Send` 的在 sweeper 上跑、要在 main thread 的交回安全點）；5d 量測和驗收。每一段開始前再列細節。5a 做完時掃頁只剩約 0.4 ms，5b 照做：它跟著 heap 長（約 900 MiB 到 1 ms，JS 文件的 heap 更大），決定 8 也接受了 concurrent sweeping。查證（kun 釘的 V8）：V8 的 sweeper 在 worker 上掃頁（`MajorSweeperJob`），配置找不到頁時 main thread 自己掃（`ParallelSweepSpace`），下一次 GC 前做完（`EnsureMajorCompleted`）；cppgc 的 `ConcurrentSweepTask` 在背景掃頁、finalizer 延到 main thread（`DeferredFinalizationBuilder`），配置時自己掃（`SweepForAllocationIfRunning`）、下一次 GC 前做完（`FinishIfRunning`）。
   2. **驗收**：決定 16 留到第 5 段的那一條，含 sweep 的整個收尾停頓 p99 在 1 ms 以內；第 4 段的各條照樣要過；main thread 在配置時自己掃頁的時間算進 GC 時間，背景 sweep 的時間另外報告；量法和第 4 段一樣（這台 M4，`bench-5-apple-m4.json`）。
   3. **還頁照舊等頁在 pool 裡待過一整輪 GC，改由 worker 去還**（甲）：停頓裡只把要還的頁從 pool 拿出來（記帳），交給 platform 的 worker 做系統呼叫，還完的頁放進「已經還掉」的清單；還在還的頁 mutator 拿不到，要頁時拿 pool 裡其他的或 cage 裡沒用過的。沒有背景 worker 的 heap 照舊在停頓裡還。系統呼叫的成本沒有少（gc-tree 一輪約 6 ms 的 worker 時間），committed 的變化和現在一樣。查證：V8 的空頁進 `MemoryPool`，worker 上延後的 `ReleasePooledChunksTask` 還待了 8 到 16 秒的（`--memory-pool-timeout` 預設 8 秒，一輪一個 epoch），記憶體壓力或最後手段的 GC 時立刻全部還（`ReleaseAllImmediately`）；cppgc 的空頁進 `PageBackend` 的 pool，平常不還，只有降低記憶體的 GC（強制、配置失敗重試、V8 帶 reduce-memory）sweep 做完後在 main thread 整批還（`ReleasePooledPages`），原始碼留著「考慮偶爾 decommit」的 TODO；兩邊都不在停頓裡還。不選照 V8 看時間（乙：platform 要有延後的 task，committed 多留 8 到 16 秒（gc-tree 約 350 MiB），要有記憶體壓力的訊號，和待決定 14 是同一類 allocator 的政策；第 8 段評估，待決定 17），不選照 cppgc 平常不還（丙：kun 沒有記憶體壓力的訊號，committed 只增不減），不選停頓裡合併連續的頁（丁：量過沒有幫助）。

36. **5b：concurrent sweeping 的核心**（2026-10-26，使用者逐條確認，都選甲；第 5 條要求第 7 段評估乙或其他做法：待決定 18）。前提（查程式時確認）：還沒掃的頁上的死物件沒有 slot set 的記錄。concurrent marking 開始前的 scavenge 把 nursery 清空、slot set 是空的；marking 期間被寫的 old 物件要嘛在快照裡（SATB：收尾時標過），要嘛是期間配置的（黑的）。所以 sweeping 期間 scavenge 照常讀 slot set，不用過濾，details.md 的「Sweeping 和 remembered set」擔心的情況不會發生（第 7 條用 TLA+ 守住）。
   1. **sweeper 只算，main thread 套用**（甲，cppgc 的做法）：收尾時把要掃的頁照 size class 列成清單交給 platform 的 posted job；sweeper 從 `MarkTable` 讀 mark bit，算出每頁的空區段、活的數目、是不是整頁空，放進有鎖的清單；main thread 在安全點和配置的慢路徑把結果套到 `Space` 的頁上，還沒套用的頁不從裡面配置。`Space` 照舊只有 main thread 改，配置的快路徑不變。查證：cppgc 的 `ConcurrentSweepTask` 把 `SweptPageState` 推進 `swept_unfinalized_pages`，main thread 的 `SweepFinalizer::FinalizePage` 跑 finalizer、把 free list 併進 space。不選乙（V8 的 JS heap：`RawSweep` 在背景直接寫頁的 free list，main thread 用 `GetSweptPageSafe` 拿掃好的頁；它的頁本來就給多個 thread 配置，我們一個 heap 一個 mutator，`Space` 要拆成多個 thread 能碰的結構、配置換頁都要鎖，第 2 到 4 段的 soundness 論證和 verifier 要重寫一大部分，停頓的改善卻一樣）。
   2. **配置時那一級沒有掃好的頁：先套用掃好的，還沒有就自己掃那一級的一頁**（甲）：在同一個鎖底下從那一級還沒掃的清單拿走一頁，在 main thread 上掃、套用、配置；那一級都掃完還是沒有空格子才拿 pool 或新頁。查證：V8 的配置的慢路徑一次掃一頁（`main-allocator.cc` 的 `ContributeToSweeping`，`kMaxPagesToSweep = 1`）；cppgc 的 `SweepForAllocationIfRunning` 先拿掃好的、再掃空頁、再掃同一個 space 還沒掃的，夠放這個物件就停。不選乙（不掃、直接拿空頁或新頁：sweeper 落後時 heap 多長，peak used 的條件可能變差）。
   3. **下一輪 marking 開始、stop-the-world 的 full GC 和 `Heap::collect` 之前在停頓裡平行掃完；sweeping 期間 scavenge 照常做**（甲）：沒掃的頁用 `Platform::run` 掃完、全部套用（marking 會清掉 sweeper 讀的 mark bit）；heap drop 時先取消 sweep 的 job。scavenge 升上去的物件只拿已經套用的頁、pool 或新頁，scavenge 的 worker 不掃頁。查證：V8 在下一次 GC 前 `EnsureMajorCompleted`、cppgc `FinishIfRunning`；V8 的 sweeping 期間 scavenge 照常做（另有 `ContributeAndWaitForPromotedPagesIteration` 處理升上去的頁），scavenge 的 worker 升級時會不會掃頁沒有查證。不選乙（scavenge 前先掃完：收尾之後的第一次 scavenge 多到 0.4 ms，minor GC 的 p99 的條件很緊）。（2026-10-26 實作時補）`Heap::collect` 在它的停頓裡 sweep 完、finalizer 也跑完：它是明確要求的完整 GC（測試和 `gc_bench` 的強制 GC 照它讀結果），照 cppgc 的強制 GC（`Heap::ForceGarbageCollectionSlow` 用 `SweepingType::kAtomic`）；沒有 worker 的 platform 也在停頓裡 sweep 完；撞到門檻、沒有 marking 在跑時的 full GC 照 concurrent marking 的收尾，把 sweep 交給背景。sweep 的 job 最多一個 worker：第一版每頁一個（照 marker 的做法），gc-parallel 的 9 個 worker 搶清單的鎖、收尾時叫醒 9 次，gc-tree 的重播背景時間 359 ms、main thread 套用和自己掃 30.7 ms，小 heap 的收尾停頓從約 25 µs 變成 80 到 100 µs；改成一個之後背景 19 ms、收尾 5 到 42 µs。查證：cppgc 的 `ConcurrentSweepTask::GetMaxConcurrency` 是 0 或 1；V8 的 `MajorSweeperJob` 一個 task 至少 2 頁，最多和要 sweep 的 space 一樣多。
   4. **marker 邊標邊數 bytes，收尾時就定 `used` 和下一輪的門檻**（甲）：每個 thread 數它掃的物件的大小，收尾時合起來，加上 marking 期間黑配置和升上來的量；`HeapStats::used_bytes`、門檻和 `bench.py gc` 的 peak used 的意思和現在一樣。代價是 marker 每個物件多一次加法，估計不到 1%（標記速度只比 cppgc 快 4% 的 graph-high 這條很緊），5d 量，明顯變慢就改成乙。查證：cppgc 在 marking 結束時用標到的 bytes 設門檻（`NotifyMarkingCompleted(marked_bytes)`、`ResetAllocatedObjectSize`、`ConfigureLimit`，在 sweep 之前）；V8 的 marker 數每頁的 live bytes（`IncrementLiveBytesAtomically`）。不選乙（sweep 做完才算：sweep 做完之前 `used` 含還沒掃的垃圾，peak used 和第 4 段、cppgc 的比較失真）。（2026-10-26 5d 改成乙，使用者看過兩個實驗的數字後決定）5d 的完整量測：單 thread 的 gc 上每秒標的物件 build 34.0、chain-high 220.4、tree-high 181.6、graph-high 55.8 百萬，同一段時間重量第 4 段是 38.7、264.6、223.1、63.9，graph-high 低於 cppgc 的 62.6；拿掉計數就回到第 4 段，每個型別預先算好格子大小（36、238、210、61.4）和標上時數（30.8、158.9、217.2、59.5）都不夠（標記的熱迴圈對程式碼生成很敏感）。實驗了兩個做法（gc 各 5 次，gc-parallel 各 3 次）：乙（marker 不數，sweep 做完才定 `used` 和門檻）35.4、269.2、217.7、63.2；丙（只有 concurrent marking 數，stop-the-world 的 marking 從停頓裡的 sweep 加總）36.4、257.4、213.9、61.2。gc-parallel 上兩者的 GC 時間和收尾停頓和甲差不多；乙的 graph-high 多一次 marking（背景標記 3.9 → 12.9 ms）、ids 的 peak used 39.4 → 43.5 MiB（門檻和 `used` 晚一點才更新）。選乙：只有它讓「標記速度 ≥ cppgc」確定過關，marker 也不用改。代價：V8 和 cppgc 都在 marking 結束時用 marker 數的 bytes 設門檻（V8 的 `IncrementLiveBytesAtomically` 和 `RecomputeLimits`、cppgc 的 `NotifyMarkingCompleted`），這裡偏離它們，門檻在 sweep 做完時才設（sweep 通常幾 ms 內做完），sweep 做完之前 `used` 含還沒掃的垃圾。不選丙（照 V8 的只有 concurrent marking，graph-high 差 cppgc 約 2%）。
   5. **有 finalizable 物件的頁留給 main thread 掃**（甲）：每頁記 finalizable 物件的數目，收尾時數目大於 0 的頁不交給 sweeper，main thread 在之後的安全點掃（先跑死物件的 finalizer，再算空區段、套用），下一輪開始前一定掃完。sweeper 不讀 `finalizable` 的 bitmap，格子在 finalizer 跑完之後才放回；5c 不能在背景跑的 finalizer 也走這條路。現在的測試物件和重播裡很少有 finalizer；第 7 段的新 DOM 若很多物件帶 `External`，main thread 要掃的頁會變多（待決定 18）。不選乙（cppgc 的做法：sweeper 掃所有的頁，有 finalizer 的死物件的格子延後放回（`DeferredFinalizationBuilder`、`unfinalized_free_list`），`finalizable` 的 bitmap 要搬到共用的表、跑完 finalizer 要把格子併回已經套用的頁，5b 的改動多約三成）。V8 的 JS 物件沒有 finalizer。
   6. **死掉的 large object 照舊在收尾的停頓裡放**（甲）：收尾時本來就要走一遍頁的狀態清單（列出給 sweeper 的頁），沒標的 large object 把頁放進 pool（有 finalizer 的照第 5 條交給 main thread），gc-tree 的 1400 頁是幾微秒。sweeper 掃到整頁空的頁，套用時放進 pool，待過一輪 GC 照 5a 交給 worker 還。查證：V8 在停頓裡放（`MarkCompactCollector::Sweep()` 的 `SweepLargeSpace`，記憶體延後還）；cppgc 的 sweeper 也掃 large page（`ConcurrentSweepTask::VisitLargePage`，因為它的 finalizer 會延後）。不選乙（交給 sweeper：省幾微秒，多一種交接）。
   7. **驗證**（甲）：`SatbYoung.tla` 加「收尾時有指向 young 的邊的 old 物件都標過」的不變式，模型的 mutation 照樣跑；verifier 在收尾時不檢查還沒掃的頁的帳，sweeping 全部套用的那個安全點做完整的頁的帳，每套用一頁檢查它的空區段和 mark bit；shuttle 要數到 sweeper 和 mutator 真的同時跑過；fuzz 的 `MarkStep` 也跑 sweep 的 job；整合測試、mutation test 照慣例；loom 不加（交接都在 mutex 底下）；Miri 照決定先不跑。V8 和 cppgc 的 sweeping 靠 TSan、cppgc 的 verifier 和測試，沒有形式化的模型。不選乙（不改 TLA+，只靠文字論證和 verifier）、丙（把 sweeping 放進模型：交接只是 mutex 底下的清單，模型抓得到的錯誤少，狀態卻變多）。
   8. **main thread 的零碎 sweep 只記計數、不進 trace**（甲，cppgc 的做法）：配置時掃頁、安全點套用和掃有 finalizer 的頁用 `Instant` 量時間，記進 `HeapStats`（main thread 的 sweep 的時間和頁數、背景 sweep 的時間），`gc_bench` 讀回合前後的差，`bench.py gc` 報出來，main thread 的那份算進 GC 時間和「sweeping」那一類；停頓裡掃完的照舊是停頓裡的 `Gc.Sweep`。查證：cppgc 的配置時的 sweep 用 `StatsCollector::DisabledScope(kSweepOnAllocation)`，只算進統計、不發 trace 事件，外面的 incremental sweep 才發。不選乙（每次發 trace 事件：一次的成本和掃一頁的 0.3 µs 差不多，量到的偏高，停頓的分布要排除這些片段）。

37. **5c：三種 finalizer**（2026-10-26，第 1、2 條使用者照建議確認，第 3 到 6 條逐條確認、都選甲；第 3 條的乙併進待決定 18，第 5 條的乙記成待決定 19）。現在沒有工作有 finalizer（microbenchmark 和重播都沒有），效益量不到；這一段的價值是第 7 段設計新 DOM 之前把 API 定下來。查證（kun 釘的 V8）：cppgc 的 finalizer 都在 main thread（concurrent sweeper 用 `DeferredFinalizationBuilder` 延後）；V8 的 JS 物件沒有 finalizer，但 ArrayBuffer 背後的原生記憶體由 worker 上的 `ArrayBufferSweeper::SweepingJob` 放掉（最多一個 worker，young 和 old 兩張清單）。
   1. **照決定 8 接受的設計全部做完**（甲）：分開兩種 `External`，`Send` 的在 sweeper 上跑，其他的在 main thread。不選只定 API、執行留在 main thread（乙），不選延到第 7 段（丙），不選照 cppgc 全部在 main thread、API 不分（丁）。
   2. **`External<T>` 要求 `T: Send`，finalizer 在 sweeper 上跑；不是 `Send` 的用新的 `LocalExternal<T>`，finalizer 在 main thread 跑**（甲，原設計）：derive 在編譯時從欄位算出型別的 finalizer 是哪一種（有 `LocalExternal` 的 drop glue 就是 main thread，只有 `External` 的就是 sweeper，都沒有就是沒有）；`External<Rc<…>>` 編譯失敗（compile-fail 測試）。不選反過來、預設 main thread、要在 sweeper 上跑的寫 `SendExternal<T>`（乙：比較保守，但用的人不會想到要選）。
   3. **照頁分**（甲）：每頁的 `finalizable` bitmap 搬到 `Marks`（atomic 的 word，sweeper 經過 `MarkTable` 讀），每頁另外數 main thread 那種的 finalizable 物件；收尾時那個數目是 0 的頁交給 sweeper，它先跑死物件的 `Drop`、清掉 bit，再算空區段（格子在 `Drop` 之後才算空）；有 main thread 那種物件的頁照決定 36 第 5 條留給 main thread。死掉的 large object 照種類分：`Send` 的交給 sweeper，套用時才放頁。debug 的毒值由 sweeper 在 `Drop` 之後寫。代價：一頁上有一個 `LocalExternal` 的物件，整頁（連同 `Send` 的）回 main thread。不選照物件分（乙：cppgc 的延後放回格子加上 `Send` 的在 sweeper 上跑；要決定 36 第 5 條沒選的延後放回，改動多約三成，等於提前決定待決定 18：併進它），不選配置時照 finalizer 的種類分頁（丙：頁變三倍、碎片多、快路徑要看種類，V8 和 cppgc 都不這樣做）。
   4. **sweeper 上的 finalizer panic 時，在 heap 的 thread 下一次等 job 時往上拋**（甲）：跑 `Drop` 之前清掉那個物件的 bit，panic 時那一頁剩下的死物件不再 finalize（leak，不是 UB），那一頁不產生結果、照「還沒掃」在 `finish_sweeping` 時掃完；和背景 marking、scavenge 的 worker panic 同一條規則。不選當場 abort（乙：一個 `Drop` 寫錯就讓 renderer 掛掉，和 main thread 上的 finalizer 不一致），不選接住後丟掉（丙：錯誤被吞掉）。cppgc 的 destructor 和 V8 放記憶體都沒有例外，沒有直接的對照。
   5. **nursery 裡死掉的物件的 finalizer 照舊在 scavenge 的停頓裡、main thread 上跑，兩種都是**（甲）：現在沒有工作有這種物件；不選把 `Send` 的交給 worker（乙：from-space 的頁要等 worker 跑完才能重用，nursery 的容量計算跟著改；V8 的新生代 ArrayBuffer 在 minor GC 之後交給 `ArrayBufferSweeper` 是它的前例）：第 7 段看新 DOM 有沒有大量短命、帶 `Send` finalizer 的物件，第 8 段用真的頁面量 minor GC 的停頓裡 `Drop` 佔多少再決定（待決定 19）。
   6. **驗證**（甲）：整合測試（`External` 的 `Drop` 在 worker 上、`LocalExternal` 的在 heap 的 thread 上，混了兩種的頁回 main thread，`Send` 的 large object，panic 往上拋、不 finalize 兩次，`collect` 在停頓裡 finalize 完）、compile-fail（`External<Rc<…>>`）、verifier（每頁的兩個數目和 bitmap 對得上，交給 sweeper 的頁沒有 main thread 那種的物件）、shuttle（5b 的 sweep 測試加 `Send` finalizer 的物件，每個剛好 finalize 一次，有排程讓 worker 的 `Drop` 和 mutator 重疊）、fuzz（物件多一種 `Send` 的 finalizer，放在空的 bit 上）、soundness 文件、mutation test；不加 loom、不擴充 TLA+（交接在 mutex 底下，`Drop` 碰不到 heap）；Miri 照決定先不跑。不選只加 shuttle、fuzz 不改（乙：fuzz 在 5b 剛抓到 finalizer 和 ASan 毒值的順序錯誤）。

38. **第 6 段：先量碎片，再決定做不做 compaction**（2026-10-26，使用者照建議確認）。到第 5 段為止沒有量過碎片：`peak_committed` 和 `peak_used` 的差（gc-tree 的重播 663 對 351 MiB、churn 17.8 對 12.8 MiB）混著 pool 裡待一輪的空頁、nursery 和量的時間點，分不出哪些是頁上的空格子。查證（kun 釘的 V8 15.2）：V8 一般的 full GC 也 compact（`compaction_on_regular_gcs` 預設開），marking 開始時挑頁（`CollectEvacuationCandidates`）：空的部分至少 70% 的頁才算（量到 compaction 的速度之後改成每頁搬 0.5 ms 以內），從最空的挑起，一次最多搬 4 MiB（`compaction_max_evacuated_bytes_mb`），估計放不掉頁就不搬；要省記憶體的 GC 放寬到 20%、6 到 12 MiB。cppgc 只 compact 標成 compactable 的 space（Blink 只標 vector 和 hash table 的 backing store，沒有查證 Blink 的原始碼），free list 合計超過 512 KiB 才做（`kFreeListSizeThreshold`），stack 上可能有指標的 atomic GC 不做。
   1. **6a 只量**（甲）：量完使用者照數字決定做不做；做的話 6b 起再列設計（挑頁、記 slot、平行搬、和 concurrent sweep 怎麼配合），不做的話第 6 段到此為止，寫進待決定，第 8 段用真的頁面再看。不選直接照 V8 做（乙：可能做了用不到，收尾的停頓變長）。
   2. **量什麼**（甲）：每次 sweep 做完時走一遍 old 的頁（只在 `gc_bench` 要時算，不在熱路徑上）：每一級有物件的頁上空格子的比例；照 V8 的挑法（空至少 70%、最多搬 4 MiB、放不掉頁就不搬）算出 compaction 能放掉幾頁、要搬多少 bytes；混放頁（整頁升上來的頁）浪費的 bytes；配置走慢路徑（換區段、換頁）的次數。不選只看 committed 和 used 的比（乙：分不出碎片和 pool、nursery）。（2026-10-26 實作時補）整頁升上去（V8 的 page promotion）到現在都沒有做，old 裡沒有混放頁，這一項量不到；V8 在 marking 開始時挑頁，這裡在 sweep 做完時量（之後的配置會填掉一些空格子，量到的是一輪裡最碎的時候）；`gc_bench` 一直打開量測（每次 sweep 做完走一遍頁）。

   4. **做不做的門檻**（甲，看數字之前先定）：任何一個工作的穩定狀態，照 V8 的挑法能放掉的頁至少是 old 的 committed 的 10%，或配置的慢路徑明顯拖慢配置的速度，就做。不選只看記憶體的目標（乙：peak used 不超過 cppgc；現在 351 對 671 MiB，照這條幾乎一定不做）。

## 之後的可能

- **wasm GC 的物件放進這個 heap**：編成 wasm GC 的語言（Kotlin、Dart、Java）的物件和 DOM 由同一個 GC 回收、循環收得掉。怎麼接不綁定 wasmtime 現在的介面（fork 它的 collector 介面、等它的介面成熟、或其他形式），接的時候決定要不要把 `External` 換成 side table（已決定的事項 7）：量 `External` 的間接存取在 DOM 的工作上的成本再定。原本是 RFC 0005 用 cppgc 的方向，這份做完之後改成這個 heap。
- **JS 語意的 GC 功能**：`WeakRef`、`FinalizationRegistry`、`WeakMap` 的 ephemeron，給 wasm 的 guest 用。
- **guest 的 handle 直接是 GC 參照**：等 GC 版的 canonical ABI，不經過 root 表。
- **把 RFC 0085 的來源 2（資料的表示）一起做進新的 DOM**：屬性、class、字串放在 GC heap 上、共用不可變的資料。
- **ephemeron 的容器**（已決定的事項 31 第 1 條）：`HeapEphemeronMap` 這類以 `EphemeronPair` 為格子、會長大的 map，給新 DOM 以節點為 key 的旁表和 guest 的 `WeakMap`。
- **weak 的容器和自訂的 weak callback**（已決定的事項 30 第 1 條的乙、丙）：會長大的 weak 清單（`HeapVector<WeakMember<T>>`，像 cppgc 的 weak 容器，收尾時清掉或壓緊死的格子），和物件在收尾時自己處理 weak 狀態的 callback（cppgc 的 `RegisterWeakCallback`，例如把死的項目從自己的 hash 表拿掉）。等 DOM 或 guest 真的要用時再加：layout 多一種種類，不改 `WeakMember` 的 API。
- **old generation 也分代的變化**：例如穩定的大樹不必每輪重標（像 sticky mark bit），量過再看。
- **接 V8 時兩邊的 marking 怎麼對齊**（第 9 段）：第 1 段的原型（1d，`progress.md`；原型在 `de8ea619` 的 `prototype/`）兩種都做了，都對：在 stub 的 `Trace` 裡同步地標我們的 heap，不用改 V8，但一個 stub 背後的子樹在一次 `Trace` 裡走完；交換（我們的 marker 在背景跑，找到的 JS 參照在 main thread 上補回 V8）能把停頓切到每步的預算內，但要 fork V8（掛點約 90 行），還要讓 V8 的排程知道我們的 heap。不 fork 的中間路線：同步的做法加上切段，把我們的 marking 包成 cppgc 的工作 token、在 cppgc 的 incremental step 裡一段一段做，要先解決結束條件和排程，第 9 段先試（`details.md` 的「兩邊的 marking 怎麼對齊」）。
- **GC 分成自己的 repo**（2026-10-26，使用者決定等第 7 到 9 段都做完再分）：放在 `../third_party/`、kun 用 `third_party.toml` 釘它；搬的時候另寫一份小的 RFC，決定新 repo 的名字和授權、跟著搬的工具（`sanity.py` 的 `unsafe`、`numerics`、`docs`，`test.py` 的 `gc-models`、`gc-fuzz`、`gc-verus`、`mutate`，`soundness.md`、fuzz、Verus 釘的 `vstd`、TLA+ 的模型、`gc_macros`）。`gc_bench` 依賴 `dom` 和 V8，留在 kun。對照：Oilpan 在 Blink 裡開發了很多年，成熟、要和 V8 共用之後才搬進 V8 成為 cppgc。
- **V8 的 GC 有、這裡還沒有的**（2026-10-26 對照 kun 釘的 V8 15.2 的原始碼列的，細節沒有逐一讀）：
  - 記憶體壓力和閒下來時縮小 heap（`MemoryReducer`、`MemoryPressureNotification`）：kun 還沒有記憶體壓力的訊號，也沒有 idle 時做 GC 的工作的機制（Blink 有）。
  - 年輕的 large object（`NewLargeObjectSpace`）：這裡的 large object 一律在 old，短命的大物件要等 full GC。
  - heap 的上限和接近上限的處理（`NearHeapLimitCallback`）：這裡的 cage 滿了就 panic。
  - heap snapshot、allocation tracker、sampling heap profiler（`src/profiler/`，DevTools 的 Memory 面板靠它們）：這裡只有 `HeapStats` 的計數，看不到誰留住了誰；新的 GC 換掉 cppgc 之後，kun 的 DevTools 要看 DOM 的記憶體就要它。
  - main thread 在配置時幫忙標（V8 的 incremental marking）：這裡只有 concurrent，跟不上時靠 overshoot margin；4e 試過，microbenchmark 上幫不上，真的頁面上再看。
