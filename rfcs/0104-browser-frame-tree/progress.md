## 做過的檢查

每一步一段：日期和平台；新的測試；mutation test（弄壞了什麼、哪個測試失敗、沒抓到的和原因）；視窗裡的手動確認；找到的 bug；不穩定的測試；跑過的檢查和測試數字。

### 1a（2026-11-18，macOS、Apple M4）

- **做了什麼**：`protocol` 加 `FrameToken`（16 個 byte，寫成 32 個大寫 hex）；`RendererMsg::DevToolsMainFrameToken` 改用它；兩則新訊息 `DidCreateChildFrame`、`DidDetachFrame`（Browser 在 1b 才處理，現在收下不做事）。engine 建子 frame 時抽 token（`dom_api::new_frame_token`），存在 engine 的 `Frame` 上，`FrameRequest::Created`、`Removed` 帶著它；主 frame 換文件時 engine 也對它的子 frame 排 `Removed`（之前只有子 frame 換文件時才排）。engine 的介面拿掉 `set_devtools_frame_ids` 和它的 closure，換成 `set_main_frame_token`。renderer 把 token 記在自己的子 frame 表（`ChildFrames`）上，DevTools 的子 frame 的 `frameId` 和 WebDriver 的 frame 參照都換成 token；renderer 的前綴照舊用在元素參照、DevTools 的請求和 style sheet 的 id（`new_id_prefix`）。
- **和計畫不同的**：WebDriver 從 id 找 frame 查的是 renderer 的子 frame 表，不是 engine 的清單；engine 的介面只多了 `set_main_frame_token`（RFC 的「DevTools 和自動化」那一段已經改成這樣，寫了理由）。
- **新的測試**：`protocol` 的 `frame_token::a_token_is_written_as_32_hex_digits`、`what_isnt_a_token`；`dom_js` 的 `frames::a_frame_goes_with_its_token`（每個子 frame 的 token 不同；iframe 被拿掉、子 frame 換文件、主 frame 換文件時 `Removed` 帶著對的 token，子孫不另外送）；`browser` 的 `links::the_browser_hears_of_child_frames_coming_and_going`（Browser 依序聽到三個子 frame 的建立和它們父 frame 的 token、iframe 被拿掉時一則 detach、主 frame 換頁時只有最外層那個子 frame 的 detach）。改的測試：`dom_js` 的 `devtools` 兩個測試改用固定的主 frame 的 token 和 `Created` 帶的 token；`shell` 的 `devtools::every_frame_has_a_context_that_goes_with_its_document` 改成檢查子 frame 的 `frameId` 是一個 token（原本檢查舊格式的 `.`）。
- **mutation test**（`python3 scripts/test.py mutate`，15 個）：抓到 14 個：每個子 frame 同一個 token、token 不是亂數（`dom_js` 的 `frames::`）；主 frame 的子 frame、子 frame 換文件時它的子 frame、被拿掉的 iframe 的 `Removed` 不排（`dom_js` 的 `frames::`）；inspector 拿不到子 frame 的 id、engine 忘掉主 frame 的 token（`dom_js` 的 `devtools::`）；子 frame 的父 frame 一律說成主 frame、不送建立、不送 detach（`browser` 的 `the_browser_hears_of_child_frames_coming_and_going`）；新的 engine 沒拿到主 frame 的 token（`shell` 的 `devtools::`）；WebDriver 從 id 找不到 frame（`shell` 的 frame 測試）；token 寫成小寫、hex 的兩位數接受正負號（`protocol` 的 `frame_token`）。沒抓到 1 個：token 到的時候 engine 已經在、當場告訴它的那條，是等價的（Browser 送的第一則訊息就是 token，那時還沒有 engine），記進 `docs/test-gaps.md` 的「等價、不用處理的 mutation」。
- **跑過的檢查**：`cargo test -p protocol -p dom_api -p dom_js -p dom_wasm -p renderer -p browser -p shell -p driver` 全部通過；`sanity.py` 的 `deps`、`spans`、`boundary`、`unsafe`、`tests`、`numerics`、`docs` 通過。`cargo test --workspace`、fmt 的整體檢查和 clippy 照規則在第 1 階段做完時跑。

### 1b（2026-11-18，macOS、Apple M4）

- **做了什麼**：`browser` 加 `FrameTree`（`frame_tree.rs`：以 token 為鍵，每個節點記父節點和照建立順序的子節點）和 `BadMessageReason`（`bad_message.rs`）。`WebContents` 的主 frame 的 token 改成樹的根；收到 `DidCreateChildFrame`、`DidDetachFrame` 時更新樹，接不上的是壞掉的訊息：記 error、`kill`、標成 crashed、樹清回只剩根（`received_bad_message`）。renderer 掛掉（`RendererGone`）、`about:crash` 時也清樹；crashed 的期間不處理舊 renderer 送來的建立和 detach。
- **和計畫不同的**：renderer 重開時不另外清樹：會走到重開的三種情況都已經清過，留著只是多一個等價的 mutant。
- **找到的問題**：舊 renderer 結束前已經排進 Browser 佇列的訊息，在新的 renderer 開始之後才被處理時，會被當成新 renderer 的（訊息不帶是哪個 renderer 送的），接不上樹的會把新的 renderer 也結束掉。第 1 階段沒有處理，記在 RFC 的「待決定」，第 2 階段開始前決定。
- **新的測試**：`browser` 的單元測試 `frame_tree::tests::frames_come_and_go_with_the_frames_in_them`、`what_the_tree_cant_take_is_a_bad_message`；整合測試 `links::a_bad_message_ends_the_renderer`（四種壞訊息各一次：renderer 結束、分頁 crashed、樹只剩根、之後舊 renderer 的 detach 不算數，重新整理之後新的 renderer 的子 frame 重新進樹）、`links::a_renderer_gone_takes_its_frames`（`about:crash` 和 `RendererGone` 都清樹）；`the_browser_hears_of_child_frames_coming_and_going` 加上樹的形狀的檢查。
- **mutation test**（14 個）：抓到 13 個：樹接受用過的 token、不在的父 frame、拿掉不在的 frame、拿掉主 frame；拿掉時留下子孫、留在父節點的子節點裡；清樹時留著子節點（`browser` 的 `frame_tree` 單元測試）；`WebContents` 不把建立、detach 放進樹；壞訊息不結束 renderer、不清樹；`about:crash`、`RendererGone` 不清樹（`browser` 的整合測試）。沒抓到 1 個：crashed 的期間照樣處理舊 renderer 的建立和 detach，是等價的（記進 `docs/test-gaps.md`）。
- **跑過的檢查**：`cargo test -p browser -p shell -p driver` 全部通過。

### 2a（2026-11-18，macOS、Apple M4）

- **做了什麼**：`browser` 加 `RendererId`；`RenderProcessHost` 交出訊息時帶著它，`ContentsEvent::Renderer` 變成 `{ renderer, msg }`。`WebContents::is_current_renderer`：是目前的 renderer、而且它還沒結束（`about:crash`、壞掉的訊息、`RendererGone` 之後到下一次導覽重開之前都算結束）。外層程式（`BrowserView::on_contents_event`、headless）把訊息交給分頁之前先問它，不算數的丟掉，之後的 DevTools、游標、popup 也就看不到；第 1 階段只對建立和 detach 的 crashed 判斷拿掉。
- **找到的問題**：一開始 `BrowserView` 在分頁已經關掉時也把訊息丟掉，關掉的分頁的 renderer 結束時的 `RendererGone` 就到不了 DevTools 的 session，還在等的 `Page.navigate` 永遠沒有回答（`shell` 的 `devtools_lifecycle::flat_sessions_detach` 每次都逾時）。改成分頁還在、而且不是目前的 renderer 才丟。
- **新的測試**：`browser` 的 `links::an_ended_renderers_late_messages_count_for_nothing`（抓住舊 renderer 的一則訊息，`about:crash` 之後和重新整理、新的 renderer 開始之後再交，都不算數；新的 renderer 的訊息照樣算）；`shell` 的 `browser_view::an_ended_renderers_late_message_counts_for_nothing`（同樣的情境經過 `BrowserView`）。`browser` 的 `a_bad_message_ends_the_renderer` 拿掉直接呼叫 `on_renderer_message` 模擬舊訊息的那一段（新的測試用真的舊訊息驗）。
- **mutation test**（6 個）：抓到 5 個：結束了的 renderer 的訊息照樣算、被取代的 renderer 的訊息照樣算、每個 renderer 的訊息都說是同一個 renderer（`browser` 的新測試）；`BrowserView` 把結束了的 renderer 的訊息交下去（`shell` 的新測試）、`BrowserView` 連關掉的分頁的 renderer 的訊息也丟掉（`devtools_lifecycle::flat_sessions_detach`）。沒抓到 1 個：headless 不過濾，是等價的（記進 `docs/test-gaps.md`）。
- **跑過的檢查**：`cargo test -p browser -p shell -p driver` 全部通過。

### 2b（2026-11-18，macOS、Apple M4）

- **做了什麼**：DOM 的導覽請求記下發起它的文件（`NavigationRequest::initiator`；`location` 的 `href`、`replace()` 是呼叫它的 script 的 realm 的文件，其他的 setter 只有同源的 script 能呼叫，就是 `Location` 自己的文件；連結是連結所在的文件），engine 把它換成 frame 交給 host，沒有 frame 顯示它時到別的文件的導覽不做。`OpenUrl` 只剩新分頁（`WindowOpenDisposition` 拿掉 `CurrentTab`），主 frame 的導覽和重新整理都是 `BeginNavigation { frame, initiator, id, kind }`（`Reload` 這則訊息拿掉），`id` 是 renderer 自己的編號。Browser 收到時：frame 或 initiator 不在樹上是壞掉的訊息（`NavigationOfUnknownFrame`、`NavigationByUnknownFrame`）；網址照第 14 條的 scheme 規則（`page_may_navigate_to`：`http:`、`https:`、`file:`、`blob:`；`data:` 不給 main frame；`about:` 只收 `blank`，子 frame 再加 `srcdoc`；`file:` 照舊看 renderer 能不能讀），新分頁也照它檢查。子 frame 的 `BeginNavigation` 現在不會送來（2c 才送），送來時只記 warn。
- **行為的改變**：網頁不能再導覽到 `about:blank` 以外的 `about:`（之前擋的只是 debug URL；`about:demo` 現在也只有使用者自己輸入的才開），`docs/limitations.md` 寫了。
- **移到 2c 的**：`NavigationDropped` 和 commit 帶回 renderer 的編號（主 frame 的導覽沒有人用到它們，子 frame 的導覽經過 Browser 時才需要）；`file:` 照發起的文件檢查（Browser 要知道子 frame 的網址，2c 才有）。
- **新的測試**：`browser` 的 `a_navigation_tells_the_browser_who_asked`（子 frame 的 `_top` 連結，initiator 是子 frame 的 token；main frame 的 `location.href` 是 main frame 自己）、`a_page_may_navigate_to_about_blank_alone`（取代 GPU 的那一份：`about:gpucrash`、`crash`、`demo`、`srcdoc`、`BLANK` 都擋，`about:blank#top` 可以）；`a_bad_message_ends_the_renderer` 加兩則（導覽不在的 frame、由不在的 frame 發起）；`a_page_may_not_navigate_to_a_data_url` 改成經過 `BeginNavigation`；`location_reload_loads_the_entry_again` 等 `BeginNavigation` 的 `Reload`。`dom_js` 的 `links::a_navigation_says_who_asked`（自己的連結、子 frame 的 `_top` 連結、top 的 script 導覽子 frame、子 frame 的 script 導覽 top、子 frame 的 script 先拿掉自己的 iframe 再導覽 top 時什麼都不送）。其他測試照新的訊息改寫（`asked_url`）。
- **mutation test**（14 個，全部抓到）：realm 被當成被導覽的文件、`href` 和 `replace()` 忘了呼叫的 realm、連結被當成被導覽的 frame 發起的（`dom_js` 的新測試）；沒有 frame 顯示的文件照樣導覽（同一個測試的最後一段，加了之後另外跑）；renderer 說是被導覽的 frame 發起的、main frame 的重新整理沒送到 Browser、導覽不在的 frame 和由不在的 frame 發起的照收、main frame 可以導覽到 `data:`、`about:srcdoc`、任何 `about:`、`about:blank#…` 不算 `about:blank`、新分頁不檢查（`browser` 的測試）。
- **跑過的檢查**：`cargo test -p dom -p dom_api -p dom_js -p dom_wasm -p protocol -p renderer -p browser -p shell -p driver` 全部通過；`test.py wpt` 的 `html/browsers/history/`、`html/browsers/browsing-the-web/`、`the-iframe-element/`、`the-base-element/`：222 個測試、694 個檢查，沒有不預期的結果。

### 2c（2026-11-18，macOS、Apple M4）

- **決定的事**：第 17 到 21 條（導覽放在節點上；`BeginNavigation` 帶 DevTools 的 initiator；renderer 送文件的請求是壞掉的訊息；`about:` 的文件照繼承的來源判斷 `file:`；錯誤頁的文件網址是 `chrome-error://chromewebdata/`）。第 18 條原本寫主 frame 由 script 發起的導覽也會有 stack，做的時候發現 DOM 沒有記下 `location` 和連結的 stack，改正成只有 iframe 的 `src` 帶。
- **做了什麼**：`browser` 的 `NavigationRequest`（新的模組）放在 `FrameTreeNode` 上，main frame 原本的 `PendingNavigation` 也搬過去；節點另外記 renderer 回報 commit 了的網址、能不能開本機檔案（commit 時 browser 送的是不是本機文件，新的子 frame 照父 frame）。子 frame 的 `BeginNavigation`：檢查（`file:` 看發起的 frame 的節點）、照 `Iframe` 載入、redirect 在 UI thread 上、commit（`CommitNavigation` 帶 `frame`、renderer 的編號、錯誤頁的旗標）；不收的送 `NavigationDropped`；子 frame 的 `Reload` 用節點的網址。`ContentsEvent` 的導覽事件帶 `frame`，多了 `BadMessage`（IO thread 找到的）和 `NavigationStarted`（給 DevTools）。讀本機檔案的旗標在 commit 時決定：main frame 的新文件決定，子 frame 的本機文件只會加上（原本想在 `DidCommitNavigation` 時照整棵樹重算，但那時 renderer 已經開始抓新文件的子資源，會有一段時間還讀得到；改回 commit 時）。renderer：子 frame 的 `src`、`location`、連結、`reload()` 送 `BeginNavigation`（`about:` 和 `javascript:` 照舊在 renderer 裡 commit），記著每個子 frame 請求的編號和 iframe 的 `referrerpolicy`，到 commit 或被丟掉之前算載入中；commit 的編號不是最後請求的就不收；送 `BeginNavigation` 之前先讓 DevTools 知道 frame（`frameAttached` 在 `frameStartedNavigating` 之前）。renderer 自己載入子 frame 的路（`children.fetches`、`frame_redirects`、`child_timing`、`Network` agent 給 iframe 文件的分支）拿掉。DevTools：子 frame 的 `frameStartedNavigating` 和 `requestWillBeSent` 由 browser 發（`loaderId` 是 browser 的導覽 id，發起者是 renderer 帶來的），main frame 的照舊在 session 看到 loader 變了時發（和開始它的命令同一輪，`navigationType` 才對得上）。
- **行為的改變**：子 frame 載入失敗時是錯誤頁（之前是空的文件），main frame 的錯誤頁的文件網址也變成 `chrome-error://chromewebdata/`；頁面不准的子 frame 導覽什麼都不載入，iframe 不分派 `load`（之前抓了、失敗、commit 空的文件）；`file:` 照發起的文件判斷。`javascript:` 的 `src` 照舊 commit 空的文件（一開始讓它也送到 browser，browser 不收、iframe 沒有 `load`，WPT 的 `history_pushstate_url_rewriting.html` 逾時；改回 renderer 自己 commit）。
- **之後才補的**：子 frame 的 `about:blank`、`srcdoc` 由 browser 知道（2d），子 frame 的 `#fragment`、`pushState` 告訴 browser（2e）：在那之前節點上的網址是 browser 載入的最後一份文件的，子 frame 的 `reload()` 照它載入。

- **做了什麼**：`NavigationController` 的 entry 是一棵位置的樹（`TreeNode`：unique name、item 序號、子節點），項目（`FrameNavigationEntry`：item 序號、網址、document 的序號、state、捲動模式）在 controller 的表上，entry 之間共用；每次 commit 之後清掉沒有 entry 用的項目（`sweep`）。對外的 `NavigationEntry` 是借出來的檢視（`url()`、`title()`、`root()`、`frame(unique_name)`）。子 frame 的導覽開始時決定種類（Chromium 的 `ShouldReplaceCurrentEntryForNavigationFromInitialEmptyDocumentOrEntry` 和 `did_create_new_entry`）：要求取代的、還沒 commit 過 `about:blank` 以外的文件的（`FrameTree` 的 `has_committed_real_load`）、目前是分頁的第一個 entry 的，都是取代，重新載入是重新載入，其他是新的 entry；commit 時新的 entry 複製目前的 entry 的樹（只留現在還在的 frame 的位置，`clone_live`），換掉那個 frame 的位置（它底下的位置跟著拿掉，`place`），取代放進目前的 entry 裡它的位置（父 frame 沒有位置時不記，Chromium 也是），重新載入留著項目、換 document 的序號。main frame 重新載入時清掉它的 frame 的位置，回到某個 entry 時留著（3d 照它還原）。等著 commit 的導覽記著 frame：子 frame 的 commit 只結束它自己較早的，main frame 的結束全部。子 frame 的 commit 帶它的項目的 state 和捲動模式、entry 的 index 和 length（renderer 在 commit 時設好，`history.length` 每個 frame 一樣），每個 frame 的 commit 之後都送 `SetHistoryOffsetAndLength`。commit 的 index 和 length 改成送出 commit 時才算（`commit_place`，Chromium 的 `UpdateHistoryParamsInCommitNavigationParams`），main frame 的也是：導覽開始時算的話，子 frame 的 commit 會把整頁的 `history.length` 設回開始時的值（WPT 的 `history-traversal-navigate-parent-while-child-loading.html`：iframe 第一次載入時 main frame `pushState`，iframe 的 `onload` 讀到 1，跑相關的 WPT 時找到的）。`UpdateState` 帶 frame，renderer 每個 frame 都送，browser 改它在目前的 entry 裡的項目（frame 不在是壞掉的訊息，`StateOfUnknownFrame`）。
- **中間的狀態**：上一頁、下一頁還只看 main frame：到只差在子 frame 的 entry 時當成 main frame 同一份文件內的 traversal（分派 `popstate`），子 frame 不換回去，3d 改（記在 `docs/limitations.md`）。
