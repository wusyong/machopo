# P2 像個瀏覽器

2026-09-30 規劃，2026-10-01 完成：在 macOS 上驗收完，Windows 上的驗收延後（見 `PROGRESS.md`）。

## 設計決定

### 1. 網路與 navigation

**`net` crate**（對應 `//services/network`）。
- **跑在自己的 thread 上**：`NetworkService` thread，上面跑 tokio runtime。reqwest 是 async 的，放在獨立的 thread，UI thread 和 renderer 都不會被網路卡住。
- **HTTP 用 reqwest 0.13，TLS 用它預設的 rustls + aws-lc-rs**，憑證用作業系統的憑證庫驗證（`rustls-platform-verifier`）：
  - **Build 只需要 C 編譯器**。2026-09-30 讀了 aws-lc-sys 0.45 的 build script：預設用 `cc` 編譯，不用 cmake；macOS、Windows MSVC、Linux 的 x86_64 和 aarch64 都附了預先產生好的 binding，不用 bindgen 和 libclang；Windows x86_64 沒有 NASM 時，改用 crate 附的預先組譯好的 object 檔（rustls 的 aws-lc-rs feature 會打開 `prebuilt-nasm`）。
  - **實測**：同一天在 macOS（Apple M4）上用 Rust 1.88.0 從頭編 release build 約 30 秒，沒有額外安裝任何工具；`https://text.npr.org/`（HTTP/2）、`https://sqlite.org/about.html` 和 `http://info.cern.ch/`（HTTP/1.1）都載入成功。Windows 上還沒實測，第一次在 Windows 上 build 時要確認。
  - **為什麼不用 ring**：build 一樣簡單，但 rustls 的 ring provider 不支援後量子的金鑰交換（X25519MLKEM768）；aws-lc-rs 預設優先使用它，Chrome 也預設使用。AWS-LC 是從 BoringSSL 分支出來的，和 Chromium 用的 BoringSSL 同一系。代價是第一次編譯比較久。
  - **為什麼不自己組 sans-I/O 的 HTTP stack**：評估過 HTTP/1.1 用 `ureq-proto`、TLS 用 `boring`（BoringSSL）的組合。HTTP/2 沒有成熟的 sans-I/O crate（`h2` 建立在 tokio 的 I/O trait 上），要自己寫；`boring` 的 build 要 cmake（Windows 另外要 NASM）和 libclang，BoringSSL 也沒有官方的 prebuilt。P2.0 會從 1 週變成 2–3 週，所以先用 reqwest，但保留之後換掉的空間（見下一點）。
- **分兩層，reqwest 只在下層**，對應 Chromium `//net` 的 `URLRequest` 和 `HttpStreamFactory`：
  - **上層是 `URLLoader`**：處理 scheme（`file:`、`http(s):`）、跟隨 redirect、把回應整理成 `protocol` 的型別。
  - **下層是 transport**：「把一個 HTTP 請求送出去、拿回回應」。現在只有 reqwest 一個實作，負責 TCP 上的 HTTP/1.1 和 HTTP/2。
  - **reqwest 的型別不出 `net`**：對外只有 `protocol` 的請求和回應，header 用我們自己的型別，錯誤轉成 Chromium 的 net error 碼。之後要換掉或加上其他 transport，例如 sans-I/O 的 HTTP/1.1 或 HTTP/2 實作，`browser` 和 `renderer` 都不用改；sans-I/O 的函式庫也可以由 `NetworkService` thread 上的 tokio socket 和計時器驅動。
- **介面是訊息**：`URLLoader` 的請求帶 URL 和用途（document / style / image），回應帶 status、完整的 header、最終 URL 和 body。Body 一次給完整的；串流等 incremental parsing 時再做。
- **`file:` 也放進 `net`**：原本在 `browser::loader` 裡的讀檔搬過去，document 和子資源走同一條路。`about:blank`、`about:demo` 只用在 navigation，留在 `browser`。
- **沒有 cookie、沒有 HTTP cache**，所以上一頁 / 下一頁一律重新載入。

**Navigation 改成非同步**（對應 `NavigationRequest`）。
- **原本的問題**：`WebContents::navigate` 在 UI thread 上同步呼叫 `loader::load`，網路載入會卡住視窗。
- **改成**：`navigate` 送出請求就返回；回應到了，由 `NetworkService` thread 直接送 `CommitNavigation` 給 renderer。Chromium 的 `NavigationRequest` 會先回到 UI thread 再 commit；我們目前在 UI thread 上沒有要做的事，所以省掉這一趟。P2.4a 的 `NavigationController` 只需要 renderer commit 之後送回的 `DidCommitNavigation`，所以仍然不需要這一趟。
- **後發的 navigation 贏**：回應到達的順序不固定，所以每個 navigation 帶一個遞增的 `navigation_id`，renderer 丟掉比目前顯示的更舊的 commit。例如先 navigate 到一個網址、馬上又 navigate 到 `about:demo`，網址的回應晚到也不會蓋掉 `about:demo`。
- **Redirect 由 `URLLoader` 跟隨**，上限 20 次，和 Chromium 的 `URLRequest` 相同；transport 只回傳 3xx，不自己跟隨（reqwest 設成不跟隨 redirect）。這樣換掉 transport 時 redirect 的行為不變，每一次跳轉也都經過同一個地方，之後可以在這裡擋掉不允許的跳轉，例如從 `https:` 跳到 `file:`。Commit 用最後的 URL。
- **HTTP 4xx / 5xx 照樣 commit 伺服器給的 body**，和 Chrome 一樣。
- **連不上時 commit 錯誤頁**，沿用 P1 的做法，錯誤碼照 Chromium 的 net error：`ERR_NAME_NOT_RESOLVED`、`ERR_CONNECTION_REFUSED`、`ERR_TIMED_OUT`、`ERR_CERT_*` 等。

**Document URL。**
- **原本的問題**：Renderer 不記得 document 的 URL，所以沒辦法解析相對網址。
- **做法**：`FrameView` 記下 document URL，以及 `<base href>` 算出的 base URL，用 `url` crate 解析。
- **放在 `FrameView`、不放在 `Document` 節點上**：這樣 `dom` 的 soundness 範圍不變。之後有 `document.URL` 時，再決定要不要搬到節點上（P3 沒有做它）。

**子資源**（對應 Blink 的 `ResourceFetcher` 加上 `URLLoaderFactory`）。
- **訊息的路線**：Renderer 送 `FetchResource { request_id, url, destination }`，收到 `ResourceResponse { request_id, … }`。
- **不經過 UI thread**：訊息送到 Browser 端現有的 IO thread（`RenderProcessHost` 為每個 renderer 開的那個），由它轉給 `net`。這對應 Chromium 的 renderer 直接拿 `URLLoaderFactory` 向 network service 要資源。
- **同一份文件裡，同一張圖片只要一次**：`FrameView` 的 `ImageTable` 以 URL 為 key，對應 Blink 的 `MemoryCache`，但只活在這份文件裡；同一個 URL 的 `<img>` 共用一份。圖片常重複，所以在 P2.2 加上；stylesheet 很少重複，沒有做。
- **Request id 以 renderer 為單位遞增**：舊 document 的請求在換頁之後才回來時，新的 `FrameView` 認不得它的 id，直接丟掉。
- **讀本機檔案的權限**（對應 `ChildProcessSecurityPolicy`）：renderer 只有在目前的 document 是 `file:` 時，才能要 `file:` 的子資源；否則 IO thread 直接回 `ERR_ACCESS_DENIED`，不交給 `net`。權限由 Browser 在 commit 時依 URL 設定，renderer 改不了。

**`DidFinishLoad`。**
- **什麼時候送**：document parse 完、所有 stylesheet 和圖片都載入完或失敗之後的第一個 frame 送出時，Renderer 送 `DidFinishLoad` 給 Browser，對應 Chromium 的同名訊息。
- **帶著那個 frame 的 token**：renderer 的訊息經 IO thread 到 Browser，frame 則直接送到 Viz，兩條路的先後不固定。所以 `DidFinishLoad` 帶上「第一個顯示載入完成的 frame」的 frame token（畫不出 frame 時，例如 viewport 是空的，是 `None`），等的一方看到 token 不小於它的 frame 被畫出來，就知道像素已經是載入完成的樣子。
- **Headless 和 reftest 等它**：原本 `headless::render` 畫出第一個 frame 就截圖，現在等到 token 對得上的 frame 才截圖。它把 renderer 的訊息和 Viz 的 frame 轉進同一個 channel，依到達順序處理；也回報畫了幾個 frame，測試用它確認 stylesheet 擋住了畫面。

### 2. 編碼

- **Document 的順序照 HTML 的 encoding sniffing algorithm**：
  1. BOM（UTF-8、UTF-16LE / BE）；
  2. HTTP `Content-Type` 的 `charset`；
  3. 預掃前 1024 bytes 的 `<meta charset>` 和 `<meta http-equiv=Content-Type>`；
  4. 預設：整份是合法的 UTF-8 就用 UTF-8，否則用 windows-1252。XHTML 是 XML，預設一律 UTF-8。
- **預設值原本打算一律用 windows-1252**：規範的預設值依地區而定，這是大多數地區的值，也讓測試結果不受機器設定影響。但這樣一來，沒寫 `<meta charset>` 的 UTF-8 頁面（例如自己寫的本機檔案）裡的中文會全部變成亂碼。Chrome 在這裡會跑編碼偵測，這類頁面會被判成 UTF-8；Firefox 對 `file:` 也是先試 UTF-8。所以加上「合法的 UTF-8」這一步；不是 UTF-8 的頁面，結果仍然不受機器設定影響。
- **解碼用 encoding_rs**：Firefox 用的就是它。Chromium 用 ICU，但 encoding_rs 的行為照 WHATWG Encoding 規範。
- **Stylesheet 的順序**：BOM → HTTP `charset` → `@charset` → 引用它的 document 的編碼。
- **取代 `document::markup_for` 原本的做法**：去掉 UTF-8 BOM 之後用 `from_utf8_lossy`。

### 3. `<link rel=stylesheet>`

- **什麼時候開始載入**：parse 完之後，照 tree order 找出 stylesheet 的 `<link>`，用 base URL 解析 `href`，然後發出請求。`media` attribute 先忽略，和 `<style>` 一樣。
- **哪些 `<link>` 算**：`rel` 有 `stylesheet` 而且沒有 `alternate`（替代的 stylesheet 預設不套用）、`type` 是空的或 `text/css`、沒有 `disabled`、`href` 不是空的。`style::stylesheet_links` 負責找，renderer 載入和 cascade 都用它，兩邊的判斷不會不一致。
- **載入完也不一定套用**：狀態碼不是 2xx（Fetch 的 ok status）的不套用；MIME 不是 `text/css` 的也不套用，但 quirks mode 例外，和 Blink 一樣（Blink 另外要求同一個 origin，我們還沒有 origin 的概念）。
- **Cascade 的順序**：`<link>` 和 `<style>` 照它們在 tree 裡的順序排；還沒載入的 `<link>` 先當作空的。
- **會擋住第一次畫面**，對應 Chromium 的 render-blocking stylesheet：
  - 所有 stylesheet 都載入完或失敗之前，不跑 layout 和 paint，避免先畫出沒有樣式的畫面再跳動。
  - 沒有逾時；載入失敗就當作空的，照樣解除阻擋。
- **WPT 的 `/fonts/ahem.css`**：P1 匯入的 WPT 裡有 4 個檔案用了它，這是以 `/` 開頭的網址。從 `file://` 載入會失敗，當成空的，結果和 P1 一樣。之後要是需要，可以讓 reftest harness 把 `/` 對應到 `tests/wpt/`，像 wptserve 那樣。

### 4. Inline box

對應 Blink 的 `InlineItem` 裡的 open tag / close tag，以及 `InlineBoxState`。

- **Box tree**：P1 的 `collect` 把 inline 元素攤平成「文字＋style」，元素本身不留下任何東西。P2.1 在元素的開頭和結尾各加一個 `Open` / `Close` item，帶元素的 `NodeId` 和 style；文字 item 也帶它所在元素的 `NodeId`。
- **Tag 在空白合併裡是透明的**：tag 不產生字元，只記下它在合併後的文字裡的位置。`a <b> b` 留下的是 tag 前面那格空白；`a </b>` 的空白留在元素裡面，和 Blink 相同。被拿掉的空白（內容結尾、強制換行前）不會把後面的 tag 一起帶走。
- **水平方向佔空間**：開頭的 margin + border + padding 寬度，用一個高度為 0 的 parley `InlineBox` 插在元素的第一個字前面；結尾的插在最後一個字後面。百分比照 CSS 2 § 8.3、§ 8.4 以 containing block（IFC 所在 block 的 content box）的寬度解析，每次 `break_lines` 時更新；算 min / max-content 寬度時當成 0。`auto` 的 margin 是 0。
- **parley 的 patch**：2026-09-30 實測，parley 在每個 in-flow 的 `InlineBox` 後面一定標一個斷行點，放不下時也會在方塊前面斷行。所以開頭的方塊會留在上一行、它的第一個字換到下一行；結尾的方塊會單獨換到下一行。0.11.1 和當時的 main 都一樣；parley 的斷行 override 只看相鄰的字元，碰不到方塊。原本的備案「把寬度加到頭尾 glyph 的 advance 上」，parley 沒有公開的 API 能做。
  - **做法**：vendor parley 的 main 到 `third_party/parley`（2026-10-01 改成 fork 的 `machopo` 分支，放在 machopo 旁邊的 `../third_party/parley`，見「已決定的事項」第 9 條），加上 `InlineBox::line_break`：開頭的方塊設成 `KeepWithNext`，結尾的設成 `KeepWithPrevious`，兩者都沒有自己的斷行點。`KeepWithNext` 後面的內容如果以斷行點開始，那個斷行點改標在方塊前面。斷行器和 min / max-content 寬度的計算都照這個規則。
  - **為什麼用 main**：main 在同一時間加了 `InlineBox` 的 `baseline` 和 `vertical_align`（上游 #766），行高也照 CSS 2 §10.8 算，P2.2 的 `<img>` 需要這兩點（見第 5 節）。
  - **上游**：上游 Blitz 的需求清單（#208）把「inline span 的 margin / border / padding」列為還沒做。這些修改還沒送上游；要送的話先寫草稿審核。來源、`machopo` 分支上的 commit 和更新方式見 `../third_party/parley/README.machopo.md`。
  - **跨行的情況**：會拆開的只有文字本身的斷行點；`<a><b>x` 這種連續的開頭、空的元素、開頭後面緊接著圖片，都會和後面的內容待在同一行，`layout` 的 `parley_inline_box` 測試逐一驗證。
- **垂直方向不佔空間**：padding 和 border 照樣畫出來，但不影響行高（CSS 2 §10.6.1）。所以它們可以蓋到上一行，reftest I4 驗證這一點。
  - **邊界的方塊也不算進行高**：parley 會把 in-flow 的 `InlineBox` 算進行高，高度是 0 的方塊等於在 baseline 上下各佔 0。`line-height` 比字型小時，文字的 descent 加上 half-leading 是負的，這個 0 反而把行框撐大。例如 50px 的字、`line-height: 10px`，一行變成 24px。P2 擴充 WPT 時，`line-height-125` 抓到這個 bug。所以加了第二個 patch：`KeepWithNext` 和 `KeepWithPrevious` 的方塊只佔寬度，不算進行高，和 out-of-flow 的方塊一樣；inline 元素在這一行的高度只來自它的內容，和 CSS 2 §10.8 相同。
- **跨行**：一個 inline 元素在每一行都產生一個 `InlineBoxFragment`，邊界照 `box-decoration-break: slice`：左邊的 border 和 padding 只在第一段，右邊的只在最後一段。
- **被 block 拆開**：`<span>a<div>b</div>c</span>` 的 span 分在兩個 anonymous block 裡，第二段只有 `Close` 沒有 `Open`。這種元素當成在那段內容開始前就已經開始（外層的在外），所以第一段只有開頭的邊界、最後一段只有結尾的，和跨行時一樣。
- **Fragment**：
  - `LineFragment` 除了文字，也列出這一行的 `InlineBoxFragment`：node、style、border box 在這一行的 rect、這一行要畫的 border（切片時開頭或結尾那一邊是 0），以及它要畫在哪一個 text run 之前。
  - **水平範圍**：從開頭的方塊（扣掉開頭的 margin）到結尾的方塊（扣掉結尾的 margin）；元素不在這一行開始或結束時，那一側改用它在這一行的內容。
  - **垂直範圍**：字型的 content area（baseline 上下的 ascent 和 descent）加上上下的 padding 和 border。字型的 metrics 優先取元素自己在這一行的文字，沒有的話取它裡面的文字，都沒有時填滿整個行框。
  - `TextFragment` 加上所在元素的 `NodeId`：P1 沒有，paint 都用 containing block 的 node 當 client。Hit testing 要靠它才知道點到的是哪一個 `<a>`。
- **行尾拿掉的空白不屬於任何 box，也沒有裝飾**：可合併的空白在行尾換行時要拿掉（css-text 的 phase II），所以它不算進 inline box 的範圍，也不畫底線。P1 把這種空白交給 parley hang，但裝飾線照樣畫到它下面（P1 時的已知限制，P2.1 修掉）；inline box 的右緣要算對，本來就得排除它，所以一起修。reftest I6 驗證。
- **Paint 順序（CSS 2 Appendix E 的步驟 7.2.1）**：inline box 的 background 和 border 不在「block 的 background」那一輪畫，而是在行的那一輪，每一行照 tree order 交錯：元素的 background 和 border 畫在它在這一行的第一段文字之前，接著是它的文字和子元素。所以內層的 background 蓋在外層上面，也蓋在外層排在它前面的文字上面；從上一行延續下來的元素最先畫。行依序畫，後面一行的 padding 伸到前一行時會蓋住前一行的文字（reftest I4）。

### 5. 圖片

**載入與保存。**
- **什麼時候載入**：parse 完之後，每個有 `src` 的 `<img>` 用 base URL 解析 `src`，發 `FetchResource`（image）。同一份文件裡同一個 URL 只要一次，幾個 `<img>` 共用。
- **收到之後先讀 header**：`raster::image_size` 用 Skia 的 `Codec` 讀出尺寸，不用整張解碼。狀態碼不是 2xx、或讀不出尺寸（不是 PNG、JPEG、GIF）的，算載入失敗，和 Chromium 一樣不管 body 是什麼。
- **圖片不放進 GC heap**：
  - `FrameView` 持有一張 URL → 狀態（載入中 / 成功 / 失敗）的表，以及 `<img>` → URL；成功的狀態帶著 `gfx::ImageData`（`Arc` 共用的原始 bytes 和一個 id）和尺寸，對應 Blink 的 `ImageResourceContent`。
  - Layout 透過 `layout::Images` 查 `<img>` 的圖片，那張表就是它的實作，所以 `dom` 和 `ComputedStyle` 都不用改。
  - 這樣 P1 預留的「`ComputedStyle` 持有圖片時要改成 GC 物件」可以再延後，等到 `background-image` 才需要決定。
- **圖片到了之後**：box tree 要重建（`<img>` 的尺寸在 box tree 建立時就決定了），但不必重算 style，所以 `FrameView` 多一個 `box_tree_dirty`。
- **`DidFinishLoad` 也等圖片**，但圖片不擋住畫面：先畫出來，圖片到了再重畫。`DidFinishLoad` 另外帶上載入失敗的子資源清單，Browser 記進 log，headless 的 `Frame` 也回報它（`sites` 測試用它確認快照的子資源都載入成功）。

**Layout**（CSS 2 §10.3.2、§10.6.2，對應 Blink 的 `LayoutImage`，在 `layout::replaced`）。
- **`width` / `height` attribute 是 presentational hint**（`style::hints`）：照 HTML 的「dimension value」規則解析成 px 或 %，以 author 層級、specificity 0、排在所有 author 規則之前的宣告加進 cascade，所以任何 author 規則和 `style` attribute 都蓋得過它。
- **尺寸**：
  - 兩邊都有指定就照用；只指定一邊時，另一邊照長寬比算；都沒指定時，用圖片本身的尺寸。
  - 百分比的寬度以 containing block 的寬度解析；百分比的高度當成 `auto`（還沒有 containing block 的高度）。
  - `box-sizing: border-box` 的尺寸先扣掉 padding 和 border。
  - `min-*` / `max-*` 兩個軸各自夾值，沒有 CSS 2 §10.4 那張保持長寬比的表。
  - 還沒載入或載入失敗的圖片，自然尺寸是 0×0：只有 style（包括 attribute）給的尺寸會佔空間。不畫破圖的圖示，也不顯示 `alt`。
- **Inline 的 `<img>`**：當成 parley 的 `InlineBox`（`Auto`，兩邊都能斷行），大小是 margin box。預設的 `vertical-align: baseline` 讓 margin box 的底邊對齊 baseline（CSS 2 §10.8.1）。它在空白合併裡算內容：前後的空白不會合併在一起，只有一張圖片的 block 也會產生一行。包著它的 inline 元素，水平範圍會涵蓋它的 margin box。2026-09-30 實測 parley 的 main：方塊的底邊對齊 baseline，行框也照 CSS 包住方塊和文字在 baseline 下面的部分（30px 的方塊放在 20px 的 Ahem 文字裡，行高 34px）；0.11.1 的行高是 30px，方塊還超出行框上緣 2px，所以改用 main（見第 4 節）。main 也有 `InlineBox::vertical_align`，之後支援 `vertical-align` 時直接用。
- **`display: block` 的 `<img>`**：taffy 的 leaf。原本打算用 measure function 回傳算出的尺寸，但 taffy 的 block layout 會把 `auto` 寬度的子元素撐滿 containing block，measure 拿到的寬度已經是撐開後的。所以改成把尺寸直接寫進它的 taffy style：px 的尺寸換成 content box；百分比的寬度保留成百分比（這時不處理 `box-sizing`）；高度是 `auto` 而有長寬比時，交給 taffy 的 `aspect_ratio`。
- **Fragment**：inline 的圖片是 `LineFragment::replaced` 裡的 `ReplacedFragment`（border box、border、padding、圖片），block 的圖片是 `BoxFragment::image`。

**Paint 和 raster。**
- **新的 op**：`PaintOp::DrawImage { image, dst }`，把整張圖縮放到 `dst`。`image` 是 `gfx::ImageData`，和 `gfx::FontData` 同一種做法。原本規劃有 `src_rect`，但還沒有 `object-fit` 之類要裁切的情況，所以先不加。
- **Paint 順序**：inline 的圖片和 inline box 一樣照 tree order 夾在 text run 之間，畫它自己的 background、border，再把圖片畫進 content box；在同一個位置上，inline box 先畫，圖片後畫（元素的 box 在它裡面的東西之前）。Block 的圖片在行的那一輪、照 tree order 畫（CSS 2 Appendix E 7.1），它的 background 和 border 照舊在 block 那一輪。
- **解碼在 raster 端**：以 id 快取 `sk::Image::from_encoded`，而這個函式本身就是用到時才解碼。這對應 Chromium 的延後解碼：`PaintImage` 在 display list 裡只是參照，由 cc 的 `ImageDecodeCache` 在 raster 時解碼。快取持有圖片 bytes 的 weak 參照：document 和 display list 都不再用某張圖片時，它的快取在下一張新圖片進來時就被清掉，不會隨著瀏覽一直累積。
- **縮放用線性取樣**，縮小時加上 mipmap，對應 Chromium 預設的 `image-rendering: auto`。Reftest 用單一顏色的圖片，縮放不影響結果。

**格式**：現在的 Skia prebuilt 已經能解 PNG、JPEG、GIF（只有第一格），2026-09-30 實測過。WebP 不做，原因見「已決定的事項」；SVG 不做。

### 6. 捲動

**Viewport 捲動在 compositor 裡做，不重新 paint。**
- **原本的問題**：
  - `LayerTreeHostImpl::prepare_tiles` 只 raster `(0, 0)` 起一個 viewport 大小的 tile；
  - 整份文件是一個 layer，bounds 等於文件大小，所以每捲一次都要整份重新 commit、重新 raster。
- **做法**：
  - `LayerTreeHost::set_root_scroll_offset` 設定 root layer 的捲動位移（CSS px），對應 cc 的 scroll tree 裡 root scroll layer 的 scroll offset。它不 commit，下一次 `composite` 就用手上的 tile 畫。
  - `LayerTreeHostImpl` 把位移換成 physical pixel 並取整，讓 tile 落在像素格上；`generate_compositor_frame` 把位移套到 tile 的 quad 上。
  - `prepare_tiles` raster 和 interest rect 相交、還沒有 resource 的 tile，interest rect 是看得到的範圍往四周各多一個 viewport（取寬、高中較大的），對應 cc 的 interest rect；離得更遠的 tile 釋放掉，所以長文件捲到底也不會留著整份的 bitmap。
  - Renderer 只在 display list 換了一個新的（`Arc::ptr_eq`）時才換 root layer；背景色沒變也不 commit。這兩條讓「只有 viewport 捲動」的 frame 完全不 commit、不 raster。
- **Commit 照舊丟掉所有 tile**：還沒有 invalidation 的追蹤，P4 再做。
- **P2 的 compositor 還在 renderer main thread 上**，P4 才拆出 cc thread；到那時，這個位移就是 compositor thread 自己能處理的捲動。

**`overflow: auto` / `scroll` 的捲動容器**（對應 Blink 的 `PaintLayerScrollableArea`）。
- **Style**：`overflow` 接受 `auto` 和 `scroll`，`clip` 當成 `hidden`，舊的別名 `overlay` 當成 `auto`；照 css-overflow，另一軸不是 `visible` 時，`visible` 變成 `auto`。`hidden` 也是捲動容器，只是使用者不能捲（`Overflow::user_scrollable`）。
- **Layout**：taffy 本來就把它們當成 scroll container，也會建立 BFC。`layout::scrollable_overflow` 算出可以捲的範圍：padding box，加上內容超出的部分和結尾的 padding。
- **Property trees**：
  - 新增 **scroll tree**：`ScrollNode { parent, element, container, transform, scroll_translation, contents, user_scrollable_x, user_scrollable_y }`，對應 Blink 的 `ScrollPaintPropertyNode`。`container` 是 padding box，在 `transform`（容器外面的空間）裡；`scroll_translation` 是內容的空間。
  - 每個捲動容器除了 clip，還有一個 scroll translation 的 transform node，位移取整到 CSS px。`overflow` 傳給 viewport 的那個元素沒有（見下面）。
- **捲動位移**：`renderer::scroll::ScrollState` 記住 viewport 的位移和每個容器的位移（以 `NodeId`）。容器捲動時重跑 pre-paint 和 paint，不重跑 layout，然後 commit。
  - 這一步會重新 raster 看得到的 tile。巢狀捲動容器的內容不多，P2 先接受這個成本，P4 再把捲動容器拆成獨立的 layer。
- **Layout 之後**，把所有位移夾回合法範圍；已經不是捲動容器的元素，位移丟掉。Viewport 大小改變也走這條路。
- **Root 和 `<body>` 的 `overflow`**：照 css-overflow 傳給 viewport。先看 root，root 兩軸都是 `visible` 時改看 `<body>`；是 `hidden` 時，viewport 不能用滾輪和鍵盤捲動，但 `#fragment` 照樣可以捲。
  - **在 layout 建 box tree 時決定**：`BoxTree::viewport_overflow` 記下傳給 viewport 的值，傳出去的那個元素自己的 used value 改成 `visible`，所以 paint、捲動、文件大小和 taffy 看到的都一致：它不 clip、不是捲動容器，它超出的內容也算進文件大小。
  - **原本的做法**是在 pre-paint 和捲動裡寫死「root 和 `<body>` 不 clip」。這樣 root 不是 `visible` 時，`<body>` 也不會 clip 自己的內容；擴充 WPT 時，`overflow-body-propagation-012` 抓到這個 bug。

**Input 怎麼變成捲動。**
- **訊息**：`protocol::input` 在這一步加入，有滾輪（像素或行）和鍵盤；`shell` 把 winit 的事件轉成它們，由 `WebContents::forward_input_event` 用 `RendererMsg::HandleInputEvent` 送給 renderer（P4.1 第 3a 段起改成先送到 renderer 的 compositor thread，見 `P4.md`）。座標是網頁區域的 CSS px。
- **滾輪和觸控板**：
  - 用 hit testing（第 7 節）找出游標底下最內層的容器，能捲的軸先由它捲，捲不完的部分交給外層，最後是 viewport。這對應 Chromium 的 scroll chaining，但沒有 latching（一次手勢固定捲同一個容器）。P2.3 原本只看各容器的 padding box，被外層 clip 掉的部分也算；P2.4a 改用 hit testing 之後，看的是畫面上真的在那裡的東西。
  - 以行為單位的滾輪一行算 40px，和 Chromium 的 `kPixelsPerLineStep` 相同。
- **鍵盤**（給使用者的完整清單在 `crates/shell/README.md` 的「鍵盤和滑鼠」）：
  - 方向鍵一次 40px；
  - Space、Shift+Space、PageUp、PageDown 一次捲 viewport 高度的 87.5%，照 Chromium 的 `kMinFractionToStepWhenPaging`；
  - Home、End 捲到頭尾；
  - P2 只捲 viewport，沒有 focus 的概念。
- **捲動之後**：只動了 viewport 時，renderer 只把新的位移交給 compositor；動了容器才重新 paint。
- **沒有捲軸**：不畫，也不佔 layout 的寬度，像 macOS 的 overlay 捲軸。

**`#fragment` 捲到目標。**
- **找目標**：先找 `id` 相同的元素，再找 `name` 相同的 `<a>`；都找不到時，percent-decode 之後再找一次，照 HTML 的「indicated part of the document」。
- **捲動**：從內到外，每一層捲動容器都捲到讓目標的頂端對齊可視範圍的頂端，最後是 viewport，也就是 `scrollIntoView` 的 `block: start`，再夾回合法範圍。水平方向只在目標不在可視範圍裡時才捲。和使用者的捲動不同，`overflow: hidden` 的容器也會捲。
- **什麼時候捲**：載入完成（所有子資源都到了或失敗了）的那一次 lifecycle update，所以 `DidFinishLoad` 回報的 frame 已經捲好了。圖片還沒到之前，目標的位置會變。
- **留著 fragment tree**：`FrameView` 保留最後一次的 fragment tree，捲動和夾值都要用它，P2.4a 的 hit testing 也用它。

### 7. Input、hit testing 和連結導航

**Input 的訊息**（對應 Chromium 的 `WebInputEvent`，以及 `RenderWidgetHostImpl::ForwardMouseEvent`）。
- **`protocol::input`**：P2.3 的滾輪和鍵盤，加上滑鼠移動、按下、放開；按鍵只有左、中、右。座標用網頁區域的 CSS px。
- **Browser 端**：`shell` 把 winit 的事件轉成這些型別送給 renderer。滑鼠的上一頁 / 下一頁鍵由 Browser 直接走歷史紀錄，不送給 renderer，和 Chrome 相同。P2.4b 有了工具列之後，工具列上的事件交給工具列，其他的扣掉工具列的高度。
- **Renderer 端**：P2 由 main thread 處理，P4 改成先送 compositor thread。

**Hit testing**（對應 Blink 的 `PaintLayer::HitTest` 和 `BoxFragmentPainter::NodeAtPoint`）。
- **放在 `paint` crate**：Blink 的 fragment hit testing 也在 `core/paint`，和 paint 共用走訪順序和 property trees。
- **輸入**：文件座標，也就是網頁座標加上 viewport 的捲動位移。
- **走訪**：照 paint 的反向順序走訪 fragment tree：
  - 子 stacking context 從最後一個開始，再來是行，最後是 block 的 background；
  - 一行裡的 text run、圖片和 inline box 照 paint 順序反過來，所以巢狀的 inline 元素先找到內層的；
  - 點用 pre-paint 的 property trees 換到每個 fragment 的 transform 空間（transform 的反矩陣，包括捲動容器的 scroll translation），還要落在 clip chain 的每個 clip 裡。
- **Text run 的範圍**：它的 advance，乘上字型的 ascent 加 descent，和 LayoutNG 的 text fragment 相同；行框裡沒有字的地方算 block 的。
- **輸出**：`HitTestResult { node, scroll }`。
  - `node` 是最內層的元素：文字是它所屬的元素，anonymous block 是它外面的元素；只有 canvas 的地方是 `None`。
  - `scroll` 是它所在的最內層捲動容器，點到的 box 本身是捲動容器時就是它；滾輪從這裡開始 chaining（第 6 節）。
  - Pre-paint 為每個 fragment 記下這個捲動容器（`FragmentProperties::scroll`）。
- **用最後一次 paint 的結果**：保留下來的 fragment tree 和 property trees，也就是使用者看到的畫面。

**點連結。**
- **判定**：主按鍵在同一個連結上按下又放開，才算點擊；中鍵和右鍵不算。Chromium 是在按下和放開的共同祖先上觸發 `click`，對連結來說結果相同。P3.4 有了事件之後改成和 Chromium 一樣：`click` 送到共同祖先，連結的導航是 `<a>` 的 activation behavior（`P3.md` 第 7 節）。
- **連結**：從 hit test 的元素往上找最近的、有 `href` 的 `<a>`。
- **網址**：用 base URL 解析 `href`。`javascript:` 不做事，P3 才有 script。
- **同一份文件內的 `#fragment`**：
  - 判定照 HTML：新網址有 fragment，而且去掉 fragment 之後和文件的網址相同。
  - 由 renderer 記下新的 fragment，在下一個 frame 捲過去，再送 `DidCommitSameDocumentNavigation`，Browser 加一筆歷史紀錄，和 Chromium 相同。
  - `#`，以及沒有對應元素的 `#top`，捲到文件頂端（HTML 的 "top of the document"）。
- **其他網址**：送 `RendererHostMsg::OpenUrl`，由 Browser 檢查之後開始新的 navigation，對應 Chromium renderer 發起的 `BeginNavigation`：
  - 只有 renderer 正在顯示本機檔案時，才能開本機檔案，和子資源同一條規則（`ChildProcessSecurityPolicy::CanRequestURL`）；
  - 只開 Browser 會載入的 scheme（`http`、`https`、`file`、`about`）。其他的（`mailto:`）Chromium 交給系統處理，P2 不做，只記 log。
- **`target=_blank` 和按著修飾鍵的點擊**：P2 只有一個分頁，都在同一個分頁開。
- **游標**：
  - 滑鼠移動時 hit test，進出連結時才送 `SetCursor(Hand)` 或 `SetCursor(Pointer)`，對應 Chromium 的 `WidgetHost::SetCursor`。名字照 `ui::mojom::CursorType`：`Pointer` 是箭頭。
  - Commit 新文件時重設成箭頭，因為游標可能停在舊文件的連結上。
  - `shell` 換成 winit 對應的 `CursorIcon`。

**歷史紀錄**（對應 `NavigationController` 和 `NavigationEntry`）。
- **放在 `browser` crate**：一串 entry（URL、標題）和目前的位置。
- **每個 navigation 開始時，記下它 commit 時要做的事**：
  - 新的 entry：輸入網址、點連結；放在目前的 entry 後面，丟掉更前面的；
  - 回到某個 index：上一頁 / 下一頁；
  - 重新整理目前的 entry。
  - Redirect 之後，entry 的網址改成最後的網址。
- **Commit 時**，比這個 navigation 早開始的都不會再 commit（renderer 丟掉比它顯示的更舊的 commit），一起清掉。
- **上一頁 / 下一頁從哪裡算**：有進行中的歷史 navigation 時，從它要去的 entry 算起，所以快速按兩次上一頁會回兩頁，對應 Chromium 的 `GetCurrentEntryIndex`。
- **快捷鍵**（工具列的按鈕在 P2.4b；給使用者的完整清單在 `crates/shell/README.md` 的「鍵盤和滑鼠」）：
  - macOS：Cmd+[ / Cmd+] 和 Cmd+← / Cmd+→，Cmd+R；
  - 其他平台：Alt+← / Alt+→，Ctrl+R；
  - 各平台都有 F5 和滑鼠的上一頁 / 下一頁鍵；
  - 按著 Cmd、Ctrl 或 Alt 的其他按鍵不送給網頁。
- **上一頁、下一頁、重新整理都重新載入那個 URL**，同一份文件裡的 entry 之間也是。沒有 back-forward cache，不恢復捲動位置，見「範圍」。

### 8. 工具列和網址列

**這個原生工具列是過渡**：之後要讓 UI 能用 HTML / CSS 自訂（見「已決定的事項」第 2 條），到時工具列本身會換掉，留下的是 embedding 的基礎。所以過渡的部分集中在 `shell`，方便整塊拿掉：工具列本身在 `toolbar.rs` 和 `omnibox.rs`，網址的補全在 `url_fixup.rs`；`browser_view.rs` 的 compositor 和 `SurfaceLayer` 會留下，工具列的那一部分（把它畫成 root layer、分配給它的 input）要跟著換。

**Browser 自己也是一個 compositor client**（對應 Chromium 的 `ui::Compositor`，它包著一個 `cc::LayerTreeHost`）。
- **分工**：
  - Browser 端有自己的 `compositor::LayerTreeHost`，frame sink 是 `BROWSER_FRAME_SINK`（client 0），成為視窗的 `Display` 的 root。
  - 工具列是它的 root `PictureLayer`；網頁是新的 `SurfaceLayer`（對應 `cc::SurfaceLayer`），放在工具列下面，畫成一個 `SurfaceDrawQuad`。
  - Tiling、raster 和 frame sink 都沿用 renderer 那一套，不另寫一條手動組 `CompositorFrame` 的路。
  - 之後換成 HTML UI 時，只是工具列的 `PictureLayer` 換成另一個嵌入 UI renderer 的 `SurfaceLayer`，和 Chromium 用 `views::WebView` 嵌入 WebUI 相同。
- **這和 Chromium 的架構相同**：網頁的 frame 不直接上螢幕，而是被 Browser 的 frame 嵌入。網頁有新 frame（例如捲動）時，Browser 什麼都不用做，由 Viz 把新的 frame 放進去。
- **Browser 只在有變化時才送 frame**：工具列重畫、視窗大小改變、網頁的 surface 換了。`SurfaceLayer` 沒變時不 commit。
- **Headless 不變**：root 直接是分頁的 sink，所以 reftest 不受影響。

**Viz 的合成**（`SurfaceAggregator`）。
- **`Material::Surface { surface_id, default_background_color }`**，對應 `viz::SurfaceDrawQuad`。
- **合成的做法**：複製 root frame 的 quad；遇到 `SurfaceDrawQuad`，就在它的位置換成被嵌入的 surface 的 quad：
  - 移到這個 quad 的左上角，clip 到它的範圍裡；
  - 後面墊一個那個 surface 的背景色（`root_background_color`）的 quad；
  - 被嵌入的 surface 還沒有 frame 時，只畫 `default_background_color`；
  - 可以一層嵌一層；嵌到自己的時候停下來。
- **位移直接算進 quad 和 clip 的座標**：原本規劃在 `SharedQuadState` 加上位移，但 `DirectRenderer` 拿到的 quad 本來就是 target 空間的座標，所以合成時直接移過去，不用改 `SharedQuadState`。完整的 `quad_to_target_transform` 等 P4。
- **用那個 sink 最新的 frame**，不管它的 `LocalSurfaceId`。視窗大小改變的那一下，網頁的 frame 可能還是舊的大小，先照樣顯示，多出來的被 clip 掉，相當於 Chromium 的 fallback surface。
- **`ResourceId` 重新編號**：不同 client 的 id 會重複，所以每個 `(sink, id)` 對應到一個合成後的 id，對應 Chromium 的 `DisplayResourceProvider` 從 child 到 parent 的對應。只要 client 還在用那個 resource，對應就不變，所以 `WgpuRenderer` 上傳過的 texture 可以繼續用；不再用的對應就忘掉。
- **`Display` 的重畫**：記下上一次合成時嵌入了哪些 sink；root 或其中任何一個送來新 frame，就要重畫。

**工具列的內容**（對應 `ToolbarView` 和 `LocationBarView`）。
- **排版**：40 CSS px 高；上一頁、下一頁、重新整理三個按鈕，右邊是網址輸入框，佔掉剩下的寬度。
- **按鈕**：
  - 圖示用 `DrawPath` 畫的多邊形，不用圖示檔：上一頁、下一頁是箭頭，重新整理是四分之三圈的環加上箭頭；
  - 不能用的是淺灰色，滑鼠移上去時有圓形的底色；
  - 主按鍵在同一個按鈕上按下又放開才算按。
- **畫的方式**：用 `compositor_paint` 的 op 組成 display list，放進工具列的 `PictureLayer`。
- **文字**：在 `shell` 裡用 parley 排版，用系統字型（`--test-fonts` 時是 Lato）；對應 Chromium 的 Views 用 `gfx::RenderText`，和 Blink 的文字排版分開。把 parley 的結果轉成 `gfx::FontData` 的那段（`layout` 裡只有十幾行）在 `shell` 另寫一份，不搬到 `gfx`（`gfx` 會因此依賴 parley 和 fontique），也不讓 `shell` 依賴 `layout`；它隨著工具列一起是過渡的，不值得開新的 crate。
- **`BrowserView`**（對應 Chromium 的 `BrowserView`）：工具列、Browser 的 compositor 和 input 的分配都在這裡，和 winit 分開，所以測試可以直接呼叫它；`window.rs` 只負責把 winit 的事件轉給它，再把游標、標題和 IME 的狀態套到視窗上。
- **Input 的分配**：
  - 游標在工具列裡的，交給工具列；其他的扣掉工具列的高度送給網頁。主按鍵按下的那一邊，會收到之後的移動和放開。
  - 網址輸入框有 focus 時，鍵盤交給它；點網頁會拿走 focus，網址還原。
  - 游標：輸入框上是 I 形，按鈕上是箭頭，網頁上照 renderer 的 `SetCursor`。
- **網頁的 viewport** 是視窗扣掉工具列。工具列的高度取整到 physical pixel，網頁從整數的像素開始。

**網址輸入框**（對應 `OmniboxView`）。
- **編輯用 parley 的 `PlainEditor`**（vendor 的 main 裡就有）：游標、選取、以字或詞刪除和移動、IME 組字，都不用自己寫。
- **Focus**：
  - Cmd+L / Ctrl+L、Alt+D（macOS 以外）、F6，或在沒有 focus 時點一下，會全選；之後再點才放游標，拖曳可以選取。
  - Esc 還原成目前的網址。
  - 有 focus 時，網頁換了網址也不蓋掉正在打的字；失去 focus 時才顯示新的網址。
- **編輯**（按鍵的完整清單在 `crates/shell/README.md` 的「鍵盤和滑鼠」）：
  - 插入字元、Backspace、Delete、左右鍵、Home、End；macOS 上 Option 是以詞為單位、Cmd 是到行頭行尾，其他平台 Ctrl 是以詞為單位。
  - 有 focus 時，Cmd+← / Cmd+→ 在 macOS 上是移動游標，不是上一頁、下一頁。
  - IME：組字中的文字直接顯示在輸入框裡，加上底線（winit 的 `Ime::Preedit`），送出的文字（`Ime::Commit`）插入；候選字視窗放在游標旁邊（`set_ime_cursor_area`）。只有輸入框有 focus 時才打開 IME，其他時候按鍵照原樣送給網頁。原本規劃組字中的文字先不顯示，`PlainEditor` 已經支援，所以一起做了。
  - 複製、剪下、貼上（Cmd / Ctrl + C、X、V）和全選（Cmd / Ctrl + A）。winit 沒有剪貼簿，所以用 `arboard`（MIT / Apache-2.0，最低 Rust 1.71；只用文字，關掉預設的 `image-data`），對應 Chromium 的 `ui::Clipboard`。貼上時把換行換成空白，和 Chrome 的網址列一樣。
  - 文字比輸入框長時，橫向捲動，讓游標一直看得到。
- **Enter 導航**，網址的補全規則（`url_fixup.rs`，對應 `url_formatter::FixupURL`）：
  - 有 Browser 會載入的 scheme（`http`、`https`、`file`、`about`）的照用；
  - 存在的本機路徑（以 `/` 或 `.` 開頭，或含有路徑分隔字元）轉成 `file://`，相對路徑照目前的目錄；
  - 其他的當成主機名稱加路徑：`localhost` 和 IP 位址補上 `http://`（本機的 server 通常沒有 TLS），其他的補上 `https://`。像 `localhost:8000` 這種會被解析成 scheme 是 `localhost` 的網址，所以要先排除。
  - 不是主機名稱的（例如有空白），結果是 `ERR_NAME_NOT_RESOLVED`，沒有搜尋。
- **Commit 之後**，輸入框顯示新的網址；視窗標題是網頁的標題，沒有標題時顯示網址。

### 9. 測試

- **網路的整合測試不連外網**：
  - 本機的 HTTP server 是 `net::test_server`，對應 Chromium 的 `EmbeddedTestServer`：只用標準函式庫，可以設定每個路徑的狀態碼、header、body 和延遲，也記下收到的每個請求。`net`、`browser` 和 `shell` 的測試都用它。
  - `net` 測 redirect、狀態碼、header、`charset`、連線失敗；`browser` 測 navigation；`shell` 的 `network` 測只在 HTTP 上才看得到的 stylesheet 規則、render-blocking 和讀本機檔案的權限。
  - `browser/tests/navigation.rs` 原本斷言 `https://example.com/` 是 `ERR_UNKNOWN_URL_SCHEME`，改成連一個沒有在聽的本機 port（`ERR_CONNECTION_REFUSED`）。
- **Reftest harness**：
  - 等 `DidFinishLoad` 之後的 frame 再比對（見第 1 節）。
  - 自己的 reftest 可以用 `<meta name="machopo-fragment" content="target">`，讓 runner 載入 `test.html#target`，用來測 `#fragment` 捲動。WPT 的捲動測試都要 JS 和捲動的 API（`scrollTop`、`scrollTo` 等），P3 有了 JS 但還沒有這些 API，所以還不能匯入。這是我們自己的擴充，寫在 `tests/reftests/README.md`。
- **Input 的端到端測試**：`shell::headless::render_after_input` 等頁面載入完、畫好之後送出一串 input，再回傳之後的下一個 frame（P4.1 第 3a 段起改成回傳 ack 帶的 frame，見 `P4.md`）；input 開始了新的 navigation（點連結）時，等那一頁載入完的 frame。`Frame` 帶著顯示的網址。
  - **要等 renderer 回 ack**：renderer 處理完每個 input 都送 `InputEventAck`，對應 Chromium `HandleInputEvent` 的 callback。Input 引起的訊息（`DidCommitSameDocumentNavigation`、`OpenUrl`）和 ack 走同一條 channel、排在 ack 前面，但 frame 走另一條。原本只等 frame，機器忙的時候 frame 會先到，拿到捲好了、網址卻還沒更新的結果；2026-10-01 全部測試一起跑時，`network` 的兩個 `#fragment` 測試因此偶爾失敗。改成等收齊 ack 再等 frame（P4.1 第 3a 段起再改成等 ack 帶的 frame）。
  - `shell` 的 `network` 用它測滾輪、鍵盤的捲動和點連結；`sites` 用它在 CERN 和 Gutenberg 的快照上點連結。
  - 點擊的判定、歷史紀錄、Browser 的檢查和游標，在 `browser` 的 `navigation` 測試裡直接看 renderer 送回的訊息，不用畫面。
- **視窗的端到端測試**（`shell/tests/browser_view.rs`）：真的分頁加上 `BrowserView`，兩邊的 frame 經過 Viz 合成到 `SoftwareRenderer`，用 `window.rs` 會做的呼叫代替 winit 的事件。測工具列和網頁的位置、網頁單獨送的 frame、點網頁、在網址列打字和貼上、按鈕、游標。
- **單元測試**：
  - 編碼的判定（encoding sniffing）；
  - compositor 的 tile 挑選和 quad 位移；
  - 滾輪位移的夾值和 scroll chaining；
  - hit testing（transform、clip、捲動位移、paint 的順序）；
  - `NavigationController`；
  - 快捷鍵在各平台的對應；
  - `SurfaceAggregator` 的嵌入、clip、背景和 `ResourceId` 重新編號；
  - compositor 的 `SurfaceLayer`；
  - 網址輸入框的編輯（各平台的快捷鍵、剪貼簿、IME）和網址的補全；
  - 工具列按鈕的判定。
- **Mutation test**：照 `docs/README.md`，每一批 reftest 和每個新測試都要弄壞實作確認會失敗，結果記在 `PROGRESS.md`。

## 已決定的事項

2026-09-30 確認：

1. **驗收網站**：上面的三個離線快照加上 text.npr.org 的手動檢查。
2. **網址列在 Browser 端畫**：像 Chromium 的 Views，工具列是 Browser 自己的 compositor frame，網頁以 `SurfaceDrawQuad` 嵌入。另一個選擇是用自己的 renderer 畫（像 WebUI），但那需要 JS 和事件分派（P3）、`<input>` 的編輯（caret、選取、IME，「完整的 form 行為」在 MVP 範圍外），以及讓 UI 頁面呼叫 Browser 的特權通道。
   - **2026-10-01 補充**：長期目標是讓 UI 能用 HTML / CSS 自訂，時間在 MVP 之後。P2 的原生工具列因此當成過渡（見第 8 節）：Browser 端的 `LayerTreeHost` 和 `SurfaceLayer` 之後直接沿用，工具列本身到時換掉。考慮過、沒選的：P2 就做成沒有 JS 的 HTML 工具列，按鈕靠 hit test 找 `data-command`、網址輸入框用原生的疊上去，多約 1 週，而且這些非標準的機制等有了 JS 又要換掉；P2 不做網址列，則少了驗收的一項，`<input>` 的編輯又在 MVP 範圍外，等的時間不確定。
3. **延到之後**：web font（`@font-face`）、incremental parsing、`@media`（繼續整段忽略，對桌面尺寸影響不大）、table layout、float、list 的項目符號、捲軸的外觀。
4. **編碼放進 P2**：真實網站馬上會碰到，而且範圍不大。
5. **時程照這份規劃的 5.5 週**，不砍範圍；`MVP.md` 的 P2 那一列和總時程跟著更新。
6. **網址列支援複製和貼上**，用 `arboard`（見第 8 節）。
7. **P2 不支援 WebP。**
   - skia-safe 的 prebuilt 是依 feature 組合發布的。2026-09-30 查了 0.153.3 的 release：現在用的組合（`jpegd-jpege-pdf`）在 macOS、Windows、Linux 都有，但**只多開 `webp-decode` 的組合沒有 prebuilt**，Skia 會改從原始碼編譯，要裝 Python、ninja、LLVM，第一次要編好幾十分鐘。
   - 有 WebP 的 prebuilt 都綁著一大組 feature，而且各平台不一樣：macOS 多了 `svg`、`textlayout`；Windows 還多了 `ganesh`（Skia 的 GPU backend）和 `vulkan`。
   - 驗收網站都沒有用 WebP，所以先不做；有 WebP 的網站上，那些圖片會是空白。
   - **之後需要時**：WebP 不經過 Skia，用純 Rust 的 `image-webp`（image-rs 維護，MIT / Apache-2.0，最低 Rust 1.80.1）在 raster 端解成像素，再交給 Skia。代價是解碼器和 Chromium 不同（Chromium 用 libwebp）。
8. **Gutenberg 的快照全部放進 repo。** 2026-09-30 量過：HTML 220 KB，37 個圖片檔（42 個 `<img>` 用到）共 1.31 MB（最大一張 81 KB），合計約 1.5 MB；當時 `tests/wpt/` 是 836 KB、測試字型 660 KB、整個 `.git` 1.1 MB。這些檔案不會再改，git 歷史不會繼續長大；只取一部分的話，圖片數量和文件長度都會變少，削弱它要驗收的長文件捲動和大量圖片。
9. **parley 改用 vendor 的 main，加上本地的 patch**（2026-10-01 確認）：原本放在 repo 裡的 `third_party/parley`，對應 Chromium 的 `third_party`，不需要對外的 fork。原因見第 4 節。
   - **2026-10-01 改成 fork，搬到 machopo 旁邊**（`../third_party/parley`，https://github.com/wusyong/parley 的 `machopo` 分支）：P3 要 fork rusty_v8 自己編 V8，它連同 V8 和 Chromium 的 build 工具有好幾 GB，又本來就是一個 git repo，不適合放進 machopo。第三方的專案因此都改成放在 machopo 旁邊的 `../third_party/`、各自是我們的 fork、用 `machopo` 分支。parley 的 `machopo` 分支從原本 vendor 的上游 commit 開始，`patches/` 裡的兩個修改變成分支上的 commit，所以更新上游變成 rebase。只留 6 個 crate 的那個 patch 不需要了：它是因為沒有 vendor 上游的測試工具 `parley_dev`，workspace 才載入不了，完整的樹沒有這個問題。
