# P1 靜態渲染

2026-09-29 規劃，2026-09-30 完成。

總規劃（`MVP.md`）裡 P1 只有一行。這份文件記錄 P1 的範圍、子階段，以及設計決定和理由，描述的是完成時的樣子。各子階段的驗收結果、做過的檢查和目前的已知限制，見 `PROGRESS.md`。

## 目標

- **驗收**：下面「第一批 reftest」全部在 headless 模式通過（Windows，測試字型模式）。✅
- **可以看的成果**：`cargo run -- path/to/page.html` 開出一個只含白名單 CSS 的靜態頁面，文字、背景、邊框都正確。✅

## 子階段

先把 GC 基礎獨立做完並驗收（P1.0），因為 parser、style、layout 都建在它的 API 上，而且它不需要 HTML 就能完整測試。接著做一條從 HTML 到像素的最細切片，讓 reftest harness 開始運作，之後每個子階段都往寬處補。

| 子階段 | 預估 | 內容 | 驗收 |
| --- | --- | --- | --- |
| P1.0 GC 基礎 | 1 週 | Heap 設定、`dom_macros`（`GcObject` / `Trace` derive、禁止 `Drop`）、`Edge` / `WeakEdge`（建立在自己的 `MemberSlot` 上）、`Node`、兩種 scope、`NodeHandle` / `DocumentHandle` / `NodeIdMap`、基本操作和走訪 API、platform task 的包裝函式、root 計數；測試用的 detached heap 和 C++ glue | `dom` 和 `bindings` 的 GC 測試全部通過，concurrent 模式也能執行 |
| P1.1 骨幹切片 | 1.5 週 | `html`（sink 接到 `dom`）、navigation 帶 body、reftest harness、最小的 style（`computed_style` crate、`style` attribute、簡單的 selector、box 相關 property）、taffy block layout、只有 root 的 property trees、paint 矩形 | WPT tree-construction `.dat` 通過；reftest B1–B6 |
| P1.2 Cascade | 1 週 | UA stylesheet 補齊、pseudo-class、繼承和 `color`、border 相關 property、solid border | reftest C1–C6 |
| P1.3 文字 | 1.5 週 | 字型、anonymous block、parley inline layout、white-space、`line-height`、`text-align`、raster 畫 glyph | reftest T1–T8 |
| P1.4 Property trees 與收尾 | 1 週 | `opacity` / `overflow` / `transform` 建出 property tree 節點、stacking context 的 paint 順序、chunk 轉成單一 layer、匯入 WPT 子集 | reftest E1–E5 與 WPT 子集 |

預估合計約 6 週，比總規劃估的 4–5 週多 1 週，多出來的是 P1.0 的 GC 基礎：它讓大部分 GC 規則由編譯器檢查，並配上一組專門的測試（見第 1 節）。之後的階段主要是在這個基礎上擴充，例如 P3 的 `TracedReference` 包裝和 event listener；P4 如果要把 concurrent marking 改成預設，還有幾個未知數要先處理（見 1.3 的「Concurrent 還剩的未知數」）。

## 設計決定

### 1. DOM 在 cppgc 上

P1.0 已經完成。這一節只記設計決定、理由，以及和 Blink / V8 的對照。現在的 API 和規則見 [`crates/dom/README.md`](../crates/dom/README.md)；為什麼安全、依賴哪些假設、要人工審查什麼，見 [`crates/dom/soundness.md`](../crates/dom/soundness.md)。

#### 1.1 節點與樹

- **只有一個 GC 型別 `Node`**，種類用 enum 區分：`Document`、`DocumentFragment`、`Element`、`Text`、`Comment`、`Doctype`。
  - 原因：`Edge<T>` 帶型別，Rust 又沒有繼承，拆成多個 GC 型別會讓樹狀指標到處轉型。
  - 對應 Blink 的 `Node` 子類別：`Document` 和 `Element` 繼承 `ContainerNode`，`Text` 和 `Comment` 繼承 `CharacterData`，`DocumentType` 直接繼承 `Node`。
- **`Node` 分成被 trace 和不被 trace 兩個區域**（見 1.4）：
  - 樹狀指標和不可變的 `kind: NodeKindData` 被 trace；
  - 可變的資料（attribute、`ComputedStyle`、文字、quirks mode）放在 `#[no_trace]` 的 `RefCell<NodeState>`。
- **`<template>` 用一個 `Edge<Node>` 指向它的 content**，也就是一個 `DocumentFragment`。html5ever 的 `TreeSink::get_template_contents` 需要它。
- **樹用五個指標的 linked list**：`parent`、`first_child`、`last_child`、`previous_sibling`、`next_sibling`。
  - Blink 只存四個：`Node` 存 `parent_or_shadow_host_node_`、`previous_`、`next_`，`ContainerNode` 另外存 `first_child_`。最後一個子節點放在 `first_child_->previous_`，是環狀的。
  - P1 先用五個求簡單。

#### 1.2 讀寫權限

- **兩種 scope 都從 `&mut DomIsolate` 建立**，所以 scope 存在時，沒有別人能使用 isolate：不會配置 GC 物件、不會執行 JS 或 V8 task。
  - **持有 `DomReadScope` 期間不會 GC**，所以拿到的 `NodeRef` 在 scope 結束前都有效。
  - **修改一律經過 `DomMutationScope`，而且接 `NodeHandle`，不接 `NodeRef`**，所以沒有 `NodeRef` 能跨越修改。
  - **Style、layout、paint 只拿得到 `DomReadScope`**，所以 lifecycle 期間不可能修改 DOM。只有 lifecycle 自己產生的資料（`ComputedStyle`、dirty flag）可以用 `DomReadScope` 寫入。
- **不變的資料（種類、element 名稱）可以只憑 `NodeHandle` 讀取**。Parser 的 `elem_name` 需要這一點（見第 2 節）。
- **`dom` 核心內部的 raw 指標，跨越配置時只能放在 stack 上**：這依賴 V8 在 atomic pause 保守地掃描 stack。
- **V8 platform task 只能在 event loop 的最外層執行。** 有些 task 以 `kNoHeapPointers` 跑 GC，不掃描 stack：
  - incremental marking job，它可能在 task 裡直接完成 marking；
  - `TaskOnContextDispose`，只在呼叫 `ContextDisposedNotification` 之後才會排進來，而 `v8` crate 沒有提供這個 API。

  所以 task 只能透過要求 `&mut self` 的包裝函式執行；raw API 由 `clippy.toml` 禁止。
- **Blink 在執行期檢查同一件事**，我們則是在編譯期：
  - `DocumentLifecycle::StateAllowsTreeMutations()` 規定 style recalc、layout、compositing inputs update、pre-paint、paint 期間不允許修改樹。
  - DCHECK build 在修改的當下檢查：`ContainerNode::ChildrenChanged`、`CharacterData` 的內容變更、attribute 變更都會呼叫 `Document::IncDOMTreeVersion()`，裡面有 `DCHECK`。
  - Release build 只在 `Document::UpdateStyleAndLayoutTreeForThisDocument()` 真正要更新 layout tree 時，有一個 `CHECK`。
  - Script 方面：`LocalFrameView::PerformLayout()` 用 `ScriptForbiddenScope`。整個 lifecycle 更新的外層用 `BlinkLifecycleScopeWillBeScriptForbidden`：DCHECK build 一律禁止；release build 只有開啟 `BlinkLifecycleScriptForbidden` runtime feature（預設關閉）時才禁止（crbug.com/1196853）。

#### 1.3 GC 模式

- **Chromium 的預設。**
  - Blink 用預設的 `CppHeapCreateParams` 建 CppHeap（`thread_state.cc`）。加上 V8 的預設 flag，前景 renderer 是 incremental 加 concurrent marking，以及 concurrent sweeping。
  - 隱藏的 renderer 會被設成 `kBestEffort` priority（`render_thread_impl.cc` 的 `OnRendererHidden`），進入 efficiency mode：marking 開始時不用背景 thread，但到了 atomic pause 又會升級回 concurrent。
  - `gin/v8_initializer.cc` 裡 GC 相關的 flag，預設都不改變 marking 模式。
- **P1 用 incremental marking**：只在 main thread 上分段執行。
  - V8 自己的 JS concurrent marker 碰到 C++ 物件時只標記它，不呼叫我們的 `trace()`。
  - 不先用 atomic marking，是為了讓 write barrier 從第一天就被測試檢查到。
- **型別設計已經為 concurrent 準備好，但 concurrent 不當預設。**
  - 被 trace 的區域必須是 `Sync`，由編譯器檢查（見 1.4）。
  - `Edge` 用我們自己的 `MemberSlot`，不用 `v8` crate 的 `Member`：後者的 aliasing 和對齊，在 concurrent 下都是 UB。細節見 soundness.md 的「Concurrent marking」。P1 時它在 `bindings` 裡，2026-10-02 搬進我們的 rusty_v8 fork（`v8::cppgc::MemberSlot`）。
  - **新物件的發布**：`v8` crate 在 C++ 標記「已建構完成」之後才寫入 Rust 的資料，形式上有 data race。P1 時我們這一側補不了建構子：prebuilt V8 是 clang-cl 加 Chromium 的 libc++ 編譯的，MSVC 編的 C++ glue 接不上它的配置模板。所以先用兩個 fence 補上（`assign` 的 release fence 配上 `MemberSlot::trace` 呼叫 cppgc 之後的 acquire fence），依賴 cppgc 在 `Trace(Member)` 裡只標記、不當場 trace 目標。2026-10-02 改成自己編 V8 之後，fork 讓 `RustObj` 的建構子寫入 Rust 的資料，fence 和那條假設都拿掉了（soundness.md 的「Concurrent marking」）。
  - 不預設開啟的原因：
    1. P1 的 heap 很小，還沒有證據顯示 concurrent 能省下時間；
    2. concurrent 的錯誤取決於時序，測試難以證明沒有 race；
    3. 沒有 sanitizer：P1 決定不從原始碼編譯 V8（見 1.7 的「不做」）；2026-10-02 改成自己編（`P3.md` 的「已決定的事項」第 10 條），sanitizer 做得到了，但還沒做。
  - **實驗開關**：`MACHOPO_CPPGC_MARKING=concurrent`。V8 的 marking flag 只能把設定調得更保守，所以開關要做在我們這一側。
  - **之後用 tracing 量 GC pause**，再決定要不要改成預設。
- **防止 V8 自己升級成 concurrent。**
  - 一輪 GC 在 efficiency mode 下開始時，V8 會呼叫 `CppHeap::ReEnableConcurrentMarking()`，不檢查我們設定的 marking 模式。
  - `bindings::initialize` 一律加上 `--no-single-threaded-gc-in-background` 關掉這條路徑（原始碼分析見 `crates/bindings/src/platform.rs` 的註解）。
  - 代價：V8 自己的 heap 在背景也不再單執行緒 GC。之後拆 process、做背景 tab 時再權衡（RFC 0004）。
- **Sweeping 由 V8 決定。** CppHeap 接上 isolate 時，`CppHeap::UpdateGCCapabilitiesFromFlags()` 會覆寫我們的設定：預設是 concurrent sweeping，加上 `--single-threaded-gc` 是 incremental，forced GC 則一律 atomic。有 finalizer 的物件一律延後到 main thread 才 finalize。
- **Concurrent 還剩的未知數。** 以下都要在 concurrent 改成預設之前處理。P1 時「處理時機」有幾列寫的是 P4；2026-10-02 規劃 P4 時沒有把它們排進去（P4 是 compositor），所以改成「之後」，目前的狀態集中在 `PROGRESS.md` 的「測試守不住的地方」：

  | 未知數 | 內容 | 處理時機 |
  | --- | --- | --- |
  | `TracedReference`（DOM 節點指向 JS 值） | `v8` crate 的 `TracedReference` 同樣是 `[u8; N]`、對齊只有 1，`reset` 也要 `&mut self`。**P3.0 已處理**：照 `MemberSlot` 的模式做了 `TracedSlot`（現在也在 fork 裡）；V8 在 concurrent marking 時怎麼讀它也查過了，順序由 V8 自己保證（soundness.md 的 C4） | 已完成（P3.0） |
  | `HeapVector`（GC 物件的集合） | 最難的一個，還沒設計。Marker 可能正在讀舊的底層陣列和長度，main thread 同時在擴容。至少需要：底層陣列本身是 GC 物件、指向陣列的指標用 atomic 替換並先發布內容、長度和元素的讀寫順序處理好。可以參考 Blink 的 `HeapVector`。P3 的 event listener 改用 linked list，所以還不需要（理由見 `P3.md` 的「已決定的事項」第 2 條） | 第一個需要大量元素的 GC 集合出現時 |
  | 驗證工具 | 沒有 TSan 和 marking verifier，只能靠 stress 和 mutation test。自己編 V8 之後兩者都做得到（見 1.7 的「不做」） | 之後（還沒排進任何階段） |
  | 記憶體順序測不出來 | x86 不會重排寫入；ARM64 會，但 stress 也碰不上：在 ARM64 上拿掉當時的 release fence，concurrent 測試照樣通過。所以記憶體順序只能靠審查。ARM64 上目前只手動跑過，CI 不跑 `matrix`（見下面的「CI」） | 在 Apple Silicon 上照 `docs/README.md` 的條件在本機跑 `scripts/ci.py matrix` |
  | 測試的空白 | Detached 測試能精確控制時機，但沒接 isolate；接上 isolate 的測試只能靠 stress | 之後 |
  | 需不需要 concurrent | 要量過 GC pause 才知道 | 之後 |

  可以回報 `v8` crate 上游的修改列在 soundness.md 的最後一節。

#### 1.4 用型別強制 GC 規則

Blink 用 clang plugin `blink_gc_plugin` 檢查 GC 的錯誤用法。它在 Chromium 預設的 `-Werror` 下直接以 error 回報。我們用型別系統和 derive macro 做同樣的事：`dom` 以外的程式碼碰不到 `Member`，也不手寫 `trace()`。

- **為什麼分成兩個區域**：最初的設計只對每個被 trace 的欄位檢查 `Sync`，但 `Node` 原本只有一個 `data: NodeData` 欄位，同時裝著 `Edge` 和可變資料的 `RefCell`，所以整個欄位不是 `Sync`，而 `trace()` 其實不讀那些 `RefCell`。問題在於「會被 trace 的資料」和「可變的資料」混在同一個型別裡。拆成兩個區域後，`Sync` 檢查的對象就剛好是 `trace()` 會讀的資料。
- **禁止自己實作 `Drop`，比 Blink 嚴格**：Blink 允許 destructor，plugin 只檢查 destructor 本體裡有沒有透過 `->`、`[]` 或函式參數使用 `Member` / on-heap collection 欄位，不追進被呼叫的函式。
- **`NoTrace` impl 全部寫在 `dom` 裡**，包括替別的 crate 的型別寫的（例如 `computed_style::ComputedStyle`，見第 4 節），因為 workspace 的 `unsafe_code = "deny"` 只讓 `dom` 和 `bindings` 寫 `unsafe`。

| 規則 | 違規寫法 | 我們為什麼編譯失敗 | Blink 的對應 |
| --- | --- | --- | --- |
| GC 指標都被 trace | 漏列欄位 | Derive 會 trace 每個 `Trace` 欄位。錯誤的 `NoTrace` impl 會藏住 GC 指標，所以 `NoTrace` impl 要人工審查 | Plugin：`kFieldsRequireTracing`；完全沒有 trace 方法時是 `kClassRequiresTraceMethod` |
| 寫入經過 barrier | `mem::swap`、整個蓋掉 | 拿不到 `&mut Edge` | C++ 的 `Member::operator=` 指派非 null 指標時一定經過 barrier（null 不需要），`swap` 也走 `operator=`；但 C++ 擋不住 `memcpy` 之類的繞過 |
| GC 指標不放一般容器 | `Vec<Edge<_>>` | 容器只在元素是 `NoTrace` 時才是 `NoTrace` | Plugin：`kCollectionOfMembers`，禁止 `std::vector` / `map` / `set` / `unordered_*` 和 off-heap 的 WTF 容器（`PartitionAllocator`）裝 `Member`；`std::array<Member>` 例外允許 |
| GC 指標不包在 `Option` / `RefCell` 裡 | `Option<Edge<_>>`、`RefCell<Edge<_>>` | 兩種 trait 都沒實作 | `Option`：plugin 的 `kOptionalDeclUsedWithMember`（欄位和 `new` 出來的 optional 包 `Member`；stack 上的允許）。`RefCell`：Blink 沒有對應 |
| GC 物件裡不放 root | `Persistent` / `WeakPersistent` 欄位 | 兩種 trait 都沒實作 | Plugin：`kClassContainsGCRoot`（兩者都是 `BasicPersistent`，都算 root） |
| Concurrent 時 trace 只讀安全資料 | 在被 trace 的區域放 `Cell` / `RefCell`；替不是 `Sync` 的型別手寫 `Trace` | `Trace: Sync`。剩下要人工審查的只有手寫的 `unsafe impl Sync`（`MemberSlot`、`WeakMemberSlot`、P3 的 `TracedSlot`，之後的 `HeapVector`） | `Member` 用 atomic 讀取；plugin 另外用 `kVariantUsedWithGC` 禁止 `absl::variant` 直接裝 GC 型別；其餘靠慣例 |
| GC 物件只透過 `Edge` 指向 | 把 GC 物件直接當成欄位 | GC 物件不實作 `Trace` | Plugin：`kGCedField` |
| Finalizer 不碰其他 GC 物件 | 替 derive 出來的型別實作 `Drop` | 和 derive 產生的 impl 衝突 | Plugin：`kFinalizerAccessesFinalizedField`（範圍見上面） |

#### 1.5 `Drop` 與 teardown

- **`Drop` 在 main thread 上執行，但時間點不固定**：
  - 配置 GC 物件的途中：sweeper 的 `SweepForAllocationIfRunning` 會當場 finalize 一批物件，可能發生在 `DomMutationScope` 的操作裡，或 parser 的 sink 持有 `RefCell` borrow 的時候；
  - platform task 裡：cppgc 的 `IncrementalSweepTask`；
  - V8 呼叫 `CompleteSweepingFull` 時，包括開始 major marking、atomic 的 major GC 和 isolate 關閉時；
  - minor GC 開始時（`FinishSweepingIfOutOfWork`）；
  - forced GC 裡；
  - CppHeap terminate 或被 drop 時。

  所以 GC 型別不能自己實作 `Drop`，`NoTrace` 欄位的 `Drop` 也只能釋放記憶體。Weak 指標在 marking 最後的 `ProcessWeakness` 就已經清成 null，比 sweep 早，所以拿不到「已經死了但還沒 finalize」的物件。
- **Teardown**：所有 root 都必須比 isolate 先 drop。`DomIsolate` 會計算還活著的 root，drop 時不是零就 abort。
  - 不用 lifetime 把 root 綁在 isolate 上，因為那會讓 `FrameView` 變成自我引用的 struct。
  - Reftest 的每個測試都會建立再銷毀一個 `WebContents`，會一直走到這條路徑。

#### 1.6 Root 與 node id

- **Root 一律放在 GC heap 之外。** `DocumentHandle` 只由 `FrameView` 持有（第 7 節）。
- **`NodeIdMap`**：以 isolate 為單位的 `HashMap<NodeId, WeakPersistent<Node>>`，放在 heap 之外。
  - 需要它，是因為 fragment tree 和 display list 不在 GC heap 上，只能用 `NodeId` 指回節點，hit testing 和 debug dump 要靠它找回節點。
  - 它是 weak 的，不讓節點保持存活；已經清成 null 的項目，在 event loop 的最外層清掉。
  - `NodeId` 以 isolate 為單位遞增，節點之後在不同 frame 之間移動也不會衝突。
- **Blink 不一樣。**
  - `LayoutObject` 在 GC heap 上，直接持有 `Member<Node>`。
  - `HitTestResult` 不是 GC 物件（`DISALLOW_NEW`），以 `Member<Node>` 持有結果。
  - Blink 的 `DOMNodeIds` 是另一回事：它用 GC 上的 `GCedHeapHashMap<DOMNodeId, WeakMember<Node>>`，由一個 static `Persistent` 持有，第一次被要求時才配置 id，用於 compositor、DevTools 等跨邊界的 id。
  - 我們的表放在 heap 之外，因為 `blink_gc_plugin` 會把 `WeakPersistent` 也算成 root，GC 物件裡不能放。

#### 1.7 測試

測試的清單和怎麼跑，見 `crates/dom/README.md` 的「測試」；做過的 mutation test 和它們的結果，見 soundness.md 的「怎麼驗證的」。這裡只記設計測試時的決定。

- **判斷對錯要靠另外的機制。** V8 的經驗是 stress 測試負責製造危險的時機，判斷對錯靠 TSan、marking verifier 和 DCHECK；V8 自己的 cppgc 測試幾乎不寫 assertion。我們沒有這些工具，所以改用：
  - 對照模型；
  - debug build 的 canary；
  - finalizer 和 trace 在哪個 thread 上執行的計數。
- **兩次「以為測到了、其實沒測到」**：
  - 一開始測試對每個節點都持有 handle，GC 最後的 pause 會從 root 重新標記，所以漏掉 barrier 不會出錯；
  - 工作負載只建立一般 element，`NodeKindData` 裡的 edge 在 GC 下完全沒被跑到。

  兩次都是用 mutation test 發現的，所以之後每個 GC 相關的測試都要做一次 mutation test。
- **照 V8 自己的 cppgc 測試移植的情境**（`detached_marking`，用 `cppgc::testing::StandaloneTestingHeap` 一步一步控制 marking）：

  | 測試 | 情境 | 對應的 V8 測試 |
  | --- | --- | --- |
  | `nodes_linked_after_marking_completes_survive` | Marking 把整棵樹都標記完之後，才把新節點接到樹上，只有 barrier 能保住它們 | `MarkerTest.MemberIsMarkedAfterMarkingSteps`、`IncrementalStepDuringAllocation` |
  | `mutations_between_marking_steps` | 每做一步 marking 就修改一批，寫入同時落在已標記和未標記的部分 | 同上 |
  | `concurrent_marking_while_mutating` | 關掉 main thread 的 marking，讓背景 thread 執行我們的 `trace()`，同時 main thread 持續修改 | `ConcurrentMarkingTest.MarkingObjects` |

- **Parser**（P1.1）：DOM 用 tree-construction 測試的格式（`| <html>`，template 的內容以 `content` 印出）dump 出來，比對 `.dat` 測試檔的子集。這些測試原本在 html5lib-tests，現在只在 WPT 的 `html/syntax/parsing/resources/` 維護。它們在 P1.1 就匯入，和 P1.4 匯入的 WPT reftest 子集是兩回事。
- **試過、目前沒用的 V8 stress flag：**
  - **`--stress-marking=N`**（V8 GC fuzzer 的 `MarkingFuzzer`）：在 P1 完全沒有作用。沒開 `--stress-incremental-marking` 時，低於啟動門檻的小 heap 會在檢查 `--stress-marking` 之前就被 `IsBelowActivationThresholds()` 擋掉（`Heap::IncrementalMarkingLimitReached`）。等 heap 變大再加回來。
  - **`--cppgc-random-gc-interval`**：要 `V8_ENABLE_ALLOCATION_TIMEOUT` 才會生效，而且觸發的是 atomic marking 的 GC，效果和 GC stress 一樣。
  - **`--random-gc-interval` / `--gc-interval`**：計算的是 JS heap 的配置次數，P1 幾乎沒有 JS。
  - **2026-10-02 加進 `ci.py fuzz`**：自己編的 debug V8 有 `V8_ENABLE_ALLOCATION_TIMEOUT`（gn 的 `v8_enable_test_features` 跟著 `is_debug`），上面這三個 flag 都會生效；P3 有了 JS 的工作負載，JS heap 的配置次數也有意義了。用 `--trace-gc` 確認過它們會多觸發 GC。
  - **`--stress-delay-tasks`、`--thread-pool-size`**：是 d8（V8 的命令列 shell）的選項，不是 V8 的 flag。Thread pool 大小改用 `MACHOPO_V8_THREAD_POOL_SIZE`；隨機延遲 task 需要自訂 platform，目前沒做。
- **CI**（2026-10-04 設定，`.github/workflows/ci.yml`；原本排在 P1 結束後）。要跑的檢查寫在 `scripts/ci.py`，用的是 `.cargo/config.toml` 指定的 V8（2026-10-02 起是從我們的 rusty_v8 fork 編的，原本是上游的 prebuilt；見 `P3.md` 的「已決定的事項」第 10 條）：

  | 指令 | 內容 | 擋不擋 merge |
  | --- | --- | --- |
  | `python scripts/ci.py unsafe` | `unsafe` 只在 `dom` 和 `bindings` | 擋 |
  | `python scripts/ci.py deps` | V8 只在 `bindings`、`dom_bindings` 和 `dom` 的 V8 模組（P3.1 加上） | 擋 |
  | `python scripts/ci.py matrix` | 兩種 marking 模式 × V8 預設、1、8 個 worker thread | 不在 CI 跑，在本機跑（見下面） |
  | `python scripts/ci.py fuzz` | 仿照 V8 的 numfuzz，隨機組合種子、thread 數、marking 模式和 GC flag | 不在 CI 跑 |

  CI 每天在 `main` 上跑一次（UTC 18:00），也可以在 GitHub 的 Actions 頁面手動觸發；不在每次 push 時跑，因為 repo 是私有的，runner 的時間要計費。它跑 `unsafe`、`deps`、`docs`、fmt、clippy 和三個平台的 `cargo test --workspace`，一個平台失敗就取消其他平台。`matrix` 和 `fuzz` 要 debug 的 V8，另一份完整的 build（約 15 GB），2026-10-04 決定不放進 CI，只在動到 GC 時在本機跑（`P3.md` 的「已決定的事項」第 10 條）。ARM64（Apple Silicon）上的 `matrix` 也一樣。
- **不做：需要從原始碼編譯 V8 的測試。** 2026-09-30 決定只用 prebuilt V8，所以下面兩個原本的計畫不做。**2026-10-02 改成從 rusty_v8 的 fork 自己編 V8**（`P3.md` 的「已決定的事項」第 10 條），下面卡住的「要完整的 `rusty_v8` 原始碼樹」已經解決，兩者都變得可行，但還沒排進任何階段：
  - **Verification build**：開啟 `cppgc_enable_verify_heap` 的 V8 會在每輪 marking 結束後從 root 重新走一遍，發現「走得到卻沒被標記」的物件就 `FATAL`。試過 `V8_FROM_SOURCE=1`，但 crates.io 上的 `v8` 套件為了壓在 10 MB 以下，排除了 build 需要的檔案（第一個卡住的是 ICU 的 `icudtl.dat`），要另外取得完整的 `rusty_v8` 原始碼樹，而且編譯很久。
  - **TSan（原本排在 P4）**：同樣要從原始碼以 `is_tsan=true` 編譯 V8。
  - 影響：漏掉 barrier 只能靠 canary、對照模型和「測試不用 root 保住節點」的設計抓到；concurrent marking 沒有 race 偵測工具，之後決定要不要改成預設時，要在這個前提下判斷。

### 2. HTML parser

- **版本**：html5ever 0.40。它的 `TreeSink` 方法全部接 `&self`，所以 sink 內部用 `RefCell` 持有 `DomMutationScope`。
- **`elem_name` 不經過 scope**：它回傳的名稱會借用 sink 和 handle，如果讀取要借用 `RefCell` 裡的 scope，之後任何 sink 呼叫都會在 `borrow_mut` 時 panic。所以 element 名稱這類不變的資料直接從 `NodeHandle` 讀取（見 1.2）。
- **`get_template_contents`** 回傳 template element 指向的 `DocumentFragment` 的 handle（見 1.1）。
- **Handle 用 `NodeHandle`**（內部是 `Persistent<Node>`），clone 時建一個新的 `Persistent`。原因是 html5ever 會把 handle 存在自己的 Vec 裡，例如 open elements stack 和 active formatting list，這些 GC 看不到。如果 handle 不是 root，parse 到一半跑 GC，還沒接上樹的節點就會被回收。html5ever 也提供 `trace_handles`，讓 parser 本身當 GC 物件、自己 trace 這些 handle。Servo 用的是這個做法，Blink 的 `HTMLDocumentParser` 也是 GC 物件。等有 incremental parsing（P3 以後）、parser 要活過好幾個 task 時再換成這種做法。
- **一次 parse 完**：用 `parse_document(sink, opts).one(text)`。`scripting_enabled = true`，和 Chromium 相同，所以 `<noscript>` 會 parse 成 raw text。P1 不執行 script。
- **Quirks mode** 記在 `Document` 上，但 P1 只實作 standards mode 的行為。
- **`dom` 不需要為 parser 加新的操作。** `reparent_children`、`add_attrs_if_missing`，以及相鄰文字節點的合併，都用現有的走訪和修改 API 組合出來，和 Blink 的 `HTMLConstructionSite` 做法相同。
- **`elem_name` 回傳自己持有 atom 的小 struct**，每次呼叫時從 `NodeHandle` 上的名稱轉換，不把 markup5ever 的 atom 存進節點：`dom` 不依賴 html5ever，而且 interned atom 的 `Drop` 會鎖一張全域的表，不適合放進會以 finalizer 身分 drop 的 GC 物件。
- **`<selectedcontent>`**：sink 實作了「maybe clone an option into selectedcontent」。但 html5ever 只在明確的 `</option>` 時呼叫它（servo/html5ever#712），被隱含關閉的 `<option>` 不會更新 `<selectedcontent>`。
- **tree-construction 測試**：WPT 的全部 `.dat` 檔都已匯入（`tests/wpt/`，固定在某個 commit）。已知失敗列在 expectation 檔裡並依原因分組，目前全是 html5ever 還沒支援的規範或需要 script 的測試。同一組測試也在 GC stress 下跑一次。結果見 `PROGRESS.md`。
- **標題**：照 `Document.title` 的規則，取第一個 `<title>` 的文字子節點，去掉並合併空白，parse 完送 `UpdateTitle`。

### 3. Navigation 帶 body

`RendererMsg::CommitNavigation` 加上 `body` 和 `mime_type`。`file://` 由 Browser 讀檔，對應 Chromium 在 browser 端的 `FileURLLoaderFactory`，Renderer 不直接碰檔案系統。這樣 P2 換成網路載入時，Renderer 端不用改，之後加 sandbox（RFC 0004）也不用回頭改這條路。

- **Browser 端**：`browser::loader`（對應 `//content/browser/loader`）處理 `about:blank`、`about:demo`（內嵌 `resources/demo.html`）和 `file://`。MIME 類型依副檔名決定，和 `net::GetMimeTypeFromFile` 一樣（`.xht` / `.xhtml` 是 `application/xhtml+xml`）。讀不到檔案或不支援的 scheme，就 commit 一個以錯誤碼當標題的錯誤頁（`ERR_FILE_NOT_FOUND`、`ERR_UNKNOWN_URL_SCHEME`），像 Chromium 的 net error page。P2.0 把 `file://` 的讀檔和 MIME 的判斷搬到 `net`，`browser::loader` 只留下 `about:` 頁和錯誤頁（見 `P2.md` 第 1 節）。
- **Renderer 端**：`text/html` 直接 parse；XHTML 也交給 HTML parser（見第 8 節）；其他類型照 Blink 的 `TextDocument`，包在 `<pre>` 裡當純文字。P1 只支援 UTF-8（去掉 BOM），不看 `charset`。新的 document 取代舊的，舊的就成了垃圾。Event loop 每一輪都執行 V8 的 platform task，incremental marking 才能完成。
- **`machopo` 的參數**：URL 直接使用；其他當成檔案路徑，轉成 `file://` URL。其他選項見 `machopo --help`。

### 4. Style

**Crate。** `selectors` 0.40 搭 `cssparser` **0.37**（`selectors` 0.40 綁的是 0.37，不能用最新的 0.38）。`selectors::Element` 實作在包著 `NodeRef` 的 newtype 上（trait 和 `NodeRef` 都在別的 crate）；`OpaqueElement` 用 node id 當身分，不需要 `dom` 交出指標。不用 bloom filter，selector flags 也不處理。

**來源。**
- **UA stylesheet**（`crates/style/resources/html.css`）：HTML 規範 Rendering 一節（以及 Chromium 的 `html.css`）裡白名單內的規則：`display`、`body` 的 8px margin、段落 / list / heading 的 margin、heading 的字級和粗體、list 的 `padding-left`、`b` / `i` / `code` / `pre` / `small` 等的文字規則、連結的顏色和底線、`hr` 的 border。Logical property 寫成 horizontal LTR 的實體方向（`margin-block` 寫成 `margin-top` / `margin-bottom`）。和規範不同的地方寫在檔頭：`hr` 用 `solid` 取代 `inset`、`fieldset` 沒有 border、list 是 block、table 是 inline（沒有 `list-item` 和 table 的 display）。
- **`<style>`**：document 裡依 tree order；`type` 只接受空的或 `text/css`；`media` 屬性先忽略（等有 `@media` 再處理；P2 也還沒有）。Template 的內容不在 document 裡，不套用也不被套用。
- **`style` attribute**：不屬於 CSSOM，只是多一個 declaration 來源，大部分 reftest 都要用到。

**Cascade 自己寫。**
- 排序：origin 和 `!important`（UA normal < author normal < author important < UA important）→ `style` attribute 贏過同一層的任何 rule → specificity → 出現順序。一條 rule 以它符合的 selector 裡最高的 specificity 計算。
- 每個元素從 parent 的繼承 property 開始（`ComputedStyle::inherit`），`font-size` 先套用，因為其他 `em` 都相對於它（Blink 的 high-priority property）；`font-size` 自己的 `em` / `%` 相對於 parent，`rem` 相對於 root element 的字級。
- `initial` / `inherit` / `unset` 都支援；`unset` 對繼承 property 等於 `inherit`。
- Root element 會被 blockify。
- 每次 recalc 重算所有 element，沒有 invalidation 和 style sharing。

**Computed value。**
- 長度換成 px，`%` 留給 layout 處理。
- 顏色轉成 RGBA，但 `currentcolor` 保留成關鍵字（`StyleColor::CurrentColor`），用到時才以該元素的 `color` 解析，和 Blink 的 `StyleColor` 一樣。原本打算在 style 階段就解析掉，但那樣 `border-color: inherit` 會繼承到 parent 解析後的顏色，而規範要的是繼承關鍵字、再用 child 自己的 `color` 解析（reftest C5 的第二個方塊驗證這一點）。`color: currentcolor` 等於繼承。
- Style 是 `none` 的邊，computed border width 是 0。
- `line-height` 的數字保持是數字（以數字繼承），長度和百分比換成 px。
- 一軸的 `overflow` 是 `hidden` 時，另一軸的 `visible` 也算 `hidden`（規範會變成 `auto`，也就是 scroll container；P1 沒有捲動，所以當成裁切）。P2 有了捲動，改成照規範變成 `auto`（見 `P2.md` 第 6 節）。
- `text-decoration-line` 不繼承，但會傳給子孫的文字：`applied_text_decorations` 是祖先和自己的聯集，對應 Blink 的 `AppliedTextDecorations`。

**Selector。** `selectors` 自己實作的 type、class、id、attribute、combinator、tree-structural pseudo-class 和 `:not()`，另外開啟 `:is()`、`:where()`、`:has()`、`:nth-child(… of S)`。自己解析的 pseudo-class 只有 `:link` / `:any-link`（有 `href` 的 `<a>` / `<area>`）和 `:visited`、`:hover`、`:active`、`:focus`、`:focus-visible`、`:focus-within`；後六個在有輸入和瀏覽紀錄之前永遠不成立。其他 pseudo-class 和 pseudo-element 不解析，整條 rule 丟掉。Quirks mode 下 class 和 id 不分大小寫。

**不支援的東西直接忽略**，並在 debug log 記次數（`RUST_LOG=style=debug`）：不支援的 property、不支援或不合法的值、被丟掉的 rule（at-rule、無法解析的 selector）。Reftest 失敗時，先看是不是用到了白名單外的東西。

**`ComputedStyle` 放在獨立的 crate `computed_style`**，對應 Blink 的 `blink/renderer/core/style`：Blink 也把 `ComputedStyle` 和各種 style 值，和 style 引擎（`core/css`，也就是我們的 `style`）分開。
- 依賴方向：`dom`、`style`、`layout` 都依賴 `computed_style`；`style` 依賴 `dom`，因為 `selectors::Element` 實作在 `NodeRef` 上；`dom` 不依賴 `style`。這樣就沒有循環依賴。
- **存在節點上**：Element 的 `NodeState`（不被 trace 的 `RefCell`）持有 `Option<Arc<ComputedStyle>>`，對應 Blink 的 `Element::GetComputedStyle()`。由 style 階段透過 `DomReadScope` 的專用 API 寫入（見 1.2）。
- **為什麼不放在 `FrameView` 的 side table**（`NodeId → Arc<ComputedStyle>`）：side table 讓 `dom` 的 soundness 範圍完全不變，但將來 `ComputedStyle` 要持有 GC 物件時（例如 `background-image`；P2 的 `<img>` 圖片放在 `FrameView` 的表裡，不需要），只能用 `Persistent`，會回到 root 太多、容易洩漏的問題。放在節點上，將來可以演進成「`ComputedStyle` 本身是 GC 物件，由節點 trace」；Blink 後來也把 `ComputedStyle` 改成了 Oilpan 上的 GC 物件。
- **代價，以及守住的做法。** `dom` 要寫 `unsafe impl NoTrace for ComputedStyle`，它的 SAFETY 註解涵蓋 `computed_style` 裡的整棵型別樹；節點死掉時，如果它握著最後一個 `Arc`，`ComputedStyle` 的 `Drop` 會以 finalizer 的身分在任意的配置點執行。所以：
  1. **編譯期檢查**：在 `unsafe impl` 旁邊斷言 `ComputedStyle: Send + Sync + 'static`，擋掉 `Rc`、`RefCell`、`Cell`、raw 指標、`Persistent` / `NodeHandle`；GC 指標在 `dom` 以外本來就拿不到（`Node` 是 `pub(crate)`，`v8::cppgc::Member` 被 `clippy.toml` 禁止）。
  2. **`computed_style` 只放純資料**：不自己實作 `Drop`，不用 interning 或全域、thread-local 的快取（它們的 `Drop` 會上鎖或碰 thread-local），這條寫在它的 crate 文件裡。共用的資料用 `Arc`（例如 `font-family` 的清單）。
  3. **列入人工審查**：`computed_style` 的型別改動，照 `crates/dom/soundness.md` 的 `NoTrace` 一節審查；設定 CI 時用 CODEOWNERS 讓 `dom` 的審查者也看這個 crate。
  4. **需要持有 GC 物件時**，把 `ComputedStyle` 本身改成 GC 物件，不要在 `NoTrace` 的型別裡偷塞 GC 指標。

### 5. Layout

**Box tree。** 對應 Blink 的 `LayoutObject` tree，由 DOM 加上 `ComputedStyle` 建出來。它是一般的 Rust 資料，用 `NodeId` 指回節點，由 `FrameView` 持有，不放在 GC heap 上。這和 Blink 不同（Blink 的 `LayoutObject` 在 Oilpan 上），但符合總規劃「pipeline 的輸出不進 GC heap」的原則，也讓 `layout` 不需要 unsafe。
- 沒有 computed style 或 `display: none` 的元素，連同子孫都不產生 box。
- Block container 裡不是全部 block，就是全部 inline：和 block 相鄰的 inline 內容包成 anonymous block（CSS 2 §9.2.1.1），只剩會被合併掉的空白時不產生。全部 inline 的 block 是 inline formatting context（IFC）的 root。
- Inline 元素攤平成「文字＋所屬元素的 style」的序列；裡面的 block 會把它切開（block-in-inline），照常變成 sibling。`<br>` 是強制換行。Inline 元素本身還沒有 box，所以它的 background、border、padding、margin 不會畫出來，也不佔空間（P2.1 加上）。
- **LayoutView**：taffy 的 root 是一個大小等於 viewport 的 box，對應 Blink 的 `LayoutView`，root element 是它唯一的 child。這樣 root element 的 margin 會被套用，也不會和 viewport collapse（`compute_root_layout` 本身不管 root 的 margin）。

**taffy 0.14 的低階 API。** 在 box tree 上實作 `TraversePartialTree`、`LayoutPartialTree`、`CacheTree`、`LayoutBlockContainer`，不使用 `TaffyTree`；feature 只開 `std`、`block_layout`、`content_size`，flexbox 和 grid 等 flex / grid 那一步再開（原本排在 P4，2026-10-02 拆成 P5，2026-10-04 改成 RFC 0003）。分派和 `TaffyTree` 一樣：IFC root 和沒有 child 的 box 走 `compute_leaf_layout`，其餘走 `compute_block_layout`。Margin collapsing 經由 `LayoutOutput` 傳遞（`BlockContext` 只有 float 用得到）。`overflow: hidden` 的 box 在 taffy 裡是 scroll container，所以會建立 BFC，margin 不再和 child collapse。不做 rounding：fragment tree 保留小數，由 paint 對齊像素。

**IFC。** 在 taffy 裡是 leaf，measure function 用 parley 在給定寬度斷行，min-content / max-content 用 `calculate_content_widths`。taffy 可能量過其他寬度又用快取的結果，所以產生 fragment 時，會用最後的 content 寬度重新斷行一次。
- **空白自己處理**（css-text 的 phase I，Blink `InlineItemsBuilder` 做的事），再以 preserve 的方式交給 parley。原本打算用 parley 的 `WhiteSpaceCollapse`，但讀了 parley 0.11 的原始碼：它會在每個 span 的開頭和結尾各自 trim，`<b>a </b>b` 會把空白吃掉，不符合 CSS。規則：可合併的空白（`normal` / `nowrap` / `pre-line` 的空白和 tab，以及 `normal` / `nowrap` 的換行）跨元素邊界縮成一個；行首和內容結尾的拿掉，強制換行前的也拿掉；行尾的空白交給 parley hang（不算進寬度和對齊）。`pre` / `pre-wrap` / `pre-line` 保留換行，`nowrap` / `pre` 不自動換行。每個字元記住它來自哪個 item，所以拿掉空白之後 style 的範圍不會錯位。
- **parley 的設定**：用 `RangedBuilder` 和 `quantize`；brush 是 run 的索引，paint 用它找回 style。`line-height: normal` 對應 `MetricsRelative(1.0)`，數字對應 `FontSizeRelative`，長度對應 `Absolute`。每個 family list 最後都補上 serif，當作 UA 的標準字型。`text-align` 用 parley 的 `align`。
- **沒做**：strut（行高至少是 block 本身字型的行高）、`tab-size`、`text-indent`、`vertical-align`、`letter-spacing`、`word-spacing`。

**字型。** Renderer main thread 持有 `layout::TextContext`（parley 的 `FontContext` 和 `LayoutContext`）。
- 一般模式用系統字型（fontique 在 Windows 上走 DirectWrite）。
- 測試模式關掉系統字型，只註冊內建的 Ahem 和 Lato Medium（`resources/test_fonts/`，來源和 license 見那裡的 README），generic family 全部對到 Lato；Lato 只有一個字重，`bold` 由 Skia 合成。
- 用 `machopo --test-fonts` 切換，reftest runner 一律開啟。旗標經 `browser::RendererFlags` 在啟動 renderer 時傳下去，對應 Chromium 把 browser 的命令列 switch 傳給 renderer（`PropagateBrowserCommandLineToRenderer`）。

**輸出：immutable fragment tree**，包在 `Arc` 裡：
- **`BoxFragment`**：node id、`BoxRole`（LayoutView / anonymous block / root element / `<body>` / 其他，paint 決定 canvas background 時要用）、style、border box 的尺寸、padding / border / margin，以及 child 和它們的位移（`FragmentLink`）。
- **`LineFragment`**：IFC root 的每一行；rect 是內容的範圍（從對齊位移開始，不含行尾 hang 的空白）。
- **`TextFragment`**：一個 glyph run：字型（`gfx::FontData`）、字級、glyph id 和位置、合成粗體和斜體的參數、裝飾線要用的字型 metrics、元素的 style。
- `BoxFragment::dump()` 會印出整棵樹，給測試和除錯用；原本打算接到 headless 的 `--dump-layout`，還沒做。

**文件大小。** Viewport 和所有 box、line 的聯集，但被 `overflow: hidden` 裁掉的內容不算，transform 也不算。當作 layer 的 bounds。

### 6. Pre-paint、paint，以及接到 compositor

**Property trees。** 型別放在 `paint` crate，對應 Blink 的 `platform/graphics/paint`。`PropertyTreeState` 是 `(transform, clip, effect)` 三個節點 id。

| 樹 | 由什麼建立 | 節點內容 |
| --- | --- | --- |
| Transform | `transform` | 2D affine（`gfx::Transform`）、parent |
| Clip | `overflow: hidden` | padding box（對齊整數 px）、所在的 transform space、parent |
| Effect | `opacity < 1` | opacity、parent |

**Pre-paint**（`PaintPropertyTreeBuilder`）走一遍 fragment tree 建出三棵樹，並替每個 fragment 記下兩組 state：自己的 background / border 用的，和內容（文字、child）用的，後者多了 overflow clip，對應 Blink 的 `LocalBorderBoxProperties` 和 `ContentsProperties`。
- Transform node 的矩陣是「移到 box 的位置、繞 border box 中心套用 transform」；box 的內容就在這個新的座標空間裡，原點是 border box 的左上角。`transform-origin` 固定在中心（還沒有這個 property）。
- Root element 和 `<body>` 的 `overflow` 屬於 viewport（P2 的捲動），不裁切。P2 改成在建 box tree 時決定傳給 viewport 的是哪一個：root 不是 `visible` 時，`<body>` 會裁切自己的內容（見 `P2.md` 第 6 節）。
- Clip rect 對齊整數 px，和 background 一樣。原本沒有對齊，anti-aliasing 讓被裁掉的內容漏出半行（WPT 的 `margin-collapse-009` 抓到）。

**Paint 順序：CSS 2 Appendix E。** P1 沒有 positioning 和 `z-index`，所以 stacking context 只有 root、`opacity < 1` 和有 `transform` 的 box。在每個 stacking context 裡：
1. 照 tree order 畫每個 box 的 background 和 border；
2. 照 tree order 畫所有文字；
3. 照 tree order 畫每個子 stacking context，整個當成一個單位。

所以子 stacking context 會畫在同一層的 normal-flow 內容之後，即使它在 tree 裡排在前面（reftest E5）。Item 加入時如果 property tree state 和上一個不同，就開新的 paint chunk。

**Background。** Root element 的 background（沒有的話用 `<body>` 的）畫在整個 canvas 上，那個 box 自己就不再畫（css-backgrounds 的 canvas background 規則）。每個矩形的邊緣四捨五入到整數 CSS px，對應 Blink 的 `PixelSnappedIntRect`；只在 device scale factor 是 1 時完全正確（P4.2 起改成四捨五入到 device pixel，見 `P4.md` 的「已決定的事項」第 53 條）。

**Border**（`BoxBorderPainter`）。Background 的範圍是 border box，border 畫在它上面。
- **同色**（每個有寬度的邊都是同一個顏色）：畫成「外框減內框」一條 path，沒有斜線，對應 Blink 的 `DrawDRRect`。原本也畫成四個梯形，但斜角交會的頂點會因 anti-aliasing 漏出一個像素的背景（WPT 的 `height-113` 抓到）。
- **不同色**：每一邊是外緣和內緣之間的梯形，角落從外角斜切到內角，所以寬度不同時斜線的角度也不同。同色的邊合成一條 path；不同色的邊之間，斜線上的 anti-aliasing 會互相混色，Chromium 也是這樣。
- 外緣和內緣都各自對齊整數 px。

**文字**（`TextFragmentPainter`）。每個 `TextFragment` 依序畫 underline、overline、glyph（`DrawGlyphs`）、line-through。Baseline 對齊整數 px。裝飾線的顏色用文字的 `color`（規範是用產生裝飾的那個元素的顏色，P1 還沒區分），位置和粗細來自字型的 metrics。

**PaintArtifact。** Display item 記 client（node id）、種類、visual rect（在 chunk 的 transform space 裡）和 paint op；paint chunk 是一段連續、`PropertyTreeState` 相同的 display item。

**P1 的 Layerize：`PaintChunksToCcLayer`。** 全部的 chunk 轉成一個 `PictureLayer` 的 display list。
- Effect 是群組：連續幾個 chunk 在同一個 effect 下時，只開一次 `SaveLayerAlpha`，所以群組裡重疊的內容只混色一次（css-color 的群組 opacity；E3 的第二部分專門測跨 chunk 的情況）。
- 不在 root state 的 chunk 用 `Save`、每個 clip 的 `SetMatrix` + `ClipRect`、chunk 自己的 `SetMatrix`、item、`Restore` 包起來。`SetMatrix` 相對於 raster 開始時的矩陣（tile 的位移和縮放），和 `cc::SetMatrixOp` 一樣，所以 display list 不必知道 tile。
- Chromium 處理不需要獨立 layer 的內容，走的就是這條路。P4 做真正的 Layerize 時，只要加上「哪些 chunk 要拆成獨立 layer」的判斷，這段轉換可以直接沿用。

**`compositor_paint` 新增的 op。**

| Op | 用途 |
| --- | --- |
| `Concat { transform }` / `SetMatrix { transform }` | Transform node；`SetMatrix` 相對於 playback 開始時的矩陣 |
| `SaveLayerAlpha { bounds, alpha }` | Effect node |
| `DrawPath { polygons, flags }` | Border。多個多邊形合成一條 path（non-zero winding），共用邊的多邊形不留 anti-aliasing 的接縫 |
| `DrawGlyphs { font, size, glyphs, positions, color, embolden, skew, bounds }` | 文字 |

- **字型的型別**：`gfx::FontData`，內容是 `Arc` 共用的字型 bytes、face index 和一個 id。`compositor_paint` 不依賴 parley，由 `layout` 在產生 fragment 時轉換。
- **Raster 端**：用字型 id 快取 Skia 的 `Typeface`（`FontMgr::new().new_from_data`）；關掉 hinting、開啟 subpixel 和 linear metrics，讓 glyph 留在 layout 算出的位置；合成粗體用 `set_embolden`，合成斜體用 `set_skew_x`。parley 的 glyph id 是 `u32`，Skia 的是 `u16`。只用到 skia-safe 的 core 功能，不需要 `textlayout` feature。
- **拆 process 的注意事項**（RFC 0004）：拆 process 後，字型 bytes 不能直接跨 process 共用，要改成像 Chromium 那樣序列化 typeface。

### 7. Lifecycle driver

`renderer` 的 `FrameView` 對應 Blink 的 `LocalFrameView`。
- **入口**：`update_all_lifecycle_phases(&DomReadScope, &StyleEngine, &mut TextContext, viewport)`，依序跑 style → layout → pre-paint → paint，只跑 dirty 的階段，回傳 layer 的 display list 和大小。
- **Dirty flag**：只有 document 層級的 `style_dirty` / `layout_dirty`。Navigation 之後兩個都設起來；style 重算時重建 box tree；viewport 改變時設 `layout_dirty`。節點層級的 dirty flag 在 P4；P3 的 JS 修改 DOM 也只設 document 層級的。P2 另外加了 `box_tree_dirty`（圖片到了）和 `paint_dirty`（捲動容器捲動了），見 `P2.md` 第 5、6 節。
- **持有**：`DocumentHandle`（見 1.6）、box tree 和最後的 display list。Fragment tree、property trees 和 `PaintArtifact` 每次從頭產生，用完就丟；P2 為了捲動和 hit testing，開始保留最後一次的 fragment tree 和 pre-paint（見 `P2.md` 第 6、7 節），P4 的 invalidation 需要時再保留更多。
- **Tracing**：style、layout、paint 各有一個 `tracing` span；接上 `tracing-chrome` 之後（還沒有），就能用 Perfetto 看每個 frame 的時間分布。

### 8. Reftest harness

- **Runner**：`4ff8d6e:crates/shell/tests/reftest.rs`（`harness = false`），用 `cargo test -p shell` 加上 `--test reftest [-- FILTER...]`（`4ff8d6e` 時的指令） 執行。`shell` 拆成 lib + bin：lib 有 `headless::render`（回傳像素）和 `reftest`（WPT 語意的邏輯，有自己的單元測試），bin 加上視窗和參數解析。
- **兩個 suite**，各有自己的 `expectations.txt`：`tests/reftests/`（自己寫的）和 WPT 的子集（2026-10-05 起從 `../third_party/wpt` 讀、清單在 `4ff8d6e:tests/wpt/reftest-include.txt`，id 是 `wpt/css/...`，來源和挑選方式見 `tests/wpt/README.md`）。檔案可以是 `.html`、`.htm`、`.xht`、`.xhtml`。
- **語意照 WPT**（對照 `wptrunner` 的 manifest 和 `RefTestImplementation`）：
  - 有 `<link rel=match>` 或 `<link rel=mismatch>` 的檔案才是測試。通過的條件：有 `match` 時至少一個相同，而且每個 `mismatch` 都不同。
  - `<meta name=fuzzy>`：兩個值都可以寫名稱或按位置，範圍含兩端，單一數字 `n` 等於 `n-n`；前綴 `ref.html:` 只套用在那個 reference。
  - 用我們自己的 `html` parser 讀 metadata（WPT 的 manifest 用 html5lib）。
  - 還不支援：reference 本身又有 reference（chain）、`reftest-wait`、絕對或以 `/` 開頭的 `href`，遇到就報錯而不是忽略。
- **執行方式**：每個頁面開一個新的 `WebContents`，viewport 800×600、一律用測試字型；reference 的結果在同一次執行裡共用。每個測試都會建立再銷毀一個 V8 isolate，所以也一直在測 teardown 的路徑（見 1.5）。
- **XHTML**：CSS2 的 WPT 測試是 `.xht`。Loader 給它 `application/xhtml+xml`，renderer 也交給 HTML parser，只先拿掉 CDATA 區段的標記（reference 常把 `<style>` 的內容包在 CDATA 裡，XML parser 會拿掉這些標記，HTML parser 不會）。
- **Expectation 檔**：Chromium `TestExpectations` 的子集：`<id> [ Failure ]`（照跑）或 `[ Skip ]`（不跑）。和 tree-construction 的 expectations 一樣，標了失敗卻通過、或列了不存在的測試，都會讓這次執行失敗。
- **失敗時的輸出**：照 Chromium web test 的命名，把 `<id>-actual.png`、`-expected.png`（決定結果的那個 reference）和 `-diff.png`（不同的像素標紅）寫到 `target/reftest-results/`。
- **`harness/mismatch.html`**：綠色方塊對空白頁的 `mismatch`，確認 test 和 reference 真的畫出了不同的東西。有一次 mutation 讓所有 box 都走 leaf layout，test 和 reference 都變成空白、B2 照樣通過，就是靠它抓到的。

### 9. 其他

- **`@font-face` 不做**：Ahem 在測試模式下直接內建。WPT 測試裡的 `<link rel=stylesheet href="/fonts/ahem.css">` 會被忽略，不影響結果。P2 起會載入 `<link>`，但這個以 `/` 開頭的網址從 `file:` 載入會失敗，當成空的，結果相同。
- **Rust 版本**：parley 0.11 需要 Rust 1.88，所以 workspace 的 `rust-version` 調到 1.88，`rust-toolchain.toml` 也把 toolchain 釘在 1.88.0。原本實際編譯用的是 rustup 預設的 nightly，`rust-version` 只是最低版本，並沒有真的用 1.88 驗證過；釘住之後，測試的就是宣稱支援的版本。兩者要一起調，調了之後要重新產生 `dom` 的 compile-fail 預期輸出（`TRYBUILD=overwrite`），並確認每個檔案的錯誤種類和位置沒變。2026-10-02 一起升到 1.99（`rust-version` 1.99、toolchain 1.99.0）：新的 clippy lint 改了兩處測試，compile-fail 的預期輸出只有措辭和排版不同。

Shorthand：`margin`、`padding`、`border`、`border-top` / `-right` / `-bottom` / `-left`、`border-width` / `-style` / `-color`、`background`（只接受一個顏色或 `none`）、`overflow`、`font`（`[style || weight]? size [/ line-height]? family`，省略的部分回到初始值）、`text-decoration`（只接受線的種類）。

值：
- **長度**：`px` 和其他絕對單位（`in` / `cm` / `mm` / `q` / `pt` / `pc`）、`em`、`rem`、`%`，以及不帶單位的 0；沒有 `calc()` 和 viewport 單位。
- **顏色**：具名顏色、hex（3 / 4 / 6 / 8 位）、`rgb()` / `rgba()`（逗號和空白兩種語法）、`transparent`、`currentcolor`。
- **`font-size`**：長度、百分比、`xx-small` 到 `xxx-large`（Chromium 在 16px 預設下的大小）、`larger` / `smaller`（乘或除以 1.2）。
- **`font-weight`**：1–1000、`normal` / `bold`、`bolder` / `lighter`（照 css-fonts 的對照表）。
- **CSS-wide keyword**：`initial`、`inherit`、`unset`。
