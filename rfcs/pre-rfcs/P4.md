# P4 Chromium 式 compositor

2026-10-02 規劃，2026-10-04 完成：在 macOS 上驗收（見 `PROGRESS.md`）。驗收之後追加 P4.4（記憶體，第 75 條），2026-10-04 完成。每個子階段開始前才決定那段的事，決定和理由都在「已決定的事項」。

總規劃（`MVP.md`）裡 P4 的內容是：cc thread（main / impl 分開、pending / active tree、在 impl thread 上捲動）、layerize、invalidation；驗收是「JS 卡住時捲動仍然順暢」。原本也排在 P4 的 taffy flex / grid，2026-10-02 拆成 P5（2026-10-04 再改成 RFC 0003，MVP 到 P4 為止）：它和 compositor 無關，又夠大，放在一起會讓兩種風險（多 thread 的 compositor、layout 的正確性）疊在一起。這份文件記錄 P4 的範圍、子階段、設計決定和理由；驗收結果、做過的檢查和已知限制寫在 `PROGRESS.md`。

## 目標 ✅

- **驗收**：
  - **JS 卡住時捲動仍然順暢**：main thread 被 script 卡住的期間，滾輪和鍵盤照樣捲動 viewport，compositor 照樣送出新的 frame。由兩層自動測試檢查（第 1 節的「測試」）：`compositor` 的單元測試一步一步驅動 pipeline 的階段；端到端測試（`browser` 的 `DrivenViz`）讓 script 真的卡住，檢查捲過的 frame 和它的 ack 比卡住的那個 input 的 ack 先到。另外在視窗裡手動確認。
  - 下面「第四批 reftest」全部在 headless 模式通過（測試字型模式）；之前的 reftest 和 WPT 照樣全部通過。
  - 小的 DOM 修改不再重新 raster 整個 layer：測試數得出只有受影響的 tile 重新 raster。
- **可以看的成果**：`about:demo` 的「Busy for 3 seconds」按鈕，按下去之後照樣能捲動整頁和第一個捲動框；用 `RUST_LOG` 看得到每個 frame 的 style、box tree、layout、paint、raster 各做了多少事。

## P4 之前

P0 到 P3 的 compositor 全部在 renderer 的 main thread 上同步執行，相當於 Chromium 的 `SingleThreadProxy`（當時 `crates/compositor` 的模組文件也這樣寫）：
- **一次做完**：`LayerTreeHost::composite` 依序 commit、raster、draw、送出 frame。`LayerTreeHost` 直接擁有 `LayerTreeHostImpl`，沒有 proxy，也沒有 pending tree：commit 直接換掉整棵 tree，所有 tile 都丟掉。
- **只有一個 layer**：整份 document 畫成 root `PictureLayer` 的一份 display list（`paint::to_display_list`）。layer 沒有 transform、clip、opacity，`DrawQuad` 也沒有 transform。
- **Raster 在 main thread 上**：interest rect（看得到的範圍外加一個 viewport）裡沒有 resource 的 tile，當場用 `raster::playback` 畫，每個 tile 都走過整份 display list。
- **捲動**：
  - viewport 的位移由 compositor 套用，只捲 viewport 時不 commit、不 raster；
  - 捲動容器的位移在 pre-paint 時畫進 display list，捲一下就要重新 paint、commit、raster 所有 tile；
  - 滾輪和鍵盤的 input 在 main thread 上處理（`renderer` 的 `scroll.rs`），viewport 的位移等下一個 `BeginFrame` 才送進 compositor，所以 script 卡住時捲不動。
- **`BeginFrame` 和 input 都走 renderer main thread 的同一條 channel**：Viz 的 `BeginFrameSource` 由 `RenderProcessHost::begin_frame_sender` 送 `RendererMsg::BeginFrame`，和 navigation、input 排在同一個 queue。
- **沒有 invalidation**：`FrameView` 的 dirty flag 都是 document 層級的；style 整份重算、box tree 整棵重建、layout 從頭算、paint 整份重畫，每次 commit 所有 tile 重新 raster，damage 一律是整個 viewport。
- **thread 的限制**：`DomIsolate`、`NodeHandle`、V8 都不是 `Send`，一定留在 main thread。`DisplayItemList`（只有幾何、`Arc` 的字型和圖片）、`TransferableResource`、`Arc<BoxFragment>` 可以跨 thread；raster 的字型和圖片快取在 `Mutex` 後面。`LayerTreeHost` 當時不是 `Send`，因為 frame sink 是沒有 `Send` 限制的 `Box<dyn LayerTreeFrameSink>`；`paint::PrePaint` 用 raw pointer 當 key，也不是。

## 範圍

| 項目 | P4 做 | 之後 |
| --- | --- | --- |
| Thread | Renderer 的 compositor thread（cc 的 impl 端）、raster 不在 main thread 上 | 有優先順序的 task queue（scheduler） |
| Commit | Main → impl 的 commit、pending / active tree、activation | Commit 時只送有變的 layer |
| Input | Input 先到 compositor thread：它能處理的捲動不經過 main thread，其他的轉給 main thread | Wheel 和 touch 的 JS 事件（`passive`）、捲動動畫、wheel latching、scroll unification（第 50 條） |
| Layer | 依 property tree 切 layer（`PaintArtifactCompositor`）；到畫面是純平移的捲動容器成為 layer（第 45 條）；`DrawQuad` 的平移 | transform 和 opacity 的 layer（等有 `will-change`、動畫這類合成理由）、任意 transform 的 `DrawQuad`、overlap testing 和 squashing、`position: fixed` / `sticky` |
| Invalidation | 節點層級的 dirty flag；style、layout、paint 局部重算；只重新 raster 受影響的 tile；damage rect | Invalidation sets 的完整版、style sharing、`contain`、paint 的 subsequence 快取和 `PaintLayer`（第 73 條） |
| Viz | `DrawQuad` 的平移 | `ReturnResources`（第 58 條）、partial swap、overlay |

`position: fixed`、`sticky` 和 `will-change` 要等它們的 layout 和 style 先有。Flex / grid 見 RFC 0003（`rfcs/0003-flex-grid/`）。

## 子階段

先拆 thread，因為一做完就能達成驗收，也最早暴露風險：thread 之間要傳哪些資料、哪些東西不是 `Send`、input 和 `BeginFrame` 怎麼繞過 main thread。Layerize 接在後面，讓捲動容器也能在 compositor thread 上捲動。Invalidation 和前兩個比較獨立，排在最後，也方便分工（2026-10-02 決定這個順序）。

| 子階段 | 預估 | 內容 | 驗收 |
| --- | --- | --- | --- |
| P4.1 Compositor thread | 1.5–2 週 | `ProxyMain` / `ProxyImpl`、main thread 的 task queue、commit 和 pending / active tree、`BeginFrame` 直接到 compositor thread、input 先到 compositor thread、viewport 的捲動在 impl 端處理（`InputHandler`、`SyncedScrollOffset`）、frame token 和 ack 的 swap promise、raster 搬出 main thread | 「JS 卡住時捲動仍然順暢」的兩層測試；之前的 reftest 照樣通過 |
| P4.2 Layerize | 1–1.5 週 | `PaintArtifactCompositor`（paint chunk 依 property tree 分成 layer）、compositor 端的 property tree、`DrawQuad` 的平移（Viz 的兩個 renderer 都要支援）、捲動容器在 compositor thread 上捲動、device pixel 的 snapping | 第四批 reftest 的 layer 部分；捲動容器的捲動不重新 raster |
| P4.3 Invalidation | 1.5–2 週 | 節點層級的 dirty flag；style、box tree、layout 局部重算；paint 的 display item 快取和 raster invalidation；damage rect；`ReturnResources` | 數得出重新 raster 的 tile 數；第四批 reftest 的 invalidation 部分 |
| P4.4 記憶體（驗收之後追加，第 75 條） | — | layer 的範圍改成它的 chunk 的聯集；空的和單色的 tile 不留像素；tile 只留一份；GPU device 遺失之後恢復 | 每一小段做完量一次記憶體 |

預估合計約 4–5.5 週，比總規劃原本估的 3–4 週多（原本還包含 flex / grid）：P2、P3 規劃之後都比原估多 50% 到一倍。實際上 2026-10-02 到 2026-10-04 做完，分成 18 段（下面）。

## 設計

這份文件的「main thread」都指 renderer 的 main thread（`CrRendererMain`），和 cc 的用語一樣（main 對 impl）；Browser 的主 thread 寫「UI thread」，就是 `PROGRESS.md` 的 thread 表裡叫 `main` 的那條。

### 1. Compositor thread（P4.1）

對應 Chromium 的 `ProxyMain` / `ProxyImpl`、`LayerTreeHostImpl`、cc 的 `Scheduler` 和 `InputHandler`、Blink 的 `InputHandlerProxy`。
- **Thread**：每個 renderer 一條 compositor thread（Chromium 的 `Compositor` thread），擁有 `LayerTreeHostImpl`、frame sink、raster 和 input 的處理；main thread 只留 `LayerTreeHost`（layer 的狀態和 commit 的發起）。它和 Viz thread 是兩條，不合併（「已決定的事項」第 7 條）。thread 由 `renderer` 建立，迴圈和邏輯（`ProxyImpl`）在 `compositor`（第 15 條）。
- **Compositor thread 的 queue**（第 16、17 條）：和 main thread 一樣只等一條 queue（`CompositorTask`）。Viz 和 Browser 經 `CompositorSender` 送 `protocol::renderer::CompositorMsg`（`BeginFrame` 和 input）；main thread 經 `ProxyMain` 送 commit、`BeginMainFrameAborted`、要不要 main frame；compositor 要 main frame 時，呼叫 renderer 給的 callback，把 `MainThreadTask::BeginMainFrame` 放進 main thread 的 queue。`renderer::channel()` 一次建立兩條 queue，Browser 拿到 `RendererSender` 和 `CompositorSender`；compositor thread 由 `renderer` 在 main thread 之前建立，main thread 結束時 drop 掉 `LayerTreeHost<ProxyMain>`（送出 shutdown），等 compositor thread 結束。`RendererGone` 不是 renderer 送的：Browser 的 IO thread 等 renderer 的 channel 關閉（每個 sender 都被 drop，包括 compositor 那邊 swap promise 抓著的）才自己報告，所以 renderer 送的訊息不可能排在它後面（第 22 條）。main frame 一律以 `commit` 結束：有變化（包括 viewport 的位移）就 commit，帶著 swap promise 時即使沒有變化也 commit，好讓一個 frame 回答它；什麼都沒有就送 `BeginMainFrameAborted`。還沒有 document 或 render-blocked 時用 `abort_main_frame`。
- **Main thread 的 task queue**（第 6 條）：main thread 只等一條 process 內部的 queue，timer 照樣用等待的 timeout。Browser 的訊息（navigation、資源、視窗大小）和 compositor thread 要給 main thread 的（`BeginMainFrame`、轉過來的 input）都放進這條；Browser 透過 `renderer` 提供的 sender 型別送，在送的那條 thread 上包裝。
- **`LayerTreeHost` 兩種模式**（第 5、18 條）：泛型 `LayerTreeHost<P>`。renderer 用 `LayerTreeHost<ProxyMain>`（threaded），Browser 的工具列繼續用 `LayerTreeHost<SingleThreadProxy>`；共用的狀態和方法寫一次，只屬於一種模式的方法（工具列的 `composite()`，renderer 的 `commit`、`abort_main_frame`）放在各自的 `impl`，呼叫錯就是編譯錯誤。兩者共用 `LayerTreeHostImpl`。
- **Commit 不擋住 main thread**（第 2 條）：main 端把要 commit 的狀態（layer、display list 的 `Arc`、viewport、背景色、viewport 能不能被使用者捲、捲動容器的範圍、viewport 的位移、swap promise）整包交給 impl 端就繼續做事，impl 端建成 pending tree。
- **Pending / active tree**：pending tree 在需要的 tile（看得到的範圍）raster 好之後才 activate，成為 draw 用的 active tree；activate 之前照樣用舊的 active tree 畫，所以 commit 不會讓畫面出現還沒 raster 的空白。raster 在 compositor thread 上同步做（第 1 條），所以 commit 一到就 raster、activate，在同一個 task 裡做完，pending tree 不會等到下一個 commit。原本規劃「還沒 activate 的 pending tree 被新的 commit 蓋過」，2b 實作時才發現這在同步 raster 下不會發生；會被蓋過的是 activate 了、還沒畫出來的 tree（例如不等 main thread 時，兩次 commit 之間沒有 `BeginFrame`）。之後 raster 改到 worker、activate 要等 raster 時，pending tree 才會真的被蓋過。display list 是同一個 `Arc` 時，pending tree 沿用舊的 tile（第 20 條）。
- **`BeginFrame` 到 compositor thread**（第 3、8 條）：Viz 的 `BeginFrame` 改送到 compositor thread 自己的 channel；它決定要不要向 main thread 要 `BeginMainFrame`（有 rAF、DOM 改了、有捲動的 delta 要交出去），同時只有一個在路上。main thread 沒有東西要更新時回 `BeginMainFrameAborted`（Chromium 同名），compositor 不再等它。畫之前等不等 main thread 是設定 `wait_for_all_pipeline_stages_before_draw`（Chromium 同名），由 `RendererFlags` 決定：
  - 開（headless 和 reftest）：等 main thread commit、raster、activate 完才畫，一個 `BeginFrame` 對應一次 main frame，結果確定；
  - 關（視窗模式和「測試」的端到端測試）：立刻用 active tree 畫，main thread 的結果在下一個 `BeginFrame` 才畫出來；main thread 卡住時照樣出 frame（只有 impl 端的捲動）。P4 不做 deadline。
- **Input 先到 compositor thread**（第 3、4、11、24、25 條）：Browser 的 input 也送到 compositor thread 的 channel（`CompositorMsg`）。決定自己處理還是轉給 main、以及回 ack 的那一層（Chromium 在 Blink 的 `InputHandlerProxy`）也放在 `compositor`；轉給 main 的 input 和 `BeginMainFrame` 經同一個 callback（`ToMainThread`），都附上還沒交出去的捲動 delta。
  - compositor 的 `InputHandler` 處理 viewport 的捲動：不在捲動容器範圍裡的滾輪，以及鍵盤；P4.2 起也捲成為 layer 的容器（第 2 節）。它有 viewport 的 scroll node（容器大小、內容大小、兩個軸能不能被使用者捲）。捲動的純計算從 `crates/renderer/src/scroll.rs` 搬進 `compositor`（第 29–33 條）：`ScrollNode`（對應 `cc::ScrollNode`：容器大小、內容大小、兩個軸能不能被使用者捲；最大位移、夾值、`scroll_by`），以及按鍵和滾輪換算成位移（`PIXELS_PER_LINE`、`PAGE_FRACTION` 兩個常數；按鍵照 Chromium 的 granularity，和目前的位移無關）。main thread 捲動容器、傳給 viewport 時也用同一份：renderer 把 paint 的每個 scroll node 轉成 `ScrollNode`，viewport 的在 layout 時建好。
  - 需要 main thread 的轉給 main thread：點擊、移動，以及落在範圍裡的滾輪（第 40、42、52 條）。範圍放的是 compositor 不能自己捲的捲動容器：沒成為 layer 的，和被畫在它之後的東西蓋到的（連同它裡面的）；使用者捲不動的容器不放。每個是容器的 border box，經過它外面的 clip（不是它自己的 overflow clip，也不用 viewport 裁），有 transform 時取外接矩形，先在容器自己的座標往外取整到整數 CSS px、再多放 1px。範圍依「哪個成為 layer 的容器移動它」分開放（document 一份、每個容器一份，在它內容的空間），compositor 捲那個容器時跟著移動；`paint` 在 pre-paint 時算出來，放在 compositor 的 property tree 上隨 commit 送過去（cc 的 `main_thread_scroll_hit_test_region`）。範圍只能比 main 的 hit test 大：大了只是多轉給 main。compositor 用 active tree 的範圍，加上自己畫出來的位移再比對。
  - compositor 對每個 input（第 41 條，對應 `InputHandlerProxy` 的 `DID_NOT_HANDLE` / `DROP_EVENT` / `DID_HANDLE`）：滑鼠事件轉給 main；畫出來的不是 active 的 document 時，滾輪和按鍵的 ack 立刻回 `None`；落在範圍裡的滾輪轉給 main；其他的滾輪從游標下最裡面的、成為 layer 的容器開始捲，捲不完的交給外層，最後是 viewport（第 2 節）；按鍵捲 viewport。有移動時 ack 掛在下一次 draw，沒移動時立刻回 `None`。按鍵不再到 main（第 43 條）。
- **捲動位移的同步**（第 12、35–39 條）：viewport 的位移照 cc 的 `SyncedScrollOffset`，記成四份相加：`base`（main thread 最後 commit 的值）、`reflected`（隨 `BeginMainFrame` 交出去、它的 commit 一定包含的）、`after`（那之後隨轉給 main 的 input 交出去的，每則一筆）、`unsent`（compositor 捲了、還沒交出去的）。
  - `BeginMainFrame` 和轉給 main 的 input 都把 `unsent` 交出去（第 35 條）；main thread 一收到就套用（夾在自己的範圍裡），之後可以再改（`#fragment`、捲動容器捲到底傳出來的捲動、layout 之後的夾值），有變化時把結果 commit 回去；只套用了 compositor 的捲動、沒有別的更新時，main frame 照樣 abort（第 36 條）。
  - commit 時 `base` 換成 main thread 的值、`reflected` 歸零，再照 main 之後套用的順序把 `after` 和 `unsent` 夾回新的範圍（第 38 條）。所以兩邊的捲動相加，main thread 跑一個 frame 期間使用者捲的量不會被 commit 蓋掉，畫面不會往回跳。abort 時什麼都不動（第 36 條）。
  - 轉給 main thread 的 input 附上還沒交出去的 delta，main thread 先套用再處理，hit testing 用的是使用者看到的位置。
  - delta 帶著它所屬的 document id（第 27、39 條）：active tree 和最後畫出來的不是同一份 document 時 compositor 不捲，所以 delta 的 document 就是畫出來的那份；main 不套用不是目前 document 的 delta；compositor 在 commit 時發現 document id 換了，就丟掉四份裡的三份 delta，所以舊頁面上的捲動不會被帶進新頁面。
  - 位移用 CSS px 的浮點數記，畫的時候才取整到 physical pixel。P4.2 每個捲動容器也用同一套。
- **Frame token 和 ack 用 swap promise**（第 9、10 條）：
  - main thread 把只差 frame token 的 `DidFinishLoad`、`ReftestWaitEnded` 掛在 commit 上（cc 的 `SwapPromise`）；compositor 送出含有那次 commit 的 frame 之後填上 token，從 compositor thread 送給 Browser。沒畫出 frame（例如 viewport 是空的）時 token 是 `None`。promise 從 activate 起等到下一次 draw：activate 了、還沒畫出來就被新的 commit 蓋過時，它跟著留下來，由畫出新 commit 的那個 frame 兌現。
  - `InputEventAck` 也帶 frame token（第 26 條）：compositor 處理的 input 由 compositor 自己回 ack，掛在下一個要畫的 frame，捲不動時立刻回 `None`；轉給 main thread 的，處理**期間**要求了 main frame 才掛在下一次 commit，否則立刻回 `None`。headless 等到畫過所有 ack 帶的 token 中最大的那個才截圖。
    - 「處理期間要求了 main frame」：main thread 每次要求 main frame 都加一次計數，處理一個 input 的前後比較（第 26 條）。event 跑了 script 一律要求 main frame，所以在 listener 裡呼叫 `requestAnimationFrame` 也涵蓋在內；代價是每個點擊（`click` 會跑 script）的 ack 都等 frame，即使 script 什麼都沒改（P4.3 之後那個 main frame 什麼都不做就結束）。
    - 等 frame 的 ack 留在 main thread，跟下一次真正的 commit 一起交出去。render-blocked 而 abort 的 main frame 不交，等之後的 commit，和 Chromium 延後 commit（`DeferMainFrameUpdate`）時 swap promise 留在 main 端一樣。
- **Input 屬於使用者看到的 document**（第 27 條）：compositor 每次 draw 時記下這個 frame 是哪一份 document（commit 帶著 document 的 `navigation_id`），轉給 main 的每個 input 都帶著它；main 丟掉不是目前 document 的、不是滑鼠移動的 input，ack 回 `None`。這擋住 input 和導航走不同的 queue 造成的競爭：main 換成新 document、新頁面還沒畫出來時，使用者點的是仍然顯示的舊頁面。還沒畫出任何 frame 時（例如 viewport 是空的）input 帶的是 `None`，滑鼠移動以外的也都丟掉：使用者什麼都沒看到，談不上點了什麼。滑鼠移動不丟，因為它只設定游標。
- **Raster 在 compositor thread 上**（第 1 條）：raster worker 等真的需要時再加。
- **測試**（第 13 條）：兩層。
  - `compositor` 的單元測試，仿照 cc 的 `LayerTreeHostScrollTest`：不開 thread，一步一步驅動 `BeginMainFrame`、commit、activate、draw，在中間插入 impl 端的捲動：只在 impl 端捲、`BeginMainFrame` 和 commit 之間又捲、main frame 被放棄、main thread 自己也捲、activate 時夾值。結果完全確定。
  - 端到端測試，用 `browser` 測試裡的 `DrivenViz`（測試自己扮演 Viz，看得到每個 frame 的 token 和每個 ack），分頁關掉 `wait_for_all_pipeline_stages_before_draw`：click handler 忙等約 500 ms（`while (Date.now() < end) {}`），期間送滾輪，捲過的 frame 和滾輪的 ack 都比點擊的 ack 先到；忙等結束後點一個連結，確認 hit testing 用的是捲過的位置。判斷用訊息的先後，不量時間，所以忙等不必長（第 44 條）。
  - 「順不順」（frame 的間隔）不做成 pass/fail，之後接上 `tracing-chrome` 再用 Perfetto 看。

### 2. Layerize（P4.2）

對應 Blink 的 `PaintArtifactCompositor`、`PropertyTreeManager` 和 cc 的 property trees（第 45–48 條）。
- **哪些成為 layer**：只有到畫面的 transform 是純平移的捲動容器，它的內容（scroll translation 底下的 chunk）成為獨立的 layer；transform、opacity、clip 照樣畫進所在的 layer（第 45 條）。所以 compositor 和 Viz 只處理平移。
- **chunk 怎麼分成 layer**：照 paint 順序依序切段，不做重疊判斷：「容器之前的」、「容器的內容」、「容器之後的」各成一個 layer，一定不會畫錯順序（第 46 條）。
- **compositor 端的 property tree**：照 cc，transform / clip / effect / scroll 四棵樹，layer 記著它在每棵樹的節點，捲動位移放在 scroll 節點上，draw 時才算出 quad 的位置和 clip；viewport 是 scroll tree 的根（cc 的 root scroller）。paint 的樹由 `PaintArtifactCompositor` 轉過去（第 47 條）。
- **Layer 的空間和轉換**（第 49 條）：`paint` 的 `layerize` 把 chunk 分成 `PendingLayer`，每個 layer 的 display list 畫在自己的空間裡（容器的 scroll translation，原點在 padding box 的左上角，沒有捲動）；renderer 的 `compositing.rs` 把它們和 paint 的 property tree 轉成 compositor 的 `PictureLayer` 和 property tree（`PropertyTreeManager`）。compositor 的 transform 節點只有平移，容器的 scroll translation 節點記著元素，位移每次 commit 帶過去；layer 從前往後畫，每個 layer 的 clip 是它的 quad 的 `SharedQuadState`，Viz 不用改。main 捲成為 layer 的容器時只重跑 pre-paint（hit testing 要用），不 paint 也不 raster。
- **Compositor 捲容器**：compositor 有自己的 scroll tree（成為 layer 的容器，各有 parent），每個容器的位移照 viewport 的方式同步（第 35–39、51 條）；滾輪找游標下最裡面的、成為 layer 的容器捲，捲到底交給外層，最後是 viewport。容器被畫在它之後的東西蓋到，或往外層傳時會經過沒成為 layer 的捲動容器，就照第 1 節轉給 main（第 48、50、52 條）；之後改成 Chromium 的 scroll unification。main 套用 compositor 捲的容器位移時，還是 layer 的只重跑 pre-paint，已經不是 layer 的才重新 paint。
  - 範圍依「哪個容器移動它」分開：不在任何成為 layer 的容器裡的在 document 的空間，在容器裡的放在最內層那個容器的 scroll node 上、在它內容的空間，compositor 捲那個容器時跟著移動。範圍放在 property tree 上，不在 layer 上（沒畫任何東西的容器沒有 layer）。
  - compositor 判斷滾輪：在任何範圍裡就轉給 main；否則選 border box（被外面的 clip 裁）包含游標的最內層容器。用畫出來的位移比對，包括還沒交出去的。
- **對齊 device pixel**（第 53、54 條）：layout 照舊用 CSS px，`paint` 知道 device scale factor，把背景、border 的外緣、overflow clip、圖片、文字的 baseline、捲動容器的位移取整到 device pixel（`round(x × dsf) / dsf`，Blink 的 `PixelSnappedIntRect`），border 寬度照 css-values 往下取整到整數 device px、至少 1 個；成為 layer 的容器，layer 的範圍也取整。display list 照舊是 CSS px；compositor 的捲動位移用同一套取整。reftest 用 `<meta name=machopo-device-scale-factor>` 指定倍率。
- Viewport 要不要也成為 **paint** 的 scroll node：第 47 條讓它成為 compositor scroll tree 的根，paint 這邊不動（改了會牽動 hit testing、pre-paint 和滾輪找容器的走法）。

### 3. Invalidation（P4.3）

對應 Blink 的 style invalidation、`NeedsReattachLayoutTree`、`LayoutObject::SetStyle` / `SetNeedsLayout`、layout result cache、`PaintController` 和 `RasterInvalidator`。由下往上做（第 55 條）：先 raster，最貴，一做完就量得到；再往上游一層層換成局部重算。每一層都和整份重做的結果比對，做了多少事用 `RUST_LOG=style=debug,layout=debug,paint=debug,compositor=debug` 看。
- **DOM 記下哪裡改了**（第 60、66 條）：每個節點有兩組不被 trace 的 flag（`StyleFlags`、`LayoutTreeFlags`），修改的方法設好自己的，並往上把祖先的「子孫裡有」設起來，停在已經有的那個。插入：被插入的節點要重算 style、要重建 box，父節點的子節點變了；刪除：父節點的子節點變了；改屬性：那個元素要重算 style，父節點的子節點變了（兄弟選擇器）；改文字：父節點的子節點變了（`:empty`），文字節點要重建。整個 isolate 有 `dom_tree_version`（Blink 的 `Document::DomTreeVersion`），`FrameView` 看到它沒變、也沒有別的原因（stylesheet 載入、viewport、dsf……）時，整個 lifecycle 都跳過。lifecycle 從 read scope 設、讀、清這些 flag，和寫 computed style 一樣是 lifecycle 的狀態。
- **Style**（第 61、63 條）：只往有 flag 的路徑走，以子樹為單位重算：自己要重算的元素連同整個子樹；stylesheet 裡有看兄弟或結構的選擇器時，子節點變了的元素也重算；有 `:has()` 時任何修改都整份重算；stylesheet 的文字變了整份重算（`StyleEngine` 記住解析過的）。新的 computed style 和舊的值不同時，標給 box tree（`style_changed`）；整個子樹被重算時大多數的值沒變，不標。
- **Box tree**（第 65–68 條）：box tree 記著每個元素的 block box（Blink 的 `Node::GetLayoutObject`），沿著 layout tree 的 flag 往下走，記著每個節點所在的容器（最近的有 block box 的祖先）：
  - 換了 style 的元素，拿 box 裡的舊 style 和新的比（`StyleDifference`）：`display` 不同就重建；只差在顏色、背景、border 的顏色和樣式、文字裝飾、`opacity`、`transform` 時只換 style（box、匿名 block、inline content 裡的文字、邊、圖片），不重新 shape、不重排；其他的換 style 和 taffy style，並重新收集自己的內容。inline 元素沒有 box，舊的 style 從所在容器的 inline content 找。
  - 插入、搬移、改文字、`display` 變了的，所在的容器重新收集內容，重新 shape 它的文字；沒變的 block 子 box 連同子樹沿用，不再持有的 box 釋放，位置留給之後的 box。重建的元素裡面一律新建（那裡的 flag 沒看過）。
  - root、`<body>`、給 viewport 的 `overflow` 變了才整份重建。
- **Layout**（第 69–71 條）：box 記著父 box。style 有排版上的變化的、重新收集過內容的、新建的 box，清掉自己和往上所有祖先的 taffy cache（Blink 的 `SetNeedsLayout` 加上 `MarkContainerChainForLayout`），其他 box 的 cache 留著，taffy 碰到結果不變的子樹直接用 cache。viewport 變了不用另外處理：它是 taffy cache 的 key 的一部分。每個 box 記著上次的 `Arc<BoxFragment>`，沒被重排、也沒換 style 的直接沿用，被推開的也一樣（位置在父 fragment 的 `FragmentLink` 上）。`InlineContent` 記住上次斷行的寬度，同樣的寬度不重新斷行。
- **Paint**（第 72–74 條）：`PaintController` 跨 paint 記著每個 box 在背景和文字兩個階段畫了哪些 display item。fragment 還是同一個 `Arc`，或只因為子孫變了而換了 fragment、但自己的 style、大小、圖片都一樣的容器，而且 pre-paint 給它的位置和 property tree 狀態、背景有沒有給 canvas 都沒變，就直接搬上次的 item（Blink 的 `UseCachedDrawingIfPossible`）。paint 照舊走過整棵 fragment tree，沒有 Blink 整段沿用的 subsequence 快取。
- **Raster**（第 56–59 條）：`PaintedLayer`（Blink 的 `RasterInvalidator`）用穩定的身分（節點、種類、同一個節點這種 item 的第幾個）比對每個 layer 新舊的 display item，有變、移動、新增、刪除、順序變的，新舊兩個位置都重新 raster；所在 chunk 的 transform、clip、opacity 變了也一樣。從上一次 paint 搬來、沒變的 item 不比內容。layer 依「移動它的容器、第幾個」保有同一個 id，帶著要重新 raster 的範圍；compositor 只重新 raster 範圍碰到的 tile（整個 tile），保留其他的；layer 沒有要重新 raster 的，沿用上次的 display list。frame 帶 damage rect（Viz 照舊整個重畫）。
- **和 Chromium 的差別，和之後**：style 沒有 invalidation sets（第 61 條）；box tree 以整個 block 的內容為單位重新 shape（Blink 會沿用沒變的 shape 結果）；layout 沒有 relayout boundary；paint 沒有 subsequence 快取和 `PaintLayer`（第 73 條）；raster invalidation 對重畫的 box 照舊比 item 的內容，Blink 看每個 client 被 invalidate 的原因（第 72 條）；沒有 partial raster（第 57 條）和 `ReturnResources`（第 58 條）。

## 已決定的事項

2026-10-02 確認（P4.1）：

1. **Raster 先在 compositor thread 上做**，raster worker（Chromium 的 `TileTaskManager`）等 P4.3 之後真的需要時再加。驗收只要求 raster 不在 main thread 上；raster 的字型和圖片快取已經在 `Mutex` 後面，之後拆成 worker 不用改介面。不選現在就做 worker：要多處理 tile 的排程，和 activation 等待非同步的 raster。
2. **Commit 不擋住 main thread**：commit 的資料都是不可變的（display list 是 `Arc`），main 端整包交出去就繼續做事，impl 端建 pending tree（raster 同步，馬上 activate，見第 1 節的「Pending / active tree」）。Chromium 的 commit 讓 main thread 等 impl 端複製完，因為它的 layer tree 是可變的；我們沒有這個需要。
3. **Renderer 多一條 channel 給 compositor thread**（對應 Chromium 的 compositor thread 自己的 mojo pipe）：Viz 的 `BeginFrame` 和 Browser 的 input 都送到這條，compositor thread 需要時再轉給 main thread；main thread 只收 navigation、資源、視窗大小，和 compositor thread 轉過來的東西（第 6 條）。不選維持一條 channel、由 main thread 轉送：main thread 卡住時 `BeginFrame` 和 input 也跟著卡住，達不到驗收。
4. **P4.1 的捲動容器上的滾輪轉給 main thread**：main thread 每次 commit 附上捲動容器的範圍（Chromium 的 main thread scroll hit test region）；滾輪落在範圍外，compositor thread 自己捲 viewport，落在範圍內，轉給 main thread 照現在的方式處理。P4.2 捲動容器變成 layer 之後再改。不選所有滾輪都轉給 main thread：驗收時滾輪捲不動。
    - **之後的變化**：P4.2 改了：成為 layer 的容器由 compositor 自己捲，只有沒成為 layer 的和被蓋到的容器還在範圍裡、轉給 main（第 48、50、52 條）。
5. **Browser 的工具列繼續 single-threaded**：它在 UI thread 上，只在工具列改變時送 frame，不需要 compositor thread；`LayerTreeHost` 保留 single-threaded 的模式給它用（`LayerTreeHost<SingleThreadProxy>`，第 18 條）。Chromium 的 `ui::Compositor` 也是用 `cc::LayerTreeHost::CreateSingleThreaded`。

2026-10-02 確認（P4.1 的細節，第 1 節）：

6. **Main thread 只等一條 process 內部的 task queue**：Browser 的訊息和 compositor thread 給 main thread 的都放進這條；Browser 透過 `renderer` 提供的 sender 型別送，在送的那條 thread 上包裝，不加 thread。
   - **Chromium**：IPC 先到 renderer 的 IO thread（`Chrome_ChildIOThread`），看 mojo pipe 綁在哪條 thread，post task 到那條 thread；compositor 也是 post task 給 main thread（例如 `ProxyMain::BeginMainFrame`）。main thread 的 run loop 只處理 task，Blink 的 scheduler 在底下分成有優先順序的 queue。
   - **不現在就加 renderer 的 IO thread**：拆 process（RFC 0004）之前沒有 IPC 給它讀，只是轉手。拆 process 時讀 IPC 的地方（ipc-channel 的 router，或自己的 IO thread）接手包裝；不管現在加不加，那一端到時候都要改。撐得過拆 process 的是 main thread 的 queue，兩種做法一樣。
   - **不選 `crossbeam-channel` 的 `select!` 同時等兩條 channel**：兩條都有訊息時它隨機挑一條，Browser 和 compositor 的訊息誰先處理每次可能不同；一條 queue 就是放進去的順序。和 Chromium「全部都是 task」的模型也不同，之後有優先順序的 scheduler 也是從這條 queue 長出去。（原本還寫了「P6 的 `IpcReceiver` 也不能放進去」，查了 ipc-channel 之後發現不對：它的 router 能把 `IpcReceiver` 轉成一般的 crossbeam receiver，見第 14 條。）
   - **不選把 compositor 給 main thread 的訊息放進 `protocol` 的 `RendererMsg`**：那是 Browser 和 renderer 之間的協定（`.mojom`），型別上會允許 Browser 送 process 內部的訊息；拆 process 之後同一個 process 裡的訊息還得經過 IPC。
7. **Compositor thread 不和 Viz thread 合併**：
   - 兩者屬於不同的 process：compositor 是 renderer 的，Viz 在 Browser 這邊（Chromium 在 GPU process）。拆 process 時一定要分開，`CompositorFrame` 就是那條邊界；cc 處理頁面的 display list 和 raster，應該留在之後會被 sandbox 的 renderer 裡。
   - 一個 Viz 合成所有 client（工具列和每個分頁），每個 renderer 有自己的 compositor。合在一起，一個分頁 raster 很慢時，工具列和其他分頁都跟著停；`viz` 也要依賴 `compositor` 和 `raster`，crate 的分層不再對應 Chromium。
   - 合併省下的只是一次 channel 的轉送。Chromium 最接近的是 Android WebView 的 synchronous compositor（renderer 的 cc impl 端跑在 app 的 render thread 上），那是嵌進 app 的 view 系統時沒有選擇的特例。
8. **畫之前等不等 main thread 是設定**（`wait_for_all_pipeline_stages_before_draw`）：headless 和 reftest 開，視窗模式和第 13 條的端到端測試關；關的時候 P4.1 不做 deadline，main thread 的結果固定晚一個 frame 畫出來。
   - **Chromium**：cc 的 `Scheduler` 收到 `BeginFrame` 之後等 main thread 的 commit，等到 deadline 為止（`SchedulerStateMachine` 的 `BeginImplFrameDeadlineMode`），趕不上就畫舊的 active tree；一直趕不上時進入 high latency mode，不再等。`wait_for_all_pipeline_stages_before_draw`（`--run-all-compositor-stages-before-draw`）讓它一定等，headless Chrome 的 deterministic mode 用它。Blink 的 web test 長期用 single-threaded compositor 求結果確定；2023-06-12 起在 Linux 上改成預設 threaded，不穩定的測試放進 quarantine list 繼續用 single-threaded。
   - **不選永遠不等**：headless 的 `BeginFrameSource` 在 client 回答之後立刻送下一個，虛擬時間會在 main thread 還在跑時一直往前，rAF 收到的 frame time 跳過幾個 frame 要看機器的速度，J5 這類測試會不穩定。
   - **不選現在就做 deadline**：結果要看 wall clock；有優先順序的 scheduler 排在之後，到時一起做。
   - **不選一律等**：main thread 卡住時 compositor 也卡住，達不到驗收。
9. **`DidFinishLoad` 和 `ReftestWaitEnded` 的 frame token 用 swap promise**：
   - **Chromium**：`LayerTreeHost::QueueSwapPromise` 把 `SwapPromise` 掛在 commit 上；含有那次 commit 的 frame 送出時呼叫 `WillSwap`，拿得到 frame 的 metadata，沒畫出來時呼叫 `DidNotSwap`。我們的 commit 還沒畫出來就被新的 commit 蓋過時，promise 留下來由下一個 frame 兌現，對應它的 `KEEP_ACTIVE`。
   - **不選在 frame 的 metadata 加上 commit 的編號、Browser 等「編號夠新的 frame」**：Chromium 的 metadata 沒有這個欄位，headless、`browser_view` 和其他測試的等待都要改。
   - **不選 main thread 等 compositor 回 token**：違反第 2 條。
   - `DidFinishLoad` 改從 compositor thread 送出之後，main thread 在那之後送的訊息（例如下一次導航的 `DidCommitNavigation`）可能比它先到 Browser。這沒有害處：`WebContents` 收到 `DidFinishLoad` 只記 log，headless 和測試只認最新導航的。會出問題的是舊導航的 `DidFinishLoad` 晚於新導航的（headless 會一直等），而 promise 照 commit 的順序兌現，所以不會發生，由 `compositor` 的測試守住（P4.1 第 2c 段之後補上）。
10. **`InputEventAck` 帶 frame token**，用第 9 條的 swap promise 填，沒有可見的變化就立刻回 `None`。
    - **和 Chromium 不同**：Chromium 的 ack 只代表處理完了（`InputHandlerProxy` 的 `DID_HANDLE` / `DID_NOT_HANDLE`），立刻回；哪個 frame 看得到結果另外用 `LatencyInfo` 追蹤（`LatencyInfoSwapPromise` 把它列進 frame 的 metadata）。Browser 依 ack 做事，例如 `MouseWheelEventQueue` 等前一個的 ack 才送下一個滾輪事件，所以 ack 要快。
    - **為什麼現在不照做**：P4.1 沒有東西依賴 ack 要快（`WebContents` 收到 ack 不做事）；ack 帶 token 用的是第 9 條同一套機制，headless 能確定截到哪個 frame。之後有依賴 ack 的功能（Browser 端的滾輪 queue、`passive` listener、touch）時，改成 Chromium 的做法。
    - **不選只把 ack 延到 frame 送出之後**：frame 走 Viz 的 channel，ack 走 Browser 的，headless 仍可能先收到 ack，截到更早的 frame。
11. **Viewport 的捲動在 compositor 處理**：`InputHandler` 和 viewport 的 scroll node，捲動的純計算搬進 `compositor`、renderer 共用；commit 帶上能不能被使用者捲和捲動容器的範圍。
    - **Chromium**：cc 有 `ScrollTree`，compositor thread 上的 `InputHandler`（`ThreadedInputHandler`）在 cc 的 layer tree 上 hit test、捲動、往外層傳遞；落在 `MainThreadScrollHitTestRegion` 裡的才需要 main thread（scroll unification 之後只請它 hit test，捲動仍在 compositor 上）。我們 P4.1 把那些滾輪整個轉給 main thread 捲（第 4 條）。
    - **鍵盤和 Chromium 不同**：Chromium 的 `keydown` 先分派給 JS，沒有被 `preventDefault` 才由 Blink 捲，所以 main thread 卡住時鍵盤捲不動。machopo 還沒有 `keydown` 事件，結果一樣；加上 `keydown` 之後，按鍵改成先到 main thread。
    - **不選規則留在 renderer、用 trait 注入 compositor**：`compositor` 不能依賴 `renderer`，compositor 的行為要看外面塞進來的東西，Chromium 沒有這種形狀，也比較難測。
    - **不選由 Browser 換算成像素**：Chromium 的滾輪在 Browser 端就換成像素，這部分之後可以照做；但 PageDown、Home、End 要知道 document 的大小，Browser 不知道。
12. **捲動位移照 `SyncedScrollOffset` 同步**：
    - **Chromium**：cc 的 `SyncedProperty`：`PullDeltaForMainThread` 在 `BeginMainFrame` 交出 delta，main thread 用 `LayerTreeHost::ApplyCompositorChanges` 套用（Blink 以 `ScrollType::kCompositor` 設定位移），`PushMainToPending`、`PushPendingToActive` 在 commit 和 activate 時扣掉交出去的量。
    - **轉給 main thread 的 input 附上 delta，和 Chromium 不同**：Chromium 只在 `BeginMainFrame` 交出 delta，main thread 卡住期間使用者捲了再點擊，main thread 的 hit testing 用的是捲動之前的位置。
    - **位移用 CSS px 的浮點數記**，畫的時候才取整。原本 compositor 存取整到 physical pixel 的值，`base` 和 `delta` 加加減減會累積誤差。Chromium 也是存沒有取整的位移，draw 時才對齊像素。
    - **不選 compositor 擁有位移、main thread 只送「捲到哪裡」的指令**：main thread 要分清楚哪些改變是自己的、哪些是抄來的，夾值要兩邊各做；P4.2 捲動容器多了之後更麻煩。
    - **不選直接採用 main thread commit 的值**：main thread 跑一個 frame 期間使用者捲的量會被蓋掉，畫面往回跳。
13. **「JS 卡住時捲動仍然順暢」用兩層測試**（第 1 節的「測試」）：
    - **Chromium**：cc 的 `LayerTreeTest` 讓同一個測試用 single-threaded 和 multi-threaded 各跑一次，靠 pipeline 階段的 callback（`DidCommit`、`DidActivateTreeOnThread`、`DrawLayersOnThread`……）控制時間點；捲動的在 cc 的 `layer_tree_host_unittest_scroll.cc`（例如 `LayerTreeHostScrollTestImplOnlyScroll`、`LayerTreeHostScrollTestScrollAbortedCommit`）。我們沒找到 Chromium 用真的 JS 忙等來判斷對錯的端到端測試；卡不卡由 tracing 量。
    - **保留端到端的那層**：P4 的驗收說的就是「JS 卡住時」，也只有它測到 thread、channel 和 input 的轉送。判斷用訊息的先後，不量時間。
    - **不選量時間**（例如 100 ms 內收到捲過的 frame）：慢的機器和 debug 的 V8 會誤判。
    - **不選用測試專用的開關卡住 main thread**：卡住的不是 JS，和驗收說的不是同一件事，renderer 也要多一段只給測試用的程式。
    - 端到端的那層原本規劃用 headless，第 4 段開始時改成 `DrivenViz`（第 44 條）。

14. **Thread 之間的 channel 從 `std::sync::mpsc` 換成 `crossbeam-channel`**，在 P4.1 之前單獨做，只換型別、不改行為。`NetworkService` 的 `tokio::sync::mpsc`（在 async runtime 裡要 `.await`）和 UI thread 的 winit `EventLoopProxy`（winit 的 event loop 只收它）不換。

2026-10-02 確認（P4.1 第二段，第 1 節）：

15. **Compositor thread 由 `renderer` 建立，迴圈和邏輯在 `compositor`**：`ProxyImpl`、什麼時候要 `BeginMainFrame`、commit、activate、draw 都在 `compositor`。Chromium 也是 content 的 `RenderThreadImpl` 建立 `Compositor` thread、把 task runner 交給 cc，`ProxyMain`、`ProxyImpl` 和 `Scheduler` 在 cc 裡。不選把迴圈放在 `renderer`：cc 的排程邏輯會散進 renderer。
16. **Viz 和 Browser 送進 compositor thread 的訊息是 `protocol::renderer::CompositorMsg`**：第二段只有 `BeginFrame`（從 `RendererMsg` 搬過來），第三段加上 input。它對應 Chromium 的兩個 interface（`CompositorFrameSinkClient`、`WidgetInputHandler`），照第 3 條放在同一條 channel。

    - **不選照 interface 分成兩個 enum**：第 3 條只開一條 channel，最後還是要再包一層。
17. **Compositor thread 只等一條自己的 queue（`CompositorTask`）**，和第 6 條的 main thread 同樣的形狀：外面的訊息、commit、`BeginMainFrameAborted`、要不要 main frame、shutdown 都是這條 queue 的 task。Viz 拿 `CompositorSender`、main thread 拿 `ProxyMain`，都是同一條 queue 的 sender，包成不同型別，只能送各自該送的東西。反方向，`compositor` 不能依賴 `renderer`（不知道 `MainThreadTask`），所以 renderer 建立 compositor thread 時交給它一個 callback，用來把 `MainThreadTask::BeginMainFrame` 放進 main thread 的 queue，對應 Chromium 的 `ProxyImpl` 經 main thread 的 task runner post `ProxyMain::BeginMainFrame`。不選 `select!` 同時等好幾條 channel，理由同第 6 條。
18. **`LayerTreeHost<P>` 用泛型分開兩種模式**：`P` 是 `SingleThreadProxy` 或 `ProxyMain`；共用的狀態和方法寫在 `impl<P>`，模式專屬的方法寫在各自的 `impl`。
    - **Chromium**：一個 `LayerTreeHost`，`CreateSingleThreaded` 或 `CreateThreaded` 建立，持有 `std::unique_ptr<Proxy>`（`SingleThreadProxy` / `ProxyMain`）。兩種模式的 API 幾乎一樣，因為 single-threaded 模式也有自己的 scheduler：使用者只說「需要更新」（`SetNeedsCommit` 等），proxy 在 `BeginFrame` 時回呼使用者的 `BeginMainFrame` / `UpdateLayerTreeHost`；`ui::Compositor` 也是由 `BeginFrame` 驅動的。只屬於一種模式的方法很少（例如 `CompositeForTest`），靠 `DCHECK` 擋。
    - **machopo 不一樣的地方**：machopo 的 single-threaded 模式沒有 scheduler，「什麼時候畫」由使用者決定（工具列改變時直接 `composite()`），所以兩種模式的 API 真的不同。泛型讓這些差別在編譯期分開，Chromium 用 `DCHECK` 在執行期擋的，在這裡是編譯錯誤。
    - **不選內部 enum 或 `Box<dyn Proxy>`**：呼叫錯模式的方法只能在執行期出錯。
    - **之後要改成 Chromium 的做法**：讓 single-threaded 模式也有 scheduler，工具列改成由 `BeginFrame` 驅動，renderer 改成由 proxy 回呼，兩種模式的 API 就一樣，只剩建立時選模式。第二段不做：這些工作和「拆出 compositor thread、確認結果不變」無關，一起做出問題時很難分辨原因，範圍也大很多。之後工具列換成 HTML / CSS 的 UI 時，Browser 端本來就要由 `BeginFrame` 驅動，那時一起改。改的時候只要替 `SingleThreadProxy` 補上 scheduler、合併兩個 `impl` 的 API，`ProxyMain` 那邊大致不用動。
    - **也比較過、不選的改變第 5 條的做法**：工具列也開 compositor thread（`LayerTreeHost` 只剩 threaded 一種，但 Browser 多一條沒有需要的 thread，和 Chromium 的 `ui::Compositor` 不同）；工具列不用 cc、自己組 `CompositorFrame`（等於在 `shell` 重寫一小份 cc，之後要搬回）。
19. **Swap promise 是 `SwapPromise(Box<dyn FnOnce(Option<u32>) + Send>)`**（第 9 條）：畫出含有那次 commit 的 frame 時帶 frame token 呼叫，沒畫出 frame 時帶 `None`；還沒畫出來就被新的 commit 蓋過時不呼叫，留給畫出新 commit 的那個 frame。compositor 結束時還沒兌現的直接丟掉。名字對應 Chromium 的 `cc::SwapPromise`，但只留 machopo 需要的一個 callback。第三段的 `InputEventAck`（第 10 條）也用它。
20. **第二段每次 main frame 有變化就 commit**：viewport 的位移隨 commit 送過去；display list 是同一個 `Arc` 時，impl 端保留舊的 tile，所以只捲 viewport 時照樣不重新 raster。這也和 Chromium 一致：main frame 跑完就 commit，tile 要不要重畫看 invalidation。不選另外加一個只改位移、不 commit 的訊息：第三段的 `SyncedScrollOffset`（第 12 條）會取代它。
21. **Compositor thread 的邏輯寫成普通的 struct**，有 `begin_frame`、`commit`、`begin_main_frame_aborted` 等方法，thread 的迴圈只從 queue 拿 task、呼叫它們。`compositor` 的單元測試不開 thread，一步一步驅動（第 13 條，仿照 cc 的 `LayerTreeTest`）。
22. **`RendererGone` 由 Browser 在 renderer 的 channel 關閉時報告**，renderer 不再送它（2026-10-02，P4.1 第 2c 段之後）。channel 要等每個 sender 都被 drop 才會關閉，包括 compositor 那邊 swap promise 抓著的 `to_browser`，所以「`RendererGone` 之後不會再有 renderer 的訊息」是 channel 的語意，不靠任何順序。
    - **Chromium**：`RenderProcessHostImpl` 也是從 channel 出錯（`OnChannelError`）得知 renderer 不見了，不是收一則訊息。拆 process、換成 ipc-channel 之後，連線關閉的意思一樣，這段不用改；renderer 當掉（panic）時也一樣會報告。
    - **原本的做法**：2c 時是 main thread 先等 compositor thread 結束、再送 `RendererGone`，順序只靠這個寫法守住，mutation test 抓不到，時間點也做不成測試。原本以為拆 process 之後自然解決，但單一 process 的模式（headless、測試；拆 process 當時也是選做）會一直存在，所以改成現在的做法。
    - **剩下的風險看得見**：有 sender 被多留住時 channel 不會關閉，`RenderProcessHost::shutdown` 會卡住，會關閉 renderer 的測試就會逾時失敗。main thread 照樣等 compositor thread 結束，那是為了讓它正確收尾，不再擔負訊息的順序。

40. **捲動容器的範圍**：

    - **放在哪**：`paint` 在 pre-paint 時、`hit_test` 旁邊算好，掛在 `PictureLayer` 上（cc 每個 layer 的 `main_thread_scroll_hit_test_region`，舊名 non-fast-scrollable region）。pre-paint 重跑一定產生新的 display list，所以範圍和 display list 一定在同一次 commit，不需要另外的 setter；P4.2 拆 layer 時自然變成每個 layer 一份。
    - **不變式**：所有範圍的聯集和任何捲動位移無關（最外層容器的位置只看 layout 和 transform，內層容器在外層的範圍裡），所以 main 捲了外層容器、compositor 的範圍還是舊的時，滾輪也不會送錯。加上 `position: fixed` 時要重新檢討。
    - **測試**：掃過測試頁面的每一格，斷言 main 的 hit test 會選中捲動容器的點一定在範圍裡（border、`scale(10)`、巢狀、被 clip 掉的、`overflow: hidden`、root / body 的 `overflow` 傳給 viewport）。
    - **不選**：padding box（border 上的滾輪會捲 viewport）；用 viewport 裁；合併成一個外接矩形（頁面大半都轉給 main）；另外送一則訊息（範圍要和 commit 的 display list 是同一份）；只在 document 座標取整（第一、二輪的提案，上面的反例）。
    - **Chromium**：Blink 在 paint 時記下 border box 的 scroll hit test 資料（`RecordScrollHitTestData`），記在帶容器外面那層 property 的 chunk 裡，`PaintArtifactCompositor` 再把它併進 layer 的範圍（細節沒有逐行核對）。

41. **compositor 對每個 input 的處理，照這個順序**：

42. **範圍裡的容器捲不動時照樣轉給 main**（compositor 要到 P4.2 才知道容器的位移，由 main 把剩下的傳給 viewport）。**不做 latching**：每個滾輪事件各自判斷，和 main 原本的行為一樣（範圍表已經把 wheel latching 列為之後）；所以同一串滾輪中，容器被捲到游標底下之後，接下來的會轉給 main 捲容器。Chromium 會 latch（`GestureScrollBegin` / `Update` / `End`，cc 記住 `CurrentlyScrollingNode`）。
    - **之後的變化**：P4.2 改了：compositor 知道成為 layer 的容器的位移，自己捲它們、捲到底往外層傳（第 48、52 條）；範圍裡的容器照樣轉給 main。不做 latching 不變。

49. **4.2a 實作時定的**：

50. **4.2b 先用兩個簡單的退路，以後改成 Chromium 的 scroll unification**（2026-10-03）：
    - **成為 layer 的容器被畫在它之後的東西蓋到時，整個容器交給 main**：compositor 只知道每個 layer 的範圍，不知道之後的 layer 哪裡真的有東西（「容器之後」的 layer 和整份文件一樣大，大部分是透明的）。所以 paint 時檢查容器之後有沒有東西和它重疊（hit test 碰得到的都算，包括沒畫背景的盒子），有的話這個容器照第 40 條放進要 main 判斷的範圍，游標在上面的滾輪照 3c 轉給 main；main 照舊能捲成為 layer 的容器（改位移、commit，不重新 raster）。常見的頁面裡容器之後的東西不和它重疊，都由 compositor 捲。
    - **從容器往外到 viewport 之間，有沒成為 layer、又捲得動的捲動容器時，整串交給 main**：compositor 的 scroll tree 只有成為 layer 的容器，往外層傳時跳過中間那個就捲錯了，所以這種容器也放進範圍。外層因為縮放、旋轉或 opacity 沒成為 layer 時，裡面的也不會成為 layer，所以實際上很少碰到；沒東西可捲的外層不算（main 碰到捲不動的也是往外傳）。

52. **4.2b-2 實作時定的**：
    - **第 50 條「被之後畫的東西蓋到」的判斷用 hit test 的同一套走法**：`paint` 的 hit test 改成走訪者的形式，同一個走法倒著 paint 順序走過所有 hit test 碰得到的東西（盒子的 border box、文字、行內的盒子和圖片，包括沒畫背景的盒子：main 的 hit test 也會選中它，再捲它的捲動鏈）。成為 layer 的容器自己的 border box 之後畫的、不在它捲動鏈裡的東西，只要可能和容器被選中的範圍（border box 被外面的 clip 裁）重疊，容器就放進範圍。「可能」：一邊被某個成為 layer 的容器移動、另一邊不會時，compositor 捲它就會改變兩者的相對位置，所以用最外層那個容器的整個範圍代替。不選用 paint chunk 判斷：沒畫東西的盒子沒有 chunk，main 卻會選中它。
    - **範圍依「哪個容器移動它」分開放**：每個要給 main 的矩形放在移動它的最內層、成為 layer 的容器的 scroll node 上，在那個容器內容的空間，只用和它一起移動的 clip 裁（外面的 clip 由 compositor 比對時先確認游標在那個容器的範圍裡）；不在任何這種容器裡的，放在 document 的空間。所以 compositor 捲容器、main 不重畫時，範圍跟著移動，第 40 條的不變式也照樣成立。範圍從 `PictureLayer` 搬到 compositor 的 property tree（document 的一份，加上每個 scroll node 一份）：沒畫任何東西的容器沒有 layer，但它裡面的還是要有範圍；property tree 和 layer 一起 commit，第 40 條「範圍和 display list 一定在同一次 commit」不變。
    - **沒成為 layer、使用者又捲不動的容器不放進範圍**（`overflow: hidden`，或沒有東西可捲）：main 碰到它也是整個往外傳，compositor 不認識它、直接捲外面的，結果一樣。常見的 `overflow: auto` 包裝不再讓整塊都轉給 main。
    - **第 50 條的第二個退路不用另外做**：沒成為 layer、使用者捲得動的外層本來就在範圍裡，它裡面的容器都在它的矩形裡，滾輪一定轉給 main。而且現在碰不到：外層因為縮放、旋轉或 opacity 不成為 layer 時，裡面的也一樣不成為 layer。
    - **compositor 的 scroll tree 節點**加上 parent（往外最近的成為 layer 的容器，中間沒成為 layer 的使用者都捲不動，見上一點）、border box 和它所在的 transform、外面的 clip、scroll translation、自己的範圍。滾輪：在 document 的範圍，或在某個容器範圍內、又在它自己的範圍裡，轉給 main；否則選範圍包含游標的最內層容器（scroll tree 照 parent 在前排，最後一個符合的就是最內層；成為 layer 的容器除了巢狀以外重疊的地方都被範圍蓋住）。從它開始捲，捲不完的交給 parent，最後是 viewport，和 main 的 scroll chaining 一樣；比對用畫出來的位移，包括還沒交出去的。按鍵照舊只捲 viewport，也照舊不做 latching（第 42 條）。
    - **驗證用性質測試**：`paint` 的測試在頁面的每一格模擬 compositor 的判斷，斷言要嘛轉給 main，要嘛 compositor 會捲的捲動容器（只算使用者捲得動的）和 main 會捲的完全相同；也包括 compositor 捲了外層容器、範圍還是捲之前畫的時。
53. **4.2c 對齊 device pixel**（2026-10-03 確認）：
    - **layout 照舊用 CSS px，`paint` 取整到 device pixel**：`paint` 知道 device scale factor，邊緣取整成 `round(x × dsf) / dsf`，display list 照舊是 CSS px，raster 乘上 dsf 之後剛好落在格線上。不選 Chromium 現在的 use-zoom-for-DSF（Blink 把 dsf 當成縮放，layout 直接用 physical pixel 算，paint 再取整）：畫出來的像素在絕大多數情況相同，但要改 style、layout、文字、hit testing、input 座標，以及所有給 script 的數值，遠超過這一段。代價是 dsf 改變時要重新 paint，以及 layout 的取整以 CSS px 為單位（Blink 是 1/64 device px），差距都不到 1 個 device px。
    - **對齊的東西**：盒子的邊緣（背景、border 的內外緣、overflow clip）、文字的 baseline、border 寬度、捲動位移。border 寬度照 css-values 的「snap as a border width」：取整（往下）到整數 device px，不是 0 的話至少 1 device px，所以 1px 的 border 在 1.5x 是 1 device px，不會糊成兩條淡線。捲動位移在 main 的 pre-paint 和 compositor 用同一套取整，成為 layer 的容器畫在哪裡和沒成為 layer 時一樣。縮放、旋轉這類一般的 transform 底下照樣只取整平移，和 Chromium 一樣。文字的 x 照舊用 Skia 的 subpixel 定位，不取整。
    - **reftest 用 `<meta name=machopo-device-scale-factor content=2>` 指定倍率**，和 `machopo-fragment` 一樣是我們自己的擴充；reference 用同一個倍率畫。K3 用 2 和 1.5 各寫幾個：1.5 才看得出縫和模糊。不選 Chromium 的 virtual test suite（`virtual/scalefactor200/` 把整個目錄用 `--force-device-scale-factor=2` 再跑一次）：整批 reftest 再跑一次多花一倍以上的時間，現有的測試多半只在 1x 調過 fuzzy。
54. **4.2c 實作時定的**：
    - **device scale factor 由 pre-paint 帶著**：`pre_paint` 多一個參數，clip 和捲動容器的 scroll translation 在那裡取整；paint 從 `PrePaint` 讀，`PaintArtifact` 記下它取整到的格線（`device_scale_factor`）。
    - **成為 layer 的容器，layer 的範圍也取整到 device pixel**（`PendingLayer::bounds`）：內容在 document 的空間裡取整，layer 的原點也要在格線上，內容在 layer 裡才會落在 device pixel 上。原本在小數的位置時，layer 的原點差半個 px（1x 時也是），內容在 tile 裡差半個 px，raster 出來是糊的（K3 的 `k3-scroller-layer` 抓到的）。
    - **compositor 的容器位移，由呼叫的一方取整到 device pixel 之後才交給 property tree**（`drawn_scroll_offsets`）：draw、準備 tile、找游標下的容器都用同一份，和 paint 取整的方式一樣（`round(x × dsf) / dsf`）。`PropertyTrees::position` 照給它的位移算，不再自己取整。viewport 的位移本來就取整到 physical pixel。
    - **border 寬度在 paint 時取整，layout 照舊用沒取整的寬度**：外緣照背景的方式取整，內緣是外緣往內縮取整過的寬度（原本內緣自己四捨五入，1.5px 的 border 在 1x 會畫成 2px，現在是 1px）。Blink 在 style 時就取整（use-zoom-for-DSF 下以 device pixel 計），layout 也用取整過的寬度；machopo 的 layout 不知道 dsf，裡面的東西和 border 之間可能差不到 1 個 device px。
    - **dsf 改變時重新 paint**：`FrameView` 記著上一次的 dsf，不同時標記要 paint（layout 只看 CSS px，不用重做）。
    - **reftest 的 frame 快取以「路徑加上 dsf」為 key**：同一份 reference 可能被不同倍率的測試共用。viewport 一律 800×600 CSS px，physical 的大小跟著倍率。
    - **不變的**：文字的 x 照舊用 Skia 的 subpixel 定位；文字裝飾的粗細照舊至少 1 CSS px；一般 transform 底下照樣只在它自己的空間取整。
55. **P4.3 由下往上分四段**（2026-10-03 確認）：4.3a raster invalidation、4.3b DOM 變更追蹤和 style invalidation、4.3c box tree 和 layout 局部重算、4.3d paint 的 display item 快取。現在只要 script 跑過，整份 document 就標成要重算（`about:demo` 的 `requestAnimationFrame` 讓每個 frame 都整份重算），display list 一換，整個 layer 的 tile 都重新 raster。先做 raster：最貴，即使上游照舊整份重畫也省得下來，而且一做完就量得到重新 raster 的 tile 數（驗收）。不選由上往下（從 DOM 變更追蹤開始）：比較符合資料流，但前幾段都做完之前量不到效果，也比較晚碰到 raster。
56. **4.3a 照 Chromium 的 `RasterInvalidator` 找出要重新 raster 的範圍**：用穩定的身分比對新舊的 display item（節點、種類、同一個節點的第幾個），有變的、移動的、新增的、刪掉的，新舊兩個位置都標成要重畫；所在 chunk 的 transform、clip 或 opacity 變了也一樣。layer 也要有穩定的身分：現在用 layer 的序號，前面多一個捲動容器，後面的 layer 就對錯。這套身分 4.3d 的 display item 快取也要用。不選每個 tile 記下碰到它的 display item 的指紋、指紋變了就重新 raster：不需要身分、比較簡單，但和 Chromium 不同，4.3d 也用不上。
    - **之後的變化**：4.3d 的快取最後以 box 為單位，用 fragment 的位址和元素找（第 73、74 條）；這裡的 item 身分照舊用在 raster invalidation。
57. **重新 raster 以整個 tile 為單位**：被標記的範圍碰到的 tile 整個重畫。不選 Chromium 的 partial raster（只重畫 tile 裡被標記的一塊，貼回原本的 tile）：machopo 的 tile 像素是不可變的 `Arc`，要先複製一份才能改，複雜度和記憶體都多一層；等量到 raster 真的太慢再說。
58. **`ReturnResources` 不在 P4 做**（從範圍表的「P4 做」移到「之後」）：Chromium 需要它，是因為 tile 的 resource 是跨 process 共用的 GPU 記憶體，Viz 用完要明確還回去。machopo 的 resource 是同一個 process 裡的 `Arc`，Viz 在 frame 不再用到時就釋放 GPU texture，compositor 丟掉 tile 時記憶體也跟著釋放，沒有東西需要「還」。等之後有跨 process 或 GPU raster 時再照 Chromium 加。
    - **之後的變化**：4.4c 的 shared image 用參考計數決定 texture 什麼時候釋放，在同一個 process 裡代替 `ReturnResources`（第 80 條）；拆 process 時要換成真正的歸還訊息。
59. **4.3a 實作時定的**：
    - **比對放在 `paint`（`PaintedLayer`，對應 Blink 的 `RasterInvalidator`），記住的狀態放在 renderer**（`PaintArtifactCompositor`，每份 document 一個）：每個 layer 記下它的 paint artifact（`Arc`）、每個 chunk 怎麼畫進 layer（到 layer 空間的矩陣、layer 和 chunk 之間的每個 clip 和它的矩陣、外面的每個 opacity），以及每個 display item 的身分和它在 layer 空間的範圍（被 clip 裁過）。不是平移的矩陣底下多放 1px 給反鋸齒。
    - **display item 的身分是（節點、種類、同一個節點這種 item 的第幾個）**，在 layer 裡算；比對內容用 `DisplayItem` 的相等（圖片和字型都比 id，不比像素）。順序：配對到的 item 照舊順序和新順序排好，第幾個不一樣的，兩邊的範圍都重畫。還沒有 paint 的快取（4.3d），所以每次都比內容。
    - **layer 的身分是（移動它的容器，或 document 的就是沒有；同樣的 layer 前面有幾個）**；`LayerId` 由整個 process 共用的計數器發（cc 的 `g_next_layer_id`），不同 document 的 layer 不會同號。
    - **`PictureLayer` 帶要重新 raster 的範圍**（`invalidation`，cc 的 `SetNeedsDisplayRect`；`None` 是全部，新的 layer 就是）。compositor 在 display list 換了時才看：同一個 document、同一個 id、同樣的倍率和底色時，新的 tiling 保留舊的 tile 中位置和大小都沒變、又沒被範圍碰到的；layer 變大或變小時，原本在邊上、大小變了的 tile 重新 raster。另一份 document 的 layer 什麼都不留。
    - **damage rect**：同一份 document 的 commit，如果只有 display list 換了（layer、位置、clip、property tree、viewport、surface layer、底色都一樣），damage 是各 layer 的範圍換算到畫面上、被 layer 的 clip 裁過、取外接的整數 px；其他的變化，或從上次 draw 之後 viewport 或容器移動了，是整個畫面。Viz 照舊整個重畫（partial swap 在「之後」）。
    - **重新 raster 了幾個 tile**：`RUST_LOG=compositor=debug` 時每次準備 tile 記一筆（`rastered`、`kept`），在視窗裡用來確認。測試從 Viz 收到的 resource 數。
    - **之後的變化**：4.3d 之後，從上一次 paint 搬來、沒變的 item 不比內容（第 72、74 條）；重畫的 box 的 item 照舊比。
60. **「哪裡改了」記在 DOM 節點的 dirty flag 上**（2026-10-03 確認，Chromium 的做法）：`Node` 上有「自己要重算 style」（`NeedsStyleRecalc`）和「子孫裡有要重算的」（`ChildNeedsStyleRecalc`）。`DomMutateScope` 的修改方法設好自己的 flag，並往上把祖先的「子孫有」設起來；`recalc_style` 只往有 flag 的路徑走、算完清掉，不在路徑上的子樹直接跳過。flag 是不被 trace 的普通資料（和 `computed_style` 一樣），之後 4.3c 的 box tree 也可以加同樣的 flag（Chromium 的 `NeedsLayoutTreeRebuild`）。動到 `dom`，所以照規則審查 `soundness.md`、跑 `ci.py debug-v8` 和 `matrix`。不選在 `DomIsolate` 裡放一份修改紀錄、由 renderer 取走：節點的結構不用動，但 recalc 還是要從每個改過的元素往上找祖先、往下標子孫，等於在 renderer 再做一份 flag，被移除、之後被回收的節點也要另外處理。
    - **之後的變化**：4.3c-1 照這個模式加了 layout tree 的 flag（第 66 條）。
61. **一個修改重算哪些元素的 style：以子樹為單位，加上保守的規則**（2026-10-03 確認）：改屬性（包括 `class`、`id`、`style`）重算那個元素和所有子孫（繼承、`.a .b` 這種選擇器都可能讓子孫改變）；插入節點重算插進來的子樹；stylesheet 裡有看兄弟或結構的選擇器（`+`、`~`、`:nth-child`、`:first-child`、`:empty` 這類）時，插入、刪除節點，或改了子元素的屬性（`.a + .b` 的後一個兄弟），改成重算整個父元素的子樹；有 `:has()` 時任何修改都整份重算；只改文字不重算 style（只要重排）；stylesheet 變了（`<style>` 的內容、載入完的 `<link>`）整份重算。一定正確，只是有時多算。不選 Blink 的 invalidation sets（從選擇器整理出「哪個 class、id、屬性變了會影響哪些元素」，只重算真的受影響的）：最精準，但要分析每個選擇器，複雜度高很多；不選 Stylo 的快照比對：`selectors` crate 只提供比對本身，Stylo 那一套 invalidation 要自己寫一大塊。**之後要做 Blink 的 invalidation sets**（範圍表的「之後」列了完整版），先從量得到多算的頁面開始。
62. **4.3b 只讓 style 局部重算**（2026-10-03 確認）：script 跑過但沒改 DOM 時，style、box tree、layout、paint 全部跳過；有改的時候 box tree 和 layout 照舊整份重建（4.3c 再改）。不在這一段算 Chromium 的 `StyleDifference`（新舊 style 的差別：只影響畫面，還是要重排）、只改顏色時跳過 layout：現在 box tree 和 fragment 各自存著一份 style，不重建就會畫出舊的顏色，要等 4.3c 改 box tree 時一起做才划算。**之後要做 `StyleDifference`**，4.3c 開始時評估。
    - **之後的變化**：4.3c 做了：box tree 局部更新和 `StyleDifference`（第 65–68 條），layout 只重排變了的 box、沿用沒變的 fragment（第 69–71 條）。
63. **4.3b 實作時定的**：
    - **節點上的 flag**（`dom` 的 `StyleFlags`，`#[no_trace]` 的 `Cell`）：`needs_style_recalc`（自己和整個子樹要重算，Blink 的 `kNeedsStyleRecalc` + `kSubtreeStyleChange`；新建的節點一開始就有）、`child_needs_style_recalc`（子孫裡有，`kChildNeedsStyleRecalc`，往上標到已經有的為止）、`children_changed`（子節點插入、刪除，或子節點的屬性、文字變了）。插入：被插入的節點要重算、父節點的子節點變了；刪除：父節點的子節點變了；改屬性：那個元素要重算、它的父節點的子節點變了（`.a + .b` 的後一個兄弟）；改文字：父節點的子節點變了（`:empty`）。style phase 從 read scope 讀和清，和寫 computed style 一樣。
    - **「有沒有改」用整個 isolate 的 `dom_tree_version`**（Blink 的 `Document::DomTreeVersion`，但不分 document）：每次修改加一，建立節點不加。`FrameView` 看到版本變了才跑 style，沒變而且沒有別的原因（stylesheet 載入、viewport、dsf……）時整個 lifecycle 都跳過。刪掉了原本「script 跑過就整份重算」的 `script_ran`、`dom_changed`。
    - **`StyleEngine` 記住解析過的 author stylesheet**，文字一樣就沿用，不一樣就重新解析、整份重算；同時判斷選擇器（含 UA 的）裡有沒有看兄弟或結構的（`+`、`~`、`Nth`（`:first-child` 這些也是）、`:nth-*(… of S)`、`:empty`，含 `:is()`、`:where()`、`:not()` 裡面的）和 `:has()`。
    - **走法**：從 document 往下，只進有 `child_needs_style_recalc`、或被強制的子樹；元素自己要重算、被強制，或有看結構的選擇器而它的子節點變了時，重算它並強制整個子樹（還沒有 style 的元素一定是新的，有自己的 flag）。所以 root 重算時整份都重算，`rem` 變了不用另外處理；document 自己的子節點變了也不用：它唯一的元素是 root，新的 root 有自己的 flag。有 `:has()` 而 document 有任何 flag 時全部重算。`RUST_LOG=style=debug` 時記下每次重算了幾個元素。
    - **寫測試時發現的**：子節點變了的元素自己也要重算（`:empty` 看的是它自己的子節點），原本只強制它的子節點；改屬性也要標父節點的子節點變了，否則 `.x + li` 這種兄弟選擇器漏掉後一個兄弟。mutation test 之後拿掉了三段多餘的判斷：`rem` 變了強制其他元素、document 的子節點變了、還沒有 style 的元素（理由見上一點）。

    - **tile 記 `TileDrawInfo`**（cc 的同名類別）：`Resource`（有像素）或 `SolidColor`（單色）。保留沒變的 tile、釋放離畫面太遠的 tile，兩種都一樣處理；畫的時候單色的變成 `SolidColor` quad，透明的不送 quad，也不進 frame 的 resource 清單。
    - **什麼算單色**：每個像素都一樣，而且完全不透明，或全部透明（premultiplied 的四個 0）。半透明的單色照樣留像素：換算回一般的顏色時四捨五入，可能和原本畫出來的差一點。
    - **做了多少事記在 `TilesPrepared`**（raster 了幾個、其中幾個是單色、保留了幾個），`RUST_LOG=compositor=debug` 的 `prepared tiles` 多記 `solid`；測試也看它，確認單色的 tile 照樣被保留。
    - **測試的內容不能是整片單色**：compositor 原本的測試大多畫一整片單色，它們要驗證的 raster、保留和 resource 重用會全被單色的 tile 取代。測試共用的內容改成底色加上每 32px 一個點（點在每格起點往右下 1px，tile 都從 32px 的倍數開始，所以連邊緣很窄的 tile 都碰得到），cc 的測試要測 raster 時也是用不是單色的內容。
    - **量到的**（視窗模式，`about:demo`，2x）：336 個 tile 裡 142 個是單色，`footprint` 從 298 MB 降到 254 MB（`MALLOC_SMALL` 110 → 74 MB）。GPU 那份只從 123 MB 降到 115 MB，194 個有像素的 tile 照算只要約 49 MB：GPU 的記憶體不是跟著 tile 數走的，可能是 wgpu 或 Metal 留著不用的 texture，4.4c 時查。

2026-10-04 確認（P4.4 第 4.4c 段）：

80. **tile 只留一份：照 Chromium 的 shared image**。Viz 提供一個 `SharedImageInterface` 式的介面給 compositor：wgpu 的模式下，compositor raster 完就透過它在 Viz 的 GPU device 上建立 texture、寫入像素，然後丟掉 CPU 的那份；frame 的 `TransferableResource` 只帶這個 handle，Viz 直接拿來畫。software 的模式（headless、reftest）照舊：像素的 `Arc` 本來就由 compositor 和 Viz 共用，只有一份（相當於 Chromium software compositing 的共用記憶體）。texture 的生命週期用參考計數：compositor 丟掉 tile、frame 也不再引用它時自動釋放，在同一個 process 裡相當於 mailbox 加上 `DestroySharedImage` 和 `ReturnResources`，拆 process 時換成真正的 mailbox 和歸還訊息，結構不用改。compositor 不依賴 wgpu：介面是 Viz 實作的 trait，handle 對它是不透明的。上傳從 Viz thread 移到 compositor thread，和 Chromium 在 raster 時就寫進 GPU 記憶體一樣；wgpu 的寫入要等下一次 submit 才送出，視窗被遮住時 Viz 不 submit，所以 compositor 上傳之後自己 flush，免得又像 2026-10-03 那樣堆積。
    - **現況**（決定時查的）：compositor 的每個 tile 都留著 CPU 的像素；Viz 只留目前這個 frame 用到的 resource 的 texture（看得到的 tile），看不到的被丟掉、捲回來時再從 compositor 那份上傳。所以重複的只有看得到的 tile；GPU 那份偏高（115 MB）另有原因，這一段一起查。
    - **Chromium**：cc 的 `TileManager` 依優先順序和記憶體預算決定 raster 哪些 tile，結果直接在 GPU 記憶體裡（OOP raster 在 GPU process 直接畫進 texture，one-copy 先畫到共用的暫存再複製進去），renderer 透過 `SharedImageInterface` 建立、寫入、銷毀，手上只有 mailbox；看不到的、預先 raster 好的 tile 也在 GPU 記憶體裡，不經過 Viz。frame 只帶 mailbox，Viz 的 `DisplayResourceProvider` 取用；不再用時以 `ReturnResources` 還給 renderer，`ResourcePool` 重用同樣大小的記憶體。
    - **不選讓 Viz 保管唯一的那份、隨 frame 建立**（compositor 送一次像素就丟掉，不用時回報 id）：看不到的 tile 也得塞進 frame 才能上傳，釋放要一條新的訊息，software 的模式也得改成 Viz 自己留一份，歸還的方向還和 Chromium 相反。不選只留 compositor 那份、Viz 每個 frame 重新上傳看得到的 tile：每個 frame 數十個 256 KB 的上傳。
81. **GPU device 遺失之後恢復，另開 4.4d**（照 Chromium）：Viz 用 wgpu 的 device-lost callback 偵測，重建 device、surface 和 pipeline，換一個新的世代；通知每個 compositor（Chromium 的 `DidLoseLayerTreeFrameSink`），compositor 丟掉所有 resource 的 tile，重新 raster、在新的 device 上重建 texture。compositor 那半邊用假的介面做單元測試，Viz 那半邊（要 GPU 和視窗）加一個手動觸發的方式（wgpu 的 `Device::destroy()`）在視窗裡確認。原本建議先記成已知限制：machopo 的 Viz 本來就不會重建 device，B 的主要工作量在 Viz；Apple Silicon 的 macOS 上 Metal device 很少遺失。選 B 的理由：4.4c 之後 compositor 不再留像素，遺失之後除了重建 device 還一定要重新 raster，和 Chromium 對齊；和 4.4c 分開審核。
    - **Chromium**：GPU process crash、驅動程式重置或系統要求時，renderer 和 Viz 的 context 收到遺失的通知（`ContextLostObserver`）；GPU process 重新啟動，display compositor 和 context 重建，還沒歸還的 resource 標上 `lost` 還給 client（`ReturnedResource::lost`）；cc 收到 frame sink 遺失，丟掉 frame sink 和所有 tile 的 resource（`ResourcePool` 清空），接上新的之後全部重新 raster。（2026-10-04 對照過原始碼，出處見第 84 條）
82. **4.4c 實作時定的**：
    - **介面在 `protocol`**：`Mailbox`（`gpu::Mailbox`）、`SharedImage`（`gpu::ClientSharedImage`：mailbox 加上一個不透明的 backing，`Arc<dyn Any>`，不跨 process 傳）和 `SharedImageInterface` 這個 trait（`create_shared_image(size, pixels)`）。`TransferableResource` 多了 `shared_image`，有它時 `pixels` 是空的。compositor 從 `LayerTreeSettings::shared_image_interface` 拿到介面，沒有時（headless、reftest、測試）照舊留像素。
    - **Viz 那半邊是 `viz::GpuSharedImages`**（Chromium 的 `SharedImageStub` 加上 `SharedImageManager`）：視窗先建立它，交給 renderer（經過 `WebContents`、`RenderProcessHost` 到 `LayerTreeSettings`）和工具列的 compositor，再交給 `WgpuRenderer::new`；renderer 在 Viz thread 上建好 device 時把 device、queue 和畫 texture 要的 layout 交給它（`OnceLock`）。在那之前它回傳 `None`，那時 raster 的 tile 照舊留像素，Viz 照舊上傳；tile 重新 raster 時才換成 shared image。
    - **Viz 畫的時候**：resource 帶著 shared image 時直接用它的 texture 和 bind group（複製參考，不上傳）；沒有時照舊上傳像素。Viz 的 resource 表照舊只留目前這個 frame 用到的，shared image 由 compositor 的 tile 留著，看不到的 tile 捲回來不用再上傳。
    - **釋放靠參考計數**：texture 在 compositor 丟掉 tile、Viz 也不再用它的時候釋放（在同一個 process 裡代替 `DestroySharedImage` 和 `ReturnResources`）。
    - **上傳和重新設定 surface 互斥**：wgpu 的 `Surface::configure` 先等 GPU 做完所有工作，等完時如果有別的 thread 又 submit 了就失敗。compositor 在自己的 thread 上傳、submit 之後，改視窗大小時 Viz 重新設定 surface，正好碰上 compositor 重新 raster 一兩百個 tile，Viz thread 因此 panic（視窗確認時發現）。`GpuSharedImages` 和 renderer 共用一個 lock：client 上傳加 submit 時拿著，renderer 重新設定 surface 時拿著。Chromium 沒有這個問題：建立 shared image 和 display compositor 的工作都由 GPU process 的 scheduler 依序執行，不會同時 submit。
    - **量到的**（視窗模式，`about:demo`，2x，視窗在前面）：`footprint` 從 254 MB 降到 234 MB。`MALLOC_SMALL` 74 → 23 MB（tile 的 CPU 那份沒了）；GPU 那份 115 → 146 MB，因為現在所有有像素的 tile 都在 GPU 上，包括畫面外預先 raster 好的，以前只有看得到的才上傳。視窗被遮住時量到的不能比：Viz 不畫，swap chain 的 IOSurface 和 GPU 的一部分不見了（138 MB）。
    - **GPU 那份偏高的原因**（4.4a、4.4b 留下的問題）：暫時加上計數查過，活著的 texture 約 204 個、49 MB，和照 tile 算的一樣，compositor 和 Viz 都沒有多留。靜態的頁面上 GPU 那份（32 MB）幾乎等於活著的 texture（27 MB）；`about:demo` 多出約 95 MB，而且不會繼續長，跟著藍色方塊的動畫出現（每個 frame 重新 raster、上傳一個 tile，Viz 畫一個 frame）。不是 texture 建立和銷毀得太快造成的，見第 83 條。
83. **GPU 那份多出的約 95 MB，記成已知限制**（2026-10-04，先試了 texture 重用）：照 cc 的 `ResourcePool` 試了重用：client 放掉的 shared image 留在 `GpuSharedImages` 的 pool 裡（最多 32 個 tile 的大小），下一個同樣大小的 tile 寫進去再用，Viz 畫的期間拿著它，不會被寫掉。pool 確實用上了（開頁面時建立 215 個 texture，之後 2785 次都是重用），但 `about:demo` 的 GPU 那份照樣是 148 MB（沒有 pool 時 146 MB），所以拿掉了。剩下的可能是每個 frame 都有、但我們不直接管的配置：`write_texture` 每次上傳用的暫存、Viz 每個 frame 的 vertex buffer 和 command buffer，或 Metal 驅動自己的快取；視窗被遮住、Viz 不畫時多出的約一半（約 47 MB），兩邊可能都有份。要查得用 Xcode 的 Metal 工具或 wgpu 的內部計數，等之後記憶體再成為問題時再做（例如有更多動畫的頁面）。Chromium 的 `ResourcePool` 這裡沒有做：省不到記憶體，只省建立 texture 的時間，目前沒看到它造成卡頓。


2026-10-04 確認（P4.4 第 4.4d 段）：

84. **device 遺失之後怎麼恢復**（第 81 條的細節，Chromium 的部分 2026-10-04 對照原始碼）：
    - **compositor 由 `SharedImageInterface` 得知**：每個 compositor 在它用的介面上註冊一個 observer（Chromium 的 `ContextLostObserver`），Viz 偵測到遺失時一一呼叫，各自轉到自己的 thread：丟掉有 resource 的 tile、整個畫面標成 damage、要求下一個 frame。不選每個 frame 檢查 device 的世代：分頁的 compositor 最多晚一個 frame，但工具列只在內容改變時才畫，可能一直不知道。不選由 Viz 透過 frame sink 送訊息：要多一條訊息，Chromium 也不是這樣通知的。平常這三種都沒有可以量到的成本。
    - **遺失到 compositor 重新送 frame 之間，Viz 跳過舊 device 的 quad，照常 present**：那些地方露出背景色，可能閃一兩個 frame。不選等所有的 resource 都換新才 present（畫面停在上一張）：只要有一個 client 沒有重送，畫面就一直卡住。
    - **重建失敗時，間隔遞增地重試，3 次都失敗就印出錯誤並結束程式**：machopo 的視窗沒有 software 的輸出，沒有可以退回的模式。不選一直重試：畫面一直是空的，使用者也不知道發生了什麼事。
    - **視窗確認用 `about:gpucrash` 觸發**：browser 攔下這個網址，叫 Viz 讓 device 遺失（`Device::destroy()`），不載入頁面。不選快捷鍵：佔用一個組合鍵，也可能被不小心按到。
    - **不做 Viz thread panic 之後重新啟動**：panic 當成 bug 修掉；真的 crash 由拆 process（RFC 0004）之後重啟 process 處理。
    - **Chromium**：
      - client 從自己用的 context 得知遺失，不是由 Viz 通知：cc 的 `LayerTreeFrameSink` 是它的 context provider 的 `ContextLostObserver`，raster 用的 worker context 的通知由 `ContextLostForwarder` 轉到 compositor thread；software compositing 時 observer 直接註冊在 `SharedImageInterface` 上（`AddGpuChannelLostObserver`）。三條路都呼叫 `DidLoseLayerTreeFrameSink`（`cc/trees/layer_tree_frame_sink.cc`）。
      - cc 收到之後 `ReleaseLayerTreeFrameSink` 釋放 tree 和 tile manager 的 resource、丟掉 `ResourcePool`；接上新的 frame sink 時 `InitializeFrameSink` 重建 `ResourcePool`、`RecreateTileResources`、整個畫面標成 damage，並要求畫出高解析度的 tile（`SetRequiresHighResToDraw`，避免恢復時畫出 checkerboard）（`cc/trees/layer_tree_host_impl.cc`）。還沒歸還的 resource 以 `ReturnedResource` 的 `lost` 還給 client（`components/viz/common/resources/returned_resource.h`）。
      - GPU process 的 context 遺失時，`GpuServiceImpl::MaybeExitOnContextLost` 重啟整個 GPU process；GPU 跑在 browser process 裡（`in_host_process()`）時沒辦法重啟，註解寫的是只能期望從遺失中恢復（`components/viz/service/gl/gpu_service_impl.cc`）。machopo 只有一個 process，對應後者，但由 Viz 自己重建 device。
      - GPU process 最近 crash 的次數到了上限就退到下一個模式（`FallBackToNextGpuModeDueToCrash`，例如 software compositing）：桌面版 3 次；ChromeOS 6 次，因為它不用 software compositing，退回會讓 browser process crash；每 5 分鐘原諒一次 crash（`kForgiveGpuCrashMinutes`）（`content/browser/gpu/gpu_process_host.cc` 的 `GetFallbackCrashLimit`）。machopo 數的是一次遺失之後重建失敗的次數，重建成功就重新算。
      - `chrome://gpucrash` 讓 GPU process crash（`GpuService::Crash()`），`chrome://gpuclean` 關掉所有的 GPU channel，`chrome://gpuhang` 讓它卡住；browser 在 navigation 時攔下，不載入頁面（`content/browser/renderer_host/debug_urls.cc` 的 `HandleDebugURL`）。
85. **4.4d 實作時定的**：
    - **介面**：`protocol` 多了 `ContextLostObserver`（`on_context_lost`），`SharedImageInterface` 多了 `add_context_lost_observer`。observer 用 `Weak` 註冊，client 丟掉自己那份就不再被通知，不用另外移除（Chromium 的 client 在 `DetachFromClient` 時移除）；`GpuSharedImages` 加新的 observer 時順便清掉已經不在的。
    - **Viz 先做好新的 device 才通知**：偵測到遺失時，`GpuSharedImages` 先不再建立 shared image（client 這時 raster 的 tile 照舊留像素），清掉 Viz 自己的 resource，做新的 device、surface 和 pipeline，交給 `GpuSharedImages`，最後才通知 client。client 收到通知時新的 device 已經可以用，重新 raster 的 tile 直接放上去，不會先留一份像素；這段期間留了像素的 tile 收到通知時也一起丟掉重來。Chromium 是先通知、client 再去要新的 channel，machopo 只有一個 process，倒過來比較簡單。
    - **跟 device 有關的狀態整組重建**：`WgpuRenderer` 裡的 device、queue、surface 的設定、pipeline、sampler 和白色的 texture 搬進 `Context`，遺失時整個換掉。每個 `Context` 有自己的世代（0、1、2……）和「已遺失」的旗標：wgpu 的 device-lost callback 只設旗標（它可能在任何一個 poll 的 thread 上被呼叫，包括 compositor 上傳時的 submit），Viz 畫下一個 frame 前看到旗標才重建；舊 device 晚到的通知只會設到舊的旗標。shared image 記著它的世代，Viz 只畫目前世代的，其他的 quad 跳過。
    - **wgpu 的錯誤不用另外處理**：對遺失的 device 呼叫，wgpu 回報的是 `DeviceLost` 類的錯誤，不交給預設會 panic 的錯誤處理（`wgpu` 的 `backend/wgpu_core.rs`）。`Device::destroy()` 之後 callback 要等下一次 poll 或 submit 才呼叫，所以 `about:gpucrash` 自己設旗標。
    - **重試**：立刻、0.5 秒後、2 秒後各試一次，都失敗就記錄錯誤、`std::process::exit(1)`。
    - **compositor**：threaded 的 host 在 `ProxyMain` 上留著一個 `ContextLostForwarder`（cc 的同名類別），把通知變成 compositor thread 的 `DidLoseLayerTreeFrameSink` task；`ProxyImpl` 丟掉有 resource 的 tile、要求 `BeginFrame`，畫的時候重新 raster。single-threaded 的（工具列）由它的使用者自己註冊 observer（視窗透過 event loop 轉到 UI thread），再呼叫 `did_lose_layer_tree_frame_sink` 和 `composite`。`LayerTreeHostImpl::did_lose_layer_tree_frame_sink` 丟掉 pending 和 active tree 裡有 resource 的 tile（單色的不用 GPU，留著），清掉「tile 是為哪個捲動位置準備的」和「上一個 frame 畫在哪裡」，下一次 `prepare_tiles` 就會重新 raster，damage 是整個畫面。
    - **`about:gpucrash` 只處理使用者自己的 navigation**：`browser` 的 `debug_urls`（Chromium 的 `HandleDebugURL`）在 `WebContents::navigate` 一開始攔下，送 `DisplayMsg::LoseContext` 給 Viz，不建立 navigation、不留歷史紀錄。網頁裡的連結（`OpenURL`）照一般的 navigation 走，所以網頁沒辦法讓 GPU 遺失（Chromium 的 debug URL 也只處理 explicit 的 navigation）；寫的時候發現連結原本會走到 `navigate`，改成直接開始 navigation。
