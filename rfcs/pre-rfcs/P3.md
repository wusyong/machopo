## 設計決定

### 1. GC 前置（P3.0）

API 和規則見 `crates/dom/README.md`，安全論證見 `crates/dom/soundness.md`。

**`TracedSlot`**（GC 物件指向 JS 值；和 `MemberSlot` 一樣放在 rusty_v8 的 fork 裡，見「已決定的事項」第 10 條）。
- **為什麼要包裝**：`v8` crate 的 `TracedReference` 和 `Member` 一樣是 `[u8; N]`、對齊只有 1，`reset` 要 `&mut self`。GC 物件只拿得到 `&`，所以照 `MemberSlot` 的模式，做一個對齊正確、能從 `&self` 寫入的包裝。直接用 `v8::TracedReference` 會被 clippy 的 `disallowed-types` 擋下。
- **V8 怎麼讀它**（規劃時要先查清楚的事，對照 V8 原始碼查過了）：slot 只存一個指向 traced handle 節點的指標，讀寫都是 relaxed atomic；節點的內容由 V8 用 release / acquire 發布；marking 中寫入時 V8 當場標記新的值；marking 中 destroy 只清掉節點裡的物件，節點到最後的 pause 才釋放。所以**不需要自己同步**，順序全由 V8 保證，和 Blink 依賴的是同一套。
- **只能用在接了 isolate 的 heap**：cppgc trace 非空的 `TracedReference` 時，把 visitor 轉型成只有 unified heap 才有的 `JSVisitor`。沒接 isolate 的測試用 heap 不能 trace 它，所以寫入一律要 isolate 的 JS scope，detached 的 DOM 上 slot 永遠是空的，`trace` 碰到空的 slot 不呼叫 C++。
- **`dom` 這一層是 `JsEdge<T>`**，在 `dom` 的 V8 模組裡（`src/v8_engine.rs`），只有那個模組能寫。用在 listener 和 event handler 指向 JS 的 function（`CallbackSlot`），以及 GC 物件指向自己的 wrapper（第 2 節）。

**Event listener 的存法**（「已決定的事項」第 2 條）：第二個 GC 型別 `Listener`，每個 EventTarget（`Node`、`Window`，第 7 節）的 `first_listener` 指向第一個，`next: Edge<Listener>` 串起來，callback 是 `CallbackSlot`；type、`ListenerOptions`（capture、`once`、`passive`）和「已移除」的標記放在不被 trace 的區域。
- **操作照 DOM 規範**：`add_event_listener` 不重複加 type、capture、callback 都相同的；`remove_event_listener` 從串列拿掉、設「已移除」、清掉 callback。
- **分派用快照**：`event_listeners(target, type)` 回傳當下的 listener（`EventListenerHandle`，是 root），對應規範 inner invoke 用的那份複本。之後新增的不在快照裡；之後移除的 `is_removed()` 變成 true，`event_listener_callback` 回傳 `None`。這就是 Blink「只走到開始時的長度、跳過已移除的」的語意。
- **Callback 用 `ScriptCallback` 傳進來**（第 4 節）：`dom` 在操作裡自己開 JS scope 轉成 `Local`，呼叫端不需要持有 scope。P3.0 原本接 `v8::Global<v8::Function>`，因為那時還沒有中性的型別；有了 `ScriptCallback` 之後改掉，`JsEdge` 也包進 V8 模組的 `CallbackSlot`。

**`insert_before` 的檢查**：DOM 規範要求檢查 host-including inclusive ancestor，原本只沿著 parent 往上找，不會跨過 template 的 content。Parser 不會觸發，但 JS 可以（把 `<template>` 移進自己的 content）。
- **做法**：template 的 content（`DocumentFragment`）原本沒有指回 template 的指標，所以加了一條 `host: Edge<Node>`（Blink 的 `TemplateContentDocumentFragment` 也記著它的 host），往上找到 fragment 時改走 host。
- **測試的模型**原本跳過這種移動（`cycles_through_template`），現在照樣做，並要求 `dom` 回傳 `HierarchyRequestError`。

### 2. Wrapper（P3.1）

對應 Blink 的 `ScriptWrappable` 和 `DOMDataStore`。這一節全是 V8 專屬的：wrapper 的 slot、`wrap` / `unwrap` 都放在 `dom` 的 V8 模組（第 4 節）。
- **綁定**：`v8::Object::wrap` 把 wrapper 綁到 GC 物件，`unwrap` 從 wrapper 找回物件，cppgc 和 V8 一起 trace 兩邊（unified heap）。API 是 `BindingContext::wrapper` / `event_wrapper`（建立或拿到 wrapper）和 `node` / `window` / `event`（從 JS 的值找回物件）。
- **同一個物件永遠是同一個 wrapper**：GC 物件用 `WrapperSlot`（`JsEdge<v8::Object>`）指向自己的 wrapper，沒有就用 `create` 建一個。JS 在 wrapper 上加的屬性因此不會消失：物件活著，wrapper 就活著。`create` 由 binding 傳入（用哪個 interface 的 template 是 binding 的事），它可能執行 script，而那段 script 可能已經替同一個物件建好 wrapper，所以 `create` 之後再檢查一次，先建好的優先。
- **Wrapper 的型別資訊用 tag 登記表**（對應 Blink 的 `WrapperTypeInfo`）：開了 pointer compression 的 V8 在 `unwrap` 時檢查 tag（`v8/include/v8-sandbox.h` 的 `ReadCppHeapPointerField`），tag 不對就回傳 null。規則有三條：
  - 每種可以被 wrap 的 Rust GC 型別一個 tag，登記在 V8 模組的 `enum WrapTag`（`Node`、`Window`、`Event`），enum 的值不會重複，`Wrappable` 每個型別一個 impl（soundness.md 的 I14）；
  - 一個 tag 只對應一個 Rust 型別，不用 V8 的 tag 範圍。interface 層級的檢查（是不是 `Element`、是不是 `MouseEvent`）看 kind，因為一個家族是同一個 Rust 型別；
  - `unwrap` 之前照樣確認是 API wrapper：對其他物件 `unwrap` 會把任意欄位當成指標，tag 檢查擋不住。

  V8 內部的物件有自己的 tag 範圍，所以不必再固定關掉 V8 自己 wrap、又進得了 JS 的 `WebAssembly.MemoryMapDescriptor`。新物件還沒 wrap 東西的檢查不能用「某個 tag `unwrap` 得到 null」，那只代表沒用那個 tag wrap，所以 fork 加了 `Object::is_wrapping`（用 `kAnyCppHeapPointer` 範圍 `unwrap`），不管 tag 都看得到。
  - **為什麼是通用的機制**：之後幾乎每個 Web API 都是被 wrap 的 GC 物件。P3.4 就有 `Window`、`Event`；MVP 之後很可能有 `NodeList` / `HTMLCollection`、`CSSStyleDeclaration`、`AbortSignal`、各種 observer、`XMLHttpRequest`、fetch 的物件、完整的 `DOMTokenList`。所以在 P3.1 只有 `Node` 一種時就把機制做對、測好，P3.4 加型別時只要登記。
  - **原本 tag 不做型別檢查**：P3.1 一開始用的 prebuilt V8 沒有 pointer compression，`unwrap` 不檢查 tag，直接回傳物件裡的欄位。那時只靠「整個 heap 裡被 wrap 的都是 `Node`」，並固定關掉 `--wasm-memory-control`。
  - **不選 internal field 的型別資訊**（V8 不檢查 tag 時的做法）：每種可以被 wrap 的 GC 型別有一份靜態的型別資訊（名稱、父型別），interface 的 template 預留一個 internal field，wrap 時寫入它的位址，`unwrap` 之前讀這個欄位比對。不依賴 V8 的 tag 檢查，但每個 template 要多一個欄位，型別資訊要自己維護。評估自己編 V8 通過（「已決定的事項」第 10 條）之後，tag 檢查在我們用的 V8 上都有，就不需要它。
  - **啟動時自我檢查**：論證一旦依賴 tag 檢查，換成不檢查的 V8（例如 rusty_v8 一般的 prebuilt）就會變成 UB。所以先用一個 tag wrap、再用另一個 tag `unwrap`，拿到東西就 panic 並說明原因。規劃時寫在 `bindings::initialize`，但那時還沒有 isolate，所以做在 `V8PerIsolateData::new`，第一個 isolate 建立時檢查一次（tag 檢查是 V8 build 的性質，整個 process 一樣）。
  - **評估時重讀 cppgc 的假設**：`Member` 是 4 bytes，但這不是 V8 的 pointer compression 造成的：V8 在 x64、arm64 上預設開 cppgc 的 caged heap，它會一起打開 cppgc 自己的 pointer compression，原本的 prebuilt 也是。soundness.md 的 A4 和 concurrent 的假設本來就是照壓縮的指標論證的，不需要改。重讀時另外發現，caged heap 也會把 cppgc 的 young generation 編進來，只差執行時的實驗性 flag `--cppgc-young-generation`；論證只涵蓋 full GC，所以 `bindings` 固定把它關掉（soundness.md 的 A10）。
- **不是每個 Web API 物件都要是 GC 物件**：是 EventTarget、需要固定的身分（每次拿到同一個物件）、是「活的」、或和 DOM 互相指向的，才要是 GC 物件。沒有身分、每次都是新的值（例如 `getBoundingClientRect()` 的 `DOMRect`），可以在宣告表裡定成中性的紀錄型別，由各前端建立自己的物件，不需要 wrap。
- **Interface**：每個 interface 一個 `FunctionTemplate`，用繼承組成 prototype chain，每個 isolate 建一次。物件的種類建立後不會改變，所以 wrapper 建立時就能決定用哪個 template（第 4 節）。

### 3. 執行 script 時的 scope 和 token（P3.1）

這是 P3 最重要的 soundness 問題。原本的規則是「scope 借用 `&mut DomIsolate`，scope 存在時不會執行 JS」（`crates/dom/README.md` 的「讀寫規則」），但 JS 呼叫 DOM API 時，正是在 JS 執行的途中修改 DOM。

做法（見「已決定的事項」第 1 條）：
- **執行 script 的入口拿走 `&mut DomIsolate`**：所以 script 執行時，Rust 這邊沒有任何 scope。入口是 `evaluate_classic_script`、`perform_microtask_checkpoint`、`run_platform_tasks`，以及 Rust 主動呼叫 script 用的 `with_binding_context(script_state, f)`：它在入口裡替 Rust 建立 `BindingContext`，規則和 binding 裡一樣。安裝 binding、事件分派、timer 和 animation frame 的 callback 都經過它，再用 `dom_bindings::V8Host` 當 `dom_api` 的 `ScriptHost`。
  - **規劃時漏掉的兩個入口**：microtask checkpoint（Promise 的 callback 會呼叫 DOM）和 V8 的 platform task（FinalizationRegistry 的 callback 由 task 執行）。兩者原本直接呼叫 `V8PerIsolateData`，在那裡執行的 script 拿不到 DOM，所以也改成入口。
- **DOM API 的 callback 自己開 scope**（`dom::BindingContext`）：V8 呼叫 binding 時，`dom` 從 isolate 裡找回 DOM 的資料，為這一次 callback 開一個 `DomMutationScope`，callback 結束就收回。這是 `dom` 裡新的 `unsafe`：前提是上一點，也就是 callback 只會在「沒有 scope 的 script 執行」裡被呼叫。
  - **怎麼找回**：入口執行期間，isolate 的 slot 放著指向 DOM 資料（`DomState`）的指標，離開時拿掉，所以入口以外執行的 script（例如經過 `isolate_data()`），binding 拿不到 DOM，只能丟例外。Slot 用 `v8` crate 的型別化 slot（`set_slot`），型別是 `dom` 私有的：raw 的 embedder data slot（`set_data`）是 safe 的，任何人都能寫入一個指標，從那裡讀出來的指標不能信任。
  - **每次都從指標建立 reference**：`BindingContext` 只存指標，`mutate()` 時才建立 `&mut DomState`，只活到 scope 結束。巢狀的 binding 從同一個指標建立自己的 reference，外層這時沒有活著的 reference，不會 aliasing。
  - **規則和 engine 無關，機制不是**：「script 執行時沒有 scope、callback 裡才開」對每個 engine 都一樣；「callback 裡從哪裡找回 DOM 的資料」是 engine 自己的機制（V8 是 isolate 上的資料，之後的 wasmtime 是 host 函式拿到的 `Caller` 和 store 的資料）。所以每個 engine 各有一份這段 `unsafe` 和它的安全論證；V8 的那份放在 `dom` 的 V8 模組（第 4 節）。
- **Callback 裡要再執行 script 時，先交出 scope**：例如 JS 呼叫 `dispatchEvent`，要執行其他 listener。API 設計成「執行 script 需要的 token 被 scope 借走」，持有 scope 時執行不了 script，由 borrow checker 擋下。
  - **Token 的實作**：沒有另外一個 token 型別。最外層的 token 就是 `&mut DomIsolate`；binding 裡是 `BindingContext` 本身：`mutate()` / `read()` 和交出 JS scope 的 `scope()` 都借用整個 context，所以持有 DOM scope 時拿不到 JS 的 scope。
  - **轉換參數也會執行 JS**：把物件轉成字串會呼叫它的 `toString`，讀字典的成員會呼叫 getter，所以 binding 一律先轉換參數、再開 DOM scope。這也由同一條借用規則擋下，不是靠慣例；`script` 測試裡有一個 `toString` 會再呼叫 binding 的例子。
  - **Token 只有一份，由 `DomIsolate` 擁有**，不是每個 engine 或每個 `ScriptHost` 各一份：每個 engine 執行 script 的入口都要借用這同一份 token。只有一個 engine 時兩種寫法沒有差別；但之後同一個頁面有兩個 engine 時（`rfcs/0001-wasm-scripts/` 的 wasmtime），token 如果各自一份，持有 scope 時雖然 JS 被擋下，卻還能呼叫進另一個 engine。這就是 `MVP.md` 列在主要風險裡的那條規則：持有 borrow 時絕不呼叫 JS。
- **GC 的時機**：callback 裡配置物件可能觸發 GC。現有的規則（raw 指標只能在 stack 上、`NodeRef` 借用 scope）不變；callback 收到的 wrapper 是 `Local`，在 V8 的 handle scope 裡。
- **soundness.md**：假設 A8（V8 只在 script 執行中呼叫 binding）、不變式 I13、審查清單的 `src/v8_engine.rs`；兩個 compile-fail 測試（最外層持有 scope 時執行 script、binding 裡持有 DOM scope 時使用 JS 的 scope）。

### 4. 與 engine 無關的 DOM 層（P3.1）

DOM 的語意和「某個 engine 怎麼呼叫它」分開，對應 Blink 的 C++ 實作（例如 `Node::appendChild(Node*, ExceptionState&)`）和它產生的 binding。細節和怎麼新增 API 見 `crates/dom_api/README.md`、`crates/dom_js/README.md`。
- **`dom_api`（safe 的 crate）**：放規範的演算法，例如 `appendChild` 的檢查和插入、`textContent` 的讀寫、事件分派、event handler。用 Rust 的型別表達，錯誤回傳 `Result<_, DomException>`（例外的名稱照 WebIDL）：

  ```rust
  pub fn append_child(cx: &mut dyn ScriptHost, this: &NodeHandle, node: NodeHandle)
      -> Result<NodeHandle, DomException>;
  ```

- **一份 API 宣告表**：用 `macro_rules!` 寫，寫法貼近 WebIDL（interface、繼承、attribute、method、constructor），名稱直接寫 WebIDL 的名稱，每個成員接一個實作它的 `dom_api` 函式：

  ```rust
  dom_api::declare! {
      interface Node : EventTarget [Document, DocumentFragment, Element, Text, Comment, Doctype]
          as NodeHandle
      {
          attribute textContent: Option<DomString>,
              get = node::text_content, set = node::set_text_content;
          method appendChild(node: Node) -> Node = node::append_child;
      }
      interface Element : Node [Element] as NodeHandle {
          method getAttribute(name: DomString) -> Option<DomString> = element::get_attribute;
      }
  }
  ```

  方括號裡是實作這個 interface 的物件種類（`ObjectKind`），`this` 和參數的型別檢查用它；`as` 後面是它的函式拿到物件的型別（`NodeHandle`、`WindowHandle`、`EventHandle`，跨好幾種 GC 型別的 `EventTarget` 用 `Object`）。表裡有 `EventTarget`、`Node`、`Document`、`DocumentFragment`、`DocumentType`、`Element`、`CharacterData`、`Text`、`Comment`、`Window`、`Event`、`UIEvent`、`MouseEvent`（`crates/dom_api/src/interfaces/`）；`dom_api::interface_of` 給出某種物件最衍生的 interface，也就是它的 wrapper 用哪個 template。
  - **它產生什麼**：每個 interface 一份靜態的描述（名稱、父 interface、接受哪些物件、建構子、成員），每個成員記錄名稱、種類（method、getter、setter）、參數和回傳值的型別，以及一個統一的呼叫入口：吃中性的值（`Value`）、回傳中性的值，裡面呼叫 `dom_api` 的函式。
  - **型別**：`DomString`、`bool`、`u32`、`i32`、`f64`、`Option<T>`、interface、`Callback`（`ScriptCallback`）、`EventHandler`、字典、沒有回傳值。參數可以有預設值（WebIDL 的 `optional`：`id: i32 = 0`）。錯誤是 `DomException`，另外有 `TypeError`，用在 `this` 或參數的型別不對、參數不夠時。
  - **物件是一個 enum**（2026-10-02 決定）：`Value::Object(Object)`，`Object` 是 `Node`、`Window`、`Event` 三種 handle 之一，每個 interface 用 `as` 宣告它的函式拿到哪一種。不選每種 GC 型別各加一個 `Value` 的 variant：之後 GC 型別變多，每個前端的轉換都要跟著改。
  - **WebIDL 的擴充屬性**：`[Global]`（global 物件的 interface，成員是 global 自己的屬性，不在 prototype 上）、`[LegacyUnforgeable]`（每個物件自己的屬性，不能刪除、不能重新定義；這裡只用在唯讀的 attribute）。其他的擴充屬性寫了就編譯失敗。
  - **建構子**：`constructor(...) = 函式;` 寫在 interface 的第一行，函式不接 `this`、回傳新物件的 handle。前端照 Chromium 產生的 binding 的流程：沒有 `new` 丟 `TypeError`，轉換參數，呼叫，把新物件 wrap 進 V8 為 `new` 建好的物件（它的 prototype 取自 `new.target`，所以 JS 的子類別也對）。沒有建構子的 interface 被呼叫時丟 `Illegal constructor`。function 的 `length` 是必填參數的數量（尾端的字典和有預設值的參數不算），參數不夠時丟 `TypeError`，和 WebIDL 一樣。
  - **前端只有一個通用的入口**：JS 的 binding 為所有成員共用一個 V8 callback，用 function 的 data 記住是第幾個成員：照參數的型別把 JS 的值轉成 `Value`（這一步可能執行 JS，所以在開 DOM scope 之前），呼叫入口，再把結果轉回 JS。
  - **不選 proc macro**：proc macro 可以把 Rust 的 snake_case 名稱自動轉成 camelCase，錯誤訊息也比較好，但要多維護一個 proc macro；名稱直接寫 WebIDL 的，`macro_rules!` 就夠了。之後的 wasm 前端和 guest SDK 需要 snake_case 的名稱時，由產生器轉換。
  - **不選每個 engine、每個成員各產生型別化的膠水**：比較快，但每加一個 engine，macro 就要多一種輸出。現在效能不是問題，之後真的需要再換。
- **宣告表支援字典**（2026-10-02 決定）：`dictionaries!` 宣告 WebIDL 的字典，每個字典產生一個 Rust struct 和一份描述。前端照描述讀出有的成員（`Value::Dictionary`：先父字典的，每個字典照成員名稱的字典序，是 `undefined` 的當成沒有），struct 填上預設值、檢查 `required`。用在 `addEventListener` 的 options 和事件建構子的 `EventInit`、`MouseEventInit`。
  - **為什麼**：事件的建構子和之後很多 API（`fetch`、observer）都吃字典。字典在宣告表裡，不是 JS 的前端（之後的 wasm）也能照同一份描述轉換，`dom_api` 拿到的是型別化的 struct。
  - **不選由膠水把字典拆成位置參數**（`new Event(type, bubbles, cancelable)`）：比較省事，但每個字典都要在膠水裡手寫一次讀取順序和預設值，每個前端都要重寫；字典一多就難維護。
  - **做法**：Rust 的欄位名稱明確寫出（`clientX as client_x`），不自動轉 snake_case（和「不選 proc macro」同一個理由）；繼承用組合（子字典的 struct 有一個放父字典的欄位）；成員要嘛有預設值、要嘛 `required`，WebIDL 裡沒有預設值的成員用 `Option<T> = None`；不支援 `any` 型別。
- **DOM 字串是 UTF-8**（2026-10-01 決定）：`DomString` 是包著 `String` 的 newtype。規範的 DOMString 是 UTF-16 的序列，可以有落單的 surrogate；JS（或用 UTF-16 的 wasm 語言）的字串轉成 `DomString` 時，落單的 surrogate 換成 U+FFFD，記成已知限制。只有刻意構造的 script 才會碰到。
  - **為什麼**：下游全是 UTF-8 的 `&str`（html5ever、cssparser、selectors、parley），不用轉換；包成 newtype，之後要換內部表示法，改動只在這個型別裡。
  - **不選 WTF-8**：能存落單的 surrogate，但要引入自訂的字串型別，交給 layout 等下游時還是要轉成 UTF-8。**不選 UTF-16**：和規範、Blink 一致，但和整個 Rust 生態都要轉換，改動最大。
- **降階的形式**：表裡的方法沒有多載和 union，可選參數明確寫出；JS 的 WebIDL 規則（多載解析、`addEventListener` 的 `options` 可以是 boolean）由 JS 的膠水在上面實作。這樣不是 JS 的前端（之後的 wasm）可以直接用降階的版本。
- **`dom` 的樹操作只檢查一部分**：`dom` 的 `insert_before` 是為 parser 寫的。規範「ensure pre-insertion validity」的其餘部分在 `dom_api` 的 `node.rs`，`appendChild` 和 `insertBefore` 共用：reference 要是 parent 的子節點；document 最多一個 element、一個 doctype，doctype 在 element 前面，沒有 text，而且照插入的位置判斷（element 不能插在 doctype 之前，doctype 不能插在 element 之後）；`DocumentFragment` 的插入搬移它的子節點，而不是插入 fragment 本身。已經是 document 子節點的 element 再插入一次也算第二個 element，和 Chromium 一樣丟 `HierarchyRequestError`。
- **`dom_bindings` 讀宣告表、安裝進 V8**，而不是一個一個手寫 `FunctionTemplate`。它負責 JS 的值和中性的值之間的轉換、wrapper、把 `DomException` 丟成 JS 的 `DOMException`：
  - 每個 interface 一個 `FunctionTemplate`，用 `inherit` 組出 prototype chain，存在 isolate 的 slot 裡給每個 context 共用；所有成員共用一個 callback，function 的 data 記著是哪個成員。
  - **`DOMException` 用 JS 定義**（`glue.js`），不做原生的：WebIDL 要求的 prototype、getter 的 `this` 檢查、常數、`Symbol.toStringTag` 都做得到，只有可序列化（`structuredClone`、`postMessage` 要複製它）做不到，那些 API 都在 MVP 之後。建立例外都經過 `dom_bindings` 的一個函式，之後換成原生的只改那裡。和 wasmtime 無關：`dom_api` 回傳的是中性的 `DomException`，每個前端自己轉換。
  - **JS 的膠水**（`glue.js`）也做 `addEventListener` 的 `options`（把 boolean 轉成字典）、`classList` 物件和 timer 的額外參數，安裝時就讀好用到的內建函式，頁面之後換掉它們也不影響。
  - **`create_realm(dom, document, frame)`**：替一份 document 建 context（global 用 `Window` 的 template，第 7 節）、建立它的 `Window` 並讓 global wrap 它、裝上 interface object 和膠水；`frame` 是 document 所在的 frame（第 7 節的 `FrameClient`）。Renderer 在 `CommitNavigation` 時經過 `ScriptEngine::create_realm` 呼叫它。
- **`ScriptHost` trait**：由每個 engine 實作，提供 DOM 的存取（`mutate`、`read`）、執行 callback（`call`）、編譯 event handler 的 content attribute（`compile_event_handler`）和 document 所在的 frame（`frame`）；`dom_api` 的函式只接 `&mut dyn ScriptHost`。這些方法都借用 `&mut self`，所以持有 DOM scope 時不能執行 script，和 `BindingContext` 是同一條規則（第 3 節），不需要另外一個 context 型別。microtask checkpoint 和替每份 document 建立 realm 原本也規劃在這裡，P3.2 改放在 renderer 用的 `ScriptEngine`（下一條）。JS 和 V8 的 wasm 共用一份實作（wasm export 的函式在 V8 裡也是 `v8::Function`），其他 engine 各自實作。
- **`ScriptEngine` trait**（P3.2 加上）：renderer 需要 engine 做的事：建立 DOM（heap 由 engine 提供）、每份 document 一個 realm（`Realm` 是不透明的）、執行 classic script（帶網址和起始行號，沒被接住的例外由 engine 回報）、microtask checkpoint，以及拿 `ScriptHost` 從 Rust 呼叫 script（事件分派、timer）。V8 的實作是 `dom_bindings::V8Engine`。
  - **renderer 不知道是哪個 engine**：`RendererFlags::script_engine` 是一個建立 engine 的函式，由啟動 renderer 的一方傳入（`shell`；`browser` 的測試），engine 在 renderer 的 thread 上才建立（`DomIsolate` 不是 `Send`）。之後把 renderer 拆成獨立的 process 時（RFC 0004），這個選擇就在 renderer process 的 main。
  - **形狀還是猜的**：只有一個 engine 時定下來的（2026-10-02 決定現在就定義，不等第二個 engine），第二個 engine 出現時預期會改。
- **`ScriptCallback`（`dom` 裡中性的 callback 型別）**：event listener、event handler、timer、`requestAnimationFrame` 的 callback 一律用它，`dom_api` 和 `ScriptHost` 的介面裡不出現 `v8::Global<v8::Function>`。現在裡面只包 V8 的 function，在 GC 物件裡存成 `CallbackSlot`。之後加 engine，或 JS 和另一個 engine 同時存在（這時一定要分得出是誰的 callback）時，只改這個型別和存它的欄位。
- **`dom` 裡 V8 專屬的部分集中成一個模組**（`src/v8_engine.rs`）：`JsEdge`、wrapper 的 slot、`wrap` / `unwrap`、`ScriptCallback` 和 `CallbackSlot` 的 V8 實作、執行 script 的入口和 callback 裡開 scope 的 `unsafe`（第 3 節）。其他模組只剩 heap 的來源（`DomIsolate` 持有 `V8PerIsolateData`，cppgc heap 接在 isolate 上）還碰到 V8。加 engine 就是加一個平行的模組。
- **依賴規則，由 `ci.py deps` 檢查**：檢查的方式和 `ci.py unsafe` 一樣，有人不小心讓 V8 的型別漏進中性的層時，CI 會擋下。
  - **crate**：除了 `bindings`、`dom`、`dom_bindings`，其他 crate 都不能依賴 `v8`、`bindings`、`dom_bindings`，也不能用 `dom` 裡屬於 V8 的公開項目（`BindingContext`、`ScriptCallback::from_v8` 等，清單在 `ci.py` 的 `DOM_V8_API`）。選 engine 的地方可以依賴 `dom_bindings`（為了 `V8Engine`），不能依賴其他 V8 的 crate：`shell`，以及 `browser` 的 dev-dependency（它的測試）。`renderer` 原本暫時例外，P3.2 改成只透過 `ScriptEngine` 之後就不需要了。
  - **`dom` 裡面**：除了 V8 模組（`src/v8_engine.rs`）和 heap 的來源（`src/isolate.rs`，`V8PerIsolateData` 和 `HeapAccess`），只能用 `v8::cppgc`。為此把 `HeapAccess` 從 `scope.rs` 搬到 `isolate.rs`。
- **為什麼現在就做**：之後加不經過 JS 的 wasm 腳本（`rfcs/0001-wasm-scripts/`）或其他 engine 時，只要寫值的轉換和「把宣告表安裝進 engine」的迴圈。新增一個 DOM API 也只改宣告和 `dom_api`。之後要換成 WebIDL 的 code generator 時，主要是把宣告搬成 `.webidl` 檔，膠水和 `dom_api` 不用動。

### 5. Script 執行（P3.2）

- **每份 document 一個 realm**：`CommitNavigation` 時經過 `ScriptEngine::create_realm` 建新的 realm，在 parse 之前，因為 document 的 script 一邊 parse 一邊執行。舊的連同 document 一起丟掉。
- **Parser 在 `</script>` 暫停**（`html::Parser`）：html5ever 的 tree builder 遇到 `</script>` 一定回傳 `Script`，原本一次 parse 完的 driver 忽略它；`Parser` 自己驅動 tokenizer，停下來把 script 元素交給 renderer，renderer 處理完再 `resume`。
  - **DOM 的借用**：parser 要跨 task 存活（等外部 script），型別不能帶著 `DomIsolate` 的借用。所以 renderer 把 `DomIsolate` 放在 `Rc<RefCell<…>>`，parser 的 sink 也持有一份，每個 tree 操作只在自己的期間借用；parser 停著時 DOM 是 renderer 的，可以執行 script。都是 safe code。代價是 `document.write` 做不到：它會在 script 執行途中把內容餵給 parser，等於重複借用。
  - **其他做法都不行**：sink 持有借用（tokenizer 活得比它久）、thread-local 傳 scope（scope 不是 `'static`）、raw 指標（renderer 不能寫 `unsafe`）。
  - **行號**：sink 記下每個 script 開始標籤結束的那一行，錯誤訊息從那裡數（V8 的 `ScriptOrigin` 的行號偏移）。content attribute 的 event handler 也記下它所在的那一行（第 7 節）。
- **「prepare the script element」**（`renderer` 的 `script.rs`）：沒接上 document 的（template 的內容）、type 不是 JavaScript 的、`type=module`、空的不執行；`nomodule` 照樣執行（不支援 module 的瀏覽器就是這樣，2026-10-02 決定）。
- **外部 script**：`<script src>` 經 `FetchResource`（用途 `Script`）載入。
  - **時機**：沒有 `async` / `defer` 的擋住 parser，回應到了才在那個 task 裡執行、繼續 parse；`defer` 在 parse 完之後照順序執行；`async` 載好就執行（2026-10-02 決定兩者都做，規劃時原本排在之後）。
  - **回應**：非 2xx、MIME 是圖片、影音或 `text/csv` 的不執行；用 BOM、回應的 `charset`，最後用 document 的 encoding 解碼。
  - **Parser 的 handle**：html5ever 把節點存在自己的 stack 裡，P1 用 `NodeHandle`（`Persistent`，是 root）讓它們不被回收，跨 task 照樣安全，只是 root 比較多。`P1.md` 第 2 節提過的另一個做法（parser 本身是 GC 物件，用 `trace_handles`）留到之後再說。
- **每個 script 之後做 microtask checkpoint**（HTML 的「clean up after running script」）：parser 一次執行好幾個 script 時也是。
- **錯誤回報**：沒被接住的例外印到 stdout，`[uncaught] 訊息 (網址:行號)`，和 `console.log` 一樣。規劃時寫的是 V8 的 message listener；實際上 script 在 `TryCatch` 裡執行，例外由 engine 自己回報，listener 丟出的例外也一樣（`V8Host::call`）。
- **載入完成**：parse 結束、所有 script 執行完、子資源都載好才算載入完成，而且只在 `start_loads` 之後判斷，parse 的結尾和 script 新增的圖片也算在內。完成時先分派 `load`（第 7 節），之後才送 `DidFinishLoad`；headless 和 reftest 等它。
- **子資源在 parser 每次停下來時就開始載入**：`start_loads` 可以重複呼叫，已經要求過的不再要求，script 新增的 `<img>` 也會載入；base URL 每次重算（`<base>` 可能出現在後面）。原本 inline script 先執行、才開始載入它前面的 stylesheet，被 script 拿掉的 stylesheet 因此永遠不會被要求（補 mutation test 時發現的）。
- **`javascript:` 網址**：點連結時在這份 document 的 realm 裡執行，不導航。回傳的字串不會取代 document（規範會）。
- **先不做的**（已知限制）：stylesheet 擋住 script（規範要 inline script 等前面的 stylesheet 載完；還沒有 `getComputedStyle`，看不出差別）；script 插入的 `<script>` 不執行；`document.write`；`document.currentScript` 和 script 元素的 `load` / `error` 事件。

### 6. Event loop 和 timer（P3.3）

對應 HTML 規範的 event loop 和 Blink 的 `scheduler`。
- **原本的 loop**：renderer 等 Browser 的訊息，處理完所有排著的訊息後執行 V8 的 platform task，有需要就跑一次 rendering update（`render_thread.rs` 的 `run`）。
- **現在**：
  - Browser 的訊息、timer 到期、網路回應都是 task；每個 task 之後經過 `ScriptEngine` 做 microtask checkpoint，timer、animation frame 和 renderer 分派的事件的每個 callback 之後也是（HTML 的「clean up after running a callback」）。
  - loop 等訊息時，最多等到最早的 timer 到期。到期的 timer 一個一個執行，每個是一個 task：最早到期的先，同時到期的照設定的順序。
  - Rendering update 只在 Viz 的 `BeginFrame` 來時跑：先執行 `requestAnimationFrame` 的 callback（拿到 `BeginFrame` 的時間），再跑 style 之後的 pipeline。
- **Timer 的資料在 `dom`**（`Timers`，2026-10-02 決定）：engine 中立的清單，callback 存成 `ScriptCallback`，時間由 renderer 在每個 task 前設定（monotonic clock，真實時間），`dom` 自己不讀時鐘。HTML 的 timer nesting level：超過 5 層時 timeout 至少 4 ms，`setInterval` 每執行一次深一層。換 document 時清空。
- **API 是 `Window` 的成員**：`setTimeout`、`setInterval`、`clearTimeout`、`clearInterval`、`requestAnimationFrame`、`cancelAnimationFrame`，都在 `[Global] interface Window` 上（第 7 節）。
  - **P3.3 時的暫時做法**：那時 `Window` 還不是 GC 物件，它們放在宣告表的一個 `global` 區塊，`this` 暫時是這個 realm 的 document；當時不選把 `Window` 提前做，因為 V8 wrap global 物件比較特殊，工作量大很多。P3.4 有了 `Window` 之後拿掉這個區塊。
  - `setTimeout` 額外的參數由 JS 的膠水綁到 handler 上，以 global 為 `this` 呼叫；字串的 handler（要編譯成 script）不支援。
- **Frame 的節奏**（「已決定的事項」第 4 條）：rAF 每個 frame 一次。
  - **協定**：renderer 經過 frame sink 對 Viz 送 `SetNeedsBeginFrame`（有東西要畫，或有 rAF 在等）；Viz 回 `RendererMsg::BeginFrame`（`BeginFrameArgs`：序號和時間）；renderer 一定回答，送 frame，或 `DidNotProduceFrame`（例如 stylesheet 還在擋 rendering），回答之前不會收到下一個。
  - **`viz::BeginFrameSource`**：記錄每個 client 要不要、上一個回答了沒。Viz 不認識 renderer 的型別：client 是 `WebContents::begin_frame_sender` 給的 closure，送在 renderer 的 channel 上，就像 mojo 傳過來的 pipe。Browser 自己的 UI 不要 `BeginFrame`，照舊自己送 frame。
  - **視窗模式**：Viz thread 每 16.7 ms 送一次（還沒有 vsync 的訊號可以跟，規劃時寫的「跟著 present 的節奏」）。**headless 和測試**：一回答就送下一個，時間是虛擬的（每個 frame 加 1000/60 ms），所以 rAF 的結果每次都一樣。
  - **`browser` 和 `shell` 的測試**也要送：沒有 `BeginFrame`，renderer 就不畫，`DidFinishLoad` 也不會來。`browser_view` 測試在讀 Viz 訊息的同一個 thread 回應，不能另開 thread 轉送：frame 要在 host channel 上它後面的訊息到達時就讀得到（轉送會讓 frame 晚到，測試第一次這樣寫就不穩定）。
- **`reftest-wait`**（第 8 節）：`RendererFlags::web_tests`（對應 content_shell 的 `--run-web-tests`，只有 headless 打開）時，renderer 在 `DidFinishLoad` 報告 `<html>` 還有沒有 `reftest-wait`，之後每個 frame 檢查，拿掉時送 `ReftestWaitEnded`（帶那個 frame 的 token）。harness 等它才截圖；等了 600 個 frame（虛擬時間 10 秒）還在就是錯誤，不讓永遠不停的動畫卡住測試。
- **DOM 修改**：只設 document 層級的 `style_dirty`（`MVP.md` 的設計決定第 3 條），下一個 frame 從 style 開始重算。節點層級的 dirty flag 和 invalidation 是 P4。

### 7. 事件（P3.4）

對應 Blink 的 `EventTarget`、`EventDispatcher`、`LocalDOMWindow` 和 `MouseEventManager`。

**GC 型別**（`dom` 的 `src/event.rs`）：
- **`Event` 是 cppgc 上的 GC 物件**（和 Blink 相同），一個型別涵蓋所有事件：`EventKind` 區分一般事件和滑鼠事件（`clientX`、`clientY`、`button`）；`target` 和 `currentTarget` 是指向節點或 window 的 `TargetEdge`；phase 和 DOM 的旗標（stop propagation、canceled、in passive listener、dispatch）放在不被 trace 的區域。JS 可以 `new Event(...)` 再 `dispatchEvent`，所以它要能被 wrap，用自己的 tag（第 2 節）。
  - **不選只活在 JS heap 的一般 JS 物件**：可能比較簡單，但那樣只有 V8 拿得到它，之後別的 engine（`rfcs/0001-wasm-scripts/` 的 wasmtime）就沒辦法分派同一個事件（「已決定的事項」第 9 條）。
- **`Window` 是 cppgc 上的 GC 物件**（對應 `LocalDOMWindow`），每份 document 一個，指向它的 document；document 也指向它的 window（`NodeKindData::Document` 的 edge，對應 `Document::dom_window_`），事件從 document 往上走到 window 時用它。理由和 `Event` 相同：如果 window 只是 V8 的 global 物件，window 上的 listener（例如 `load`）就只有 V8 拿得到。
  - **Window 被 global wrap**：realm 的 global proxy 用 `WrapTag::Window` wrap `Window`（`BindingContext::bind_window`），和 Blink 一樣；V8 允許 wrap global proxy 這類特殊物件。binding 從 `this` unwrap 出 window，unified heap 一起 trace 兩邊，不需要 root。不選「realm 用 root 持有」：binding 只拿得到 context，要找回 window 就得在 V8 的 slot 裡放 root，而 slot 什麼時候釋放由 V8 的 GC 決定，可能比 `DomIsolate` 晚。
- **Listener 掛在 EventTarget 上，不只掛在節點上**：P3.0 的 listener 串列在 `Node.first_listener`，`Window` 不是節點，所以串列的開頭放到每個 EventTarget（`Node`、`Window`，之後的 `AbortSignal` 等），listener 的操作接 `EventTarget`（節點或 window），串列本身不變。

**宣告表裡的事件**：
- **`EventTarget` 是 interface**：`addEventListener` / `removeEventListener` / `dispatchEvent`，`Node` 和 `Window` 繼承它。沒有 `new EventTarget()`：單獨的 EventTarget 要多一種 GC 型別（Blink 的 `EventTargetImpl`），P3 用不到。
- **`Window` 是 `[Global]` interface**：成員有 `window`、`self`、`document`、`onclick`、`onload` 和 timer。realm 的 global 用它的 instance template 建立（`ScriptState::with_global_template`），所以 global 的 prototype chain 是 `Window.prototype` → `EventTarget.prototype`，成員是 global 自己的屬性；`window` 和 `document` 是 `[LegacyUnforgeable]`。
- **`Event`、`UIEvent`、`MouseEvent`**：`new Event(type, EventInit)`、`new MouseEvent(type, MouseEventInit)`，建立的事件 `isTrusted` 是 false、`timeStamp` 是 event loop 現在的時間。`Event` 有 `type`、`target`、`currentTarget`、`eventPhase`、`bubbles`、`cancelable`、`defaultPrevented`、`isTrusted`（`[LegacyUnforgeable]`）、`timeStamp`、`stopPropagation`、`stopImmediatePropagation`、`preventDefault`；`MouseEvent` 有 `clientX`、`clientY`（CSSOM View 的 `double`）、`button`。`UIEvent` 只是 `MouseEvent` 的父 interface，沒有建構子。
- **V8 不會把父 interface 的 instance template 套到子 interface 的物件上**，所以父 interface 的 `[LegacyUnforgeable]` 成員（`Event` 的 `isTrusted`）在每個子 interface 的 instance template 上再裝一次。

**分派**（`dom_api::event::dispatch`，照 DOM 規範）：
- **路徑**（`event_path`）：target、它的祖先、document，再到 window；`load` 不從 document 到 window（window 的 `load` 另外分派）。不選「分派時由呼叫端傳入 window」：JS 的 `dispatchEvent` 只拿得到節點，還得另外找 window。
- **順序**：capture pass 從最外層到 target（target 的 capture listener 在這時呼叫）、bubble pass 從 target 往外（target 的其他 listener；事件 bubble 時才往外）。每個 listener 經過 `ScriptHost::call`，是一次 script 執行，前後交出和取回 scope（第 3 節）；例外由 host 回報，分派繼續。`once` 在呼叫前移除，`passive` 時 `preventDefault` 無效，`stopPropagation` / `stopImmediatePropagation` 照規範，結束時清掉 phase、current target 和 stop 的旗標。
- **`dispatchEvent`**：對分派中的事件丟 `InvalidStateError`，回傳是否沒被取消。
- **Activation behavior**：`MouseEvent` 的 `click` 有 activation target（target 本身，或 bubble 時路徑上第一個有 activation behavior 的）；分派結束、沒被取消時執行它。有 activation behavior 的只有 `<a>`：有 `href` 就經過 `FrameClient` 沿著連結導航（下面的「renderer」）。JS 的 `dispatchEvent` 送的 `click` 也會導航。
- **HTML 的「legacy target override」**：window 的 `load` 的 `target` 是 document（`dispatch_with_legacy_target_override`）。

**Event handler**（`onclick`、`onload`；`dom_api` 的 `handlers`）：IDL attribute 和 content attribute 都做，在 `Element`、`Document`、`Window` 上；`<body>` 的 `onload` 是 window 的（HTML 的「Window-reflecting body element event handlers」）。
- **handler 是串列裡一個特別的 listener**：照規範，值改變時留在原位，設成 `null` 時移除，再設時加在最後，所以和 `addEventListener` 混用時順序也對；`addEventListener` 的比對規則碰不到它。回傳 `false` 時取消事件（HTML 的「event handler processing algorithm」）。
- **content attribute 第一次用到時才編譯**：parser 建元素時、`setAttribute` 時呼叫 `handlers::attribute_changed`，存成沒編譯的原始碼和行號（`html` 因此依賴 `dom_api`）；分派或讀 IDL attribute 時經過 `ScriptHost::compile_event_handler` 編譯（V8 的 `CompileFunction`，`function (event) { ... }`，scope 是元素、document、global，和 Blink 一樣），存回去。編譯失敗由 host 回報，handler 停用。沒編譯的 handler 不碰 callback slot，所以沒接 isolate 的 parser 測試也能加。
- **只做 IDL attribute 不夠**：P2 擴充 WPT 時就因為 `onload=` 擋掉了一個測試。

**Renderer**：
- **`click` 送到按下和放開的共同祖先**：主按鍵按下和放開時各 hit test 一次，trusted 的 `MouseEvent`（帶指標的 viewport 座標）送到兩個元素最近的共同祖先，和 UI Events、Chromium 的 `MouseEventManager::GetClickTarget` 一樣；只打到 canvas 時是根元素。P2 的「在同一個連結上按下又放開才算點擊」拿掉了，連結導航變成 `<a>` 的 activation behavior：沒被 `preventDefault` 才導航，和 Chromium 相同。
- **連結的導航經過 `FrameClient`**（`dom_api`，對應 Blink 的 `LocalFrameClient`；2026-10-02 決定）：renderer 建立 realm 時把它交給 engine（`ScriptEngine::create_realm`），`dom_api` 經過 `ScriptHost::frame` 拿到，現在只有 `follow_link`。
  - **為什麼**：Chromium 是 core 同步呼叫 embedder 實作的介面（`HTMLAnchorElement::HandleClick` → `LocalFrame::Navigate` → `FrameLoader` → `LocalFrameClient::BeginNavigation`）。之後很多 API 要當下從 renderer 拿到答案（`getBoundingClientRect`、`innerWidth`、`scrollY`、`confirm()`），只有介面做得到。
  - **不選「導航請求記在 `DomState`，renderer 之後取出」**：比較省事，但每種要求都要多一種請求型別，要回傳值的 API 也做不到。
  - **renderer 的實作先記下來**（`FrameRequests`）：回呼發生時 script 正在執行，`FrameView` 不能動。HTML 的導航本來就是非同步的，所以 event loop 每一輪的結尾（這一輪的訊息、timer 和 animation frame 都跑完之後）才處理：fragment 捲動、其他文件交給 browser、`javascript:` 網址執行。只有 input 例外，回 `InputEventAck` 之前先處理：fragment 的導航是同步的，browser 和 headless 收到 ack 時捲動要已經做完。原本也在每輪結尾才處理，`shell` 的 fragment 連結測試因此偶爾截到捲動之前的畫面。
- **`DOMContentLoaded` 和 `load`**：parse 結束、`defer` 的 script 執行完時在 document 分派 `DOMContentLoaded`（bubble）；子資源和 script 都完成時，在 window 分派 `load`（target 是 document），之後才送 `DidFinishLoad`。都是 trusted。`load` 的 listener 新增的子資源照常開始載入，但不再延後 `DidFinishLoad`，和瀏覽器一樣。
- **`about:demo`**：保留原本的內容，加一段 script 的示範：`onclick` 的按鈕、`preventDefault` 擋住的連結、`setTimeout` 換顏色、`setInterval` 的計時、rAF 的動畫、`load` 時的訊息。

### 8. 測試

- **`dom_api` 的單元測試**：不經過任何 engine，直接測規範的演算法（`ScriptHost` 用測試用的實作）。這個測試用的實作等於第二個 engine，證明 `dom_api` 不需要 V8 就能跑。
  - **分派不在這裡測**：沒有 engine 就註冊不了 listener（`ScriptCallback` 只能包 V8 的 function），所以 `dom_api` 只測事件的路徑，分派和重新進入（listener 裡再 `dispatchEvent`）在 `dom_bindings` 用 V8 測。規劃時原本打算這裡也測分派；不選讓 `ScriptCallback` 也能裝測試用的 Rust callback：要改 `dom` 存 callback 的 GC 欄位，只為了測試不划算。
- **依賴規則**：`ci.py deps` 檢查第 4 節的依賴規則。
- **`dom_bindings` 的單元測試**：建 document、直接跑 script，檢查 DOM 和 script 的回傳值。不經過 renderer，跑得快，也方便 mutation test。
- **GC 加上 JS**：
  - GC stress 加上 JS 的工作負載（`dom_bindings` 的 `gc_stress`）：用種子隨機產生 script，wrapper 上加屬性、listener 的 closure 抓住節點、節點從樹上拿掉後只靠 JS 活著，每次配置節點都強制 GC，檢查該活的都還活著、該回收的都回收了；`ci.py matrix` 和 `fuzz` 也跑 `dom_bindings`。
  - `--gc-interval` / `--random-gc-interval` 在 P1 沒有用（P1 幾乎沒有 JS），和 `--cppgc-random-gc-interval` 一起加進 `ci.py fuzz` 的 flag：自己編的 debug V8 有 `V8_ENABLE_ALLOCATION_TIMEOUT`，三個都會生效。
- **Reftest**：需要等 script 的測試照 WPT 用 `reftest-wait`：harness 等 `<html>` 的 `reftest-wait` class 被拿掉才截圖（第 6 節，「已決定的事項」第 6 條）。runner 也支援 reference 自己還有 reference 的鏈：reference 還要通過它自己的 reference，和 wptrunner 一樣，做過的比較跳過，因為 WPT 裡有互相指向的 reference。
- **端到端**：`shell::headless::render_after_input` 送點擊；`browser` 的測試看導航和載入事件的順序。
- **Mutation test**：照 `docs/README.md`，每一批 reftest 和每個新測試都要弄壞實作確認會失敗。

## 已決定的事項

2026-10-01 確認：

1. **JS 呼叫 DOM 時，callback 直接修改 DOM**，照第 3 節：執行 script 的入口拿走 `&mut DomIsolate`，callback 由 `dom` 開 scope，執行 script 需要的 token 被 scope 借走。
   - **和 Chromium 一樣直接改**：Blink 產生的 binding 從 wrapper 拿出 `Node*`，直接呼叫 `Node::appendChild`，沒有延後套用。它沒有 borrow checker，「狀態做到一半時不要執行 JS」靠的是慣例和 runtime 的檢查：`ScriptForbiddenScope` / `EventDispatchForbiddenScope` 標出不准執行 JS 的區域；custom element 的 callback 排進 `CEReactions`，等這次 binding 呼叫結束才執行；會呼叫到 JS 的 DOM 演算法在 JS 回來之後重新確認狀態。在修改 DOM 途中同步執行 JS 的 mutation events，因為造成很多安全問題，Chrome 已經預設關掉。我們把同一條規則改成在編譯期由型別擋下。
   - **不選延後套用**：callback 把修改排進清單、script 結束後才套用，就不需要新的 `unsafe`，但 JS 讀不到自己剛寫的東西（`appendChild` 之後 `lastChild` 還是舊的），不符合規範。
2. **Event listener 用 GC 物件串成的 linked list**（第 1 節）：每個 listener 是一個小的 GC 物件，用 `Edge` 串起來，callback 是 `ScriptCallback`（V8 的實作裡用 `TracedSlot` 指向 JS 的 function）。
   - **Blink 用 `HeapVector`**：`EventTarget` 的 `EventListenerMap` 依事件類型分成幾個 `HeapVector`，每個 listener 是 GC 物件（記著 capture、once、passive 和一個「已移除」的標記），JS 的 callback 用 traced reference 持有。分派時只走到開始時的長度，所以途中新增的不會被呼叫；途中移除的標成已移除、跳過。我們的行為照這個語意，只有「清單本身」不同。
   - **為什麼不先做 `HeapVector`**：Oilpan 的 `HeapVector` 在 concurrent marking 下的正確性（底層陣列的重新配置、元素的寫入和標記之間的同步）是多年累積的基礎設施；我們用的 `v8` crate 沒有這一層，要從頭做，而記憶體順序的錯誤很難用測試抓到（P1 在 ARM64 上拿掉 fence，stress 照樣通過）。Linked list 只用現有的 `Edge`，concurrent marking 時已經是安全的。一個節點上的 listener 通常只有一兩個，O(n) 的成本可以接受。之後真的需要大量元素的 GC 集合時再做 `HeapVector`。
3. **`dom_bindings`（和 `dom_api`）保持 safe**：`Object::wrap` / `unwrap`、callback 開 scope 這些 `unsafe` 寫在 `dom`（和 `bindings`）裡，對 `dom_api` 和 `dom_bindings` 提供 safe API。`ci.py unsafe` 的規則不變，soundness 的審查範圍還是那兩個 crate。另一個做法是允許 `dom_bindings` 寫 `unsafe`，寫起來直接，但審查範圍會變成三個 crate。
4. **Viz 發 `BeginFrame` 驅動 `requestAnimationFrame`**：renderer 有東西要畫時才要求下一個（對應 Chromium 的 `SetNeedsBeginFrame`）；headless 由 harness 送，測試可以精確地推進 N 個 frame。P4 的 compositor thread 本來就要這個機制。不用 renderer 自己的 16 ms timer：headless 的測試要靠真實時間，不穩定，P4 也還是要改。
5. **DOM API 比 `MVP.md` 的最小集合多一點**：
   - `classList` 的 `add` / `remove` / `contains` / `toggle`：WPT 的 `reftest-wait` 測試幾乎都用 `classList.remove("reftest-wait")`，`toggle` 在一般頁面上和 `add`、`remove` 一樣常見。`MVP.md` 把 `classList` 列在「先不做」，這裡只做這四個方法。
     - **降階的做法**：宣告表裡沒有 `DOMTokenList`，只在 `Element` 上放四個扁平的方法（`classListAdd` 等），JS 的膠水組出一個普通的 JS 物件當 `classList`，存在 element 的 wrapper 上，所以每次都是同一個物件；它不存狀態，每次都直接讀寫 class attribute，所以是「活的」。和規範的差別：沒有 `length`、索引、迭代、`replace`，`instanceof DOMTokenList` 是 false。
     - **演算法是通用的**：規範的 token list 操作（解析成有序集合、增刪、toggle、序列化）和「是哪個 attribute」無關，寫成 `dom_api` 的 `token_list` 模組，參數是 (element, attribute 名稱)。之後的 `relList`、`iframe.sandbox`、`link.sizes` 等也用它。
     - **之後需要完整的 `DOMTokenList` 時**：改成真正的 GC 物件，只存 (element, attribute 名稱)，裡面呼叫同一個模組；wrapper 的型別資訊（第 2 節）已經做好，不會卡在 wrap。
   - `on*` attribute（`onclick`、`onload`）：簡單的網頁和 WPT 很常用；P2 擴充 WPT 時就因為 `onload=` 擋掉了一個測試。
   - `createTextNode`、`removeChild`、`getAttribute`、`parentNode`、`firstChild` / `nextSibling`：最小集合裡沒有，但幾乎所有改 DOM 的 script 都會用到。匯入 WPT 時又加了 `documentElement`、`body`、`insertBefore`（「第三批 reftest」的「WPT」）。
   - `javascript:` 網址（P2 讓它什麼都不做）在 P3.2 做。
6. **WPT 只匯入 reftest**。`testharness.js` 的測試（例如 `MVP.md` 測試策略提到的 `dom/nodes`）不在 P3 做：`testharness.js` 本身需要的 DOM API 遠超過最小集合（`Promise` 的整合、各種 node 的方法、`testharnessreport.js` 的回報），值得之後當成一個獨立的工作。
7. **`Intl`（ICU 資料）留到之後**：`MVP.md` 的 P3 沒有排它，驗收也用不到。
8. **與 engine 無關的 DOM 層和 API 宣告表在 P3 就做**（第 4 節）：`dom_api` 放規範的演算法和事件分派，一份用 Rust macro 寫的宣告表產生各 engine 的 binding，`ScriptHost` 是執行 script 的唯一入口。
   - **為什麼**：之後要支援不經過 JS 的 wasm 腳本（MVP 之後的目標，設計和比較過的做法見 `rfcs/0001-wasm-scripts/`），也可能接其他 engine。分層之後，每加一個前端只寫一層膠水，所有前端共用同一份 DOM 語意。
   - **不選每個 engine 手寫 binding**：最快，但第二個前端要全部再寫一次，也容易漏。
   - **不選現在就做 WebIDL 的 code generator**：最標準（Blink 和 Servo 的做法），但前期成本最高，`MVP.md` 也排在「API 變多時」。宣告的寫法貼近 WebIDL，之後換過去主要是搬宣告。
9. **engine 中性的邊界**（第 4 節，2026-10-01 加上）：`ScriptCallback` 是中性的 callback 型別；`ScriptHost` 負責 DOM 的存取和執行 callback，`ScriptEngine` 負責 realm、執行 script 和 microtask checkpoint（P3.2 加上，renderer 只看得到它）；`dom` 裡 V8 專屬的部分集中成一個模組；依賴規則由 `ci.py` 檢查；執行 script 的 token 只有一份，由 `DomIsolate` 擁有（第 3 節）；`Event` 和 `Window` 是 cppgc 上的 GC 物件，listener 掛在 EventTarget 上（第 7 節）；DOM 字串是 UTF-8 的 `DomString`（第 4 節）；wrapper 的型別資訊在 P3.1 做（第 2 節）。
   - **為什麼**：wasm 腳本先跑在 V8 上，但有一天希望改走「fork wasmtime、用 cppgc 當它的 collector」（`rfcs/0001-wasm-scripts/details.md` 的「未來考慮：wasmtime 加上 cppgc collector」）。這幾處如果照原本的規劃直接用 V8 的型別，`v8::Global<v8::Function>` 和只活在 JS heap 的 `Event` 會散進 `dom_api` 和 event loop，到時候要整層重寫。現在就分開，成本只是一個包裝型別和一條 CI 規則。
   - **不現在就把 `ScriptCallback` 做成可替換的介面**（trait 或 enum）：只有一種實作時，看不出介面該長什麼樣子。等第二種 engine 真的要做時再改，改動只在這個型別和存它的欄位。
   - **保證的範圍**：這些規則保證的是「我們這一側不會無意間加上新的 V8 依賴」；wasmtime 那一側還待回答的問題列在 `rfcs/0001-wasm-scripts/details.md` 的「未來考慮：wasmtime 加上 cppgc collector」。
10. **自己編 V8**（2026-10-02，第 2 節的評估）：machopo 依賴我們 rusty_v8 的 fork（`../third_party/rusty_v8`，`machopo` 分支，從上游的 v152.2.0 開始），開 `v8_enable_pointer_compression`，V8 從 fork 的原始碼編 debug 和 release 兩種。2026-10-04 起由 fork 的 CI 編（`machopo-v*` tag 的 GitHub Release），machopo 用 `.cargo/config.toml` 的 `RUSTY_V8_MIRROR` 和 `RUSTY_V8_MIRROR_TAG` 下載（見下面的「由 fork 的 CI 編」）。平常的 build 和測試連結 release 的 V8，要 V8 的 DCHECK 時才用 debug 的（見下面的「平常用 release 的 V8」）。
    - **由 fork 的 CI 編，預設下載**（2026-10-04 改）：fork 的 `.github/workflows/machopo-release.yml` 在推 `machopo-v<版本>-<n>` tag 時編 Windows x86-64（只有 release）、macOS arm64、Linux x86-64 的 debug 和 release，放進那個 tag 的 release；檔名和上游的 prebuilt 相同，所以 rusty_v8 的 `build.rs` 不用改。`../third_party/rusty_v8` checkout 在同一個 tag，Rust 這側和 static library 才是同一個 commit。
      - **原本的做法**：每個人用 `python scripts/ci.py v8` 在本機編，結果放在 machopo 旁邊的 `rusty_v8_artifacts` 目錄（`ci.py v8` 的輸出，不是 repo），`.cargo/config.toml` 的 `RUSTY_V8_ARCHIVE` 指向那裡。
      - **為什麼改**：第一次設定要先編四十分鐘以上（Windows 更久），還要 libclang 和 fork 全部的 submodule；machopo 自己的 CI 也需要一份不用每次重編的 V8。現在只要 fork 的 `v8` submodule（`bindings` 的 build script 讀它的原始碼）。
      - **保留本機編的選項**：改 fork 時不能每次都推 tag、等 CI 編完才測，所以 `ci.py v8` 還在，在環境變數設 `RUSTY_V8_ARCHIVE` 就連結本機編的（`build.rs` 讓它優先於 mirror）。
      - **不 fallback 到上游**：沒設 `RUSTY_V8_MIRROR_FALLBACK`，release 裡缺檔案時 build 直接失敗，不會悄悄連結上游沒有我們 patch 的 prebuilt。
      - **代價**：發新版要等 CI 編完（幾個小時）；只有上面三個平台有 prebuilt；下載的檔案沒有雜湊驗證（`RUSTY_V8_ARCHIVE_SHA256` 只能釘一個檔案）。
    - **為什麼**：有 pointer compression，V8 才會在 `unwrap` 時檢查 tag，wrapper 的型別資訊就能用 tag 登記表；rusty_v8 有 pointer compression 的 prebuilt 只有 macOS 和 Linux x86-64。自己編也打開了之後的 TSan、marking verifier（P1 因為不從原始碼編而放棄的兩項）、V8 sandbox、debug build 的 DCHECK，以及在 fork 上 patch `binding.cc`。
    - **Fork 上的修改**（清單在 fork 的 `README.machopo.md`）：
      - `RustObj` 的建構子寫入 Rust 的資料，在 cppgc 標記「已建構完成」之前，所以 `MemberSlot` 的兩個 fence 拿掉了（soundness.md 的「Concurrent marking」）。這是 P1 想做、但 MSVC 編的 glue 接不上 prebuilt 而做不到的修法（`P1.md` 1.3）。
      - GC 的 slot 型別（`v8::cppgc::{MemberSlot, WeakMemberSlot, TracedSlot}`）和測試用的 `v8::cppgc::testing` 從 `bindings` 搬進 fork。它們用的是 `v8` crate 私有的 C 函式和 layout，原本 `bindings` 要自己宣告那些函式、用 `build.rs` 比對原始碼；放在 fork 裡，大部分直接用上游的宣告和 build 產生的 layout 常數，上游改了就是編譯錯誤，`build.rs` 只剩比對 V8 的行為和 fork 的初始化。`bindings` 也不再有 C++ glue。
      - `Object::is_wrapping`（第 2 節）。
    - **平常用 release 的 V8，要 DCHECK 時才用 debug 的**（2026-10-02，P3 完成之後改）：一般的 build、`cargo test` 和 `--release` 都連結 release 的 V8；設了 `V8_FORCE_DEBUG=1` 才連結 debug 的，這是 rusty_v8 上游原本的規則。`python scripts/ci.py matrix`、`fuzz` 會自動設，並用另一個 target 目錄（`target/v8-debug`），兩種 build 不會互相蓋掉、來回重編。2026-10-04 起 `matrix` 和 `fuzz` 只在動到 GC 時跑（見下面的「拿掉 `ci.py debug-v8`」）。
      - **原本的做法**：fork 改了 `build.rs`，設了 `RUSTY_V8_ARCHIVE` 時照 cargo 的 profile 選，所以 dev build 和所有測試都連結 debug 的 V8。現在 fork 的 `build.rs` 回到和上游相同。
      - **為什麼改**：量過，release 的 V8 底下跑全部測試、改了 renderer 之後重新 link 都明顯比較快，每一組相鄰的比較都是 release 快；差距主要在每個啟動 renderer 和 V8 的測試 binary 上，reftest 每一頁都開一個新的 renderer，所以最明顯。測試結果完全相同。數字和量的方法見 `PROGRESS.md` 的「做過的檢查」。
      - **量的過程踩過的坑**：這台機器的雜訊很大（同一個設定的秒數可以差好幾倍，剛 link 好的 binary 第一次跑也比較慢），每種只量兩次、沒有暖身時，一度量出「沒有差別」而撤回了這個改動。從頭重編兩種 V8、先暖身、交替量四輪之後，結論才穩定。之後再量這類東西，只比較相鄰的兩次，並先暖身。
      - **為什麼不是只在驗 GC 時用 debug**：DCHECK 檢查的是 V8 內部的前提條件，包括 cppgc 的；`dom`、`bindings`、`dom_bindings` 的 `unsafe` 依賴 V8 的這些前提。它抓到過 `cppgc_member` 的測試在建立 heap 之前就建立 slot。`ci.py fuzz` 用的 `--gc-interval` 等 flag 也只有 debug 的 V8 有效（要 `V8_ENABLE_ALLOCATION_TIMEOUT`）。所以用 debug 的條件和跑 `ci.py matrix` 的相同。兩種 V8 都沒開 `v8_enable_v8_checks`（rusty_v8 的 build 設定），V8 header 裡 inline API 的額外檢查（`V8_ENABLE_CHECKS`）兩種都沒有。
      - **拿掉 `ci.py debug-v8`**（2026-10-04）：原本另外有 `ci.py debug-v8`，在 debug 的 V8 底下跑全部的測試，條件和 `matrix` 相同。使用者決定拿掉：整套檢查的 156 秒裡它佔 103 秒（其中 28 秒是重編），而 `matrix` 已經在 debug 的 V8 底下跑 `dom`、`bindings`、`html`、`dom_bindings` 的測試，也就是 `unsafe` 依賴 V8 前提的那幾個 crate。少掉的是 `browser`、`shell` 這些啟動 renderer、也會執行 script 的端到端測試，它們不再在 DCHECK 底下跑。同一天使用者也決定 `matrix` 和 `fuzz` 只在動到 GC 時跑，動到 `dom`、`bindings`、`dom_bindings`、`html` 的其他部分和階段驗收時不再必跑。
      - **代價**：平常沒有任何測試在 DCHECK 底下跑；只有動到 GC 時跑 `ci.py matrix`，動到 `dom`、`bindings`、`dom_bindings`、`html` 的其他部分（例如 binding 或 script 的入口）時不在 DCHECK 底下測；debug 的 V8 要另一份 build，多佔磁碟，第一次也要完整 build 一次。
    - **代價**：第一次編很久、要不少磁碟空間（數字見 `PROGRESS.md` 的「做過的檢查」），macOS 上要 Homebrew 的 llvm（bindgen 要 libclang 21.1 以上）；升級 `v8` 時 fork 要 rebase、再編一次；pointer compression 讓 heap 上限約 4 GB（Chrome 也是這樣）。Windows 2026-10-03 編過（要關掉 PartitionAlloc，見 fork 的 `README.machopo.md`）。
    - **取代 `MVP.md` 和 `P1.md` 原本的決定**：用 prebuilt，不從原始碼編 V8（`P1.md` 1.7 把需要從原始碼編 V8 的測試列為不做）。
