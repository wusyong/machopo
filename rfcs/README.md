# RFC

MVP（P0 到 P4，2026-10-04 完成）之後，新的功能和要先比較好幾種做法才能動手的設計都寫成 RFC：要解決什麼、比較過的做法和理由、架構、已決定的事項；開始實作之後，進度也記在同一個資料夾。格式參考 [Rust 的 RFC](https://github.com/rust-lang/rfcs)，依 machopo 的需要調整（見「和 Rust 的 RFC 不同的地方」）。

文件共通的規則（日期的寫法、測試數字只寫在 `progress.md`、RFC 的引用只放在 `rfcs/`）照 `docs/README.md`，RFC 用中文。`rfcs/` 以外的檔案不寫 RFC 的編號和路徑，所以由 RFC 指向它改到的東西：「動機」列出它要解決的 `docs/limitations.md` 裡的限制，設計寫出它改到的檔案和模組；要找某個檔案的來歷，在 `rfcs/` 裡 grep 它的路徑。

## 什麼時候寫

- **新的功能**，例如 wasm 腳本（`rfcs/0001-wasm-scripts/`）、flex 和 grid（`rfcs/0003-flex-grid/`）。
- **現在的做法有風險、要先比較選項的題目**，即使改動不大，例如網頁在視窗裡的位置（`rfcs/0002-web-contents-layout/`）。
- **不用寫**：範圍在某份 RFC 之內的設計（直接寫進那份 RFC）、bug 修正、不牽動設計的小改動。

## 資料夾

```
rfcs/
  README.md                  這份：流程和索引
  0000-template/             範本，新的 RFC 從這裡複製
  0001-wasm-scripts/
    README.md                RFC 本身
    details.md               細節
    progress.md              開始實作之後才有：進度、驗收、做過的檢查（做完時併成一份）
    wasmtime-questions.md    實作前要用原型釐清的問題和結論（原型做完時刪掉，見它的開頭）
    wasmtime-yield-report.md 給 wasmtime 的 issue 草稿（還沒送出）
  0005-cppgc-wasm-gc/
    README.md                RFC 本身（草稿）
    details.md               細節
    q14-prototype/           cppgc 版的 wasm GC 的 lowering（反組譯 wasmtime 的程式碼）的原型（不合併）
    q15-prototype/           cppgc 版的 Store 執行中的 GC（弱參照表）的原型（不合併）
    q16-prototype/           cppgc 上的 wasm GC 物件的原型（不合併）
  pre-rfcs/                  有 RFC 之前的 MVP 文件（MVP.md、P1.md 到 P4.md、PROGRESS.md）
```

- **編號**：四位數，依建立的順序，不重用（延後或否決的也留著）。
- **名稱**：英文 kebab-case，建立後不改，因為其他 RFC 用路徑引用它。
- **`README.md`**：RFC 本身，照範本的各節寫。只讀這份就要知道：要做什麼、為什麼、不做什麼、選了哪個做法、還有什麼沒決定。每一節可以只寫結論，指向 `details.md` 的某一節。
- **`details.md`**：支撐 `README.md` 的細節：實測紀錄、和其他實作（Chromium、V8、wasmtime…）的逐項比較、沒選的做法的完整分析、留給之後參考的研究、參考資料。
- **`progress.md`**：排程（開始實作）時從範本複製。每一步的狀態、驗收（測了什麼、怎麼驗證）、做過的檢查（mutation test、手動確認、找到的 bug）和測試數字；怎麼更新見 `docs/README.md` 的「完成一步時」。目前仍然成立的限制不寫在這裡，寫在 `docs/limitations.md`。
- **待釐清的問題**（需要時，例如 `0001-wasm-scripts/wasmtime-questions.md`）：實作前要用原型回答的問題，每題寫為什麼重要、目前知道什麼、怎麼釐清、狀態。一題有了結論就併進 `README.md` 或 `details.md`，這裡只留結論和指過去的位置。
- 圖或原型程式需要的話也放在同一個資料夾，原型不合併。RFC 做完時，結論都寫進文件之後，原型可以刪掉（寫明在哪個 commit 找得到），還有用的移到需要它的 RFC。
- **`pre-rfcs/`** 不是 RFC：MVP 時期的規劃、各階段的設計和進度，2026-10-04 起凍結（見它的 README）。

## 狀態

每份 RFC 的 `README.md` 開頭有一行「狀態」，前面加上下表的 emoji，讓人一眼看出狀態；下面的索引也一樣：

| 狀態 | 意思 |
| --- | --- |
| 📝 草稿 | 還在比較選項；可以寫「某天的看法」，但還沒確認 |
| 👍 已接受 | 設計確認了，「已決定的事項」寫上確認的日期；還沒開始做 |
| 🚧 已排程 | 開始實作，有 `progress.md` |
| ✅ 已完成 | 做完了，RFC 改寫成完成時的樣子；之後基本上不再更新（見「流程」第 6 步） |
| ⏸️ 延後 | 暫時不做，寫明理由、日期和什麼時候再考慮 |
| ❌ 否決 | 不做，寫明理由和日期 |

## 流程

1. **新增**：複製 `rfcs/0000-template/`，取下一個編號，狀態寫「草稿」，加進下面的索引。
2. **討論**：選項和比較寫進 RFC。傾向某個做法但還沒確認時，寫成「2026-10-03 的看法：A2」，不寫成決定。
3. **接受**：確認的事寫進「已決定的事項」，附上日期；狀態改成「已接受」。「待決定」裡還有東西也可以接受，只要它們不影響已決定的部分。
4. **排程**：決定開始做時，狀態改成「已排程：日期」，從範本複製 `progress.md`。「分階段」的每一步開始前，只決定那一步要決定的事，寫進「已決定的事項」。**開 branch 之前，RFC 的草稿（`README.md`，有的話連同 `details.md`）一定要已經 commit 在 `main` 上、並且 push 到 `origin/main`**：branch 從那個 commit 開出來，`main` 上一直看得到這份 RFC 打算怎麼做（其他人和其他機器也看得到），branch 上只放實作和隨著實作對 RFC 的修改。開 branch 前先確認本地的 `main` 和 `origin/main` 一致（見第 6 步）：草稿只在本地的 `main` 上時兩者不一致，先 push。**實作在從 `main` 開出來的 branch 上做，branch 直接用編號命名**（例如 `0013`，不加名稱或前綴）；`main` 上不放做到一半的實作：「分階段」的一個階段做完、經過審核，可以先 merge 回 `main`（第 5 步的「階段的 merge」），做到一半的階段不行。
5. **實作中**：設計改變時照 `docs/README.md` 的「做到一半、有設計改變時」，直接改 RFC 原本的段落，留下理由。
   **階段的 merge**（2026-10-07 起）：「分階段」的一個階段做完，可以不等整份 RFC，先 merge 回 `main`。條件：那個階段照 `docs/README.md` 的「完成一步時」更新過（`progress.md`、`docs/limitations.md`、情境），`CLAUDE.md` 列的檢查全部跑過，經過審核；`main` 上看得到的行為和文件要一致，不留只做了一半、會誤導人的 API。merge 的做法和第 6 步一樣（fetch、確認 `main` 和 `origin/main` 一致、rebase 到最新的 `main`、`git merge --ff-only`）；merge 之後 branch 留著，下一個階段接著在同一個 branch 上做。RFC 的狀態維持「已排程」，「一份 RFC 做完時」的整理在最後一個階段做。這樣幾條線同時做的時候，branch 不會活太久，其他線 rebase 時一次要解的衝突比較少（RFC 0012 的路線圖：三條線在三台裝置上並行）。
6. **完成**：照 `docs/README.md` 的「一份 RFC 做完時」，RFC 改寫成完成時的樣子：狀態改成「已完成：日期」；每一節直接描述最後的設計；「待決定」清空，還沒解決的移到新的 RFC 或 `docs/limitations.md`；驗收結果寫在 `progress.md`，限制寫在 `docs/limitations.md`。這些都做完、經過審核之後，那份 RFC 的 branch 最後一次 merge 回 `main`（之前的階段可能已經照第 5 步先 merge 過）。**merge 一律 fast-forward**，不產生 merge commit，`main` 的歷史保持一條直線：先 `git fetch origin`，確認本地的 `main` 和 `origin/main` 一致：只是落後，就在 `main` 上 `git merge --ff-only origin/main` 跟上；本地的 `main` 有 `origin/main` 沒有的 commit（包括兩邊分岔），就先停下來確認是誰的、要不要先 push，不要直接 rebase 或 merge。「最新的 `main`」指的是這樣跟上 `origin/main` 的 `main`。再把 branch rebase 到最新的 `main`（`main` 之後又往前走了，就再 rebase 一次），跑完檢查，再 `git merge --ff-only <編號>`；`--ff-only` 失敗就表示還沒 rebase 到最新的 `main`。
   **完成的 RFC 基本上不再更新，除非有特殊要求**：它記錄的是完成時的設計和驗收，之後的改動（改名、搬家、換指令、推翻某個決定）寫在新的 RFC、`docs/` 和 crate 的 README，不回頭改它。例外是 `python3 scripts/sanity.py docs` 抓到的壞掉的引用（章節），照 `pre-rfcs/` 的做法只修那一處；它記的路徑和測試指令是當時的樣子，`sanity.py docs` 不檢查它們還在不在，之後搬家、改名都不回頭改。
7. **延後或否決**：狀態寫上日期和理由；資料夾留著，以後有人想走同一條路時，才知道它試過、為什麼停下來。

## 和 Rust 的 RFC 不同的地方

- **沒有 PR 和 final comment period**：討論和確認直接記在 RFC 裡，「已決定的事項」的日期就是接受的時間。
- **RFC 會跟著實作改**：Rust 的 RFC 合併之後就不再改，之後的變更記在 tracking issue；machopo 的原則是每件事只寫在一個地方（`docs/README.md`），所以 RFC 一直是這個功能的設計文件，完成時改寫成最後的樣子。
- **多了「已決定的事項」**：編號、附日期，讓其他 RFC 可以引用某一條（`rfcs/` 以外的文件不引用 RFC）。
- **細節分到 `details.md`**：`README.md` 保持能一次讀完的長度。
