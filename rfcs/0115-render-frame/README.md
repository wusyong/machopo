# RFC 0115：每個 frame 的狀態照 content 和 Blink 的界線各有一個擁有者

- 開始日期：2026-11-25
- 狀態：✅ 已完成：2026-11-26（第 1 到 4 段，第 3 段做到 engine 的 frame 清單是唯一的一份；驗收在 `progress.md`）
- 細節：`details.md`

## 摘要

一次導覽原本橫跨三處：engine 擁有的 hook（`RendererFrameClient`）在 setter 裡送 `BeginNavigation`，renderer 的 `RenderThread` 在 engine 的呼叫回來之後照 engine 記下的 `FrameRequest` 記帳（`handle_frame_requests`，十八個呼叫的地方）、收到 Browser 的 commit 時建文件、餵 parser、捲到 fragment；照 frame 記的狀態在 `RenderThread` 散成八張表。根源是界線：`renderer` 同時做 Chromium 的 content 層和一部分 Blink（文件的載入、parser、script 的排程），engine 呼叫 hook 時碰不到 renderer，只好呼叫之後再補。

這份照 Chromium 的界線重新分，做完的樣子：

- **engine 那一側的每個 frame**（Blink 的 `LocalFrame` 加上 `DocumentLoader`）：文件和它的載入（`dom_api` 的 `DocumentLoader`：解碼、parser、parser 的 script、樣式表的請求和帳、HTML 的「the end」、「接著 parse」是 DOM 的 task），和這個 frame 在路上的導覽（送給 Browser 的，或 renderer 要 commit 的 `javascript:` 的空文件），在送出的那次呼叫裡就記好。iframe 不送給 Browser 的導覽（同一份文件的 fragment、`javascript:`）和 traversal 的捲動也在這一側。
- **renderer 那一側**（content 的 `RenderFrameImpl`）：hook（`FrameClient`、`LoadSink`）在 engine 的呼叫裡當場送 Browser 的訊息、告訴 DevTools；Browser 的 commit、drop 時 renderer 從 engine 的 frame 拿走那個導覽，commit 照舊由 renderer 做（畫面、body 的 pipe、DevTools、navigation timing 是它的）。renderer 照 frame 存的 `FrameDocument` 只放它自己的東西，是 engine 的 frame 的附屬資料：哪些 frame 存在只問 engine，沒有第二份清單。
- **沒有呼叫之後的對帳**：`FrameRequest` 只剩沒有 load sink 的 engine 的 blob URL；`handle_frame_requests` 只在 task 之後放掉不見的 frame 的資料，正確性不靠它的時機。

和原本的目標不同的地方：renderer 的 per-frame 物件沒有由 engine 的 frame 擁有、當場建（Chromium 的形狀），而是 renderer 擁有、照 engine 的清單在第一次用到時建（已決定的事項第 34 條）；`FrameView` 和畫面那一步留在 renderer。

## 動機

現況（`details.md` 的「現況」，2026-11-25 的 `main`）：

- **送和帳分在兩處**（RFC 0112 的第 10 條）：hook 送出導覽，什麼都不記；engine 推一筆 `FrameRequest`（帶著 `begin_id`）、自己告訴 DOM「frame 在載入中」；呼叫回來之後 `handle_frame_requests` 才照那筆記 renderer 的帳（子 frame 的導覽、`navigations_asked`、origin 的來源、session history 的計數），並做幾件當場要做的事（子 frame 的 fragment 捲動、排 `javascript:` 的 commit、告訴 DevTools、要一個 main frame、跟著 frame 的增減更新表）。改導覽時要一起改 hook、engine 的 `FrameRequest` 和 `handle_frame_requests`。
- **對帳要記得叫**：每個 task 結束時 `after_task` 一定叫一次，所以 Browser 之後的 commit 不會對不上；但同一個 task 裡呼叫 engine 之後馬上讀帳或 frame 清單的地方要先叫，現在有十八處。漏了不會當掉，是靜靜地做錯：資源的回應找不到新 frame 的文件被丟掉、session history 的位置算錯、輸入的 ack 比它觸發的捲動早。
- **照 frame 記的狀態散在八張表**（最上層的 `document`、`ChildFrames` 的 `documents`、`navigations`、`commits`、`owner_loads`、最上層才有的 `main_origin_source`、`devtools_main_frame_token`，整個 renderer 的 `navigations_asked`），最上層和子 frame 分開；frame 不見時要每張各清一次（`ChildFrames::remove` 漏了 `owner_loads`）。
- **只在 renderer 這一側補做不乾淨**（`details.md` 的「做法的比較」）：把帳搬進 hook、拆成共用的 `Rc<RefCell>`，都拿不掉要用 engine 的那幾件（fragment 的捲動要 layout，`FrameDocument` 的 parser 和 engine 同時借），一個 frame 的狀態照樣分兩半；只把八張表收成一個物件，對帳的十八處照舊。
- RFC 0112 的「之後的可能」記過這件事，建議在 site isolation 之前做；renderer 已經是自己的 process（RFC 0108），site isolation 會讓一個 renderer 只有一部分 frame 是 local 的，到時候本來就要 per-frame 的物件。

**目標**：

1. 每一份 per-frame 的狀態只有一個擁有者：文件和它的載入（parser、script 的排程、`load`、readiness、「在載入中」）在 engine 那一側的 `LocalFrame`；對 Browser 的那一面（進行中的導覽、`begin_id`、`navigation_id`、commit 的參數、navigation timing、cancellation window、這個 frame 的 fetch）在 renderer 那一側的 `RenderFrame`。
2. 沒有呼叫之後的對帳：送出導覽的那串呼叫裡兩邊各記自己的帳（engine 那一側記 frame 在導覽，`RenderFrame` 記對 Browser 的請求，照 Chromium），Browser 的訊息經過 engine 交給那個 frame、當場建文件和更新帳；`handle_frame_requests` 和它的十八個呼叫拿掉。
3. frame 的生命週期一處管：engine 建 frame 時建它的 `RenderFrame`，frame 不見時一起走，沒有要各清一次的表。
4. `RenderThread` 只剩整個 renderer 的事：scheduler、IPC 的分派、compositor 和 widget、DevTools 的分派。
5. 看得到的行為不變（`shell` 的導覽、iframe、session history、DevTools 的測試，WPT 的 `html/browsers/`、`html/semantics/embedded-content/the-iframe-element/` 照舊通過），Speedometer 不變慢。

**不在範圍內**：

- site isolation、remote frame（`RenderFrameProxy`）。
- 導覽本身的行為（`javascript:` 網址在呼叫之後才算載入中、`BlobURLToken`，`docs/limitations.md` 的那幾條）：界線搬好之後各自比較好修，但不在這份。
- `FrameView` 和 layout、paint、compositor 怎麼接：`FrameView` 留在 renderer（畫面那一側），這份只讓它問文件「擋著沒」、在 main frame 時捲到 fragment（待決定的第 1 條）。

## 設計概要

給改 machopo 的人：

- 要知道一個文件的載入到哪（parser、script、樣式表、`load`），看 engine 那一側的 `DocumentLoader`（`ScriptEngine::document_loader`）和 DOM；要知道一個 frame 在路上的導覽，問 engine（`ScriptEngine::navigation`）；要知道 renderer 這一側的事（Browser 的 navigation id、body 的 pipe、畫到哪一版、DevTools 的資源），看它的 `FrameDocument`（`RenderThread::doc`，先問 engine 還有沒有那個 frame）。
- 加一種導覽：engine 在 setter 裡呼叫 frame client，client 當場送出，engine 當場記在 frame 上。Browser 回的訊息到 `RenderThread`，它從 engine 的 frame 拿走那個導覽、commit。不用在任何地方對帳。
- 加一個 engine 的入口、或在 task 中間讀 frame：不用記得任何事（frame 的清單只有 engine 那一份）。

給寫網頁的人：沒有看得到的改變（iframe 的 fragment 導覽和規範不同的那一點原本就是這樣，記在 `docs/limitations.md`）。

## 詳細設計

- **engine 那一側**：
  - 文件的載入是 `dom_api` 的 `DocumentLoader`，每個 frame 一個（`dom_js` 的 `Frame::loader`、`dom_wasm` 的最上層）：renderer 交 body 的 bytes（Blink 的 `BodyDataReceived`），`DocumentLoader` 解碼、parse，跑 parser 擋住的和 deferred 的 script（DOM 的 pending script），送 `<link>` 的樣式表的請求（`LoadSink::start_sheet_fetch`），script 和樣式表的回應交給它（`script_fetched`、`sheet_fetched`、`dom_api::subresource` 解碼），讓出時排 DOM 的 task（`Cx::queue_parse_on`），做 HTML 的「the end」（`finish_load`：`Interactive`、DOMContentLoaded、捲到 fragment、`load`）。擋不擋 render、失敗的子資源是 DOM 的（`Cx::render_blocked`、`Cx::note_load_failed`），要畫面是 widget 的（`FrameLayout::schedule_frame`）。標題和 DevTools 的 lifecycle 經過 hook 當場告訴（`FrameClient::title_changed`、`document_lifecycle`）。
  - 導覽的帳：client 送出導覽時回傳它的編號，engine 當場記在那個 frame 上（`dom_api::NavigationRequest`：編號、iframe 的 `no-referrer`、到 `about:blank` 時發起的文件；`dom_js` 的 `frames::Pending`，換文件時帶著）。iframe 的導覽不送給 Browser 的種類由 engine 判斷一次（`dom_api::child_navigation_here`，`ChildNavigationAsked::here` 告訴 client 不送）：同一份文件的 fragment 當場改網址、捲過去（`navigate_child_to_fragment`），別的 origin 的、載完的文件的 iframe 晚 100 ms 發 `load`（DOM 的 native timer `NativeAction::OwnerLoad`，一串只發最後一次）；`javascript:` 的記在同一格（一個 frame 一個，新的取代舊的），叫 `FrameClient::commit_here`。拿走帳時 engine 自己清掉「父 frame 的 `load` 要等它」。同文件的導覽和 traversal 在 engine 的呼叫裡要畫面，traversal 的捲動在 `traverse_within_document`（`popstate` 之後）。
- **renderer 那一側**：
  - hook 當場送 Browser 的訊息：`BeginNavigation`，並為它 post 一個 task 結束取消窗口（`InternalTask::NavigationCancellationWindowEnded`，Blink 的 `NotifyNavigationCancellationWindowEnded`）；同文件的導覽加一的歷史計數和 `RenderThread` 共用（`OwnHistoryEntries`，`Rc<Cell<u64>>`，換 engine 時留著）；`commit_here` post `InternalTask::ChildCommit`。
  - Browser 的訊息：`CommitNavigation`、`NavigationDropped` 從 engine 的 frame 拿走導覽（`ScriptEngine::take_navigation`），`ChildCommit` 的 task 拿走 `javascript:` 的（`take_commit_here`）；commit 由 renderer 做（`commit_document_navigation`、`commit_child`：建 window、`FrameView`、body 的 pipe、DevTools、navigation timing）。
  - `RenderFrames`：最上層的 token 和每個 frame 的 `FrameDocument`（Browser 的 navigation id、MIME、原文、body 的 pipe、time origin、編碼、畫到哪一版、網路是否安靜、DevTools 的資源）。哪些 frame 存在、它們的 parent、iframe、token、文件都是 engine 的：`doc`、`doc_mut` 先問 engine 還有沒有那個 frame（`has_frame_document`），子 frame 初始文件的那一份第一次用到時建；走 frame 的地方照 engine 的 `frames_in_tree_order()`，用文件找 frame 問 engine（`ScriptEngine::frame_of_document`）。`forget_gone_frames`（task 之後）放掉 engine 沒有的 frame 的資料、取消不見的文件的 fetch、讓 DevTools 重新比對 frame。
- **擁有權和呼叫的方向**：renderer 擁有 engine，engine 擁有 hook；往外（要送 Browser、告訴 DevTools）是 engine 的呼叫裡的 hook，往內（Browser 的訊息、body、回應）是 engine 的方法或 `dom_api` 的函式（`dom_api` 的函式拿 `Box<dyn ScriptEngine>`，因為 html5ever 的 parser 拿著它的 host）。共用的可變狀態只有歷史計數（`Rc<Cell<u64>>`）；沒有 `Rc<RefCell>`。
- **Process 的邊界**：往 Browser 的訊息都由 renderer 的 hook 和 `RenderThread` 送，照 `docs/architecture.md` 的「Process 的邊界」。

### 測試

每一段的測試、WPT 的目錄、mutation test 的結果在 `progress.md`。新的測試守的是：送出的導覽記在 frame 上、一個 frame 一個導覽、iframe 的 fragment 和 `javascript:`、同文件的導覽和 traversal 要畫面、parser 和樣式表的先後、被擋住渲染的子 frame、輸入結束之前的命令都有回答。

### 分階段

1. **renderer 那一側收成 `RenderFrames`**（已決定的事項第 2 到 10 條）：八張表收成一張、每種轉換一個方法、frame 不見時一起拿掉（修了漏清 owner `load` 的 bug）、debug build 檢查沒對帳就讀（第 3 段拿掉）。
2. **文件的載入搬到 engine 那一側**（第 11 到 28 條）：2a body 和 parser、parser 的 script、樣式表的請求、標題；2b 併進 2c；2c 要畫面、擋 render 和失敗的子資源、「the end」和 lifecycle、「接著 parse」、回應。`documents.rs` 從 5765 行到 4743 行（`dom_api` 的 `document_loader.rs` 1154 行）。
3. **導覽的帳在送出時記在 engine 的 frame 上**（第 29 到 34 條）：先做小步（3a 導覽的帳、3b iframe 不送的導覽和 traversal 的捲動、3c 拿掉 11 處 `handle_frame_requests`），做完評估之後做完整的那一半的 D（3d：engine 的 frame 清單是唯一的一份）。
4. **fragment 的捲動**：併進第 3 段（第 32 條：「記下、下一次 layout 時捲」本來就是 Chromium 的 `FragmentAnchor` 的形狀，觸發的地方搬進 engine）。

每一段都有停損點（新增的 hook 和問 engine 的方法、共用的可變狀態、新的「呼叫之後記得做」、DevTools 和 WPT 的退步、Speedometer），都沒碰到。

### 做完時的評估

| 目標 | 做完之後 |
| --- | --- |
| 1. 每份 per-frame 狀態一個擁有者 | 成立：文件和它的載入、導覽的帳在 engine 那一側；Browser 的 navigation id、body 的 pipe、畫面、DevTools 的那一份在 renderer 的 `FrameDocument`；兩邊沒有交集（engine 從不讀 `FrameDocument`） |
| 2. 沒有呼叫之後的對帳 | 成立：導覽在送出時記好，十八處和八處過期的讀法都不在了；task 之後只剩放掉不見的 frame 的資料 |

| 4. `RenderThread` 只剩整個 renderer 的事 | 部分：文件的載入搬走了，commit、body 的 pipe、畫面那一步、DevTools、回應的路由還在 `RenderThread` 照 frame 走 |
| 5. 行為不變、Speedometer 不變慢 | 成立（`progress.md`）：WPT 和 `shell` 沒有退步；Speedometer 整份 +0.3%，都在區間裡（第一次量到 +6.6%：2c 和第 3 段在每個 task 之後走 frame tree 找 frame，改成 engine 自己的清單 `ScriptEngine::frames`） |

跨界線的新方法比原本多（2a 7 個、2c 的決定裡的和多出的 2 個、第 3 段的 `commit_here`、`navigation`、`take_navigation`、`take_commit_here`、`frame_of_document`、`frames`），每個都在決定的事項裡；沒有為了對帳加的。

## 缺點

- 規模：`render_thread/documents.rs` 的大半、`render_thread.rs`、`dom_js` 和 `dom_wasm` 的 frame、`dom_api` 的新模組（`document_loader`、`link_style`、`subresource`）和 `FrameClient`、`ScriptEngine` 的方法。
- renderer 讀一個 frame 的 `FrameDocument` 多問 engine 一次（`child_parent`）；子 frame 初始文件的資料第一次用到才建，不見的 frame 的資料到 task 之後才放掉。
- `RenderThread` 照舊照 frame 走畫面那一步和 commit，這一半的整理不在這份。

## 理由和其他做法

完整的比較在 `details.md` 的「做法的比較」和第 3 段的兩份盤點。

- **不選只在 renderer 這一側補**（2026-11-25）：只收成 `RenderFrames`（第 1 段本身）十八處照舊；導覽的帳搬進 hook，文件和 parser 留在 `RenderThread`，一個 frame 照樣兩半；共用的 `Rc<RefCell>`，要 engine 的那幾件搬不進去，借著格子呼叫 engine 就在執行時 panic。
- **不考慮 engine 的入口多收一個 `&mut` 的 host**：hook 在 V8 的 callback 裡被呼叫，從 isolate 的 slot 拿狀態，借用存不進去。
- **第 3 段完整的那一半**（第 34 條）：不選停在小步（task 中間讀 frame 要讀 engine 的只靠約定）或加 debug 檢查（承認兩份清單）；不選 `FrameDocument` 放進 engine 的 frame（trait 加 downcast、經過 engine 借、分開借的方法）；不選把表交給 engine 擁有的 client、hook 當場建（renderer 跟 engine 借自己的資料、分開借、換 engine 時表要搬）。

## 先例

- **Chromium**（2026-11-25 對過原始碼，`details.md` 的「對照 Chromium（原始碼）」）：每個 local frame 兩個物件：Blink 的 `LocalFrame`（`DocumentLoader` 擁有 body 的 loader、parser 和解碼器；`HTMLParserScriptRunner`、`ScriptRunner`、`RenderBlockingResourceManager`、`Document::CheckCompleted`、`LocalFrameView`）和 content 的 `RenderFrameImpl`（`blink::WebLocalFrameClient`，對 Browser 的 `FrameHost`、`NavigationClient`）。送出導覽時兩邊各記一份：Blink 記這個 frame 在導覽（`FrameLoader::client_navigation_`），content 記對 Browser 的這次請求（`navigation_client_impl_`、`is_requesting_navigation_`），都在送出的那串呼叫裡；commit 時 content 把 Browser 的 data pipe 交給 Blink，Blink 建 `DocumentLoader`、自己收 body。parser 自己 post 到文件的 task runner；fragment 的導覽同步 commit，捲動排到下一次 lifecycle。兩個物件一起建、一起走，但靠 raw 指標和約定（content 先建、交給 Blink 的工廠，Blink 拆 frame 時告訴它）。照做：兩邊各自的狀態、在送出的那串呼叫裡各記一份、同步的呼叫互通、body 交給文件那一側、fragment 的捲動「記下、下一次 layout 時捲」。不照做：renderer 的 per-frame 物件不是 Blink 建 frame 時當場建（Rust 裡不互相拿著指標：renderer 擁有它，照 engine 的 frame 清單在第一次用到時建，第 34 條）；fragment 在下一次 layout 捲（script 讀 `scrollY` 讀得到），不是下一次 main frame。

## 已決定的事項

1. **接受的範圍：第 1 段，第 2 到 4 段是方向**（2026-11-25，使用者決定）：第 1 段把 renderer 那一側收成 `RenderFrame`（八張表、每種轉換一個方法、最上層和子 frame 同一種、十八處變成一行分派、debug build 在讀帳的地方檢查 engine 裡沒有沒分派的 `FrameRequest`），擁有者照舊是 `RenderThread`，行為和時機不變；它不管之後選哪個方向都要做。第 2 到 4 段照「分階段」和「信心和未知數」是方向，第 1 段做完之後重新評估，再決定接不接受。理由：依賴的盤點之後，第 1 段的信心高、自己看得出對不對；之後的幾段規模大、信心中等，第 1 段做完依賴會清楚得多。不選一次接受整個方向：第 2 段要拆的函式（兩個 commit、parse 的迴圈）還沒拆過，現在定細節會猜。不選只做第 1 段、不寫方向：第 1 段的形狀（`RenderFrame` 只放對 Browser 的那一面，還是連文件一起）要照之後的方向定。
2. **第 1 段：`RenderThread` 照 frame 的狀態是一張 `BTreeMap<FrameId, RenderFrame>`**（2026-11-25，使用者決定；A）：`RenderFrames` 取代 `document`、`ChildFrames`（`documents`、`navigations`、`owner_loads`；`commits` 的佇列也在 `RenderFrames` 上，第 4 條）、`main_origin_source`、`devtools_main_frame_token`；最上層和子 frame 同一種，最上層是 `frames[&TOP]`。`FrameId` 是 engine 照建立的順序給的（最上層是 0），走訪的順序和原本的 `Vec` 一樣。對照 Chromium：content 的 `g_frame_map`，每個 frame 一個 `RenderFrameImpl`。不選最上層一個欄位、子 frame 一張表：「照 frame 找」要分兩種情況，`doc`、`is_top` 的特例留著。不選 `Vec` 照 id 找：每次查表掃一遍。
3. **第 1 段：`RenderFrame` 的欄位，最上層和子 frame 的導覽同一種**（2026-11-25，使用者決定；A）：`document: Option<FrameDocument>`（子 frame 一建立就有 initial 的，最上層第一次 commit 之前沒有）、`navigation: Option<NavigationRequest { begin_id, no_referrer, origin_source }>`（最上層的 `main_origin_source` 併進來，`no_referrer` 是 false；commit 時照舊：子 frame 比 `begin_id`，最上層只拿 `begin_id` 對得上的 `origin_source`）、`owner_load_at: Option<f64>`。最上層的 DevTools token（Browser 給的）實作時改放在表上（`RenderFrames::top_token`），不放進最上層的 `RenderFrame`：Browser 可能在第一份文件 commit 之前就給，那時還沒有最上層的 `RenderFrame`，而換 engine 時表清空、token 要留著。最上層 commit 了別的文件（不是它在等的那個導覽）時，那個導覽留著，照原本的 `main_origin_source`。對照 Chromium：`RenderFrameImpl` 的 `navigation_client_impl_` 不分最上層和子 frame。不選兩種各記各的：特例還在，第 3 段搬到 client 時要搬兩種。不選只搬文件：frame 不見要清每張表的問題還在。
4. **第 1 段：整個 renderer 的帳和 `javascript:` 的佇列留在外面**（2026-11-25，照建議，使用者同意）：`own_history_entries`（整個分頁的 session history 的計數）和 `navigations_asked`（照送出的順序在 task 結束時一次送 `NavigationCancellationWindowEnded`）留在 `RenderThread`；`javascript:` 的 commit 佇列跨 frame、照排進來的順序，在 `RenderFrames` 上，`RenderFrame` 的方法排和清。不選把 `navigations_asked` 放進每個 frame（Chromium 是每個 `NavigationClient` 一個 window）：送出的順序變成照 frame 的順序，換不到第 1 段要的東西。新的檔案 `render_thread/render_frame.rs` 放 `RenderFrames`、`RenderFrame`、`NavigationRequest`；`FrameDocument` 的定義實作時留在 `documents.rs`（它的三十個欄位是那裡私有的，搬過去要全部改成 `pub(super)`）；`documents.rs` 裡用它們的程式先不搬。
5. **第 1 段：`RenderFrame` 的方法只改自己的資料**（2026-11-25，使用者決定；A，**第 3 段要再看一次**）：方法回傳接下來要做什麼（例如沒送出的導覽是 fragment 還是 `javascript:` 的 commit），要用 renderer 狀態的步驟（子 frame 捲到 fragment、告訴 DevTools、要一個 main frame、排 `javascript:` commit 的 task）由 `RenderThread` 照回傳做。資料和動作分開、`RenderFrame` 可以單獨測。第 3 段 engine 擁有 `RenderFrame` 時它要自己做這些，那時再決定服務怎麼給（對照 Chromium：`RenderFrameImpl` 的欄位拿著 `FrameHost` 的 remote、task runner）。不選服務是 `RenderFrame` 的欄位：捲動和要 main frame 照樣要 `RenderThread`，第 3 段的形狀還沒定就先定了服務。不選服務當參數傳：每個呼叫要先組參數，第 3 段又改一次。
6. **第 1 段：debug build 在每次讀表時檢查 engine 沒有沒分派的 `FrameRequest`**（2026-11-25，使用者決定；A；做法改成第 9 條、範圍縮成第 10 條）：`ScriptEngine` 多一個 `has_frame_requests()`；`RenderFrames` 的讀取（`frame`、`frame_mut`、走訪）在 debug build 斷言它是 false，`handle_frame_requests` 分派的期間例外。忘了在呼叫 engine 之後分派的地方，第一次讀表就 panic。實作時逐一確認有沒有「先讀表、再分派」本來就對的地方。對照 RFC 0114 的 `assert_no_dom_task_lost`。不選只在處理 Browser 的訊息前和 task 結束時檢查：task 結束時本來就分派，抓不到十八處要防的「同一個 task 裡呼叫完馬上讀」。不選不加：十八處照舊只靠審查。
7. **第 1 段：子 frame 的 `RenderFrame` 照舊在呼叫之後建和拿掉**（2026-11-25，使用者決定；A）：`follow_child_frames` 照 engine 的 frame 清單建和拿掉 `RenderFrame`，時機不變；當場建（Chromium 的 `CreateChildFrame`）是第 3 段 engine 擁有 `RenderFrame` 時的事。不選在 hook 的 `child_frame_created` 當場建：hook 碰不到 `RenderThread` 的表，等於把第 3 段提前做一部分。
8. **第 1 段：frame 不見時它排著的 owner `load` 一起拿掉，照修**（2026-11-25，使用者決定；A）：現在 `ChildFrames::remove` 沒清 `owner_loads`，`known()` 把不見的 frame 當成還在；收成 `RenderFrame` 之後拿掉 frame 就清掉。加一個測試，記進 `progress.md` 的找到的 bug。這是第 1 段唯一的行為改變。不選第 1 段保留舊行為、之後另外修：要在新的結構裡刻意重現漏清。
9. **1c：debug build 的檢查由 hook 設旗標**（2026-11-25，使用者決定；A）：renderer 的 hook 每個 `FrameClient` 方法先設一個 `Rc<Cell<bool>>`（只在 debug build），`RenderFrames` 拿著同一個，它的讀法斷言沒設，`handle_frame_requests` 對帳的期間例外、拿走 `FrameRequest` 之前清掉。取代第 6 條的 `ScriptEngine::has_frame_requests()`：`dom_js` 的佇列在 isolate 的狀態裡要 `&mut self`，讀表的地方多半只有 `&self`。`Rc<Cell>` 的理由：hook 是 engine 擁有的、表是 render thread 的，engine 在它的呼叫裡叫 hook，共用一個旗標只有這樣；只在這條 thread、只在 debug build。不選只在有 `&mut` 的讀法檢查：直接讀 `render_frames` 的幾十處守不到。不選所有讀法經過 `RenderThread` 的一個入口：子模組看得到欄位，繞過入口只靠約定。
10. **1c：檢查只守導覽的帳**（2026-11-25，使用者決定；B）：檢查的是 `navigation`、`take_navigation`、`take_any_navigation`、`is_navigating`，不守子 frame 的清單和文件。第一版也守清單，找到八處 renderer 在 engine 的呼叫之後、對帳之前就讀了清單（`docs/test-gaps.md`）；逐一先對帳修得掉，但對帳的動作跟著提早、和第 1 段「時機不變」不合，照這樣是每個會跑 script 的 engine 呼叫之後都要對帳。這八處在第 2、3 段搬到 engine 那一側（讀 engine 自己的 frame，不會過期）時處理，剩下的是「跑完 script 之後這個 frame 還在不在」（Blink 的 `IsDetached`）。不選逐一修：十八處對帳長成三十處上下，第 2、3 段又要拿掉。不選只在讀「表上沒有的 frame」時檢查：不見了還留著的 frame 抓不到，規則難說清楚。
11. **第 2 段先只排 2a，有停損點**（2026-11-25，使用者決定；A）：2a（body 和 parser 搬到 engine 那一側的 `LocalFrame`）做完時照「信心和未知數」的三個停損點看，都順才做 2b。使用者在意的是「送和帳分開」和「很多地方要做檢查」（目標 2）；「一個 frame 的狀態全在一處」不必完全成立，界線乾淨就好（目標 1 照這個讀：每份狀態一個擁有者、擁有者之間的界線清楚，一個 frame 可以有幾個物件）。不選一次接受第 2、3 段：最難的函式還沒碰，2a 會讓真實的難度清楚。不選停在第 1 段：十八處和八處過期的讀法照舊。
12. **2a：`LocalFrame` 在 `dom_api`，engine 擁有**（2026-11-25，使用者決定；A）：和 engine 無關的 Rust 型別，兩個 engine 的每個 frame 各拿一個（`dom_js` 的 frame、`dom_wasm` 的最上層），要跑 script 時經過 `ScriptHost`、`ParserHost` 這類既有的介面；每個 engine 只做「找到 frame 的 realm、進 scope」的薄包裝。對照 Chromium：`DocumentLoader` 在 Blink 的 core，和 V8 無關。不選各 engine 一份：同一套規則寫兩次。不選型別在 `dom_api`、實例在 renderer：engine 的呼叫裡碰不到，過期的讀法照舊。
13. **2a：renderer 讀 data pipe，`LocalFrame` 解碼和 parse**（2026-11-25，使用者決定；A）：renderer 只管傳輸（從 pipe 讀 bytes、排下一次讀），bytes 交給 engine；判斷編碼（`encoding.rs` 的 `DocumentDecoder` 搬到 engine 那一側）、文件的編碼、parse 是 `LocalFrame` 的。DevTools 要的原始碼改成問 engine。界線是「傳輸」對「文件」，`dom_api` 不依賴 `ipc`。對照 Chromium：Blink 的 `NavigationBodyLoader` 自己讀 mojo 的 pipe、解碼器是 parser 的；machopo 的 pipe 是 `ipc` 的、process 之間的東西，留在 renderer。不選 `LocalFrame` 自己讀 pipe：`dom_api` 要依賴 `ipc`，讀的訊號要經過 hook 叫醒 thread。（2026-11-26 更正：`dom_api` 經過 `protocol` 本來就依賴 `ipc`，不是限制；理由是後半，讀的訊號要經過 hook 叫醒 thread，pipe 是 renderer 的傳輸。）不選 renderer 也解碼：文件的編碼是文件的事（它的 script 和樣式表用它解碼），留在 renderer 要再給 engine 一份。
14. **2a：「接著 parse」是 DOM 的一種 task**（2026-11-25，使用者決定；A）：parser 讓出時 `dom` 編號、經過 `TaskWaker` 送記號，和 timer、element task 一樣（Chromium 的文件的 `kNetworking` task runner）；讓出照時間的預算和「有輸入在等」（原本寫的是既有的 `InputMonitor`；查過不是同一個訊號，第 28 條改成照舊由 renderer 經過 `ParseRun` 給）。從 renderer 的 `InternalTask::ParseOn` 移到 DOM 的 queue，和別的 task 的先後可能變（兩個 queue 都照 post 的順序，差在 DevTools 暫停時取哪些 queue）：WPT 和 `shell` 的測試守著。不選經過 hook 排 renderer 的 task：多一個 hook，文件的事繞回 renderer。
15. **2a：parser 擋住的和 deferred 的 script 跟著 parser 一起搬**（2026-11-25，使用者決定；A）：第 14 條讓 parse 在 engine 的呼叫裡跑，script 留在 renderer 的話，parser 碰到 script 只能記一筆、呼叫之後處理，又是一種對帳。所以 2a 是 body 的解碼加上 parser 加上 parser 的 script：請求走 DOM 自己排的 script 那條路（`LoadSink::start_script_fetch`、回應交給 engine），`advance_document` 整個搬到 `LocalFrame`（對照 Chromium 的 `HTMLParserScriptRunner`，parser 的）。原本的 2b 併進來，2a 變大，但中間沒有對帳的過渡形狀。不選 script 留到 2b、2a 的 parse 經過 renderer 的 task：過渡形狀，2b 又要改一次 parse 怎麼排。不選碰到 script 時記一筆對帳：和這份的目標相反。
16. **2a：renderer 和 engine 之間的方法**（2026-11-25，照建議，使用者同意）：renderer 往下：commit 時建 `LocalFrame`（`create_window` 多帶 MIME type、transport 的 charset、要不要 parse）、`body_data(frame, bytes)`、`body_ended(frame, status)`、script 的回應（DOM 自己排的 script 那條路）（原本還有 `set_scripts_blocked(frame, bool)`：樣式表擋不擋 script 由 renderer 推下去；來不及，第 18 條拿掉）。engine 往上：script 的請求（`LoadSink::start_script_fetch`）、有沒有輸入在等（`InputMonitor`）。renderer 在呼叫之外問 engine：DevTools 要的原始碼、編碼、body 做出來了沒（render-blocking）。名稱和參數實作時可能調整，改了寫回這一條。對照 Chromium：往下的是 `WebNavigationBodyLoader::Client` 和 `WebLocalFrame` 的那幾個方法，往上的是既有的 hook。
17. **2a：會 parse 的 engine 方法照值收 engine**（2026-11-25，使用者決定；A）：`html` 的 parser 照值借它的 host（`Parser::resume(Box<H>) -> (ParserState, Box<H>)`：html5ever 的 sink 是 `&self`，host 放在 sink 的 `RefCell` 裡，跨好幾次 `resume` 的 tokenizer 存不了一次的借用），所以 engine 那一側要 parse，就要能把自己照值借給 parser：parse 的迴圈在 `dom_api`，收 `Box<dyn ScriptEngine>`、回傳它；renderer 呼叫時 `take()` engine、再放回去（`advance_document`）。不是新的 hook。（原本寫的是 `ScriptEngine` 的 `parse` 和 `run_dom_task` 收 `self: Box<Self>`；2a 實際做成 `dom_api` 的函式 `document_loader::parse`，trait 不動；2026-11-26 照第 24 條改成這樣寫。）對照 Chromium：Blink 的 parser 拿著 `Document` 的指標、script 在 Blink 裡跑，沒有這個擁有權的問題。不選 `run_dom_task` 回傳「parse frame X」、renderer 再叫 `parse`：parse 怎麼排要經過 renderer 轉一手。不選讓 parser 用 `unsafe` 的「在這段呼叫裡借給 callback」拿 host（`bindings` 才能有 `unsafe`，`html` 又不能依賴 `bindings`）：多一個要論證的機制。
18. **2a：`<link>` 的樣式表的請求和「擋 script、擋 render」的帳併進 2a**（2026-11-25，使用者決定；A）：實作 2a-2 時發現，第 16 條的 `set_scripts_blocked`（樣式表的帳變了時由 renderer 推下去）來不及：parser 在同一次 engine 的呼叫裡 parse 出 `<link rel=stylesheet>` 和後面的 `<script>`，renderer 在呼叫之外，沒機會先掃出 `<link>`、照 media 判斷、送出請求，script 就會在樣式表到之前跑。呼叫裡回頭叫 renderer 的 `start_loads` 也不行：engine 借給了 parser，renderer 碰不到 DOM，要共用 `pending_sheets` 就得 `Rc<RefCell>`。所以 `<link>` 的掃描、media 的判斷（經過 `FrameLayout`）、請求（新的 `LoadSink` 的 hook，和圖片、script 的一樣）和「擋 script、擋 render、`load` 等著」的帳搬到 engine 那一側，帳記在 DOM（和 script 的請求一樣，照請求的編號）；回應照舊由 renderer 收、解 CSS，交給 DOM；renderer 要知道 render-blocking、要不要等時問 engine。拿掉第 16 條的 `set_scripts_blocked`。對照 Chromium：`HTMLLinkElement` 插進樹時 `LinkStyle` 當場在 Blink 裡送出請求，`StyleEngine` 記著擋 script 的樣式表，`HTMLParserScriptRunner` 問 `Document::IsScriptExecutionReady`，全在 parser 的那串呼叫裡。不選 parser 碰到每個 script 都回 renderer（renderer 跑 `start_loads` 再叫 engine 跑 script）：迴圈照舊跨著界線，「接著 parse」改成 DOM 的 task（第 14 條）時，task 跑到 script 還是要回 renderer。不選停在 2a-1：parse 迴圈裡的過期讀法還在。新增的介面（hook 和問 engine 的方法）因此多三個左右，第 1 個停損點照算。
19. **2a：分頁的標題經過 `FrameClient` 的 hook，由 engine 那一側告訴**（2026-11-25，使用者決定；A）：實作 2a-3 時發現，parse 的迴圈搬進 engine 的呼叫之後，renderer 沒辦法在 parser 的 script 跑之前送出 parse 到那裡的標題（原本迴圈裡的 `update_title`）：script 馬上改掉的標題就不送了，`browser` 的 `navigation::the_tab_title_follows_document_title` 守著這件事（和 Blink 一樣，`</title>` 結束就告訴 Browser）。所以 `FrameClient` 多 `title_changed`（renderer 的實作送 `UpdateTitle`），「上次告訴的標題、在樹的哪個版本讀的」從 `FrameDocument` 搬到 `DocumentLoader`（每份文件一份），`ScriptEngine::tell_title` 由 parser 在每個 script 之前、renderer 在 task 和 animation frame 之後叫。對照 Chromium：`LocalFrameClient::DispatchDidReceiveTitle`，content 的 `RenderFrameImpl` 當場送給 Browser。不選把 renderer 上次送的標題放進 `ParseRun`、標題變了就回傳新的停下原因再接著 parse：標題留在 renderer，但多一種往返。不選只在呼叫結束時送：script 改掉的標題不送，和 Chrome 不同。這把標題的時機從「畫面那一半」移到 engine 那一側；新增的介面多兩個（`title_changed`、`tell_title`）。
20. **「接著 parse」是 DOM 的 task（第 14 條）從 2a 移到 2c**（2026-11-25，使用者決定；B）：2a-3 做完時發現，parse 完之後的事（`Interactive`、deferred script 之後的 DOMContentLoaded、DevTools、`finish_load`；讓出、等 body 時的 `parser_stopped`）還在 renderer，要到 2c 才搬；在那之前讓 DOM 的 task 去 parse，`run_dom_task` 得收 `Box<Self>`、把停下的原因交回 renderer（第 17 條），預算、讓出的次數、`parse_due` 搬到 engine 那一側，換來的只是拿掉 `InternalTask::ParseOn`，回傳值到 2c 又要再改。所以 2a 做到 2a-3，「接著 parse」和「the end」一起在 2c 做，`run_dom_task` 只改一次。對照 Chromium：`HTMLDocumentParser::SchedulePumpTokenizer` 排在文件的 `kNetworking` task runner 上，parse 完的「the end」也在 Blink 裡（`Document::FinishedParsing`），不用交回 content。不選照第 14 條現在做：過渡的回傳值。不選一直留在 renderer 的 scheduler：2c 之後 renderer 為了排它還要知道 parse 停在哪裡。
21. **2b 併進 2c**（2026-11-25，使用者決定；A）：第 18 條之後 2b 剩下樣式表的回應：解碼和 parse、DevTools 的原文、`set_link_sheet`、`load` 和 `error`、失敗的網址；renderer 接著還要叫 parser 繼續（擋著的 script）和 `finish_load`，這兩件是 2c 的。單獨先做，就是「renderer 解碼、engine 設定、renderer 再叫 parser」或「engine 做完、把原文和能不能接著 parse 交回 renderer」的過渡形狀（和第 20 條同一種問題）。所以樣式表的回應和「the end」、parse 的排程一起在 2c 搬：renderer 只交 bytes。對照 Chromium：`CSSStyleSheetResource` 解碼、`LinkStyle::NotifyFinished` 設 sheet、排 `load` 的 task，`StyleEngine` 在擋著的樣式表不擋時叫 parser 接著跑，都在 Blink 裡。不選現在做 2b：過渡的回傳值。不選最小的 2b（DOM 合併「拿帳、設 sheet」）：幾乎沒減少什麼。
22. **2c：DevTools 的 lifecycle 事件經過 `FrameClient` 的 hook 當場送**（2026-11-25，使用者決定；A）：「the end」搬進 engine 之後，DOMContentLoaded 和 `load` 發生在 engine 的呼叫裡，renderer 的 `tell_lifecycle` 拼不出 frame 的資訊（`render_frames` 加上 engine 的 frame，engine 借出去了）。盤點（`details.md` 的「2c 的依賴盤點」）顯示 lifecycle 只要 frame 的 token、文件、loader id，engine 都有；`PageAgent::update` 只在 frame 增減和換文件時送事件，frame 的增減現有的 hook 已經當場告訴 DevTools。所以 hook 帶這些，renderer 的實作當場叫 `PageAgent::lifecycle_event`，標題先由 engine 告訴（第 19 條）；最新的資源清單和原文留到 renderer 下次 `update`。對照 Chromium：`probe::LifecycleEvent` 在 Blink 裡當場叫 `InspectorPageAgent`。風險是同一次呼叫裡新的 frame 的 `frameNavigated` 和 lifecycle 的先後，`shell` 的 `devtools_lifecycle` 守著；不過就改成下面不選的那個。不選 hook 把事件排進佇列、renderer 在呼叫之後送：順序和現在一樣，但每個可能跑到「the end」的呼叫之後都要記得送。不選停在這裡：「the end」和三十處重讀都留著。
23. **2c：要一張新的畫面經過 `FrameLayout::schedule_frame`**（2026-11-25，使用者決定；A）：「the end」裡要 main frame 的地方（捲到 fragment 之後、`DidFinishLoad` 要跟著下一張畫面、中止的文件、wasm script 之後）在 engine 的呼叫裡，碰不到 `RenderThread::request_main_frame`。所以「要畫面」的旗標和計數（`needs_begin_main_frame`、`main_frame_requests`）從 `RenderThread` 搬到 `Frame` 的 widget（engine 拿著的 layout），`FrameLayout` 多 `schedule_frame()`；renderer 自己要畫面的地方改成設同一處，`update_begin_main_frame` 和輸入的 ack 的比對讀 `Frame` 的。不是共用的狀態：engine 不在呼叫裡時 renderer 經過 `engine_frame` 讀它。對照 Chromium：`LocalFrameView::ScheduleAnimation` 經過 `ChromeClient::ScheduleAnimation` 當場叫 widget 的 `LayerTreeHost::SetNeedsAnimate`。不選 engine 記旗標、renderer 每次呼叫之後問（要在輸入的 ack 比對之前問，每處都要記得）。不選 renderer 在呼叫之後自己推斷（呼叫之後的檢查變多）。
24. **2c：會接著 parse 的入口是 `dom_api` 的函式，照值收 engine**（2026-11-26，使用者決定；A′）：2c 之後 parse 完的事在 engine 那一側，body 的 bytes、parser 的 script 的回應、樣式表的回應、「接著 parse」的 DOM task 這四個入口都要在呼叫裡 parse，parser 要照值借 engine（第 17 條：html5ever 的 sink 是 `&self`、活過好幾次 `resume`，建構 custom element 要整個 engine，safe Rust 存不了只在這次呼叫有效的 `&mut`，`html` 不能有 `unsafe`）。所以四個都照 2a 的 `parse` 的形狀，做成 `dom_api` 的函式，收 `Box<dyn ScriptEngine>`、回傳它；DOM 的 task 由 `dom_api` 的函式先看是不是「接著 parse」的，不是就照舊叫 `engine.run_dom_task`（大多數 task 不用拿出 engine）。`ScriptEngine` 的 trait 不改，規則只在 `dom_api` 一份（第 12 條）。對照 Chromium：這幾處在 Blink 都是當場 parse（`HTMLDocumentParser::Append`、`PendingScriptFinished`）。不選四個 trait 方法收 `self: Box<Self>`：每個 engine 各寫一樣的轉手，沒有別的好處。不選每個 engine 拆出可以單獨借的內層：`dom_js` 要重排 isolate 的擁有權。不選 parse 之後才建構 custom element：html5ever 建元素時就要 handle，延後就成了 upgrade，和規範不同。
25. **2c：iframe 晚一點的 `load` 留到第 3 段**（2026-11-26，使用者決定；A）：它只在父 frame 把跨 origin 的子 frame 導覽到同一份文件的 fragment 時，100 ms 之後觸發（父 frame 分不出是不是同一份文件，Blink 的 `DocumentLoader::CommitSameDocumentNavigation`，crbug.com/1248444），觸發點在 renderer 的導覽的帳（`book_frame_requests` 底下的 `child_navigation_not_sent`、`navigate_to_fragment`），是導覽的一部分，不是「the end」。所以 2c 不動它，`RenderFrame::owner_load_at`、`fire_due_owner_loads` 和它裡面的「frame 還在不在」留到第 3 段，和子 frame 的 fragment 導覽一起搬。對照 Chromium：Blink commit 同文件的導覽時當場排它。不選 2c 先改成 DOM 的延後 element task、renderer 多叫一個過渡的往下方法（第 3 段又要拿掉）。不選 2c 連子 frame 的 fragment 導覽一起搬（提前做第 3 段的核心）。
26. **2c：擋不擋 render 要用的時候從 DOM 算**（2026-11-26，使用者決定；A）：一個 frame 的文件 render-blocked 是「parser 還在跑、還沒有 body，或有擋 render 的樣式表」；現在 renderer 記 `parsing`、`body_parsed`（2a 之後 `DocumentLoader` 也有一份），子 frame 的由 `update_child_blocking` 在好幾個時機推給 `FrameView`（`set_render_blocked`）。DOM 自己知道這三件事（`LoadProgress::Loading`、`cx.body`、樣式表的帳），`FrameView` 的 style 和 layout 拿著 `&Cx`。所以子 frame 在它的 lifecycle 裡從 DOM 算，最上層由 renderer 在要畫之前讀 DOM；`update_child_blocking`、`set_render_blocked`、`FrameDocument` 的 `parsing` 和 `body_parsed` 拿掉。body 剛做出來時要有一張畫面：樹變了本來就要畫面的話不用做什麼，不然照第 23 條要。對照 Chromium：`LocalFrameView` 的 lifecycle 問 `Document::ShouldScheduleLayout`、`RenderBlockingResourceManager`。不選 engine 在狀態變時經過 `FrameLayout::set_render_blocked` 推（每個改變它的地方都要記得推）。不選 renderer 每次畫之前問 engine 再推（呼叫之後記得做，狀態分在兩邊）。
27. **2c：失敗的子資源全部記在 DOM**（2026-11-26，使用者決定；A）：和 `DidFinishLoad` 一起送給 Browser 的失敗的網址（Browser 記 log，headless 和 WPT 的 runner 看子資源載入失敗）現在分在 renderer 的 `FrameDocument::failed`（回應失敗或內容不能用：圖片、script、module、樣式表）和 DOM 的 `failed_sheets`（`href` 解析不了的 `<link>`）；2c 之後樣式表和 script 的內容能不能用在 engine 那一側才知道。所以 DOM 的 `failed_sheets` 擴大成每份文件的「失敗的子資源」，記的是知道失敗的那一方（engine 那一側的解碼，renderer 的圖片那一條也記過去），送 `DidFinishLoad` 時 renderer 從 DOM 拿；`FrameDocument::failed` 拿掉。對照 Chromium：失敗由 Blink 的 `ResourceFetcher`、`ResourceLoadObserver` 記（log 是 `FrameConsole::DidFailLoading`），content 不另記。不選維持兩份、送的時候合併（分在兩邊）。不選 engine 經過 hook 告訴（hook 碰不到 `FrameDocument`，要共用清單或另記一份）。
28. **2c：parser 讓出的條件照舊由 renderer 經過 `ParseRun` 給**（2026-11-26，使用者決定；A）：第 14 條說讓出時問 `InputMonitor`，查了之後不是同一個訊號：`InputMonitor` 是 `isInputPending()` 的計數（Blink 的 `PendingUserInput::Monitor`，不算不知道給誰的事件，連續的可以不算），現在的 `scheduler.has_task(INPUT)` 是 input 的 queue 有沒有 task；Chromium 的 parser 看的是 scheduler 的 `ShouldYieldForHighPriorityWork`，和現在的一樣。照第 24 條，會接著 parse 的入口（連「接著 parse」的 DOM task）都是 renderer 叫 `dom_api` 的函式，所以預算、一段多大、「有沒有輸入在等」照舊每次經過 `ParseRun` 傳下去，engine 那一側不用知道 scheduler；`yields`、`parse_due` 搬到 `DocumentLoader`。不選照第 14 條問 `InputMonitor`（讓出的時機變，和 Chromium 不同）。
29. **第 3 段先做小步：只把導覽的帳搬到 engine 的 frame**（2026-11-26，使用者決定；A）：盤點（`details.md` 的「第 3 段的依賴盤點」）把第 3 段分成兩半。小步：導覽的帳（`NavigationRequest`、`javascript:` 的 commit 佇列、iframe 晚一點的 `load`）在送出的那次呼叫裡記在 engine 的 frame 上，commit 照舊由 renderer 做、`FrameDocument` 的表留著；拿掉 `FrameRequest` 的兩種導覽、`book_frame_requests` 的分派、第 1 段的檢查和 12 處額外呼叫裡的大約 11 處，「送和帳分開」在導覽上解決；成員的跟隨（`follow_child_frames`）照舊在呼叫之後。完整的：`RenderFrame` 連 `FrameDocument` 都由 engine 的 frame 擁有，成員的跟隨也拿掉，但要 `dom_api` 的 trait 拿著 `FrameDocument`（照 `Frame` 當 `FrameLayout` 的前例）、engine 給分開借的方法、約 60 處 `doc()` 改寫。先做小步，做完照停損點評估，再定完整的那一半。對照 Chromium：導覽的帳在 Blink 的 `FrameLoader` 和 content 的 `RenderFrameImpl` 各一份，都在送出的那次呼叫裡記好；frame 的增減是 Blink 建 `LocalFrame` 時經過 `LocalFrameClient` 當場建 `RenderFrameImpl`（完整的那一半）。不選直接做完整的（風險比 2c 高得多）。不選只做小步、明確不做完整的（先不排除）。
30. **第 3 段：導覽的取消窗口結束，送出時就為它 post 一個 task**（2026-11-26，使用者決定；A）：script 在一個 task 裡要求的導覽，現在在 task 結束時一次送 `NavigationCancellationWindowEnded { ids }`（renderer 的 `navigations_asked`），Browser 收到之前不 commit 它們（task 裡排在前面的請求、撤銷的 blob URL 先生效，同一個 task 裡後一個導覽能取代前一個）。帳改在 client 送出時記之後，client 送出時經過它拿著的 scheduler（跨 thread 的 `Arc`，load sink 也拿著）為這個導覽 post 一個 internal task，task 裡送；`navigations_asked` 拿掉。只差時機：每個導覽一則訊息，前面有排著的 task 時晚一點到。對照 Chromium：Blink 每個導覽 post 一個 task（`kInternalLoading`）叫 `NotifyNavigationCancellationWindowEnded`。不選清單搬到 engine、task 結束時拿（「task 結束時記得問」）。不選 client 和 `RenderThread` 共用 `Rc<RefCell<Vec<u64>>>`。
31. **第 3 段：同文件導覽的歷史計數由 `RenderThread` 和它的 client 共用**（2026-11-26，使用者決定；A）：`OwnHistoryEntries`（renderer 送出、Browser 還沒收到的同文件歷史項目數，commit 和 `SetHistoryOffsetAndLength` 時算 `history` 的長度和位置；換 engine 時不歸零，Browser 的接著算）在 client 送出同文件的導覽時加一，`RenderThread` 照舊讀：兩邊共用一個 `Rc<Cell<u64>>`。共用的理由（註解寫明）：兩邊都是 renderer 自己的物件，client 由 renderer 做給每個 engine，換 engine 時新的 client 拿同一份；`Cell`，沒有借用的檢查，不在每次呼叫的路上。對照 Chromium：計數在 content 那一層（`RenderViewImpl` 的 history list 的長度和位置），不在 Blink。不選放在 engine 那一側、換 engine 時帶過去（多兩個方法，要記得帶；計數是 content 層的）。不選 client 回報、renderer 在呼叫之後加一（呼叫之後的對帳）。
32. **第 3 段：fragment 的捲動照現在的行為搬進 engine，第 4 段併進來**（2026-11-26，使用者決定；A，B 記進「之後的可能」）：盤點發現捲動已經是 Chromium 的 `FragmentAnchor` 的形狀：導覽到 fragment 時只記下目標（`scroll_into_view_after_layout`），下一次 layout 捲，script 強制的也算，所以設完 `location.hash` 馬上讀 `scrollY` 是新的（和 Chrome 一樣）。所以「待決定」的第 1 條定成「下一次 layout」（不是下一次 main frame：那樣讀 `scrollY` 讀不到新的）；小步把觸發的地方搬進 engine：子 frame 的 fragment 的導覽、traversal 的捲動，經過 `FrameLayout::scroll_to_fragment`，同一次呼叫裡 `schedule_frame`，輸入的 ack 照舊等那張畫面。iframe 的 `src` 只換 fragment 時照現在的行為（只改網址、捲動），不走 `history::navigate`（規範的同文件導覽：`hashchange`、history 的項目、告訴 Browser）：這份是重構，行為不變；和規範的差別記進 `docs/limitations.md`。第 4 段因此併進第 3 段的小步。不選順便照規範走 `history::navigate`（功能的改變，要新的測試和 WPT 的預期，記進「之後的可能」）。不選下一次 main frame 才捲（和 Chrome 不同）。
33. **第 3 段：子 frame 的 `javascript:` 導覽由 engine 決定，經過新的 hook 交給 renderer commit**（2026-11-26，使用者決定；B）：iframe 的 `src` 或子 frame 的 `location` 是 `javascript:` 時不跑它，commit 一份空的文件（像 renderer 抓它失敗了一樣）；commit 用的是 renderer 的東西（`FrameDocument`、畫面、`DidCommitNavigation`），照第 29 條還是 renderer 做。engine 判斷一次這個導覽不送給 Browser 的種類（fragment 的自己做，第 32 條），`javascript:` 的記在 frame 上（和送出的導覽同一格：一個 frame 一個，新的取代舊的），再叫 `FrameClient::commit_here(frame)`，client 在裡面 post 這個 frame 的 commit task，task 跑時跟 engine 拿走那一格，拿不到（被之後的導覽取代）就不做。拿掉 `RenderFrames` 的跨 frame 佇列、`FrameRequest::ChildNavigationHere` 和 `Navigate` 的分派。跨 frame 的 commit 順序改成照 post 的順序。對照 Chromium：`javascript:` 的導覽整個在 Blink（`LocalDOMWindow` 排 task 跑它、commit 結果），content 只聽到 commit。不選把判斷放進給 hook 的 `NavigationAsked`、client 看欄位 post（交出的動作不是一個明確的方法）。不選佇列留在 renderer、engine 照舊留 `FrameRequest`（呼叫之後的分派留著）。
34. **第 3 段：做完整的那一半的 D，engine 的 frame 清單是唯一的一份**（2026-11-26，使用者決定；D）：小步之後，呼叫之後的對帳只剩 `follow_child_frames`（renderer 的 `FrameDocument` 表在 task 之後才跟上 engine 建了、丟了的 frame，task 中間讀表要記得讀 engine 的，只靠約定）。盤點（`details.md` 的「第 3 段完整的那一半的盤點」）：engine 那一側從沒讀過 `FrameDocument`，它只放 renderer 自己的東西。D：哪些 frame 存在只問 engine；renderer 的表是照 frame 存附屬資料的快取，`doc`、`doc_mut` 只回傳 engine 還有的 frame 的，初始文件的那一份第一次用到時建；走表的地方照 engine 的 `frames_in_tree_order()`，`frame_of_document` 問 engine（`ScriptEngine` 多一個方法）；`follow_child_frames` 只剩 task 之後的清理（放掉不見的 frame 的資料、取消它們的 fetch、DevTools 的「frame 變了」），正確性不靠它的時機。表照舊是 `RenderThread` 擁有的。對照 Chromium：content 的 `RenderFrameImpl` 在 Blink 建 `LocalFrame` 時當場建，D 的 renderer 資料晚建，但兩者都只有一份 frame 的清單。不選 A（到小步為止，task 中間讀 engine 的只靠約定）和 A 加 debug 檢查（承認兩份清單、守著不在不該的時候讀）。不選 B（`FrameDocument` 放進 engine 的 frame：trait 加 downcast、經過 engine 借、分開借的方法）。不選 C（表交給 engine 擁有的 `RendererFrameClient`、hook 當場建：renderer 跟 engine 借自己的資料、要分開借的方法、換 engine 時表要搬）。

## 之後的可能

- site isolation：不是 local 的 frame 是 `RenderFrameProxy`，engine 那一側是 remote frame。
- 導覽的限制（`BlobURLToken` 這些，`docs/limitations.md`）：界線搬好了，在 engine 的 frame 和 renderer 的 hook 裡各自修。
- DevTools 的 agent 照 engine 的 frame 清單。
- renderer 的 per-frame 資料當場建、當場放（第 34 條沒選的 C：表交給 engine 擁有的 client，hook 當場建；要分開借的方法）：要在 `FrameDetached` 的當下放掉資料，或拆成 process、site isolation 時再看。
- 畫面那一步（`update_document_rendering`）和 commit 的 per-frame 狀態的整理。
- iframe 的 `src` 只換 fragment 時照規範做同文件的導覽（`history::navigate`：子 frame 裡的 `hashchange`、history 的項目、`DidCommitSameDocumentNavigation`）：現在只改網址、捲動（第 32 條）；要新的測試，WPT 的預期要重看。
