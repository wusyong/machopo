# 測試

machopo 有哪些測試、怎麼跑、CI 的現況、mutation test 的做法。效能的量測（Speedometer、Blink 的 perf tests、tile 的 raster）在 `benchmarks.md`，目前測試守不住的地方（只靠審查的、只做過手動確認的、沒有計數守著的優化、等價的 mutation……）在 `test-gaps.md`。新的行為都要有測試，並且跑 mutation test（`CLAUDE.md`）。

## 測試的種類

| 種類 | 測什麼 | 在哪裡 | 怎麼跑 |
| --- | --- | --- | --- |
| 單元和整合測試 | 各 crate 的行為 | 單元測試在各 crate 的 `src/`；整合測試在各 crate 的 tests/it/，每個檔案是 `main.rs` 的一個模組，整個 crate 是一個 binary（cargo 把 `tests/` 直接底下的每個檔案編成一個 binary，改了底層的 crate 要每個都重新 link）。不能和其他測試共用 process 的才是 `tests/` 直接底下的獨立 binary：V8 的 flag 不同的 stress 測試（`dom_js` 的 `marking`、`bindings` 的 `cppgc_traced_marking`、`isolate_teardown`；V8 的 flag 整個 process 只設一次）、trybuild 的 `compile_fail`、自己有 `main` 的（`harness = false`：`shell` 的 `scenarios`）。`python3 scripts/sanity.py tests` 檢查 | `cargo test --workspace`，或用 `-p` 指定 crate；一組測試：`cargo test -p dom --test it tree::`（模組名稱加 `::`；幾個篩選放在 `--` 之後，`cargo test -p dom --test it -- tree:: events::`） |
| Reftest | 一個測試頁配一個預期結果頁，比對截圖；WPT 的格式（`<link rel=match>`），用測試字型（Ahem、Lato）。由上游的 wptrunner 經過 machopodriver 跑，在 WPT 旁邊的 `/_machopo/`；`hidpi/` 在 wptrunner 的 subsuite 裡用別的倍率跑，預期結果是 wptrunner 的 `.ini` | `tests/reftests/`（格式見它的 README） | `python3 scripts/test.py reftest` |
| WPT | `tests/wpt/include.txt` 列出的 testharness.js 測試、reftest 和 crashtest，由上游的 wptrunner 對 machopodriver 和 machopo 跑（product 和 wdspec 的同一個，machopo 帶 `--test-fonts`），上游的 wptserve 提供（網址是 `web-platform.test`；`.any.js` 照 manifest 包成 window、worker 等版本，`variant` 各自是一個測試）；預期結果是 wptrunner 的 `.ini`（`tests/wpt/metadata/`，全部通過的沒有；不跑的寫 `disabled` 和理由）。reftest 是 `css/CSS2` 的 block、inline、replaced element 和用 script 改樹的 normal flow、`css/css-text/white-space`、`css/css-overflow`，以及 `css/css-flexbox`、`css/css-grid`、`css/css-sizing` 全部的候選；失敗的 reftest 的截圖寫在 `target/wpt-results/screenshots/`。一個測試一組、從同一個佇列拿著平行跑，process 數預設每個 CPU 四個、最多 32 個（`--processes` 可以改） | 上游 WPT 的 checkout `../third_party/wpt`（`third_party.toml` 固定 commit）；清單和預期結果在 `tests/wpt/`（挑選的方式和怎麼更新見它的 README） | `python3 scripts/test.py wpt`；`MACHOPO_UPDATE_EXPECTATIONS=1` 重新寫預期結果 |
| WPT 的 WebDriver 測試（wdspec） | WPT 的 `webdriver/tests/classic/`（pytest 寫的）裡 `tests/wpt/wdspec-include.txt` 列出的，由上游的 wptrunner 對 machopodriver 和 machopo 跑：machopo 的 product 在 `tests/wpt/wptrunner_machopo/`，不經過 `wpt run`、直接呼叫 wptrunner（它對內建以外的 product 要系統的 hosts 檔有 WPT 的網域）；預期結果是 wptrunner 的 `.ini`（`tests/wpt/metadata/`，全部通過的沒有）。第一次在 `target/wptrunner/` 建 venv（要網路）、產生 WPT 的 manifest（和 `wpt` 共用，WPT 的 commit 變了才重新產生，約一分鐘），之後一次約一分鐘（32 個 process 平行；一次一個時約十分鐘，多半是 user prompt 的測試等到逾時）；和 `wpt`、`reftest` 不能同時跑（wptserve 的 port 固定） | `../third_party/wpt`；清單、預期結果和 product 在 `tests/wpt/`（見它的 README） | `python3 scripts/test.py wdspec`；`MACHOPO_UPDATE_EXPECTATIONS=1` 重新寫預期結果 |

| fork 的 patch | `ci.py patches` 匯出 fork 在 `upstream_rev` 之後的 commit：一個 commit 一個 patch、檔名和 subject 不編號、沒有簽名、內容每次一樣、換掉舊的、CRLF 的檔案和二進位檔照原樣；shallow 的 checkout 先加深；不是從 `upstream_rev` 長出來的不匯出。`ci.py third-party` 的檢查：patch 套在 `upstream_rev` 上和 `rev` 的檔案一樣，沒匯出的 commit、被改過的 patch 和套不上的 patch（指出是哪一個）都報出來；用暫時的 index，checkout 自己的 index 和檔案不動；shallow 的 checkout 從 `origin` 拿 `upstream_rev`；沒有 patch 就是上游本身、有 patch 卻沒有 `upstream_rev` 也報出來 | `scripts/ci_patches_test.py`（每個測試造一個上游加 fork 的 repo 和它的 shallow clone） | `python3 scripts/ci_patches_test.py` |

## CI

整套的測試由 CI 跑（設定由使用者維護）：每天跑 `test.py` 的 `wpt`、`wdspec`、`reftest`、`scenarios`，和 `cargo test --workspace`；每週跑 `matrix`、`fuzz`。做 RFC 時開發機上只跑和改動相關的部分（`CLAUDE.md` 的「測試」：每段工作做完跑改到的 crate，階段做完跑整個 workspace；`wpt`、`reftest`、`scenarios` 只跑改到的部分，不跑 `matrix`、`fuzz`、`wdspec`），所以：

- 改動沒涵蓋到的部分壞掉，要到下一次 CI 才知道；merge 不等 CI，CI 上壞掉的看到就修。
- `test.py automation`（真的視窗）不在 CI 上：它要螢幕和 GPU，照舊在開發機上、動到視窗那一層和驗收時跑。
- 開發機和 CI 用過的平台以外沒有自動測試（「測試守不住的地方」的「各平台」）。
- CI 在 GitHub Actions 的標準 runner 上跑（`.github/workflows/`）：`ubuntu-24.04`，4 個 CPU、沒有 GPU，畫面用 Mesa 的 lavapipe（wgpu 的 CPU adapter），所以 `test.py wpt` 一次只跑一個測試（CPU adapter 上 process 數是 CPU 的四分之一）。釘住 Ubuntu 的版本、不用 `ubuntu-latest`：WPT 和 reftest 的結果跟著 image 的 Mesa 變。`ci.yml` 在每次 push、PR 和每天跑 `cargo fmt --check`、clippy、`sanity.py` 的各項和 `numerics` 的檢查本身的測試，以及 `cargo test --workspace`；`nightly.yml` 每天跑 `scenarios`、`reftest`、`wpt`、`wdspec`：`scenarios` 是 `cargo test`，用 debug build；其他三套用 `ci` profile 的 machopo 和 machopodriver（`Cargo.toml`：release，留著 debug build 的檢查和溢位的 panic，像 Chromium 的 release bot 打開 `dcheck_always_on`），由一個 job 編一次、交給三套（`test.py` 的 `--profile ci --no-build`），測試的結果不論 job 怎麼結束（失敗、取消、逾時）都上傳。`wpt` 分成 4 份、各用一個 runner 同時跑（`test.py wpt --chunk I/4`，wptrunner 依目錄切：同一個目錄的測試在同一份），只跑一份時跳過整份清單的檢查，由下一個 job 的 `test.py wpt-check` 拿 4 份的 log 一起檢查（每份都跑完、清單的每一行都有測試跑到、每份預期結果的測試都有跑），再把 4 份的結果合成一個 artifact；`gc.yml` 每週跑 `matrix`、`fuzz`（GC 的測試用 debug 的 V8，比其他的都慢；`fuzz` 的 20 組設定分在兩個 job，各用自己的 seed），動到 GC 時手動開始一次。每套一個 job、平行跑，也可以在 Actions 的網頁上手動開始、選要跑哪一套。一個 job 失敗不取消其他的；`wpt` 和 `wdspec` 失敗只算警告（`continue-on-error`），其餘都通過時整次照樣算通過。每個 job 的準備（系統的函式庫、toolchain、`ci.py third-party`、cargo 的快取）在 `.github/actions/setup/`：快取照建置的內容分成三份（lint、平常的 debug build、`ci` profile），每份只有 `main` 上的一個 job 存，其他的讀它，repo 的快取上限（10 GB）才放得下。`gc.yml` 不用快取：GitHub 刪掉 7 天沒人讀的快取，每週跑一次的會找不到自己存的，還佔著每天的快取要用的空間。
- WPT 的時間在 CI 上也不放寬（不設 `MACHOPO_WPT_TIMEOUT_MULTIPLIER`）：它只拉長 testharness 的計時（`step_timeout`），wptserve 的延遲（`pipe=trickle`）不變，拿兩者比先後的測試就會失敗（`module/dynamic-import/delay-load-event.html`、`moving-between-documents/ordering/in-order.html`）。

## 快取和增量的交叉檢查

下面這些沿用上一次結果的做法，debug build 會從頭再算一次比對，不同就 panic（style 的 invalidation 範圍（invalidation set 和 stylesheet 改動的除外）、box tree 和 layout 的增量更新、paint 沿用的 item 和 raster invalidation 不在其中，靠測試守）。`cargo test`、reftest、情境和 WPT 都用 debug build 跑（CI 的 reftest 和 WPT 用 `ci` profile：release 加上同樣的檢查），所以新的功能漏改了這些做法（`docs/architecture.md` 的「快取和增量：加新東西時要跟著改的地方」）時，只要有測試踩到，多半當場失敗：

| 做法 | debug build 比對什麼 |
| --- | --- |
| 增量的 pre-paint（`paint`） | 每次增量的 pre-paint 之後從頭做一次，逐個 fragment 比對解析之後的狀態，連同活著的 node 和紀錄 |
| paint 記下的 hit test 目標（`paint`） | 每次 paint 之後用 hit test 的走訪收集目標，比對和記下的完全相同；被蓋住的 scroller 用外框排除的都是不會蓋到的 |
| `MatchedPropertiesCache`（`style_resolver`） | 命中時也重新 cascade 加依位置的調整，比對和共用的 style 相同 |
| descendant invalidation set（`style`：屬性、state 改了只重算 set 找到的後代） | 以前會重算整棵子樹、set 跳過的元素，不帶動畫的重新 cascade 一次（不設 selector 旗標），比對 style 和 pseudo-element 的 style 相同；為了檢查才往下走的元素不套用任何 set，和 release build 重算的範圍一樣 |
| stylesheet 改動只重算特徵找到的元素（`style` 的 `rule_set_invalidation`） | 沒被找到、也沒有因為別的原因重算的元素（規則變了的 tree scope 裡的），逐一比對多了、少了的規則，確認一條都不符合 |
| shaping 的快取（`layout`：段落的，和 parley fork 以字為單位的） | 段落的快取命中時、有字取用或存下了字的 shaping 時，也整段 shape 一次比對 |
| 選字型記住的第一個字型（`layout`，parley fork 的 `FontSelector`） | 不經過 query 用了它時，也跑整個 query，比對字型、index 和 synthesis |
| 清單的編號和 CSS counters（`layout`） | 每次建完、更新完也跑一次整份文件的 pass，比對每個 marker 和 `counter()` 的文字 |
| parse 的 fast path（`html`） | 收下時也用 tokenizer 和 tree builder parse 一次，比對兩棵樹 |
| cppgc 的讀取在 Rust 裡 inline（`v8` crate 的 fork） | 每次讀取也呼叫 C++ 的 `Get` 比對 |

paint 的快取另外由測試的 harness 守著（`paint` 的 `paint_controller`）：每一步把沿用的結果（item、chunk、hit test 的目標、raster invalidation）和整個重畫、逐個比對的比對。

守不住的：沒有測試踩到的輸入（新功能要有測試）；release build 不比對（`ci` profile 除外）；只在特定時序出現的失效。

## Mutation test

暫時弄壞實作，確認有測試失敗；沒抓到的補測試，或說明為什麼是等價的。

- **用 `python3 scripts/test.py mutate <spec>` 跑**：spec 是 TOML，列出每條 mutation（檔案、原文、改成什麼）和要跑的測試指令，格式見 `test.py mutate -h`。spec 放在那份 RFC 的資料夾，之後要重跑或補一條時照樣用。下面幾條它都會做：
  - **先確認原本的程式通過**每個測試指令：不然編不過或本來就失敗時，每一條都會被當成「抓到」。
  - **原文在檔案裡要剛好出現一次**，不對就在動任何檔案之前停下。
  - 結果分成抓到、卡住（超過 spec 的 `timeout`，連同底下的 process 一起結束，也算抓到）、沒抓到和編不過。**編不過不算抓到**：mutation 要編得過才測得到東西，改寫那一條。
  - **還原檔案之後更新修改時間**：搬回來的檔案比改壞後的 build 舊，不更新的話 cargo 會繼續用改壞的程式。Python 的檔案另外刪掉它的 bytecode 快取（`__pycache__`）：Python 照原始檔的大小和修改時間的整秒判斷快取有沒有過期，和原文一樣長的 mutation 在測試跑完的同一秒還原時，快取還是 mutation 的（2026-10-20 一條 `a / b` 換成 `b / a` 的 mutation 還原之後，測試照樣跑 mutation 的程式而失敗）。
  - 原檔在跑的期間放在 `target/mutate/originals/`；被強制結束的 run 留下的，下一次會拒絕開始，用 `test.py mutate --restore` 放回去。
  - **`to` 的行數比 `from` 少時補上空行**，讓後面的行號不動：rustc 的增量編譯會重新產生行號變了的每個函式（行號表是 debug info 和 panic 的位置），`dom_js` 的 `templates.rs` 裡的泛型函式每個宣告表的成員都單型化一份，加或刪一行比改一行多花約三分鐘（2026-11-04 量：只改註解的字 11 秒，最前面加一行 194 秒）。空行加在不改程式的地方：`from` 在行尾結束就加在 `to` 之後，從行首開始就加在之前，都不是時加在那一行的結尾之後。
- **限制測試的記憶體**（Linux）：讓串列或樹繞成圈的 mutation，可能讓測試把繞圈的結果一直收進 `Vec`，無限長大：2026-10-19 一條讓兄弟節點指向自己的 mutation，讓 `dom` 的測試長到 58 GB（這台 62 GB），OOM 連帶結束了跑 `test.py` 的其他程式，兩次。測試指令前面加 `systemd-run --user --scope -q -p MemoryMax=24G -p MemorySwapMax=0`，超過時只結束那次測試，算抓到。timeout 照基準那一輪的時間設幾倍（`test.py` 印出它），不要設成幾十分鐘：卡住的 mutation 要等滿才換下一條。
- **先跑最相關的測試**，抓到就換下一條；全部跑過再跑完整的 `cargo test --workspace`。
- **第一條沒抓到就停下來**，補了測試或確認等價之後再繼續，免得後面的結果建立在錯的前提上（`test.py mutate` 預設這樣做；`--keep-going` 跑完全部）。
- 跑的期間實作檔案是壞的：先告訴其他人不要 stage 或 commit，跑完確認都還原了。
- 結果（弄壞了什麼、哪個測試失敗、沒抓到的和原因）記進那份 RFC 的 `progress.md`；補不了測試、又不是等價的，記進 `test-gaps.md`，等價的記進那裡的「等價、不用處理的 mutation」。

## 工具和跑法

- **macOS 會掃描剛連結好的執行檔**（`syspolicyd`、`XprotectService`）：每個測試 binary 都靜態連結 V8，一次完整的測試有大半時間花在這裡。把終端機加進「系統設定」的「開發者工具」，在終端機裡跑就不會被掃描；長時間的測試和 mutation test 都在那裡跑。
- **`target/*/deps` 裡的 `.o` 會越堆越多**：macOS 的 debug build 預設 `split-debuginfo = "unpacked"`，DWARF 留在執行檔自己的 `.o` 裡，每次重新 link 都留下新的一批。`raster` 第一次建立 Skia 的字型管理器時，CoreText 會把執行檔所在的目錄讀好幾次，目錄大了之後每個會畫文字的測試 binary 都要多等好幾秒到十幾秒才開始。一份 RFC 做完時跑 `cargo clean` 清掉（`docs/README.md` 的「一份 RFC 做完時」），做到一半明顯變慢時也可以先跑；它刪掉整個 `target/`，不要和 cargo 或 `test.py` 同時跑。不用 `packed`（每次 link 多跑 `dsymutil`）或 `off`（backtrace 沒有檔名和行號）。
- **Windows 上 `target/*/deps` 堆的是整個執行檔**：重新 link 會蓋掉同一個檔案，但換 toolchain、改 `Cargo.lock`，或 `-p` 的 feature 和 `--workspace` 不同時，cargo 會用新的雜湊另外 link 一整套，舊的留著；連結 V8 的每個執行檔約 90 MB，`.pdb` 約 180 MB（完整的 debuginfo 時約 600 MB，`target/debug/deps` 曾經堆到 400 GB 以上，2026-10-09）。同樣在 RFC 做完時 `cargo clean`，磁碟不夠時也可以先跑。
- **link 是重編的大頭**：改了 `dom` 這類底層的 crate，連結 V8 的測試 binary 都要重新 link。所以每個 crate 的整合測試是一個 binary（tests/it/；2026-10-10 合併之前 workspace 有 159 個測試 binary、140 個連結 V8，之後 44 個、30 個；改 `dom` 之後 `cargo test --workspace --no-run` 從 38.7 秒變成 13.8 秒，`cargo test --workspace` 跑測試的時間從 34.3 秒變成 21.3 秒，因為同一個 crate 的測試在一個 process 裡平行跑，3 次的中位數）。debug build 只留行號表（`Cargo.toml` 的 `[profile.dev]` 的 `debug = "line-tables-only"`：backtrace 照樣有檔名和行號，debugger 看不到變數；Chromium 的 `symbol_level = 1`），Windows 上用 rust-lld link（`.cargo/config.toml`；Chromium 在 Windows 上也用 lld-link）。2026-10-09 在 Windows 上量（3 次的中位數）：改 `dom` 之後 `cargo test --workspace --no-run` 從 58 秒變成 29 秒，改 `dom` 再跑一個 `shell` 的測試從 10.1 秒變成 6.9 秒，只重新 link 一個測試從 5.8 秒變成 2.3 秒；只換 linker 時是 41.5、8.5、3.7 秒，只改 debuginfo 時是 35、7.7、3.5 秒。要用 debugger 看變數時見下面的「測試和建置用的環境變數」。
- **在 `dom_js` 的泛型程式碼所在的檔案加刪行，重編要多約三分鐘**：宣告表的每個成員都單型化一份 `templates.rs` 的 callback，行號一動，它們的行號表都變了，增量編譯整批重新產生（2026-11-04 在 Linux 上量：`templates.rs` 只改註解的字或 `touch`，`dom_js` 的測試重編 11 秒；最前面加一行共 196 秒，`dom_js` 本身 194 秒，測試 crate 和連結約 1 秒）。改一行、或改在檔案尾端，比在前面加刪行快得多；`test.py mutate` 因此替 mutation 補空行。
- **`cargo test --workspace` 跳過情境，reftest 和 WPT 不在 `cargo test` 裡**：machopo 自己的 reftest 約 13 秒（wptrunner）、情境約 8 秒、WPT（testharness.js 測試、reftest 和 crashtest）約 50 秒（wptrunner，32 個 process），`cargo test --workspace` 約 21 秒（2026-10-09 到 10 在 Windows 上量，都已經編好）。沒設 `MACHOPO_SLOW_TESTS` 時情境印一行 skipped 就結束，`python3 scripts/test.py scenarios` 設了再跑；`reftest`、`wpt` 經過 wptrunner。它們不在完成一段工作前的清單裡：開發機上只跑改到的部分（什麼時候跑見 `CLAUDE.md`），整套由每天的 CI 跑（見「CI」）。
- **一個整合測試讓 process 結束時**（V8 的 abort、stack overflow），同一個 crate 的整合測試都停在那裡，沒跑到的不會回報：找原因時用篩選單獨跑它（`cargo test -p dom --test it tree::nodes_have_their_kinds_types_and_names`）。
- **合併的整合測試的 V8 flag 在 `main` 之前設**：`bindings`、`dom_js`、`gc_bench` 的 tests/it/main.rs 用 `bindings::initialize_v8_before_main!`（前兩個是 `"--expose-gc"`）。V8 的 flag 整個 process 只有第一次初始化生效，`bindings` 自己也會不帶 flag 地初始化（`platform`、`V8PerIsolateData::new`），由測試自己設的話就看哪個測試先跑。其他 crate 的測試都不帶 flag，不用它；要不同的 flag 的測試寫成獨立的 binary，在 `sanity.py` 的 `OWN_TEST_BINARIES` 寫明理由。
- **每個 crate 都設了 `doctest = false`**：沒有 doctest，但 `cargo test` 照樣會對每個 crate 跑 rustdoc，很花時間。
- **會跑很久的指令前面加 `caffeinate -i`**（macOS）：電腦休眠時 monotonic clock 不前進，看起來像卡住。Windows 沒有內建的對應指令：跑 `test.py fuzz` 這類跑很久的之前，先在電源設定裡暫時關掉睡眠（2026-10-09 跑 wdspec 時兩次停了幾十分鐘，都是電腦休眠，不是 machopodriver 或 machopo 的問題）。
- **真的視窗要螢幕開著**：螢幕閒置關掉時，macOS 把視窗當成被遮住，Viz 拿不到 texture、整個 frame 跳過，截圖（`Machopo.captureWindow`、情境的截圖）照設計等一個真的畫出來的 frame，就一直等到逾時（`caffeinate -i` 不防螢幕關掉）。`test.py automation` 在 macOS 上自己跑 `caffeinate -d -i`，跑完就結束；直接跑 `MACHOPO_WINDOW_TESTS=1 cargo test` 或 `machopo --automation` 時，前面加 `caffeinate -d -i`。2026-10-10 在 Apple Silicon 上碰到：`pipe --window` 剛好在螢幕關掉的那一刻開始，每次都在第一張截圖逾時。
- **log 預設帶 ANSI 的顏色控制碼**，接到 pipe 也一樣，要先濾掉才能 grep（`perl -pe 's/\e\[[0-9;]*m//g'`）。
- **不穩定的測試不要用重跑蓋過去**：找出原因，記進那份 RFC 的 `progress.md`。WPT 的測試查過之後一時修不好的（例如確定 `main` 上也會、不是這次的改動造成的），在它的 `.ini` 標成 known intermittent：`expected` 寫成狀態的清單（`[OK, ERROR]`，第一個是平常的），上面用 `#` 註解寫找到了什麼、原因還沒找到時在哪裡查；跑出清單裡的另一個狀態不算非預期，`test.py` 在結尾列出來，沒有註解的清單它不跑（格式見 `tests/wpt/README.md`）。修好之後把清單拿掉。
- **結果要看 GC 什麼時候標的新測試，交審核前照 CI 的跑法重複跑上千次**（增量的 marking、`--stress-incremental-marking` 這類壓力的 flag、平行的 marker、斷言收掉了或還活著）：千分之幾的失敗跑 20 次看不出來。直接跑測試的 binary（路徑見 `cargo test --no-run` 的輸出），不帶篩選、讓同一個 binary 的測試照 `cargo test` 的方式在一個 process 裡平行跑，跑 1000 次，再在所有核心都忙著時跑幾百次：stack 上剩下什麼、時序怎麼排都跟著變（2026-10-28 一個測試兩個一起跑時 1000 次失敗 4 次，單獨跑 1000 次都沒有）。斷言 V8 收掉了的，先做一次不掃 stack 的完整 GC（`request_garbage_collection_for_testing_with_stack_state` 帶 `EmbedderStackState::NoHeapPointers`）：V8 在可能有 heap 的指標在 stack 上的停頓裡保守地掃 stack，用過的 stack 上留著的舊 word 指著某個 `TracedReference` 的節點時，那個 wrapper 會多活一輪。
- **連結本機編的 V8（`RUSTY_V8_ARCHIVE`）時，編輯器的 rust-analyzer 要帶同一個值，或用自己的 target 目錄**（VS Code 的 `rust-analyzer.cargo.extraEnv`、`rust-analyzer.cargo.targetDir`）：不然它在 rusty_v8 的 fork 的檔案改了之後（mutation test 改 fork 時也是）跑的 `cargo check` 重跑 v8 的 build script，下載 `RUSTY_V8_MIRROR_TAG` 的 release，蓋掉 `target/debug/gn_out/obj/librusty_v8.a`，接著的 `cargo test` 就找不到 fork 新加的符號（`undefined symbol: v8__…`），即使 `RUSTY_V8_ARCHIVE` 那一份裡有。v8 的 rlib 重編時把當時的 archive 包進去（static 的 library 包在 rlib 裡），所以換回 archive 不夠：要讓 cargo 這一側的 build script 重跑（`RUSTY_V8_ARCHIVE` 換一個寫法，例如結尾加 `/`）；`cargo clean -p v8` 也行，但連 rust-analyzer 那一份也清掉，它下次又會下載。

## 測試和建置用的環境變數

`machopo` 執行時讀的環境變數在 `machopo --help`；這裡是只在測試或編譯時用的：

| 變數 | 誰讀 | 作用 |
| --- | --- | --- |
| `MACHOPO_UPDATE_EXPECTATIONS` | `test.py wpt`、`reftest`、`wdspec` | 設了（任何值）就把跑出來的結果寫成預期結果：wptrunner 的 `.ini`（WPT 的在 `tests/wpt/metadata/`，machopo 自己的 reftest 的在 `tests/reftests/` 的 `metadata` 目錄，全部通過的刪掉），別的平台的條件、`disabled` 和註解留著。之後檢查 diff。 |
| `MACHOPO_WPT_TIMEOUT_MULTIPLIER` | `test.py wpt`、`reftest`、`wdspec` | 正數：每個測試的逾時乘上它（wptrunner 的 `--timeout-multiplier`），慢的機器用。 |
| `MACHOPO_UPDATE_GOLDEN` | `dom_wasm` 的 `wit` | 設了就用目前的宣告表重寫 `crates/dom_wasm/wit/machopo-dom.wit`，之後檢查 diff（`crates/dom_wasm/README.md`）。 |
| `MACHOPO_SLOW_TESTS` | `shell` 的 `scenarios` | 設了才跑情境；`test.py scenarios` 會設，`cargo test --workspace` 不跑它們。 |
| `MACHOPO_TEST_SEED` | `bindings` 的 `cppgc_traced_marking` | 亂數種子，十進位或 `0x` 開頭的十六進位；測試會印出用到的種子，失敗時拿來重播。 |
| `MACHOPO_PRINT_FAILURES` | `html` 的 `tree_construction` | 設了就以 `<id> [ Failure ]` 印出每個失敗，可以直接貼進 `tests/wpt/tree-construction-expectations.txt`；沒設時只印前 10 個非預期的失敗。 |
| `V8_FORCE_DEBUG` | `v8` 的 build script | 設成 `1` 時連結 debug 的 V8（有 DCHECK）。依賴 `v8` 的 crate 都會重編，所以另外指定 `CARGO_TARGET_DIR`（絕對路徑：trybuild 從各 crate 的目錄解析相對路徑）；`test.py matrix`、`fuzz` 用 `target/v8-debug`。 |
| `RUSTY_V8_ARCHIVE` | `v8` 的 build script | 連結這個目錄裡本機編的 V8（`ci.py v8` 的結果），取代 prebuilt；只在改 rusty_v8 的 fork 時用。 |
| `MACHOPO_V8_CRATE_DIR` | `bindings` 的 build script | `v8` crate 原始碼的目錄（編 C++ 的 glue、檢查 `v8` 內部的實作）；預設在 cargo 的 registry 裡找，找不到時才要設。 |
| `CARGO_PROFILE_DEV_DEBUG=full` | cargo | 完整的 debuginfo，debugger 看得到變數；平常的 debug build 只留行號表。它改掉輸出的檔名，第一次整個重編，之後和平常的並存；用完跑 `cargo clean` 清掉。 |
