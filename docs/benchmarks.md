# 效能的量測

machopo 和 Chrome 的效能怎麼量：`scripts/bench.py` 的 benchmark 工具（Speedometer、blink_perf、raster 和 Chrome 比，`calls` 只量 machopo 每次呼叫 DOM 的指令數，`gc` 只量 machopo 的 DOM 的 GC）、它們的雜訊和怎麼讀數字。測試的種類和跑法在 `testing.md`；最近一次量出來差在哪、可以開 RFC 的方向在 `performance-gaps.md`。

`python3 scripts/bench.py speedometer` 量 Speedometer 3.1 在 machopo（`perf` profile）和 Chrome for Testing 上的時間（完整一次約 10 分鐘，要接電源；`-h` 有選項）。

**平常不量，只在使用者要求時跑**：RFC 的測試計畫不排量測，一段做完、一份 RFC 做完、讓新的 suite 變有效時都不量；優化的 RFC 要拿數字當驗收時，也是在計畫裡寫明、到時候由使用者決定要不要量。量了的數字和比較記進 Speedometer 量測工具那份 RFC 的 `progress.md`（每次量的數字都記在那裡）。

工具經過 CDP 的 pipe 控制兩個瀏覽器（Chrome 的 `--remote-debugging-pipe`、machopo 的 `--automation-pipe`）：開頁面、錄 Chrome 的 trace、關掉都經過它，兩邊都是自己正常結束的。Windows 上工具給 Chrome for Testing 的資料夾（`target/chrome-for-testing/`）加上 app container 的讀取權限，和裝在 `C:\Program Files` 底下的 Chrome 一樣：Chrome 的 sandbox 讀不到 `chrome.exe` 時 network service 起不來，頁面一個請求都發不出去。

`--trace` 錄兩邊的 trace（Perfetto 的 protobuf；Chrome 的用 CDP 的 `Tracing`，從頁面載入前錄到報告送回，緩衝區滿了丟掉事件時工具會說），`--sample` 在 Linux 的 `perf` 或 samply（macOS、Windows）底下跑 machopo、只留 renderer main thread 在 runner 計時的區間裡的樣本：時間花在哪個 span、哪個函式（JS 的由 V8 命名）。區間照 runner 在每個 test 前後打的 mark（`<suite>.<test>-start` 到 `-async-end`，和它回報的 sync 加 async 是同一段）；trace 裡沒有 mark 時（machopo 還不寫 User Timing 的版本，`--against` 會碰到）照 runner 的 frame 猜，`sample.md` 和 `compare.md` 寫明用的是哪一種。`--trace` 跑完也寫出 `phases.md` 和 `phases.json`：每個 suite 的計時區間裡，renderer main thread 上各階段（script、style、建 box tree、layout、paint、parse、GC、canvas）的 self time，machopo 和 Chrome 並列、差多少，加上合計；巢狀的 slice 時間算最裡面那個，兩邊的 slice 名稱怎麼對到階段寫在 `speedometer.py` 的 `PHASE_SLICES`，沒對到的 slice 列出前 10 名（新的 span 名稱出現時要補進對照表）。trace 裡沒有 runner 的 mark 時不算。它們也是量測，跟著同一條規則。`perf` profile 在 Linux 和 macOS 上留著 frame pointer，和 Chrome 一樣。

`--profile` 讓兩邊各跑每個 suite 一次（`--iterations`），用 DevTools 的 `Profiler`（V8 的 `CpuProfiler`）每 1 ms 取樣頁面的 script：Chrome 經過 CDP，machopo 經過 automation pipe 的同樣的方法（`common.py` 的 `open_profiled`：導覽之後開始，到報告送回；`measure.mjs` 讓 runner 等 profile 開始了才開始，suite 的程式都在 profile 開始之後才編譯）。profile 在 `profile/`（`.cpuprofile`，Chrome DevTools 的 Performance 面板開得了），`profile.md` 和 `profile.json` 是兩邊的時間照頁面的 JS 函式並列（`profiles.py`）：一個樣本算給 stack 上最內層、有網址的 JS 函式，它呼叫的 DOM、getter、setter（和 Chrome 的 Fast API）都算它的；沒有 JS 的是 `(program)`（在 task 裡、不在 script）、`(idle)`（等下一個 task）、GC，stack 上沒有有網址的 JS 函式的是 `(no JS function)`。兩邊的 JS 本身一樣（同一個 V8），同一個函式差很多，差的就是它用的平台功能。另一張表是 machopo 的 DOM 成員（只有 machopo：Chrome 的 Fast API 沒有自己的 node；machopo 走共用路徑的成員共用一個 callback，合成一列）。只算 runner 計時的區間（每個 test 的 sync 和 async，照 runner 的 mark，和 `--trace`、`--sample` 一樣），其餘（載入、iteration 之間）是 `(outside the timed windows)` 一列，`profile.json` 也存整次執行的。mark 是頁面的時鐘（`performance.now()`），profile 是 V8 的：頁面在 profile 開始之後、runner 開始之前空轉 10 ms（`__machopoPageClock`），落在它裡面的樣本把兩個時鐘對起來，每個 suite 寫明對齊的誤差上限（和同時錄的 trace 比過，誤差最大 0.52 ms）。取樣讓兩邊各慢約一成（machopo 的 renderer 照 Blink 標閒置）。它也是量測，跟著同一條規則。

`--sample` 取樣兩個事件：使用者空間的 cycle 和指令，各每一百萬個取一個樣本，所以樣本數就是花了幾百萬個 cycle、執行了幾百萬條指令，不跟著時間走（`sample.md` 兩者都列，加上 IPC；指令的樣本在 `<suite>-machopo.instructions.folded`）。cycle 是花的時間，會隨 CPU 的狀態和 build 的佈局（inline、函式的位置）變，同一段程式換一個 build 就可能差上一兩成；指令數是做的工作，幾乎不受這些影響，但看不到等記憶體的時間（cache miss）。比較兩個版本時兩個都看：指令數變了是工作量變了，只有 cycle 變是記憶體、佈局或機器的狀態。

**Windows 上 samply 經過 ETW 取樣**（`cargo install --locked samply`，加上 Windows Performance Toolkit 的 xperf，在 Windows ADK 裡），和 macOS 一樣以 CPU 時間計；stack 照 binary 的 unwind table 展開（x64 不靠 frame pointer，Chrome 也沒有），連 kernel 的 frame 一起算（Linux 的 `cycles:u` 只算使用者空間；2026-10-20 的 TodoMVC-jQuery 約 5% 在 kernel 裡，page fault、驅動程式），掛在 machopo 的函式底下。ETW 要系統管理員：工具在一般權限下 build 好 machopo，再把所有要取樣的 suite（`--against` 的每一輪也是）交給一個以系統管理員跑的自己，UAC 只問一次，它的輸出照樣印在原本的終端機。那個 process 由系統建立、不繼承環境變數，工具把自己的環境（`MACHOPO_V8_FLAGS` 等）傳過去。machopo 的函式由 PDB 命名：Windows 上 `perf` profile 的 exe 記著 PDB 的絕對路徑（`common.py` 的 `build_options`；只記檔名時 samply 找不到它，函式只有位址），Windows 自己的 DLL（ntdll 的 heap、vcruntime140 的 `memcpy`、kernel）由 Microsoft 的 symbol server 命名：samply 錄的時候 DLL 在磁碟上就只用 DLL 本身（沒有 export 的函式是 `fun_<位址>`），所以工具讀樣本時把它們的位址交給 `samply load` 的 symbolication API 另外查（拿掉 DLL 的路徑，它才去 symbol server；第一次要下載 PDB，約一分鐘，之後在 samply 的快取裡；查不到時照舊是 `fun_…`，沒有公開符號的驅動程式也是），JS 的函式由 V8 經過 ETW 命名（`--enable-etw-stack-walking`）。樣本的時間從 samply 的 kernel ETL 的開頭起算，和 trace 一樣是 QueryPerformanceCounter：samply 寫在 profile 裡的開始時間是它自己啟動的時間，每次差上幾百 ms，不能用。

**取樣 Chrome 用 `--sample --browser chrome`**（只有 Linux）：Chrome for Testing 的 Linux 版沒有符號，取樣的是有符號的 Chromium，預設 Fedora 的 `/usr/lib64/chromium-browser/chromium-browser`（`sudo dnf install chromium`，符號用 `sudo dnf debuginfo-install chromium`），`--chrome-binary` 換別的。它先不取樣地量一次每個 suite 的時間（`chromium-runs.json`），再照 machopo 的設定在 `perf` 底下跑：加 `--no-sandbox`（renderer 的 sandbox 擋住 V8 寫 perf map），trace 只錄 `blink.user_timing`（`--trace` 錄的那些 category 讓它慢一倍）；Linux 上 Chromium 不給 process 的 main thread 命名，renderer 的 main thread 照 trace 的 thread descriptor 的 tid 挑，它的 trace 的時間是 `CLOCK_MONOTONIC`。兩邊的樣本（`<suite>-machopo.folded`、`<suite>-chrome.folded`）和兩邊的時間（上一次 `bench.py speedometer` 的 `machopo-runs.json`、`chrome-runs.json`）都在時，`--sample` 跑完寫出 `categories.md`：每個樣本照 stack 上最內層說得出種類的 frame 分成 JS、DOM、style、文字、box layout、GC、bindings……（規則在 `categories.py`：配置和容器算給呼叫它的，V8 自己的 frame 往外看是 JS 還是 machopo、Blink 呼叫的），每個 suite 各類佔樣本的比例乘上它沒有取樣時的時間換成 ms（取樣讓兩邊各慢不同的幅度），列出各類的差、只有這一類追平時的幾何平均、每個 suite 差最多的類別、每一類最多的函式，和那個 Chromium 比 Chrome for Testing 慢多少：Fedora 的 Chromium 沒有 Google 的 PGO（2026-11-06 的 156 慢 23%），它各類的比例只是 Chrome for Testing 的近似。

**比較兩個版本用 `--against REV`**（`--runs N`，預設 3）：在 repo 旁邊的 worktree（`../machopo-against`）checkout `REV`、build 到 `target/against`，和工作目錄的 machopo 輪流各跑 N 次（只有 machopo），寫出 `compare.md`。不帶 `--sample` 時比時間：每個 suite 兩邊所有 iteration 的總時間的中位數和 95% 區間、變化，machopo 的記憶體峰值（macOS 是 phys footprint 的峰值，Linux 是 `VmHWM`，Windows 是 private bytes 的峰值；每次跑完讀一次，取中位數）和它的變化，各 suite 變化的幾何平均，和每一輪的中位數（看漂移）。帶 `--sample` 時比樣本：每個 suite 兩邊的 cycle 和指令數（macOS 是 CPU 時間）的中位數、範圍和變化，和變最多的函式。兩邊共用 `../third_party`，所以 `REV` 的 `third_party.toml` 和 `.cargo/config.toml` 要和工作目錄的一樣。只比一次的總數不可靠：同一個 build 跑兩次就會差好幾 %。同樣的程式碼比兩個 build（`--against HEAD`、工作目錄沒改 machopo）時，TodoMVC-jQuery 的指令數每次在 1% 以內、中位數差 0.4%，cycle 卻差了 5.6%；工作量本身每次不同的 suite（TodoMVC-Preact-Complex-DOM 的指令數每次差到 ±12%）只看得出大的差別。函式層級的差，同樣的程式碼也可能有兩三成（malloc 這類隨 heap 的狀態變），用來找方向，判斷看總數。

**Blink 的 perf tests 用 `python3 scripts/bench.py blink-perf`**（路徑、`--dirs`、`--pages`、`--timeout`、`--against`、`--runs`；`-h`）：Chromium 的 `third_party/blink/perf_tests`（`../third_party/blink_perf/`，`third_party.toml` 固定的 commit）一頁一頁在 machopo（`perf` profile）和 Chrome for Testing（headless）裡各開一個新的瀏覽器跑，每頁量一種操作（`PerfTestRunner` 跑 20 次，第一次熱身不算）。沒有 `--dirs`、`--pages` 時跑頁面清單（`scripts/bench/blink_perf/pages.txt`：照領域分段，machopo 現在連續兩次跑得有效、人工看過的頁，從很小的一組開始慢慢加）；給了路徑（`bench.py blink-perf dom/ layout/`）時只跑清單上那些路徑底下的頁，平常只量改到的領域。一頁有效：兩邊都交了數值，結束時 document 的摘要（每種元素、每個 class 有幾個，文字多長）相同；只有 Chromium 的 harness 有的東西（tracing、`internals`、`testRunner`、`GCController`、`gpuBenchmarking`、`gc()`）的頁不跑。報告（`target/bench/blink_perf/report.md`）最前面是清單上變無效的頁（回退），再來是每頁兩邊的中位數、machopo 慢幾倍，目錄和全部的幾何平均，無效的頁和原因，排除的頁（`runs.json` 有 runner 最後幾行的 log）。machopo 快 2 倍以上的標「可疑」，不算進幾何平均：machopo 可能沒做到那件事，摘要看不出來（例如沒有更新 `<textarea>` 的值）；自己 catch 例外的頁標「會吞例外」：machopo 缺的 API 可能被吞掉。這兩種加進清單前要人工確認兩邊做的事一樣。要加頁（或 machopo 補上一個功能之後），用 `--pages` 跑兩次，兩次都有效、不可疑才加進清單：同一頁兩次的倍數可能差很多。**比較 machopo 的兩個版本用 `--against REV`**（`--runs N`，預設 3；worktree、build 和要求和 Speedometer 的一樣，見上面）：只有 machopo，兩個版本輪流跑清單（或給的路徑、`--pages`、`--dirs`）各 N 次，寫出 `compare.md`：每頁兩邊所有 iteration 的中位數和 95% 區間、變化，各頁時間（current 除以 against）的幾何平均，每一次的中位數（有的頁每次 process 落在不同的水準，例如 `css/AttributeDescendantSelector` 的 machopo）。兩個版本的 document 摘要不同的頁（新的少做了事）不比，列出原因。不判斷單頁變快、變慢：2026-10-20 同樣的程式碼的兩個 build 比 10 頁，`css/PseudoClassSelectors` 差 34%（每個 build 自己三次都很穩）、`layout/line-layout-line-height` 差 15%，幾何平均差 0.0%，是程式碼在兩個 build 裡的位置不同，重複再多次也在；單頁的變化要遠大於這個才算數，可疑時用取樣找原因，或在另一個 build 上再確認。微基準放大單一操作，倍數很極端，不能換算成 Speedometer 的分數：用來找哪一種操作慢。和 Speedometer 一樣只在使用者要求時跑。

**和 Chrome 比 GC 用 `bench.py blink-perf --gc`**（`--runs N`，預設 3；不能和 `--against` 一起用）：每一頁 `--runs` 次，每次在 machopo 和 Chrome 裡各開一個新的瀏覽器、開著 trace（留在 `target/bench/blink_perf/gc/`，Perfetto UI 打得開；Chrome 只錄 `common.py` 的 `CHROME_GC_TRACE_CATEGORIES`，machopo 錄它固定的那一組，比 Chrome 多），從 runner 計時的區間（`console.time("blink_perf")`，第一個計時的 iteration 到最後；Chromium 的 `tools/perf/benchmarks/blink_perf.py` 也照這個區間讀 trace）讀 renderer 的 GC，寫出 `target/bench/blink_perf/gc.md`（和 `gc.json`），每一格是「machopo / Chrome」、幾次的中位數。選頁的規則和平常一樣；看 GC 時量 `bindings/gc-forest.html`、`gc-mini-tree.html`、`gc-tree.html`、`create-element.html`、`insert-before.html` 和 `parser/innerHTML-setter.html`。怎麼讀：
- **GC** 是 runner 的 thread 上最外層的 GC slice（切法和 `bench.py gc` 一樣：相隔不到 10 µs 的算同一次停頓），只算它所在的 process；V8 處理 GC 請求的那一層（`V8.GCHandleGCRequest`，Chrome 的 full GC 多半包在裡面）拿掉，裡面的 GC 照它的種類算。其中 **DOM heap** 是每個 thread 上最外層的 `CppGC.*` 和 `Gc.*`（elise 的），在 V8 的 GC 裡或自己一段；machopo 的 `CppGC.*` 是空的 `CppHeap`（V8 照樣推它），另外一欄。**V8** 是 GC 減掉 DOM heap。
- **其他 thread** 的 GC 可能和 main thread 的停頓重疊（main thread 在等）。其中 DOM heap 的：elise 的 worker 跑它的 job 時各是一段 `Gc.ConcurrentMark`、`Gc.ConcurrentSweep`、`Gc.ParallelScavenge`、`Gc.Discard`（heap 的 thread 跑的那一份在它的 `Gc.Mark`、`Gc.Sweep`、`Gc.Scavenge` 裡），Oilpan 的是 `CppGC.ConcurrentMark` 這類。
- **停頓**：Chrome 每頁有上萬個，多半是 Oilpan 在 low priority task 裡的 sweep（一次幾 µs），中位數看不出什麼，看 1 ms 以上的個數和最長的。
- **V8 的排程**（兩邊都錄的 `v8.memory` 的 counter 和 V8 的事件）：full GC 和 scavenge 的次數；每次 marking 開始的原因（`V8.GCIncrementalMarkingStart` 帶的）和當時全域的用量（嵌入端的、V8 的 old generation 和 external）是全域上限的幾倍；full GC 之後嵌入端的大小（GC 結束後第一次記的全域減 old generation 和 external）。V8 跨過上限就開始 marking，但嵌入端說頁面正在載入時（`Isolate::SetIsLoading`，最多 7 秒）等到超過上限加上 `max(上限的一半, 32 MiB)` 才開始：Chrome 在 blink_perf 的頁上就是這樣（倍數遠大於 1），machopo 不呼叫它（倍數約 1），full GC 因此比較多次。Oilpan 在 GC 之後才 sweep，Chrome 的「full GC 之後」是垃圾放掉之前的大小：只在兩邊都在 heap 還小時收的頁上比得起來（`gc-forest`、`gc-mini-tree`），heap 很大才收的（`gc-tree`）比不了。
- **成績**是開著 trace 的，和平常的 `blink-perf` 不同。

**tile 的 raster 用 `python3 scripts/bench.py raster`**（`--pages`、`--window`、`--scale`、`--raster-threads`）：幾個頁面（`tests/sites/` 的 Gutenberg、SQLite，Speedometer 的 NewsSite-Next）在 machopo（`perf` profile）裡捲動、改視窗大小，報告（`target/bench/raster/raster.md`）列每一段的內容更新（Compositor thread 上的 `TileManager::PrepareTiles`）的次數、raster 的合計、平均和最長、main frame 的合計、raster 了幾個 tile、幾個是單色。預設 headless：Compositor thread 上的 raster 和用哪個 Viz 的 renderer 無關，不會跳出視窗；device scale factor 預設 2（高解析度的螢幕的，raster 的成本跟著像素走），和真的視窗量到的相近（真的視窗另外有上傳到 GPU 的時間）。machopo 的 raster 是同步的，raster 慢是 frame 變長、不是露出空白，所以不報 frame 的間隔（滾輪事件要等 renderer 處理完才回覆，frame 跟著送事件的節奏）。一次約 1 分鐘，也是量測，跟著同一條規則。

**一次 DOM 呼叫的成本用 `python3 scripts/bench.py calls`**（`--cases`、`--n`、`--runs`；`-h`；Linux，要有 `perf`）：幾個成員（`firstChild`、`nodeType`、`getAttribute`、`setAttribute`、`appendChild`、`createElement`、`addEventListener`（再加一次已經有的 listener：找、比 callback）和 `dispatchEvent`（在一個不在樹裡的元素上，一個空的 listener：分派的固定成本））各在一個迴圈裡呼叫 `--n` 次（預設一百萬），由 `dom_js` 的 `bench::bench_calls` 跑（一段 script，在自己的 realm 裡用 `machopoDom` 的 document 和 interface 物件），`perf` profile 的測試 binary、`#[ignore]` 的測試；`perf stat` 數整個 process 的使用者空間的指令和 cycles，減掉同樣的空迴圈、除以 `--n`，每個是 `--runs` 次（預設 3）的中位數（空迴圈每一輪跑 3 次：它的指令數大約六次裡有一次多約 1000 萬（每次呼叫 10 條），三次的中位數幾輪就會碰到一次，所有的 case 一起少 10），綁在一顆最快的 CPU 上。報告在 `target/bench/calls/calls.md`（和 `calls.json`）。**指令數幾乎不隨次數和 build 變**（同一個設定三次差 0.2%，程式碼的位置不影響它），所以**比較兩個 build（兩種做法、優化前後）量每次呼叫的指令數**，不比時間：同樣的程式換一個 build，每次呼叫的時間就可能差一成，runs/s 差更多；cycles 也印出來參考。CPU 數得到時（AMD 的 `ls_bad_status2.stli_other`、Intel 的 `ld_blocks.store_forward`，照 `/proc/cpuinfo` 的廠商選、`perf list` 要有），也數 **store forwarding 的衝突**（load 要等一個和它重疊、轉不過來的較舊的 store 寫進 cache：窄的 store 接著寬的 load 就是），同樣換算成每次呼叫，印在報告的方括號裡：熱門的成員每次呼叫應該是 0（x86-64 上，callback 的回傳值被編成 32 bits 的 store、builtin 接著讀整格，佔了空的 getter 5.4 ns 裡的 2.3 ns）。數不到時那一欄不印。

**動到 binding 或每次呼叫 DOM 都會走到的路時，那一段結束時跑一次 `bench.py calls`**（幾分鐘），和上一段記下的數字比（記在那份 RFC 的 `progress.md`）：變多的在同一段裡查清楚是哪一處、修掉或寫明為什麼值得。每段的差只有幾個到幾十個指令，沒有每段量時一路累積，到後面要用 worktree 回頭找是哪一段加的。寫每次呼叫都會走到的檢查或查找時，先對照 Chrome 怎麼做、成本多少（一次讀取、一次指標比較），不要先寫線性的掃描或字串的比較。

**量舊的 commit 時，每個 worktree 用自己的 target 目錄**（`--against` 用 `target/against`）：幾個 worktree 共用一個 target 時，cargo 會把別的 worktree 編出來的 workspace 的 crate 當成最新的，連主目錄的 `target/perf` 都會被汙染、編不過，要 `cargo clean --profile perf` 重編。

**DOM 的 GC 用 `python3 scripts/bench.py gc`**（`--heaps v8,v8-single,gc,gc-parallel`、`--baseline`、`--workloads`、`--runs`、`--scale`；`-h`）：`gc_bench`（`perf` profile，`crates/gc_bench`）在新的 GC 上跑 DOM 的四個工作和 `ids`，加上六個配置模式。DOM 的工作：節點和以前在 cppgc 上的 DOM 的節點一樣大（和之前量的比得起來）、有一樣的五條樹的連結，沒有 DOM 本身的成本（id、mutation 的事件、style）。build 建十萬個節點（一回合一千個，像 parser）；churn 在一萬個節點的樹上每回合換掉一棵第二層的子樹（一樣大）；replace 每回合把容器底下的一千個節點整個換掉（像 `replaceChildren()`）；list 是兩千個節點的清單，每回合在尾端加 10 項、從頭拿掉 10 項（無限捲動）。配置模式拿 machopo 的 GC 和 V8 自己的 GC 比：一般的物件（N 條邊加資料，和以前在 cppgc 上的一樣大），每回合建 80 組、一組 128 個，一個一個配置、每個馬上從前面的連上（不會有剛配置、還沒連上的物件被收）；chain 的 N 是 1、tree 是 2（二元樹）、graph 是 4（先連成鏈，另外三條隨機指向同一組的物件）；high 留下 90% 的組、low 留下 5%（接到上一個留下的組的最後一個物件，其他的組馬上變成垃圾）。同樣的模式在新的 GC 和 v8（V8 自己的 heap，同樣的物件寫成 JS 的 class，`crates/gc_bench/src/patterns.js`）上跑；Rust 和 JS 用同一個亂數產生器和種子，選的組和邊都一樣，留下的物件數也一樣。v8-single 是 v8 加上 `--single-threaded-gc`（scavenge 不平行，但那一個 task 還是可能在 worker 上跑，main thread 在等）。每個工作在新的 heap 上、各自一個 process；DOM 的工作只跑新的 GC。**新的 GC（elise）的 heap 是 gc 和 gc-parallel**：工作和模式用 elise 的 API 寫（`gc_bench` 的 `gc_heap`，節點和物件和以前在 cppgc 上的一樣大、一樣多條邊），一個回合是一個操作（`Heap::mutate`），GC 在操作開始的安全點；gc 只在 heap 的 thread 上 mark，gc-parallel 用核心數減 1 個 worker。它的 GC 的階段經過 platform 的掛點進 trace（`Gc.Pause` 裡面是 `Gc.Mark`（裡面有清 weak 和 id 表的 `Gc.Weak`）、`Gc.Sweep`、`Gc.Finalize`；concurrent marking 的開始是裡面有 `Gc.MarkStart` 的 `Gc.Pause`，收尾是裡面有 `Gc.Mark` 而沒有 `Gc.Scavenge` 的：只在一個 thread 上的 full GC 先 scavenge），`gc_bench` 的報告另外帶它自己的強制 GC 的紀錄（`gc`），`bench.py gc` 拿它和 trace 對帳：標到的 bytes 要等於留下的、marking 的時間和 `Gc.Mark` 差不到 20 µs，對不上時停下。回合之間跑 platform 的 task，像 event loop；什麼時候收由 GC 自己決定，最後再強制一次完整的 GC。報告（`target/bench/gc/gc.md` 和 `gc.json`）從 trace 讀 main thread 上、回合期間的 GC：時間和佔的比例，分成 marking、atomic、young（V8 的 scavenge）、sweeping，停頓的次數、中位數、p95 和最長（相隔不到 10 µs `(baseline)`，報告開頭寫出它的版本和日期：cppgc 的 heap（standalone、isolate）已經拿掉，和它們比只能用存下的報告（當時照釘住的 V8 跑；時間跨兩次執行比雜訊大一點，peak used 每次一樣）。**存下的 isolate 的列：那個 heap 在沒有 JS 配置時很少收**：V8 照自己的 heap 決定什麼時候 GC，replace **Linux 和 Windows 上兩個工具（Speedometer 和 Blink 的 perf tests）把兩個瀏覽器都綁在最快的那組 CPU 上**（`common.py` 的 `browser_cpus`；報告寫出是哪些）：Linux 上是最高時脈最高的那些，用 `taskset` 啟動；Windows 上是 `GetSystemCpuSetInformation` 的 efficiency class 最高的那些（Intel 的 P-core），沒有 `taskset`，工具在啟動瀏覽器（或包著 machopo 的取樣器）的那一刻把自己的 affinity 設成它們、啟動完設回去。兩者的子 process 都繼承（Chrome 由 broker 建立的 GPU process、renderer 也是）。有大小核的 CPU（AMD 的 Zen 5 和 Zen 5c、Intel 的 P-core 和 E-core）上，一個瀏覽器整頁落在大核或小核上，數字差上小核的時脈那麼多（2026-10-20 在 Ryzen AI 9 HX 370 上約 1.5 倍），兩個瀏覽器各自落，倍數也跟著跳；綁在同一組之後，兩次的倍數多數差在 16% 以內。Windows 上不綁時落在 E-core 上更常見：2026-10-20 在 i9-13900K 上，Blink 的 perf tests 的預設清單不綁時兩個瀏覽器的數值常常只有綁的時候的四成，一頁的倍數兩次差到 2.2 倍，綁了之後兩次差的中位數 3%、最多 23%。每顆核心一樣快的機器等於沒綁。macOS 照 thread 的 QoS 排，不能綁（Apple Silicon 的 P-core 和 E-core 照樣是雜訊）。沒綁時量的數字（Linux 和 Windows 上 2026-10-20 之前的），不能直接和之後的比。

**Windows 上的 Chrome 有時整段時間都變慢，量完先對照 Chrome 的數字**：2026-10-23 在 i9-13900K 上，早上的 Speedometer 比較表裡 Chrome 每個 suite 都慢（中位數合計 838.4 ms，同一天下午重量 543.6 ms；輕的 suite 慢兩倍多，同步和非同步的時間一起慢），同一次量的 machopo 和下午差不多，比值因此看起來只有一半；同時的 `--profile` 也一樣。下午另有兩次 Chrome 停在一個 suite 裡、幾乎不用 CPU。原因沒找到（Chrome 的版本和綁的 CPU 都沒變）。所以 Chrome 的版本沒換時，它的數字應該和前一次相近，差很多就重量，不要拿那次的比值下結論。卡住的瀏覽器到頁面的期限（30 秒加每個 iteration 10 秒）就放棄那個 suite。

**和 Speedometer 的網頁版**（瀏覽器的視窗裡開它的 `index.html`，20 個 suite 輪流在同一頁跑）**的分數對得上**：2026-10-23 Chrome 的每個 suite 和工具量的差在 5% 以內，headless 和真的視窗一樣。machopo 在真的視窗裡慢約一成，主要是 canvas：工具的 headless machopo 的 devicePixelRatio 是 1，真的視窗是螢幕的縮放（150% 時 1.5），chart.js 照它放大 canvas，machopo 在 CPU 上畫 2.25 倍的像素（Charts-chartjs 122 對 207 ms）。

量之前可以降低機器的雜訊（要 root、只對那台機器有效，所以不在工具裡）：Linux 上 CPU 的 governor 設成 `performance`（`cpupower frequency-set -g performance`）、關掉 turbo（Intel 的 `/sys/devices/system/cpu/intel_pstate/no_turbo`，AMD 的 `/sys/devices/system/cpu/cpufreq/boost`）、關掉其他的程式，量完改回來。

理由：machopo 現在比 Chrome 慢好幾倍，一般改動帶來的幾 % 看不太出來；要比出差別得兩邊輪流量好幾輪，一次就是幾十分鐘、要接電源，例行地量，花的時間多過它帶來的資訊。變慢在下一次量的時候才看得出來，那時用 git 二分找出是哪一個 commit（只量 machopo 的 `--browser machopo --suites …` 一次約 5 分鐘）。數字不在 CI 上量：機器不同，不能和開發機的比。
