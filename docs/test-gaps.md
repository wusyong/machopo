# 測試守不住的地方

測試的種類和跑法、mutation test 的做法在 `testing.md`；這份是它們守不住的部分。

正確性沒有自動測試守住的地方都集中在這裡：只靠審查的、只做過手動確認的、缺少的工具，以及能補但還沒補的測試空缺；另外是沒有計數守著、拿掉了只會變慢的優化。只放**目前仍然成立**的，解決了就刪掉；某次工作當時發生了什麼，記在那份 RFC 的 `progress.md`。

## 沒有計數守著的優化

下面這些捷徑被拿掉時結果照樣對（debug build 的交叉檢查只比結果），只是多做事，沒有測試會失敗。2026-10-20 逐項讀過測試盤點：其他的優化（style 的 invalidation、MPC、祖先的 Bloom filter、增量的 pre-paint 和 paint、raster invalidation、tile 的跳過、root 的計數、parse 的 fast path……）都有 debug build 的計數（各 crate 的 `*_for_testing`、`layout` 的 `BoxTreeUpdate` 和 `LayoutUpdate`）和斷言它的測試。改到這些地方時特別注意；量到變慢時（Speedometer 用 git 二分，`--sample` 看多出來的函式）先對照這份。之後照下面的順序補計數，補了就從這裡刪掉。

- **影響大的**（當時量到幾 % 到幾十 %）：
  - `dom_js` 每次操作之後看 DOM 的 heap 長了多少，用 `Dom::counted_bytes`（elise 的 `Heap::counted_bytes`，一次讀完），要報給 V8 時才用 `used_bytes`（扣掉每一級 cursor 還沒用的尾巴，走過 51 個 cursor）：每次都用 `used_bytes` 時結果一樣，每個會回報的成員多約 510 條指令（2026-11-08 `bench.py calls` 量到：`getAttribute` 700 → 1213）。要守的話數 `used_bytes` 算尾巴的次數，`calls` 的迴圈裡應該只在回報時有。
  - rusty_v8 的 fork 的 callback 回傳值寫整格（`src/function.rs` 的 `set_internal`，relaxed 的 `AtomicUsize` store）：換回一般的寫入時值一樣（debug build 的交叉檢查只比值），但 LLVM 把它縮成 32 bits 的 store，builtin 接著讀整格，store forwarding 失敗（x86-64 上空的 getter 5.4 ns 裡的 2.3 ns）。現在靠 `bench.py calls` 的 store forwarding 衝突數（每次呼叫的方括號）和審查；`cargo test` 沒有 `perf`。要數：新的 binding 的 callback 在 `bench.py calls` 裡每次呼叫的衝突數是 0，或在有 `perf` 的機器上把它寫成測試。
  - DOM 的 `createElement` 用 front 預測時查到的名稱編號直接建元素（`dom_api` 的 `document::create_element`，HTML 文件裡小寫、沒有 `-` 的名稱）：不用時照樣轉小寫、intern（連 HTML 的命名空間字串一起查），結果一樣。預測本身由 `dom_js` 的 `wrappers_wasted` 計數守著（`wrappers::create_element_foresees_its_wrapper`），省掉的 intern 沒有計數。現在靠 `bench.py calls` 的 `createElement`（2026-11-04：2231 條指令，不用時約多 300）。要數：`names::intern` 查表的次數。
  - style 走訪帶下來的狀態（`style`）：`dom` 的 `forget_removed` 只看這次走訪遇到的被移除的根、`rendered` 和 `moved` 跟著走訪往下帶、不為每個元素往上走祖先。要數：每次 recalc 檢查的 `removed` 項數、往上走祖先的步數。
  - cascade 的浪費（`computed_style`、`style_resolver`）：initial style 只建一次（`thread_local`）、CSS-wide keyword 不 clone 整個 style、cascade 只走有勝出宣告的 longhand（`Declared`：改成走全部的 longhand 結果一樣，只是每個元素多跑三趟兩百多格；2026-10-21 量到 blink-perf 的 `CustomProperties*Inheritance` 差 10% 左右）。要數：`ComputedStyle::initial()` 建了幾次、整個 style 被 clone 幾次。
  - 文字（`layout` 的 `text.rs`、parley fork）：選字型記住的第一個字型（`first_font`）、`TextSource::clusters` 從上一次的位置往後找。要數：完整的字型 query、退回二分搜尋的次數。
- **DOM 的 binding 不讓結果經過記下再讀回**（`dom_js` 的 `front.rs`、`dom` 的 `DomString`）：已經是 V8 的結果（wrapper、快取裡的字串、不用配置的值）在操作裡就寫進 return value，只把要配置的記下；`DomString` 的旗標是一整格，不是 `bool`。改回全部記下、`finish` 一次讀出整個結果，或改回 `bool`，值一樣，只是分段寫、整格讀的 store forwarding 衝突回來（`firstChild` 每次呼叫 0.24 → 1.6，`getAttribute` 4.5 → 6.3）。現在靠 `bench.py calls` 的方括號和審查；要守的話在 CI 上跑 `bench.py calls` 比門檻（只在有那個事件的 CPU 上）。同一類的 `[NewObject]` 先建 wrapper（不經過 root 和第二次操作）、字串結果先查快取（`peek`，不 clone `DomString`）、名稱表記住元素的 `nodeName`（`names::node_name`，拿掉時 `intern` 照樣找到同一個，只是每次重組、轉大寫、查表）拿掉時結果也一樣，只是多做事：要數 root 的建立次數（`createElement` 應該是 0）和重組 `nodeName` 的次數。字串結果借出、不 clone 有測試（`dom_api` 的參照數）。
- **DOM 的 binding 檢查型別和找 interface 不走表、少做的配置**（`dom_api` 的 `declare::ACCEPTED`、`NODE_INTERFACES`，`dom` 的 `names::TEMPLATE`，`dom_js` 的 `V8Front::callback`，和 `create_element_named`、V8 的 front 的 `has_args`、`ret_new_node` 的 `#[inline]`）：interface 接受哪些節點種類、節點的 wrapper 是哪個 interface 在編譯時算好（兩張表和逐一走 interface、parent 的定義一樣有測試），建元素時「是不是 template」比名稱的編號，一次呼叫的 callback 存在一格裡、不是每次建再丟掉的 `Vec`，幾個熱的小函式標了 inline。改回逐一走、比字串、用 `Vec`、拿掉 inline 時結果都一樣，只是變慢：第 2 段一路加上去時 `appendChild` 從 1111 個指令到 1269、`createElement` 從 2285 到 2377、`addEventListener` 多 145，改了之後是 1074、2312、926。現在靠 `bench.py calls` 和審查；要守的話在 CI 上跑 `bench.py calls` 比門檻。
- **DOM 的 V8 front 和分派的程式碼形狀**（`dom_js` 的 `Kept` 放在 `Option<Box<…>>` 裡（沒有結果要留時 drop 只檢查一個 null）、要留的結果交給 cold 的 `keep` 配置（回傳 primitive 的 setter 因此 inline）、`throw` cold、`V8Op` 只借 `Call` 和 `Caches` 兩個指標（不把操作前取得的東西逐個複製進來）、`finish` 只 inline「有沒有留結果」的判斷、`this_as` 一定 inline、listener 的例外交給 cold 的 `report_caught`、沒有 wrapper 的節點交給 cold 的 `keep_node`，`dom_api` 的 `invoke` 把 listener 的迴圈放進不 inline 的 `invoke_listeners`、分派只在走到有 window 的 document 時才比 `load`）：都是為了讓每次呼叫、path 上每個節點少存幾個暫存器、少比一次字串，結果不變。`Kept` 的 drop 迴圈被 inline 時每個成員多 13 個指令，`Kept` 不放在 box 裡時每次呼叫都呼叫一次它的 drop glue、`ret_u32` 裡有 `Box::new` 時不 inline（`nodeType` 151 → 184 條指令），`V8Op` 逐個複製操作前取得的東西時 `firstChild` 多約 20 條、`createElement` 的頁慢 14%（`prepared` 分段寫、整塊讀），`finish` 沒拆開時多約 20，`this_as` 有了 V8 檢查過的 receiver 和其他的兩條路之後 LLVM 把它留在外面，`firstChild` 多 15 條、`appendChild` 38 條，`invoke` 變大時事件頁上每次分派多約 130 ns。overload 的形式的 callback 的位址只對 overload 取（`templates.rs` 的 `CollectOverloads` 在編譯時用 `declare::is_overload` 判斷）：每個成員都被取位址時，callback 不再 inline 進 V8 的 trampoline，`getAttribute`、`setAttribute`、`createElement` 各多約 22 條指令、`appendChild` 16 條。改回去時測試都過，只是變慢；現在靠 `bench.py calls`、`blink-perf` 和審查，要守的話同上一條。
- **DOM 的名稱不查表、binding 的固定成本**（`dom` 的 `Names::find`、`attribute_value_by_id`，`bindings` 的 isolate 的狀態（state callback 讀 slot 不檢查）和 `on_thread`，rusty_v8 的 fork 的 `v8::machopo::unwrap` 和 `ReturnValue::set_global`）：空字串直接是 `NONE`、`id` 和 `className` 照固定的編號找屬性、狀態和型別在同一個 box、成員的 callback 讀狀態不比型別（`isolate_state::unchecked`：一次 load 和一個加法，debug build 照樣比）、目前的 thread 的 `ThreadId` 存在 thread-local、API wrapper 在 Rust 裡 unwrap、名稱的 V8 字串從 `Global` 直接寫進回傳值。拿掉任何一個結果都一樣（fork 的兩個 debug build 每次和 V8 的比對，只比結果），只是變慢：最大的是空字串，查表時用長度 0 呼叫 `memcmp`，glibc 的 AVX-512 版在 AMD Zen 5 上每次幾百 cycles（`n.id` 404 → 84 cycles，`createElement` 840 → 536）。現在靠 `bench.py calls`、`bench.py blink-perf` 和審查；要守的話數 `Names` 查表的次數（`id`、`className`、建元素時是 0），其他的只能量。名稱的 V8 字串只做一次有計數（`dom_js::names_made`）守著。
- **DOM 的名稱表的查詢路徑**（`dom` 的 `names.rs`、`name_hash.rs`）：固定的名稱用編譯時產生的 perfect hash，hash 是 8 bytes 一步的 FxHash 加 murmur3 的收尾（不用 `phf` 的 SipHash），最後不滿 8 bytes 的部分用重疊的整塊讀取（不經過 `memcpy`），找到的名稱用同樣的整塊讀取比對（不呼叫 `bcmp`）；thread-local 的表用 `const` 初始化（每次存取不檢查第一次使用）；照名稱找屬性先查成編號再比整數，只有帶前綴的屬性才拆名稱；固定的 local name 轉大寫的 `nodeName` 讀編譯時的陣列（`UPPERCASE`），不經過表（拿掉時照樣從表裡組出同一個固定的編號，mutation test 抓不到，`tagName` 的頁慢約 14%）。改回去時結果一樣，只是變慢：用 `phf` 時 JS 的 `createElement` 每次多約 250 條指令、cycles 多 15%；用 `copy_from_slice` 接最後幾個 byte 時 `memcpy` 分段寫、整個 word 讀的 store forwarding 衝突佔了 `getAttribute` 那一頁 `find_fixed` 的 70%。現在靠 `bench.py calls` 和審查；perfect hash 的正確性有測試（每個固定的名稱找得回自己、差一個 byte 或長短不同的找不到）。要守的話數 `find_fixed` 的指令數（`perf stat` 的門檻，只在 CI 的固定機器上）。
- **DOM 的字串參數讀 V8 自己的字元、`hasAttribute` 不 clone 值**（`dom_js` 的 `ArgString`、`bindings` 的 `LentString`、rusty_v8 的 fork 的 `one_byte_chars`，`dom_api` 的 `has_attribute`）：平的 one-byte ASCII 參數不複製、不經過 `ValueView`；`hasAttribute` 看值在不在，不 clone 出一個 `DomString`。改成每個參數都複製（或都經過 `ValueView`）、`hasAttribute` 改回 `get_attribute(...).is_some()`，結果一樣（借出的那條 fork 的讀法 debug build 和 `ValueView` 比對，只比結果），只是變慢：`ValueView` 一個參數約 540 條指令，clone 是兩次 atomic 的加減（`hasAttribute('id')` 217 → 141 cycles）。現在靠 `bench.py calls` 和審查；要守的話數參數走了哪一條路（借出的次數，`bindings::borrowed_texts` 在操作裡看得到）。
- **DOM 的 getter 從 handle 直接寫回傳值**（`bindings::return_wrapper`、`NoGc::return_weak`（`dom_js` 的 `StringCache::find`），fork 的 `ReturnValue::set_traced`、`set_weak`）：節點的 wrapper 從節點的 `TracedReference`、快取的屬性值從 weak handle 的那一格讀出來寫進回傳值，不建 `Local`。拿掉（一律回 `false`）結果一樣：操作後的 `finish` 照樣找到同一個 wrapper、同一個快取的字串（fork 的讀法 debug build 和 V8 的 setter 比對，只比結果），只是多一次 C++ 呼叫（`parentNode` 約 50 → 58 cycles）。現在靠 `bench.py calls` 和審查；要守的話數 `finish` 拿已經有的 wrapper 或字串的次數（應該是 0）。
- **DOM 的 V8 狀態裡，frame 的 layout 的 cell 放在自己的 box 裡**（`dom_js` 的 `State::layout`）：放回 `State` 裡（每次呼叫寫的欄位旁邊），結果一樣，只是每個拿到它的位址的操作變慢（`setAttribute` 248 → 332 cycles，指令數一樣），沒有操作碰它。現在靠 `bench.py calls` 的 cycles 和審查；要守的話在 CI 的固定機器上比 `setAttribute` 的 cycles 的門檻。
- **DOM 的 V8 front 讀 dictionary 的字串的函式是 cold**（`dom_js` 的 `V8Front::dict_string`，只有 `KeyboardEvent` 的建構子用）：拿掉 `#[cold]` 結果一樣，只是它放在熱的呼叫之間時 `appendChild` 205 → 275、`dispatchEvent` 698 → 793 cycles（指令數一樣）。現在靠 `bench.py calls` 的 cycles 和審查；要守的話同上面 layout 的 cell 那一條。
- **DOM 沒有 mutation observer 時少做的事**（`dom`）：DOM 記著有沒有觀察過任何東西（`observed`），沒有時改樹、改屬性、改文字都不找 registration、不收集節點；`textContent` 的 setter 沒有 observer 時直接 link 新的 text（有的時候才走 replace all，一個 record）；節點的 `HAS_OBSERVERS` bit 讓找 registration 時跳過沒有的祖先。拿掉任何一個結果都一樣（有 observer 的情況都有測試），只是每次改 DOM 多做事：`textContent` 的 setter 走 replace all 時 `calls/text-content` 慢 3% 到 5%。現在靠 `blink-perf` 和審查；要守的話數找 registration 和建節點清單的次數（沒有 observer 時是 0）。
- **DOM 在第一個 form 之前插入和移除不看 form owner**（`dom` 的 `FormState::seen`，`form_inserted`、`form_removed`）：第一個 `<form>` 建立、第一次有 `form` 屬性、parser 第一次關聯之前，插入和移除只讀一個旗標，不走子樹找 listed element。拿掉判斷結果一樣（沒有 form 時沒有元素有 owner；設旗標的三處有測試：不設就沒有 owner），只是每次插入和移除多走一次子樹。現在靠 `bench.py calls` 和審查；要守的話數 form owner 的子樹走了幾次。同一個旗標的另外兩個 bit（第一個 `<fieldset>`、第一個 radio 之前插入和移除不看 disabled 的狀態、radio group）、radio 的 group 改了時 document 的 style 沒有 `:indeterminate` 就不走樹（`dom` 的 `radio_groups_changed`），checkedness 和 `indeterminate` 沒變時不記給 style（`set_checked_bit`、`set_indeterminate_bit`）、和第一個 `<fieldset>` 之前不記祖先的 disabled 狀態（`ancestor_disabled` 直接回答 enabled）也一樣：拿掉判斷結果不變，只是多走、多配置。
- **DOM 改屬性時只看一個 bit 的兩處**（`dom` 的 `attribute_changed`）：`HAS_INLINE_STYLE`（元素有 `style` 的宣告時才比名稱是不是 `style`）和 `HAS_ID`（插入、移除時只看加過 `id` 的元素）。拿掉 bit 的判斷結果一樣（`HAS_ID` 的「不設」有測試：設了才找得到），只是每次改屬性多一次名稱的比較、每個插入的元素多看一次屬性：第一版沒有這些時，`set-class-name` 慢 11%、`appendChild` 多 143 條指令。現在靠 `bench.py calls`、`blink-perf` 和審查；要守的話數改屬性時比名稱的次數。
- **DOM 的 selector 查詢的 fast path 和快取**（`style` 的 `SelectorQuery`）：只有一個 class 或 tag 的 selector 直接比名稱的編號，不經過 `selectors` 的完整比對；只有一個 id、root 是 document 的 `querySelector` 用 document 的 id 表；解析過的 selector 每個 thread 留著（256 個）。拿掉任何一個結果都一樣（每一種的大小寫、quirks mode、root 不算有測試），只是變慢。id 表本身的「不走樹」和「記住第一個」有計數（`dom::id_walks`）守著，`querySelector` 經不經過它沒有。現在靠審查；要守的話數完整比對和解析的次數（舊的 `style` 的 `QUERY_MATCHERS`、`QUERY_PARSES` 的做法），量到 `querySelector` 的頁時一起加。
- **V8 的 scavenge 在平行的 thread 上重設 DOM 的節點對 wrapper 的參照**（`bindings` 的 `Roots::try_reset_root`，glue 的 `TryResetRoot`）：一律回 false 結果一樣（V8 改在 main thread 上一個一個呼叫 `ResetRoot`），只是變慢（`bindings/gc-tree` 的 scavenge 裡約 157 ms 在 main thread 上依序做，Chrome 幾乎都在平行的階段）。`many_dropped_wrappers_are_made_again` 守住平行的那條路走得到、重設得對（回報重設了卻沒做的 mutant 抓得到），沒守住它有沒有被用到。要數的話數平行重設的次數（V8 的 trace 裡 `SCAVENGER_TRACED_HANDLES_RESET_PARALLEL` 以外、`WEAK_GLOBAL_HANDLES_PROCESS` 自己的時間應該接近 0）。
- **能用計數守的其他捷徑**：renderer 的 display list 沒換時不換 root layer、`rendered_version`；paint 沿用的 item 共用 glyph（`Arc`）；raster thread 重複用的 tile buffer（`TILE_PIXELS`）。
- **只守住一部分**：wheel listener 的 region 和被蓋住的 scroller 的矩形（`paint` 的 `hit_test`：沒有數看了幾個 chunk、比了幾個矩形）、composited scroller 不走第二次 pre-paint（只數主要那一次）。
- **`gc_bench` 的工作從 site 配置**（`gc_heap` 的節點和配置模式的物件各一個 `Site`）：改回 `alloc`（沒有 site）結果一樣，只是存活率高的工作不會 pretenure，GC 時間回到每個物件複製兩次的樣子；小的測試工作 nursery 長不到 8 MiB，本來就不 tenure。要數：報告的 pretenured 物件數，在一個長得到 8 MiB 的工作上。
- **很難用計數守的**：`NodeId` 等的表用 FxHash（換回 std 的 hasher 結果和次數都一樣；之後可以在 `sanity.py` 擋掉用 std hasher 的 `HashMap<NodeId, …>`）、cppgc 的讀取在 Rust 裡 inline（debug build 本來就呼叫 C++ 比對；靠審查）、少配置一次的（cascade 的暫時配置在 stack 上、invalidation 查表不配置字串、parse 的 scan 只記位置；要在測試裡換一個會數配置的 allocator）。
- 下一節「等價、不用處理的 mutation」的「只會變慢或多用記憶體」那些（祖先的 dirty flag 停在已經標過的、`InlineContent` 記住斷行和寬度、`has_important`……）也一樣：前兩個和 `has_important` 在已有的計數上多數一項就能守。

- **DOM 的 style 比名稱的編號**（`style` 的 `rule_index.rs` 建 index 時替 selector 的名稱編號（`css::IdentAtom`），`selector.rs` 讀它；`bloom.rs` 走樹時 push、回來時 pop）：selector 的名稱沒編號時比對改用 `names::find` 查表，結果一樣，只是每次比對多一次 hash；bloom filter 少 pop 時只是多留幾個 hash，候選的 selector 照樣完整比對。現在靠審查（還沒量）；要守的話數 `names::find` 在比對裡被叫的次數（應該是 0）。

- **DOM 的 slot 的分配在 style 之前一次算完**（`dom` 的 `recalc_slot_assignments`、`assignment_stale` 的清單，`style` 的 `recalc_style` 一開始呼叫）：不登記、每次都登記、算完不拿掉、不算、style 前不呼叫，結果都一樣：flat tree 的走法看到分配過期時照名稱找（`slot_flat_children` 的 `Found`），只是一個 host 有 n 個子節點、m 個 slot 時多 n×m 次比較。之後有數 slot 的重算次數的方法時，用「一個 frame 一個 shadow root 重算一次、走的時候不照名稱找」守住。

- **DOM 的 `<use>` 和 SVG 資源沒有變動時不做的事**（`dom` 的 `svg_use.rs`，`layout` 的 `tree_builder.rs` 的 `update_svg_clients`）：第一個 `<use>` 建立之前插入、移除、改屬性只讀一個旗標；`update_use_trees` 在沒有 `<use>` 要重建、沒有 id 變動時不走清單，有 id 變動時才重查每個 `<use>` 查過的 id；layout 只在走訪看到 `<svg>` 裡的變動或子節點的變動時才重查 box 查過的 id。拿掉任何一個結果都一樣，只是每次改樹、每個 frame 多走一次清單或多查一次 id（重建和重抓有守：copy 是不是同一個節點、`BoxTreeUpdate::svg_captured`）。要數：`update_use_trees` 看了幾個 `<use>`、layout 重查了幾個 id。

- **DevTools 沒有打開 `Network`、不要 stack 時，請求和 stack 什麼都不看**（`renderer` 的 `render_thread/documents.rs` 的 `send_request_with_initiator`、`keep_parser_lines`，`dom` 的 `initiator.rs` 的 `notes_askers`）：拿掉 `NetworkAgent::enabled` 的判斷時，發起者照樣算出來再丟掉（agent 沒有 session 什麼都不送），parser 的行號一直留著；拿掉「要不要 stack」的判斷時 DOM 每次載入都記下元素、engine 每次操作都抓 stack。結果一樣，只是多做事（抓 stack 一次幾十 µs）。`dom` 的 `initiators.rs` 守著「不要時 `Microtasks::stacks` 不設」，renderer 那兩處沒有計數。最後一個要 stack 的 session 離開時告訴 DOM 不再要（`render_thread/devtools.rs` 的 `devtools_detach` 的 `update_stacks_wanted`）也一樣：拿掉時 DOM 照樣記、engine 照樣抓，每輪清掉，沒有測試失敗（mutation test 確認過）。要守的話數 `initiator` 的呼叫次數和 engine 抓 stack 的次數。
- **DevTools 沒有強制 pseudo-class 時，match 和移除只讀一個旗標**（`dom` 的 `probe.rs` 的 `ForcedStates::any`，`style` 的 `match_non_ts_pseudo_class`、`dom` 的 `removed_connected`）：旗標一律是 true 時結果一樣（找表都找不到），只是每個 pseudo-class 的 match 和每個移除的元素多找一次表。要數：沒有強制時找表的次數。
- **rendering update 的文件只找一次**（`renderer` 的 `begin_main_frame` 呼叫 `ScriptEngine::begin_rendering_update`，之後每一步用它找到的文件）：不呼叫時每一步各自走 frame tree 的文件找 iframe（一個 frame 五、六次），結果一樣。engine 這一側有計數（`dom_api::frame_tree_walks_for_testing`，`dom_js` 的 `frames::a_rendering_update_walks_the_frame_tree_once`、`the_hosts_loop_walks_no_frame_tree`）；renderer 的呼叫在 renderer 的 thread 上，`shell` 的測試數不到它的計數。現在靠取樣（`documents_in_tree_order`、`child_content_documents`）和審查。
- **給 V8 的、Chrome 的 renderer 也給的 JIT 和 IC 的 flag**（`bindings` 的 `platform.rs` 的 `CHROME_FLAGS`：`--sparkplug-plus` 等四項）：拿掉時 JS 的結果一樣，Sparkplug 改走通用的 IC 和比較的 builtin（Speedometer 的 JS 那一類多約 11 ms）。V8 的 flag 從 rusty_v8 讀不到，JS 也看不出 Sparkplug 呼叫哪個 builtin。現在靠 machopo 的 log（`V8 initialized` 那一行列出 flag）和取樣（`LoadICGenericBaseline`、`*_Generic_Baseline` 在 JS 那一類裡的時間）。要守的話：fork 加讀 flag 的值的 API，測試斷言它是開的；或在有 `perf` 的機器上跑一段只在 Sparkplug 的迴圈，斷言 `LoadICGenericBaseline` 不在前幾名。
- **`innerHTML` 的 fast path 建元素時省掉的查找**（`dom` 的 `create_html_element_with_attributes`）：名稱用編號建（不從字串 intern，HTML 的命名空間字串也不查）、屬性不先找同名的、屬性的清單一次配到它的大小。改回 `create_element` 加一個一個 `set_attribute_ns` 時結果一樣（`dom` 的 `attributes::an_element_made_with_its_attributes_is_one_given_them_one_by_one` 比兩種的結果），只是多查表、多配置。input 照它的型別建有計數（`dom::input_type_changes_for_testing`），值只解碼一次也有（`html::decodes_for_testing`）。現在靠取樣（`fast_path_build::build` 底下的 `names::intern`、`attribute_ns`）和審查。要數：`names::intern` 查表的次數（和 `createElement` 的那條一起補）。
- **DOM 在第一個 `<iframe>` 建立之前不看 iframe**（`dom` 的 `frame.rs` 的 `has_seen_iframes`，插入和移除的走訪的 `has_seen_connection_steps`、`has_seen_removal_steps` 也算可能在插入時跑的 script 元素、`<base>`）：插入、移除的走訪和改屬性只讀一個旗標。拿掉判斷結果一樣（不是 iframe 的元素什麼都不記），只是每個走到的節點多比一次名稱。要守的話數 `connection_steps`、`frame_owner_removed` 的呼叫次數。
- **DOM 只在 commit 的 pre-paint 變了時重找指標底下的東西**（`renderer` 的 `render_thread/documents.rs` 的 `recompute_under_mouse`：比 top-level view 的 document 和 `pre_paints()`，指標還沒到過頁面上、有 move 等著時也不做）：拿掉這些判斷，每個 commit 都多一次 hit test 和 hover 的更新，事件和游標照樣對（底下的東西沒變時不發 boundary event，`SetCursor` 只在變了時送）。要守的話數 `EventHandler::recompute_under_mouse` 的次數（或它的 hit test），在不改 layout 的 frame 上斷言是 0。
- **DOM 的 Selection API 在 editing host 已經有 focus 時不出操作**（`dom_api` 的 `selection.rs` 的 `focus_host` 先看 host 是不是已經有 focus）：拿掉時結果一樣（focusing steps 對已經有 focus 的元素什麼都不做），只是在有 focus 的 editing host 裡每次 `collapse`、`setBaseAndExtent` 這些都出操作，多兩三個操作、兩個 `Persistent` 和一次 layout。要數：`#[then_script]` 的成員交回要做的事的次數（host 有 focus 時的 `collapse` 應該是 0）；`bench.py calls` 的文件沒有 window、沒有選取，量不到。
- **離 tile 太遠的 glyph 不交給 Vello**（`raster` 的 `vello_backend.rs` 的 `draw_glyphs`）：拿掉時畫出來一樣（Vello 自己會裁掉），文字多的頁面每個 tile 都把整段文字的外框線攤平一次。測試只看得到「該畫的有畫」（`a_glyph_that_begins_outside_is_drawn`）。要守的話在 playback 加一個測試讀得到的計數：交給 Vello 的 glyph 數。
- **一輪的 tile 上傳完之後送一次 queue**（`viz` 的 `GpuSharedImages::flush`）：拿掉裡面的 submit 時畫面一樣（下一次畫 frame 的 submit 會把寫入帶出去），只是視窗被遮住、不畫 frame 的期間，上傳的像素在 wgpu 的 staging 裡堆積。compositor 這一側「全部建完才呼叫一次」有測試（`shared_images_are_flushed_once_all_of_a_frames_are_made`）；Viz 這一側有沒有真的 submit 看不到。要守的話要 wgpu 給出還沒送出的寫入有多少。


## 等價、不用處理的 mutation

弄壞之後行為完全一樣，記在這裡免得重複追查。

**只會變慢或多用記憶體（拿掉的是效能或記憶體的捷徑，結果一樣）**

- `layout` 的表格的 `colspan` 不夾到 1000（`table::span`）：沒有 cell 開始的欄被併掉、沒有自己的 spacing，排版一樣，只是多算幾千個空的欄；照 HTML 和 Blink 的上限留著（`rowspan` 的 0 有測試）。
- DOM 的 style 把 author 的 rule 排在 UA 的之後（`style` 的 `Walk::cascade` 的 `first`）：UA 和 author 是不同的 origin，cascade 先比 origin，同一個 origin 裡的順序才看這個數，拿掉時結果一樣。
- DOM 的 presentational hints 的 digest（`style` 的 `hints::digest`）都給同一個數：它只是 matched properties cache 的 hash，cache 找到的那一項再照值比 hint 的 declaration（`MatchedPropertiesCache::matches`），所以只會多碰撞、變慢，結果一樣。
- DOM 的 style 的 invalidation set 把 part（`::part()`，DOM 還沒有）和其他跨 tree scope 的 combinator 當成 set 說不出的（`style` 的 `FeatureSets::add_selector` 的 `plain`）：`:host()`、`::slotted()` 的 combinator 是 pseudo-element 的，本來就算一般的（有測試守著重算的元素），剩下的 combinator DOM 的 selector 都沒有，拿掉這個條件結果一樣；有 `::part()` 時要有測試守住。
- DOM 的 `setHTMLUnsafe` 不走 fragment 的 fast path（`html` 的 `parse_fragment_with`）：走也一樣，fast path 只認得一組固定的標籤、沒有 `template`，碰到 `<template shadowrootmode>` 就交回 tree builder；略過它只是少試一次。fast path 之後認得 `template` 時，這條會變成真的要守的。
- DOM 的 parser 請 engine 建構 custom element 之後，invoke 建構的 element queue（`dom_js` 的 `create_custom_element`）：不 invoke 也一樣，parser 建構完就插入，插入的 element queue 會跑同一個元素的佇列裡剩下的（屬性的 `attributeChangedCallback`），只是建構的那個 queue 留在 DOM 裡沒拿走。建構和插入分開的路（之後有的話）才看得出來。
- DOM 的 style 的 `Features` 記下選擇器問別的元素的 `:defined`（`style` 的 `rule_index`，像 `:hover`、`:focus` 那幾個）：拿掉也一樣，它只給 debug build 的檢查（`touched_by`：invalidation set 之前的那條路會重算什麼）用，少了它檢查只是變寬；DOM 記不記這個狀態看的是 `StyleNames`（每個選擇器的狀態都算）。
- DOM 只替定義有的 callback 排 reaction（`dom` 的 `enqueue_callback_reaction` 看 `definition_has_callback`）：都排也一樣，engine 呼叫時拿不到那個 callback 的函式就返回，只是多一個 reaction 和一次 engine 的呼叫（規範的「callback 是 null 時不排」也是這樣省工）。要守的話數元素的 reaction。
- DOM 的 `customElements.upgrade` 先挑出 undefined 的元素（`dom` 的 `upgradable_under`）：不挑也一樣，每個 upgrade 自己先看狀態（`dom_api` 的 `custom_elements::upgrade`），不是 undefined 或 uncustomized 的不做，只是多查一次定義。
- DOM 的 custom element 的定義用 strong 的 JS edge 存建構子（`dom_js` 的 front 的 `store_custom_element_definition` 用 `set_strong`）：改成 droppable 的（`set_wrapper`）結果也一樣。V8 的 scavenge 只丟沒改過的 API 物件（FunctionTemplate 建的 wrapper），建構子是一般的函式，永遠不會被丟；major GC 時兩種都在定義活著時標。callback 存的也是函式，一樣。用 strong 是照它的意思（Blink 的 `TraceWrapperV8Reference`），不靠 V8 怎麼判斷可以丟。
- DOM 的 style 在 adopted 的 sheet 變了時，只把上一次收集時 adopt 它的 shadow root 標成 sheet 變了（`style` 的 `ShadowScopes::roots_adopting`）：每一個都標，結果也一樣（沒有 adopt 它的重新收集之後沒有變化，什麼都不重算），只是多收集。要守的話數一次 recalc 收集了幾個 shadow root。
- **DOM 的 binding 的 rejected promise**（`dom_js` 的 front 的 `reject`、`dom_api` 的 `Promise<I>` 的 `RetType::fail`）：回傳 promise 的成員現在只有 `CSSStyleSheet.replace`，它不會失敗，這條路沒有測試走到。有會失敗的成員時（或 receiver 的檢查改成 reject 時）補測試：rejected 的 promise、例外的種類和訊息、不丟出。
- DOM 的 style 比對新舊的 sheet 時，留著的 sheet 的規則不算進變了的（`style` 的 `changed_rules` 的 `changed`）：算進去也一樣，留著的 sheet 兩邊的順序一樣（先檢查過，不一樣就整份重算），它的規則在兩邊的位置相同、互相抵消，只是多做工。
- DOM 的 style 在 sheet 變了時清掉 `MatchedPropertiesCache`、media query 的結果變了時整份重算（`style` 的 `collect_sheets`）：快取的 entry 拿著它的規則（不會有別的規則在同一個位址），不清只是留著舊規則的記憶體；media query 的結果只在 viewport 或 system color 變了時才會變，那時本來就整份重算。分到 slot 的節點的 sibling set 只標在 flat tree 裡的兄弟（`mark_siblings`）：沒分到的節點標了也一樣，它被分到時 slot 整個重算，只是旗標留在它身上。
- DOM 的 style 在一個子節點插入或搬動之後，有 `~` 的 rule 時後面每一個兄弟重算（`style` 的 `Walk::children` 的 `positional`）：父元素的 selector 旗標（比對 sibling combinator 時設的）在它的子節點變了時本來就讓每個子節點重算，拿掉時結果一樣；留著，不依賴旗標每次都設到。
- DOM 的 slot 離開 shadow tree 時清空它分配到的節點的清單（`dom` 的 `slots_changed` 的 `set_assigned(slot, &[])`）：不在 shadow tree 裡的 slot 的 `assigned_nodes` 先看 `is_slot`，回答空的，清單只是少留著參照；它再進 shadow tree 時整個重算。
- DOM 的 `childNodes` 的 index cache（`dom` 的 `lists.rs` 的 `ChildList`）：長度數過之後記著、每次重數、超過長度時不走、不記住最後一個：都只是少走或多走兄弟，結果一樣（它清得對不對有測試守著：插入、移除、`textContent`、clone 之後的長度和項目）。
- DOM 的 `normalize` 跳過已經併進前一個的 text：它已經沒有 parent，下一個兄弟是 none，什麼都不做；`getElementsByClassName` 的 class 名稱去掉重複：每個都要有，重複的只是多比一次。
- DOM 的 `assigned_nodes` 先看 `is_slot`，改成只看在不在 shadow tree 裡：在 shadow tree 裡、不是 slot 的元素沒有 `SlotData`，清單也是空的，只是多重算一次分配。
- DOM 的 intersection observer 在有 observer 追蹤 visibility 時，paint 換了就重算（renderer 的 `compute_intersections` 的狀態裡的 `last_paint`）：拿掉也一樣，DOM 的 frame 只要 restyle 就重新 layout、重新 pre-paint，paint 變了時 pre-paint 的計數已經變了。有只改 paint、不重新 layout 的東西（canvas 畫了新的內容）時這條才要守：照 `shell` 的 `what_covers_a_tracked_target` 寫一個那樣的情況。


- DOM 的 heap 的一步（`dom` 的 `Dom::advance_marking`、`dom_js` 的 `State` 的 `EmbedderHeapState::advance`，一路到 `bindings` 的 `StateHeap`、`Marking::advance`、V8 的 patch 的 `CppHeap::AdvanceMarking`）一律回報做完：V8 的三個呼叫的地方（增量的步驟、停頓裡的閉包、minor GC）都不看 `AdvanceMarking` 的回傳值，能不能收尾只問 `IsMarkingDone`，也就是 heap 的 marker 清空了沒有（`is_done`，有自己的測試）。回傳值之後被 V8 用到時要補測試。

- `--automation-pipe` 的 reader 一次最多讀一則訊息的上限加一個 byte（`automation_pipe` 的 `take(limit)`）：拿掉它照樣讀到 NUL 或輸入結束，照樣因為超過上限而關掉 pipe，只差在太長的訊息先整則讀進記憶體。
- `layout` 的 `InlineContent::new` 不為 `hyphens: none` 的 run shape 連字號（它的 style 在 parley 那裡是不斷行，連字號用不到）。
- style 的 flag 往上標時停在已經標過的祖先（不停只是多走幾步）。
- box tree 標「要重排」時停在已經標過的祖先、`InlineContent` 在同樣的寬度不重新斷行（兩者都只省時間）。
- `layout` 的 `compute_inline` 判斷盒子的寬度是不是由內容決定（`sized_by_content`）時不看 `aspect-ratio`：試過的情況（float、inline-block、flex 和 grid 的子項）裡，有比例的盒子的寬度都由父盒子算好傳進來，走不到這個條件。走到的話行會先在 fit-content 的寬度斷，做 fragment 時發現盒子的寬度不同再斷一次，結果一樣。
- `InlineContent` 記住 min-content 和 max-content 寬度（只省時間）。
- `layout` 的 `InlineContent` 不追蹤開著的行內元素、一律拿 container 的 style 和 run 的比（`push_runs` 的 `enclosing`）：行內元素裡的文字的 style 和那個元素的一樣，多設一次和元素的 span 相同的 text property，排版結果一樣，只多做一點事）。
- `Range` 的文字盒子裡 collapse 的範圍找到之後就停（`layout::text_rects`：一個 text 節點的 run 不重疊地蓋滿它的原文，含有一個點的 run 只有一個，停下只省下走完 fragment tree）。
- `PaintController` 清掉只剩它拿著的 fragment 的紀錄（拿錯只會讓那個 box 重畫，沒清掉只多佔記憶體；要上千個 box 才清，沒有測試）。
- `BrowserView` 關掉分頁時清掉以它為 opener 的紀錄（分頁的 id 只增不減，留下的紀錄不會再被比對到，只是佔一點記憶體）。
- `style_resolver` 的 `cssText` 每個 shorthand 只試一次（`CssPropertyValueSet::css_text` 的 `shorthands_tried`：宣告清單沒變，再試一次結果一樣，合回過的 shorthand 的 longhand 都已經寫過，只省時間）、cascade 跳過沒有 `!important` 的區塊的 important 那一輪（`push_block` 的 `has_important`：那一輪沒有宣告可套用）。
- renderer 的 `request_next_frame_if_dom_changed` 要求之後不記下樹的版本（`rendered_version`；下一次 `update_document_rendering` 照樣記下，之前每一輪多要一次 main frame、多叫一次 `start_loads`，都是重複的）。
- `viz` 的 `gpu_context::instance_with` 給 instance 設平台的 backend（`BACKENDS`）：不設時 instance 多開其他的 backend，列舉 adapter 照樣只取 `BACKENDS` 的，選到的一樣，只多花啟動的時間（Windows 上約 70 ms）；wgpu 沒有問 instance 開了哪些 backend 的 API。
- `shell` 的 `windowless::start` 給 compositor `GpuSharedImages`：不給時 tile 交 CPU 的像素、由 Viz 上傳，畫出來的一樣，只差在哪條 thread 上傳。
- 祖先的 bloom filter 每次從根重建（只變慢）。
- DOM 的節點的「有 listener」旗標（`dom` 的 `Cx::listeners` 開頭的檢查）：拿掉時照樣從節點的種類的資料找 listener，沒有資料或沒有 listener 的一樣是沒有，只是分派時每個沒有 listener 的節點多讀一次資料。
- `dom` 的 `window_named` 在 id 和 name 的表都只有同一個元素、或只有一邊有一個時直接回答它（不經過集合）：拿掉時改成「好幾個」，`dom_api` 建 window 的集合、看到只有一個再回傳它，結果一樣，只多建一個集合。
- 新的 GC 的 scavenge 切 LAB 時，頁剩下的不夠就把頁尾填成空段（`heap/young.rs` 的 `Source::cut`）：LAB 一次 32 KiB、整除一頁，nursery 的物件最大 32 KiB，所以頁尾不會短，這段走不到；留著是為了 LAB 的大小改了時，young 的頁照樣從頭走得到 `top`（verifier 檢查）。

**DOM、bindings 和 script**

- DOM 的 collection 往回走時停在 root（`dom` 的 `collection_previous` 的 `parent` 的條件）：往回走只從快取的元素走到它之前、已經在 collection 裡的元素（或從最後一個走到它），永遠不會走過第一個元素，所以走不到 root 的 parent，拿掉條件結果一樣；它讓這個函式本身照「在 root 之內」的意思，之後有走過第一個元素的呼叫時才看得出來。
- trace 裡 rAF callback 之後的 microtask checkpoint 移到 `FireAnimationFrame` 的 span 外面（`dom_api` 的 `run_animation_frame_callbacks`）：V8 的 engine 在 callback 回來時就跑了 checkpoint（`dom_js` 的 `run_callback`），在 span 裡面，之後這一次已經沒有東西可跑。wasm 的 engine 或不先跑 checkpoint 的 engine 才看得出來。
- DOM 的 idle callback 的 timeout 不看到期了沒有（`dom` 的 `take_due_idle_timeout` 的 `due <= now`）：只有最早的 timeout 到期了才會叫它（`dom_api` 的 `timer::run_next_due` 先問 `next_idle_timeout`），它拿的就是那一個。
- DOM 的 iframe 的步驟不在被 discard 的文件裡建子 browsing context（`dom_api` 的 `frame.rs` 的 `create_child_frame` 看 `is_discarded`）：拿掉時 V8 的 engine 照樣不建，它拿掉 frame 時一起從 isolate 的 frame 清單拿掉（`dom_js` 的 `discard_child`），`create_child` 找不到顯示那份文件的 frame。留著給沒有自己的 frame 清單的 host。
- DOM 的宣告表（`dom_api_macros` 的 `declare!`）產生的 method 的呼叫，把每個參數的位置都寫成第一個交給 `node_param`：位置只用在節點參數不是那個 interface 的 `TypeError` 的訊息，而表上的節點參數都是 `Node`，任何節點都接受，經過專用路徑碰不到這個錯（`node_param` 本身的訊息有單元測試）。表上有了比 `Node` 窄的節點參數時要補測試。
- DOM 的 wasm 那一側（`dom_wasm` 的 `handles.rs`）讀到 main Store 在節點的 engine word 裡的編號時，不對回 Store 的表、只看是不是 0：main Store 活著時，那個編號只在交出時寫、release 時清，一直是對的；main Store 死掉之後不再有 main，沒有 Store 讀它留下的編號。對回表是防著之後的程式漏清。
- DOM 的 V8 front（`dom_js` 的 `V8Front::dict_bool`）把 undefined 的 dictionary 成員當成沒給（`Some(None)`，用預設值），不 `ToBoolean` 成 false：表上唯一的 dictionary `EventInit` 的成員預設值都是 false，兩者一樣。有預設值是 true 的 `boolean` 成員時要補測試。
- DOM 的 number 的使用者的一步走完之後再對齊 step（`dom` 的 `StepRange::apply`，Blink 的 `AlignValueForStep`）：拿掉也一樣。它只在原本的值對齊時（`mismatch` 說沒有不對齊）做，對齊的值加整數個 step 只差 float 的誤差，那個誤差比 step 的 2^-24 小，最後照 step 和 step base 的小數位數四捨五入時就消掉；位數超過 15 或值在 10^15 以上時不四捨五入，double 本來也分不出那個誤差。
- DOM 的 search 欄位空的時候不接 Escape（`dom_api` 的 `controls::keydown` 回 false）：接了也一樣，Escape 不打字，按鍵的處理兩種都接著結束。Escape 有別的預設動作（關掉 dialog、離開全螢幕）時要補測試。
- DOM 的 spin button 放開時換一個按下的編號（`dom_api` 的 `controls::release`）：不換也一樣，放開時清掉按的是哪一半，舊的計時器到期時先看它、什麼都不做；下一次按下自己換編號，舊的計時器也對不上。
- DOM 的 optgroup 的 `disabled` 改了時記下它的 option 的 `:disabled`（`dom` 的 `select_attribute_changed`）：不記也一樣，UA 的 stylesheet 有 `optgroup:disabled option`，`:disabled` 在祖先的位置，style 的 invalidation 本來就重算 optgroup 底下的 option。UA 的這條規則拿掉時要補測試（作者的規則只有 `option:disabled` 的頁面）。
- DOM 的 style 的 `:-internal-list-box` 讀 `size`（`style` 的 `pseudo_class_attributes`）：不記也一樣，`size` 是 presentational hint 的屬性（`hints`），改了本來就重算那個元素。`multiple` 的那一個要記。
- DOM 的 `valueAsNumber` 設成 `NaN` 時把值清空（`dom_api` 的 `forms::set_value_as_number`）：不清空、寫進 `"NaN"` 也一樣，number 和 range 的值讀的時候整理（不是合法的數字時 number 是空的、range 是預設值）。值的整理改成設的時候做時要補測試。
- 同一個 front 的 `ret_f64` 不把 -0 當成 Smi 的 0：表上 `double` 的結果只有 `timeStamp`，不會是 -0。有可能給 -0 的成員時要補測試。
- renderer 對沒有 frame 的 Switch To Frame 回的值（`webdriver_commands.rs` 的 `switch_to_frame` 的 `(None, None)`：子 frame 的 id，最上層的 null）：machopodriver 只在 Switch To Parent Frame 時送它，確認要回去的 frame 還在（找不到 frame 時 context 先是 `no such window`），不看回的值，所以一律回 null 也一樣。
- frame 的 id 的前綴檢查（`webdriver_commands.rs` 的 `frame_id_of`：別的 renderer 的前綴不是這個 renderer 的 frame）：一個分頁只有一個 renderer，machopodriver 交來的 frame id 都是這個 renderer 發的，測試做不出別的 renderer 的 id。
- renderer 的 `ScrollIntoViewIfNeeded` 要捲時要一個 main frame（`render_thread.rs` 的 `scroll_into_view_if_needed` 的 `request_main_frame`）：它不回答，情境的 runner 在 `scroll-to` 之後一定接著要畫面（`RequestVisualState`，那會要 frame），所以拿掉時一樣在下一個 frame 捲。只有不等畫面就送它的用法才看得出差別。
- DOM 的 parser（`html` 的 `parser`）的 `same_node` 只比 handle 是不是同一個 `Rc`，不再比節點：html5ever 比的 handle 都是同一個節點的同一個 handle 複製出來的（每個元素只在 `create_element` 做一次 handle，document 和 fragment parse 的 context 也是），只有 template 的內容每次問都給新的 handle，而 html5ever 不拿它和別的 handle 比。比節點是防著 html5ever 之後換了比法。
- 同一個 parser 在 fragment parse 裡不理會 `set_quirks_mode`（`FragmentSink::set_quirks_mode` 什麼都不做）：tree builder 只在 initial 的 insertion mode 看到 DOCTYPE 時設 quirks mode，fragment parse 沒有那個 mode，走不到；留著防 html5ever 之後改了。
- 同一個巨集產生的 setter 的呼叫，不在操作一結束就放掉值（`typed::release`），留到呼叫結束：放掉是為了字串參數借著 engine 的字元時，engine 再配置之前還回去；setter 操作後 engine 會配置的只有 `throw`（表上的 setter 都不丟錯）和 `finish`（setter 的結果是 `undefined`，V8 的 front 什麼都不建）。method 的同一條有測試（`dom_js` 的字串參數）；有了會丟錯的 setter 時要補測試。

- 新的 GC 的 marking 收尾再跑一次 `run` 時，`Worklist::reseed` 讓 joining 的 run 一開始就算 busy（`worklist.rs`）：不設時 joining 的 run 做完自己的可能提早把 `done` 設上，但拿著段的 worker 在自己的迴圈裡做完全域剩下的段，`Platform::run` 又等所有 worker 返回才返回，所以標的一樣。留著是為了和 `Worklist::new` 的不變式一致（joining 的 run 帶著 seed、一開始就算 busy）。
- 新的 GC 的 concurrent marking 不處理刪掉的 root（`Heap::begin_marking` 的 `watch_removals`、`drain_removed_roots`）：marking 開始時每個 root 都當場標上，之後加的 root 拿到的不是開始時的快照裡的（到得了它的路斷掉時由寫邊的 barrier 標上），就是 marking 期間配置的（黑的），刪掉它不會漏標；TLA+ 的模型拿掉它也成立。留著是因為 root 表大了之後要改成 concurrent 地掃 root（開始時不再全部標完），那時刪 root 的 barrier 是必要的。

- effect 被別的動畫拿走時，原本的動畫留著那份 keyframe（`dom_api` 的 `take_effect` 不換成空的 effect）：它的 timing 同時換成預設的（長度 0、沒有 fill），keyframe 不會套到值上，script 也讀不到（它的 `effect` 是 `null`）。
- `<input>` 的 `value` 屬性改了、它的狀態不是 `dom` 存的（照屬性算）時也存一份（算出來的一樣，之後照樣跟著屬性）。
- `TracedSlot` 的 `Drop` 不 destroy V8 的節點。
- `dom_api` 複製節點時，子節點和 template 內容的複本建在原本的 document（接著插進複本時就 adopt 到正確的 document）。
- `measure` 的 end 先看 end mark 再看 options 的 end（options 有成員時再給 end mark 已經是 `TypeError`，沒有成員的 options 當成沒給，兩者不會同時存在；照規範的步驟順序留著）。
- `postMessage` 的 `targetOrigin: "/"` 當成 `"*"`（`"/"` 是呼叫的一方的 origin，只有在它和目標文件的 origin 不同時兩者才不一樣，而 machopo 的 script 碰不到別的 origin 的 window，連 `postMessage` 也不行，也沒有 `document.domain`；跨源的 window 能用 `postMessage` 之後就不是等價的，要補測試）。
- 拿掉這幾處 JS 的成員的 `set_accept_any_receiver(false)`（`dom_js` 的 `templates::checks_receiver`），讓 V8 不檢查 `this`：`[Replaceable]` 的 setter（在 `this` 上定義屬性，跨源的 window 在那裡就被 V8 的 access check 擋下，一樣是 `TypeError`）、pair iterator 的 iterator 和 `forEach`（`pairs.rs`）（`Window` 不是 iterable，別的 origin 的其他物件只能經過 window 拿到）。照 Blink 留著；開放給跨源的成員（`[CrossOrigin]`，`cross_origin.rs`）不經過它，再加開放給跨源的成員時要重新檢查。
- 事件的分派：在 retarget 到的 host 上找 activation behavior（能有 shadow root 的元素沒有 activation behavior；有 form-associated custom element 之後就不是等價的）。
- custom element 的 upgrade 失敗時不清掉元素的 definition，或讓元素留在 precustomized 而不是 failed（`dom_api` 的 `upgrade`：failed 的元素不再排 callback、不再 upgrade，`attachShadow` 照名稱找 definition，兩者都只有 `ElementInternals` 看得出來；有了它之後就不是等價的）。
- `Range` 的「insert」不先擋 comment 和 processing instruction 的起點（`dom_api` 的 `range::insert`：接著的 pre-insert 檢查一樣是 `HierarchyRequestError`，在那之前什麼都沒改；照規範先擋）。
- `IntersectionObserver` 判斷扭曲的效果時，只看 target 所在的 effect node、不往上找祖先的（`paint` 的 `intersection::Mapper::distorted`）：pre-paint 只在 opacity 小於 1 或有 filter 時才建 effect node，target 所在的不是根的話，它自己就已經是扭曲的效果。照 Blink 的 `HasDistortingVisualEffects` 往上找：之後有不是真效果的 effect node（`will-change`、合成用的）就不再等價。
- `IntersectionObserver` 的可見的判斷，矩形相交時先比外框的那一步不嚴格（`paint` 的 `hit_test::overlaps`：邊相接也算過）：接著照平行四邊形的兩個軸比，軸對齊的框的兩個軸就是 x 和 y，一樣是嚴格的；只差在轉過的框的角剛好落在 target 的邊上，浮點數幾乎不會剛好相等。
- number 和 range 的 step：`stepUp()` 不先看最小值大於最大值（下一步的對齊的最大值低於最小值，照樣不改），`valueAsNumber` 設成 `NaN` 時把值設成 `"NaN"`（sanitization 把它變成空的，range 的是預設值，和清空一樣），使用者往上加時不先把低於最小值的值設成最小值、在最大值以上時不先停下（`dom` 的 `step_range.rs` 的 `StepRange::apply` 夾到對齊的最小值、往反方向時不改，number 和 range 的 step base 有 `min` 時就是它，結果一樣）。
- DOM 的 `new DOMRectReadOnly(...)` 做出的 rect 標成 `DOMRect`（`dom_api` 的 `geometry::construct_read_only_rect` 的 `read_only`）：建構子的 wrapper 是建構的呼叫自己做的，prototype 照 `new.target`，不經過照 `read_only` 選 interface（`typed::interface_of`）的那一步，wrapper 之後一直留著；`DOMRect` 的 setter 由 V8 的 signature 擋掉不是 `DOMRect` 的物件。`read_only` 只對 DOM 做的、之後才包 wrapper 的 rect 有作用（`fromRect`、observer 的 entry），它們有測試。

- debug build 比對 fast path 和 tree builder 的結果時，不比 input 的型別（`html` 的 `fast_path_build::same_tree` 的 `input_kind`）：兩邊屬性一樣時，只有 fast path 把 input 建錯才會型別不同，檢查就是為了抓這個；fast path 建對時拿掉它結果一樣。fast path 照屬性建 input 的型別由 `html` 的 `fast_path::inputs_are_made_of_their_types` 直接比兩種 parser 的結果守著。

**style 和 CSS**

- DOM 的文件的 base URL 給 `about:` 的文件也先看快取（`dom` 的 `base.rs` 的 `with_document_base_url` 的 `!about`）：快取只在非 `about:` 的路徑寫進去，`about:` 文件（初始的 `about:blank`、srcdoc）的那一格永遠是空的，看了也是照原本的路往下算；照「`about:` 的每次算」留著，免得之後有人在 `about:` 的路徑也寫快取時讀到舊的 fallback。

- `css` 的 `FontSize::compute` 拿掉 NaN 變 0 的檢查：每一條算出字級的路都已經不會是 NaN（長度經過 `Length::to_px`、帶百分比的 `calc()` 經過 `resolve`，兩者都把 NaN 變成 0），留著是防著之後新加的路。
- `style_resolver::shorthand_longhands` 回傳的 longhand 順序（`shorthand_value` 把它們設進宣告清單，序列化照 property 自己的順序讀，呼叫的一方也只是逐個取值，所以順序外面看不出來）。
- `css` 的 `cursor` 的游標座標要兩個數字：第二個不是數字時當成 0 也一樣無效（cssparser 的 `expect_number` 失敗時照樣吃掉那個 token，後面的逗號或關鍵字已經不在原處，整條宣告無效）。
- `css` 的 `parse_selector_list` 在 `SelectorList::parse` 之後的 `expect_exhausted`（`SelectorList::parse` 照逗號切開的每一段都要解析完，後面不會剩下 token；`querySelector`（`style` 的 `query`）和 `selectorText` 的 setter 都經過它，照樣留著，不依賴 `selectors` 的這個細節）。
- `computed_style` 的 `ComputedStyle::inherit` 不複製父元素的自訂 property（`style_resolver` 的 cascade 一定用 `compute_custom_properties` 重新設定每個元素的；`inherit` 照樣複製，它的意思是「繼承的 property」）。
- shadow root 的 stylesheet 變了時不為了規則走進 shadow tree（`dom` 標記 shadow root 的 sheet 時也標記了 host 的祖先，host 本來就往下走；照樣留著，別的原因重收的 scope 也要走到）。
- 整棵子樹的後代 invalidation set 不強制重算整棵子樹（`any` 的 set 照樣帶下去，每個元素都重算）、debug build 的交叉檢查只為了檢查才走到的元素不套用 set 的那個條件（只在 `descend` 漏算 `below` 時才有差）。
- matched properties cache 拿到別的位置的 entry（hash 已經含位置，只有 hash 碰撞時有作用）、menu list 的內層元素進快取（UA 的規則用了 `text-overflow: inherit`，這種 style 本來就不存；排除照樣留著當保險）。
- DevTools 的「說明」的路（`style` 的 `StyleEngine::explain`）match 時設 selector 的 flag（`NeedsSelectorFlags::Yes`）：它說明的是上一次 recalc 照同一份 stylesheet match 過的元素，那時已經設過一樣的 flag，再設一次不改變什麼；不設是照「說明不影響之後的 style」。
- 文件的 stylesheet 重新收集時沒變（`style` 的 `collect_sheets` 的 `same`），把留著的每一份換成現在的物件的 id（DevTools 的規則的 `styleSheetId` 照它）：現在每個 `CssStyleSheet` 有自己的 media（`Arc`），內容和 media 都是同一個才算沒變，所以沒變時一定是同一個物件，id 本來就一樣。留著是為了之後 media 共用時 id 不會停在舊的物件。

**layout**

- `layout` 給 parley 的 variation 在 `font-variation-settings` 自己設了 `opsz` 時不另外加字級的 `opsz`（`font_features.rs` 的 `variations`）：設定排在後面、後面的贏，兩個都給結果一樣；照樣不加，不依賴 shaper 取哪一個。
- parley fork 的軟連字號：新的一行把「上一個 atom 是軟連字號」重設回 `Break`（`LineState::reset`；斷在軟連字號之後，下一行從那裡的狀態開始，但一行的第一個 atom 和開頭的元素邊緣都在 x 是 0 的地方，那裡不記斷點）；連字號的前進量乘上 display scale（machopo 的排版的 scale 是 1）；`ResolvedStyle::check` 比較 `SoftHyphens`（只有 `RangedBuilder` 用它，machopo 用 ranged builder 的 `shape_line` 一律給 `Break`）；min/max-content 的量測在 `hyphens: none` 的軟連字號之後只在 `overflow-wrap: anywhere` 時斷（拿掉 `NoBreak` 的條件也不斷，`anywhere` 本來就在每個 atom 之前斷，量到的最寬的一段一樣）。
- IFC 的 measure 在知道寬度時回傳那個寬度（taffy 的 leaf 在知道寬度時不看 measure 回傳的寬度）。
- 絕對定位盒子的 resolved `top` 和 `left` 改成取 layout 算出來的位置（`layout::geometry` 的 `used_inset`：machopo 只有 horizontal-tb、ltr，`top` 和 `left` 一定是被採用的那一邊，給了值就擺在那裡，兩者相等；同一行的 `right` 和 `bottom` 不等價，由 `shell` 的 `absolute_boxes_and_their_insets` 抓到）。
- `layout` 的 `compute_box` 在量大小時（不是 `PerformLayout`）也呼叫 taffy 的 `compute_oof_layout`（taffy 的 block、flex、grid 只在 `PerformLayout` 時設 `oof_positioning_area`，量大小時它是 `None`，`compute_oof_layout` 直接 return；照 taffy 自己的 `TaffyTree` 只在 `PerformLayout` 呼叫）。
- 只有 float（和 out-of-flow 盒子、會摺掉的空白）的內容也照行內內容排（`layout` 的 `set_content` 的 `only_floats`：Blink 就是在沒有行的 inline formatting context 裡放它們，位置和 taffy 的 block layout 放的一樣，交給 taffy 只省下 parley 的 layout）。
- `InlineContent` 放 float 時也用斷行的快取（`break_lines` 的 `!places`：快取的 key 是 `PerformLayout` 時包含自己的 float 的區段，下一次排版傳進來的只有外面的 float，對不上；只有大小是 0、不留區段的 float 對得上，它放不放只差在 `clear` 和「不比前面的 float 高」的邊界情況。照樣在放 float 時不用快取，意思清楚，不依賴 key 的這個細節）。
- `layout` 的 `container_of` 找有沒有正在重建的祖先時沿 DOM 的 parent 往上（停在 shadow root、看不到 host）：只有 counter 的文字變了的元素在 shadow tree 裡、它的 host 又在同一次更新裡重建時才不同，而那時外面的盒子先重新收集（`walk` 照樹的順序記下要收集的盒子），新的盒子在舊的放掉之前就配置好，再收集一次的只是已經離開樹的舊盒子，結果一樣；照樣沿 flat tree 往上，免得依賴這個順序）。
- table 的 collapsed 邊框算 cell 的邊框寬度時，不看邊能不能畫（`CollapsedEdge::can_paint`）只看寬度，結果一樣（`border-style` 是 `none`、`hidden` 的邊，computed 的寬度本來就是 0）。
- `layout` 認 inner editor 時不看它沒有子元素（editing view port 也算，它裡面的 inner editor 或 placeholder 已經有一行高，結果一樣）。
- parley 的 fork 的 `LayoutData` 的 `line_after_final_break` 的預設值（每次 build 都先 `clear()`，它在那裡設回 `true`，`Default` 的值看不到）、強制換行之後的空行只在它不是唯一的一行時拿回（`line_break.rs` 的 `len() > 1`：builder 給每個 layout 至少一個 item，沒有文字時也是，第一行一定有 item；照樣留著，layout 的第一行不會被拿回）。
- `layout` 的 `TextFragment::for_each_glyph` 對自己存 glyph 的 run 也照數量截（`TextGlyphs::Owned` 的 `take(count)`）：自己存 glyph 的只有 `text-overflow` 的省略號，`text-overflow` 只藏行上的 run、不藏省略號，paint 問它的數量一律是全部。照樣截，兩種 run 照同樣的規則。
- line clamp 的容器裡的盒子，隱藏的記號變了時標成要重建 fragment（`needs_fragment`）：taffy 對每個盒子先量、再用不同的 known size 排，clamp 的容器裡的盒子每次都重排、重建 fragment，記號只在 taffy 的呼叫方式改了時才用得到。
- `-webkit-box` 的項目只在水平的 box 裡把 `auto` 的寬當成 fit-content（`webkit_box_item`）：垂直的 box 裡也這樣做結果一樣，垂直方向上 fit-content 的高度就是內容的高度。
- parley fork 給 tab 新的前進量時，連同它的 glyph 和 run 的 advance 一起改：不改結果一樣（tab 是存在 cluster 裡、沒有位移的單一 glyph，只有存在 glyph 陣列的 glyph 才讀 glyph 的 advance，排版也不讀 `ShapedRun.advance`），照樣改，讓資料和 cluster 一致。
- scroll anchoring 找 anchor 時，out-of-flow 的盒子在它的 containing block 那裡也照 children 的順序看（`layout` 的 `scroll_anchor.rs` 不濾掉它們）：containing block 的 children 裡 out-of-flow 的排在 in-flow 的後面，輪到它們時 in-flow 的都沒選上，和之後的後備（Blink 的 `FindAnchorInOOFs`）看的是同樣的盒子、同樣的順序，只多看一次。
- 非換行的 column flexbox 被問寬度時只取子項貢獻的那條路（taffy 的 fork 的 `compute_preliminary`）不量子項 flex 之後的高度：子項照自己的 style 給的高度量，沒有的話高度未知。寬度會跟著給它的高度變、又不是經由 `aspect-ratio` 的子項（measure function 自己用高度算寬度的 leaf、換行的 column flexbox），結果和走完整的演算法不同；Blink 算 column 的 intrinsic 寬度時也只用子項自己的貢獻。machopo 的 replaced 元素都帶比例（不走這條路），文字的寬度不看高度，所以 machopo 的測試做不出差異，也沒有每次比對完整演算法的檢查；fork 的 `column_width` 測試守著這條路自己的行為。machopo 加了寬度看高度、卻不帶比例的盒子時，要回來看這一條。
- flex 和 grid container 在確定的空間裡寬度未知時 shrink-to-fit 的那條路（`layout` 的 `fit_content_width`）在寬度已知、或自己的 `width` 有值時不走：走的話，taffy 量出來的 min-content、max-content 寬度就是那個寬度，夾出來的一樣，只多量兩次。
- parley fork 以字為單位 shaping 時，選字型的樣式沒有號碼的字也逐字（`shape_segment`）：parley 的 selector 一律給號碼，只有沒有實作 `font_style` 的 selector 會沒有；照樣整段，免得用沒有號碼的 key 存字。
- parley fork 碰到要整段 shaping 的字型、整段重來時不重設 selector（`begin_segment`）：selector 的狀態只在樣式或字型清單變了時重設，第一個字型對現在的 query 仍然成立；照樣重設，不依賴這個細節。
- parley fork 以字為單位 shaping 時，default ignorable 開頭的字「前一個字是空白」的條件（`WordRuns::joins`）：字只在空白和 inline object 的前後切開，inline object 之後另起一個 run，所以同一個 run 裡 default ignorable 開頭的字前面一定是空白；條件只是把意思寫出來。
- parley fork 判斷字型的規則和空白時，`kern` 的 pair 不把空白後面的 mark 算成「空白後面的 glyph」（`space.rs` 的 `in_kern`）：算進去只是多合併一些字、比較慢，HarfBuzz 的 kerning 本來就跳過 mark。照樣不算。
- parley fork 查斷行表時，交給 ICU4X 的字一律從文字開頭看起（`line_table.rs` 不記前一個字的開頭）：ICU4X 看到的上下文只多不少，結果一樣，只是比較慢。照樣只從前一個字開始。
- `layout` 的 `TextContext` 不關掉字的界線（`set_word_boundaries(false)`）：machopo 不讀 parley 的字的界線，只是分析比較慢；測試看不到。之後若有算分析次數或時間的計數，再補。
- parley fork 判斷字型的規則和空白時，chained context 的 backtrack 不倒過來（`space.rs` 的 `chained`）：backtrack 有兩格以上時規則就有三格以上，有空白就一律當成跨過空白，順序看不出差別；只有一格時倒不倒都一樣。照樣倒過來，位置的順序和比對的順序一致。

**paint、raster、compositor 和 Viz**

- `gfx::Size::checked_area` 的 `checked_mul` 改成 `wrapping_mul`：64 位元上兩個 `u32` 的乘積放得下 `usize`（32 位元的平台才會溢位，machopo 目前沒有）。
- compositor 交給 main 的容器 delta 不照元素排序（main 各自套用，排序只是讓訊息固定、測試能比對）。
- paint 整段沿用 stacking context 時不比它的紀錄是不是上一次 paint 的、不看底下有沒有 child frame（兩者都要 pre-paint 從上一次 paint 之後沒重走它：上一次沒畫到的不在樹上，回來時會重走；有 child frame 的每次重走）。
- pre-paint 的 node 的 key 不拿另一個活著的 fragment 拿著的位置、不放開這次已經走過的 fragment 的紀錄（兩者都要同一個 box 有兩個 fragment，或 layout 把一個 fragment 搬到另一個 parent 底下才會碰到，現在的 layout 不會：暫時加的紀錄在 `paint`、`renderer`、`shell` 的測試、reftest、情境和 4285 個 WPT 測試裡都沒有碰到；留著防止兩個 fragment 共用 node）。
- pre-paint 不把沒再用到的 transform、clip、effect node 的位置清空（活著的 node 的 parent 都是這次給出的位置，cc 端的 tree 也只從被參照的 node 建，沒有東西讀到舊的 node；scroll node 的位置照樣清空，捲動容器的清單照它）。
- paint 搬來的 item 照樣比內容（只影響速度）、搬來的 item 只要有來源就算沒變（目前走不到：同一個元素和種類的 item 分在幾個 box 時，只有匿名 block 這種情況，而其中一個變了 layout 一定重做所有的匿名 block）。
- `viz` 的 readback 在 surface 的格式不是每像素 4 byte 時關掉自己（`wgpu_renderer` 的 `swap_chain_format` 一定先選到 8-bit 的格式，目前每個平台的 surface 都提供，所以是走不到的防禦）。
- `raster::draw_into` 給不透明的 canvas 用不透明的 alpha type（照 Chromium 的 `alpha: false`）：現在畫的 op 都是 source-over，畫在 alpha 是 255 的像素上，結果的 alpha 一定還是 255，不透明的 canvas 的 `clearRect` 又是畫黑色，所以和 premultiplied 一樣；有會減少 alpha 的合成模式（`globalCompositeOperation` 的 `copy`、`destination-out`）之後就不是等價的，要補測試）。
- hit test 對被 `text-overflow` 截掉一部分的 run 用它可見的寬度還是完整的寬度（`paint` 的 `hit_test`：run 一定在它元素的 inline 框裡，而 inline 框照沒截的幾何（`offsetWidth` 不變，Blink 也是），在被截掉的位置打到的一樣是那個元素；run 是 block 自己的文字時，打到的是 block 的背景，一樣是 block）。
- `paint` 的 hit test 在背景階段不跳過 float（float 的階段在背景階段之前，點在 float 上一定先在那裡找到，不在 float 上的背景階段也找不到它）。
- `paint` 的 `PaintController` 照元素找上一次 paint 的盒子時不排除 pseudo-element 的（`by_node`：pseudo-element 的盒子的 style 和元素的不是同一個 `Arc`，接著比對 style 一定不同，只是少搬一次、照樣重畫，結果一樣；元素和 pseudo-element 哪個留在表裡又看 `HashMap` 的順序，寫成測試也抓不穩）。
- raster invalidation 的 item 序號不在每個 chunk 重新算（`raster_invalidator` 的 `ordinals.clear()`：前面的 chunk 裡同一個元素和種類的 item 數變了時，後面的 chunk 的 item 對不上、多 raster 一次，不會少；要前面的 chunk 多一個同元素、同種類的 item，後面的 chunk 又不動，沒有構造出這樣的頁面）、一個舊的 chunk 只對上一個新的（`matched` 的篩選：要一個新的 chunk 的 id 剛好是另一個新 chunk 整段搬自的舊 chunk 的，前者照樣逐個比、後者沒變，結果一樣）。

**renderer、browser 和自動化**

- script 停住而 layout 被借出去時那次停住不畫（`renderer` 的 `render_thread/devtools.rs` 的 `cannot_render`）：現在沒有一條 operation 拿著 layout 呼叫 script，拿掉這個判斷的 mutation 走不到；留著是因為走到時停住的迴圈會一直說有 frame 要畫又畫不了。
- renderer 不呼叫 `ScriptEngine::end_rendering_update`（`begin_main_frame` 的最後）：renderer 列出 frame 的地方都在 rendering update 裡，每次 `begin_rendering_update` 都重新找一次；update 之外只有每轉一圈 loop 的動畫檢查，它不經過這份清單（照 frame 建立的順序），所以看不出差別。engine 的「update 之後再走」由 `dom_js` 的 `frames::a_rendering_update_walks_the_frame_tree_once` 守著。renderer 之後在 update 之外列 frame 時，這條會變成真的要守的。

- renderer 的 `render_thread::next` 的 `prepare_script` 的 `already_started` 的檢查：parser 插入的 script 每個只在 parser 停在它的 `</script>` 時 prepare 一次，這條路上拿掉也一樣；script 元素被搬動或複製後再插入時才有作用，那時補測試。
- DOM 的 `removeAttributeNode` 先看 `Attr` 的元素是不是它（`dom` 的 `remove_attribute_node`）：拿掉也一樣，接著在元素的屬性表裡照指標找 `Attr` 的屬性物件，別的元素的、沒有元素的都找不到，一樣是 `NotFoundError`（一個屬性物件只在一個元素的表裡）。先看是省掉走一遍屬性表。
- DOM 的 `Range.insertNode` 先看 start 是不是 comment 或 processing instruction（`dom_api` 的 `range.rs` 的 `insert`）：拿掉也一樣，start 是它們時 parent 是它們自己，接著的 pre-insert 的檢查一樣是 `HierarchyRequestError`（它們不能有子節點）。照 DOM 的步驟寫（Blink 的 `Range::insertNode` 也先看）。
- renderer 在 commit 時照 MIME type 設 document 的 `contentType`（renderer 的 `render_thread::next` 的 `set_document_metadata`）：DOM 現在只 load HTML，每份的 MIME type 都是 `text/html`，和沒設時的預設一樣，不設也一樣。DOM 能 load XML 和其他的文件時要補測試。
- renderer 丟掉比現在顯示的文件舊的 commit（`commit_navigation` 開頭的 `navigation_id` 比較）：shell 的測試一次只有一個導覽，排不出回應晚到的舊導覽。

- DevTools 的 `Page` agent 把第一份文件 commit 之前的 main frame（`frame_infos` 在還沒有文件（`document`）時報的那個）標成 initial：拿掉不會多出 `Page.frameNavigated`。renderer 處理每個 DevTools 的 message 之前都先更新 frame 的清單，那時處理中的 `Page.enable` 還沒生效，所以開著 `Page` 的 session 看到這個 frame 時它已經在清單裡，不算新的。
- renderer 在 update animations 時不把離開元素、還在播的動畫算成要畫的（`animating`：run loop 的 `wants_frames` 照樣算它，frame 照樣來；拿掉 `wants_frames` 那一邊的有測試抓到）。
- `RenderProcessHost::abandon` 停止轉送訊息（只在 renderer 已經結束之後呼叫，被 `about:crash` 結束的早就停了，自己結束的 IO thread 也已經結束）。
- `BrowserView` 不把按鍵、滾輪和指標移動送給當掉的分頁（送了也只是送進已經關閉的 channel，多一行 log）。
- 情境的查詢（`QueryElement`、`ScrollIntoViewIfNeeded`）之前先把 lifecycle 更新到 pre-paint（情境的查詢先等到畫出改變的那個 frame 才問，那時已經是最新的；照 Blink 留著）。
- renderer 在 DOM 的樹有任何改動之後都重算主 frame 的標題（`update_title` 看 `tree_version`：不只 `<title>` 改了的時候，子 frame 的文件的改動也算）：重算的標題和上次送的一樣，不會再送。
- DevTools 的 `DOM.requestNode` 對不是物件的值回答別的錯誤文字（`dom_js` 的 `devtools_page` 的 `node_of_object`，`v8::Object` 的 `try_from` 失敗的那一支）：V8 的 inspector 只給物件 `objectId`，`unwrapObject` 拿回來的一定是物件，這一支走不到；留著是因為 `unwrapObject` 的型別是 `Value`。

**網路和載入**

- 同一張圖片重複要求、只在 task 結尾開始載入。
- `Request` 的建構子在 init 有成員時把 `navigate` mode 改成 `same-origin`（script 建不出 `navigate` 的 request，走不到），`request-no-cors` guard 的 `delete` 不理不是 no-CORS-safelisted 的名稱、每次改動之後拿掉 `Range`（這種 guard 的 list 只會經過它自己的檢查進來，不會有那些名稱；照規範留著）。
- DOM 的 autofocus 處理過之後仍收候選（`dom_api` 的 `autofocus_inserted` 不看 processed flag）：`flush_autofocus_candidates` 只在還沒處理時看候選（`has_autofocus_candidates`），處理時清掉清單，之後收進來的永遠不會被用到，只是最上層的文件多留幾個 id；照規範的步驟留著。
- `net` 的 `URLRequest` 擋不是 token 的 method（reqwest 的 `Method::from_bytes` 也拒絕，錯誤一樣；不依賴它而留著）。
- `net` 的 CORS 判斷 basic 時看 tainting 還是 basic（`cors.rs` 的 `start`：tainting 只在跨源的網址變成 `cors` 或 `opaque`，之後回到自己的 origin 一定是從那個網址轉回來，那次 redirect 就 taint 了 origin，「沒有 taint」已經排除它；照規範的兩個條件留著）。
