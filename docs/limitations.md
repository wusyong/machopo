# 已知限制

目前仍然成立的限制，依領域分組；解決了就刪掉（`docs/README.md` 的「完成一步時」）。測試守不住的地方（只靠審查、只做過手動確認、缺少的工具）在 `docs/test-gaps.md` 的「測試守不住的地方」。

## 平台和建置

- 驗收和視窗模式的手動確認只在 macOS（Apple Silicon）上做過。自動測試在開發機和每天的 CI 上跑（`docs/testing.md` 的「CI」）。真視窗的情境（`test.py automation`）在 Windows 11 和 macOS 上跑過（macOS 從 2026-10-07 起，Metal 的 surface 讀得回畫面）。Linux（Fedora 44、Wayland、AMD 的 Mesa）2026-10-08 第一次跑，修掉兩個視窗那一層的 bug 和三份情境的假設之後全部通過。Wayland 的視窗在 compositor 第一次 configure 之前改大小會被它蓋掉（30ms 後又 configure 回原本的大小），所以情境要在頁面載入之後才 `resize`；真視窗用系統的字型和螢幕給的大小，所以情境不能假設視窗的高度（放不下時 `click` 會把頁面捲走），測試頁也要留夠文字的行高（溢出到捲動框上會讓 compositor 把滾輪交給主執行緒）。macOS 的視窗不會比螢幕高，`window size=` 超過螢幕的高度時開出來的比較矮。2026-10-15 在同一台 Linux 上再跑，五份情境失敗，都和視窗的大小有關：視窗的截圖是 1067 px 寬（800 px 的視窗）、`resize` 的視窗是 999 px 寬，`intersection-observer`、`resize-observer`、`resize`、`wasm-demo` 讀到的寬度帶小數（`732.25`），`position-relative` 的 `window size=800x4100` 開不出那麼高的視窗；同樣的情境在沒有平台視窗的 `test.py scenarios` 裡通過。2026-10-30 再跑也是五份：`position-relative` 過了，換成 `scroll-anchoring` 捲 141 px（要 140 px），其他四份一樣。螢幕的縮放設定還沒查。從原始碼編 V8 在 macOS、Linux（Fedora 44，2026-10-16，用 Perfetto 編）和 Windows 11（2026-10-22，只有 release：rustc 在 Windows 上連結不了 debug 的 V8）上跑過；fork 的 CI 在三個平台上都編過。
- V8 的 prebuilt 只有 rusty_v8 fork 的 CI 編的平台：Windows x86-64（只有 release）、macOS arm64、Linux x86-64。其他平台要用 `python3 scripts/ci.py v8` 自己編，再設 `RUSTY_V8_ARCHIVE`。
- 下載的 V8 沒有雜湊驗證：rusty_v8 的 `RUSTY_V8_ARCHIVE_SHA256` 只能釘一個檔案。
- `python3 scripts/ci.py guests`（編 repo 裡的 wasm guest）現在編的 DOM 的 guest（WASI 0.3，`wasm32-wasip3`）只在 macOS（Apple Silicon，2026-11-10）上跑過，repo 裡的 `.wasm` 是那裡編的（WASI 0.2 時的在 Linux 上編過，更早的其他 guest 在 macOS 和 Windows 11 上也跑過）。同樣的原始碼在不同平台上編出的 `.wasm` 不逐 byte 相同：Rust 的 guest 帶著 std 和 crate 的原始碼路徑（panic 的訊息用），Windows 上是 `\` 分隔。
- WPT 的測試（`test.py wpt`、`reftest`、`wdspec`）經過上游的 wptrunner 跑，只在 Windows 11 上跑過（2026-10-09 到 10）；改用它之前，上游的 wptserve 加上 machopo 自己的 runner 在 Linux 和 Windows 11 上驗證過。macOS 上還沒跑過：platform verifier 接不接受 WPT 的根憑證、預期結果的平台條件、process 數的預設都還沒確認，下次在 macOS 上跑時確認；出了問題再開 branch 修（只影響跑 WPT，不影響瀏覽器本身）。
- `python3 scripts/bench.py speedometer` 控制 Chrome 的 pipe 只在 Windows 11 上跑過（`--remote-debugging-io-pipes`，2026-10-18）：Linux 和 macOS 上 Chrome 讀寫 fd 3、4，工具經過 `sh` 的 `exec` 把 pipe 換到那兩個號碼，還沒在那兩個平台上跑過。在那裡壞了時，Chrome 那一側的盤點、量測和 `--trace` 都會因為連不上 Chrome 而失敗。
- 沒有 ICU data，`Intl` 不能用。
- workspace 不能把 `panic` 設成 `abort`：圖片的 decoder（`image` crate）自己說碰到惡意的檔案可能 panic，`raster` 用 `catch_unwind` 把 panic 當成解不開的圖片；改成 abort 的話，一張壞圖會讓整個 process 結束。`catch_unwind` 接不住無窮迴圈和 stack overflow。
- Windows 上連結時有 `LNK4098` 警告：prebuilt 的 `rusty_v8.lib` 用靜態 CRT（`/MT`，`libcmt`），Rust 用動態 CRT。這是 prebuilt V8 本身的設定，把我們的 C++ glue 改成靜態 CRT 也消不掉。
- Windows 上 timer 的精度是系統計時器的一個 tick（約 15.6 ms）：renderer 的 event loop 用 `recv_timeout` 等下一個 timer，所以 1 ms 的 `setTimeout` 要等到 16 ms 左右才執行。WPT 的 `timer-nesting-not-inherited-in-microtask.html` 因此只在 Windows 上不跑（它在 `tests/wpt/metadata/` 的 `.ini` 是 `if os == "win"` 的 `disabled`，2026-10-07）。之後照 Chromium 的做法（`base::Time::ActivateHighResolutionTimer`）：有短的 timer 等著時用 `timeBeginPeriod(1)` 提高精度；要呼叫 Win32，`unsafe` 放在哪裡要先決定。
- VS Code 的 rust-analyzer 會鎖住 proc macro（`gc_macros` 這類）的 dll，`cargo build` 可能出現 `LNK1104`。把被鎖住的 dll 改名後重新 build 即可。
- `MACHOPO_TRACE` 的 trace 只有 span、V8 自己的事件（GC 的各個階段、deopt；compile 和 parse 的事件在 `disabled-by-default-v8.compile`，和 Chrome 那一側一樣不錄；log 的事件不在裡面）、cppgc 的各個階段（`CppGC.AtomicMark` 這類，`cppgc`；JS 文件和 wasm 文件的 DOM heap 都有，Chrome 那一側也錄 Oilpan 的；細的子階段在 `disabled-by-default-cppgc`，不錄）、V8 的 heap 的大小和上限（`v8.memory` 的 counter；V8 的速度在 `disabled-by-default-v8.gc`，不錄：嵌入端的速度是空的 `CppHeap` 的，會誤導）和網頁的 User Timing（`performance.mark()`、`measure()`，`blink.user_timing`；不像 Chrome 的帶 `startTime`、`callTime` 等參數）和 Navigation Timing 的每個時間點（同一個 category 的 mark，名稱照 Chrome，不帶 frame），machopo 的 span 照 Chrome 的 trace 的名稱和層次，標到呼叫 JS 的入口（`v8.callFunction`，最外層的是 `FunctionCall`）、HTML 的 parse（`ParseHTML`）、custom element 的 reaction 和 main frame 的每一步：JS 和它呼叫的 DOM API 裡面哪個函式花時間要靠取樣：V8 的 CPU profiler（automation pipe 的 `Profiler`，`bench.py speedometer --profile`）或 `--sample`。取樣的工具（`bench.py speedometer --sample`）在 Linux 上用 `perf`（cycles 和 instructions），在 macOS 上用 samply（`cargo install --locked samply`；每 1 ms 取一次 stack，以那段時間用掉的 CPU 時間計，沒有 instructions 這種和 CPU 的頻率無關的計數，同一台機器上兩次的差也就比較大）；Windows 上也用 samply（經過 ETW；和 macOS 一樣以 CPU 時間計、沒有 instructions，連 kernel 的 frame 一起算），要 Windows Performance Toolkit 的 xperf 和系統管理員：每次取樣跳一次 UAC，取樣在提權的 process 裡跑，原本的終端機按 Ctrl+C 只停得了自己，停不了它（一般權限的 process 結束不了提權的 process），要等它跑完或從工作管理員結束。`--sample --against` 比較 machopo 開始寫 User Timing 之前的版本時，那一邊的 trace 沒有 runner 的 mark，計時區間照 runner 的 frame 猜：大部分 suite 每個 test 差在 ±0.7 ms 內，但頁面自己的 timer 排在 runner 的之前時區間提早結束（React-Stockcharts-SVG 每次少約 11 ms），頁面自己在一個 frame 排兩個 animation frame callback 時多一個區間（TodoMVC-Preact-Complex-DOM）；`compare.md` 寫明兩邊各用哪一種。`--sample` 只取 machopo：Chrome for Testing 沒有符號（`--profile` 兩邊都取，只到 JS 函式）。取樣的那次跑多開了 V8 的 `--perf-basic-prof`（Windows 上是 `--enable-etw-stack-walking`）、`--interpreted-frames-native-stack`，和量時間的那次有一點不同；Rust 的 std 是預先編好的、沒有 frame pointer，展開經過它的函式（不是在 machopo 裡展開的 generic）時會斷掉。一個 process 錄一份：renderer 拆成自己的 process 之後會變成好幾份（Chrome 由 browser process 收成一份）。
- 還沒有 `--dump-layout`：`BoxFragment::dump()` 已經能印出 fragment tree，但還沒接到 headless。
- 畫面一律經過 GPU（wgpu）合成：沒有 GPU 時用 wgpu 的 CPU adapter（Windows 的 WARP，Linux 的 Mesa lavapipe 或 llvmpipe），兩者都沒有的機器上 machopo 畫不出東西（macOS 的虛擬機、沒裝 Mesa 的 Linux）；Chromium 這時退回 software compositing，machopo 沒有。CPU adapter 比 GPU 慢很多（仿 NewsSite 的一個 frame 約 23 ms，32 個 process 同時畫時約 470 ms）。

## 隔離

- 沒有任何隔離：V8 沒開 sandbox（machopo 用的是自己 fork 編的 V8，已經可以開，但還沒開），renderer 也還不是獨立的 process（程式照 process 的邊界寫，見 `docs/architecture.md` 的「Process 的邊界」）。所以 V8 或 DOM 的 heap（elise）的任何記憶體錯誤，都能碰到整個 browser 的記憶體。
- renderer panic 時整個程式結束：沒有錯誤頁，也不重新啟動 renderer。記憶體耗盡也一樣：`border-collapse: collapse` 的表格的邊是一個密的陣列（Blink 的 `TableBorders` 也是），一列 1000 個 `colspan=1000` 再加上幾千列的表格要好幾十 GB，配置不到時整個程式結束（拆成 process 之後和 Chrome 一樣只結束那個 renderer）。
- `gfx::FontData` 和 `gfx::ImageData` 不能序列化：拆 process 後要改成像 Chromium 那樣傳 typeface 和圖片。
- **名稱表和屬性值的表在同一個 renderer 裡共用**（`dom` 的 `names.rs` 和 `string.rs`，thread-local：同一個分頁導覽過的網頁和它們的 iframe 都用同一份）：前面的網頁的名稱一直留著（見「GC 和 `dom`」），屬性值（包括 CSRF token、hidden input 的值）留到值的表下一次丟掉沒人用的。沒有 API 讀得到表的內容，但 intern 時找到的只 clone、沒有的要配置，花的時間不同：頁面可以一次測一組猜得到的名稱或值有沒有出現過，例如某個網站特有的 custom element 名稱（這個分頁去過哪裡）或低熵的值；隨機的 token 猜不到，測不出來。跨 site 的網頁和 iframe 分到各有一份表的 renderer 時才沒有；只回收沒人用的名稱擋不住（還活著的 iframe 的名稱照樣測得到）。

## GC 和 `dom`

- 同一個 thread 上只有最新建立的 isolate 能用：`v8` crate 建立 isolate 時就 enter 它。renderer 一個 thread 只有一個 isolate，所以只影響測試。
- JS 文件的 V8 platform task（incremental marking 的步驟、GC 的收尾）只在有別的 task 叫醒 renderer 的 event loop 時才執行：頁面閒下來時，做到一半的 GC 會停在那裡，寫入照樣走 barrier、垃圾也不釋放。V8 的 platform 放進 task 時不通知 machopo。之後讓 V8 的 platform 放進 task 時也叫醒 loop。
- **renderer 的 DOM heap（JS 文件，V8 驅動的那個）沒有 nursery**：有 wrapper 的物件本來就一開始在 old（V8 記著它的位址），掛在節點上的資料跟著放 old，剩下的短命物件（事件的資料和路徑、暫時的陣列）也放 old，只在 V8 發動的 full GC 回收；Speedometer 上和有 nursery 一樣快、記憶體的高峰不變或更低。配置走只 bump、寫 header 的快路，不看 `Site`；write barrier 每次還是檢查目標是不是 young（讀一次頁的表）。GC 照樣分代、會搬動（之後 wasm GC 的物件配在 DOM 的 heap 上時要它）；事件很多的長時間頁面上，兩次 full GC 之間短命物件累積多少也還沒量。下面和 scavenge、nursery 有關的幾項只影響不是 engine 驅動的 heap（測試、`gc_bench`，和之後接上 renderer 的 wasm 文件）。
- 新的 GC（elise，`gc_bench` 在 microbenchmark 上量，也在以前的 DOM（cppgc 上的）錄下的工作上量過；錄製和重播已經拿掉，現在的 DOM 不錄）的這些做法只在那些工作上量過，要等跑真的頁面時再量、再決定：
  - **沒有 compaction**：old 的頁不搬動。marking 開始時（V8 挑要搬空的頁的時候）照 V8 的挑法（`CollectEvacuationCandidates`：空的至少 70%、活的少的先、最多搬 4 MiB、放不掉頁就不搬）能放掉的頁，量過的工作中位數都不到 10%（多數是 0，ids 1%，old 只有 11 頁的 gc-mini-tree 的錄製 6.2%；sweep 剛做完時 churn 放大 10 倍有 11%，之後的配置先填最滿的頁的空格子，到下一次 marking 時填回了）；長時間反覆增刪的頁面（單頁應用）沒量過。用 `HeapStats::fragmentation_at_marking`（`gc_bench` 的報告）量，中位數到了 old 的 committed 的 10% 再做。
  - **scavenge 照年齡 copy**：活下來的物件 copy 一次、第二次升到 old；V8 的整頁升上去（活得多的頁不 copy）和先標再整頁升上去（MinorMS）都沒做，沒有 pretenure 時，全部活著的工作（gc-tree 的錄製）每個物件 copy 兩次。真的頁面上有大量活很久、又不是同一個配置的地方（`Site`）配置的物件時再做。
  - **full GC 的門檻固定**：上次留下的 2 倍（最少 2 MiB），concurrent marking 在一半時開始（marking 期間可以再多長 V8 的 overshoot margin）。cppgc 是 1.5 倍，V8 照 GC 和 mutator 的速度在 1.1 到 4 倍之間調（`MemoryController`）；churn 放大 10 倍的 peak used 是 62 MiB，cppgc 52 MiB。真的頁面上量 peak used 和 GC 的時間再決定要不要動態調；marking 期間的 margin 在真的頁面上撞到幾次、heap 因此多長多少也一起量，再決定要不要照 V8 改成 old 大小的一半（或放寬成門檻的 2 倍）；開始 marking 的時機也可以照配置速度往前推（固定在門檻的 25% 量過比較差）。
  - **標記時數每個物件的配置的地方**：tenure 了的 `Site` 自己撤回要知道它的物件標到幾個，小物件的鏈和樹標記慢 4% 到 10%；量過的工作上沒有一個 `Site` 撤回過。真的頁面上也沒有撤過的話，改成沒有 `Site` 被 tenure 時不數，或照 V8 整個 old 一起撤回、標記時完全不數。
  - **concurrent marking 開始前的 scavenge 把活的全部升上去**（old 的 marker 才能跳過 young）：全部活著、nursery 最大（16 MiB）時這次停頓長，gc-tree 的錄製最長 3.3 ms（沒有 overshoot margin 時 17.8 ms，為什麼變短沒有查）。真的頁面上看它出現的頻率，常出現的話試開始前縮小 nursery、只升活過兩次的（marker 要能處理 young），或在 idle 時開始。
  - **空頁過一整輪 GC 就還給作業系統**，下一輪要用時重新 commit、付 page fault；V8 讓頁在 pool 裡待 8 到 16 秒、記憶體壓力時才立刻還。要 platform 有延後的 task 和記憶體壓力的訊號；真的頁面上量重新 commit 的成本和多留的 committed，和下面 mimalloc 的歸還一起定。
  - **有 `LocalExternal` 物件的頁整頁由 heap 的 thread sweep**（同一頁上 `Send` 的 finalizer 也在那裡跑），sweep 的 worker 只掃其他的頁；cppgc 讓 sweeper 掃所有的頁、有 finalizer 的死物件延後到 main thread 才放回格子。現在量的工作都沒有 finalizer；DOM 決定哪些物件帶 `External`、`LocalExternal` 時，量這種頁的比例和 heap 的 thread 的 sweep 時間（`HeapStats::sweep_on_main_ns`），再看要不要照物件分，或分散到幾個安全點掃。
  - **nursery 裡死掉的物件的 finalizer 在 scavenge 的停頓裡跑**（`Send` 的也是）；V8 的新生代 ArrayBuffer 在 minor GC 之後交給 worker 放。DOM 有大量短命、帶 `Send` finalizer 的物件時，量 minor GC 的停頓裡 `Drop` 佔多少，p99 超過 1 ms 或佔了明顯的一塊才改。
  - **零散存活時配置常走慢路徑**：一百萬個物件只留 16 個裡的一個（`ids` 的工作）時，old 的空區段平均只有 4 到 5 格，配置一段一段地換（`HeapStats::old_ranges`、`old_range_slots`），慢了多少沒量；其他工作平均每段幾百格。真的頁面上也這樣時，先量配置的時間，再看要不要 compaction 或別的挑頁方式。
- machopo 用 mimalloc（`shell` 的 `#[global_allocator]`），它延後歸還記憶體（`MIMALLOC_PURGE_DELAY` 到了，在下一次配置裡 `madvise`），GC 的停頓裡的任何一次配置都可能撞上：以前錄下的 DOM 工作的重播在 cppgc 的 heap 上量到 1.5 到 4.4 ms。Chrome 的 PartitionAlloc 由定期的 task 歸還（沒有查證）。改 machopo 整個 process 的 allocator 政策（例如在 idle 時歸還）要量 Speedometer 的記憶體和時間，新的 GC 跑真的頁面時一起評估，或另外做。
- **名稱表只增不減**（`dom` 的 `names.rs`：沒有固定編號的 local name、前綴、命名空間和事件型別，帶前綴或轉成大寫的 `nodeName`，放不進 bit 的 `QualifiedName`）：每個 renderer 的 main thread 一張，留到 thread 結束（關掉分頁），同一個分頁導覽到別的網頁也不清。節點、listener、style 的 index 和快取存的是編號，不是有計數的字串，表不知道哪個編號沒人用了；Blink 的 `AtomicString` 有計數，最後一個參照放掉時離開 `AtomicStringTable`。一般的網頁只加幾個到幾百個名稱（每個約 100 到 135 bytes），固定名稱的字串（`fixed_strings`，約 62 KB）每個 thread 只配一次；網頁一直用新的名稱（`'data-' + i` 的屬性、`'t' + i` 的事件型別、`createElement('x-' + i)`）時，每一百萬個約 120 MB，離開網頁也不還，到 2^27 個（`NAME_BITS`，約 16 GB）時 `intern` panic（和記憶體耗盡一樣整個程式結束，見「隔離」）。之後要回收時，在 full GC 標記還在用的動態名稱（型別的 layout 列出名稱的欄位，heap 外的持有者報上來），不照 Blink 計數：計數要每一種節點都有 finalizer。屬性值的表（`string.rs` 的 `VALUES`）會回收：長到上次留下的 2 倍時丟掉只剩它持有的值。
- **DOM 的 heap 沒有上限**（JS 文件和 wasm 文件的都是）：elise 的 cage（4 GiB）滿了就 panic，renderer 是 browser process 裡的 thread，整個程式跟著結束。Chrome 的 V8 超過 heap 的上限時先 `NearHeapLimitCallback`、再不行讓 renderer 當掉；machopo 等 renderer 拆成 process 時一起定。wasm guest 的 GC 物件和 DOM 在同一個 heap（`dom_wasm`），也一樣：Store 的 `ResourceLimiter` 管不到它，wasm 的配置不會因為超過上限而 trap。
- wasm guest 的 GC 物件和 DOM 在同一個 heap，guest 呼叫 DOM 的期間（Store 借出時）DOM 的安全點不 GC：GC 由會配置的 host 函式經過 Store 做（看得到 wasm 的 stack）；有兩個以上的 Store 同時借出（一個 guest 的呼叫裡又呼叫另一個的）時，裡面那層不做要 root 的 GC，配置的直接進 old，回到呼叫之間才收。
- wasmtime 的 stack switching（machopo 沒有開）上游 v50.0.1 有 bug：一串兩層以上的 continuation 暫停時做 GC，走那串 stack 時 panic（`trace_wasm_continuation_roots`）；fork 的 elise 每次配置都 GC 的測試碰得到，預設的 collector 在同樣的時間點從 host 呼叫 GC 也是。

## Parser 和載入

- XML document 的 `innerHTML`、`outerHTML`、`insertAdjacentHTML`、`Range.createContextualFragment`，和 `DOMParser` 的 XML 類型（`text/xml`、`application/xml`、`application/xhtml+xml`、`image/svg+xml`）丟 `NotSupportedError`：XML parser 只接到 SVG 圖片，沒有 XML 的序列化。`getHTML()`、`setHTMLUnsafe` 在任何 document 都照 HTML 的規則。XML parser（`xml5ever`）只用在 SVG 圖片的檔案：格式不對的 XML 照它修復後的樹處理（Chrome 用 libxml2，有任何錯誤就是壞圖），DOCTYPE 只認內部宣告、有值的一般 entity（外部的和 parameter entity 不認，展開的量和深度有上限，超過的引用照原樣留著；libxml2 會報錯）。
- processing instruction 序列化成 `<?target data>`（html5ever 的寫法），HTML 新的規則是 `<?target data?>`；parser 也還照舊把 `<?…>` 當成註解（`tests/wpt/tree-construction-expectations.txt`）。
- 沒有 Trusted Types（`innerHTML` 等收一般的字串）、Sanitizer API（`setHTML`、`setHTMLUnsafe` 的 `sanitizer` 選項），也沒有 declarative shadow DOM（`setHTMLUnsafe` 的 `<template shadowrootmode>` 照一般的 `<template>` parse）。
- XHTML 用 HTML parser：只處理了 CDATA，其他 XML 語法（例如自己關閉的非 void 元素）照 HTML 的規則解析。
- Body 一次收完，沒有串流，也還沒有 incremental parsing。WPT 裡靠伺服器分段送出、在兩段之間動 DOM 的測試因此不穩定（`moving-between-documents/` 的 external move-back，`.ini` 標成 `[PASS, FAIL]`）。
- 沒有宣告編碼時，只分辨「合法的 UTF-8」和「其他」（其他一律 windows-1252），沒有完整的編碼偵測。
- 沒有 `@import`、`@namespace`、`@layer`、`@container`、`@property` 這些 at-rule：parser 丟掉它們（at-rule 只收 `@media`、`@supports` 和 `@keyframes`），也沒有 CSS nesting。
- 沒有 web font：`@font-face` 忽略，也沒有 CSS Font Loading API（`document.fonts`、`FontFace`）；頁面和 canvas 的文字都只用系統的字型（測試時是 Ahem 和 Lato）。
- 字型名稱的對應照 Chrome 152 寫死在 `layout` 的 `font_families`（Blink 的替代名稱：Arial 和 Helvetica、Times 和 Times New Roman、Courier 和 Courier New；Linux 上 Skia 接受的尺寸相容字型；Linux 的通用字型照 Chrome 的出廠設定：`serif` 和清單最後的 standard 字型是 Times New Roman，`sans-serif` 是 Arial，`cursive` 是 Comic Sans MS，`fantasy` 是 Impact），所以：
  - Linux 上尺寸相容的字型只認 fontconfig 自己的 `30-metric-aliases.conf` 有對應的那幾類（Arial、Times New Roman、Courier New、Symbol、Cambria、Calibri 和它們的替代），照它的順序（Arial 先 Arimo、再 Liberation Sans）。Chrome 看的是系統的 fontconfig 實際給的第一個結果：系統或使用者的設定把名稱對到別的字型（例如發行版替 MS Gothic、SimSun 加上 Noto CJK 的別名），或改了 Arimo 和 Liberation Sans 的先後時，Chrome 跟著變、machopo 不會。
  - 沒有使用者改預設字型的設定（Chrome 的「自訂字型」），一律是出廠值。
  - `system-ui` 照 fontique 的（Linux 上是 fontconfig 的 `system-ui`），Chrome 照 GTK 的設定：Fedora 44 上 Chrome 是 Noto Sans，machopo 是另一個字型。
  - 沒有 em 的字型（`head` 的 units-per-em 是 0，或沒有 `head`：Apple 舊式的 bitmap 字型只有 `bhed`、`bdat`，例如 macOS 的 GB18030 Bitmap）不收：要它的文字照找不到字型時 fallback。Chrome 畫得出它的點陣字（macOS 上經過 CoreText，FreeType 也讀 `bhed`、`bdat`）；machopo 讀不了 `bdat` 的點陣，縮放 glyph 也要 em。
  - 沒有 `emoji`、`math` 這兩個通用字型：寫了它們當成字型名稱，找不到就換下一個（Chrome 的 `emoji` 用 emoji 字型畫數字和符號，`math` 照出廠設定是 Latin Modern Math）。
  - 每個 `font-family` 的值在字型集合裡查到的 family 會記住（`FontFallbackMap`），執行中安裝或移除系統字型不會讓它重新查（shaping 的快取也一樣）：要重開。Blink 在系統的字型變動時整個作廢（`FontCache::Invalidate`）。
- iframe 的 HTML 一次解析完整份 body，不是邊收邊解析：空的 `src` 的 `<script>` 的 `error` task 在 script 被移到別的文件之前就排了，WPT 的 `moving-between-documents/before-prepare-*-success-empty-src-*` 四份因此失敗。iframe 的 `load` 在跑子 frame 的 load task 的那一輪之後才分派（不在那個 task 裡，免得 wrapper 做在子 frame 的 realm）。
- 移到別的文件的元素的圖片還在載入時，舊的 window 拿著它，直到 window 不在；排進 task 之後 window 被丟掉的 Blob 的讀取不會 settle。

## 網路

- 沒有 cookie 和 HTTP cache，每次載入都重新向伺服器要。
- 沒有擋 Fetch 的 bad port（`fetch` 到 port 13、25 等照樣去連）：在 Windows 上連 localhost 那些 port 的請求可能等很久才結束，WPT 的 `request-bad-port.any.js` 在 Windows 上等到逾時。
- `fetch()`、module script、`modulepreload` 和帶 `crossorigin` 的 classic script 跨源時照 CORS；preflight 不快取：不是 simple 的跨源請求每次都先送 `OPTIONS`（Chrome 照 `Access-Control-Max-Age` 快取，預設 5 秒）。preflight 不帶 `Referer`（machopo 都不送）。沒有 cookie，`credentials` 只改變 CORS 要求對方的條件。
- HTTP/1 的回應的 status text 是 status 標準的 reason phrase（reqwest 不留伺服器給的）；HTTP/2 沒有 reason phrase，是空字串。request header 的名稱送出時一律小寫（hyper 的 HTTP/1），Chrome 照 script 給的大小寫。沒有 `Accept-Language`。request header 的值有控制字元（tab 以外 0x20 以下的 byte，Fetch 允許）時送不出去，是網路錯誤：hyper 的 `http` crate 不接受（WPT 的 `header-values-normalize.any.js`、`cors-preflight-not-cors-safelisted.any.js`）。伺服器回 421（Misdirected Request）時不換一條連線重送（Chrome 會，WPT 的 `request-upload-421.any.js`）。`fetch()` 的 `Origin` 不看 referrer policy（`no-referrer` 時 Chrome 送 `null`）。伺服器在 204、205、304 的回應後面多送 body（HTTP 不允許）時，hyper 照樣重用那條連線，下一個用到它的請求把殘留的 bytes 當成回應解析而失敗；Chrome 發現回應之後還有資料就不重用（`HttpStreamParser`）。WPT 的 `response-null-body.any.js` 因此不穩定，寫成 `disabled`。
- `Accept-Encoding` 只有 `gzip, deflate, br`（Chrome 還有 `zstd`），`net` 自己解壓（收完整份 body 之後）。
- 同時對同一個 HTTPS 伺服器發出的請求，在第一條連線由 ALPN 確認是 HTTP/2 之前各開一條連線，最後都走同一條、其他的關掉（hyper-util 的連線池；Chrome 的 `SpdySessionPool` 等第一條）。
- 沒有 `Content-Type` 時，只分辨 markup 和純文字，不像 Chromium 那樣完整地 sniff。
- DNS 失敗是從 hyper-util 的錯誤訊息辨認的（它沒有專用的錯誤型別）；升級 reqwest 時，`net` 的 `connection_failures` 測試會告訴我們它還對不對。
- 讀本機檔案的權限只看目前的 document 是不是 `file:`；Chromium 還會依 origin 做更細的限制。
- `file:` 的目錄是一份簡單的清單（上一層和每個項目的連結，目錄在前、照名稱排序），沒有 Chrome 那份的大小、修改時間和排序的按鈕；沒有尾端斜線的目錄網址不轉到有斜線的（Chrome 會），連結都是完整的網址。
- frame 不在了時，它還在路上的 `fetch()` 不取消：回應來了找不到 window，丟掉（Chrome 取消請求）。

## Style

- 支援的 property 是一份白名單（`crates/css/src/properties.rs`）。邊框的樣式都有；圓角的 `dashed`、`dotted` 沿著整圈的中線畫一個 pattern，間隔照整圈的長度調整，各邊交界的地方不一定是一段虛線或一個點；各邊寬度不同的 `double`、`groove`、`ridge`，角上的條紋照各邊自己寬度的比例接起來；`<fieldset>` 沒有 UA 的邊框（沒有 `<legend>` 的排版，它會落在邊框裡面，不是邊框上）；`transform` 只有 2D 的函式：有一個 3D 的函式（`translate3d()`、`translateZ()`、`rotateX()`、`perspective()` 這些）整條宣告就無效，所以強制成為 layer 的 `translate3d(0, 0, 0)` 連同同一條的 2D 函式一起丟掉（Chrome 照 3D 算）；沒有個別的 `rotate`、`scale`、`translate` property 和 `perspective`、`transform-style`、`backface-visibility`；`position` 有 `static`、`relative`、`absolute`、`fixed` 和 `sticky`（`-webkit-sticky` 是它的別名，和 Chrome 一樣；sticky 的限制見「Layout」）；邏輯屬性（`margin-inline-start`、`inset-block`、`border-inline-end-color`、`inline-size` 這些和它們的 shorthand）照 `writing-mode: horizontal-tb`、`direction: ltr` 對應到物理的（machopo 沒有這兩個 property），邏輯的圓角（`border-start-start-radius` 這些）也是；`z-index` 對有 `position` 的元素和 flex、grid item 生效；`width`、`height`、`flex-basis` 有 `min-content` / `max-content` / `fit-content`，但 `min-*` / `max-*` 沒有（taffy 的 `min_size`、`max_size` 放不進關鍵字；不 fork taffy，等上游），也沒有 `stretch`、`fit-content(<長度>)` 和加了 `-webkit-` 的寫法。長度沒有 `ex`、`ch`、`lh`、`cap` 和 container 的單位。CSS-wide 關鍵字只有 `initial`、`inherit`、`unset`，沒有 `revert`、`revert-layer`（WPT 的 `border-radius-valid.html` 有一項是它）。圓角沒有 `corner-shape`，也沒有 `-webkit-border-radius` 這類舊名字。
- 背景：`background-attachment` 的 `fixed`、`local` 照 `scroll` 畫（解析、cascade、序列化都有）；`background-clip` 沒有 `text`、`border-area`，`background-position` 沒有 `x-start` 這類邏輯關鍵字；圖片只有 `url()`（PNG、JPEG、GIF）、`linear-gradient()`、`radial-gradient()` 和它們的 `repeating-`，和選項是它們的 `image-set()`，沒有 `conic-gradient()`、`image()`、`cross-fade()`、`light-dark()`，漸層也沒有 `in <color space>`、只有一個色停點的寫法。`image-set()` 的 `type()` 只認 machopo 解得開的 MIME type（`image/png`、`image/jpeg`、`image/gif`、`image/svg+xml`），其他的選項跳過：寫了 `image/webp`、`image/avif` 等 Chrome 解得開的選項時，Chrome 可能選它、machopo 選別的。scale 改變之後，新選中的圖下載完之前那一層什麼都不畫。漸層的 hint 換成九個色停點近似（和 Blink 一樣）。inline 元素跨好幾行時，每一行的背景各自定位（沒有 `box-decoration-break: slice`，Chrome 照連成一個的盒子定位）；圓角也是：開頭的角只在它開始的那一行、結尾的角只在它結束的那一行，百分比的半徑照每一行的那一段算（Chrome 照連成一個的盒子算）。`display: inline` 的 `<body>` 的背景不傳到 canvas（只畫在它的每一行上；Chrome 照樣傳）：machopo 從 `<body>` 的盒子找背景，inline 元素沒有盒子。`background` shorthand 省略的顏色讀回 `rgba(0, 0, 0, 0)`（WPT 的 `background-valid.html` 有一處期待 `transparent`，另一處期待 `rgba(0, 0, 0, 0)`）。
- 顏色只有 named color、hex、`rgb()` / `rgba()`、`transparent` 和 `currentcolor`：沒有 `hsl()` / `hsla()`、`hwb()`、`lab()` 這類、`color()`、`color-mix()`、relative color（`rgb(from …)`）和 CSS Typed OM 的顏色物件；頁面和 canvas 的 `fillStyle` 一樣（WPT 的 `fill-and-stroke-styles/` 有四十多個因此失敗）。
- System color（`ButtonFace`、`CanvasText`……，連同已經不用的和 `-webkit-link`）：Windows 上照 registry 的系統色（`Control Panel\Colors`，和 Chrome 的淺色模式一樣），macOS 和 Linux 是 Blink 的預設（Chrome 在 macOS 上照 `NSColor`，在 Linux 上用 Chromium 自己的預設）；headless 和用測試字型的視窗也用預設。只在啟動 renderer 時讀一次：改了系統的設定，新的分頁才看得到（Chromium 會讓頁面重新 style）。沒有深色和 forced colors。`-webkit-focus-ring-color` 作者也能用（Chrome 只給 UA stylesheet）。
- `font` 的 system font（`caption`、`menu`、`-webkit-small-control`……）的 family 一律是 `system-ui`，大小照 Windows 上的 Chrome（控制項的 13.333px、`menu` 等的 12px，其他的 16px），不讀作業系統；Chrome 在 Windows 上算成 Arial 和系統的 UI 字型。
- 陰影和 outline：`outline-color` 沒有 `auto`。outline 的樣式是邊框的樣式（不含 `hidden`）和 `auto`，畫法和邊框一樣。`auto` 是 Chrome 在 Windows 和 Linux 上的 focus ring（2px 的 `-webkit-focus-ring-color`，`rgb(16, 16, 16)`，外面 1px 白色），macOS 上也一樣（Chrome 照系統的強調色）；block 的 focus ring 只圍住自己的盒子，Chrome 連超出它的子孫的盒子也圍進去（WPT 的 `outline-with-padding-001`）。inline 元素跨好幾行時，每一行的那一段各自有完整的 outline 和陰影：Chrome 的 outline 把各行連成一個外框，陰影照連成一個的盒子在斷行處切掉（`box-decoration-break: slice`，WPT 的 `slice-inline-fragmentation-*`）。
- flex 和 grid 的屬性：`justify-*`、`align-*`、`place-*` 沒有 `left`、`right`、`safe`、`unsafe`、`last baseline`、`legacy`；grid 沒有 `grid` shorthand、subgrid 和 masonry。
- 沒有 `overflow-clip-margin`：`overflow: clip` 裁在 padding box，replaced element（`<img>`、`<canvas>`，UA stylesheet 給它們 `overflow: clip`）的內容裁在 content box（Chrome 的 UA 給 `overflow-clip-margin: content-box`，作者改不了）。
- 自訂 property 和 `var()`：沒有 `@property` 和 `CSS.registerProperty`（每個自訂 property 都是沒有型別、會繼承的 token），`var()` 以外的代換函式（`env()`、`attr()`、`if()`）都沒有，自訂 property 的 `revert`、`revert-layer` 也沒有（當成一般的值）。代換是 token 的代換：兩邊的文字會連成一個 token 的地方（`var(--a)px`），machopo 在中間插入 `/**/`，`getComputedStyle` 讀自訂 property 時也看得到它。`getComputedStyle` 的 `length` 和 `item()` 把自訂 property 依名稱排在 longhand 之後（Chrome 照它的 hash table 的順序）。含 `var()` 的值每次 cascade 都重新代換、解析，沒有快取。`var()` 的名稱在解析時就要是自訂 property 的名稱：`var(var(--x))` 無效（Chrome 收，但它和 machopo 一樣還沒有 css-variables-2 的名稱代換）。
- `calc()`、`min()`、`max()`、`clamp()`：數字、整數和角度的在解析時就算出來，CSSOM 讀回的 specified value 是算出來的值（Chrome 寫成 `calc(0.5)`）；css-values-4 的其他數學函式（`round()`、`mod()`、`rem()`、`abs()`、`sign()`、三角函數、`pow()`、`sqrt()`、`hypot()`、`log()`、`exp()`）照 Chrome 152：參數都是標準單位（px、deg、s、dppx、數字）時在解析時算出來，否則（相對長度、百分比）留到元素上算；但在解析時就算出來的數字、整數、角度和時間裡，要元素才算得出來的（`z-index: sign(1em)`、`rotate(calc(90deg * sign(1em)))`）無效（Chrome 支援）。它們用 f64 算、結果是 f32，三角函數和指數函數的值最後一位可能和 Chrome 不同。沒有 `rgb()` 的各個值、`attr()`、`sibling-index()`、`progress()` 這些。`infinity`、`-infinity`、`NaN` 和除以 0 照 css-values-4（computed value 照 Blink 夾：長度到約 ±3,355 萬 px、字級到 10000px、角度到 `2.86708e+15deg`、NaN 是 0），但算的是 f32（Chrome 是 double）：`calc(1e38px * 10)` 讀回 `calc(infinity * 1px)`（Chrome `calc(1e+39px)`），時間的上限是 `3.40282e+38s`（Chrome `1.79769e+308s`）。長度的限制見「Layout」。
- Pseudo-class 有限：表單的有 `:checked`、`:indeterminate`、`:disabled`、`:enabled`、`:default`、`:placeholder-shown`、`:read-only`、`:read-write`、`:required`、`:optional`，custom element 的 `:defined`，還有 `:lang()`、`:target`、`:open`（清單開著的 select，有 `open` 的 `<details>`、`<dialog>`；沒有選擇器的 `<input>`）、`:window-inactive`（頁面沒有 focus 時），沒有 `:valid`、`:invalid`、`:in-range`、`:out-of-range`、`:user-valid`、`:autofill`；`:dir()` 等不支援。pseudo-element 只有 `::before`、`::after`（連同 CSS 2 的單冒號寫法）、`::marker`、`::selection`、`::placeholder` 和 `::-webkit-` 開頭的那些（控制項的 UA shadow tree 的部件：`::-webkit-input-placeholder`、`::-webkit-search-cancel-button`、`::-webkit-inner-spin-button`、`::-webkit-slider-thumb` 等，見下面表單控制項的那一條），其他的（`::first-line`、`::first-letter`、`::target-text`、`::part()` 等）讓整條規則無效；`@supports selector()` 不收 `::-webkit-scrollbar` 和它的部件（Chrome 收；Blink 的 scrollbar 部件不在 machopo 認得的 UA 部件的清單裡），樣式規則和 `querySelector` 收；`::slotted()` 之後的 `::placeholder` 收（Chrome 也收）但比對不到（slot 進來的控制項的 placeholder 不看 slot 那棵樹的規則）。`:read-write` 不看 `designMode`（machopo 沒有）；`:lang()` 只認得沒有 namespace 的 `lang`，不認得 `xml:lang`（`.xhtml` 也走 HTML parser）。content language 來自 response 的 `Content-Language`（照 Blink 取第一個逗號之前）和接上文件的、或接著時改了 `http-equiv`、`content` 的 `<meta http-equiv="content-language">`（照 HTML：`content` 有逗號時不算，取第一個 token；最後設的那個算，同 Blink）；沒有 `HTMLMetaElement.httpEquiv`。
- `element.style`：只認白名單裡的 property，其他的 `setProperty` 不做事、讀回空字串，attribute 裡 machopo 不認得的宣告在第一次經過 CSSOM 修改之後就不見了；camelCase 和 dashed 的屬性（`style.backgroundColor`、`style['background-color']`）照 Blink 是 named property，不是 prototype 上的 accessor（規範和 Gecko、WebKit 是，`Object.getOwnPropertyDescriptor(CSSStyleProperties.prototype, 'color')` 看得出差別；這樣 property 的清單只在 `style` 一處，加 property 不用動 bindings），每次存取經過 interceptor；沒有 `-webkit-` 的寫法、`cssFloat`；HTML 和 SVG 的元素有 `style`，其他 namespace 的元素（MathML）沒有。每次讀寫都從 attribute 解析整段 inline style（inline style 只存成 `style` attribute 的字串，沒有解析結果的快取）。
- stylesheet 的 CSSOM（`new CSSStyleSheet()`、`replace`、`replaceSync`、`insertRule`、`deleteRule`、`cssRules`、`media`，舊的 `rules`、`addRule`、`removeRule`，規則的 `CSSStyleRule`、`CSSMediaRule`、`CSSSupportsRule` 和它們的 `cssRules`、`insertRule`、`deleteRule`、`conditionText`、`media`，`CSSKeyframesRule`（`name`、`cssRules`、`length` 和 index 的 getter、`appendRule`、`deleteRule`、`findRule`）和 `CSSKeyframeRule`（`keyText`、`style`），`MediaList`），`adoptedStyleSheets`（`ObservableArray`），`document.styleSheets`、`ShadowRoot.styleSheets` 和 `<style>`、`<link>`、SVG 的 `<style>` 的 `sheet`）：adopt 的 document 和 shadow root 的都排在它自己的 stylesheet 之後。adopt 的清單、一份 stylesheet 的內容、`media` 或 `disabled` 改了，adopt 它的 document 整份、shadow root 整棵 shadow tree 重算 style（和 `<style>` 的原文改了一樣，見「Invalidation」）。`<style>`、`<link>` 的 sheet 透過 CSSOM 改了，照規則重算它們可能配到的元素（和原文改了一樣）。沒有 `@import`：`parentStyleSheet`、`ownerRule` 都是 `null`。`<link>` 的 `rel`、`href`、`disabled` 改了又改回來時，machopo 用之前載入的文字馬上做新的 sheet（Chrome 重新載入，載入之前 `sheet` 是 `null`；`href` 改了照樣不載入新的網址，見「Script」的 `modulepreload` 那一條）。規則只有 style rule、`@media`、`@supports` 和 `@keyframes`：machopo 的 parser 丟掉其他 at-rule（`insertRule` 收到它們丟 `SyntaxError`）和巢狀的規則，所以 `CSSStyleRule` 照 CSS Nesting 之前直接繼承 `CSSRule`（Chrome 112 起和規範是 `CSSGroupingRule`，style rule 有自己的 `cssRules`、`insertRule`、`deleteRule`；給了這些成員的話，偵測 nesting 的 script 會以為 machopo 支援）。`CSSMediaRule` 和 `CSSSupportsRule` 沒有 css-conditional-5 的 `matches`。keyframe 的 selector 只有 `from`、`to` 和百分比，沒有 scroll-driven animation 的 `entry 10%` 這種。
- Transition 和 CSS animation：沒有 scroll-driven animation：`animation-timeline` 只收 `auto`、`animation-range-start` / `-end` 只收 `normal`（machopo 的動畫都照 document 的 timeline 跑；其他的值當成無效，`@supports` 照實回答），`animation` 照 Chrome 重設它們；沒有 `animation-composition`（`auto` 的 duration 是 `0s`）；自訂 property 不 transition（`transition-property` 裡的 `--foo` 什麼都不做）。keyframe 在 style change 時在元素上算（base style、parent 的 style、root 的 font size 和 viewport 都沒變時沿用上次的；其他東西變了，例如 document 的 base URL 改了之後 keyframe 裡的 `url()`，要等這些之一也變了才重算），之後只插值。全部在 main thread 上：每個 frame 重算動畫的元素的 style、重畫和重新 raster 它所在的 layer，JS 忙的時候不動（Chrome 的 `transform`、`opacity` 在 compositor 上動）。timeline 的時間是 frame 開始時 renderer 的時鐘（和 `requestAnimationFrame` 的同一個，見「Bindings 和 DOM API」的 `Performance` 那一條）。`display` 不動畫（transition 和 keyframe 都是），沒有 `@starting-style`；grid 的 track list、`d`、背景圖、`font-style` 是一步（Chrome 有些情況會插值）。`transform` 的清單照 Chrome：同一種函式的前綴逐項插值，剩下的併成矩陣，照 css-transforms 1 的 2D 分解插值（Chrome 每個矩陣都照 3D 分解、用四元數轉，翻轉和 skew 的中間值不同）；矩陣是 f32（Chrome 是 f64），極端的值最後一位可能不同。`currentcolor` 和顏色插值時照那一邊的 `color` 解出來（Chrome 留著 `currentcolor` 的混合）。時間的 `calc()` 的宣告值寫成算好的值（`6s`，Chrome 寫 `calc(6s)`），和數字的一樣。沒有 `-webkit-transition*` 的別名。動畫的是 `font-size` 時元素自己的 `em` 跟著動，但動畫的 property 繼承下去時，子孫和 pseudo-element 每個 frame 都重新 cascade（Chrome 只重算繼承的部分）。document 不在任何 frame 裡（iframe 拿掉了）的元素的 transition 和 CSS animation 直接停掉，不發 `transitioncancel`、`animationcancel`。`linear()` 的 computed value 的百分比寫六位有效數字（Chrome 寫到小數第六位），stop 的百分比照 CSS 的 parser 是 `f32`（`60%` 是比 0.6 大一點的值，Blink 是 double），progress 剛好在這種 stop 上時用的是前一段；easing function 裡的 `calc()` 寫成算好的值（`steps(calc(5 / 2))` 寫成 `steps(3)`，Chrome 留著 `calc()`）；`steps()` 的步數最多 2147483647，computed value 照樣寫成整數（Chrome 寫成 `2.14748e+09`）。
- 頁面載入時 transition 可能自己跑起來：帶 `transition` 的元素在外部樣式表到之前被算過一次 style 的話（什麼時候會發生還沒查清楚，測試同時跑、機器忙的時候看得到），樣式表到了之後那個 property 從沒有樣式表時的值過渡到新的值，headless 在載入完成時取的那一張圖停在過渡的中間。Chrome 的樣式表擋住第一次 style，不會這樣。看到的例子：TodoMVC 的 `label` 的 `transition: color 0.4s`（`tests/scenarios/pages/todomvc-static.html` 因此把它關掉）。
- `getComputedStyle`：唯讀、live；`length` 和 `item()` 只列白名單裡的 longhand 和元素的自訂 property，其他 property 讀回空字串（shorthand 讀得到，從它的 longhand 合回；`font` 照 Chrome 省略 400 的粗細）。resolved value（layout 之後的 used value）只有 `width`、`height`、`padding-*`、`margin-*`、`transform` 的 matrix，和 `top` / `right` / `bottom` / `left`（給了值的位移保留 computed value，只有 `auto` 取 layout 算出來的，和 CSSOM 一樣），邏輯屬性照它對應的物理屬性，其他 property 回傳 computed value；`min-width`、`min-height` 和它們的邏輯屬性的 `auto` 讀回 `auto`（Chrome 對不是 flex、grid item 的元素讀成 `0px`）；`display: none` 的元素沒有盒子，照 Chrome 回 computed value（`transform` 回 `none`）；SVG 的元素沒有 CSS 的盒子，`transform` 照 Chrome 回它的 matrix，但百分比還沒有參考的 box（當成 0；Chrome 是 SVG 的 viewport）。`row-gap` / `column-gap` 的 `normal` 讀回 `0px`（Chrome 是 `normal`：machopo 的 `ComputedStyle` 裡就是 0）。pseudo-element 的參數：`::before`、`::after`、`::marker` 讀它的 style（沒有規則配到時是從元素繼承、沒有 `content` 的那一份，和 Chrome 一樣），`::placeholder` 讀文字控制項的 UA shadow tree 裡的 placeholder 元素的（沒有 `placeholder` attribute、沒有那個元素時是從元素繼承、沒有規則的那一份；Chrome 照樣比對規則），但 layout 相關的 property 讀 computed value，不是它的盒子的 used value（Chrome 照盒子算，例如 `width: 50%` 讀到 px）；machopo 沒有的 pseudo-element（和 `:marker` 這種只有 CSS 2 的四個才收的單冒號寫法）回傳沒有 style 的 declaration（每個值是空字串、`length` 是 0）；不以冒號開頭的照元素自己的；以冒號開頭卻解析不了的（`::bogus`、有 escape 的名稱）丟 `SyntaxError`，Chrome 回空的 declaration（WPT 的 `getComputedStyle-pseudo*.html`）。`display: none` 的 iframe 裡的 document 在 machopo 還是算 render 的，所以它的元素讀得到 computed style（Chrome 回沒有 style 的 declaration；WPT 的 `getComputedStyle-detached-subtree.html` 的那兩項）；不在樹上的元素和 Chrome 一樣沒有 style。
- Media query（`@media`、`<style media>`、`<link media>`、constructed stylesheet 的 `media`、`matchMedia`，和 `<img>` 的 `<source media>`、`sizes`）看 frame 的 viewport 和 device pixel ratio；`prefers-color-scheme` 一律是 `light`、`prefers-reduced-motion` 是 `no-preference`，`hover` 是 `hover`、`pointer` 是 `fine`（桌面的答案；headless 的 Chrome 說 `none`），不認得的 feature 是 unknown（Level 4 的三值邏輯）；`print` 一律不符合（沒有列印）。沒有 `@custom-media`、Level 5 的 `prefers-contrast`、`dynamic-range` 這些 feature（unknown），也沒有 `calc()`。`<link media>` 不符合的 stylesheet 照樣載入（和 Chrome 一樣，Chrome 降低它的優先順序）。
- Web Animations 的 JS API：`element.animate()`、`new Animation()`、`KeyframeEffect`（`AnimationEffect` 的 timing）、`effect` 和 `timeline` 可以設（timeline 只有 document 的或 `null`），CSS transition 和 CSS animation 沒有建構子，`getAnimations()` 沒有 `pseudoElement`，`TransitionEvent` 和 `AnimationEvent` 沒有 `animation`。`composite` 只有 `replace`（`KeyframeEffect.composite` 一律讀回 `replace`，設了不做事；keyframe 的 `composite` 照寫的讀回，但也是 `replace`）；沒有 `KeyframeEffect` 的 copy 建構子（`new KeyframeEffect(effect)`）和 `CSSPseudoElement`（`target` 是元素、`pseudoElement` 是字串）；keyframe 只給 JS（`machopo:dom` 沒有 `animate()` 和 `KeyframeEffect` - table 的 property：`caption-side` 只有 `top`、`bottom`（和 Chrome 一樣）。UA stylesheet 的 `th`、`caption` 的 `text-align` 是 `center`（Chrome 的 `-internal-center`、`-webkit-center` 連 block 的子盒子也置中）；沒有 quirks mode 的 table 規則（table 不重設字型和 `white-space`）。table 的 presentational hint 有 `<table>` 的 `width`、`height`、`border`、`cellspacing`、`cellpadding`、`align`，row group、row、cell 的 `valign`、`align`（`center`、`left`、`right` 是一般的關鍵字，Chrome 是 `-webkit-` 的那幾個），row 和 cell 的 `height`、cell 的 `width`、`nowrap`，`<col width>`、`<colgroup width>`（HTML 不對應 `<colgroup>` 的，照 Chrome），table 和它的各部分（column 也是）的 `bgcolor`、`background`，`<table bordercolor>`（照 Chrome：有它時 table 和 cell 的邊框是實線，HTML 照樣是 outset、inset）；沒有 `rules`、`frame`、`hspace`、`vspace`。cell 的邊框顏色是它自己的顏色或 table 的 `bordercolor`，不繼承作者給 table 的 `border-color`：Chrome 152 的 cell 會繼承（crbug.com/40745409，WPT 的 `table-border-color-not-inherited` 照不繼承寫）。cell 照 HTML 的 table model 找它的 table（它的 row 的 parent，或 row group 的），Chrome 找 flat tree 裡最近的 `<table>` 祖先：只在 HTML 的 table model 裡沒有 cell 的 markup 不同。
- `pointer-events`：HTML 的盒子只看 `none`，其他的值當成 `auto`（和 Chrome 一樣）；SVG 的圖形照全部的值。
- 只解析、沒有效果的 property（cascade、繼承、`getComputedStyle` 照 Chrome，`@supports` 也回答支援）：字型的 `font-size-adjust`（`from-font` 讀回 `from-font`，Chrome 讀回字型的度量）、`font-language-override`、`font-variant-emoji`、`font-variant-alternates` 的函式（machopo 沒有 `@font-feature-values`；`historical-forms` 有效果）、`border-image` 和它的 longhand（邊框照 `border-style` 畫，圖片不畫也不下載；`border` 照 Chrome 重設它）、`user-select`（照 Chrome 繼承，規範不繼承；使用者還選不了頁面的文字，它只決定 `cursor: auto` 在文字上是不是 I 形）、`-webkit-user-modify`（只有表單控制項能編輯）、`forced-color-adjust`（沒有 forced colors 模式）、`-webkit-tap-highlight-color`、`text-size-adjust`（不放大行動版的文字）、`-webkit-font-smoothing`（文字照舊畫）、`resize`（不畫拖曳的把手）、`scroll-behavior`（見「捲動」）。`-webkit-user-select`、`-webkit-text-size-adjust` 是別名，`cssText` 寫沒有前綴的名字（和 Chrome 一樣）。
- 字型的 property：`font-variant-*`、`font-feature-settings`、`font-kerning` 照 Blink 的順序成為 OpenType feature（`font-feature-settings` 最後），`font-stretch` 選字寬，`font-variation-settings` 和 `font-optical-sizing: auto`（`opsz` 是字級）設可變字型的軸，畫的時候也照這些軸。字型沒有的 feature 不合成：small caps（`font-variant-caps`）和上標、下標（`font-variant-position`）只用字型的字形（Blink 字型沒有時縮小大寫、縮小並移動），所以 `font-synthesis-small-caps` 沒有效果；`text-rendering` 只有 `optimizeSpeed` 有效果（關掉 kerning 和連字，Chrome 的 `geometricPrecision` 在 macOS 以外還關掉 hinting，machopo 本來就不 hint）；`font-feature-settings` 的值超過 65535 時當成 65535。
- `:has()` 對 option、optgroup 的 `disabled` 改變不重算（WPT 的 `css/selectors/invalidation/has-with-pseudo-class.html`）。

## Layout

- 只有 block、inline、flex、grid 和 table layout（各有 inline-level 的 `inline-block`、`inline-flex`、`inline-grid`、`inline-table`）和 float。絕對定位有了，但：`position: relative` 的 inline 元素（不是 atomic inline）不是它裡面的絕對定位盒子的包含塊（machopo 的 inline 元素沒有盒子；包含塊是更外面的 positioned 盒子）；`getComputedStyle` 對絕對定位盒子的 `auto` inset 照包含塊的 padding box 算，grid container 的絕對定位子盒子不照它的 grid 區域（排版照區域；WPT 的 `css/cssom/getComputedStyle-insets-grid.html`）；`position: fixed` 的包含塊是 viewport，或有 `transform`、`filter`（根元素的除外）、`contain: layout` / `paint` 的祖先（它們也接住 absolute 的盒子；Chrome 的 `will-change`、`perspective` 這類 machopo 沒有）。`display` 只接受 `block`、`inline`、`inline-block`、`flow-root`、`flex`、`inline-flex`、`grid`、`inline-grid`、`-webkit-box`、`-webkit-inline-box`、`list-item`、`contents`、`none` 和 table 的值（`contents` 的元素不能 focus，Chrome 可以；replaced 元素和表單控制項的 `contents` 在建盒子時當成 `none`，computed value 照舊是 `contents`，Chrome 是 `none`；SVG 的元素的 `contents` 不照 css-display 的規則（`<g>`、`<tspan>`、`<use>` 這類排它們的內容，其他的不畫），照它原本的 `display` 畫；沒有 `run-in`、`ruby`、`block flow-root`、`inline list-item` 這類雙值的寫法等）。
- `position: sticky`：layout 照 relative 排、不移動，layout 之後照 Blink 為每個捲動容器（和 viewport）算出它裡面的 sticky 盒子的限制，捲動時重算位移，`getBoundingClientRect`、`offsetTop`、hit test 和畫面都用它。但：表格的 row group、row 和 cell 不會黏（照 relative 排；Chrome 的 containing block 是 table），非 atomic 的 inline 元素也不會（machopo 的 inline 元素沒有盒子）；沒有 `direction` 和 writing mode，一軸的兩個 inset 都放不下時一律讓結尾那一側（Chrome 在 rtl 的 containing block 裡讓左邊）；只有一軸捲動的容器（另一軸 `overflow: clip`）不是 machopo 的捲動容器，Chrome 的 sticky 照軸各自找捲動容器（`SingleAxisScrollContainers`）。捲動時 compositor 移動 sticky 盒子的 layer（和 Chrome 一樣），但在 opacity、`filter`、非平移的 `transform` 或路徑的 `clip-path` 底下的，在 fixed 盒子裡的，和在沒成為 layer 的捲動容器裡的，畫在所在的 layer 裡：compositor 捲動之後，要等 main thread 收到捲動、重畫才移到新的位置（Chrome 的 composited transform 和 render surface 讓它們也成為 layer）。sticky 盒子可能移到一個成為 layer 的捲動容器上時，滾輪落在 sticky 盒子上要等 main thread（machopo 的 compositor 只照範圍判斷滾輪給誰，Chrome 照 layer 做 hit test）。
- table：有 fixup（匿名的 table、row group、row、cell）、auto layout 的欄寬（照 Blink 的分配：cell 的 min-content / max-content 寬度、固定和百分比的 `width`、`colspan`）、fixed layout、列高（`rowspan` 和 table、row group 的 `height` 照 Blink 分給列）、`border-spacing`、cell 的 `vertical-align`、caption、baseline，畫的時候照 Blink 的層次（table 的邊框和背景只包住格子，column group、column、row group、row 的背景畫在 cell 裡）。column 和 column group（`<col>`、`<colgroup>`、`span`）照 Blink 給欄寬和背景，`visibility: collapse` 的 row、row group、column、column group 照 Blink 收起來。`border-collapse: collapse` 照 Blink 的 `TableBorders` 決定每一段邊、由 table 畫（cell 的邊框是它四邊的一半，table 沒有 padding 和間距）。和 Chrome 不同的：跨過收起來的欄或列的 cell 照縮小的大小排，溢出的內容不裁掉（css-tables 3 要在欄、列的位置裁掉，WPT 的 `visibility-collapse-colspan-003`、`visibility-collapse-rowspan-005` 照它）；collapsed 的邊框照 computed 的寬度比，Chrome 的邊框寬度在 computed value 就取整到 device pixel（5.95px 是 5px），小數的寬度比較的結果可能不同；沒有 `direction`，欄一律從左排；row 的百分比 `height` 不算；cell 只在它是 out-of-flow 盒子的包含塊（positioned、有 `transform` 或 containment）、或有百分比高度的 child 而且高度有設定（它自己或 table 的 `height`）時照列的高度再排一次，其他照內容排一次再拉成列的高度；Blink 量有固定高度的 cell 時，裡面百分比高度的 replaced 元素和捲動容器不算高度、百分比照 cell 的 `height` 算，machopo 照內容量；只有跨進來的 cell 的空列，Blink 有特例（不給高度、高度給第一列），machopo 照一般的分攤；沒有 cell 的列，Blink 不算 border spacing，machopo 照算；`table-layout: fixed` 而且 `width` 是百分比的 table 在 block 裡的 max-content 寬度，Blink 當成「無限大」（讓它撐滿容器），machopo 照一般的算；table 的 `overflow` 照 padding box 裁切、caption 也在裡面（Blink 只裁格子，caption 在 machopo 沒有的 wrapper box 裡）；table 的 `clientWidth`、`scrollWidth` 這些照 block 算（Blink 的含邊框、`clientLeft`、`clientTop` 是 0）；grid item 的 table 的大小是 taffy 的 grid 給的，固定大小的軌道比 table 的內容小時 table 跟著縮小（Blink 的 table 不比內容小；block、flex 和絕對定位裡不會）。 `colspan`、`rowspan`、`span` 大到超過 2147483647 時排版當成沒寫（1），Chrome 夾到上限（1000、65534），和 `colSpan` 這些 IDL attribute 讀到的一樣。
- 生成內容：`content` 只有 `normal`、`none`、字串、`attr(<名稱>)`（HTML 元素的屬性名稱不分大小寫）、`counter()` 和 `counters()`；沒有 quote（`open-quote`、`quotes`）、`url()`、`/` 之後的替代文字、css-values 5 的有型別或預設值的 `attr()`，也沒有用 `content` 取代元素自己的內容。生成的文字沒有 text 節點：選不到、不在 `Range` 的幾何裡（和 Chrome 一樣）。`<input>`、`<textarea>`、`<select>` 不產生 `::before`、`::after`（Chrome 對 text 類的 `<input>`、`<textarea>`、`<select>` 也不產生；checkbox、radio 等其他 `<input>` 在 Chrome 有沒有還沒查）。
- float：`float: left | right` 和 `clear: none | left | right | both`（沒有 `inline-start`、`inline-end`）。行內內容的 max-content 寬度把裡面的 float 加在最寬的那一行旁邊，Chrome 加在 float 所在的那一行：float 不在最寬的那一行時，shrink-to-fit 的盒子比 Chrome 寬。taffy 的限制：寬是 0 的 float 和它旁邊的 BFC 盒子的邊界情況和 Chrome 不同（`css/CSS2/floats/zero-width-floats.html`、`zero-space-between-floats-003.html`）；自己是 block formatting context 的盒子照它的高度避開 float，但高度是內容決定的盒子，移到比較窄的地方之後沒有照新的寬度重排（Chrome 會；`css/CSS2/floats-clear/floats-bfc-003.html`）。旁邊有 float 的盒子、和把 float 放進同一個 block formatting context 的盒子，每次 layout 都重排（taffy 的快取不知道 float）。
- SVG：最外層的 `<svg>` 是 replaced element，大小照 Chrome（`width`、`height` 屬性是 CSS 的 presentation attribute，也是它的自然大小（是長度、不是百分比時），CSS 蓋過它們時照樣是；比例是兩者的、只有一個或都沒有時是 `viewBox` 的；只有 `viewBox` 時撐滿 containing block 的寬、高照比例，什麼都沒有時 300×150），百分比的高度和 `<img>` 一樣當成 `auto`；畫的有 `<g>`、`<a>`、巢狀的 `<svg>`（照 `x`、`y`、`viewBox` 放、裁切到它的 viewport）、`<use>`、`<symbol>`（只在 `<use>` 參考它時）、`<switch>`、`rect`、`circle`、`ellipse`、`line`、`polyline`、`polygon`、`path`，`fill`、`stroke` 和 stroke 的各個 property、`opacity`、`transform`、`visibility`。`<text>`、`<tspan>` 和文字裡的 `<a>` 畫得出來（`x`、`y`、`dx`、`dy`、`rotate` 的清單、`text-anchor`、填色和描邊、漸層，空白照 CSS 的 `white-space` 和 `xml:space`；字元的格子打得到），但沒有 `textPath`、`textLength` / `lengthAdjust`、`dominant-baseline` / `alignment-baseline` / `baseline-shift`、直書、`text-decoration` 和 `text-shadow`（Chrome 都有）；雙向文字照邏輯順序放每個字元，從右到左的 chunk 的 `text-anchor` 也照左到右算（Chrome 照視覺順序）；位置清單照 Unicode 的字元數（Chrome 照 UTF-16 的 code unit，BMP 以外的字元會差一格）。還不畫：`<image>`、`foreignObject`（裡面的 HTML 看不到），以及 marker、`mask`、`<filter>`（CSS 的 `filter` 的函式有，`url()` 沒有）、pattern（`url()` 的 paint 用它的 fallback，沒有 fallback 就不畫）、`paint-order`、`vector-effect`。漸層（`linearGradient`、`radialGradient`）畫得出來，但 `url()` 只認同一份文件裡的 `#id`（寫成完整網址的同一份文件，Chrome 也找得到，machopo 用 fallback），沒有 `color-interpolation: linearRGB`（Chrome 也沒有）。圖形照它的幾何和 `pointer-events` 打到（fill 照 fill rule、stroke 照它的外框；hit test 用 `kurbo` 算，conic 換成三次曲線近似，邊緣和 Chrome 的 Skia 可能差不到一個像素），SVG 的 `<a>` 點了換頁。SVG 的子孫沒有 CSS 的盒子，但畫出來的可以 focus（有 `tabindex` 的、有連結的 `<a>`；和 Chrome 一樣，有 `focus`、`blur` 這類 listener 的圖形元素也能 `focus()`，但不在 Tab 的順序裡），`outline` 和 focus ring 照 Chrome 畫在元素自己的座標裡，圍住它畫的範圍（stroke 算寬度的一半；Chrome 對路徑和多邊形照 stroke 實際的外框，尖角的 miter 超出的部分 machopo 不算），`getBoundingClientRect()` 是它的 bbox 換算到 viewport 的一個框。`<defs>`、文件裡的 `<symbol>` 和 `display: none` 的 `<g>` 是隱藏的容器（不畫、打不到、不能 focus，但裡面的元素算得出 bbox 和矩陣，和 Chrome 一樣）；`<svg>` 外面的 SVG 元素沒有盒子。`getBBox()`、`getCTM()`、`getScreenCTM()` 照 Chrome 152（沒有面積的圖形的 bbox 是它的位置，隱藏的容器裡的元素有 bbox；WPT 照較新的 SVG 2 決議要 0），但：矩陣在 layout 裡是 `f32`（Chrome 是 `double`），旋轉這類的值最後幾位可能不同；沒有 layout 節點的巢狀 `<svg>`（`display: none`）裡的元素，`getCTM()` 不含那個 `<svg>` 的 `x`、`y` 和 `viewBox`（Chrome 從 attribute 算）。`transform-box` 的 stroke bounding box 和 Chrome 一樣是近似的：矩形、圓、橢圓往外擴半個描邊寬度，其他照 `stroke-miterlimit` attribute）。`elementsFromPoint` 照 Chrome 152：SVG 的容器（`<g>`、巢狀的 `<svg>`、`<a>`、`<use>`）不列，文字只列字元所在的最內層元素（WPT 的 `elementsFromPoint-svg.html` 和規範要列出容器）；`pointer-events: bounding-box` document 裡的元素（`#id`；別的檔案要 XML parser，`data:` 的網址 Chrome 也不畫）；它畫的 copy 不是 DOM 的節點（Chrome 是 `<use>` 的 shadow tree 裡的元素），是 style 那一步給 `<use>` 的一組 style，所以 copy 沒有自己的 `:hover`、`:active`（照原本的元素的狀態比對）；點到 copy 時事件的 target 是 `<use>`（和 Chrome 一樣），但原本的元素上的 listener 不會被叫到（Chrome 把它們複製到 copy 上）。一個 `<use>` 的 copy 超過一萬個元素時（互相參考的 `<use>` 會指數地長大）什麼都不畫（Chrome 全部複製）。`<switch>` 和 `systemLanguage` 照固定的語言 `en-US`、`en`（和 `navigator.languages` 一樣），`requiredExtensions` 只認得 HTML 和 MathML 的 namespace（和 Chrome 一樣）。`<svg>` 不發 `load` 事件（Chrome 在它的內容解析完之後發，`<svg onload>` 會執行；WPT 的 `change-sync-for-nested-use.html` 等它）。
- **Flex 和 grid**：
  - flex 演算法是 taffy 的，它不合規範的地方也是 machopo 的：flex base size 被 `max-width` 限制、量 item 的 min-content 時 item 自己的 `height` 沒有傳給子孫、換行的 column container 的自動最小高度、wrap-reverse 的 column 裡 `align-items: baseline` 的 item 排在 line 的右緣。grid 演算法也是 taffy 的，最多 10000 條 track（taffy 的 `MAX_GRID_TRACKS`；`grid-template-areas` 的 computed value 照寫的保留，排版只到那裡，Chrome 到一百萬條）：跨過 `fr` 和固定 track 的 item 讓 `min-content` 的 grid 太窄、高度不確定的 grid 裡 flex factor 加起來小於 1 的 `fr` 列照 item 的高度排，知道 grid 的高度之後沒有重排（Chrome 會，列和它的 grid 區域只有一半高）。每一項由過不了的 WPT 測試標出來（它們在 `tests/wpt/metadata/` 的 `.ini` 是預期的失敗，註解寫著原因）。taffy 的 fork 跟著上游的 main，上游修好時跟著拿到。
- `calc()`：computed value 是一個長度加一個百分比，所以 `min()`、`max()`、`clamp()` 和 `round()`、`mod()`、`abs()`、`hypot()` 這類函式裡同時有長度和百分比的（`width: min(100%, 600px)`、`round(1em, 3%)`）無效（Chrome 支援）；只有長度、或只有百分比的照常。除以 0 的 `calc()` 無效（規範是無限大再夾值）。
- min-content 寬度（parley 的 `calculate_content_widths`）：`white-space: pre-wrap` 保留、會掛在行尾的空白也算進去；零寬連接字元（U+200D）旁邊的空白之後不能斷行；歐甘文的空白（U+1680）不會掛在行尾。
- List 和 counter：
  - counter style 只有預先定義的 `disc`、`circle`、`square`、`disclosure-open`、`disclosure-closed`、`decimal`、`decimal-leading-zero`、`lower-roman`、`upper-roman`、`lower-greek`、`lower-alpha` / `lower-latin`、`upper-alpha` / `upper-latin` 和 `none`；其他名稱（`armenian`、`georgian`、CJK 的……）照收、照寫回，畫成 `decimal`（沒定義的 style 的 fallback）；沒有 `@counter-style`、`symbols()`。counter 的值不收 `calc()`。
  - 沒有 marker 的圖片：`list-style-image` 只收 `none`（`url()`、gradient 讓宣告無效），`list-style` 也是。
  - disc、circle、square 畫成 `• `、`◦ `、`▪ ` 這幾個字（從 fallback 的字型）；Chrome 畫成照字型大小算的圖形（Blink 的 `ListMarkerPainter::PaintSymbol`），大小和位置差一點。
  - outside marker 放在 list item 第一行的開頭之前（照 float 移，不照 `text-align`）；list item 沒有行時放在 content box 的開頭，旁邊有 float 時 Chrome 放在 float 之後。
  - `::before`、`::after` 是 `display: list-item` 時沒有自己的 marker（`::before::marker`），也不算 `list-item` 的 increment。
  - `::marker` 只套用 css-pseudo 4 列的 property（字型、`color`、`content`、`white-space`、文字的 property），counter 的 property 不套用；沒有 `unicode-bidi`（UA stylesheet 的那一條）。
  - quirks mode 的 `li { list-style-position: inside }`（在清單外的 `<li>`）沒有。
  - counter 照 css-lists 3 的「Inheriting Counters」（和 Chrome 一樣，前一個兄弟 reset 的 counter 在父元素已經有同名的時候不繼承）；照舊 CSS 2 scope 的 WPT（`counter-list-item-2.html`、`counter-reset-reversed-siblings-003.html`）和 Chrome 一樣失敗。
  - 文件有 counter 時，每次 layout 有內容要重新收集（插入、移除、不只影響繪製的 style 變化），就整份文件重算一次 counter（Blink 只在 counter 相關的改動時重算）：只走 DOM 和讀 computed style，但大的文件每次都多一趟。
- 不同元素裡的文字分開 shape：空白和下一個元素開頭的字之間沒有 kerning（`, <span>Third`），Chrome 有。生成的文字（`::before`、`::after`、marker）也和旁邊的文字分開 shape。
- `text-indent` 只有 `<length-percentage>`（`hanging`、`each-line` Chrome 也沒有）；`word-spacing` 只收 `<length>`（css-text 3 的百分比 Chrome 也沒有）；`letter-spacing` 在每個字元之後都加，一行最後一個字元之後也加（照 Chrome）；零寬的格式字元（U+200B 等）之後不加。
- 長度單位沒有 `ch`、`ex`（要字型的 metrics）：用它們的宣告整個無效（WPT 的 `css/css-text/` 有一大半用 `width: 5ch`）。
- `hyphens`：只在軟連字號（U+00AD）斷字，`auto` 沒有斷字的字典，和 `manual` 一樣（Chrome 照 `lang` 斷字）；沒有 `hyphenate-character`、`hyphenate-limit-chars`、`hyphenate-limit-lines`。行尾的連字號是 U+2010，軟連字號的第一個字型沒有它時是「-」（和省略號一樣以「排在同一個字型」判斷）。連字號接在軟連字號那段文字的後面：軟連字號後面緊接著元素的結束邊緣（padding、border）時，連字號畫在邊緣之內、蓋住它（parley 留的空間在邊緣之後；Chrome 的連字號在元素之內，邊緣在它後面）。一行有兩種方向的文字時，連字號照段落的方向放在整行的文字的末端（Chrome 照 bidi 重排，在軟連字號那段文字的末端）。連字號和省略號一樣不是文字節點裡的文字（hit test 到它找到它所在的元素）。希伯來字母之間的軟連字號不斷（ICU4X 的 UAX #14 還是 Unicode 15.1 以前的 LB21a）。
- `overflow-wrap: break-word` 和 `anywhere` 在 `word-break: keep-all` 的文字裡不斷行（parley 的 `keep-all` 關掉所有的斷點；Chrome 在整個字放不下時照樣斷）。
- `text-transform`：沒有 `full-width`、`full-size-kana`；大小寫的對應不看 `lang`（Chrome 照 locale 有土耳其文的 i、立陶宛文、希臘文的特例）；`capitalize` 的字的開頭以一個文字節點的文字加它前一個字元來判斷（Blink 也是）。
- `white-space-collapse` 沒有 css-text 4 的 `preserve-spaces`、`discard`（Chrome 也沒有）；`text-wrap` 只有 `wrap`、`nowrap`，沒有 `text-wrap-style`（`balance`、`pretty`、`stable` 無效，Chrome 有）。
- `text-overflow` 只有 `clip`、`ellipsis`：沒有 `<string>` 和兩個值（Chrome 的 `<string>` 還在 flag 後面）。省略號是 U+2026，block 的第一個字型沒有它時是「...」（machopo 以「U+2026 和 `X` 排在同一個字型」判斷，Blink 問 primary font 有沒有這個 glyph）；用 block 的 style，沒有 `::first-line`。只有由左到右、橫排。截行在 layout 做，捲動之後不重新截（css-overflow 4 允許捲動時露出被截的內容）。被隱藏的 atomic inline 連同它裡面的定位元素一起不畫（Blink 在有定位的後代時不隱藏它）。
- `clip`、`clip-path`：`clip-path` 沒有 `shape()` 和 `circle()`、`ellipse()` 的 `closest-corner`、`farthest-corner`；`polygon()` 的 `round` 照 machopo 自己的算法畫圓角（相鄰兩邊的切線上的圓弧，最多到邊的一半；和 Chrome 的可能差幾個像素）。非 atomic 的 inline 元素上的 `clip-path` 沒有作用（machopo 的 inline 元素沒有盒子；Chrome 照它每一行的框的外框裁）。包含塊在外面的 out-of-flow 盒子不被祖先的 `clip-path` 裁到，固定在 viewport 的 `position: fixed` 盒子也不被祖先的 `clip` 裁到：它們照包含塊的 clip（畫的順序和 `opacity` 照樹上的位置）；Chrome 裁它們（`clip` 是 `CssClipFixedPosition`）；根元素的 `clip-path` 不裁 canvas 的背景（Chrome 裁）。`clip-path: url()` 只認同一份文件裡的 `<clipPath>`（`#id`；別的檔案的什麼都不裁）；裡面有 `<text>` 或 `<use>` 的 `<clipPath>` 什麼都不裁（Chrome 用它們的形狀裁），裡面的形狀自己的 `clip-path` 也不算（Chrome 先用它裁那個形狀）。`<clipPath>` 裡的長度的百分比照被裁的元素的 viewport 算（HTML 元素是它的 border box；Chrome 照 `<clipPath>` 所在的 `<svg>`）。路徑的裁切底下不成為 compositor 的 layer：這樣的捲動容器捲動時在 main thread 重畫，canvas 畫進頁面（Chrome 用 mask layer，`SynthesizedClip`）。
- `filter`：只有函式（`blur()`、`brightness()`、`contrast()`、`drop-shadow()`、`grayscale()`、`hue-rotate()`、`invert()`、`opacity()`、`saturate()`、`sepia()`），沒有 `url()` 和 SVG 的 `<filter>`，也沒有 `backdrop-filter`、`mix-blend-mode`（`isolation` 因此只影響 stacking context）。顏色的函式在 sRGB 裡算（和 Chrome 一樣，不是規範預設的 linearRGB）。filter 底下不成為 compositor 的 layer：整個畫進所在的 layer，filter 的動畫每個 frame 在 main thread 重畫（Chrome 的 filter 和它的動畫由 compositor 做）；裡面的 op 每個 tile 都播，大的 filter 區域會慢。根元素的 `filter` 不套在畫在 canvas 上的背景上（Chrome 套）。數字和百分比的 `calc()` 寫回時是它的值（`brightness(calc(3))` 讀回 `brightness(3)`，Chrome 照寫的）。
- `contain`：沒有 `contain-intrinsic-size`（size containment 的盒子的 intrinsic 大小一律是 0，grid 照它的 track），也沒有 `content-visibility` 和 `container-type`。style containment 只限制 counter 的範圍（machopo 沒有 quote）。有 containment 的 `<img>` 這類 replaced 元素沒有 natural 的比例，`width`、`height` attribute 給的比例也沒有（machopo 沒有 `aspect-ratio`；Chrome 照它）。stacking context 照 `display` 判斷，`display: inline` 的 replaced 元素有 layout、paint containment 時也不是（Chrome 是）。
- line clamp 只有 `-webkit-line-clamp`，在 `display: -webkit-box`、`-webkit-inline-box` 加 `-webkit-box-orient: vertical` 時才有作用（Chrome 出貨的這個組合），沒有標準的 `line-clamp`、`max-lines`、`block-ellipsis`、`continue`（Chrome 也還沒出貨）。省略號和 `text-overflow` 的一樣，用那份行內內容的 block 的 style。被 clamp 掉的行和盒子照排、不畫、打不到。`text-align: justify` 的 clamp 的那一行先左右對齊、再放省略號（Chrome 先放再對齊；靠右、置中的照 Chrome）。`-webkit-box` 照 Chrome 對到 flex，但沒有 `direction`，從右到左的照從左到右排。
- 文件大小不算 transform，也不含最後的 margin。
- transform 的矩陣是 f32（Blink 是 double）：幾個 transform 疊起來（兩個 `rotate(45deg)` 合成四分之一圈）時位置差到約 1e-5 px，剛好在像素邊上的邊緣的抗鋸齒差一階（WPT 的 `css-transforms/group/svg-transform-nested-007.html`）。
- **Inline box**：
  - `vertical-align`：`sub`、`super` 的位移是父元素 `font-size` 的 1/5 和 1/3（Blink 各多 1px）；`middle` 用的 x-height 是字型 `OS/2` 表的，沒有時是 ascent 的 0.56 倍（parley 照 Blink 的估法）。只有 CSS 2 的值，沒有 css-inline 3 的 `first`、`last`、`alphabetic` 等。
  - `inline-block` 的 baseline 是它裡面最後一行的，`overflow` 不是 `visible` 時是下 margin 邊（照 Chrome；CSS 2.2 取兩者較高的，四個主要瀏覽器都沒照做）；裡面最後的是 flex 或 grid container 時，用的是它最後一個有 baseline 的 item 裡最後一行的，不是規範的 container 的「last baseline set」。沒有 `baseline-source`。checkbox、radio 以外的 `<input>` 的 baseline 和 Chrome、Firefox 不同（差幾 px 到整個框高，`overflow` 是 `visible` 時也是；它們讓文字類的照樣是 `visible`、文字垂直置中，`color`、`range` 這類照 content box 或 replaced element 的規則），還沒有規範（whatwg/html#5065），WPT 的 tentative 的 `baseline-alignment-and-overflow.tentative.html` 因此有 114 項失敗。
  - 只有由左到右：開頭的邊界一律是左邊，沒有 bidi。
  - Inline 元素不會變成 stacking context：它的 `opacity`、`transform`、`filter` 和 `isolation` 沒有作用。
  - Inline 元素的 `position: relative` 只有位移：照它那一行原本的順序畫（CSS 2 附錄 E 第 7 步，不是第 8 步），`z-index` 對它沒有作用；放在它裡面的 block 不跟著位移（box tree 把 inline 元素拆開，block 是外面的 block container 的 child）。`inline-block` 這些 atomic inline 照完整的規則。
  - 一個 block 裡如果只有空的 inline 元素（例如 `<span style="padding: 10px"></span>`），不產生行，也就不畫它。
  - `<br>` 的字型和 `line-height` 撐高它所在的那一行（`<div>XX<br style="font-size: 40px">X</div>` 在 20px 的 Ahem 裡是 60px）：Chrome 152 的 `<br>` 不影響行高（40px）。
  - 強制換行（`<br>`、`white-space: pre` 的換行，`content` 的 `\A`）之後緊接著的元素結束邊，排在下一行的開頭（它的 end padding、border 跟著到下一行）；Blink 把強制換行之後的結束標記留在換行的那一行（WPT 的 `css/CSS2/generated-content/content-175.xht`）。
  - 沒有 strut：行高只來自文字和 atomic inline；inline box 的 content area 用它自己文字的字型，這一行上沒有它的文字時，改用它裡面的文字，都沒有就填滿整個行框。
  - Inline box 的高度（`getBoundingClientRect`、DevTools 的盒模型和框）和 Chrome 不同：20px 的 Times 的 `<span>`，machopo 是 20px，Chrome 是 23px，原因還沒查。
  - parley 是我們 fork 的 `machopo` 分支，上游的 main 加上我們的修改；修改還沒送上游（見 `../third_party/parley/README.machopo.md`）。

## 圖片

- 只有 PNG、JPEG、GIF（只有第一格，沒有動畫）、BMP、ICO 和 SVG；沒有 WebP。格式照內容認，不看 MIME type（SVG 除外）。ICO 有好幾張圖時用每個 pixel 的 bit 數最多的、其次是最大的那一張（Blink 先比大小；只有大的那張顏色比較少的檔案才不同），裡面的 PNG 要是 RGBA 的（格式的規定；Chrome 其他的也讀）。SVG 圖片（MIME type 是 `image/svg+xml`）在 `<img>`、`<picture>` 和 `background-image`；它的文件照 Chrome 不跑 script、不載入外部資源，畫法和 inline 的 SVG 一樣（同樣的限制，見「Layout」的 SVG），但：網址的 fragment（`#svgView(...)`、指向 `<view>` 的 id、`#xywh=`）不認；沒有動畫。
- 圖片的 list of available images 是整個 renderer 的 DOM 一份（同一張圖在 iframe 和 parent 只抓一次，和 Chrome 的 memory cache 一樣；HTML 是每份文件一份），圖留到用過它的文件都 shutdown（導覽離開、iframe 移除）為止，照 Blink 的 weak cache 和 `ResourceFetcher`；Blink 的 resource 要等 GC 才真的不在，machopo 在 shutdown 時就拿掉，之後的文件要同一張圖會再抓一次。
- 載入中和載入失敗的圖片沒有破圖的圖示，也不顯示 `alt`：有 `alt` 的失敗的 `<img>` 沒有大小（Chrome 給它一個放 `alt` 文字的 inline box，WPT 的 `current-pixel-density/error.html` 因此失敗）。
- `object-fit` 只收一個關鍵字（css-images 4 的 `cover scale-down` 這種組合 Chrome 也不收）。圖片照 EXIF 的方向轉（尺寸和像素都是，Chrome 的 `image-orientation: from-image`），但沒有 `image-orientation` 這個 property：`none` 不能要求不轉。`decoding`、`fetchPriority`、`crossOrigin`、`referrerPolicy` 只有 reflection，抓圖時不管。沒有 image map（`usemap` 的 `<area>` 點不到）。
- `<img>` 有 pending request，換 `src` 時和 Chrome 一樣留著舊的圖，下面的快取整個 renderer 一份、載入中的也算。`currentSrc` 在圖來了之前是空字串，和 Chrome 一樣（HTML 是 microtask 之後就是新的網址，WPT 的 `current-request-microtask-002.html`）。沒有 frame 顯示的 document（`createHTMLDocument`、`DOMParser` 的）裡的 `<img>` 不載入，`complete` 一直是 false。圖片的快取（HTML 的「list of available images」）每份 document 一份，不跨 document，而且只有載入完的圖：Chrome 的記憶體快取裡還在載入的圖也算，另一個 `<img>` 選了同一個網址時立刻接上那張圖（`decode()` 不會因為接著插進 `<picture>` 而被拒絕，WPT 的 `image-decode-with-quick-attach.html` 的一項），machopo 要等 microtask 才接上。
- `srcset`、`sizes` 和 `<picture>`：`<source type>` 只認得 PNG、JPEG、GIF 和 SVG（`image/avif`、`image/webp` 跳過，Chrome 會用；`image/x-icon`、`image/bmp` 也跳過，雖然 machopo 解得開）。`sizes` 的長度沒有 `ex`、`ch`（那一項無效，換下一項；`em`、`rem` 是 16px）；沒有 `sizes=auto`。選候選照 Blink：已經載入、密度比較高的優先，所以 Chrome 的結果看時序（它的 preload scanner 先抓好的圖會被選上；machopo 沒有 preload scanner）。同一個網址只是密度不同時（環境改變之後），只改密度，不重新載入、不發 `load`，和 Chrome 一樣（HTML 說要重新載入）。選不到來源時，只有有 `src` 屬性才發 `error`，和 Chrome 一樣（HTML 說用 `srcset` 或 `<picture>` 時也要）。
- `loading=lazy`：照 Chrome 量到的距離，最上層的 viewport 上下 1250px、左右 625px 以內才載入（Chrome 照網路的速度換距離，machopo 固定用快的網路的那一組）；只在 layout 之後檢查，捲動容器裡的圖不看容器的捲動範圍（只看整頁的 viewport；Chrome 對捲動容器另外加距離）。`sizes="auto"` 的寬度是上一次 layout 的 content box；沒有 `width` 屬性、還沒載入而寬度是 0 時當成 300px（HTML 的 default object size），所以 CSS 把寬度設成 0 的也是 300px，有 `min-width`（或 `min-inline-size`）的則是它（Chrome 是 300px：machopo 的 layout 給還沒載入的圖 0 的寬度，不是 default object size），`aspect-ratio`、`writing-mode` 這些 machopo 沒有的 CSS 給的寬度也拿不到（WPT 的 `sizes-auto.html` 剩下的失敗）。
- `<img>` 選來源時的 media query（`<source media>`、`sizes`）和 stylesheet、`matchMedia` 的一樣，見「Style」的 media query 那一條。
- 環境改變（視窗的大小、device pixel ratio、iframe 的大小）時，在 document 裡的 `<img>` 重新選來源。還沒 layout 過的子 frame 裡的 `<img>` 選來源（和 `matchMedia` 判斷）時，先 layout 那個 frame 一次（拿到 iframe 的大小；Blink 的子 frame 在 iframe 插入時就有大小，不必 layout）；那個 frame 還在等 stylesheet 時只 layout 父 frame，大小從 iframe 的內容框拿，不算子 frame 的 style；子 frame 開始載入子資源、第一次算 style 前也這樣先拿到大小。layout 過的子 frame 在下一次 rendering update 之前照上次 layout 的大小判斷：script 改了 iframe 的大小之後馬上讀 `matches`，拿到的是舊的結果（Chrome 是新的），`change` 在下一次 rendering update 發。
- 尺寸：百分比的高度當成 `auto`；有自然比例時 `min-*` / `max-*` 照 CSS 2 § 10.4 保持比例（block 的寬度是百分比、或被 `min-width`、`max-width` 夾住時，`auto` 的高度交給 taffy 照比例算）；block 圖片的百分比寬度不處理 `box-sizing`，有 padding 或 border 時高度也偏大（taffy 把自然比例套在 border box 上，Chrome 套在 content box）。寬度或 `max-width` 是百分比的 replaced 元素在 min-content 裡不佔寬度（css-sizing 3 的 compressible replaced element：`1fr` 的欄、flex 容器照可用的空間縮，圖跟著縮），但 block 裡 `display: block`、寬度不是百分比而只有 `max-width` 是的，外面的 block 的 min-content 照它的寬度算（taffy 的 block 排版直接用 style 的寬度）：`<div style="width: min-content"><svg height=720 viewBox="0 0 1280 720" style="display: block; max-width: 100%">` 的 div 在 Chrome 是 0，machopo 是 1280px。grid 的 `fr` 欄放不下時（其他欄的最小值已經超過容器），Chrome 把 `fr` 欄縮到它自己的最小值，machopo 照 taffy 讓它和最寬的 `fr` 欄一樣寬。
- Raster 的圖片快取在 process 裡共用，只在有新圖片進來時才清掉沒人用的；解碼後的像素沒有大小上限。
- lazy 的 `<img>` 搬進沒有 script 的 sandbox 的 iframe 之後不載入（WPT 的 `image-loading-lazy-move-into-script-disabled-iframe.html`）。

## Paint 和 raster

- 裝飾線照每段文字自己的字型放：一個元素的底線經過字型大小不同的子元素時跟著上下、粗細也跟著變（Chrome 照產生裝飾的元素（decorating box）的字型和位置畫，整條是直的，Blink 的 `InlinePaintContext`；WPT 的 `text-decoration-subelements-*`、`-decorating-box-001`、`-propagation-display-contents*`）。同一行上好幾個元素的裝飾線的陰影，各段文字各自畫（`text-shadow/decorations-multiple-zorder.html`）。沒有 `text-decoration-skip-ink`（Chrome 預設的 `auto` 讓底線在字的下降部斷開，machopo 一律畫滿）、`text-decoration-inset`、`text-decoration-skip-spaces`、`text-decoration-line` 的 `spelling-error` 和 `grammar-error`、`text-emphasis`、`-webkit-text-stroke`。`text-underline-position` 的 `under` 用字型的 ascent 和 descent 換算成 em box 的下緣（Blink 用字型的 em box 的度量）。
- 選取：畫的是 script 選的（使用者還不能用滑鼠選）。顏色沒有 `::selection` 規則時，Linux 和 macOS 都用 Chrome 152 在 Linux 上的（`rgba(0, 65, 198, 0.8)` 和白色，page 沒有 focus 時灰底）：macOS 的 Chrome 照系統的強調色，Windows 的 machopo 讀系統的 `Highlight`，沒有 focus 時的灰色三個平台都一樣（Windows 的 Chrome 照系統的）。SVG 的文字不畫成被選到；選到的圖片不疊上選取的顏色（Chrome 疊上半透明的選取底色）；highlight 的 `fill`、`stroke`、`stroke-width` 不用。字照 glyph 的位置裁開，連字跨過選取的邊界時從中間切開（Chrome 一樣）。
- 游標：畫在有 focus 的文字欄位（text、search、url、tel、password 和 `<textarea>`；email、number、日期時間那幾種打不進字，也沒有游標，Chrome 有）和 editing host 裡收合的選取上，只在 page 有 focus、它的 frame 是 focused frame 時。文字欄位顯示 placeholder 時不畫游標（placeholder 佔掉 inner editor 的那一行，游標照高度是 0 的 inner editor 畫，被欄位裁掉；Chrome 畫在 placeholder 的前面，用欄位的顏色）。閃爍的間隔 Windows 讀系統的（`CursorBlinkRate`），Linux 和 macOS 一律 500 ms：Chrome 在 Linux 上讀 GTK 的 `gtk-cursor-blink-time`（預設 1200 ms 一個週期，所以亮暗各 600 ms，關掉時不閃），macOS 讀 NSUserDefaults 的 `NSTextInsertionPointBlinkPeriodOn`、`Off` 和輔助使用的「不閃爍的插入點」，之後照它們讀。游標的位置照 DOM 的位置，Chrome 會先調整到看得見、能放游標的位置（canonical position）：例如落在 `visibility: hidden` 的文字裡的游標，Chrome 畫在它前面，machopo 畫在那個 offset。空的 contenteditable 沒有一行的高度（Blink 的 `HasLineIfEmpty`，machopo 只給文字欄位的 inner editor），高度是 0，游標照樣畫在它開頭、一行的位置。沒有 `caret-shape`、`caret-animation` 和 `caret` shorthand（Chrome 152 有前兩個）。
- 合成粗體：測試字型的 Lato 只放了 Medium，`bold` 由 Skia 的 embolden 合成，和真正的 Bold 字重不同。合成的條件是 `font-synthesis-weight` 是 `auto`、要求的字重到 600、字型不到 600、沒有 `wght` 軸（`layout` 的 `needs_synthetic_bold`），和 Blink 的 fallback 字型、Firefox 一樣；Blink 在 Linux 和 Windows 上的一般路徑（fontique 也是）要求的字重要比字型重 200 以上，所以在那裡 Medium 字型的 `bold` 不加粗，machopo 會加粗；Blink 在 macOS 上從 501 起就合成，machopo 的 501 到 599 不合成。
- paint 沒有 cull rect：每一步把每個變了的 fragment 都轉成 `PaintOp`，文字的 run 每個 glyph 都放一次，畫面外的也一樣（Blink 的 `CullRect` 只畫和可見範圍相交的）。很長的文字（Speedometer 的 Editor-TipTap，23 萬個 glyph）每一步在 paint 上約花 2 ms（release），大部分是畫面外的。
- 比 1 個 device pixel 還薄的背景（例如 `height: 0.25px`）對齊之後可能變成 0，整個不見；Chrome 至少畫 1 個 device pixel。
- border 寬度只在 paint 時取整到 device pixel，layout 照舊用沒取整的寬度（Blink 在 style 時就取整）：border 和裡面的東西之間可能差不到 1 個 device px（layout 不知道 device scale factor）。
- tile 的 raster 是同步的，預設在 compositor thread 上一個一個畫：raster 慢的頁面（tile 多的，改大小時）frame 變長（Chrome 先畫已經好的 tile，沒好的畫 checkerboard）。`--num-raster-threads N` 讓它平行，但每條 thread 畫一個 tile 的時間比一條時長（節能核心、和其他 thread 搶核心），頁面跑的時候多用 CPU 和記憶體，所以預設不開；開了之後每個分頁一組 thread。真的視窗裡上傳到 GPU 也在 compositor thread 上一個一個做（每個 tile 送一次 queue）。

## Compositor、layer 和 input

- 不等 main thread 的模式（視窗）沒有 deadline：main thread 的結果一律晚一個 frame 才畫出來，即使它在那個 frame 裡就 commit 了。
- 視窗被遮住或縮小時，renderer 照樣每個 `BeginFrame` 跑 main frame，只是 Viz 不畫：CPU 照樣在用（Chromium 會把被遮住的分頁設成隱藏，`WasHidden`，停掉 `BeginFrame` 和 `requestAnimationFrame`）。
- 視窗模式的 `BeginFrame` 照固定的 16.7 ms，不跟 vsync；headless 一回答就送下一個。
- 滑鼠的按下、放開、按鍵和交給 main thread 的滾輪會分派事件、跑 script，跑 script 一律要求 main frame，所以它們的 ack 都等下一個 frame，即使 script 什麼都沒改；滑鼠移動在下一個 main frame 才分派（rAF 對齊），ack 等分派之後（分頁隱藏時當場分派）；分派了 `mousemove` 的 frame 也一律跑一次 rendering update（Chrome 只在有東西變了時才更新）。
- 和以前全部由 main 依序處理不同、和 Chromium 相同的兩點：一批 input 一起送時，main 把容器捲不完的量傳給 viewport，要到下一次 commit compositor 才知道；已經捲到底、而讓頁面變長的 commit 還沒到時，這期間的滾輪被丟掉。compositor 的 ack 也可能比更早轉給 main 的 ack 先到。
- `navigator.scheduling.isInputPending()` 的滑鼠和滾輪算給哪個 frame，compositor 照 paint 記下的範圍判斷：子 frame 的內容框，和祖先 frame 在它之後畫的、打得到的目標的框（`HitTestData` 的 rect，蓋到的地方算「不知道」）；Chrome 照 cc 的 layer 判斷。所以 layer 的範圍比打得到的目標大時不同：`box-shadow` 伸到 iframe 上時，Chrome 照 layer 的範圍（元素和 shadow 的聯集）也算「不知道」，machopo 照元素的框算給 iframe；好幾個蓋在 iframe 上的東西被 Chrome 合成一個 layer 時，點在它們之間的空隙裡 Chrome 是「不知道」，machopo 算給 iframe（2026-10-24 對照 Chrome 152）。被合併的 `mousemove` 一直算到下一個 main frame 分派它（Chrome 一樣等 rAF 對齊的分派）。跨 origin 的 iframe 和外面的頁面在同一個 renderer 裡，計數也是同一份，判斷照 Blink 的 `CanAccessEvent` 擋掉看不到的（Chrome 的跨 site iframe 在另一個 renderer process，各數各的）。
- 被縮放、旋轉，或它和外面有 opacity 的捲動容器不會成為 layer：捲動時重跑 pre-paint 和 paint、再 commit，所在的整個 layer 重新 raster（compositor 和 Viz 只處理平移；有 opacity 時切成幾個 layer 會把群組透明度分開算）；transform 和 opacity 本身也不成為 layer（等有 `will-change`、動畫這類合成理由）。
- 在兩層以上的圓角 clip（`overflow` 不是 `visible`、有 `border-radius` 的祖先，或它自己）底下的捲動容器不成為 layer：compositor 給 Viz 的每個 quad 只帶一個圓角的 clip（Viz 的 `mask_filter_info` 也是一個；Chromium 多的那幾層用 render surface 疊起來，machopo 還沒有 render surface）。
- 每個成為 layer 的容器把頁面切成「之前、容器、之後」，不做重疊判斷（依序切段一定正確），n 個容器最多 2n+1 個 layer。「之後」的 layer 和容器自己的 layer 是透明的：裡面抗鋸齒的像素先 raster 在透明的底上、再由 Viz 疊上去，和直接畫在背景上的捨入不同，可能差 1；差不差看平台（Skia 畫在透明的底上和畫在不透明的底上的捨入，在 macOS 上和其他平台不同），所以這類 reftest 的預期結果照平台分：WPT 的 `margin-collapse-009`、`css/CSS2/floats/new-fc-beside-adjoining-float`、`new-fc-separates-from-float-2`、`css/CSS2/floats-clear/clear-on-parent-and-child`、`css/css-overflow/text-overflow-020` 只在 macOS 上是預期的失敗（block 的背景比文字先畫，捲動容器裡的背景就讓前面段落的文字落到「之後」）。使用者捲不動的容器（`overflow: hidden`、`clip`）有東西可捲時也成為 layer，Chrome 不會（它的 composited scrolling 只給使用者捲得動的）：它裡面的文字因此和 Chrome 差 1（`css/css-overflow/text-overflow-012`、`022`，macOS 上兩者捨入一樣、通過）。canvas 也一律是自己的 layer，它的 bitmap 和頁面上直接畫的同樣形狀在 macOS 上也差 1（machopo 自己的 reftest 用 fuzzy 容許）；canvas 之後畫的東西同樣落到「之後」的透明 layer，Linux 上它的抗鋸齒像素也可能差 1（WPT 的 `css/css-images/object-fit-none-png-00{1,2}c`、`object-fit-scale-down-png-00{1,2}c`：第二個以後的 canvas 的虛線邊框，`.ini` 用 fuzzy 容許；Chrome 把不和 canvas 重疊的內容併回下面的 layer，Blink 的 `PendingLayer` merging）。
- 這些捲動容器上的滾輪還是要等 main thread，JS 卡住時捲不動：被縮放、旋轉或有 opacity 的；被畫在它之後的東西蓋到的（連同它裡面的）；以及在這些容器裡面的。compositor 判斷「被蓋到」很保守：只要有一點可能重疊，整個容器都交給 main。之後改成 Chromium 的 scroll unification。
- 範圍的不變式（所有範圍的聯集和捲動位移無關）照舊成立：`position: fixed` 的內容不算進捲動範圍，`covered_scrollers` 也跳過它。它自成一個 layer，捲動時 compositor 把捲動位移加回那一層的原點，所以不用重 raster。
- layout 沒有 Chromium 的 `LayoutUnit`：computed value 的長度和百分比照 Blink 夾到約 ±3,355 萬 px，但幾個大的值加起來（`margin` 加 `width`、百分比乘上容器的寬度）可以超過，Chrome 的 `LayoutUnit` 讓加總也飽和在那裡（`width: 1e39%` 在 Chrome 是 3,355 萬 px，machopo 是 3,355 萬 % 乘上容器的寬度；`getComputedStyle` 的 `width` 讀回的 used value 跟著不同），仍然是有限的數。超過 f32 能精確表示的整數（約 1,677 萬 px）之後，位置和大小有誤差。

## 捲動

- 沒有捲軸：不畫，也不佔 layout 的寬度。
- `wheel` 事件：有 blocking listener（不是 passive 的 `wheel` / `mousewheel`）的元素和 flat tree 裡在它底下的元素的盒子是 wheel event handler region（root element 也算 document 和 window 的，shadow tree 最上層的元素也算 shadow root 的），上面的滾輪等 main thread，JS 卡住時捲不動；區域外 compositor 先捲，事件不能取消。區域照盒子的範圍，`pointer-events: none` 的盒子不算；SVG 的文字的每個字元照 `<text>` 的，`<tspan>` 自己的 listener 不算；listener 加減、盒子移動要到下一個 frame 才更新區域（Chrome 也是）。target 已經被回收的 listener 還算「頁面可能有 `wheel` listener」，compositor 照樣把捲過的滾輪轉給 main 分派（多花一點，結果一樣）。`deltaMode` 一律是像素；`wheelDelta` 照 Blink 的建構子從 `deltaY` 算（`-deltaY`），不是平台的刻度；沒有 touchpad 的 phase 和 momentum。
- 沒有捲動動畫，滾輪和鍵盤都一次跳到位。
- `scrollIntoView` 的置中和 `focus()` 置中算出的捲動位置留著小數（`1710.8`），Chrome 152 取整（`1711`）；`scrollTo` 兩邊都取整。
- 不做 wheel latching：同一串滾輪中，容器被捲到游標底下之後，接下來的會轉給它。
- 文字編輯只有文字控制項裡最小的一部分：`<textarea>` 和 text、search、url、tel、password 的 `<input>`（email、number 和日期時間那幾種打不進字，鍵盤照舊捲頁；number 的 ↑、↓ 照 step 加減，range 的方向鍵、PageUp、PageDown、Home、End 移動它），在 selection 插入打出的字、Backspace、Delete、←、→、Home、End（加 Shift 時延伸選取）、`<textarea>` 的 Enter。沒有輸入法和 composition 事件、undo、剪貼簿、Ctrl+A、以字為單位的移動和刪除（Ctrl+←、Ctrl+Backspace）；↑、↓ 照舊捲頁，Home、End 照值裡的換行（machopo 不知道排版之後的折行）。刪除和移動以 grapheme cluster 為單位，Backspace 對某些文字（Chromium 的 `BackspaceStateMachine` 只刪一部分的那些）也刪整個 cluster。`InputEvent` 沒有 `dataTransfer`、`getTargetRanges()`。`maxlength` 放不下任何字時不分派事件。`<input>` 的 Enter 只 commit 它的 `change`，不送出表單；分頁失去系統的焦點（例如 Tab 到網址列）時不 commit，焦點在頁面裡換了才 commit。`contenteditable` 裡不能打字（editing host 只能 focus），`execCommand` 也沒有（`Selection` 見「Bindings 和 DOM API」）。Mac 的 Cmd+↑、Cmd+↓ 這類捲到頭尾的組合鍵沒有。
- Scroll anchoring（viewport 和捲動容器，`overflow-anchor`）照 Blink 的 `ScrollAnchor` 做。和 Chrome 不同的地方：
  - priority candidate 只有有 focus 的可編輯元素，沒有 Blink 的另一個：find-in-page 找到的文字（machopo 沒有 find-in-page）。
  - 一行裡的候選（文字和 inline-block 等）照「第幾行、再左到右」的順序看，不是 Blink 的 layout tree 的順序：從右到左的文字、一個元素跨好幾行時，選到的可能不同。
  - 傳給 viewport 的東西（`overflow` 等）改了、整棵 box tree 重建時，anchor 留著（和 Blink 一樣），同一次更新裡 block 盒子的 style 改變照樣讓它不跟，inline 元素的看不到。
  - 被搬到別處的 text node，machopo 當它還是同一個 anchor；Blink 重建它的 layout object，重新選。
  - 在 inline 內容中間插入 block 時，Blink 把兩邊包進新的匿名 block，它們沒有 layout 過，選 anchor 時整段跳過；machopo 照舊在裡面選。
  - SVG 裡的元素不會是 anchor（外層的 `<svg>` 會）；Blink 用它們的 decorated bounding box 選。
  - 沒有 `scroll-padding`：捲動框的可見範圍是整個 scrollport（Blink 扣掉 `scroll-padding`）。
- 回上一頁時不恢復捲動位置（同一份文件的 entry 之間只捲到 entry 的 fragment）；文件的 `#fragment` 在載入完成時捲一次，之後導覽到 fragment 時再捲；設 `location.hash` 時在 event loop 的最上層才捲（Chrome 當場捲：設完馬上讀 `scrollY` 已經是新的）。
- scroll anchoring 調整捲動的位置時不分派 `scroll`：WPT 的 `css/css-scroll-anchoring/after-scrollable-range-shrinkage-001.html` 在 `scrollBy` 的那一個趕在 `setTimeout(0)` 之前的 frame 就發了時，等不到而 TIMEOUT（時好時壞）。
- 打字時不把 caret 捲進視野（只有 script 的 `focus()` 時捲）；文字框的值比框長時，inner editor 也不照 caret 捲動（Blink 的 `RevealSelection`）。

## Invalidation

- style 的重算範圍：元素的屬性或 state 改了只重算它自己，規則在它以下的位置用到改了的 class、id、屬性或 state 時，照規則收集的 descendant invalidation set（Blink 的做法）重算它的後代裡有那些規則的主體的 id、class、屬性或標籤名稱的（主體沒有這些時整棵子樹；shadow tree 的規則用到 host 的時候在那棵 shadow tree 裡找），set 只認 feature、不分位置（`.a .b span` 的 `.a` 改了，重算底下所有的 `span`）；UA shadow tree 的部件（`input.x::placeholder`）、list box 的規則和 `::slotted()` 前面用到 slot 的，以及 `lang`、`dir`、`contenteditable` 改了，照舊重算整棵子樹；它的 computed style 變了時，子節點照繼承的值、`display` 等決定要不要跟著重算。子節點進出時，照比對時記在節點上的旗標只重算受影響的子節點和它們的子樹：`:first-child`、`:last-child`、`:only-child` 重算第一個、最後一個和改變點前後的元素，`+` 重算改變點之後 tree scope 裡最長的一串 `+` 那麼多個（Blink 只重算下一個），`~`、`:nth-child()`（包括 `of` 的）和 `:first-of-type` 這類從前面數的重算改變點之後的全部，`:nth-last-child()`、`:last-of-type` 這類從後面數的重算全部，`:empty` 重算父元素；shadow tree 的 `:host(…)` 用到 host 的位置時，從改變點之後全部重算。位置在 `+` 左邊時（`:first-child + p`）從改變點之後全部重算。兄弟位置的屬性、state 改了（`.a:checked ~ .b`），或元素的 `:empty` 變了（`:empty + p`）時，照規則收集的 sibling invalidation set（Blink 的做法）只重算之後的兄弟裡有要找的 class、id、屬性或標籤名稱的（`+` 只到那一串的長度），或它們底下有 subject 的這些的後代；set 只認 feature、不分位置（`.x + p + p` 兩個 `p` 都重算）。set 說不出的（巢狀 list 裡的、`:nth-child(… of …)`、UA shadow tree 的部件、`::slotted()` 前面的兄弟）照子節點進出的方式重算；host 的子節點和 shadow root 的子節點之間有這種改變時，那些子節點全部重算。旗標只加不清（Servo 也是）：規則或子節點換過之後，照舊重算以前符合過的位置。有 `:has()` 時整份（shadow tree 的規則有 `:has()` 時那整棵 shadow tree）都重算。document 和 shadow root 的 stylesheet 變了（`<style>`、`<link>`、adopted stylesheet 多了、少了，`<style>` 的文字改了就是舊的整份少了、新的整份多了；constructed stylesheet 被 `insertRule`、`deleteRule` 改了只算增減的規則，改了 `@media`、`@supports` 裡面的規則時算整個 group rule）只重算多了、少了的規則可能符合的元素（Blink 的做法）：照規則最右邊那一節的 id、class、屬性或標籤名稱找，那一節沒有時找左邊最近有的那一節，重算它的整棵子樹（祖先）或之後的兄弟；`::placeholder` 這類 UA shadow tree 的部件重算 host 的整棵子樹。以下整份重算：選擇器每一節都沒有這些（`*`、`:root`、只有 state、`:not()`）、有 `:has()`（Blink 有專門的 invalidation）、有 `@keyframes`（Blink 只重算有動畫的元素）、留下的 stylesheet 順序變了、viewport 讓 media query 的結果變了（Blink 照結果變了的規則判斷）。shadow root 的規則有 `:host` 的重算 host，有 `::slotted()` 的重算分配到它的 slot 的節點；shadow root 的 stylesheet 要整份重算時，重算那棵 shadow tree 的每個元素、host 和分配到它的 slot 的節點，host 的 light DOM 更深的後代只在繼承的值變了時跟著重算）；沒有 style sharing。
- 元素和屬性的名稱：html5ever 清單裡的和 7 bytes 以內的是 atom（比整數），清單外、又更長的（`data-todo-id`、custom element 的長名稱、HTML 新的 `autocapitalize`）是字串，比較時比字串（`autocapitalize`、`enterkeyhint` 是 `dom::name::unlisted` 的常數）。script 給的名稱（`getAttribute`、`setAttribute`、`dataset`、`createElementNS`、custom element 的名稱）每次從字串建（長的要查一次靜態清單的雜湊）。
- 重算一個元素時，只比對它的 id、class、名稱的桶和「其他」的桶裡的 selector（Blink 的 `RuleSet`），比對前先查祖先的 bloom filter（Blink 的 `SelectorFilter`）；bloom filter 只用在元素自己那棵樹的規則（`:host`、`::slotted()` 這類跨 tree scope 的照樣比對），不放屬性的名字。屬性選擇器逐一比對元素的每個屬性的名字（字串比較）：`[dir="rtl"] .x` 這類規則沿著祖先找，Blink 一樣往上找，但比的是 atom。matched properties 的快取（Blink 的 `MatchedPropertiesCache`）只在符合的宣告區塊、parent（或它的繼承值）和依位置的調整的輸入（root、flex 或 grid 的子元素、表單控制項、blocking 的 `wheel` listener、pseudo-element 的種類）都相同時共用調整完的 style（Blink 的 full hit；沒有 partial hit），有 `style` 屬性的、有 keyframe 或動畫的 font size 的、`inherit` 了非繼承 property 的、menu list 的內層元素不快取，同一個 key 第二次遇到才存；其他的每個重算的元素都從頭套用符合的規則（Blink 一樣）。`ComputedStyle` 只有少用的欄位和字型分成五個共用的組（`rare`、`rare_inherited`、`font`、`backgrounds`、`svg`），其他約 67 個欄位在主體，每個重算的元素都複製一份主體（Blink 的欄位全部分組，只複製改了的組）。同一個 parent 的子元素不共用繼承後的起點，也沒有 style sharing（兄弟的 style 相同時直接共用）。document 的任何一份 `<style>` 改了，整個 document 的 `RuleSet` 重建；document 或 shadow root 的 stylesheet 只在 `<style>`、`<link>` 進出、內容或 attribute 改了，或 adopt 的改了時重收，重收時走過它整棵樹找 `<style>`（Blink 只看記下來的 style element）。
- box tree 以「最近的 block box 的內容」為單位：一個字改了，整個段落重新 shape（Blink 也是整個 inline formatting context 重新收集，但會沿用沒變的 shape 結果）；文字和影響 shaping 的 style 都和快取裡的段落一樣時（跨節點、跨文件，有字元數的上限），共用那次的 shaping；不一樣時沒變的字沿用存下的字型和 glyph（空白旁邊是字型會和空白一起 shaping 的 glyph 時，前後的字併起來重新 shape），但字型的規則比對得比空白旁邊的一個 glyph 更遠時不沿用：Calibri 和測試字型的 Lato 有跨空白的 `calt`，段落整段重新 shape（Blink 不分字型都沿用沒變的部分，它 shape 一個 item 時看 HarfBuzz 標的哪裡可以安全地切開）；沒有 box 的元素換了 style 也保守地重新收集所在的容器。
- layout 只重排變了的 box 和它的祖先，但祖先照樣整個重跑 taffy 的演算法（block、flex 或 grid；沒有 Blink 的 relayout boundary 和 simplified layout）；文件大小和捲動容器的 scrollable overflow 每次 layout 都走過整棵 fragment tree。
- paint 走過每個有改變的 stacking context 裡的每個 box（沒變的整段照搬，不走進去；pre-paint 只重走改變的子樹）；自己畫的東西沒變的 box 沿用上次的 display item。比對新舊 display item 時，重畫的 box 的 item 照舊比內容（Blink 看每個 client 被 invalidate 的原因、不比內容）；沿用的 item 共用它的 glyph 和邊框的多邊形，但 path（邊框、SVG 的形狀）照樣複製一份（Blink 的 `PaintRecord` 整個共用）。
- 位置變了的 box 要重畫，它新舊兩個位置經過的 tile 都要重新 raster：段落變矮、下面整頁往上移時，整頁大部分的 tile 都重新 raster（和 Blink 相同；Blink 有 composited 的部分可以只移動 layer）。

## Viz、GPU 和記憶體

- 每個 frame 只有一個 render pass；`DrawQuad` 只有平移，Viz 嵌入 surface 時直接把位移算進座標。
- 沒有 `ReturnResources`：shared image 的生命週期靠參考計數；Viz 照舊整個畫面重畫（damage rect 送到了，但沒用來 partial swap）。
- 網頁 frame 的 `LocalSurfaceId` 不比對：Viz 用那個 sink 最新的 frame，視窗大小改變的那一下會先顯示舊大小的 frame。
- `about:demo` 的 GPU 那份比活著的 texture 多約 95 MB，跟著動畫出現（每個 frame 上傳一個 tile、畫一個 frame），不會繼續長；不是 texture 建立和銷毀造成的（重用 texture 試過，省不下來），原因還沒查到。
- 不做 cc 的 `ResourcePool`：每個重新 raster 的 tile 都建立新的 texture。
- raster 為可變字型建的 Skia typeface（照字型和軸的值，`RasterCache` 的 instance）跟著 compositor，不會變小：每種字型、每組軸的值一個，macOS 的系統字型有 `opsz`，每個字級各一個（Blink 的 `FontCache` 會清掉不用的 `FontPlatformData`）。
- GPU device 遺失之後，新的 device 做不出來時（重試 3 次）直接結束程式：視窗沒有 software 的輸出可以退回（Chromium 退到 software compositing）。
- Viz 不用 texture 上限小於 8192 的 adapter（renderer 把不超過它的 canvas 當成 layer）：這樣的 GPU 建不出 device、程式結束，不會改用下一個 adapter（例如 CPU 的）。目前的桌機 GPU 和 lavapipe、WARP 都到 16384 以上。
- 視窗的實體像素超過 GPU 的 texture 上限（Apple Silicon 每邊 16384；使用者把視窗拉過好幾個高 DPI 的螢幕時）時 surface 的設定失敗、整個程式結束：Viz 的輸出是一張 texture，沒有夾到上限、也沒有分塊畫（Chrome 的視窗一樣受 GPU 的限制）。automation 設的大小夾到 8192（見「WebDriver 和自動化」）。
- Viz 收到 renderer 送來的不合法的 frame（resource 的像素和大小對不上、超過 texture 的上限）時丟掉它、照舊顯示上一個，記一筆錯誤；Chromium 結束那個 renderer 的 process，machopo 的 renderer 是同一個 process 裡的 thread，停不乾淨，要等拆 process。
- 只會在原地重建 device，不會重啟 process；GPU 驅動程式真的 crash 會讓整個程式結束，要等拆 process。
- device 遺失到 compositor 送來新的 frame 之間，舊 device 上的 tile 不畫，露出背景色，可能閃一兩個 frame。
- `machopo` 的 Rust 那一側用 mimalloc，空出來的記憶體預設留 10 ms（arena 的再乘 10）才還給系統：Speedometer 的記憶體峰值比平台的 allocator 多約 13%（macOS，phys footprint；TodoMVC-jQuery 多約 40%）。`MIMALLOC_PURGE_DELAY=0` 立刻歸還，峰值只多約 6%，時間慢約 2.7%。Linux 和 Windows 上還沒量。C++ 那一側（V8、Skia）照舊用平台的 `malloc`。
- mimalloc 延後的歸還落在當時那一次配置或釋放裡：剛釋放大量記憶體之後，一次普通的配置可能在 kernel 裡花 1.5 到 4.4 ms（以前 `gc_bench` 重播讀完幾 GB 的錄製之後，GC 的 scavenge 停頓因此偶爾有一次這麼長；`MIMALLOC_PURGE_DELAY=-1` 時沒有）。總成本不變，只是落在誰身上；還沒改成在 idle 時歸還。

## Script

- timer 的字串 handler 裡的 `import()` 照它的 document 的 base URL 解析（HTML 的 settings object 的 API base URL）；HTML 和 Chrome 照設定它的 script 的 base URL（initiating script 的），WPT 的 `dynamic-import/string-compilation-base-url-inline-classic.html` 的 `setTimeout` 那項因此失敗。之後在設定 timer 時記下那個 script 的 base URL。
- script 插入的外部 script 的 `src` 和 inline module 的 base URL，在插入它的 script 跑完之後才解析（renderer 的 `start_loads`；規範和 Blink 是插入的當下）：插入之後、同一個 script 裡又改了 `<base>` 時解析的結果不同。inline classic script 在插入的當下用當時的 base URL。
- module script：靜態的 `import`、動態的 `import()` 和 `<link rel="modulepreload">`。`import.meta.resolve` 沒有。`import()` 一個已經在 module map 裡的 module，要等這個 task 結束、回到 event loop 才完成，規範是在 `import()` 的當下完成，所以先排好的 microtask 會全部先跑（WPT 的 `dynamic-import/microtasks/basic.any.js`；請求要等 script 跑完才交給 renderer）。不同的 script 裡原始碼相同的 `new Function(...)` 呼叫 `import()` 時，都照第一個 script 的 base URL 解析（WPT 的 `dynamic-import/code-cache-base-url.html`，像 Chromium 的 crbug.com/990810；原因還沒查清，可能是 V8 的 eval cache 只用原始碼當鍵）。沒有 import map，bare specifier（`import "lodash"`）是 `TypeError`。只有 JavaScript 的 module：`with { type: "json" }`、`"css"` 是 `TypeError`。wasm 文件沒有 module（`type="module"` 是不認得的種類，`modulepreload` 不抓）。每份文件重新抓、重新編譯每個 module（沒有 HTTP cache 和 V8 的 code cache），在 main thread 上編譯。頁面忙著跑 script 時，`import()` 可能很久才完成：Blink 的 perf test `dom/range-select-node`（20 輪、每輪對 20000 個元素各做一個 `Range`）在載入時 `import()` 一個小 module，machopo 在 20 輪跑完（約 36 秒）之後再過 285 秒才 resolve，Chrome 約 1 秒；原因還沒查（可能和留著的 `Range` 數量有關）。
- `modulepreload`：`as` 是 `json`、`style`、`text` 的分派 `error`、不抓（machopo 只有 JavaScript 的 module，Chrome 會抓 JSON 和 CSS 的）。每個 `<link>` 只處理一次：規範在 `href` 改了、或移除之後再插入時重新處理，machopo 不會（和 stylesheet 的 `<link>` 一樣）。HTTP 回應的 `Link` header 裡的 `modulepreload` 不處理。
- 抓失敗的 module 留在 module map 裡（照實作時的規範，Blink 的 `ModuleMap` 也記下失敗）：之後同一個網址的 `<script type="module">` 和 `import()` 直接失敗、不再抓。WPT 的 `module/concurrent-failed-imports.html` 期待重新抓（「the failed fetch was not cached」），可能是規範之後的改動，還沒查證；那份測試和 `dynamic-import/repeated-imports.any.js` 因此預期失敗（`dynamic-import/concurrent-failed-imports.any.js` 失敗的訊息帶著每次不同的網址，寫成 `disabled`）。
- SVG 的 `<script>` 不執行（它是 `SVGScriptElement`，但只有 HTML 的 `<script>` 會 prepare）：WPT 的 `svg-script-fragment-parsed-not-executed-on-clone.html`。
- rendering update 裡只有 animation frame callback 照 HTML 的順序走過 document（父的先、子 frame 照 iframe 的 tree order，輪到時才拿它的 callback）；`ResizeObserver`、`IntersectionObserver` 等其他步驟照子 frame 建立的先後。`setTimeout`、`setInterval`、`requestAnimationFrame`、`requestIdleCallback` 和同一個 renderer 裡所有的 window 共用一個 handle 的計數器（到 `i32::MAX` 之後繞回 1、跳過還在用的，和 Blink 一樣）：WPT 的 `no-interference-timers` 因此不同（Chrome 每個 context 的每一種各自從 1 算），同一個分頁裡的 frame（包括跨 origin 的 iframe）也從 handle 的跳躍看得到彼此建了幾個。清除時比對 owner，清不掉別的 window 的。之後處理跨 origin iframe 的隔離時，照 Blink 分成每個 context 各自的計數器。
- module script、`modulepreload` 和帶 `crossorigin` 的 classic script 照 CORS（`crossorigin` 決定 credentials mode），`file:` 頁面的 module 照 Chrome 擋下（`file:` 的 origin 是 opaque，CORS 只適用於 HTTP(S)；`data:` 的照樣能讀）。動態的 `import()` 一律以 `same-origin` 的 credentials mode 抓，規範是沿用 import 它的 script 的（`crossorigin=use-credentials` 的 module 裡的 `import()` 和 Chrome 不同）。沒有 `crossorigin` 的跨源 classic script 的錯誤訊息不 mute（`window.onerror` 看得到完整的訊息，Chrome 只給「Script error.」）。`<script>` 的 `integrity`、`referrerpolicy` 不管。
- module 裡的錯誤在 window 回報時，位置是建立錯誤的地方（`new Error` 的，不是 `throw` 的），和 Chrome 一樣；renderer 判斷的錯誤（解析不了的 specifier、不支援的 import attribute）沒有檔名和行號。不支援的 `type` 記成 import 它的 module 的 parse error，規範是 graph 的 error to rethrow：同一個 graph 有好幾個錯誤時，回報的那一個可能不同。
- `src` 是空的或解析不了的 `<script>` 的 `error` 事件，在 parser 這一輪停下之後分派；規範是排一個 task。
- 沒有 `document.write`：parser 和 script 透過 `RefCell` 共用 DOM，script 執行途中不能再餵 parser。
- inline script 的欄位從它的程式開始的地方算（`<script>` 後面的第一個字是第 1 欄），Chrome 從那一行的開頭算：`Error.stack`、`ErrorEvent.colno` 和 DevTools 看到的位置，在 `<script>` 那一行上的差 `<script>` 前面的字數。
- Stylesheet 擋 parser 的 script 時（還在載入的、document 自己的 parser 插入的 `<link rel=stylesheet>`），只看自己的 document：規範也算 iframe 所在那份 document 的（和 Blink 一樣不算）；`media` 在開始載入時判斷一次，子 frame 還沒排版時一律當成符合（寧可讓 script 等）。machopo 一次 parse 整個回應，WPT 的 `moving-between-documents/` 的 move-back 測試假設 script 在串流的途中才 prepare，在 machopo 上 script 先在自己的 document 裡 prepare、被 stylesheet 擋住，搬出去又搬回來之後照樣執行；`before-prepare-*-success-empty-src-*` 的 4 份（`src` 是空的 script 搬到 iframe 或 `createHTMLDocument` 的 document）也一樣，script 搬走之前已經在自己的 document 裡 prepare，`error` 排在那裡、照樣分派。要邊收邊 parse 的 parser 才做得到。
- `<script>` 的 `charset` attribute 不管：外部 classic script 的回應沒有帶 charset（也沒有 BOM）時，用文件的編碼解碼（Chrome 用 `charset` attribute）。WPT 的 `script-charset-01.html`、`-03.html` 因此各有一項失敗。
- `javascript:` 網址回傳的字串不會取代 document。
- 在 timer 的 task 之後的 microtask 裡設的 timer，巢狀的層數從 0 算（照 HTML：microtask 跑的時候它自己是 event loop 正在跑的 task，不是 timer 的；WPT 的 `timer-nesting-not-inherited-in-microtask.html`）；Chrome 152 算成那個 timer 的下一層（2026-10-11 實測，2026-10-24 再確認：callback 回來之後的 checkpoint 在 Blink 的 `DOMTimer::Fired` 把層數歸零之前），所以從那裡開始的 `setTimeout(0)` 的鏈，Chrome 第五個就被夾到 4 ms，machopo 要到第七個。
- wasm 的文件（前 1024 byte 裡有 `<meta name="script" content="wasm">` 的 HTML）只跑 wasm 的 script，不跑 JS；其他文件只跑 JS，它的 `application/wasm` 的 script 不執行。wasm 文件現在的限制：
  - **只有 parser 插入、有 `src` 的 `<script type="application/wasm">` 會執行**（MIME 要是 `application/wasm`），照文件順序在 parse 完之後、`DOMContentLoaded` 之前；guest 自己插入的 script 元素不執行，沒有 inline 的。component 在 main thread 上同步編譯，編譯時頁面不動；每次載入都重新編譯。
  - **guest 能呼叫的只有 `machopo:dom` 的 WIT 列的成員**，一份明列的清單（`crates/dom_wasm/README.md` 的「WIT」）：建和改樹、屬性、選擇器、表單控制項的 `value` 和 `checked`、`classList`、`style`、`focus()`、`blur()`、`click()`、`window` 和 `location`、事件的 listener。沒有 timer、`requestAnimationFrame`、`requestIdleCallback`、observer、custom element、`fetch`、`dispatchEvent` 和事件的建構子；`focus(options)` 的 options 給不了。頁面自己的行為（連結、表單控制項的輸入、focus、捲動、CSS 的動畫）照常。
  - **listener**：`addEventListener` 的 options 只有 `capture`（沒有 `once`、`passive`、`signal`）；事件的成員只有 `type`、`target`、`currentTarget`、`defaultPrevented`、`preventDefault()`、`stopPropagation()`、`UIEvent.detail`、`MouseEvent.button`、`KeyboardEvent.key`，事件的 handle 只在 listener 的那次呼叫裡能用。**guest 自己呼叫 `click()`、`focus()`、`blur()` 分派的事件只會呼叫同一個 script 的 listener**，頁面上其他 wasm script 的 listener 在那次分派裡被跳過（頁面自己分派的事件，每個 script 的都會呼叫）；Chrome 的 listener 不分是哪個 script 加的。listener 是 guest 自己編的號碼，host 不告訴 guest 哪個號碼不用了（節點被回收、listener 跟著沒了也一樣）：guest 那一側記號碼的表到換頁才清。listener 不能等待（等待當成 trap）；一個 listener trap，那個 script 的 Store 結束，它其他的 listener 也不再被呼叫。
  - **沒有 JS**：event handler 的屬性（`onclick=""`）不執行；DevTools 的 Console、`Runtime` 和 `Debugger` 沒有 inspector 回答，其他由 renderer 回答的 domain 在 wasm 文件上沒有測過；WebDriver 的 Execute Script、Get Element Property 回錯誤，所以 `test.py reftest` 和 `test.py wpt` 跑不了 wasm 文件（情境可以）。
  - **只有最上層的 frame**：iframe 沒有子文件；JS 頁面的 iframe 載入 wasm 文件時，它的 wasm script 不執行（engine 是整頁一個，照最上層的文件選）。
  - guest 只能在 `start` 裡等待（WASI 的時鐘）；它讀到的時鐘降到 100 µs。guest trap 時印到 console、不分派 `error`，那個 script 的 Store 結束。它印的最後一行沒有換行時，要到 Store 丟掉（換頁）才印出來。
  - TodoMVC 的 guest（`crates/dom_wasm/tests/guests/todomvc.c`）不保存 todo（JS 版在這裡也只存在記憶體裡）；最多 64 個 todo、標題最多 255 byte（超過的截掉），`trim` 只認 ASCII 的空白。JS 版會丟例外的地方（要找的元素不見了）它直接從 listener 回來。
  - 換到另一種文件時整頁換 engine（renderer 拿著的前一份 DOM 的東西都放掉）；DevTools 連著時換 engine 沒有測過。

## Bindings 和 DOM API

- `navigator`：UA 和 Chrome 的完全一樣（依 UA 分路的程式走和 Chrome 一樣的路），伺服器、網站和 log 認不出 machopo；網站以為是 Chrome 時，用到 machopo 沒有的功能會壞得更徹底。`language` 和 `languages` 固定是 `en-US`、`en`（沒有語言的設定），`onLine` 永遠是 `true`（沒有網路狀態的通知），`cookieEnabled` 是 `false`（沒有 cookie）。`connection`（`NetworkInformation`）是 Chrome 估不出網路品質時的固定值：`effectiveType` `4g`、`rtt` 0、`downlink` 10、`saveData` `false`，不發 `change`（machopo 沒有 Chromium 的 `NetworkQualityEstimator`；Chrome 給的是量出來的、每個 host 加了雜訊的估計）；沒有只在 Android 和 ChromeOS 上的 `type`、`downlinkMax`（和桌面版的 Chrome 一樣）。`geolocation` 沒有定位，也沒有權限的提示：每個請求都照 Chrome 在使用者拒絕時回答（`PERMISSION_DENIED`、「User denied Geolocation」），時序照 Chrome：權限的回答比請求晚一個 task 到，先給 `getCurrentPosition` 的、再給 `watchPosition` 的，`timeout` 是 0 的先 timeout，頁面看不見時請求等到看得見。`timeout` 1 ms 以上的 timer 不會比權限的回答早到（Chrome 的回答要到 browser 一趟，很短的 timeout 有時先到）。Chrome 在不是 secure context 的頁面和沒有 `allow="geolocation"` 的跨 origin iframe 裡的訊息是另外兩句（「Only secure origins are allowed」和 permissions policy 的那句），machopo 沒有 secure context 和 permissions policy，一律是拒絕的那句。沒有 `GeolocationPosition`、`GeolocationCoordinates` 的物件（interface 在）。`wakeLock` 只有 API：`request()` 照 Chrome 的桌面版給（比請求晚一個 task，頁面看不見時拒絕），`release()` 和頁面看不見時照 Chrome release、發 `release`（在 `visibilitychange` 之前），但不向作業系統要求螢幕不暗（Chromium 的 `PowerSaveBlocker`）；同時被 release 的幾個 lock 照取得的順序發 `release`（Chrome 照它的 hash set，不固定）；沒有 `system` 的 lock（Chrome 也要 flag 才有）；跨 origin 的 iframe 沒有 `allow="screen-wake-lock"` 時 Chrome 拒絕（permissions policy），machopo 照樣給。沒有 `clientInformation`、`plugins`、`mimeTypes`、`javaEnabled()`、`pdfViewerEnabled`，也沒有 `maxTouchPoints`、`registerProtocolHandler()` 和其他規範加在 `Navigator` 上的成員（`clipboard`…，框架用它們偵測功能）。WPT 的 `navigator.any.js` 用 `XMLHttpRequest` 比對 UA，machopo 還沒有 XHR，那一項失敗（baseline）。`navigator.webdriver` 在 `RendererFlags::automation` 時是 `true`：`machopo --automation-pipe`，也包括情境（像 Chrome 的 `--enable-automation`）。
- `crypto`：只有 `getRandomValues` 和 `randomUUID`，沒有 `subtle`；`randomUUID` 在任何頁面都有（machopo 沒有 secure context 的概念，也沒有 `isSecureContext`；Chrome 只在 secure context 給）。`QuotaExceededError` 的建構子不檢查負數和 `requested` 小於 `quota`（照 Chrome 152，WebIDL 說是 `RangeError`）。
- `requestIdleCallback`：正在畫時 idle period 的期限是上一個 main frame 開始的時刻加 1000/60 ms（沒在畫時開始的長 idle period，開始畫之後也截到這裡），不看螢幕實際的更新率和 Viz 下一個 `BeginFrame` 的時刻（Chrome 的 scheduler 用 compositor 給的下一個 frame 時刻）。
- bytes 的形式：宣告表有 `ArrayBufferView`、`BufferSource`（參數）和 `ArrayBuffer`、`Uint8Array`（回傳值），沒有單獨的 `ArrayBuffer` 參數、其他種類的 typed array 的回傳值、`[AllowShared]` 和 `[AllowResizable]`（resizable 的 buffer 一律是 `TypeError`，照 Chrome）。machopo 沒有 `SharedArrayBuffer`（頁面沒有 cross-origin isolation）。Lua 的 runtime 裡字串本身就是 bytes：union 的 bytes 的 case（`Blob` 的 part、body 的 `BufferSource`）不給 Lua 用，Lua 的字串走字串的 case，所以 Lua 給不出不是 UTF-8 的 body 或 blob。
- `Blob`：沒有 `stream()`、`textStream()`（沒有 streams）、`FileList`（沒有選檔案的控制項）、`FileReaderSync`（沒有 worker）；整份 bytes 在 renderer 的記憶體裡，大的 blob 不存到磁碟（Chromium 存）。`File` 沒有 Chrome 的 `lastModifiedDate`（規範拿掉了，WPT 的 `historical.https.html` 要它不存在）。`FileReader` 一次讀完：`progress` 只有一個（Chrome 讀 20MB 的 blob 也一樣），`error` 一律是 `null`（記憶體裡的 bytes 讀不會失敗）；事件和 `Blob.text()` 的先後照 task 的順序（Chrome 的 bytes 在 browser 的 process，來回一趟的延遲讓先後每次不同，`loadstart` 通常在 `setTimeout(0)` 之後）。和 Chrome 152 不同、照規範（WPT 這樣測）的兩處：`readAsText` 沒有 label 時照 blob 的 `type` 的 `charset` 解碼（Chrome 不理，一律 UTF-8），在 `load` 或 `abort` 的 handler 裡開始新的讀時舊的那次不發 `loadend`（Chrome 照樣發）。照 Chrome、和規範不同的：前後有空白的 label 不算（Encoding 會先去掉空白），讀完之後的 `abort()` 留著 `result`（File API 是 `null`）。`Response.blob()` 的 type 是 `Content-Type` 的值轉小寫（照 Chrome 152，Fetch 說是解析、序列化過的 MIME type）。
- `<canvas>`：只有 2D context。畫布到最上層只有平移、沒有 opacity、至多一個圓角 clip，而且寬和高都不超過 8192 時是自己的 compositor layer（Chrome 照 GPU 真正的 texture 上限，Apple Silicon 上 8193 到 16384 的 canvas 在 Chrome 是 layer，在 machopo 畫進頁面），變了只換那個 layer 的 texture；transform 不只平移（`scale`、`rotate`、skew）、在 opacity 底下、在兩層以上的圓角 clip 裡、或在 `clip-path` 的路徑裁切裡時，每次變了都把快照畫進頁面的 display list，重新 raster 它碰到的 tile（Chrome 這些情況還是 layer，transform 和 opacity 由 compositor 做；machopo 的 compositor 和 Viz 只會平移 layer）；快照是像素的一份複本。CSS 讓它變大或變小時用雙線性取樣、沒有 mipmap（Chrome 的預設），沒有 `image-rendering`。context 只有狀態（`save`、`restore`、`reset`）、transform（`setTransform` 收六個數字或 `DOMMatrix2DInit` 的字典，沒有 `getTransform` 和 `DOMMatrix`）、`globalAlpha`、`globalCompositeOperation`（Porter-Duff 的模式和 `multiply` 那類的 blend mode）、陰影（`shadowOffsetX` / `Y`、`shadowBlur`、`shadowColor`）、`fillStyle` / `strokeStyle` 是顏色、漸層（線性、放射、圓錐；沒有 Chrome experimental 的 `colorInterpolationMethod`、`hueInterpolationMethod`、`premultipliedAlpha`）或圖案（`createPattern`，`setTransform` 收 `DOMMatrix2DInit`）、線的樣式（`lineWidth`、`lineCap`、`lineJoin`、`miterLimit`、虛線）、`fillRect`、`strokeRect`、`clearRect`、路徑（`beginPath` 到 `roundRect`）、`fill` / `stroke` / `clip`、`isPointInPath`、`isPointInStroke`、`Path2D`（建構子收另一個 `Path2D` 或 SVG 的 path data，`addPath`）、`getImageData`、`createImageData`、`putImageData`、`toDataURL`（PNG 和 JPEG，照 Chrome 的編碼器和設定；`image/webp` 和其他格式給 PNG，Chrome 有 WebP；`quality` 只給 JS，`machopo:dom` 的 guest 用預設的品質；沒有 frame 的文件編不了碼，給 `data:,`）、`toBlob`（同樣的檔案；main thread 上只拿快照，在 renderer 的一條編碼 thread 上編，Chrome 的 PNG 在 idle task 裡分段編、JPEG 交給 worker thread）、圖片（`drawImage` 的三種形式、`imageSmoothingEnabled`、`imageSmoothingQuality`），和文字的狀態（`font`、`textAlign`、`textBaseline`、`direction`、`letterSpacing`、`wordSpacing`、`fontKerning`、`fontStretch`、`fontVariantCaps`、`textRendering`）、`fillText` / `strokeText`、`measureText`；沒有 `lang`、`filter`、`OffscreenCanvas`，`getContext` 的其他 id（WebGL、WebGPU、`bitmaprenderer`）都是 `null`。`getContext` 的 `options` 不管 id 都照 2D 的設定轉換（規範是 `any`、只有 2D 才轉），給別的 id 不是物件的 options 也是 `TypeError`。`desynchronized`、`colorSpace`、`colorType` 只記下、`getContextAttributes()` 回報，不影響怎麼畫；`willReadFrequently` 決定 canvas 在哪裡畫：設了的在 main thread 上，其他的在 canvas raster thread 上，讀像素時 main thread 等它，`getImageData` 讀回兩次之後搬回 main thread、之後一直在那裡畫（和 Chrome 一樣；Chrome 在一份 document 裡搬回的 canvas 夠多時，新的 canvas 一開始就在 CPU 上，machopo 沒有）；`display-p3` 的畫布和 `ImageData` 的像素不換算色彩空間。`currentcolor` 照 hit test 共用；Chrome 用 Skia 的 `SkPath::contains` 和 stroker）：conic 近似成 cubic、kurbo 的 stroker 和 Skia 的不同，離邊緣不到一個像素的點可能和 Chrome 不同。陰影一律畫成 drop shadow 的 image filter 的 layer（Chrome 不透明的畫用 looper：mask filter 的個數，再看數字是不是有限的。`strokeRect` 只有寬或高是 0 時是來回的閉合路徑，沒有端點（Chrome 的）。`fill` 和 `stroke` 一律錄成路徑（Chrome 把一條線、空路徑上的一個 `arc` 另外錄成線和弧，Skia 畫出來應該一樣）。fallback content 一律不排版（machopo 一直執行 script），裡面的元素也就拿不到 focus（規範和 - blob URL：
  - Browser 只把網址交給登記它的 renderer 的子資源（Chromium 照 storage partition 分：同源的另一個分頁也拿得到），導覽不限。
  - 撤銷在 renderer 當場生效，但要等 loop 這一輪結束才送到 Browser：同一個 task 裡先撤銷、再設 `<script>` 或 iframe 的 `src`，照樣載得到（規範說要失敗；`fetch()` 和 `<img>` 在 renderer 就擋下了）。反過來，一個 task 要的載入如果要到下一輪才送（lazy 的 `<img>`、layout 之後才開始的），撤銷會先到，載不到。
  - `Request` 不記住它的網址建立時對應的 blob：建立 `Request` 之後撤銷，再 `fetch(request)` 是 network error（規範和 Chrome 拿得到；WPT 的 `url-with-fetch.any.js`）。
  - 用 `target=_blank` 等開到新分頁的 blob URL，要等 embedder 開好分頁才載入，那時可能已經撤銷了。
  - blob 的 `Content-Type` 照 blob 的 type 送，不檢查是不是合法的 MIME type；`Range` 的單位不分大小寫。兩者都照 Chrome 152，WPT 要求的是空的 type 和分大小寫。
- `URL` 和 `URLSearchParams`：沒有 `webkitURL` 這個舊名字；`URL.createObjectURL` 只收 `Blob`（沒有 `MediaSource`）。解析用 `url` crate（2.5.8）和它的 `idna`，和 URL Standard 不一致的地方不在 machopo 這邊修：WPT 的 URL 資料（2026-10-08）`urltestdata` 896 個裡 69 個不過（`file:` URL 的 host 和多個斜線、Windows 的磁碟代號 `|`、opaque path 結尾的空白沒有編碼成 `%20`、IPv4 形式的 host 裡的 `xn--` 標籤），setter 278 個裡 22 個，`toascii` 87 個裡 21 個，`IdnaTestV2` 2671 個裡 759 個（大多是 `xn--` 標籤解碼之後的檢查比規範嚴）。Lua 的 runtime 把 table 當成 record 時，順序是 Lua 的 `next` 的（Lua 的 table 沒有別的順序），JS 的物件和 wasm 的 `list<tuple<…>>` 照給的順序。
- shadow DOM 有 shadow tree（`attachShadow()`、`shadowRoot`、`ShadowRoot` 的設定、markup 和 `getElementById`），裡面的節點和 host 一起算在 document 裡（`isConnected`、`getRootNode({ composed })`、執行 `<script>`、載入 `<iframe>`，`clonable` 的跟著 host 複製），事件經過 shadow root 到 host、retarget（`composed`、`composedPath()`、`relatedTarget`），`activeElement` 照 shadow tree retarget；還沒有的：
  - shadow tree 照 flat tree 算 style、排版、畫出來（host 的盒子裝它的 shadow tree，slot 的位置是分配到的節點或 fallback，沒有分配到 slot 的子節點沒有盒子（style 照樣算、從 host 繼承，`getComputedStyle` 讀得到，和 Chrome 一樣）；shadow tree 的 `<style>` 和 `adoptedStyleSheets` 只套用到那棵樹，分配到 slot 的節點從 slot 繼承；`:host`、`:host()`、`::slotted()`，不同樹的宣告照 css-scoping 的順序 cascade）。沒有 `::part()`、`exportparts`、`:host-context()`、`:has-slotted`。`:host()` 的參數裡的 `:host` 照樣成立（`:host(:host)` 符合 host；規範和 Chrome 不符合：比對參數時 host 不是 featureless 的）：比對是 `selectors` crate 的，不在 machopo 這邊繞過。shadow tree 裡的 `<link rel=stylesheet>` 照樣載入、只套用到那棵樹（Chrome 也是），但不擋住 render 和 parser 的 script（Blink 的 render-blocking 只算 document tree 的）。`elementFromPoint` 照 DOM 的規則 retarget（`document` 的回答 host，`ShadowRoot` 也有，回答它的樹裡的），文字回答它的 parent 元素；`elementsFromPoint` 只列出自己的盒子在那一點的元素，沒有盒子的 slot 不會因為它的 fallback 文字被列出（WPT 的 `DocumentOrShadowRoot-prototype-elementFromPoint.html` 有四項因此失敗）。
  - `delegatesFocus` 只存著設定，不把 host 的 focus 委派給 shadow tree 裡的元素，shadow tree 裡的元素也不在 Tab 的順序裡。
  - slot 有 named 和 manual assignment（`HTMLSlotElement`、`assignedNodes()`、`assignedElements()`、`assign()`、`assignedSlot`、`Element.slot`）、`slotchange` 和經過 slot 的事件路徑。沒有 declarative shadow DOM（`getHTML()` 的 `serializableShadowRoots` 照樣不序列化 shadow root）。
- custom element 有 registry（`customElements` 的 `define`、`get`、`getName`、`whenDefined`、`upgrade`）、建構（`new X()`、`createElement`、`createElementNS` 當場呼叫建構子）、upgrade、四種生命週期 callback（`[CEReactions]` 的成員回來之前呼叫）和 `:defined`。和 Chrome 不同、還沒有的：
  - 主文件的 parser 碰到已經定義的名稱時不同步建構：照舊建成 undefined 的元素，插進 document 時排 upgrade，在 parser 那一步之後的 microtask 才 upgrade（Chrome 在 parser 裡就呼叫建構子），建構子和 `connectedCallback` 晚於後面的元素的 parse。module script 和 `defer` 的 script 定義的元素（Speedometer 的都是）兩者一樣，都是 upgrade。
  - `createElementNS` 帶 prefix 的名稱（`p:x-foo`）建構出來的元素沒有 prefix（HTML 在建構之後設；`dom` 的元素名稱建立之後不變）。
  - `HTMLElement` 的建構子在檢查 `new.target` 有沒有定義之前，已經讀過它的 `prototype`：V8 呼叫 API function 當建構子時，先照 `new.target.prototype` 建好 receiver 才呼叫 callback（只有 `prototype` 的 getter 看得出差別）。
  - 沒有 customized built-in element（`define` 的 `extends` 是 `NotSupportedError`，`is` 不理；Safari 也不做）、`ElementInternals`（`attachInternals()`）和 form-associated custom element（`formAssociated` 和表單的 callback 照樣讀、檢查，但不用）、scoped registry（`new CustomElementRegistry()`）。
- `Range` 的幾何（`getClientRects`、`getBoundingClientRect`）照 Blink 的 `Range::GetBorderAndTextQuads` 取元素和 text 節點，文字的盒子從 fragment 算，高度是字型的 ascent 加 descent，整個在 range 裡的 `display: contents` 元素算它的子節點的；SVG 的 `<text>` 裡的文字沒有（不經過 inline layout，Chrome 有）；只有 LTR（從右到左的文字，例如希伯來文，一個盒子都沒有），ligature 裡的位置算整個 cluster（Chrome 照字元平分）；`zoom` 不縮放盒子；在 `position: fixed` 的元素裡、但它的 parent 不是那個元素的 text，盒子照樣扣掉 viewport 的捲動（和元素的 `getClientRects` 一樣，只看元素自己）。

  - `fetchStart` 和之後沒有用到的連線的時間通常是 0：browser 一開始導覽就發請求，在 0.1 ms 以內（Chrome 有幾毫秒）。

打開一個能複選的 popover）；頁面沒有 `direction`，清單一律對齊 select 的左邊。listbox 照 Chrome 用滑鼠（Shift 是一段、Ctrl 加減、拖曳）和鍵盤選，但拖到 listbox 外面時不自動捲動；沒有打字找 option（type-ahead）；按鍵不跳過 `display: none` 的 option（Blink 跳過沒有 box 的）；方向鍵不看 writing mode；Enter 不送出表單（還沒有 implicit submission）；Ctrl+Space 在 `keydown` 加減（machopo 的 Ctrl+Space 沒有 `keypress`，Chrome 有）。script 改了選取之後，listbox 不捲到選到的 option，鍵盤也從使用者上一次移到的 option 走（Blink 都照 script 選的那個）。滑鼠 focus 的 listbox 之後按鍵也不畫 focus ring（`:focus-visible` 只在 focus 的當下決定，Chrome 按了鍵就畫），所以 `multiple` 的 listbox 用 Ctrl+方向鍵移到的 option 的 focus ring 只在用 Tab 進來時看得到。Ctrl 還是 Cmd 加減照編譯的平台（Mac 是 Cmd），不照情境選的快捷鍵。拿掉 `multiple` 時好幾個選中的留最後一個（HTML 的演算法；WPT 較新的 `select-attribute-change-reset` 要第一個）。選取範圍：只在控制項有 focus 時畫（和 Chrome 一樣），使用者只能在文字控制項裡用 Shift 加方向鍵、Home、End 選（不能用滑鼠）；textarea 的子節點變短或 type 換了，存著的範圍不跟著縮，只在讀的時候限制（Chrome 會改），所以之後值又變長時還是原本的位置；`selectionDirection` 沒給時一律是 `none`（HTML 讓不支援沒有方向的平台用 `forward`）；WPT 的 runner 不跑 `<meta name=variant>`，`selection-not-application.html` 只跑到沒帶 query 的那一份。
- `<link>` 的 `crossorigin`：`modulepreload` 和 stylesheet 照它用 CORS 抓（見「Script」）；stylesheet 沒有 `crossorigin` 時從別的 origin 抓到的照樣套用，script 讀不到它的規則（`SecurityError`）。`integrity` 只有 reflection（SRI 沒有）。`relList.supports()` 只對 machopo 會處理的 `stylesheet`、`modulepreload` 回答 `true`（宣稱支援卻不處理，用 `supports()` 偵測功能的頁面會依賴它）：Chrome 也回答 `preload`、`prefetch`、`preconnect` 等，WPT 的 `html/semantics/rellist-feature-detection.html` 照 Chrome 的寫，因此不跑；`<a>`、`<area>`、`<form>` 還沒有 `relList`。`<link rel="stylesheet">` 不分派 `load` / `error`。
- 一個 DOM 有多個 realm 時（iframe 的子 frame），事件、static `NodeList` 的 wrapper 建在第一個碰到它的 realm，不是規範的 relevant realm（Blink 的事件也是在呼叫 listener 時用 listener 的 context）。
- 宣告表和規範的 WebIDL 刻意不同的地方：Chrome 才有的 `onmousewheel`、`document.body` 沒有 setter…；`GlobalEventHandlers` 在 `Element` 上。
- `getClientRects`、`getBoundingClientRect` 從 layout 的 fragment 算：在行上沒有 box 的 inline 元素沒有 rect，例如空的 inline 元素（行框是空的時候）、`<br>`、包著 block 的 inline 元素（Chrome 給在那個位置、大小為 0 的 rect）。WPT 的 `getBoundingClientRect-empty-inline-002`、`getClientRects-br-htb-ltr`、`getClientRects-inline-with-block-child` 因此失敗（baseline）。頁面捲動之後，fixed 盒子裡的元素（不是 fixed 盒子自己）的 rect 多扣了捲動的距離（捲 15px 時 405 變成 390，Chrome 152 照樣是 405），`layerY` 也跟著差這麼多。
- 沒有 `scrollend` 事件，也沒有 visual viewport 和它的 `scroll` 事件。
- 捲動的原點都在左上：往上、往左溢出的內容（flex 的 `column-reverse`、`row-reverse`）捲不到，也不算進 `scrollWidth`、`scrollHeight`。Chrome 把這種捲動容器的原點放到另一端，`scrollTop` 是負的。WPT 的 `scrollWidthHeight-flex-column-padding-001` 因此失敗（baseline）。
- `behavior: 'smooth'`（`ScrollToOptions`、`ScrollIntoViewOptions`）和 CSS 的 `scroll-behavior` 沒有作用：script 的捲動都是 instant。`scrollIntoView` 不看 `scroll-margin` 和 `scroll-padding`（machopo 沒有這兩個 property），也只有水平的文字（`block` 是垂直、`inline` 是水平）。`scroll`、`scrollTo`、`scrollBy`、`scrollIntoView` 回傳的 promise 在 microtask 裡就 resolve、值是 `undefined`；Chrome 在下一個 task 裡 resolve、值是 `ScrollResult`。沒有 `scroll-snap`。
- `offsetParent` 是 flat tree 裡最近的有定位的祖先，否則 `body`、`table`、`td`、`th`（不是元素所在之外的 closed shadow tree 裡的）；`position: fixed` 的元素和沒有盒子的、根元素、body 元素是 `null`，和 CSSOM View 一樣。
- Geometry Interfaces 只有 rect（`DOMRectReadOnly`、`DOMRect`、`DOMRectList`），沒有 `DOMPoint`、`DOMQuad`、`DOMMatrix`。
- `NodeFilter` 的 `acceptNode` 回傳物件時當成 0（WebIDL 轉 `unsigned short` 時會呼叫它的 `valueOf`，`dom_api` 碰不到 engine），回傳字串時照 Rust 的數字解析，和 JS 的 `ToNumber` 在少數寫法上不同（`0x10`、`Infinity`）。
- document 記住它的 `NodeIterator` 的集合是線性的（`WeakSet`：加入時從頭找空格，移除節點時走過每一個活著的 iterator），Blink 用 hash set。一次建很多 iterator、又一直拿著的頁面（上千個）會讓加入和每次移除節點都變慢；沒被拿著的在 GC 之後空出格子。
- `MutationObserver` 通知的順序照規範（observer 第一次拿到紀錄的順序），Blink 照 observer 建立的順序，同時有好幾個 observer 在等時看得出差別。
- `ResizeObserver`：`devicePixelContentBoxSize` 照這個 frame 的 paint offset 對齊（迴圈的每一輪先 pre-paint），Chrome 用的是上一個 frame 的（它在 pre-paint 之前 gather），元素剛移到小數位置的那個 frame 可能差 1；SVG 元素的 bounding box 只四捨五入。深度是 shadow-including 的樹裡的深度（規範和 Chrome 是 flat tree 的：分配到 slot 的節點比它的 host 深一層以上）。entry 的大小是 gather 時的，Chrome 在呼叫 callback 時才從 layout object 讀，前一個 observer 的 callback 改了大小時看得出差別。
- `IntersectionObserver` 的 v2（`trackVisibility`、`delay`、`isVisible`，只有 Chromium 有）照 Blink 算，和 Chrome 152 實測的不同在：跨 site 的 iframe 裡的 target 照實際的範圍判斷（Chrome 的跨 site iframe 在另一個 process，外面的東西只要蓋到 iframe 的任何一處，裡面的 target 都看不見；machopo 的 iframe 都在同一個 renderer，也沒有 public suffix list 判斷 site）；畫到盒子外面的範圍取自 paint 的 display item：只算元素自己畫的（Blink 的 ink overflow 包括子孫的，子孫自己會被找到，只有很邊緣的情況不同），被轉過的 clip 照它外面的矩形裁（範圍大一點）；沒有 3D transform、SVG 的 `<filter>`、`<image>`、`foreignObject`，`<tspan>` 上的 `filter` 也不畫，這些蓋不住、也扭曲不了 target。`rootMargin`、`scrollMargin` 讀回時每一邊取整數（照 Chrome；規範是換算後的值）。看不見的子 frame 裡的 target 照樣每個 frame 計算（子 frame 不 throttle，見「iframe」）。圓角的 clip 當成矩形（照 Chrome）。`disconnect()` 照規範留著還沒送出的 entry。
- `AbortSignal.any()` 的來源和 dependent 互相強指著：沒有 listener 的 dependent 也活到它的來源被回收為止，一個長命的 signal 一直被拿去 `any()` 時會累積。Blink 是雙向 weak，加上撐住「有 listener、還可能 abort」的 signal。`AbortSignal.timeout()` 的 signal 在時間到之前一直被它的 DOM task 撐住，沒有 listener 也一樣。
- 沒有 `XMLHttpRequest`。`fetch()` 等整份 body 收完才 resolve（沒有 streams）：body 沒有盡頭的回應永遠不 resolve（直到 abort、document 丟棄），response 回來之後 abort 只讓 body 不能讀，連線早已結束。`Request` 的 `referrer`、`referrerPolicy`、`cache`、`integrity`、`keepalive`、`priority` 照規範檢查、讀得回來，但不改變行為：不送 `Referer`，沒有 HTTP cache 和 SRI；`mode` 照 CORS 生效，`credentials` 因為沒有 cookie，只改變 CORS 要求對方的條件。`RequestInit` 沒有 `window`（`any`，只能是 `null`）：給了非 `null` 的值也不是 `TypeError`。wasm 的 guest 的 `RequestInit` 是 record，`signal` 的 `none` 就是沒給，表示不出 JS 的 `signal: null`（不跟著 input 的 signal）。`Request` 和 `Response` 沒有 `body`、`formData()`，所以把 `Request` 當成 `RequestInit` 傳（`new Request(url, request)`）時拿不到它的 body。`json()` 和 static 的 `json()` 只有 JS 有（`any`）。body 可以是字串、`URLSearchParams`、`Blob` 和 `BufferSource`，沒有 `FormData`（其他的值照 WebIDL 的 union 轉成字串），整份在記憶體裡，沒有 `ReadableStream`（`response.body`）。`ResponseInit` 的 `status` 宣告成 `unsigned long`（規範是 `unsigned short`）：超過 65535 的值是 `RangeError`，Chrome 先除以 65536 取餘數（`65736` 是 200）。
- 很深的樹可能讓 renderer thread 的 stack 溢位、整個程式結束：Blink 的 perf test `dom/deep-tree-clonenode` 對深度 10000 的 `<span>` 鏈（`display: none`）做 `cloneNode(true)` 再 append，machopo 以 `fatal runtime error: stack overflow` 結束（Chrome 沒事）。溢位在哪一步（clone、插入、GC 或其他遞迴）還沒查。
- 回傳 promise 的成員，receiver 不對或參數轉換失敗時丟出例外，不是回傳 rejected 的 promise（WebIDL 和 Blink 的 `ExceptionToRejectPromiseScope` 是 reject），成員本身失敗時才 reject。現在這樣的成員是 `CSSStyleSheet.replace` 和捲動的那幾個（`scroll`、`scrollTo`、`scrollBy`、`scrollIntoView`：`scrollTo(1)` 丟出）。
- 跨 origin 的物件的 setter 用 holder 當 receiver：HTML 的 CrossOriginSet 用 [[Set]] 的 receiver，`Object.create(crossOriginWindow).location = url` 應該是 `TypeError`，machopo 照 holder 導覽（rusty_v8 的 `PropertyCallbackArguments` 沒有 V8 的 `This()`；WPT 的 `window-location-and-location-href-cross-realm-set.html` 兩項）。
- `KeyframeEffect`、`animate()` 的 `pseudoElement` 只認得 `::before`、`::after`、`::marker`：其他合法、machopo 沒有的 pseudo-element（`::first-line`、`::placeholder`）丟 `SyntaxError`；Chrome 收下、照寫法給回、動畫什麼都不套。
- `file:` 這種 opaque origin 的頁做的 `blob:null/…`（`URL.createObjectURL`），`revokeObjectURL` 不撤銷：只撤銷同 origin 的，opaque 的 origin 彼此不同。
- `performance.timing.unloadEventStart`、`unloadEventEnd` 一律是 0：前一份文件的 `unload` 沒有記下時間。`PerformanceObserver.observe()` 對不支援的型別、`entryTypes` 帶 `buffered` 時不印 console 的警告（Chrome 印）。
- IDL 的形狀和 Chrome 不同的地方（`idlharness` 的測試看得到）：`Window` 的一部分 attribute 和 operation（`css/cssom-view/idlharness` 的 54 項、`requestidlecallback/`、`hr-time/` 的 `performance`）、`Blob` 的 operation。global 上的 `queueMicrotask` 在屬性的最後（Chrome 在 `cancelIdleCallback` 和 `fetch` 之間），只影響 `Object.keys(window)` 的順序。
- `Selection.toString()` 是 range 的文字，不是排版之後的（Chrome 照 `innerText` 那一套：`display: none` 的不算、`<br>` 是換行）。
- geolocation 和 wake lock 的權限是模擬的（沒有使用者的詢問），沒有 permissions policy（跨 origin 的 iframe 的 `allow`）。

## 事件

- UI Events 的事件 interface 有 `UIEvent`、`MouseEvent`、`WheelEvent`、`KeyboardEvent`、`FocusEvent`、`InputEvent` 和沒有建構子的 `TextEvent`，沒有 `CompositionEvent`、`PointerEvent`、`TouchEvent`、`DragEvent`；`MouseEvent` 的 `layerX/Y`（沒有規範）照 Chrome 152：從目標（沒有盒子時往上第一個有盒子的祖先）往上第一個有定位或是 stacking context 的盒子（root element 也算）的 border box 起算（捲動容器和其他裁切不算），沒有就是 `pageX/Y`，捨去成整數；它和 `offsetX/Y` 每次讀都照當時的 layout 算（分派中和分派之後都是從目標的 padding edge 起算；Blink 第一次讀時算好、之後沿用），`UIEvent` 沒有 `pseudoTarget`，`InputEvent` 沒有 `dataTransfer`、`getTargetRanges()`。`pageX` 在讀的時候照 `view` 現在的捲動算（Blink 在建立時算好；兩邊都不先更新 layout，等著的 layout 會改的捲動位置讀不到），沒有 `view` 的事件不加捲動（和 Blink 一樣，和 CSSOM View 的「event's associated Window」不同）。`createEvent` 只認得 machopo 有的 interface（`Event`、`UIEvent`、`MouseEvent`、`KeyboardEvent`、`FocusEvent`、`TextEvent`、`CustomEvent`、`MessageEvent`），其他名稱照規範丟 `NotSupportedError`。
- user activation：
  - 觸發的只有 trusted 的 `mousedown` 和 Escape 以外的 `keydown`（machopo 還沒有 Pointer Events 和 touch，所以沒有 `pointerdown`、`touchend`）。
  - 沒有「用掉」activation：machopo 還沒有需要它的 API（`window.open`、全螢幕、控制項的 popup），activation 在期限內一直有效。
  - 狀態只在 renderer 的 DOM 裡（每個 window 一份），browser 不知道（Chromium 在 browser 也有一份，給跨 process 的 frame 和 browser 自己的檢查）；multi-process、跨 process 的 iframe 或 browser 要擋 popup 時要補上同步。
- `postMessage`：
  - 只能給同一個 renderer 裡、同源的 window（自己、子 frame、`parent`、`top`）；跨源的 window 連 `postMessage` 也碰不到（見「iframe」）。
  - transfer 只有 `MessagePort` 和 `ArrayBuffer`：machopo 還沒有其他能 transfer 的平台物件（`ImageBitmap`、`OffscreenCanvas`、`ReadableStream`……），放進 transfer list 是 `DataCloneError`（不是能 transfer 的型別）。port 只能 transfer 給同一個 renderer 裡碰得到的 window（同上）。
  - 帶著 port 的訊息沒送到時（目標的 document 被丟棄、`targetOrigin` 不符、訊息的目標 port 自己在 transfer list 裡），那些 port 就留在 detached 的狀態：配對的另一個 port 照舊配對著它，之後送過去的訊息留在它的 queue 裡，直到兩邊都被收掉（另一個 port start 過時，要等它 `close()` 或它的 document 被丟棄）。Chrome 的 port 在 mojo 的 pipe 裡，接收端不在時 pipe 關閉、訊息跟著丟掉。
  - 規範的 incumbent（`MessageEvent.source`、`origin` 和 `targetOrigin: "/"` 用的「呼叫的一方」）用 V8 的 entered context 近似：一般的情況（一份文件的 script 呼叫另一個 window 的 `postMessage`）一樣；別的 realm 的函式被呼叫、再由它呼叫 `postMessage` 時，用的是外層進入的那個 realm（Chromium 用 V8 的 `GetIncumbentContext`）。
  - `source` 是 `Window`（沒有 `WindowProxy`，見「iframe」）。
  - `data` 第一次讀時才反序列化；序列化用的是「for storage」，不能複製的在 `postMessage` 時就丟 `DataCloneError`，所以 `messageerror` 不會發生。
  - 只有 JS 有：`postMessage` 和 `MessageEvent.data`、`initMessageEvent` 的 `data`；`MessageChannel`、`MessagePort`、`MessageEvent.ports`、`structuredClone()` 也是。
- `MessageChannel` 和 `MessagePort`：兩個 port 都在同一個 renderer 裡，訊息直接排進對方的 posted message task（Chromium 經過 mojo 的 pipe，同一個 process 也一樣）；之後拆 process、port 要跨 renderer 時要補上通道。start 過、還配對著的 port 活到 `close()` 或它的 document 被丟棄（和 Chrome 一樣，兩個都沒人拿著也不會被收掉）。沒有 port 的 `close` 事件（`onclose`，Chrome 有）、`BroadcastChannel`、worker。
- Event handler 有 `GlobalEventHandlers`（照 Chrome 的那一組，不含 Pointer Events 和 touch 的）、window 和 `<body>` 的 `WindowEventHandlers`（照 `html.idl` 的 18 個；Chrome 152 的 `<body>` 沒有 `onpagereveal`、`onpageswap`）和 `AbortSignal` 的 `onabort`；沒有 `oncopy`、`oncut`、`onpaste`。其中 `scrollend`、`afterprint`、`beforeprint`、`beforeunload`、`languagechange`、`offline`、`online`、`pagehide`、`pagereveal`、`pageshow`、`pageswap`、`rejectionhandled`、`storage`、`unload` machopo 從來不分派，用 `"onscrollend" in window` 這樣判斷支援的頁面會等一個不會來的事件；`onbeforeunload` 照一般的 handler，沒有 `OnBeforeUnloadEventHandler` 的回傳值。`window.onerror` 和 `<body onerror>` 照 `OnErrorEventHandler`。值是不能呼叫的物件時當成 `null`（WebIDL 會留著、呼叫時才失敗）；content attribute 編譯失敗的回報沒有網址。
- focus：能 focus 的只有有 `tabindex` 的元素、有 `href` 的 `<a>`、表單控制項（`<input>` 但 hidden 的、`<button>`、`<select>`、`<textarea>`，disabled 的不行）、有 `focus`、`blur`、`focusin`、`focusout` listener 的 SVG 圖形元素（照 Chrome，`tabIndex` 還是 -1）和 editing host（Tab 也會停在它，`tabIndex` 照 Chrome 是 -1；Chrome 的 Tab 會不會停在它沒有實測），`<details>` 的第一個 `<summary>` 不行（它的 `tabIndex` 也是 -1，Chrome 是 0；WPT 的 `tabindex-getter`）；沒有 `visibility`、`inert`，「being rendered」只看有沒有 box。`focus()` 先做一次完整的 layout（Blink 只更新到 layout tree）；已經是 focused element 的和 Blink 一樣什麼都不做，也不捲進畫面（HTML 要捲）。`focus()` 照 Blink 的 `CenterIfNeeded` 捲進畫面：整個看得到不捲，部分看得到捲到最近的邊，看不到時置中；文字控制項和 editing host 捲的是 focus 之後 caret 的位置。machopo 畫不出 caret 時（選取不是收合的、editing host 裡只有空的 inline 元素）捲的是元素的盒子（Chrome 捲選取的位置，或它畫在 host 開頭的 caret）。`:focus-within` 不跨 frame：子 frame 的元素有 focus 時，父 frame 的 `<iframe>` 不成立。沒有 `window.focus()`、`window.blur()`、`FocusOptions.focusVisible`。autofocus 不等 script-blocking 的 stylesheet，也不看網址的 fragment。屬性和 state（focus、hover……）改變時的 style 失效：沒有規則用到就不重算；有規則在元素以下的位置用到（`.a span`、`div:hover span`）就照 descendant invalidation set 重算後代裡可能配到的（見「Invalidation」的 style 的重算範圍），否則只重算元素自己，子元素只在它們繼承的值、`display` 或用 `inherit` 取的值變了時重算。
- 使用者的滑鼠分派 `mousedown`、`mouseup`、`mousemove`、`click`、`auxclick`、`dblclick`、`contextmenu` 和 `mouseover`、`mouseout`、`mouseenter`、`mouseleave`，沒有拖曳和選取文字；`screenX`、`screenY` 一律是 0（machopo 不知道視窗在螢幕上的位置）。`contextmenu` 沒有選單；macOS 的 Ctrl+點擊不當成右鍵（Chrome 會）。連點的間隔只有 macOS 照系統的設定；Windows（讀系統設定要 `unsafe`）和 Linux 用 500 ms；距離各平台都是 Chromium 的預設（各方向 2 px）。`element.click()` 的合成 click 是 `MouseEvent`（HTML 是 `PointerEvent`，machopo 沒有 Pointer Events）；disabled 的表單控制項的 `click()` 什麼都不做，使用者的 `click` 不分派到它和它裡面，其他滑鼠事件照樣。有 activation behavior 的只有 `<a>`、checkbox 和 radio、送出和重設表單的按鈕，有 default event handler 的只有 `<a>`、`<label>`、`<input>` 和 `<button>`（按鍵）；`<a>` 沒有 `href` 等 `HTMLAnchorElement` 的 IDL attribute，script 要用 `setAttribute` 設連結。
- `dispatchEvent` 不會把瀏覽器建立的（trusted）事件改成 untrusted：script 拿不到那種還沒分派過的事件。
- 沒處理的 rejection 只分派 `unhandledrejection`，之後才加上 handler 時不分派 `rejectionhandled`；通知在 microtask checkpoint 之後當場做，不是 HTML 的另一個 task。
- `document.readyState` 和 `readystatechange` 有了，但沒有 `onreadystatechange` 這個 event handler（只能 `addEventListener`）。`load` 的 listener 新增的子資源不延後 `DidFinishLoad`（和瀏覽器一樣，但 reftest 要截到它們得用 `reftest-wait`）。
- `composedPath()` 在分派中看的是現在的樹：一項是不是經過分配到它的 slot，看前一項現在的 parent（DOM 照分派開始時記下的）；分派中 listener 把前一項移到 slot 底下或移走時結果不同。
- 處理一個輸入時 renderer 要一個 main frame，合併的 `mousemove` 在接下來的 `setTimeout(0)` 之前就分派了：`navigator.scheduling.isInputPending()` 在那之間回答沒有。
- 編輯鍵加上 Ctrl、Alt、Cmd 時不編輯、不移動：Chrome 的 Ctrl+方向鍵照字移動、Ctrl+Backspace 刪一個字，Mac 的 Cmd+方向鍵到行的頭尾。

## iframe

iframe 照同源、同 process 的情形做：有自己的 browsing context、window 和 document，照 `src`、`srcdoc` 由 renderer 載入，畫在 iframe 裡，接收點擊和滾輪。

- iframe 是 replaced element（300×150 加上 2px 的邊框，`width`、`height`、`frameborder`），子 frame 照 iframe 的內容框跑 style、layout，畫在內容框裡，點擊和滾輪會進子 frame，滾輪捲到底往外層傳；鍵盤從 focus 的元素（沒有時從最後按下滑鼠的元素，或 focused frame）往外捲。子 frame 裡的連結只有連到自己的 `#fragment` 會捲動，換頁、`javascript:` 和開新分頁都沒有作用。
- `<body>` 的 `marginwidth`、`leftmargin`（左右）、`marginheight`、`topmargin`（上下）照 Chrome 是 presentational hint：兩個一起出現時後寫的贏（HTML 的「The page」是 `marginwidth`、`marginheight` 贏；Chrome 152 和 machopo 一樣），`rightmargin`、`bottommargin` 照 Chrome 不算。iframe 的 `marginwidth`、`marginheight` 不傳給子 frame 的 body：子 frame 的 body 照樣是預設的 8px margin（WPT 的 `body-margin-*` 有 8 個是預期的失敗）。
- 子 frame 不 throttle：每個 main frame 都看每個子 frame 要不要更新，看不見的、跨源的也一樣（Chromium 會 throttle 看不見的跨源 frame；同一個 process 裡 `display: none` 的 frame 不 throttle，和 machopo 一樣）。
- 跨源的 window 什麼都碰不了（security token 擋下所有存取，`TypeError`；把自己的 realm 的成員用在它身上也一樣，例如 `getSelection.call(other)`）：規範允許的少數成員（`postMessage`、`closed`、`frames`、`length`、`parent`、`top` 等）也不行。
- 跨網站的 iframe 和頁面在同一個 renderer，只靠 security token 擋住互相存取（Chromium 的 site isolation 放在別的 process）。
- 子 frame 的導覽由 renderer 自己載入（一種子資源），browser 不知道子 frame：沒有子 frame 的歷史。子 frame 裡導覽到自己的 `#fragment`（連結、`location.hash`）照樣捲動、改網址、分派 `popstate` 和 `hashchange`，但不進 session history；導覽到別的文件（點連結、`location.href = …`）由 renderer 載入、換掉子 frame 的文件（舊的文件裡的 frame 跟著不在），一樣不進 session history。
- `javascript:` 的 `src` 不執行（當成一般的網址抓取，失敗）。`loading`、`sandbox`、`allow` 都還沒有（sandbox 的 iframe 照樣跑 script，裡面的 `loading="lazy"` 的圖照樣等到接近 viewport 才載入；`name` 只是屬性的 reflection，名稱給 window 的具名屬性，沒有 `window.name`）；`referrerpolicy` 只用在子 frame 的 navigation timing（`no-referrer` 時 redirect 的 `Timing-Allow-Origin` 只認 `*`；machopo 的請求都不送 `Referer`）。
- 載入失敗（網路錯誤、被擋下）的子 frame 是一份空的 document，沒有錯誤的說明（Chromium 是錯誤頁）。
- `window[i]` 和集合的 indexed property 一樣只能讀：設定、刪除、`Object.defineProperty` 會在 global 上建一般的屬性（規範是失敗）。
- `srcdoc` 的子 frame 在插入它的 script 跑完之前就載完、iframe 的 `load` 已經分派了；Chrome 之後才載入，script 之後加的 listener 等得到（WPT 的 `css/cssom-view/cssom-geometryutils-lifecycle.html` TIMEOUT）。

## 連結導航和 hit testing

- `history` 的 traversal 和 `scrollRestoration` 的時序和 Chrome 不同：`history.back()` 時捲動的還原和進行中的平滑捲動誰先，和 Chrome 不一定一樣（WPT 的 `scroll-behavior-smooth-navigation.html` 的平滑捲動那項標成 known intermittent）。
- 上一頁、下一頁、重新整理：同一份文件的 entry 之間（`#fragment`、`pushState`）不重新載入，分派 `popstate` 和 `hashchange`；其他的都重新載入，沒有 back-forward cache，不恢復捲動位置，只在 entry 有 fragment、捲動恢復的模式不是 `manual` 時捲到 fragment（Chrome 恢復之前的捲動位置）。
- `history`：state 沒有大小上限（和 Blink 一樣）；只收 `ValueSerializer` 能存的值，DOM 物件、函式、`SharedArrayBuffer`、`WebAssembly.Module` 是 `DataCloneError`。子 frame 的 `pushState`、`replaceState` 只改它自己的網址和 state，不進 session history（上一頁回不去，不分派 `popstate`，重新整理之後 state 不見），它的 `length` 和 `back()` 是主 frame 的（Chrome 的子 frame 的 entry 也在 joint session history 裡）。`history.go()` 等交給 browser 的時間是 task 結束時（Chrome 是呼叫的當下），看不出差別。
- `Location` 物件的 `[[PreventExtensions]]` 照一般物件（`Object.preventExtensions(location)` 成功，HTML 是 `TypeError`）：V8 的 template 做不到；`[[SetPrototypeOf]]` 照 HTML 不能換 prototype（`set_immutable_proto`）。沒有 `ancestorOrigins`（要 `DOMStringList`）。
- `location` 的導覽：不分派 `beforeunload`（`pagehide`、`unload` 在下一份文件 commit 時發，見 Navigation Timing 那一條）；`javascript:` 網址的結果是字串時不取代 document（和連結一樣）；不帶 referrer。交給 browser 的時間是 task 結束時（Chromium 是呼叫的當下），看不出差別。
- 導覽到同一份文件的 `#fragment` 之後，捲動等到 event loop 的最上層才排定、下一個 frame 才捲：同一個 task 裡接著讀 `scrollY` 還是舊的位置（HTML 的「navigate to a fragment」當場捲動，Chrome 也是；WPT 的 `location_hash.html` 的 srcdoc iframe 那項）。script 寫捲動位置的路已經有了，之後可以改成在導覽的當下捲動。
- 連結只有 `<a href>`，沒有 `<area>`；`mailto:` 之類交給系統的 scheme 不開，只記 log。頁面的連結和 `location` 不能導覽到 `data:` 網址（這個分頁和新分頁都不行，Chrome 也擋；iframe 和自動化的導覽可以），但 Chrome 會在 console 報錯，machopo 只記 log。
- 連結開在哪裡只看它自己的 `target`：`<base target>` 只是 `HTMLBaseElement.target` 反映的 attribute，沒有自己 `target` 的連結不照它開（HTML 的「get an element's target」、Chrome 會）。`target` 是名字時一律開新分頁：沒有具名的 frame（WPT 的 `the-base-element/base_multiple.html` 因此逾時）。
- 滑鼠離開視窗、或移到工具列和分頁列上時，頁面收不到：hover 留在最後的元素上，也不發 `mouseout`、`mouseleave`（Chrome 會）。要等下一次滑鼠在頁面上移動。
- 連結開新分頁：沒有 `window.open`；有名字的 target 每次都開新分頁，不重用；Shift+點擊開新分頁而不是新視窗，Alt+點擊照一般的點擊（沒有下載）；script 自己觸發的點擊（`dispatchEvent`）不開新分頁，它的 `target="_blank"` 什麼都不做（沒有使用者手勢的概念，Chrome 會封鎖這種彈出視窗）；iframe 裡的連結照舊不導覽。右鍵有 `contextmenu`，但沒有選單。
- 游標照 `cursor` 的關鍵字（Blink 的 `EventHandler::SelectCursor`）：`url()` 的游標圖片不載入，用它後面的關鍵字；`image-set()` 照 Chrome 只收 `url()` 的選項、和 `url()` 一樣不載入；沒有 `light-dark()`（有它的宣告整條無效，Chrome 收）。`auto` 在連結上是手指、在選得到的文字（`user-select` 不是 `none`）上是 I 形，雖然 machopo 還不能選取頁面的文字；文字欄位的 I 形來自 UA stylesheet 的 `cursor: text`（machopo 沒有 contenteditable）。`::before`、`::after` 的文字照產生它的元素的 `cursor`（Chrome 照 pseudo-element 自己的）。按著按鈕拖曳時照滑鼠底下的元素（Chrome 在拖曳選取時一直是 I 形）；捲軸上沒有自己的游標。滑鼠不動、底下的東西變了時，下一次 pre-paint 之後更新（Blink 用 50ms 的 timer）。
- Hit testing（點擊和 `elementFromPoint` 都是）：text run 的範圍用字型的 ascent 和 descent。
- 新的 document 的第一個 frame 畫出來之前，點擊還是送給上一份（照 compositor 畫的是哪一份），上一份已經丟棄了，所以點擊沒有作用。輸入的 hit test 先把 lifecycle 更新到 pre-paint（和 Blink 一樣），script 剛改的東西照它現在的位置。

## 工具列和網址列

- 這是過渡的原生 UI，之後要換成能用 HTML / CSS 自訂的。
- 分頁列在系統的視窗框（標題列）下面，不像 Chrome 畫在標題列裡。分頁沒有 favicon、載入中的動畫和 tooltip；不能拖拉排序（之後）；分頁太多、縮到最窄（56 CSS px）之後，超出右邊的看不到、點不到，只能用快捷鍵切換。標題太長時的淡出是用幾條透明度遞增的細條疊出來的，不是真的漸層。新分頁是 `about:blank`，沒有新分頁頁面。切換分頁時網址列失去 focus，打到一半的網址不保留。沒有停止載入的按鈕，也沒有載入中的提示。
- renderer 當掉的分頁顯示 sad tab，分頁列上看不出是哪一個（沒有 favicon）；一再當掉時說明不變。`about:crash` 讓 renderer 立刻結束（像 `chrome://kill`），不是真的 crash。卡在無窮迴圈裡的 renderer 不會因為 `about:crash` 結束：它只在處理完目前的工作之後才讀到結束的訊息。
- 隱藏的分頁不畫、不跑 `requestAnimationFrame`，計時器照常跑；它的 `DidFinishLoad` 要等再顯示時才送（跟著 frame 送）。只有切到別的分頁算隱藏：視窗縮到最小或被其他視窗擋住時，`document.visibilityState` 還是 `visible`（Chrome 縮到最小時是 `hidden`，也照被擋住的程度判斷）。等著 frame 的 input ack 不等：隱藏時立刻送出，不帶 frame。
- 網址列沒有搜尋、沒有自動完成和建議，也不會把網址裡的 scheme 或路徑變淡顯示。
- 游標不會閃爍；沒有雙擊選詞、三擊全選；右鍵沒有選單。
- 工具列的顏色和大小是寫死的，不跟著系統的深色模式和字型大小。
- 視窗的版面只有一層：工具列和網頁 view 是平的清單，沒有巢狀的 view 和版面管理；Tab 鍵只在網址列和網頁之間移動 focus，工具列的按鈕和分頁拿不到 focus；指標離開一個網頁時不通知它（網頁沒有 `mouseout`）；滾輪每次都給指標下面的網頁，沒有 scroll latching。現在只有一個網頁，看不出差別。

## WebDriver 和自動化

- machopodriver 的指令見 `crates/driver/README.md` 的「有的指令」，其他的回答 `unknown command`：沒有 Get Element Text、Get Active Element、cookie、user prompt、Print、最大化、最小化和全螢幕，也沒有 Set Permission（testdriver 的 `set_permission`）：WPT 的 `geolocation/`、`screen-wake-lock/` 大多先用它設權限，在 machopo 上停在那裡（machopo 也沒有權限的狀態可以設）。
- Element Click 只照元素的框（`<option>`、`type=file` 的 `<input>` 沒有規範裡的特別處理）。點擊開始的導覽只等在點擊處理完之前就開始的（`setTimeout` 之後才導覽的不等，chromedriver 也大致如此）。截圖只截顯示中的分頁，大小是 physical px（device pixel ratio 不是 1 時比 CSS px 大）。
- WebDriver 的視窗都是分頁：New Window 不管要求的種類都開分頁（規範允許）。Switch To Window 會把分頁切到前面（和 chromedriver 一樣；背景的分頁不跑 rAF，也截不到圖）；切到背景的分頁（例如網頁的連結在前景開了新分頁）裡開始的導覽，要等它再顯示，machopodriver 才等得到畫面（`load` 之後的 `Machopo.waitForLoad`；上面「隱藏的分頁」）。
- 視窗的大小包括工具列：800×600 的視窗裡網頁的 viewport 是 800×526（Chrome 的 headless 沒有工具列，視窗多大 viewport 就多大）。WPT 寫死 600 高的 viewport 的測試因此不同（`intersection-observer/v2/` 的幾份比對 `rootBounds`）。
- Set Window Rect 和 `Browser.setWindowBounds` 的大小每邊夾到 8192 實體像素（Viz 畫成一張 texture；Chrome headless 照收，100000×100000 的 `innerWidth` 是 100000）。沒有最小的視窗大小：Set Window Rect 給 10×10 就是 10×10，網頁 view 是空的（Chrome 有最小的大小，wdspec 的 `test_set_smaller_than_minimum_browser_size` 不過）。沒有平台視窗時，視窗的位置只是記下來（`screenX`、`screenY` 跟著它，但沒有 `screen` 物件：wdspec 的 `set_window_rect` 有幾個測試要 `screen.availWidth`）。
- Perform Actions 只有滑鼠、鍵盤和滾輪：`pen`、`touch` 的指標和滑鼠的第 3、4 個按鍵（上一頁、下一頁）回答 `unsupported operation`（machopo 沒有 Pointer Events 和 touch）。有 `duration` 的移動和捲動一次到位、再等滿時間，不拆成好幾個事件（和 chromedriver 一樣；規範要拆：wdspec 的 `duration.py`、`test_interspersed_wheel_pointermove` 因此失敗）。輸入狀態每個視窗一份（照規範；chromedriver 整個 session 一份）：一個視窗裡按著的 modifier 和按鈕，切到別的視窗就不算按著；關掉視窗時它按著的不放開，也不分派 `keyup`、`mouseup`。連點（`clickCount`）只在同一個 Perform Actions 裡算（規範還沒定，WPT 的 tentative 測試這樣期待；chromedriver 和平台的 500 ms、4 px）。`keyCode` 是 machopodriver 照美式鍵盤給的，沒有輸入法。
- Element Send Keys：machopo 沒有檔案，`<input type=file>` 回答 `unsupported operation`（不照規範先檢查檔名）。不可輸入的控制項（color、日期時間那幾種、range）照規範直接設值，不分派事件。modifier 照規範只在一次 Send Keys 裡按著，結束時放開（chromedriver 在不同次之間一直按著）。不只一個 code point 的 grapheme cluster（組合字元、emoji 的序列）當成一個鍵打出來：規範要送 composition 事件，machopo 沒有。`<body>`、`<html>` 以外不能取得焦點的元素（`visibility: hidden` 的 machopo 還算得到焦點）是 `element not interactable`。
- Element Clear：machopo 沒有 constraint validation，空的控制項一律不動；「在畫面裡」只看元素的第一個框（大小是 0 也算）在不在 viewport 裡，不做 hit test（WPT 的 wdspec 期待畫面外的是 `element not interactable`、被蓋住的照樣清空，這樣兩者都對）。`<textarea>` 清空後當成 dirty（它的值不再跟著子節點），規範是不 dirty 但值是空的；`color` 清空後是空字串（machopo 的 `color` 不清理值，Chrome 是 `#000000`）。
- 找元素只有 `css selector` 和 `tag name`：`link text`、`partial link text` 要元素畫出來的文字（`innerText`，machopo 還沒有），`xpath` 要 XPath，都回答 `unsupported operation`。
- WebDriver 的 `javascript error` 只有例外的 `ToString`（`Error: …`），`stacktrace` 是空的。script 逾時之後還在跑（規範也不中止它），之後的結果丟掉；script 還沒 settle 就導覽走了，回答 `javascript error`（document 不見了）。wasm 的文件不執行 WebDriver 的 script，Get Element Property 也不行。
- DevTools 的 heap snapshot 裡，DOM 的物件照 elise 的型別命名：節點都叫 `Node`（和它的 wrapper 併成一個），不是 Chrome 的 `HTMLDivElement` 這樣的類別名，Memory 面板的 Summary 因此把所有節點列在同一組；不在任何文件的樹裡的節點標成 detached，其他物件（event、listener 的資料……）不標。物件的大小是它在 elise 的 heap 裡的 bytes，不含 heap 外的字串和 `External` 的資料。
- WPT 的 wdspec 裡不少失敗是 machopo 的 DOM 還沒有的 API，不是 WebDriver 的：使用者用滑鼠選取文字（三連擊）、XML 文件，machopodriver 也還不給 shadow root 的參照；還有 `alert` 等 user prompt、`window.open`、`window.close`、拖放。鍵盤的測試大多先點 `<input>` 讓它有焦點，文字控制項沒有大小時點不到，測試在 fixture 就失敗，有了 Chrome 的大小之後還沒在本機重跑（每天的 CI 跑 wdspec）；`test_actions.html` 的座標照 Chrome 的版面寫死，版面和 Chrome 不同時點不到。在 Wayland 的 Linux 上，`set_window_rect/set.py` 的 `test_partial_input` 失敗：測試的 `is_wayland_headful` 看 wptrunner 的設定有沒有 `headless`，machopo 的 product 沒有給，測試因此以為視窗是 Wayland 上真的視窗、位置不能改，但 machopodriver 的 machopo 沒有平台視窗，位置照樣記下來（metadata 是 macOS 上的結果）。
- machopodriver 對 machopo 的呼叫只有導覽的等待（`pageLoad`）、script 的逾時和 implicit wait 有期限，其他的沒有：machopo 活著卻少回答一次，driver 就一直等。machopo 結束時照樣回答 `disconnected`。
- 一次一個 session，每個 session 一個新的 machopo。沒有 WebDriver BiDi（`webSocketUrl`）、proxy、cookie、user prompt；`acceptInsecureCerts` 只能是 `false`。
- `machopo --automation-pipe --window`（真的視窗）期間不理會平台的滑鼠和鍵盤（自動化的結果才穩定），視窗在最上層；人不能一起操作。`--window`、`--host-resolver-rules`、`--additional-trust-anchors` 只在 `--automation-pipe` 時有用，視窗和 `--headless` 不收。
- machopo 只有一個視窗：`Browser.setWindowBounds` 改位置和大小，沒有最小化、最大化、全螢幕。`Machopo` domain 的操作都作用在目前的分頁。
- `Machopo.waitForLoad`（machopodriver 在 `load` 之後也用它等畫面）等的是分頁「現在」最新的導覽；藏在後面的分頁不畫 frame，載入完要等它顯示出來（machopodriver 的 Switch To Window 會把分頁切到前面）：點了連結之後馬上問，導覽可能還沒開始（renderer 要開的網址還在路上），就回答前一份文件已經載入完。情境在點連結之後等文字（`wait-text`），不用 `wait-loaded`。
- Get Title 是分頁的標題，不是在網頁裡讀 `document.title`（chromedriver 是）：renderer 在每個 task 之後才把改了的標題告訴 browser，script 剛改的標題要等那個 task 結束才讀得到。
- browser 自己回答的 CDP 方法只有 WebDriver、情境和 `Target` 用到的那幾個（`crates/shell/README.md` 的「自動化的 pipe」），和 `Network` 的 cookie、cache、網路狀況的命令（同一份的 `Network`），pipe 和 `--remote-debugging-port` 都一樣；分頁的 session 的其他命令交給 renderer 的 agent（`Page`、`Network`、`Log`、`DOM`、`CSS`、`Overlay`）和 V8 inspector（`Runtime`、`Debugger`、`Profiler`、`HeapProfiler`、`Console`、`Schema`），其他的 domain 回答找不到方法：Chrome 的 DevTools 的 Elements 面板列得出 DOM 樹、跟著 script 更新，滑過節點時頁面上框出它，Computed 和 Chrome 一樣（property 的清單是 machopo 有的那些），Styles 列出元素自己的規則、inline style、presentational hint、它的 pseudo element 的規則和每個祖先的規則（繼承來的），規則帶著它在 stylesheet 原文裡的位置、包著它的 `@media` 和 `@supports`，宣告照原文列出（Sources 列出每份文件和 shadow root 的 `<link>`、`<style>` 和 adopted 的 stylesheet）。解析時丟掉的宣告劃掉，包括 machopo 還不支援、Chrome 支援的 property 和值（Chrome 不劃）；machopo 丟掉的 at-rule（`@import`、`@layer`、`@container`、`@font-face`……）和裡面的規則不在 Styles 裡。`@media` 沒有拆開的條件（`mediaList` 是空的，也沒有 `getMediaQueries`：只有裝置模式的 media query 尺規用它們，machopo 沒有裝置模式），選擇器的 specificity 沒有逐個簡單選擇器的分解（Chrome 152 的 `specificity.components`，specificity 的提示用）。script 用 CSSOM 改過的 stylesheet（`insertRule`、`deleteRule`、改規則的 `style`），原文從此是 CSSOM 序列化的規則，一條一行，位置照它算（Chrome 把改的規則寫進原本的原文，留著註解和排版，也留著刪掉的規則）。inline style 改了只送一次 `styleSheetChanged`（Chrome 送兩次）。stylesheet 的原文：`<style>` 的是它現在的文字（script 用 `insertRule` 填的空 `<style>` 是它的規則序列化的），constructed 的是 CSSOM 序列化的規則（和 Chrome 一樣）；`<link>` 的是 DevTools 連上時載入的回應，連上之前就載入的，第一次要它的原文時照它的 `<link>` 再抓一次（Chrome 從快取拿，machopo 沒有快取）：伺服器現在給的解析出來和頁面的規則不一樣時給 CSSOM 序列化的規則，停在斷點時要等繼續才回答，抓到之前 header 的 `length` 和結束的位置照序列化的算。script 建的 `<style>`（`innerHTML`、`textContent` 的）的文字從 0 行 0 欄開始（Chrome 給 fragment parser 的位置）；載入失敗的 `<link>` 是一份空的 stylesheet，`loadingFailed` 一律是 false。`CSS` 的命令只有 computed style、套用的規則、inline style、字型、動畫的樣式（`getAnimatedStylesForNode`）、跟著 computed style 的改動（`trackComputedStyleUpdatesForNode`，不收 pseudo element：Computed 選著 `::before` 時不跟著更新）和強制的 pseudo-class（`forcePseudoState`，Styles 的 `:hov`：強制的 `:visited` 收下但不生效，machopo 的 `:visited` 一律不成立；Chrome 讓 `:visited` 的規則套上顏色類的 property），其他（`getMediaQueries`、`getBackgroundColors`、`getLayersForNode`……）回答找不到方法。`getPlatformFontsForNode` 的 `isCustomFont` 一律是 false（machopo 沒有 `@font-face`），不算 SVG 的文字。`DOM` 只讀：編輯的命令（`setAttributeValue`、`setOuterHTML`、`removeNode`、`undo`……）回答找不到方法，DevTools 裡的編輯不生效。行內元素的盒模型是它在每一行的 box 的外框，沒有 margin（Chrome 有左右的 margin），`getContentQuads` 是每一行的 box（Chrome 往下拿它的子節點的）。`getNodeForLocation` 不管 `ignorePointerEventsNone`。`Overlay` 只畫元素的四個框和標籤（名字、id、class、大小）：沒有 grid、flex、container query、scroll snap 的 overlay，沒有尺規、延伸線、距離，標籤沒有 accessibility 的資訊和對比度（`getHighlightObjectForTest` 的 `elementInfo` 也沒有它們和 `layoutObjectName`）；要畫其他 overlay 的 `setShow…` 回答錯誤（不畫時回答成功），`setInspectMode` 的 `captureAreaScreenshot` 當成關掉；選取元素的模式只用滑鼠（沒有 Esc 取消）。overlay 在 compositor thread 上捲動時要等下一個 main frame 才跟上（Chrome 也是）。停在斷點時照樣畫（Console 的改動、框的節點、`setPausedInDebuggerMessage` 的提示），但提示沒有繼續、逐步執行的按鈕，CSS 動畫不往前走（Chrome 的照樣走），停在 `requestAnimationFrame`、ResizeObserver 的 callback 裡時不畫（那個 main frame 停在半路；Chrome 也不畫，這時的 `Page.captureScreenshot` 等到繼續才回答）。`DOM.resolveNode` 不管 `executionContextId`，一律在節點的 frame 的 main world 裡給物件（machopo 沒有 isolated world）。Elements 的搜尋（`performSearch`）沒有 XPath（machopo 沒有 `document.evaluate`），只有 selector、文字、標籤、屬性。樹的改動照每個 task（和回答 `DOM` 的命令、script 停住時）一批告訴 DevTools，照那時的 DOM：同一批裡插入又拿掉的節點不送，插入的節點帶著同一批裡之後的屬性，沒送子節點的節點的子節點數量在一批的最後送一次，值沒變的屬性設定照樣送（Chrome 在每個改動的當下送，略過值沒變的設定）。樹裡的 pseudo element 只有 machopo 有的 `::before`、`::after` 和 `::marker`；節點沒有 `adoptedStyleSheets`、slot 的 `distributedNodes`，`isScrollable` 照上一次的 layout（改動的事件送的節點沒有它），`getTopLayerElements` 是空的（machopo 沒有 top layer）。Network 面板的請求的發起者：parser 的沒有欄（machopo 的 tokenizer 不記），script 的 stack 在 DevTools 送了 `Network.setAttachDebugStack` 之後才有（DevTools 一連上就送），async 的呼叫鏈只接得上 `await`（V8 自己記的），`setTimeout`、事件的 callback 裡發的請求只看得到 callback 自己的 frame（renderer 沒有把計時器、事件告訴 inspector：Blink 用 `probe::AsyncTask` 接上排程它的 stack），script 的 stack 只留到那一輪 loop 的載入開始：script 加的 `loading=lazy` 的圖片捲到附近才載入時是 `other`（parser 建的照樣是 parser 的那一行），parser 建的元素的行號只在 `Network` 打開時記（打開之前 parser 建的、之後才載入的是 `other`），module 的 import 沒有 import 那一行的位置；沒有 `requestWillBeSentExtraInfo`、`responseReceivedExtraInfo`（DevTools 顯示 provisional 的 header），請求的 header 是 renderer 給的，不含 `net` 加上的（`Accept-Encoding`、`User-Agent`……）；時間沒有 SSL 那一段（包在連線裡）；傳輸大小的 head 是照 HTTP/1 的寫法估算的（HTTP/2 壓縮過的 header 比較小）；CORS 的 preflight 沒有自己那一列。寫在屬性裡的 event handler（`onclick="…"`）在 stack 裡沒有網址和名字（`(anonymous) @ VM13:27`，Chrome 是 `onclick @ (index):27`；行號是對的）：編譯它時沒給文件的網址和屬性的名字。`Page.getResourceContent` 給的子資源的內容是那個 session 的 `Network` 留著的 body：DevTools 連上之前就載入的給不出來（Sources 打開那個檔案是空的，要重新整理；Chrome 從快取拿），超過 `Network` 的上限被丟掉的也是。frame 的 `domainAndRegistry` 一律是空的（machopo 沒有 public suffix list，Chrome 對網域給 eTLD+1），`adFrameStatus` 一律是不是廣告。`Log` 只有載入的兩種訊息（Chrome 還有 CSP、mixed content、deprecation、violation……），`Log.startViolationsReport` 回答成功、不報任何東西。DevTools 的 screencast 是黑的（沒有 `Page.startScreencast`），可以關掉。只有 frame 的 main world 是 context（沒有 isolated world、worker）。停在斷點時頁面的其他 task（計時器、事件、輸入）都等著，畫面照樣更新（上面的 `Overlay`），compositor 的捲動照常。停住時才連上的 client，它的命令等頁面繼續之後才回答（Chrome 當場回答）。script 跑著時只有 `Debugger.pause`、斷點的設定這幾個命令打斷它（和 Chrome 一樣），`Runtime.evaluate` 等 script 跑完。session 打開的 domain（`Runtime.enable`、`Network.enable`、`Log.enable` 等）在分頁的 renderer 當掉重開、或換 script engine 之後，renderer 那一側不再是打開的：session 照樣接到新的 renderer，但 client 要再送一次（Chrome 把 session 的狀態交給新的 renderer）；只有 `Page.enable` 和 lifecycle 事件由 browser 再交給新的 renderer（machopodriver 靠它們等導覽）。`Network` 和 `Log` 這時是半開的：browser 記著，main frame 的導覽的 `requestWillBeSent`、`responseReceived` 和 browser 回答的命令的警告照送，子資源、文件的 `dataReceived` 和 `loadingFinished`、`Log` 的訊息停了。wasm 的文件沒有 inspector，分頁的 session 的命令都回答找不到方法。`Page.lifecycleEvent` 沒有 paint 的那幾個（`firstPaint`、`firstContentfulPaint`……：machopo 還沒有 paint timing，網頁的 `PerformancePaintTiming` 也沒有）；`networkIdle` 在 render thread 每個 task 之後數請求，Blink 在請求開始、結束時數，還把 task 的時間加進安靜的窗。`Page.frameStartedNavigating` 的 `navigationType` 只分 `differentDocument`、`reload`、`historyDifferentDocument`；`Page.navigate` 到只差 fragment 的網址也重新載入文件（Chrome 在同一份文件裡捲動、回答不帶 `loaderId`）。
- `--remote-debugging-port` 只聽 127.0.0.1（沒有 `--remote-debugging-address`），也不寫 Chrome 的 `DevToolsActivePort` 檔案（machopo 沒有 profile 的資料夾）：要從 stderr 的 `DevTools listening on …` 讀 port。沒有 `/json/protocol`，`/json/version` 沒有 Chrome 的 `V8-Version`（browser 不連結 V8，只知道它的 milestone）；`Target.setAutoAttach` 回答成功但不接上任何 target：browser 層級的不像 Chrome 接上現有和新開的分頁，也不停住等 debugger（`waitForDebuggerOnStart`），所以 Puppeteer 連不上 machopo（它還要 isolated world：`Page.addScriptToEvaluateOnNewDocument` 的 `worldName`、`Page.createIsolatedWorld`）。`/json/new` 給的不是網址時開 `about:blank`。
- pipe 是 stdin 和 stdout，不是 Chrome 的 fd 3 和 4：Playwright 的 `launch()`、Puppeteer 的 `pipe: true` 啟動不了 machopo（它們給 fd 3、4 和 Chrome 的一串開關），要連已經在跑的 machopo（`connectOverCDP`，經過 `--remote-debugging-port`）。
- 網頁的輸出（`console.log`、沒接住的例外、wasm guest 的 stdout 和 stderr）和 machopo 的 log 一樣都在 stderr（stdout 是 pipe 的），兩者混在一起。
- `console` 是 V8 內建的（和 Chrome 一樣，DevTools 的 Console 看到的是 Chrome 的樣子）。V8 的 inspector 留著最近 1000 則訊息和它們的引數（引數加起來估計超過 10 MB 時丟掉最舊的，但 V8 的估計不算陣列的元素：2000 則各帶 50000 個 double 的陣列，GC 之後還留著約 380 MB；和 Chrome 一樣），晚一點連上的 DevTools 也看得到，main frame 導覽時清掉（`Runtime.discardConsoleEntries` 也會）。印到終端機的是 inspector 交給 embedder 的文字：引數寫成字串、空格分開，不套用 `%s`、`%o` 等（Chrome 的 `--enable-logging=stderr` 也是），`group` 不縮排，`dir` 和 `table` 只寫值，`trace` 沒有 stack，等級不顯示。每一行是 `[console] 文字 (網址:行)`，沒有網址的程式（`eval` 的）不加括號（Chrome 寫成 `"文字", source: 網址 (行)`）；沒有引數的 `console.log()` 不印。`console` 只在 JS 裡：wasm 的 guest 用 WASI 的 stdout。
- `machopo --automation-pipe` 的分頁從 `about:blank` 開始，是 initial entry（第一次新增 entry 的導覽取代它，和 Chrome 的新分頁一樣）；只有這個模式有，視窗和 `--headless` 的分頁沒有 initial entry。
