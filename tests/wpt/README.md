# web-platform-tests

machopo runs [web-platform-tests](https://github.com/web-platform-tests/wpt) from an upstream checkout next to the repo, `../third_party/wpt`, at the commit `third_party.toml` pins (`python3 scripts/ci.py third-party` puts it there; see the root README). Nothing of WPT is copied into this repo, and machopo never changes the checkout: it is upstream's, byte for byte (cloned with `core.autocrlf=false`: html5lib's `.dat` files hold carriage returns, and with converted line endings most tree-construction tests ran together). This directory holds what is ours: which tests run, and what we expect of them. Chromium's counterpart is `third_party/blink/web_tests/`, with its `TestExpectations` and the baselines of `platform/*/external/wpt`, a tree that mirrors the tests; Firefox's and Servo's, the `.ini` files of their metadata trees, which machopo keeps too.

| File | What | Read by |
| --- | --- | --- |
| `include.txt` | the testharness.js tests, reftests and crashtests that run: files, or directories ending in `/` (all the tests in them, of every kind) | `python3 scripts/test.py wpt` |
| `wdspec-include.txt` | WPT's WebDriver tests (wdspec) that run: files or directories, from the checkout's root with its leading `/` | `python3 scripts/test.py wdspec` |
| `metadata/` | the expected results of the tests `include.txt` and `wdspec-include.txt` name, in wptrunner's format (`.ini`, at the test file's path, `dom/nodes/x.html` → `metadata/dom/nodes/x.html.ini`; none for a test that passes whole), and the tests that don't run (`disabled`, with the reason) | `test.py wpt` and `wdspec` |
| `wptrunner_machopo/` | machopo as a wptrunner product (a Python package, registered through the `wptrunner.products` entry point), the script that runs wptrunner with it, and the one that writes a run's results as the expectations | the same |
| `tree-construction-expectations.txt` | the html5lib tree-construction tests known to fail, grouped by cause; every `.dat` file in `html/syntax/parsing/resources/` runs | `cargo test -p html --test it tree_construction::` |

Where results differ between platforms, the `.ini` says so with a condition (`if os == "win": FAIL`, or the same for `disabled`): so far a measured time, which changes every run (that test is `disabled` on Windows), and reftests whose anti-aliased pixels round differently on macOS, where text rastered in a transparent layer and composited is compared with text drawn on white (`expected: FAIL` there, or `PASS` where the others fail; the `.ini` comments say which).

The runs fail on a list entry or an expectation that no longer fits the checkout: an include line naming a path that doesn't exist, an `.ini` for a test file that isn't there (`test.py` checks these before wptrunner starts, which would pass over them), and an include line that no test came from (after the run).

Until 2026-10-09 the testharness.js tests, and until 2026-10-10 the reftests (with their list, `reftest-include.txt`, and the failures and skips of `reftest-expectations.txt`), ran in a runner of machopo's own: the tests it skipped were listed in `testharness-skip.txt`, and each failing test's results were kept as Chromium's `-expected.txt` (a baseline) under `baselines/`, which the record below names. Since then wptrunner runs them, and both are in `metadata/` (`disabled`, and `expected:`), converted test by test, with each group's reason as `#` comments: the results stayed the same, but for two testharness.js tests that now reach testdriver and wait for `postMessage`, `fetch/api/basic/status.h2.any.js`, which passes (wptrunner starts wptserve's HTTP/2 server, which the old runner left off, and machopo speaks HTTP/2), a reftest that waits out the timeout (the old runner counted it as failing after 10 s), now `disabled`, and `css/CSS2/backgrounds/background-root-012a.xht` and `-013a.xht`, which left the list: their `interact` flag makes them manual tests in WPT's manifest, which wptrunner doesn't run.

### testharness.js tests, reftests and crashtests

`python3 scripts/test.py wpt` runs the testharness.js tests, reftests and crashtests that `include.txt` names, all in one run, with upstream's wptrunner against machopodriver and machopo, as wdspec's run (below) does, through the same product: wptrunner starts a machopodriver, which starts machopo (with the test fonts, `--test-fonts`) for each session, and runs each test in a new tab, as other browsers run them. Upstream's wptserve serves them at `http://web-platform.test:8000/` (a `.https.` test at `https://web-platform.test:8443/`): machopo maps WPT's domains to this machine and trusts WPT's root certificate, given by the product, so the hosts file stays as it is. Everything of wptserve's works (`.sub.`, `.headers`, `.py` handlers, pipes); `.any.js` tests run in every global their `META` names (window, workers...), and each `variant` is a test of its own, as the manifest has them. A line of the include list names a file or a directory; `test.py` hands wptrunner its path in the checkout, since a `.any.js` file isn't a test's URL. TEST paths (`test.py wpt dom/events/`) run what the list holds under them, or a path under one of its lines: a directory also holds tests the list leaves out, which have no expectations, so run whole they would all be unexpected; `--all` runs the paths whole.

- **Expected results** are wptrunner's `.ini` files in `metadata/`, with wdspec's: harness and subtest statuses (`expected: FAIL`), for the tests that don't pass whole. A test that doesn't run has `disabled:` with its reason in a line, its group's longer explanation as `#` comments above (wptrunner prints the reason when it skips one); a directory's is its `__dir__.ini`.
- **Known intermittent** results are wptrunner's lists: `expected: [OK, ERROR]` (or a condition's, `if os == "win": [PASS, FAIL]`) expects the first and takes the others too, as upstream's and Firefox's metadata have them. A test is marked so once it has been looked into and can't be fixed for now (it fails on `main` too, say): `#` comments above say what was found, or where the cause is looked for; `test.py` refuses to run an `.ini` with a list and no comment, and names at the end of a run the tests that took one of their other statuses. A harness status that fails every subtest (`ERROR`) needs each subtest's list as well (`[PASS, FAIL]`). Once fixed, the lists go.
- `MACHOPO_UPDATE_EXPECTATIONS=1 python3 scripts/test.py wpt` writes each test's results as its expectations with wptrunner's own metadata update (`wptrunner_machopo/update.py`), which keeps what it doesn't touch: conditions on other platforms, `disabled`, comments, and a known intermittent list the result is one of (a result outside it replaces the list with that status); review the diff. TEST arguments (paths in the checkout, without the leading `/` under Git Bash) run only those.
- **Reftests** are rendered at 800×600 and compared with their references, chains and `fuzzy` as wptrunner has them; a failing one's screenshots, expected or not, go to `target/wpt-results/screenshots/` at the test's path (`-actual.png`, `-expected.png` for the reference the failing comparison was with, `-diff.png` with the differing pixels in red). **Crashtests** pass if the page loads (and takes off `test-wait`) without the renderer going.
- **Timeouts** are wptrunner's (10 s, 60 s for `timeout=long`); `MACHOPO_WPT_TIMEOUT_MULTIPLIER=N` makes them N times as long. It stretches the harness's timers (`step_timeout`) too, but not wptserve's delays (`pipe=trickle`), so the tests that race one against the other fail with it.
- **Speed**: each test is a group of its own that the processes take from one queue (`--fully-parallel`), the browser not restarted between them; the manifest is updated only when the checkout's commit changes (it lives in `target/wptrunner/`, with a stamp); processes default to 4 per CPU, at most 32 (`--processes N`). Most of them wait, on a test's timeout or the next frame.

The logs, the wptreport and the include file handed to wptrunner go to `target/wpt-results/`. Python writes no bytecode, and the run fails if anything was written into the checkout. wptserve's ports are fixed (8000, 8443, 8444...): one run at a time, not with `wdspec` or `reftest`.

To try a directory out before listing it, run `test.py wpt --all <directory>` (without `MACHOPO_UPDATE_EXPECTATIONS`, which would write expectations for tests the list doesn't run). To add one, add its line to `include.txt`, run `test.py wpt <directory>` with `MACHOPO_UPDATE_EXPECTATIONS=1`, look at what fails and why, write `disabled` with the reason into the `.ini` of what can't run (one that times out, say), and run again.

### WebDriver tests (wdspec)

`python3 scripts/test.py wdspec` runs WPT's WebDriver tests (`webdriver/tests/classic/`, written with pytest) that `wdspec-include.txt` names, against machopodriver and machopo, with upstream's wptrunner, as other browsers run them: `wptrunner_machopo/` is machopo's product (as Ladybird's: wptrunner starts `machopodriver`, which starts a machopo for each session), registered through the entry point upstream documents (`tools/wptrunner/docs/plugins.rst`), so the checkout stays as it is. The command builds `machopo` and `machopodriver`, makes a venv under `target/wptrunner/` the first time (downloading wptrunner's, pytest's and the manifest's packages: it needs the network once) and installs a copy of the product into it, then runs `python -m wptrunner_machopo.run`. That calls wptrunner directly, as Chromium's blinkpy does, rather than `wpt run`, which wants the system's hosts file to list WPT's domains for any product but its built-in ones: machopo resolves them itself (the product passes machopo `--host-resolver-rules` and WPT's root certificate through the driver), and wptserve binds to `127.0.0.1`. WPT's manifest goes to `target/wptrunner/`, shared with `wpt` (built the first time, about a minute, and again when the checkout's commit changes), the raw log and the wptreport to `target/wdspec-results/`; the run takes about a minute, the tests in 32 processes (most of them wait out user prompts' timeouts); Python writes no bytecode (`PYTHONDONTWRITEBYTECODE`), and the run fails if anything was written into the checkout. wptserve's ports are fixed, as for `wpt`: not at the same time.

- **Expected results** are wptrunner's metadata in `metadata/` (a test without a file passes whole), as for the testharness.js tests.
- `MACHOPO_UPDATE_EXPECTATIONS=1 python3 scripts/test.py wdspec` writes each test's results as its expectations; review the diff. TEST arguments (paths in the checkout, without the leading `/` under Git Bash, which rewrites it) run only what `wdspec-include.txt` holds under them; `--all` runs them whole.

wptrunner follows a test's chain of references whether or not the references are in `include.txt`; a reference gets a line only to also run as a test of its own.

The CSS2 tests are XHTML (`.xht`). We parse them with the HTML parser, after dropping CDATA section markers around `<style>` contents as an XML parser would (see `crates/renderer/src/document.rs`).

## Updating

1. Pick a WPT commit and put it in `third_party.toml`. `python3 scripts/ci.py third-party` (and every `test.py` command, first) fetches it into `../third_party/wpt` and checks it out.
2. Run the test targets above. Fix the lists and expectations the runs complain about (tests removed or renamed upstream).
3. Rewrite the expectations with `MACHOPO_UPDATE_EXPECTATIONS=1` and review the diff, as for any change. Every new failure, here or in the reftests and tree-construction tests, needs a look: a bug on our side gets fixed; a test that is wrong upstream, or an html5ever limitation, gets its expectation with the reason. `MACHOPO_PRINT_FAILURES=1` prints every failing tree-construction id in `tree-construction-expectations.txt` format (see "選項和環境變數" in the root README).
4. Update the commit above.

A test that is wrong upstream is never fixed in the checkout: draft the report for upstream locally, for review, and expect or skip the test here until upstream changes.
